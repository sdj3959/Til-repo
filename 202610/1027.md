# 1027 운영 자동화/AI 워크플로우 심화 (51/N)
## Dead Letter Queue·Poison Message·Retry Budget·Quarantine·Safe Redrive와 실패 작업 재처리 시스템

**시리즈 날짜: 2026년 10월 27일**

---

## 1. 자동 복구가 실패한 작업은 어떻게 처리할까?

### ✅ 1. 이전 내용과의 연결

1022에서는 장기 실행 AI Workflow의 내구성을 설계했다.

1023에서는 실제 장애를 발생시켜 복구 기능을 검증하는 방법을 다뤘다.

이번에는 한 단계 더 나아가 다음 상황을 다룬다.

**정상적인 재시도를 모두 수행했지만 작업이 여전히 실패하거나, 다시 실행해도 안전한지 판단할 수 없다면 어떻게 해야 할까?**

### ✅ 2. 일반적인 Workflow

```text
Workflow 생성
      ↓
Worker 실행
      ↓
외부 API 호출
      ↓
결과 검증
      ↓
Checkpoint 저장
      ↓
SUCCEEDED
```

### ✅ 3. 실패가 발생했다면?

```text
Worker 실행
      ↓
외부 API Timeout
      ↓
Retry 1
      ↓
Retry 2
      ↓
Retry 3
      ↓
여전히 실패
```

이 상태에서 계속 재시도하면 외부 서비스에 불필요한 부하를 주거나 API 비용을 증가시킬 수 있다.

### ✅ 4. 실패 작업을 삭제하면?

```text
작업 실패
      ↓
Job 삭제
      ↓
고객 업무 누락
      ↓
원인 추적 불가
```

가 발생할 수 있다.

### ✅ 5. 모든 실패를 관리자에게 전달하면?

일시적인 네트워크 오류까지 모두 수동 검토해야 한다면 자동화의 의미가 줄어든다.

### ✅ 6. 필요한 구조

```text
Workflow Execution
        ↓
Failure Detected
        ↓
Failure Classification
        ↓
   ┌───────────────┬────────────────────┐
   │               │                    │
Retryable       Non-retryable       Outcome Unknown
   │               │                    │
Retry Policy    Quarantine         Reconciliation
   │               │                    │
   └───────────────┴────────────────────┘
                   ↓
             Safe Recovery
                   ↓
             Final Verification
```

### ✅ 7. 이번 편의 핵심 원칙

**실패한 작업을 보존하는 것보다 중요한 것은, 해당 작업을 다시 실행해도 안전한지 판단하는 것이다.**

## 2. Dead Letter Queue란?

### ✅ 8. DLQ의 정의

Dead Letter Queue는 정상적인 처리 경로에서 성공적으로 처리되지 못한 메시지를 별도로 보관하는 Queue다.

### ✅ 9. 기본 구조

```text
Producer
    ↓
Main Queue
    ↓
Worker
    ↓
Execution
    ├── Success
    │      ↓
    │   Complete
    │
    └── Failure
           ↓
         Retry
           ↓
      Retry Exhausted
           ↓
           DLQ
```

### ✅ 10. DLQ의 목적

```text
실패 작업 보존

정상 작업과 분리

원인 조사

문제 영향 범위 확인

재처리 대상 관리

운영자 개입
```

이다.

### ✅ 11. DLQ가 없을 때

하나의 작업이 계속 실패하면 정상 작업 처리에 영향을 줄 수 있다.

예:

```text
Job A
계속 실패

Job B
정상

Job C
정상
```

잘못된 재시도 구조에서는 Job A가 Worker와 API 호출 자원을 계속 점유할 수 있다.

### ✅ 12. DLQ가 있을 때

```text
Main Queue

Job B
Job C

Dead Letter Queue

Job A
```

실패한 Job A를 정상 처리 경로에서 분리할 수 있다.

### ✅ 13. DLQ가 문제를 해결하는 것은 아니다

DLQ는 작업을 격리하는 수단이다.

실패 원인을 자동으로 수정하거나 외부 Side Effect의 중복을 방지하지 않는다.

### ✅ 14. DLQ와 일반 실패 로그의 차이

실패 로그:

```text
어떤 오류가 발생했는가?
```

DLQ:

```text
어떤 메시지가 정상적으로 처리되지 못했는가?
```

를 관리한다.

### ✅ 15. DLQ와 업무 상태도 다르다

Queue 메시지가 DLQ에 들어갔다고 실제 고객 주문이 취소된 것은 아니다.

예:

```text
Queue Message
DLQ

Business Order
APPLICATION_RECEIVED
```

두 상태는 서로 구분해야 한다.

## 3. Poison Message

### ✅ 16. Poison Message란?

반복해서 처리해도 계속 실패를 일으키는 메시지를 의미한다.

### ✅ 17. 예시 ① — 잘못된 데이터

```json
{
  "orderId": null,
  "action": "SEND_NOTIFICATION"
}
```

필수 주문 ID가 없다면 계속 재시도해도 성공하기 어렵다.

### ✅ 18. 예시 ② — 지원되지 않는 상태

```json
{
  "orderId": "12345",
  "targetStatus": "UNKNOWN_STATUS"
}
```

서버가 해당 상태를 지원하지 않는다면 입력 자체를 수정해야 한다.

### ✅ 19. 예시 ③ — 오래된 Schema

```text
Job 생성 당시
Payload Version 1

현재 Worker
Payload Version 3
```

이전 메시지를 해석할 수 없어 실패할 수 있다.

### ✅ 20. 예시 ④ — 잘못된 LLM Output

```json
{
  "action": "UPDATE_ORDER",
  "targetStatus": "INVALID_VALUE"
}
```

AI가 생성한 구조화된 출력이 업무 Schema와 일치하지 않는 경우다.

### ✅ 21. 예시 ⑤ — 외부 정책 충돌

고객 알림 발송 작업이 생성된 이후 해당 템플릿이 더 이상 승인되지 않은 상태일 수 있다.

### ✅ 22. Poison Message와 일시적인 장애의 차이

일시적인 장애:

```text
외부 API 일시 중단
```

Poison Message:

```text
작업 데이터 자체가 유효하지 않음
```

### ✅ 23. 구분이 중요한 이유

일시적인 장애는 시간이 지나면 해결될 수 있다.

반면 잘못된 업무 데이터는 같은 내용을 반복 실행해도 해결되지 않을 가능성이 높다.

## 4. Failure Classification

### ✅ 24. 모든 실패를 동일하게 처리하지 않는다

실패 원인을 다음과 같이 분류할 수 있다.

```text
TRANSIENT

RATE_LIMITED

VALIDATION_ERROR

BUSINESS_CONFLICT

AUTHORIZATION_ERROR

DEPENDENCY_UNAVAILABLE

OUTCOME_UNKNOWN

POISON_MESSAGE
```

### ✅ 25. TRANSIENT

일시적인 장애다.

예:

```text
Connection Reset

Temporary Network Failure

일시적인 HTTP 503
```

### ✅ 26. RATE_LIMITED

외부 서비스에서 허용된 호출량을 초과한 경우다.

예:

```text
HTTP 429
```

`Retry-After`가 제공된다면 해당 정책을 고려한다.

### ✅ 27. VALIDATION_ERROR

입력 데이터 또는 Output Schema가 잘못된 경우다.

수정 없이 반복 호출하면 성공하기 어렵다.

### ✅ 28. BUSINESS_CONFLICT

현재 업무 상태와 요청한 작업이 충돌하는 경우다.

예:

```text
이미 취소된 주문을
신청서 발송 상태로 변경
```

### ✅ 29. AUTHORIZATION_ERROR

현재 요청자나 Agent에게 해당 작업 권한이 없는 경우다.

권한 거부를 자동으로 우회해서는 안 된다.

### ✅ 30. DEPENDENCY_UNAVAILABLE

DB, 외부 API, LLM Provider 등의 의존 서비스가 장애 상태인 경우다.

### ✅ 31. OUTCOME_UNKNOWN

외부 작업이 실제로 성공했는지 실패했는지 확인할 수 없는 상태다.

### ✅ 32. POISON_MESSAGE

입력이나 메시지 구조 자체에 문제가 있어 정상적인 처리가 불가능한 상태다.

### ✅ 33. 권장 처리 정책

| 오류 유형 | 기본 처리 |
|---|---|
| TRANSIENT | 제한된 재시도 |
| RATE_LIMITED | 제한 정책에 따른 지연 |
| VALIDATION_ERROR | Quarantine |
| BUSINESS_CONFLICT | 현재 업무 상태 확인 |
| AUTHORIZATION_ERROR | 실행 차단 및 조사 |
| DEPENDENCY_UNAVAILABLE | 의존 서비스 회복 대기 |
| OUTCOME_UNKNOWN | Reconciliation |
| POISON_MESSAGE | Quarantine |

### ✅ 34. 중요한 예외

같은 HTTP 500이라도 외부 Write 요청 이후 발생했다면 실제 작업이 처리됐을 가능성이 있다.

따라서 HTTP 상태 코드만으로 재시도 가능 여부를 확정하지 않는다.

## 5. Retry Budget — 얼마나 재시도할 것인가?

### ✅ 35. Retry Budget이란?

자동 재시도에 허용되는 횟수·시간·비용 등을 제한하는 정책이다.

### ✅ 36. 단순 횟수 제한

예:

```text
Initial Attempt
1회

Retry
최대 3회

총 실행
최대 4회
```

### ✅ 37. Backoff

재시도 사이에 대기 시간을 둔다.

```text
첫 실패
2초

두 번째 실패
4초

세 번째 실패
8초
```

위 수치는 설명용이다.

### ✅ 38. Exponential Backoff

재시도할 때마다 대기 시간을 증가시키는 방법이다.

### ✅ 39. Jitter

여러 Worker가 동시에 재시도하지 않도록 지연 시간에 무작위성을 추가한다.

### ✅ 40. 횟수 외에도 제한이 필요하다

```text
Max Attempts

Maximum Elapsed Time

Maximum Cost

Provider Rate Limit

Workflow Deadline
```

등을 검토한다.

### ✅ 41. LLM API 비용

예:

```text
LLM 호출 1회
실패

↓

Retry 3회

↓

동일한 업무의 호출 비용 증가
```

문제가 발생할 수 있다.

### ✅ 42. Retry Amplification

상위 Workflow와 하위 Tool이 모두 자체 Retry를 수행하면 예상보다 훨씬 많은 요청이 발생할 수 있다.

예:

```text
Workflow Retry
3회

Tool Retry
3회
```

두 계층이 각각 전체 호출을 반복하면 최대 9번의 시도가 발생할 수도 있다.

### ✅ 43. Retry Ownership

어느 계층이 재시도를 책임지는지 명확히 정한다.

```text
Workflow Layer

또는

Tool Adapter Layer
```

업무 작업 단위의 재시도와 HTTP 연결 수준의 재시도는 구분할 수 있지만 전체 예산을 함께 관리해야 한다.

### ✅ 44. Retry Budget 초과

```text
Retry Exhausted
       ↓
Failure Classification
       ↓
Quarantine / Reconciliation / Manual Review
```

로 전환한다.

### ✅ 45. 중요한 원칙

**재시도 횟수를 늘리는 것은 원인을 해결하는 방법이 아니다.**

## 6. Quarantine — 실패 작업 격리

### ✅ 46. Quarantine이란?

문제가 있거나 안전한 실행 여부가 확인되지 않은 작업을 일반적인 실행 경로에서 분리하는 상태 또는 저장 영역이다.

### ✅ 47. DLQ와 Quarantine의 차이

DLQ는 주로 메시지 전달·처리 실패를 관리한다.

Quarantine은 업무적으로 해당 작업이 다시 실행돼도 되는지 검토하는 상태를 의미한다.

### ✅ 48. 두 구조를 함께 사용할 수 있다

```text
Main Queue
      ↓
Worker
      ↓
Failure
      ↓
DLQ
      ↓
Failure Inspector
      ↓
Business Quarantine
      ↓
Review
```

### ✅ 49. PostgreSQL만 사용한다면?

별도의 Queue 서비스 없이 DB의 Workflow 상태로 Quarantine을 구현할 수 있다.

```text
Workflow Status
QUARANTINED
```

### ✅ 50. Quarantine 상태의 의미

```text
자동 실행 금지

오류 원인 보존

운영자 검토 가능

재처리 정책 필요
```

### ✅ 51. Quarantine은 최종 실패와 다르다

작업이 다시 실행 가능할 수도 있다.

다만 아직 실행을 허용하지 않는 상태다.

### ✅ 52. Quarantine 상태에서 금지할 것

```text
자동 재시도

자동 외부 발송

관리자 승인 없는 실행

작업 Payload 임의 수정
```

### ✅ 53. Quarantine 해제 조건

```text
오류 원인 확인

영향 범위 파악

기존 Side Effect 확인

현재 권한 검증

현재 업무 상태 확인

재처리 방식 결정
```

등이다.

## 7. Safe Redrive — 실패 작업을 다시 실행하기

### ✅ 54. Redrive란?

처리하지 못한 메시지나 작업을 다시 정상적인 처리 경로로 이동시키는 것이다.

### ✅ 55. 단순한 Redrive

```text
DLQ
 ↓
Main Queue
 ↓
Worker
```

### ✅ 56. 안전한 Redrive

```text
Quarantined Workflow
        ↓
Failure Analysis
        ↓
Current State Check
        ↓
External Outcome Check
        ↓
Permission Validation
        ↓
Dry-run
        ↓
Human Approval if Required
        ↓
Controlled Redrive
        ↓
Result Verification
```

### ✅ 57. 왜 단순 재실행이 위험할까?

예를 들어 외부 알림 발송이 실제로 성공했지만 응답만 유실된 경우가 있다.

이때 재실행하면 같은 고객에게 두 번 발송될 수 있다.

### ✅ 58. 재처리 전 질문

```text
원래 작업이 실제로 실행됐는가?

외부 Side Effect가 존재하는가?

현재 업무 조건이 유효한가?

같은 메시지를 보내도 되는가?

승인이 여전히 유효한가?

사용자의 요청이 취소되지 않았는가?

기존 Idempotency Key를 재사용해야 하는가?
```

### ✅ 59. Redrive는 Retry 버튼 하나로 끝나서는 안 된다

특히 주문·발송·개인정보 관련 작업에서는 검토 과정이 필요하다.

### ✅ 60. Dry-run

실제 변경 없이 어떤 작업이 실행될지 미리 보여준다.

### ✅ 61. Redrive Preview

```text
Workflow:
notification-send-123

Current State:
QUARANTINED

Failure:
PROVIDER_TIMEOUT

Existing External Operation:
OUTCOME_UNKNOWN

Recommended Action:
RECONCILIATION_REQUIRED

Automatic Redrive:
BLOCKED
```

### ✅ 62. 관리자 판단

외부 발송 여부를 확인할 수 없다면 자동 Redrive를 허용하지 않고 별도 확인 절차로 전환한다.

## 8. 재처리할 때 새로운 Workflow를 만들어야 할까?

### ✅ 63. 재시도와 새로운 업무 요청을 구분한다

기존 작업을 복구하는 것과 새로운 업무를 생성하는 것은 다르다.

### ✅ 64. 동일 작업 재시도

```text
Workflow ID
123

Logical Operation
notification-send-456

Idempotency Key
notification-send-456
```

를 유지한다.

### ✅ 65. 새로운 작업

관리자가 새로운 발송을 명시적으로 요청한 경우 별도의 논리적 Operation을 생성할 수 있다.

### ✅ 66. 같은 작업인데 Idempotency Key를 바꾸면?

외부 Provider가 해당 작업을 새로운 요청으로 처리할 수 있다.

따라서 기존 논리적 작업의 재시도라면 안정적인 Key를 유지해야 한다.

### ✅ 67. Redrive Generation

재처리 이력을 구분하는 별도 번호를 둘 수 있다.

```text
Workflow ID
123

Redrive Generation
1
```

### ✅ 68. Generation 증가

```text
기존 작업
Generation 0

수동 재처리
Generation 1
```

처럼 관리한다.

### ✅ 69. 주의

Redrive Generation이 증가했다고 외부 Idempotency Key를 자동으로 바꿔서는 안 된다.

두 값은 역할이 다르다.

### ✅ 70. Retry Count 초기화

수동 재처리할 때 전체 재시도 이력을 삭제하지 않는다.

```text
Total Attempts

Attempts In Current Generation

Redrive Count
```

를 구분한다.

## 9. PostgreSQL 기반 최소 Quarantine 설계

### ✅ 71. 추천 구조


## 10. Quarantine 상태 변경의 원자성

### ✅ 81. 위험한 구현

```text

↓
```

### ✅ 82. 상태 불일치 방지

Workflow 상태 변경과 Quarantine 기록을 하나의 DB Transaction에서 처리한다.

### ✅ 83. 권장 흐름

```text
BEGIN TRANSACTION

현재 Workflow Lock

Lease Owner / Epoch 검증

실패 원인 확인

Workflow → QUARANTINED

Quarantine Record UPSERT

Audit Event 기록

COMMIT
```

### ✅ 84. Lease 검증이 중요하다

이미 실행권을 잃은 오래된 Worker가 현재 Workflow를 Quarantine으로 변경해서는 안 된다.

### ✅ 85. 예시 조건

```sql
UPDATE agent_workflow_runs
SET
  status = 'QUARANTINED',

  lease_owner = NULL,

  lease_until = NULL,

  state_version = state_version + 1,

  updated_at = NOW()

WHERE id = $1

  AND status = 'RUNNING'

  AND lease_owner = $2

  AND lease_epoch = $3

  AND lease_until > NOW()

RETURNING id;
```

### ✅ 86. 업데이트가 0건이라면?

해당 Worker가 더 이상 실행권을 갖고 있지 않거나 상태가 변경됐을 수 있다.

### ✅ 87. 임의로 다시 업데이트하지 않는다

정식 Recovery Worker가 최신 상태를 조회해 판단하도록 한다.

### ✅ 88. 중요한 원칙

**Workflow 상태·Quarantine 기록·Audit가 서로 다른 사실을 나타내지 않도록 Transaction 경계를 설계한다.**

## 11. TypeScript Failure Classifier

### ✅ 89. 실패 분류는 LLM에게만 맡기지 않는다

HTTP 응답, Error Code, 작업 유형, 외부 Side Effect 여부 등 검증 가능한 값으로 우선 분류한다.

### ✅ 90. 실패 입력 구조

```typescript
type FailureCode =
  | 'NETWORK_TIMEOUT'
  | 'RATE_LIMITED'
  | 'VALIDATION_ERROR'
  | 'BUSINESS_CONFLICT'
  | 'AUTHORIZATION_DENIED'
  | 'DEPENDENCY_UNAVAILABLE';

type ExternalOutcome =
  | 'NOT_STARTED'
  | 'CONFIRMED'
  | 'UNKNOWN';

interface FailureContext {
  code: FailureCode;

  attempts: number;
  maxAttempts: number;

  hasExternalSideEffect: boolean;
  externalOutcome: ExternalOutcome;
}
```

### ✅ 91. Recovery Decision

```typescript
type FailureDecision =
  | 'RETRY_WAIT'
  | 'QUARANTINE'
  | 'RECONCILE'
  | 'MANUAL_REVIEW'
  | 'SECURITY_HOLD';
```

### ✅ 92. 분류 함수 예시

```typescript
function classifyFailure(
  context: FailureContext,
): FailureDecision {
  if (
    context.hasExternalSideEffect &&
    context.externalOutcome === 'UNKNOWN'
  ) {
    return 'RECONCILE';
  }

  if (context.code === 'AUTHORIZATION_DENIED') {
    return 'SECURITY_HOLD';
  }

  if (context.code === 'BUSINESS_CONFLICT') {
    return 'MANUAL_REVIEW';
  }

  if (context.code === 'VALIDATION_ERROR') {
    return 'QUARANTINE';
  }

  if (context.attempts >= context.maxAttempts) {
    return 'QUARANTINE';
  }

  if (
    context.code === 'NETWORK_TIMEOUT' ||
    context.code === 'RATE_LIMITED' ||
    context.code === 'DEPENDENCY_UNAVAILABLE'
  ) {
    return 'RETRY_WAIT';
  }

  return 'MANUAL_REVIEW';
}
```

### ✅ 93. 이 함수의 역할

실패 처리의 기본 방향을 결정한다.

### ✅ 94. 실제 구현에서 추가할 항목

```text
현재 Workflow 상태

Operation Ledger

Provider Response

Retry Deadline

Business Priority

Permission Policy

Approval

Circuit Breaker

Provider Retry-After
```

### ✅ 95. 중요한 한계

`externalOutcome = NOT_STARTED`가 실제로 외부 요청 미실행을 증명하는지는 별도 검증이 필요하다.

DB 기록이 누락된 상황에서는 외부 Write가 시작되지 않았다고 단정할 수 없다.

### ✅ 96. 기본값은 보수적으로

외부 Side Effect의 성공 여부가 불확실하다면 자동 재처리보다 Reconciliation을 우선한다.

## 16. AWS SQS Dead Letter Queue

### ✅ 127. SQS 구조

```text
Application
     ↓
SQS Main Queue
     ↓
Consumer
     ↓
Processing
     ↓
Failure
     ↓
DLQ
```

### ✅ 128. Redrive Policy

SQS는 `maxReceiveCount`와 DLQ를 이용해 반복 처리되지 못한 메시지를 별도 Queue로 이동시킬 수 있다.

### ✅ 129. 예시

```text
maxReceiveCount
5
```

로 설정한 경우 정해진 수신 횟수를 초과해도 처리되지 않은 메시지가 DLQ로 이동한다.

### ✅ 130. 중요한 구분

SQS의 `maxReceiveCount`는 메시지 수신 횟수에 관한 설정이다.

애플리케이션 내부의 HTTP Retry 횟수와 동일한 개념이 아니다.

### ✅ 131. Visibility Timeout

Consumer가 메시지를 처리하는 동안 일정 기간 다른 Consumer에게 보이지 않게 하는 기능이다.

### ✅ 132. Visibility Timeout이 만료되면?

메시지가 다시 전달될 수 있다.

따라서 동일 메시지의 중복 처리를 고려해야 한다.

### ✅ 133. SQS는 업무 Exactly-once를 보장하지 않는다

특히 외부 API 발송과 DB 업데이트까지 포함한 정확히 한 번 실행은 별도 멱등성 설계가 필요하다.

### ✅ 134. FIFO Queue와 DLQ

FIFO Queue에 DLQ를 연결하면 실패 메시지가 정상 처리 순서에서 분리되므로 엄격한 업무 순서가 깨질 수 있다.

### ✅ 135. 순서가 중요한 업무

예:

```text
주문 생성

↓

주문 승인

↓

주문 취소
```

같은 상태 전이는 과거 메시지를 나중에 재처리할 때 현재 상태와 충돌할 수 있다.

### ✅ 136. 메시지 보존기간

SQS DLQ는 메시지 보존기간을 고려해야 한다.

특히 Standard Queue에서는 원래 메시지의 최초 Enqueue 시점이 보존기간 계산에 영향을 준다.

### ✅ 137. Redrive 시 메시지 수정 제한

SQS의 기본 DLQ Redrive 기능은 메시지 내용을 수정하거나 선별적으로 변환하면서 이동시키는 기능을 제공하지 않는다.

### ✅ 138. Payload 수정이 필요하다면?

별도의 검증된 Application Recovery Process를 사용해야 한다.

### ✅ 139. 현재 도입 판단

이미 SQS를 사용하고 있다면 공식 DLQ 기능을 활용한다.

하지만 PostgreSQL 기반 Worker만 사용하는 작은 시스템에 DLQ를 도입하려는 이유로 SQS를 새로 추가할 필요는 없다.

## 17. BullMQ Failed Jobs

### ✅ 140. BullMQ를 사용하는 경우

BullMQ는 실패한 Job의 보관과 자동 재시도 기능을 제공한다.

### ✅ 141. 재시도 설정 예시

```typescript
await queue.add(
  'generate-report',

  {
    workflowId: 'workflow-123',
  },

  {
    attempts: 3,

    backoff: {
      type: 'exponential',
      delay: 1000,
    },
  },
);
```

### ✅ 142. 실패한 Job

정해진 시도를 모두 소진하면 `failed` 상태에 남을 수 있다.

단 실패 Job 자동 제거 설정을 사용하는 경우 보존 여부가 달라진다.

### ✅ 143. UnrecoverableError

재시도해도 해결하기 어려운 오류는 `UnrecoverableError`를 사용해 일반 Retry를 중단할 수 있다.

### ✅ 144. Manual Retry

BullMQ의 `Job.retry()`를 이용해 실패한 Job을 다시 대기 상태로 옮길 수 있다.

### ✅ 145. 주의

`Job.retry()` 호출 전에 실제 업무 상태와 외부 Side Effect를 검증해야 한다.

### ✅ 146. BullMQ의 Failed Set과 업무 Quarantine은 다르다

```text
BullMQ Failed Job
작업 처리 실패 상태

Business Quarantine
재실행 안전성 검토 상태
```

이다.

### ✅ 147. 재시도 횟수 초기화 주의

수동 재시도 과정에서 Attempt Counter를 초기화하면 기존 실패 이력을 잃거나 Retry Budget을 우회할 수 있다.

### ✅ 148. 현재 추천

BullMQ를 사용하더라도 주문·발송 업무의 최종 Source of Truth는 PostgreSQL의 Workflow와 Operation Ledger에 유지한다.

## 📌 요약

1022에서는 AI Workflow의 Durable Execution을 설계했다.

```text
Workflow
    ↓
Checkpoint
    ↓
Lease
    ↓
Crash Recovery
    ↓
Resume
```

1023에서는 이러한 복구 기능이 실제 장애 상황에서도 안전하게 작동하는지 검증했다.

1027에서는 더 근본적인 질문을 다뤘다.

**복구와 재시도를 반복했는데도 실패한 작업은 어떻게 관리해야 하는가?**

기존의 단순한 구조는 다음과 같다.

```text
작업 실행
    ↓
실패
    ↓
Retry
    ↓
실패
    ↓
Retry
    ↓
실패
```

반면 이번 편에서 설계한 구조는 다음과 같다.

```text
Workflow Execution
         ↓
Failure Detection
         ↓
Failure Classification
         ↓
Retry Budget
         ↓
    ┌─────────────┬────────────────┐
    │             │                │
Retryable    Non-retryable   Outcome Unknown
    │             │                │
Backoff       Quarantine     Reconciliation
    │             │                │
    └─────────────┴────────────────┘
                  ↓
           Operator Review
                  ↓
            Safe Redrive
                  ↓
           Result Verification
                  ↓
                Audit
```

이번 편에서 중요한 원칙은 다섯 가지다.

**첫 번째 — 실패한 작업을 무조건 삭제하지 않는다.**

실패 작업은 고객 업무 누락이나 시스템 장애의 근거가 될 수 있다.

**두 번째 — 재시도 횟수에 제한을 둔다.**

무한 Retry는 외부 서비스에 부하를 주고 API 비용을 증가시킬 수 있다.

**세 번째 — Poison Message를 격리한다.**

입력이 잘못된 작업은 반복 실행보다 원인 수정이 우선이다.

**네 번째 — 외부 실행 결과가 불명확하다면 재처리하지 않는다.**

```text
External API Timeout
        ↓
OUTCOME_UNKNOWN
        ↓
Reconciliation
```

을 우선한다.

**다섯 번째 — Redrive는 새로운 업무 승인과 검증이 필요한 작업일 수 있다.**

특히 고객 발송, 주문 변경, 외부 데이터 변경은 안전한 재처리 절차가 필요하다.

현재 프로젝트에서는 다음 순서로 시작하는 것이 현실적이다.

```text
1. 기존 Retry 분석

2. Failure Classification

3. Retry Budget

4. OUTCOME_UNKNOWN 처리

5. Quarantine State

6. External Operation Ledger 연결

7. Safe Redrive Preview

8. 관리자 수동 재처리

9. Audit / Monitoring

10. Canary / Batch Redrive
```

현재 PostgreSQL을 이미 사용하고 있다면 별도의 SQS나 Redis를 도입하지 않고도 상당 부분 구현할 수 있다.

중요한 것은 Queue 기술 자체가 아니라 **실패한 업무를 안전하게 관리할 수 있는 운영 정책**이다.

예를 들어 고객 알림이 발송됐는지 확인할 수 없는데 자동 재전송한다면 이는 정상적인 복구가 아니다.

반대로 결과를 확인할 수 없다는 이유로 업무를 조용히 삭제해도 문제가 된다.

따라서 적절한 상태를 남긴다.

```text
OUTCOME_UNKNOWN

RECONCILIATION_REQUIRED

QUARANTINED

MANUAL_REVIEW
```

그리고 실제 처리 결과가 확인될 때까지 추적한다.

**최종적으로 기억해야 할 원칙은 다음과 같다.**

> 자동화 시스템의 완성도는 정상적인 작업을 얼마나 빨리 처리하는지만으로 결정되지 않는다. 실패한 작업을 잃어버리지 않고, 반복 실행으로 피해를 키우지 않으며, 필요한 경우 사람의 판단을 거쳐 안전하게 복구할 수 있는지가 중요하다.
