# 1022 운영 자동화/AI 워크플로우 심화 (46/N)
## Durable Agent Execution·Checkpoint·Task Lease·Crash Recovery·Human-in-the-Loop Resume와 장기 실행 AI 워크플로우

**시리즈 날짜: 2026년 10월 22일**

## 1. AI 작업이 중간에 멈추면 어떻게 해야 할까?

### ✅ 1. 1021과의 연결

1021에서는 여러 AI Agent가 작업을 위임할 때 신원과 권한을 관리하는 방법을 다뤘다.

```text
Authenticated User
        ↓
Supervisor Agent
        ↓
Delegation Policy
        ↓
Scoped Grant
        ↓
Worker Agent
        ↓
Tool Gateway
        ↓
Authorization
        ↓
Execution
        ↓
Audit
```

1022에서는 새로운 문제를 다룬다.

**AI Agent가 작업을 수행하다 서버가 재시작되거나, 외부 API가 응답하지 않거나, 관리자 승인을 기다려야 하는 상황에서 어떻게 안전하게 작업을 이어갈 것인가?**

### ✅ 2. 일반적인 AI 작업 흐름

예를 들어 관리자에게 주문 통계 분석을 요청받았다고 하자.

```text
관리자 요청
      ↓
주문 데이터 조회
      ↓
통계 계산
      ↓
LLM 분석
      ↓
보고서 생성
      ↓
관리자 확인
      ↓
Notion 업로드
```

각 단계가 몇 초 안에 끝날 수도 있지만 외부 API 장애나 승인 대기 때문에 몇 분에서 며칠이 걸릴 수도 있다.

### ✅ 3. 가장 단순한 구현

```typescript
async function runAgent() {
  const orders = await getOrders();

  const analysis = await analyzeOrders(orders);

  const report = await generateReport(analysis);

  await waitForApproval();

  await uploadToNotion(report);
}
```

이 코드는 흐름을 이해하기에는 쉽다.

하지만 운영 환경에서는 문제가 있다.

### ✅ 4. 서버가 재시작된다면?

```text
주문 조회 완료
      ↓
통계 계산 완료
      ↓
LLM 분석 완료
      ↓
서버 재시작
      ↓
진행 상태 소실
```

프로세스 메모리에만 결과를 보관했다면 어디까지 완료했는지 알기 어렵다.

### ✅ 5. 같은 작업을 처음부터 다시 실행하면?

```text
주문 조회
      ↓
LLM 재호출
      ↓
보고서 재생성
      ↓
Notion 중복 업로드
```

가 발생할 수 있다.

특히 알림톡 발송이나 주문 상태 변경 같은 작업에서는 중복 실행이 실제 고객 피해로 이어질 수 있다.

### ✅ 6. Durable Execution이란?

작업의 진행 상태를 영속적으로 저장해 프로세스가 종료되더라도 다른 Worker가 작업 상태를 복구하고 실행을 이어갈 수 있도록 설계하는 것이다.

### ✅ 7. 핵심 구조

```text
Workflow Request
       ↓
Persistent Workflow State
       ↓
Worker Claims Task
       ↓
Step Execution
       ↓
Checkpoint
       ↓
Next Step
       ↓
Completion
```

작업 중 장애가 발생하면:

```text
Worker Crash
       ↓
Lease Expiration
       ↓
Recovery Process
       ↓
Saved Checkpoint
       ↓
Safe Resume
```

로 처리한다.

### ✅ 8. 중요한 전제

**Durable Execution은 모든 외부 작업을 정확히 한 번만 실행한다고 보장하는 기술이 아니다.**

작업 재개 가능성과 외부 Side Effect의 중복 방지는 별도로 설계해야 한다.

## 2. Durable Workflow와 일반 Queue의 차이

### ✅ 9. Queue의 역할

Queue는 실행할 작업을 Worker에게 전달한다.

```text
Producer
    ↓
Queue
    ↓
Worker
```

### ✅ 10. Workflow의 역할

Workflow는 여러 작업의 순서와 상태를 관리한다.

```text
Step A
   ↓
Step B
   ↓
Approval
   ↓
Step C
   ↓
Complete
```

### ✅ 11. Queue와 Workflow는 같은 개념이 아니다

Queue는 작업 실행을 분배하는 수단이다.

Workflow는 작업의 전체 생명주기를 관리하는 구조다.

### ✅ 12. Queue만 사용하면 부족할 수 있는 상황

```text
주문 분석
      ↓
보고서 생성
      ↓
관리자 승인 대기
      ↓
Notion 업로드
```

처럼 여러 단계와 승인 대기가 존재하면 각 단계의 업무 상태를 관리해야 한다.

### ✅ 13. BullMQ 같은 Queue

BullMQ는 Redis 기반으로 사용되는 대표적인 Node.js 작업 큐이며 재시도, 지연 작업, Worker Lock 등을 지원한다.

다만 Worker가 Lock을 유지하지 못하면 Stalled Job이 다시 실행될 수 있다.

### ✅ 14. At-least-once Execution

일부 작업 시스템은 장애 복구 과정에서 동일 작업을 두 번 이상 실행할 수 있다.

```text
Job A 실행

↓

Worker 장애

↓

Job A 재실행
```

따라서 Worker 코드는 중복 실행을 고려해야 한다.

### ✅ 15. Queue가 있으면 Workflow DB가 필요 없을까?

반드시 그렇지는 않다.

Queue가 실제 실행을 담당하고 PostgreSQL이 비즈니스 Workflow 상태를 관리하도록 구성할 수도 있다.

### ✅ 16. 현재 추천

이미 PostgreSQL을 사용하고 작업량이 많지 않다면 다음 구조부터 검토한다.

```text
NestJS API
     ↓
PostgreSQL Workflow Table
     ↓
Scheduler / Worker
     ↓
Step Execution
     ↓
PostgreSQL Checkpoint
```

Redis나 별도 Workflow Engine은 실제 요구사항이 확인된 뒤 도입한다.

## 3. Workflow를 상태 머신으로 표현하기

### ✅ 17. State Machine이란?

작업이 어떤 상태에서 어떤 상태로 변경될 수 있는지 정의하는 방식이다.

### ✅ 18. 기본 상태

```text
READY

RUNNING

WAITING_APPROVAL

WAITING_EXTERNAL

RETRY_WAIT

RECOVERY_REQUIRED

SUCCEEDED

FAILED

CANCELLED
```

### ✅ 19. READY

실행 가능한 작업이다.

### ✅ 20. RUNNING

Worker가 작업을 실행 중인 상태다.

### ✅ 21. WAITING_APPROVAL

사람의 승인을 기다리는 상태다.

### ✅ 22. WAITING_EXTERNAL

외부 시스템의 결과나 Callback을 기다리는 상태다.

### ✅ 23. RETRY_WAIT

일시적인 오류로 재시도 시각을 기다리는 상태다.

### ✅ 24. RECOVERY_REQUIRED

장애 후 자동 재실행이 안전한지 확인해야 하는 상태다.

### ✅ 25. SUCCEEDED

모든 필수 단계가 성공적으로 완료된 상태다.

### ✅ 26. FAILED

재시도나 복구가 불가능하거나 허용 횟수를 초과해 종료된 상태다.

### ✅ 27. CANCELLED

허용된 사용자 또는 시스템 정책에 의해 작업이 취소된 상태다.

### ✅ 28. 정상 상태 전이

```text
READY
   ↓
RUNNING
   ├── SUCCEEDED
   ├── WAITING_APPROVAL
   ├── WAITING_EXTERNAL
   ├── RETRY_WAIT
   └── RECOVERY_REQUIRED
```

### ✅ 29. 승인 후 상태 전이

```text
WAITING_APPROVAL
        ↓
APPROVED
        ↓
READY
        ↓
RUNNING
        ↓
SUCCEEDED
```

### ✅ 30. 승인 거부

```text
WAITING_APPROVAL
        ↓
REJECTED
        ↓
CANCELLED
```

단 승인 거부 후 다른 경로로 진행해야 하는 업무라면 별도 상태 전이를 정의한다.

### ✅ 31. 모든 상태 전이를 허용하면 안 된다

예:

```text
SUCCEEDED
→ RUNNING
```

을 아무 조건 없이 허용하면 이미 끝난 작업이 다시 실행될 수 있다.

### ✅ 32. State Transition Policy

```text
현재 상태

+

요청한 변경

+

Actor 권한

+

Business Rule

↓

허용 / 거부
```

를 적용한다.

## 4. Workflow Step 설계

### ✅ 33. Workflow와 Step

Workflow는 전체 업무다.

Step은 그 안의 개별 작업이다.

예:

```text
Workflow:
Daily AI Report

Step 1:
READ_GIT

Step 2:
ANALYZE_DIFF

Step 3:
GENERATE_REPORT

Step 4:
VALIDATE_REPORT

Step 5:
PUBLISH_NOTION
```

### ✅ 34. Step 단위 분리 기준

하나의 Step은 다음 조건을 고려해 나눈다.

```text
독립적인 성공 여부

재시도 가능 여부

외부 Side Effect

Checkpoint 필요 여부

실행 시간

승인 필요 여부
```

### ✅ 35. 너무 큰 Step의 문제

```text
전체 보고서 처리
```

를 하나의 Step으로 만들면 장애 후 어떤 부분을 다시 실행해야 하는지 판단하기 어렵다.

### ✅ 36. 너무 작은 Step의 문제

반대로 단순 변수 계산까지 모두 Step으로 분리하면 DB Write와 상태 관리가 과도하게 증가한다.

### ✅ 37. 권장 기준

**독립적으로 재시도하거나 성공 여부를 확인해야 하는 작업을 Step으로 나눈다.**

### ✅ 38. Step Metadata

```text
Step Key

Step Type

Status

Attempt

Started At

Completed At

Input Reference

Output Reference

Idempotency Key

Error Code
```

### ✅ 39. Step Type

예:

```text
READ_ONLY

COMPUTE

LLM_CALL

EXTERNAL_WRITE

APPROVAL

WAIT_CALLBACK
```

### ✅ 40. Step Type이 중요한 이유

실패 이후 재시도 정책을 Step 유형별로 다르게 적용하기 위해서다.

## 5. Checkpoint — 어디까지 완료했는지 저장하기

### ✅ 41. Checkpoint란?

작업을 안전하게 이어갈 수 있도록 진행 상태와 필요한 결과를 영속 저장하는 것이다.

### ✅ 42. 메모리 상태만으로는 부족하다

```typescript
let currentStep = 'GENERATE_REPORT';
```

이 변수는 서버 프로세스가 종료되면 사라진다.

### ✅ 43. 영속적인 Checkpoint

예:

```json
{
  "workflowId": "workflow-123",
  "status": "READY",
  "currentStep": "VALIDATE_REPORT",
  "completedSteps": [
    "READ_GIT",
    "ANALYZE_DIFF",
    "GENERATE_REPORT"
  ]
}
```

### ✅ 44. 완료한 Step은 다시 실행하지 않는 것이 기본이다

```text
READ_GIT
DONE

ANALYZE_DIFF
DONE

GENERATE_REPORT
DONE

VALIDATE_REPORT
PENDING
```

이라면 다음 실행은 `VALIDATE_REPORT`에서 시작할 수 있다.

### ✅ 45. Checkpoint를 저장하는 시점

```text
Step 시작
      ↓
작업 실행
      ↓
결과 검증
      ↓
Checkpoint 저장
      ↓
다음 Step
```

### ✅ 46. Checkpoint 저장 실패

Step 자체는 끝났지만 Checkpoint 저장에 실패할 수 있다.

```text
LLM 응답 수신
      ↓
DB Checkpoint 실패
      ↓
Worker 종료
```

이 경우 LLM이 이미 호출됐다는 사실을 잃을 수 있다.

### ✅ 47. 따라서 Step은 재실행 가능성을 고려해야 한다

특히 외부 API를 사용하는 Step에서 중요하다.

### ✅ 48. Checkpoint에는 모든 데이터를 넣을 필요가 없다

대형 LLM 결과를 Workflow Row에 전부 저장하면 DB가 불필요하게 커질 수 있다.

### ✅ 49. Output Reference

예:

```json
{
  "step": "GENERATE_REPORT",
  "status": "SUCCEEDED",
  "outputRef": "reports/workflow-123/report-v1.md"
}
```

처럼 저장할 수 있다.

### ✅ 50. Output 저장소

```text
PostgreSQL

S3

기존 Artifact Storage
```

중 데이터 크기와 보관정책에 따라 선택한다.

### ✅ 51. Output Integrity

중요한 결과는 Checksum 또는 Version을 기록해 재개 시 파일이 변경되지 않았는지 검증할 수 있다.

### ✅ 52. 민감정보 보관 주의

Checkpoint에 고객정보·LLM 전체 대화·API Token을 무조건 저장하지 않는다.

필요한 업무 상태만 저장하고 Retention 정책을 적용한다.

## 6. PostgreSQL Workflow 데이터 모델

### ✅ 53. 최소 테이블

```text
agent_workflow_runs

agent_workflow_steps

agent_workflow_events

agent_workflow_approvals

external_operations
```

### ✅ 54. Workflow Run

전체 작업 상태를 저장한다.

### ✅ 55. Workflow Step

각 단계의 실행 결과와 재시도 정보를 저장한다.

### ✅ 56. Workflow Event

상태 변경과 실행 이력을 기록한다.

### ✅ 57. Approval

승인 대기·승인·거부·만료 상태를 저장한다.

### ✅ 58. External Operation

알림 발송이나 외부 시스템 변경처럼 실제 Side Effect가 있는 작업을 추적한다.

### ✅ 59. PostgreSQL 예시 Schema

```sql
CREATE TABLE agent_workflow_runs (
  id UUID PRIMARY KEY,

  workflow_type TEXT NOT NULL,

  request_key TEXT NOT NULL,

  status TEXT NOT NULL,

  current_step TEXT NOT NULL,

  state_version INTEGER NOT NULL DEFAULT 1,

  lease_owner TEXT,

  lease_until TIMESTAMPTZ,

  lease_epoch BIGINT NOT NULL DEFAULT 0,

  attempt INTEGER NOT NULL DEFAULT 0,

  next_run_at TIMESTAMPTZ NOT NULL DEFAULT now(),

  context JSONB NOT NULL DEFAULT '{}',

  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),

  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),

  UNIQUE (workflow_type, request_key)
);
```

설명용 구조다.

실제 서비스에서는 상태값 제약조건, 인덱스, 보관기간, 접근권한 등을 추가한다.

### ✅ 60. Request Key

동일한 업무 요청을 중복 생성하지 않도록 하는 식별자다.

예:

```text
workflow_type:
daily_work_report

request_key:
repository-20261022
```

### ✅ 61. 같은 Request Key의 의미를 정의해야 한다

동일 Request Key로 다시 요청할 때:

```text
기존 Workflow 반환

새로운 Workflow 생성 거부

명시적 재실행 버전 생성
```

중 어떤 정책을 적용할지 정한다.

### ✅ 62. UNIQUE Constraint

DB 차원에서 중복 Workflow 생성을 방지한다.

### ✅ 63. 상태 Version

동시에 여러 요청이 Workflow를 변경하는 문제를 방지하는 데 사용할 수 있다.

### ✅ 64. Lease Epoch

Worker의 실행권이 새로 부여될 때 증가하는 세대 번호다.

이전 Worker의 오래된 작업이 현재 상태를 덮어쓰지 못하도록 하는 데 활용한다.

## 7. Task Lease — 어떤 Worker가 작업을 실행할까?

### ✅ 65. Lease란?

특정 Worker가 제한된 시간 동안 작업을 실행할 수 있도록 부여받은 실행권이다.

### ✅ 66. 예시

```text
Workflow
TASK-001

Lease Owner
worker-A

Lease Until
10:05:00
```

### ✅ 67. Lease가 필요한 이유

여러 Worker가 같은 작업을 동시에 처리하면 중복 실행이 발생할 수 있다.

### ✅ 68. 정상적인 구조

```text
Workflow READY
       ↓
Worker A Claim
       ↓
Workflow RUNNING
       ↓
Worker A Execute
```

Worker B는 이미 선점된 작업을 가져가지 않는다.

### ✅ 69. Worker 장애

```text
Worker A
RUNNING

↓

프로세스 종료

↓

Lease 갱신 중단

↓

Lease 만료
```

### ✅ 70. Lease 만료 후

복구 로직이 작업을 확인한다.

단 **Lease가 만료됐다는 사실만으로 기존 외부 요청이 실패했다고 판단해서는 안 된다.**

### ✅ 71. Lease Owner

어떤 Worker가 작업을 선점했는지 기록한다.

### ✅ 72. Lease Until

언제까지 실행권이 유효한지 기록한다.

### ✅ 73. Lease Epoch

작업의 실행권이 새로 부여될 때 증가한다.

예:

```text
Worker A
Epoch 1

Worker B
Epoch 2
```

### ✅ 74. Stale Worker

Lease를 잃었지만 아직 실행 중인 이전 Worker를 의미한다.

### ✅ 75. 위험 사례

```text
Worker A
느린 LLM 응답 대기

↓

Lease 만료

↓

Worker B
작업 재개

↓

Worker A
늦게 응답 수신

↓

두 Worker가 상태 저장 시도
```

### ✅ 76. 방어

Checkpoint 저장 시 현재 Lease Owner와 Epoch를 확인한다.

### ✅ 77. 중요한 한계

DB의 Epoch 검증은 오래된 Worker가 DB 상태를 덮어쓰지 못하도록 할 수 있다.

하지만 이미 외부 서비스에 보낸 요청까지 자동으로 취소하거나 차단하지는 못한다.

## 8. PostgreSQL에서 안전하게 작업 선점하기

### ✅ 78. SELECT FOR UPDATE SKIP LOCKED

PostgreSQL은 이미 다른 Transaction이 Lock을 잡은 Row를 건너뛰는 `SKIP LOCKED`를 지원한다.

여러 Worker가 Queue 형태의 테이블에서 서로 다른 작업을 가져갈 때 활용할 수 있다.

### ✅ 79. Claim SQL 예시

```sql
WITH picked AS (
  SELECT id
  FROM agent_workflow_runs
  WHERE status IN ('READY', 'RETRY_WAIT')
    AND next_run_at <= NOW()

  ORDER BY next_run_at, created_at

  FOR UPDATE SKIP LOCKED

  LIMIT 1
)

UPDATE agent_workflow_runs AS w
SET
  status = 'RUNNING',

  lease_owner = $1,

  lease_until = NOW() + INTERVAL '90 seconds',

  lease_epoch = lease_epoch + 1,

  attempt = attempt + 1,

  updated_at = NOW()

FROM picked

WHERE w.id = picked.id

RETURNING w.*;
```

### ✅ 80. 이 SQL의 역할

하나의 SQL Statement 안에서 실행 가능한 작업을 선택하고 RUNNING 상태로 변경한다.

### ✅ 81. 여러 Worker가 동시에 요청하면?

Row Lock 때문에 이미 선택된 작업을 다른 Worker가 동일하게 가져가는 것을 방지하는 데 도움이 된다.

### ✅ 82. SKIP LOCKED의 한계

`SKIP LOCKED`는 Queue 형태의 작업 선점에 적합하다.

하지만 일반적인 데이터 조회에서 항상 일관된 결과를 제공하기 위한 기능은 아니다.

### ✅ 83. 긴 Transaction을 유지하지 않는다

작업을 Claim한 Transaction은 빠르게 종료한다.

LLM 호출이나 외부 HTTP 요청을 처리하는 동안 DB Transaction을 계속 열어두지 않는다.

### ✅ 84. Prisma 적용

현재 프로젝트의 Prisma 버전에 맞는 Raw Query 또는 Transaction API를 사용할 수 있다.

다만 실제 버전에 따라 지원 API가 다르므로 확인해야 한다.

### ✅ 85. SQL Injection 방지

Worker ID 등 동적 값은 Parameter Binding을 사용한다.

사용자 입력을 SQL 문자열에 직접 이어 붙이지 않는다.

### ✅ 86. 처음부터 Worker를 여러 개 둘 필요는 없다

현재 규모에서는 Worker 하나와 안전한 Claim 구조만으로 시작할 수 있다.

Claim 구조가 제대로 설계돼 있으면 나중에 Worker 수를 늘리기 쉽다.

## 9. Heartbeat — Worker가 살아 있는지 확인하기

### ✅ 87. Heartbeat란?

Worker가 자신이 작업을 계속 처리 중임을 주기적으로 알려주는 신호다.

### ✅ 88. Lease Renewal

예:

```text
Lease TTL
90초

Heartbeat Interval
20초
```

로 설계할 수 있다.

수치는 설명용이며 실제 작업 시간과 장애 복구 요구에 맞게 설정해야 한다.

### ✅ 89. Heartbeat SQL

```sql
UPDATE agent_workflow_runs
SET
  lease_until = NOW() + INTERVAL '90 seconds',

  updated_at = NOW()

WHERE id = $1

  AND status = 'RUNNING'

  AND lease_owner = $2

  AND lease_epoch = $3

  AND lease_until > NOW()

RETURNING id;
```

### ✅ 90. Heartbeat 결과가 0건이라면?

현재 Worker가 실행권을 잃었거나 작업 상태가 변경됐을 수 있다.

### ✅ 91. Lease Lost

```text
LEASE_LOST
```

상태로 내부 처리를 전환하고 새 Side Effect를 시작하지 않도록 한다.

### ✅ 92. Event Loop Blocking

Node.js에서 CPU를 오래 점유하는 동기 작업이 실행되면 Heartbeat 갱신이 지연될 수 있다.

### ✅ 93. LLM 처리와 CPU 작업

단순 HTTP 기반 LLM 호출은 비동기 I/O 작업이다.

하지만 대량 JSON 처리, 이미지 변환, 복잡한 동기 계산 등은 Node.js Event Loop를 막을 수 있다.

### ✅ 94. 해결 방법

```text
작업 분리

Worker Thread

별도 Process

Timeout

Concurrency 제한
```

등을 고려한다.

### ✅ 95. Heartbeat 성공이 업무 진행을 보장하지는 않는다

Worker가 Heartbeat만 갱신하면서 실제 작업이 무한 대기할 수도 있다.

### ✅ 96. Progress Timeout

따라서 실제 마지막 Checkpoint나 Step 진행 시각도 확인해야 한다.

## 10. Fencing Token — 오래된 Worker의 실행 차단

### ✅ 97. Fencing Token이란?

실행권의 세대 번호를 사용해 오래된 Worker의 작업을 구분하는 방식이다.

### ✅ 98. 예시

```text
Worker A

leaseEpoch = 10
```

이후 Lease가 회수된다.

```text
Worker B

leaseEpoch = 11
```

### ✅ 99. Worker A가 늦게 완료된다면?

```text
Worker A
Epoch 10

↓

Checkpoint 저장 요청
```

DB는 현재 Epoch 11과 일치하지 않으므로 거부한다.

### ✅ 100. Checkpoint SQL 예시

```sql
UPDATE agent_workflow_runs

SET
  current_step = $4,

  state_version = state_version + 1,

  updated_at = NOW()

WHERE id = $1

  AND lease_owner = $2

  AND lease_epoch = $3

  AND status = 'RUNNING'

  AND lease_until > NOW()

RETURNING id, state_version;
```

### ✅ 101. 0건 반환

다음 원인을 조사한다.

```text
Lease Expired

Lease Owner Changed

Epoch Mismatch

Workflow State Changed
```

### ✅ 102. 실행권을 잃었다면?

Worker가 임의로 다시 DB를 수정하도록 해서는 안 된다.

정식 재실행 절차를 사용해야 한다.

### ✅ 103. 외부 시스템에도 Fencing이 가능할까?

일부 외부 시스템은 Version이나 조건부 갱신을 지원한다.

이런 경우 Fencing 개념을 확장할 수 있다.

### ✅ 104. 외부 API가 지원하지 않는다면?

Idempotency Key, 상태 조회, Reconciliation 등 별도 보호가 필요하다.

**Fencing Token 하나만으로 모든 중복 Side Effect가 방지되는 것은 아니다.**

## 11. Crash Recovery — 서버 장애 이후 복구

### ✅ 105. 서버 장애 유형

```text
Process Crash

EC2 Restart

Deployment Restart

Worker OOM

Network Failure

DB Connection Failure

LLM Timeout
```

### ✅ 106. Recovery Worker

Lease가 만료된 작업을 탐지하는 별도 로직이다.

### ✅ 107. Stale Workflow 탐지

```sql
SELECT
  id,
  current_step,
  lease_owner,
  lease_epoch,
  lease_until

FROM agent_workflow_runs

WHERE status = 'RUNNING'
  AND lease_until < NOW();
```

### ✅ 108. 모든 Stale Workflow를 즉시 재실행하면 안 된다

예:

```text
알림톡 발송 중

↓

Worker Timeout

↓

Lease 만료

↓

같은 알림톡 재발송
```

이 발생할 수 있다.

### ✅ 109. Recovery Classification

```text
SAFE_TO_RETRY

RECONCILIATION_REQUIRED

MANUAL_REVIEW_REQUIRED

NON_RETRYABLE
```

로 구분한다.

### ✅ 110. SAFE_TO_RETRY

순수 읽기 또는 멱등성이 보장된 작업이다.

### ✅ 111. RECONCILIATION_REQUIRED

외부 작업 결과를 확인해야 하는 상태다.

### ✅ 112. MANUAL_REVIEW_REQUIRED

자동으로 성공·실패를 판단하기 어려워 관리자 확인이 필요한 상태다.

### ✅ 113. NON_RETRYABLE

입력이 잘못됐거나 업무 정책상 재시도가 허용되지 않는 작업이다.

### ✅ 114. 안전한 Recovery 흐름

```text
Expired Lease
       ↓
Mark Recovery Required
       ↓
Inspect Current Step
       ↓
Check Side Effect
       ↓
Determine Recovery Policy
       ↓
Resume / Reconcile / Review
```

### ✅ 115. Recovery와 Retry의 차이

Retry는 실패한 작업을 다시 실행한다.

Recovery는 실제 완료 여부와 저장 상태를 확인하고 안전한 재개 방식을 결정한다.

## 12. Idempotency — 중복 실행 방지

### ✅ 116. Idempotency란?

동일한 작업이 여러 번 요청되더라도 의도한 업무 효과가 중복으로 발생하지 않게 만드는 성질이다.

### ✅ 117. 대표적인 위험

```text
알림 중복 발송

주문 중복 생성

Notion 페이지 중복 생성

고객 상태 중복 변경

외부 API 중복 실행
```

### ✅ 118. Idempotency Key

동일한 업무 작업을 식별하는 안정적인 키다.

예:

```text
workflowId
+
stepKey
+
logicalOperationVersion
```

### ✅ 119. 예시

```text
workflow-123:publish-notion:v1
```

### ✅ 120. 재시도할 때 같은 Key를 사용한다

한 번의 논리적 발송 작업에서 재시도할 때마다 새로운 키를 생성하면 중복 실행 방지 효과가 사라질 수 있다.

### ✅ 121. 외부 API의 Idempotency 지원 여부

Provider가 지원한다면 해당 규격에 맞게 Key를 전달한다.

지원하지 않는다면 서버 측 Operation Ledger와 결과 조회 등 대체 방식을 검토해야 한다.

### ✅ 122. Idempotency가 어려운 사례

예:

```text
외부 알림 발송 요청

↓

Provider 성공

↓

응답이 네트워크에서 유실
```

이 경우 실제 발송 여부를 확인할 수 없다면 무조건 재시도하면 안 된다.

### ✅ 123. OUTCOME_UNKNOWN

```text
SUCCEEDED
```

도 아니고:

```text
FAILED
```

도 아닌 상태다.

### ✅ 124. Reconciliation

외부 Provider의 발송 조회 API나 고유 요청번호 등을 사용해 실제 결과를 확인한다.

### ✅ 125. Provider가 조회 API를 제공하지 않는다면?

자동 재시도 대신 별도 수동 확인 절차를 둘 수 있다.

### ✅ 126. 중요한 원칙

**오류 응답을 받았다는 사실과 실제 업무가 실행되지 않았다는 사실은 다르다.**

## 13. External Operation Ledger

### ✅ 127. Ledger의 목적

외부 Side Effect의 실행 요청과 결과를 추적한다.

### ✅ 128. Operation 상태

```text
PLANNED

DISPATCHING

CONFIRMED

FAILED

OUTCOME_UNKNOWN

CANCELLED
```

### ✅ 129. 예시 Schema

```sql
CREATE TABLE external_operations (
  id UUID PRIMARY KEY,

  workflow_id UUID NOT NULL,

  step_key TEXT NOT NULL,

  idempotency_key TEXT NOT NULL UNIQUE,

  operation_type TEXT NOT NULL,

  status TEXT NOT NULL,

  provider_request_id TEXT,

  last_error_code TEXT,

  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),

  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

### ✅ 130. PLANNED

실행할 작업이 기록됐지만 아직 외부 전송이 시작되지 않은 상태다.

### ✅ 131. DISPATCHING

외부 시스템 호출을 시작한 상태다.

### ✅ 132. CONFIRMED

Provider가 작업 완료 또는 수락 상태를 확인해 준 상태다.

단 Provider의 수락과 최종 완료는 별도로 구분해야 할 수도 있다.

### ✅ 133. FAILED

확인 가능한 실패 상태다.

### ✅ 134. OUTCOME_UNKNOWN

외부 요청의 결과를 확정할 수 없는 상태다.

### ✅ 135. 실행 전 기록

외부 API를 호출하기 전에 논리적 Operation을 DB에 기록한다.

### ✅ 136. 외부 호출 후 기록

응답 및 Provider Request ID를 저장한다.

### ✅ 137. DB 저장 실패

외부 API는 성공했지만 DB 업데이트가 실패했다면 다음 Recovery에서 Provider 결과를 조회한다.

### ✅ 138. Transactional Outbox와 연결

업무 상태 변경과 외부 발송 요청 생성을 하나의 DB Transaction으로 묶어 Outbox에 기록할 수 있다.

다만 Outbox만으로 외부 발송의 Exactly-once 처리가 자동으로 보장되는 것은 아니다.

## 14. Retry Policy 설계

### ✅ 139. 모든 오류를 재시도하지 않는다

오류를 분류한다.

```text
TRANSIENT

RATE_LIMITED

AUTHENTICATION

VALIDATION

BUSINESS_CONFLICT

OUTCOME_UNKNOWN
```

### ✅ 140. TRANSIENT

일시적인 네트워크 장애나 서비스 오류일 수 있다.

정책에 따라 재시도할 수 있다.

### ✅ 141. RATE_LIMITED

외부 서비스의 사용량 제한이다.

Retry-After 또는 Provider 제한 정책을 따라야 한다.

### ✅ 142. AUTHENTICATION

Credential이 없거나 무효인 경우다.

동일한 요청을 반복해도 해결되지 않을 수 있다.

### ✅ 143. VALIDATION

입력 형식이 잘못된 경우다.

입력을 수정하지 않고 재시도하는 것은 무의미할 수 있다.

### ✅ 144. BUSINESS_CONFLICT

예:

```text
주문이 이미 취소됨

이미 다른 상태로 변경됨
```

같은 상황이다.

업무 상태를 다시 확인한다.

### ✅ 145. OUTCOME_UNKNOWN

재시도 전에 결과를 확인한다.

### ✅ 146. Exponential Backoff

예:

```text
1차 재시도
2초 후

2차 재시도
4초 후

3차 재시도
8초 후
```

처럼 대기 시간을 늘린다.

### ✅ 147. Jitter

여러 Worker가 동시에 재시도하지 않도록 대기 시간에 무작위 지연을 추가할 수 있다.

### ✅ 148. Max Attempts

무한 재시도를 방지한다.

### ✅ 149. Retry Budget

전체 Workflow에 허용된 재시도 비용이나 시간을 제한할 수 있다.

### ✅ 150. Dead-letter 또는 Manual Review

재시도 횟수를 초과하면 무조건 삭제하지 않고 실패 원인과 업무 영향에 따라 검토 대상으로 분류한다.

## 15. Human-in-the-Loop — 승인 대기와 재개

### ✅ 151. Human-in-the-Loop란?

AI 작업 중 중요한 판단이나 실행에 사람이 참여하는 방식이다.

### ✅ 152. 대표적인 상황

```text
보고서 게시 승인

고객 알림 발송 승인

주문 상태 변경 승인

가격 조건 변경 승인

Production 배포 승인
```

### ✅ 153. 잘못된 대기 방식

```typescript
await waitForeverForHumanApproval();
```

처럼 Worker 프로세스를 계속 점유하는 방식이다.

Workflow RUNNING

```text
관리자 승인
      ↓
Approval Validation
      ↓
Workflow State Update
      ↓
READY
      ↓
Worker Claim
      ↓
Resume
```

### ✅ 156. 승인 대기 정보

```text

Approval ID

Action

Resource

Payload Digest

Approver Permission

Status
```

### ✅ 157. Approval이 만료된다면?

```text
WAITING_APPROVAL
        ↓
EXPIRED
        ↓
CANCELLED / MANUAL_REVIEW
```

등의 정책을 적용한다.

### ✅ 158. 승인 후 실행 전 검증

1021에서 다룬 원칙을 그대로 적용한다.

```text

```

### ✅ 159. Resume는 승인 버튼 자체가 아니다

실제 실행은 Worker가 별도로 수행한다.

### ✅ 160. 승인을 두 번 누르면?

동일한 Approval이 한 번만 소비되도록 DB에서 방지한다.

## 16. Approval Resume의 원자성

### ✅ 161. 승인 요청과 Workflow 상태를 함께 확인한다

다음 과정이 필요하다.

```text
BEGIN TRANSACTION

Workflow Row Lock

Approver Authentication

Approval State Check

Grant Validation

Payload Match

Workflow State Check

Approval Consumed

Workflow READY

Resume Event / Outbox

COMMIT
```

### ✅ 162. 왜 같은 Transaction을 사용할까?

승인은 완료됐지만 Workflow 재개 이벤트가 생성되지 않는 상태를 방지하기 위해서다.

### ✅ 163. Outbox

Workflow 상태 변경과 재개 이벤트를 동일 DB Transaction에서 저장할 수 있다.

### ✅ 164. Queue 발행 실패

DB에는 READY 상태가 저장됐는데 Queue 발행이 실패했다면 Outbox Dispatcher가 나중에 재시도할 수 있다.

### ✅ 165. READY Polling

별도 Queue가 없다면 Worker가 PostgreSQL의 READY 상태를 주기적으로 조회해도 된다.

### ✅ 166. 두 방법 모두 가능하다

```text
DB Polling
단순한 구조
```

```text
DB + Queue + Outbox
복잡하지만 실행 분리에 유리
```

### ✅ 167. 현재 권장

작업량이 적고 PostgreSQL을 이미 사용한다면 DB Polling부터 검토한다.

## 17. WAITING_EXTERNAL — 외부 Callback 대기

### ✅ 168. 외부 시스템이 나중에 결과를 전달하는 경우

예:

```text
알림 발송 요청
       ↓
Provider 접수
       ↓
배송 / 발송 처리
       ↓
Callback
       ↓
Workflow Resume
```

### ✅ 169. WAITING_EXTERNAL

외부 결과가 도착하기 전까지 실행을 중단한다.

### ✅ 170. Callback 인증

외부 Callback이 도착했다고 무조건 신뢰하지 않는다.

### ✅ 171. 확인할 항목

```text
Provider Signature

Request ID

Operation ID

Event Type

Timestamp

Replay Protection
```

### ✅ 172. Callback 중복

외부 시스템이 동일한 이벤트를 여러 번 전달할 수 있다.

### ✅ 173. Deduplication

Provider Event ID 또는 안정적인 이벤트 식별자를 기준으로 중복 처리를 방지한다.

### ✅ 174. Callback이 먼저 도착한다면?

외부 요청의 결과를 DB에 완전히 반영하기 전에 Callback이 도착하는 Race Condition도 고려해야 한다.

### ✅ 175. Callback Timeout

정해진 기간 안에 Callback이 도착하지 않으면 조회 API를 통한 Reconciliation이나 수동 검토로 전환할 수 있다.

### ✅ 176. Callback이 없더라도 상태 조회가 가능할 수 있다

Provider가 조회 API를 제공한다면 Polling 방식으로 결과를 확인할 수 있다.

### ✅ 177. Callback과 Polling

```text
Callback
결과가 오면 처리

Polling
주기적으로 상태 확인
```

두 방식을 업무 특성에 맞춰 선택한다.

이 경우 추가 비용이나 다른 결과가 발생할 수 있다.

### ✅ 185. LLM 호출 자체의 Exactly-once를 가정하지 않는다

Provider의 요청 추적 기능과 Idempotency 지원 여부를 확인하되, 모든 모델 API에서 중복 추론 방지가 보장된다고 가정하지 않는다.

Checkpoint

↓

메시지 생성과 실제 고객 발송을 하나의 불투명한 Step으로 묶으면 장애 복구와 승인 관리가 어려워진다.

Workflow Code가 History Replay와 호환되도록 결정적으로 동작해야 한다.

실제 외부 작업은 Activity로 분리하는 방식이 중요하다.

### ✅ 252. Temporal도 외부 API Exactly-once를 완전히 보장하지 않는다

Activity는 장애와 재시도 상황에서 여러 번 실행될 수 있다.

따라서 Side Effect의 멱등성은 별도로 관리해야 한다.

### ✅ 253. 선택지 D — AWS Step Functions

AWS Step Functions는 상태 기반 Workflow Orchestration을 지원한다.

### ✅ 254. Standard Workflow

장기 실행과 감사 가능한 Workflow에 적합하며 상태 전이와 실행 이력을 관리한다.

### ✅ 255. Callback Task Token

외부 이벤트나 사람의 승인을 기다리는 Callback 패턴을 사용할 수 있다.

### ✅ 256. Express Workflow와의 차이

Express는 짧고 빈번한 작업에 적합하다.

장기간 Human Approval을 기다리는 Workflow에는 일반적으로 Standard 방식이 더 적합하다.

### ✅ 257. 현재 프로젝트 선택 기준

| 조건 | 검토할 방식 |
|---|---|
| 적은 작업량, 기존 PostgreSQL 활용 | PostgreSQL Workflow |
| 이미 Redis 사용, Queue 작업 많음 | BullMQ |
| 복잡한 장기 실행 Agent, 많은 Workflow | Temporal |
| AWS 서비스 간 Orchestration 중심 | Step Functions Standard |

### ✅ 258. 현재 추천

**기존 PostgreSQL 기반으로 상태·Checkpoint·Lease·Approval Resume를 최소 구현하고, 복잡도가 실제로 증가할 때 전문 Workflow Engine을 검토한다.**

새로운 인프라를 도입하면 기능뿐 아니라 비용, 장애 대응, 배포 및 백업 운영 부담도 증가하기 때문이다.

## 📌 요약

1021에서는 AI Agent 간 권한 위임과 승인 구조를 다뤘다.

```text
Authenticated User
        ↓
Supervisor Agent
        ↓
Scoped Grant
        ↓
Worker Agent
        ↓
Tool Gateway
        ↓
Authorization
        ↓
Approval
        ↓
Execution
```

1022에서는 이 작업이 장시간 실행되거나 중간에 멈췄을 때 안전하게 복구하는 구조를 다뤘다.

```text
Workflow Request
       ↓
Persistent State
       ↓
Worker Claim
       ↓
Lease
       ↓
Step Execution
       ↓
Checkpoint
       ↓
Next Step
       ↓
Approval / External Wait
       ↓
Resume
       ↓
Final Verification
```

핵심은 다섯 가지다.

**첫 번째 — 작업 상태는 프로세스 메모리에만 보관하지 않는다.**

서버가 재시작돼도 Workflow가 어디까지 진행됐는지 확인할 수 있어야 한다.

**두 번째 — Checkpoint는 완료한 업무를 다시 반복하지 않도록 돕는다.**

```text
READ
DONE

ANALYZE
DONE

GENERATE
DONE

PUBLISH
PENDING
```

이라면 PUBLISH부터 이어갈 수 있다.

**세 번째 — Lease는 현재 작업을 실행하는 Worker를 제한한다.**

하지만 Lease가 만료됐다고 외부 작업이 실패했다고 단정할 수는 없다.

**네 번째 — 외부 Side Effect는 별도의 멱등성 및 결과 확인이 필요하다.**

```text
외부 API 호출

↓

응답 유실

↓

OUTCOME_UNKNOWN

↓

Reconciliation
```

처럼 처리해야 한다.

**다섯 번째 — Human Approval은 Worker가 계속 대기하는 방식이 아니라 Workflow 상태로 표현한다.**

```text
WAITING_APPROVAL

↓

APPROVED

↓

READY

↓

RUNNING
```

구조를 사용한다.

전체 설계를 정리하면 다음과 같다.

```text
API / User Request
        ↓
Idempotent Workflow Creation
        ↓
PostgreSQL Workflow State
        ↓
Scheduler / Worker
        ↓
Atomic Task Claim
        ↓
Lease + Heartbeat
        ↓
Step Execution
        ↓
Output Validation
        ↓
Checkpoint
        ↓
Next Step
        ↓
Human Approval if Required
        ↓
External Operation Ledger
        ↓
Side Effect Verification
        ↓
Workflow Completion
        ↓
Audit / Monitoring
```

현재 프로젝트에서는 처음부터 Temporal이나 AWS Step Functions 같은 전문 Workflow Engine을 도입할 필요는 없다.

기존 NestJS·PostgreSQL·Scheduler 구조를 기반으로 다음 순서부터 구현하는 것이 현실적이다.

```text
1. Workflow ID

2. Persistent Status

3. Request Idempotency

4. Step Checkpoint

5. External Side Effect 분리

6. Task Lease

7. Heartbeat

8. Crash Recovery

9. Approval Resume

10. Reconciliation / Audit
```

특히 Git → Local LLM → Markdown → Notion 업무 보고 자동화와 카카오 상담 자동화는 Durable Workflow의 장점을 확인하기 좋은 사례다.

그러나 **모든 자동화에 복잡한 상태 머신을 적용하는 것이 목표는 아니다.**

실패해도 쉽게 다시 실행할 수 있는 단순 읽기 작업은 기존 방식으로 충분할 수 있다.

반면 중복 발송, 주문 변경, 고객정보 처리, 장기간 승인 대기처럼 실제 업무 피해가 발생할 수 있는 작업은 영속 상태와 복구 정책을 갖추는 것이 중요하다.

**Durable Execution의 핵심은 작업이 절대로 실패하지 않게 만드는 것이 아니라, 실패하더라도 무엇이 완료됐고 무엇이 불확실한지 확인한 뒤 안전하게 다시 진행할 수 있도록 만드는 것이다.**
