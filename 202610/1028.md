## Policy as Code·Operational Guardrails·Runbook Automation·Change Approval와 자동화 운영 정책 관리

**시리즈 날짜: 2026년 10월 28일**

## 1. 자동화 시스템에서 정책이 중요한 이유

### ✅ 1. 1027과의 연결

1027에서는 반복해서 실패하는 작업을 격리하고 안전하게 재처리하는 방법을 다뤘다.

```text
Workflow Execution
        ↓
Failure Classification
        ↓
Retry Budget
        ↓
Quarantine
        ↓
Manual Review
        ↓
Safe Redrive
```

1028에서는 다음 질문을 다룬다.

**어떤 작업을 자동으로 실행하고, 어떤 작업은 사람의 승인을 받아야 하며, 어떤 경우에는 실행 자체를 차단해야 할까?**

### ✅ 2. 초기 자동화 시스템의 모습

작은 프로젝트에서는 운영 규칙이 여러 곳에 흩어져 있을 수 있다.

```text
Controller
관리자 권한 확인

Service
주문 상태 변경 조건

Worker
재시도 횟수 판단

Scheduler
실행 시간 확인

AI Prompt
위험한 작업 금지

Admin UI
승인 버튼 표시
```

각각의 코드가 독립적으로 판단한다.

### ✅ 3. 정책이 분산돼 발생하는 문제

예를 들어 고객 알림 발송 정책이 변경됐다고 하자.

```text
기존 정책:
관리자가 승인하면 발송 가능

신규 정책:
관리자 승인
+
주문 상태 검증
+
발송 대상 재확인
```

그런데 관리자 화면만 수정하고 Worker의 검증은 수정하지 않았다면 오래된 실행 경로를 통해 발송될 수 있다.

### ✅ 4. Policy as Code란?

보안·업무·운영 정책을 명시적인 코드 또는 선언형 규칙으로 정의하고, 테스트·버전 관리·배포·감사가 가능하도록 만드는 접근이다.

### ✅ 5. 기본 구조

```text
User / Agent / Scheduler
          ↓
     Action Request
          ↓
      Policy Input
          ↓
      Policy Engine
          ↓
  ┌────────┬──────────────┐
  │        │              │
ALLOW     DENY     REQUIRE_APPROVAL
  │        │              │
  │      BLOCK        Approval Flow
  │                       │
  └──────────┬────────────┘
             ↓
     Business Validation
             ↓
     Controlled Execution
             ↓
            Audit
```

### ✅ 6. 정책과 업무 실행의 차이

정책은 다음 질문에 답한다.

```text
이 요청을 실행해도 되는가?
```

업무 실행은 다음 작업을 수행한다.

```text
실제로 주문 상태를 변경한다.
```

### ✅ 7. 중요한 원칙

**Policy Engine은 실행 가능 여부를 판단하지만, 실제 업무 작업은 검증된 Service가 수행한다.**

### ✅ 8. 정책을 AI Prompt에만 작성하면 안 된다

예:

```text
AI에게 전달한 지시:

관리자 승인 없이
고객 알림을 보내지 마세요.
```

이는 AI의 행동을 안내하는 문장일 뿐 실제 권한 통제는 아니다.

### ✅ 9. 서버에서 다시 검증해야 한다

```text
AI:
notification.send 요청

↓

Policy Service:
승인 필요

↓

Approval Service:
승인 없음

↓

Execution:
DENIED
```

### ✅ 10. 이번 편에서 다룰 내용

```text

Risk Classification

```

## 2. 운영 정책의 종류

### ✅ 11. 모든 정책이 같은 목적을 갖는 것은 아니다

자동화 시스템의 정책은 크게 구분할 수 있다.

```text
Authorization Policy

Business Policy

Execution Policy

Safety Policy

Recovery Policy

Change Policy
```

### ✅ 12. Authorization Policy

누가 어떤 리소스에 접근할 수 있는지 결정한다.

예:

```text
일반 고객
자신의 주문만 조회

상담 담당자
허용된 주문 범위 조회

관리자
승인된 관리 작업 실행
```

### ✅ 13. Business Policy

실제 업무 상태와 규칙을 검증한다.

예:

```text
이미 취소된 주문은
신청서 발송 상태로 변경하지 않는다.
```

### ✅ 14. Execution Policy

언제·어떻게 작업을 실행하는지 결정한다.

예:

```text
외부 API 동시 실행
최대 3개

Worker Timeout
30초
```

수치는 설명용 예시다.

### ✅ 15. Safety Policy

중요한 위험이 발생하지 않도록 제한한다.

예:

```text
개인정보 전체 Export
AI 자동 실행 금지
```

### ✅ 16. Recovery Policy

실패한 작업을 어떻게 복구할지 결정한다.

예:

```text
일시적인 네트워크 오류
제한된 Retry

외부 발송 결과 불명
Reconciliation

잘못된 Payload
Quarantine
```

### ✅ 17. Change Policy

운영 정책이나 시스템 구성을 변경할 때 필요한 검증을 정의한다.

예:

```text
Production 정책 변경

↓

Test

↓

Impact Analysis

↓

Approval

↓

Controlled Release
```

### ✅ 18. 정책이 서로 충돌한다면?

예:

```text
Authorization:
주문 수정 허용

Business Policy:
현재 주문 상태에서 수정 금지
```

실제 실행은 거부해야 한다.

### ✅ 19. 실행에는 여러 정책이 모두 적용된다

```text
Authorization PASS

AND

Business Rule PASS

AND

Safety Policy PASS

AND

Execution Condition PASS
```

가 충족돼야 한다.

### ✅ 20. 중요한 구분

`권한이 있다`는 사실과 `현재 업무에서 실행 가능한 상태다`라는 사실은 다르다.

## 3. Default Deny — 기본 거부 정책

### ✅ 21. Default Deny란?

명시적으로 허용되지 않은 작업을 기본적으로 거부하는 원칙이다.

### ✅ 22. 위험한 방식

```typescript
if (policyNotFound) {
  return true;
}
```

정책을 찾지 못했다는 이유로 실행을 허용하는 구조다.

### ✅ 23. 안전한 방식

```typescript
if (policyNotFound) {
  return false;
}
```

### ✅ 24. Policy Decision

단순 Boolean 대신 다음과 같이 구분할 수 있다.

```text
ALLOW

DENY

REQUIRE_APPROVAL
```

### ✅ 25. ALLOW

정의된 정책에 따라 해당 작업을 진행할 수 있다.

다만 실제 Service에서 현재 업무 상태와 입력값을 재검증해야 한다.

### ✅ 26. DENY

현재 요청을 허용하지 않는다.

### ✅ 27. REQUIRE_APPROVAL

해당 작업은 권한상 검토 대상이지만 실행하려면 추가 승인이 필요하다.

### ✅ 28. REQUIRE_APPROVAL은 허용이 아니다

```text
REQUIRE_APPROVAL
≠
ALLOW
```

승인 기록이 실제로 검증되기 전에는 실행할 수 없다.

### ✅ 29. Deny 우선

복수의 정책을 평가할 때 명시적인 거부 조건이 충족되면 실행을 차단해야 한다.

### ✅ 30. 정책 우선순위 예시

```text
1. Authentication Failure
   → DENY

2. Authorization Failure
   → DENY

3. Critical Safety Violation
   → DENY

4. Business Rule Violation
   → DENY

5. Approval Required
   → REQUIRE_APPROVAL

6. All Checks Passed
   → ALLOW
```

### ✅ 31. 구현 시 주의

위 순서는 애플리케이션의 정책 설계 원칙이다.

AWS IAM이나 Cedar 등 외부 정책 엔진의 전체 평가 규칙을 그대로 단순화한 것은 아니다.

### ✅ 32. Policy Error

정책 평가 중 예외가 발생한 경우다.

```text
POLICY_EVALUATION_ERROR
```

### ✅ 33. Evaluation Error를 ALLOW로 처리하지 않는다

특히 고객정보·주문 변경·외부 발송·Production 변경은 정책을 평가할 수 없으면 실행하지 않는 것이 기본이다.

### ✅ 34. Fail Closed

```text
Policy Engine 장애
         ↓
위험한 작업 실행 중단
```

### ✅ 35. Fail Closed의 운영 문제

정책 서버에 장애가 발생하면 정상적인 업무도 일시적으로 중단될 수 있다.

따라서 고가용성, 로컬 캐시, 검증된 정책 Snapshot, 복구 절차 등을 함께 설계해야 한다.

### ✅ 36. 중요한 원칙

**가용성을 높이기 위해 권한 검증을 무조건 생략하는 Fail Open을 사용하지 않는다.**

## 4. Risk Classification — 작업 위험도 분류

### ✅ 37. 모든 작업에 사람의 승인이 필요할까?

그렇지 않다.

공개 상품 조회까지 매번 승인해야 한다면 자동화 효율이 떨어진다.

### ✅ 38. 위험도 분류

```text
LOW

MEDIUM

HIGH

CRITICAL
```

### ✅ 39. LOW

예:

```text
공개 상품정보 조회

공개 FAQ 검색

읽기 전용 일반 문서 분석
```

### ✅ 40. MEDIUM

예:

```text
관리자 보고서 생성

대량 읽기 작업

외부 LLM 분석 실행
```

비용과 데이터 민감도에 따라 HIGH가 될 수도 있다.

### ✅ 41. HIGH

예:

```text
고객 알림 발송

주문 상태 변경

외부 API Write

고객정보 Export
```

### ✅ 42. CRITICAL

예:

```text
Production DB 대량 수정

IAM 권한 변경

전체 고객 데이터 삭제

Production Secret 변경
```

### ✅ 43. 위험도별 실행 정책

| 위험도 | 기본 정책 | 추가 검증 |
|---|---|---|
| LOW | 자동 실행 가능 | 기본 권한·입력 검증 |
| MEDIUM | 조건부 자동 실행 | Quota·Audit·업무 검증 |
| HIGH | 승인 기반 실행 | 대상·Payload·권한 재검증 |
| CRITICAL | 강화된 변경 절차 | 별도 승인·복구계획·실행 제한 |

### ✅ 44. 위험도는 Action만으로 결정되지 않는다

예를 들어 `report.generate`는 일반적으로 낮은 위험일 수 있다.

하지만 전체 고객 개인정보를 포함해 외부 LLM에 전송하는 작업이라면 위험도가 높아진다.

### ✅ 45. Resource Sensitivity

```text
PUBLIC

INTERNAL

CONFIDENTIAL

RESTRICTED
```

등으로 분류할 수 있다.

### ✅ 46. Bulk Action

동일한 작업이라도 처리량이 많으면 위험도가 증가한다.

```text
고객 알림 1건

vs

고객 알림 4,000건
```

### ✅ 47. Production Environment

Staging과 Production은 별도 정책을 사용할 수 있다.

### ✅ 48. AI Autonomy

사람이 직접 선택한 주문을 수정하는 작업과 AI가 대상을 자동 선택해 수정하는 작업은 위험 수준이 다를 수 있다.

### ✅ 49. 최종 위험도 평가 요소

```text
Action

Resource Sensitivity

Environment

Batch Size

External Side Effect

AI Autonomy

Rollback Possibility

Customer Impact
```

## 5. Policy Input 설계

### ✅ 50. Policy Engine에는 구조화된 입력을 전달한다

예:

```json
{
  "actor": {
    "id": "staff-123",
    "role": "STAFF"
  },
  "action": "order.update_status",
  "resource": {
    "type": "ORDER",
    "id": "order-456"
  },
  "environment": "production"
}
```

### ✅ 51. Actor

실제 작업을 요청한 주체다.

### ✅ 52. Action

수행하려는 작업이다.

### ✅ 53. Resource

작업 대상이다.

### ✅ 54. Environment

작업 환경이다.

### ✅ 55. Context

추가적인 판단 정보다.

예:

```text
현재 주문 상태

외부 실행 결과

작업 개수

승인 필요 여부

Workflow 상태
```

### ✅ 56. Policy Version

현재 어떤 정책으로 판단했는지 추적하기 위한 값이다.

### ✅ 57. 정책 입력 예시

```typescript
type Action =
  | 'report.read'
  | 'order.read'
  | 'notification.send'
  | 'workflow.redrive'
  | 'production.deploy';

type Role =
  | 'CUSTOMER'
  | 'STAFF'
  | 'ADMIN';

interface PolicyInput {
  actor: {
    id: string;
    role: Role;
    authenticated: boolean;
  };

  action: Action;

  resource: {
    id: string;
    ownerId?: string;
  };

  environment:
    | 'development'
    | 'staging'
    | 'production';

  externalOutcome?:
    | 'NOT_APPLICABLE'
    | 'CONFIRMED'
    | 'FAILED'
    | 'UNKNOWN';
}
```

### ✅ 58. 중요한 보안 조건

`actor.role`, `authenticated`, `ownerId`는 LLM이 생성한 값을 그대로 사용하지 않는다.

서버의 인증 Context와 실제 Repository에서 조회한 정보를 사용해야 한다.

### ✅ 59. 정책 입력의 신뢰 수준

```text
Authenticated Actor
신뢰된 서버 Context

Current Order State
Database Source of Truth

Approval
Approval Repository

LLM Suggestion
검증되지 않은 제안
```

### ✅ 60. LLM이 정책을 결정하지 않는다

LLM은 작업과 대상을 제안할 수 있다.

정책 입력에 필요한 권한·현재 상태·승인 여부는 서버가 결정한다.

## 6. Policy Decision 설계

### ✅ 61. 결과를 Boolean 하나로 반환하지 않는다

운영자가 왜 실행됐거나 차단됐는지 알 수 있어야 한다.

### ✅ 62. Decision 구조

```typescript
type PolicyEffect =
  | 'ALLOW'
  | 'DENY'
  | 'REQUIRE_APPROVAL';

interface PolicyDecision {
  effect: PolicyEffect;

  reasonCode: string;

  policyVersion: string;

  evaluatedAt: string;
}
```

### ✅ 63. Reason Code

예:

```text
ALLOWED_READ

UNAUTHENTICATED

INSUFFICIENT_PERMISSION

RESOURCE_OWNERSHIP_MISMATCH

EXTERNAL_OUTCOME_UNKNOWN

APPROVAL_REQUIRED

POLICY_NOT_FOUND

POLICY_EVALUATION_ERROR
```

### ✅ 64. 구조화된 Reason Code의 장점

```text
API 응답

관리자 UI

Audit

Monitoring

Regression Test
```

에서 재사용할 수 있다.

### ✅ 65. 응답에 민감한 정보를 포함하지 않는다

외부 고객에게 상세 내부 권한 구조나 다른 고객의 존재 여부를 불필요하게 노출하지 않는다.

### ✅ 66. 사용자 메시지와 내부 Reason 분리

예:

```text
Internal:
RESOURCE_OWNERSHIP_MISMATCH

External:
해당 주문을 확인할 권한이 없습니다.
```

### ✅ 67. Policy Version은 항상 기록한다

같은 Action이더라도 정책이 변경되면 다른 결과가 나올 수 있기 때문이다.

## 7. NestJS 기반 최소 Policy Engine

### ✅ 68. 처음부터 OPA를 도입할 필요는 없다

현재 프로젝트 규모에서는 TypeScript로 작성한 Policy Service부터 시작할 수 있다.

### ✅ 69. Policy Evaluation 함수

다음은 개념을 설명하는 최소 코드다.

```typescript
const POLICY_VERSION = '2026-10-28-v1';

function decision(
  effect: PolicyEffect,
  reasonCode: string,
): PolicyDecision {
  return {
    effect,
    reasonCode,
    policyVersion: POLICY_VERSION,
    evaluatedAt: new Date().toISOString(),
  };
}

function evaluatePolicy(
  input: PolicyInput,
): PolicyDecision {
  if (!input.actor.authenticated) {
    return decision(
      'DENY',
      'UNAUTHENTICATED',
    );
  }

  switch (input.action) {
    case 'report.read':
      return decision(
        'ALLOW',
        'ALLOWED_READ',
      );

    case 'order.read': {
      if (
        input.actor.role === 'ADMIN' ||
        input.actor.role === 'STAFF'
      ) {
        return decision(
          'ALLOW',
          'ROLE_AUTHORIZED',
        );
      }

      if (
        input.resource.ownerId !== undefined &&
        input.resource.ownerId === input.actor.id
      ) {
        return decision(
          'ALLOW',
          'RESOURCE_OWNER',
        );
      }

      return decision(
        'DENY',
        'RESOURCE_OWNERSHIP_MISMATCH',
      );
    }

    case 'notification.send': {
      if (input.actor.role !== 'ADMIN') {
        return decision(
          'DENY',
          'INSUFFICIENT_PERMISSION',
        );
      }

      if (input.externalOutcome === 'UNKNOWN') {
        return decision(
          'DENY',
          'EXTERNAL_OUTCOME_UNKNOWN',
        );
      }

      return decision(
        'REQUIRE_APPROVAL',
        'APPROVAL_REQUIRED',
      );
    }

    case 'workflow.redrive': {
      if (input.actor.role !== 'ADMIN') {
        return decision(
          'DENY',
          'INSUFFICIENT_PERMISSION',
        );
      }

      if (input.externalOutcome === 'UNKNOWN') {
        return decision(
          'DENY',
          'RECONCILIATION_REQUIRED',
        );
      }

      return decision(
        'REQUIRE_APPROVAL',
        'REDRIVE_APPROVAL_REQUIRED',
      );
    }

    case 'production.deploy': {
      if (
        input.actor.role !== 'ADMIN' ||
        input.environment !== 'production'
      ) {
        return decision(
          'DENY',
          'DEPLOY_POLICY_DENIED',
        );
      }

      return decision(
        'REQUIRE_APPROVAL',
        'DEPLOY_APPROVAL_REQUIRED',
      );
    }

    default:
      return decision(
        'DENY',
        'POLICY_NOT_FOUND',
      );
  }
}
```

## 12. Policy Lifecycle

### ✅ 122. 정책의 생명주기

```text
DRAFT
   ↓
VALIDATION
   ↓
TESTED
   ↓
SHADOW
   ↓
APPROVED
   ↓
ACTIVE
   ↓
RETIRED
```

### ✅ 123. DRAFT

새로운 정책을 작성하는 단계다.

### ✅ 124. VALIDATION

정책의 형식과 Schema가 유효한지 확인한다.

### ✅ 125. TESTED

사전에 정의된 테스트 사례를 통과한 상태다.

### ✅ 126. SHADOW

실제 실행에는 영향을 주지 않고 새 정책이 어떤 판단을 내리는지 관찰하는 단계다.

### ✅ 127. APPROVED

필요한 검토와 승인을 완료한 상태다.

### ✅ 128. ACTIVE

실제 요청의 실행 여부를 결정하는 정책이다.

### ✅ 129. RETIRED

더 이상 신규 실행에 적용하지 않는 정책이다.

### ✅ 130. 정책 변경과 배포를 구분한다

정책 코드를 배포했더라도 실제 활성화는 별도 단계로 관리할 수 있다.

### ✅ 131. 기존 Workflow와 호환성

새 정책 활성화 전에 진행 중인 Workflow가 어떤 영향을 받는지 확인한다.

### ✅ 132. Rollback

문제가 발견되면 이전에 검증된 정책으로 복귀할 수 있어야 한다.

다만 보안 취약점 때문에 강화된 정책을 이전 버전으로 되돌리는 것은 새로운 위험을 만들 수 있다.

### ✅ 133. Rollback도 승인 대상이다

특히 보안 제한을 완화하는 Rollback은 단순 복구 명령으로 자동 실행하지 않는다.

## 14. Shadow Evaluation

### ✅ 143. Shadow Mode란?

현재 ACTIVE 정책으로 실제 실행을 판단하면서 새로운 후보 정책도 동시에 평가하는 방식이다.

### ✅ 144. 구조

```text
Actual Request
        ↓
   Policy Input
        ↓
   ┌─────────────┐
   │             │
ACTIVE         SHADOW
Policy v1      Policy v2
   │             │
실제 판단      비교용 판단
   │             │
   └──────┬──────┘
          ↓
    Difference Report
```

### ✅ 145. Shadow Policy는 실제 실행을 제어하지 않는다

예:

```text
ACTIVE:
ALLOW

SHADOW:
DENY
```

이라면 실제 판단은 ACTIVE 정책을 따른다.

단 현재 필수 보안 정책이나 별도 안전 장치가 DENY하는 작업을 Shadow 결과로 허용해서는 안 된다.

### ✅ 146. Shadow Mode의 목적

정책 변경이 실제 운영 요청에 어떤 영향을 미칠지 미리 확인하기 위해서다.

### ✅ 147. 결과 비교

```text
ALLOW → ALLOW

ALLOW → DENY

ALLOW → REQUIRE_APPROVAL

DENY → ALLOW
```

등을 분석한다.

### ✅ 148. 특히 위험한 변경

```text
기존:
DENY

신규:
ALLOW
```

는 권한 확대일 수 있다.

### ✅ 149. 반대 상황

```text
기존:
ALLOW

신규:
DENY
```

는 정상적인 고객 업무를 차단할 가능성이 있다.

### ✅ 150. Shadow 결과 보고서

```text
Policy v1

Policy v2

Evaluated Requests

Changed Decisions

Newly Allowed Actions

Newly Denied Actions

Approval Changes

Critical Risks
```

### ✅ 151. 개인정보 주의

실제 운영 입력을 Shadow Evaluation에 사용할 경우 개인정보를 불필요하게 복제·보관하지 않는다.

가능하면 필요한 속성만 이용한다.

### ✅ 152. Shadow Evaluation만으로 모든 문제를 발견할 수는 없다

아직 발생하지 않은 희귀한 요청이나 악의적인 입력은 별도 테스트가 필요하다.

## 18. Runbook Automation

### ✅ 186. Runbook이란?

반복되는 운영 상황에서 어떤 절차를 수행해야 하는지 정리한 문서다.

### ✅ 187. 기존 Runbook

```text
1. 실패 작업 확인

2. 오류 유형 확인

3. 외부 실행 결과 확인

4. 재시도 가능 여부 판단

5. 관리자 승인

6. 재처리

7. 최종 검증
```

### ✅ 188. Runbook Automation

이 절차의 일부를 시스템이 자동으로 수행하도록 만든다.

### ✅ 189. 기본 구조

```text
Incident / Failure
        ↓
Runbook Selection
        ↓
Precondition Check
        ↓
Policy Evaluation
        ↓
Automated Safe Steps
        ↓
Approval if Required
        ↓
Controlled Action
        ↓
Verification
        ↓
Audit
```

### ✅ 190. 모든 절차를 자동화할 필요는 없다

정책 판단과 업무 영향이 명확한 단계부터 자동화한다.

### ✅ 191. 자동화하기 좋은 작업

```text
Workflow 상태 조회

오류 유형 분류

Lease 확인

Operation Ledger 조회

Retry Budget 확인

실패 이력 정리

복구 보고서 작성
```

### ✅ 192. 신중해야 하는 작업

```text
고객 알림 재발송

주문 상태 강제 변경

Production DB 수정

광고 예산 변경

IAM 권한 변경
```

### ✅ 193. Runbook Version

Runbook도 버전을 관리한다.

예:

```text
notification-recovery-v1
```

### ✅ 194. Runbook과 Policy의 차이

```text
Policy:
이 작업을 수행할 수 있는가?
```

```text
Runbook:
허용된 작업을 어떤 순서로 수행하는가?
```

### ✅ 195. 실행 전 Precondition

예:

```text
Workflow Status = QUARANTINED

AND

Operation Outcome = FAILED

AND

Retry Budget Available

AND

Approval Valid
```

### ✅ 196. Precondition을 만족하지 않는다면?

Runbook 실행을 중단한다.

### ✅ 197. Runbook의 Postcondition

작업 완료 후 어떤 상태여야 하는지 검증한다.

예:

```text
Workflow READY

External Operation Consistent

Audit Recorded
```

### ✅ 198. 실행 성공과 업무 성공을 구분한다

Runbook의 명령이 성공했다고 고객에게 정상 발송됐다고 단정하지 않는다.

## 20. Policy as Code 도구 비교

### ✅ 207. 선택지 A — TypeScript Policy Service

현재 NestJS 서비스 내부에서 정책을 구현하는 방법이다.

장점:

```text
기존 기술 재사용

추가 인프라 불필요

간단한 Unit Test

빠른 적용
```

단점:

```text
서비스 간 정책 공유 어려움

정책 배포와 애플리케이션 배포 결합

정책이 커지면 관리 복잡도 증가
```

### ✅ 208. 선택지 B — Open Policy Agent

OPA는 Rego라는 선언형 언어로 정책을 작성하고 구조화된 입력을 평가할 수 있는 Policy Engine이다.

### ✅ 209. OPA의 구조

```text
Application
      ↓
Policy Query
      ↓
OPA
      ↓
Policy Evaluation
      ↓
Decision
      ↓
Application Enforcement
```

### ✅ 210. OPA의 주요 기능

```text
Rego Policy

Policy Testing

Decision Logs

Policy Bundles

REST API

Policy Distribution
```

### ✅ 211. OPA를 사용하면 좋은 상황

여러 서비스가 동일한 정책을 사용하거나 정책이 복잡해져 중앙 관리가 필요할 때다.

### ✅ 212. OPA의 운영 부담

```text
정책 배포

Rego 학습

Policy Bundle 관리

서비스 통신

캐시

Decision Logging

장애 대응
```

등을 고려해야 한다.

### ✅ 213. Rego 예시

```rego
package togethermall.authz

import rego.v1

default allow := false

allow if {
  input.actor.role == "ADMIN"
  input.action == "order.read"
}

allow if {
  input.actor.role == "CUSTOMER"
  input.action == "order.read"
  input.actor.id == input.resource.ownerId
}
```

### ✅ 214. 위 정책의 동작

명시적인 허용 규칙이 충족되지 않으면 `allow`는 false다.

### ✅ 215. 주의

이 예시는 단순한 Authorization 정책이다.

실제 고객 주문 조회에서는 인증된 Actor와 서버에서 조회한 주문 소유권을 입력으로 사용해야 한다.

### ✅ 216. OPA 테스트

OPA는 `opa test` 명령으로 Rego 정책 테스트를 실행할 수 있다.

```bash
opa test ./policies -v
```

### ✅ 217. OPA에서도 Enforcement가 필요하다

OPA가 DENY를 반환했다고 애플리케이션이 자동으로 작업 실행을 중지하는 것은 아니다.

실제 Tool Gateway나 Service가 결과를 적용해야 한다.

### ✅ 218. OPA Decision Log

OPA는 정책 평가에 대한 Decision Log를 지원한다.

다만 평가 입력에 개인정보가 포함될 수 있으므로 민감한 필드를 마스킹하거나 제거해야 한다.

### ✅ 219. Policy Bundle

OPA는 Bundle을 통해 정책을 배포하고 갱신할 수 있다.

정책 배포의 검증·승인·Version 관리가 필요하다.

### ✅ 220. 현재 OPA 도입 판단

현재 NestJS 중심의 1인 개발 운영 환경에서는 TypeScript 기반 정책 서비스로 충분한 경우가 많다.

여러 독립 서비스 간 정책 공유가 실제 필요해질 때 OPA를 검토한다.

## 21. AWS Verified Permissions와 Cedar

### ✅ 221. Amazon Verified Permissions

AWS에서 제공하는 세부 권한 관리 서비스다.

### ✅ 222. Cedar

권한 정책을 표현하기 위한 언어다.

### ✅ 223. 기본 구조

```text
Application
      ↓
Principal

Action

Resource

Context
      ↓
Verified Permissions
      ↓
ALLOW / DENY
```

### ✅ 224. Cedar의 특징

```text
Principal

Action

Resource

Context

Permit / Forbid
```

를 기반으로 정책을 정의한다.

### ✅ 225. Cedar 정책 예시

```cedar
permit(
    principal,
    action == Action::"readOrder",
    resource
)
when {
    principal.role == "ADMIN"
};
```

실제 Cedar Schema와 Entity 정의에 맞춰 검증해야 하는 설명용 예시다.

### ✅ 226. Cedar에서도 명시적인 거부가 중요하다

`forbid` 규칙이 적용되는 경우 허용 규칙보다 우선한다.

### ✅ 227. Verified Permissions가 대신하지 않는 것

```text
사용자 인증 자체

실제 DB Transaction

Order State Validation

External Idempotency

Human Approval Lifecycle

Workflow Recovery
```

등은 애플리케이션에서 별도로 구현해야 한다.

### ✅ 228. IAM과 Verified Permissions는 다르다

AWS IAM:

```text
AWS 리소스 접근 권한
```

Verified Permissions:

```text
애플리케이션 업무 리소스 권한
```

### ✅ 229. 현재 추천

이미 AWS를 사용한다는 이유만으로 Verified Permissions를 추가할 필요는 없다.

실제 권한 정책 규모와 운영 부담을 비교해야 한다.

### ✅ 230. 도구 선택 기준

| 방식 | 적합한 상황 |
|---|---|
| TypeScript Policy Service | 작은 NestJS 중심 서비스 |
| OPA / Rego | 여러 서비스의 통합 정책 관리 |
| Cedar / Verified Permissions | 세부적인 앱 Authorization 관리 |
| AWS IAM | AWS 인프라 권한 통제 |

## 📌 요약

1027에서는 정상적인 복구로 해결되지 않는 작업을 격리하고 안전하게 재처리하는 구조를 다뤘다.

```text
Workflow Failure
        ↓
Failure Classification
        ↓
Retry Budget
        ↓
Quarantine
        ↓
Safe Redrive
```

1028에서는 이 과정에서 사용되는 **실행·권한·승인·복구 규칙을 일관된 정책으로 관리하는 방법**을 다뤘다.

핵심 구조는 다음과 같다.

```text
User / Agent / Scheduler
         ↓
Authenticated Context
         ↓
Policy Input
         ↓
Policy Evaluation
         ↓
 ┌────────┬──────────────┐
 │        │              │
ALLOW    DENY     REQUIRE_APPROVAL
 │        │              │
 │      BLOCK         Human Review
 │                       │
 └──────────┬────────────┘
            ↓
    Business Validation
            ↓
    Controlled Execution
            ↓
      Result Verification
            ↓
           Audit
```

이번 편에서 중요한 원칙은 여섯 가지다.

**첫 번째 — 정책이 없으면 기본적으로 거부한다.**

새로운 Tool이나 Action이 추가됐다는 이유만으로 기존 관리자 권한을 자동으로 부여하지 않는다.

**두 번째 — 권한·업무·실행·복구 정책을 구분한다.**

```text
Authorization
누가 실행할 수 있는가?

Business Rule
현재 실행 가능한 상태인가?

Execution Policy
어떻게 실행하는가?

Recovery Policy
실패하면 어떻게 처리하는가?
```

**세 번째 — AI Prompt는 보안 경계가 아니다.**

AI가 작업을 제안하더라도 실제 실행 여부는 서버에서 검증한다.

**네 번째 — 정책도 Version과 테스트가 필요하다.**

```text
Policy v1
        ↓
Policy v2
        ↓
Regression Test
        ↓
Impact Analysis
        ↓
Approval
        ↓
Activation
```

**다섯 번째 — 정책 변경은 진행 중인 Workflow에도 영향을 줄 수 있다.**

기존 승인이나 오래된 실행 권한으로 새로운 필수 보안 제한을 우회하지 않도록 한다.

**여섯 번째 — Runbook 자동화에서도 위험한 작업은 승인과 검증을 거친다.**

장애 복구 중이라는 이유로 권한 검사를 무조건 생략해서는 안 된다.

현재 프로젝트에 적용할 때는 다음 순서가 가장 현실적이다.

```text
1. 기존 정책 위치 분석

2. 핵심 권한·업무 규칙 정리

3. Default Deny

4. TypeScript Policy Service

5. Policy Unit / Integration Test

6. Approval 연동

7. Policy Version 관리

8. Quarantine / Redrive Policy

9. Shadow Evaluation

10. Runbook Automation
```

처음부터 OPA, Cedar, 별도 정책 서버를 모두 도입할 필요는 없다.

현재 NestJS·PostgreSQL 중심 구조에서는 공통 TypeScript Policy Service와 기존 Auth·Business Service를 활용하는 것이 단순하고 유지보수하기 쉽다.

다만 여러 서비스가 동일한 권한 정책을 독립적으로 관리하게 되거나 정책이 복잡해진다면 OPA·Cedar 같은 전문 도구를 검토할 수 있다.

가장 중요한 것은 기술 선택이 아니다.

**AI와 자동화가 많아지더라도 동일한 업무 요청에 대해 일관된 권한·실행·승인·복구 판단이 이루어지고, 그 판단의 근거를 검증하고 추적할 수 있어야 한다.**

결국 Policy as Code의 목적은 규칙을 많이 만드는 것이 아니라 **운영자의 기억과 개별 개발자의 판단에 의존하던 중요한 운영 규칙을 테스트 가능하고 재현 가능한 시스템의 일부로 만드는 것**이다.
