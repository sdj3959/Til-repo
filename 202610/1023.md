## 1. 장애 복구 기능은 실제로 테스트하기 전까지 믿을 수 없다

### ✅ 1. 1022와의 연결

1022에서는 장시간 실행되는 AI Workflow가 서버 재시작이나 Worker 장애 이후에도 안전하게 이어서 실행될 수 있도록 설계했다.

```text
Workflow Request
       ↓
Persistent State
       ↓
Worker Claim
       ↓
Lease / Heartbeat
       ↓
Step Execution
       ↓
Checkpoint
       ↓
Approval / External Wait
       ↓
Resume
       ↓
Completion
```

하지만 실제로 이 구조를 구현했다고 하더라도 다음 질문이 남는다.

**Worker가 외부 API 호출을 완료한 직후 강제로 종료된다면 정말 중복 실행 없이 복구할 수 있을까?**

### ✅ 2. 일반적인 테스트의 한계

예를 들어 다음 테스트가 모두 통과했다고 하자.

```text
Workflow 생성 성공

Step 실행 성공

Checkpoint 저장 성공

최종 완료 상태 정상
```

하지만 실제 운영에서는 다음 상황이 발생할 수 있다.

```text
Step 실행 성공
       ↓
외부 API 처리 완료
       ↓
Worker 강제 종료
       ↓
Checkpoint 저장 실패
       ↓
Recovery 실행
       ↓
같은 작업 재실행
```

정상 경로 테스트만으로는 이러한 문제를 발견하기 어렵다.

### ✅ 3. Happy Path Testing

모든 의존성이 정상 동작한다는 가정하에 기능을 검증하는 방식이다.

예:

```text
주문 조회
PASS

AI 분석
PASS

관리자 승인
PASS

알림 발송
PASS

상태 변경
PASS
```

### ✅ 4. Failure Path Testing

각 단계에서 일부러 장애를 발생시켜 시스템이 올바르게 대응하는지 확인한다.

예:

```text
주문 조회
PASS

AI 분석
TIMEOUT

Retry
PASS

관리자 승인
PASS

알림 발송
RESPONSE_LOST

Recovery
RECONCILIATION_REQUIRED
```

### ✅ 5. Workflow Testing의 핵심 질문

```text
장애를 감지하는가?

진행 상태를 보존하는가?

중복 실행을 방지하는가?

실행 결과를 확인하는가?

잘못된 권한을 사용하지 않는가?

안전하게 재개하는가?

복구 불가능한 상태를 식별하는가?
```

### ✅ 6. 정상 동작과 안전한 실패는 모두 성공 조건이다

테스트의 성공은 항상 Workflow가 `SUCCEEDED`에 도달하는 것이 아니다.

예를 들어 외부 알림이 발송됐는지 확인할 수 없다면 다음 상태가 올바른 결과일 수 있다.

```text
RECOVERY_REQUIRED

또는

OUTCOME_UNKNOWN
```

**불확실한 작업을 무작정 다시 실행하지 않는 것도 올바른 복구 동작이다.**

### ✅ 7. 이번 편의 목표

```text
Workflow Test Strategy

Fault Injection

Failure Matrix

Crash Simulation

Lease Concurrency Test

Checkpoint Recovery

External Side Effect Test

Approval Resume Test

Deterministic Replay

Recovery Invariants

CI Release Gate

Operational Drill
```

을 실제 NestJS·PostgreSQL 기반 프로젝트에 적용하는 방법을 다룬다.

## 2. Workflow Testing의 다섯 단계

### ✅ 8. Level 1 — Unit Test

각 함수의 판단 로직을 검증한다.

예:

```text
현재 상태:
WAITING_APPROVAL

입력:
APPROVED

기대 결과:
READY
```

### ✅ 9. Level 2 — Integration Test

실제 PostgreSQL과 여러 컴포넌트를 연결해 검증한다.

예:

```text
Workflow Repository

+

PostgreSQL

+

Lease Claim

+

Transaction
```

### ✅ 10. Level 3 — Worker Execution Test

실제 Worker Process 또는 격리된 실행 환경에서 작업을 수행한다.

예:

```text
Worker A 실행

↓

Worker A 종료

↓

Worker B 시작

↓

복구 확인
```

### ✅ 11. Level 4 — Fault Injection Test

실행 중 의도적으로 장애를 발생시킨다.

예:

```text
DB Connection Failure

LLM Timeout

Provider Response Loss

Worker Crash

Lease Expiration
```

### ✅ 12. Level 5 — Recovery Drill

운영 환경과 유사한 Staging에서 실제 복구 절차를 검증한다.

### ✅ 13. 각 테스트의 역할

| 테스트 | 검증 대상 | 실행 위치 |
|---|---|---|
| Unit | 상태 전이·오류 분류 | Local / CI |
| Integration | DB Transaction·경합 | 격리된 PostgreSQL |
| Worker | 프로세스 장애·재시작 | 독립 Process |
| Fault Injection | 장애별 복구 경로 | Test / Staging |
| Recovery Drill | 복구 절차 전체 | Staging |

### ✅ 14. 모든 장애 테스트를 Production에서 할 필요는 없다

대부분의 테스트는 Mock Provider와 가상 데이터를 이용한 격리 환경에서 수행할 수 있다.

### ✅ 15. 현재 추천 조합

```text
Jest

+

NestJS Testing Module

+

Test PostgreSQL

+

Mock External Provider

+

Fault Injection Hook

+

Workflow Test Runner
```

기존 프로젝트에 Jest가 있다면 이를 재사용한다.

## 3. 테스트 대상은 기능보다 보장해야 할 성질이다

### ✅ 16. Test Invariant란?

시스템이 어떤 장애를 겪어도 반드시 유지해야 하는 조건이다.

### ✅ 17. Invariant 1 — 동일 업무 중복 생성 방지

```text
동일한 Request Key
       ↓
Workflow 생성 요청 2회
       ↓
실제 Workflow 1개
```

### ✅ 18. Invariant 2 — 하나의 현재 Lease

동일한 Workflow에 두 Worker가 동시에 유효한 실행권을 가지지 않도록 한다.

### ✅ 19. Invariant 3 — 오래된 Worker의 Checkpoint 차단

```text
Worker A
Epoch 10

Worker B
Epoch 11
```

인 상황에서 Worker A의 오래된 상태 저장을 거부해야 한다.

### ✅ 20. Invariant 4 — 완료된 Step 보존

이미 성공적으로 Checkpoint된 Step을 장애 복구 과정에서 불필요하게 다시 실행하지 않는다.

### ✅ 21. Invariant 5 — 승인 없는 외부 Write 차단

고객 발송이나 주문 상태 변경을 수행할 때 필요한 Approval이 존재해야 한다.

### ✅ 22. Invariant 6 — 외부 Side Effect 중복 방지

하나의 논리적 발송 요청에 대해 의도하지 않은 중복 발송을 방지해야 한다.

단 외부 Provider의 지원 여부에 따라 완전한 중복 방지 가능 범위가 달라질 수 있다.

### ✅ 23. Invariant 7 — 결과 불명 상태 보존

외부 API 결과를 알 수 없는 상황을 임의로 성공 또는 실패로 확정하지 않는다.

### ✅ 24. Invariant 8 — Grant 재검증

승인 대기 중 권한이 만료되거나 취소됐다면 Resume 시 실행을 거부해야 한다.

### ✅ 25. Invariant 9 — 종료 상태 재실행 금지

```text
SUCCEEDED

CANCELLED

FAILED_FINAL
```

등 최종 상태를 정의하고 허용되지 않은 재실행을 막는다.

### ✅ 26. Invariant 10 — 추적 가능한 결과

작업 실행과 복구 판단을 Workflow ID·Step ID·Operation ID로 추적할 수 있어야 한다.

### ✅ 27. 테스트는 Invariant를 중심으로 작성한다

단순히:

```text
함수가 오류 없이 종료됐다.
```

보다 다음 검증이 중요하다.

```text
외부 발송이 중복되지 않았다.

승인 없이 실행되지 않았다.

이전 Worker가 상태를 덮어쓰지 않았다.

복구 후 업무 상태가 일치한다.
```

## 4. Fault Injection이란?

### ✅ 28. Fault Injection의 의미

시스템의 특정 위치에서 의도적으로 오류나 비정상 상황을 발생시키는 테스트 기법이다.

### ✅ 29. 일반적인 장애 예시

```text
Network Timeout

Connection Reset

Database Deadlock

Process Crash

OOM

HTTP 500

HTTP 429

Response Loss

Expired Approval

Stale Lease
```

### ✅ 30. Fault Injection은 무작위 장애와 다르다

처음에는 정해진 위치에서 정해진 장애를 발생시키는 방식으로 시작하는 것이 좋다.

### ✅ 31. Deterministic Fault Injection

예:

```text
GENERATE_REPORT 단계 종료 직전

↓

DATABASE_WRITE_ERROR
```

를 항상 같은 조건에서 발생시킨다.

### ✅ 32. Fault Injection Point

장애를 삽입하는 위치다.

예:

```text
BEFORE_STEP

AFTER_EXTERNAL_REQUEST

BEFORE_CHECKPOINT

AFTER_CHECKPOINT

BEFORE_APPROVAL_CONSUMPTION

AFTER_APPROVAL_CONSUMPTION
```

### ✅ 33. 왜 정확한 위치가 중요할까?

다음 두 상황은 다르다.

```text
외부 API 요청 전 장애
```

```text
외부 API 처리 후 응답 유실
```

첫 번째는 아직 외부 작업이 실행되지 않았을 수 있다.

두 번째는 이미 실행됐을 수 있다.

### ✅ 34. 실패 시점에 따라 복구 정책이 달라진다

따라서 테스트에서는 어떤 단계에서 장애가 발생했는지를 기록해야 한다.

### ✅ 35. Fault Injection은 Production 기본 비활성화

테스트용 장애 유발 기능은 실제 운영 요청에서 실행되지 않도록 제한해야 한다.

### ✅ 36. Test-only Adapter

가능하면 테스트 환경에서만 사용하는 Dependency Injection을 통해 장애를 유발한다.

실제 운영 API에 임의 장애를 발생시키는 엔드포인트를 추가하지 않는다.

## 5. Fault Matrix 설계

### ✅ 37. Fault Matrix란?

실행 단계와 장애 유형, 기대 결과를 조합해 테스트 목록을 만드는 표다.

### ✅ 38. 기본 Fault Matrix

| 장애 위치 | 주입할 장애 | 기대 결과 |
|---|---|---|
| Workflow 생성 | 중복 요청 | 기존 Workflow 반환 |
| Task Claim | 동시 접근 | 1개 Worker만 Claim |
| Lease 유지 | Heartbeat 중단 | Lease 만료 감지 |
| Checkpoint | DB Write 실패 | 재개 가능 상태 유지 |
| LLM 호출 | Timeout | 정책에 따른 Retry |
| 외부 발송 | 응답 유실 | OUTCOME_UNKNOWN |
| 승인 | 중복 클릭 | 1회만 소비 |
| 승인 후 | Grant 취소 | 실행 거부 |
| Outbox | Publish 실패 | 발행 재시도 |
| Worker | 강제 종료 | 안전한 복구 |
| Callback | 중복 수신 | 중복 상태 변경 없음 |

### ✅ 39. Severity 분류

```text
P0
개인정보·주문·외부 발송 피해 가능

P1
Workflow 중복·데이터 정합성 문제

P2
복구 지연·재시도 비효율

P3
운영 편의성·보고 문제
```

### ✅ 40. 우선 테스트할 영역

고객정보, 주문 상태, 실제 메시지 발송처럼 업무 피해가 발생할 수 있는 작업을 우선한다.

## 6. 테스트 환경은 Production과 격리한다

### ✅ 41. 안전한 테스트 환경의 조건

```text
독립 DB

Synthetic Data

Mock External API

Test Credential

Restricted Network

Test-only Workflow
```

### ✅ 42. 실제 고객 데이터를 사용하지 않는다

테스트용 주문과 고객은 가상 데이터로 생성한다.

### ✅ 43. 발송 Provider도 Mock으로 대체한다

카카오 알림톡이나 Notion에 실제 요청을 보내지 않고 응답과 오류를 재현할 수 있도록 한다.

### ✅ 44. AWS Production 자격증명 제거

테스트 Worker에 Production RDS, S3, AWS 관리자 권한이 필요하지 않다.

### ✅ 45. 독립된 PostgreSQL

기존 로컬 DB의 실제 개발 데이터를 직접 수정하지 않는 것이 안전하다.

### ✅ 46. Testcontainers

Testcontainers를 사용하면 테스트에서 격리된 PostgreSQL Container를 실행할 수 있다.

### ✅ 47. OrbStack 환경

현재 사용하는 OrbStack이 Docker 호환 환경으로 구성되어 있다면 Testcontainers 실행을 검토할 수 있다.

실제 지원 여부와 설정은 설치 상태를 확인해야 한다.

### ✅ 48. 대안

Testcontainers를 도입하지 않고 테스트 전용 PostgreSQL 데이터베이스를 별도로 사용할 수도 있다.

### ✅ 49. 테스트 종료 후 정리

```text
Test Workflow

Test Approval

Test Operation

Test Audit
```

을 격리된 테스트 저장소에서 정리한다.

### ✅ 50. 중요한 원칙

**장애 복구 테스트 자체가 실제 운영 데이터를 변경하는 사고를 발생시켜서는 안 된다.**

## 7. 재현 가능한 테스트를 만드는 방법

### ✅ 51. 테스트가 가끔 실패하면 안 된다

Workflow 테스트가 실행할 때마다 다른 결과를 내면 실제 결함인지 환경 문제인지 구분하기 어렵다.

### ✅ 52. Flaky Test

같은 코드에서 테스트 결과가 불규칙하게 바뀌는 현상이다.

### ✅ 53. 대표적인 원인

```text
실제 시간 대기

네트워크 상태 의존

외부 API 의존

공유 DB 상태

비동기 실행 순서

무작위 ID 충돌

정리되지 않은 Worker
```

### ✅ 54. Clock Injection

시간을 직접 읽기보다 Clock 인터페이스를 주입한다.

```typescript
interface Clock {
  now(): Date;
}
```

### ✅ 55. Production Clock

```typescript
class SystemClock implements Clock {
  now(): Date {
    return new Date();
  }
}
```

### ✅ 56. Test Clock

```typescript
class FakeClock implements Clock {
  constructor(
    private currentTime: Date,
  ) {}

  now(): Date {
    return this.currentTime;
  }

  advance(milliseconds: number): void {
    this.currentTime = new Date(
      this.currentTime.getTime() + milliseconds,
    );
  }
}
```

### ✅ 57. 장점

```text
Approval TTL

Retry Delay

Workflow Deadline

Token Expiration
```

을 실제로 기다리지 않고 테스트할 수 있다.

### ✅ 58. 주의 — PostgreSQL NOW()

JavaScript의 Fake Clock을 변경해도 PostgreSQL의 `NOW()`가 자동으로 변경되는 것은 아니다.

### ✅ 59. DB 시간 테스트 방법

다음 중 하나를 사용한다.

```text
테스트용 시간 Parameter

격리 DB의 테스트 Fixture

Lease Until 명시적 설정

시간 계산을 분리한 Repository 설계
```

### ✅ 60. 실제 운영에서는 일관된 시간 기준이 필요하다

Lease 판정은 DB 시간을 기준으로 하고 애플리케이션의 임의 시간을 신뢰하지 않는 방식이 일반적으로 더 단순할 수 있다.

테스트 편의를 위해 운영 보안 정책을 약화시키지 않는다.

### ✅ 61. Randomness Injection

Retry Jitter나 작업 ID 생성에 무작위성이 있다면 테스트에서 Seed 또는 고정 함수를 사용할 수 있다.

### ✅ 62. Network Injection

실제 인터넷 연결 상태에 의존하지 않고 Mock Transport에서 응답을 제어한다.

### ✅ 63. 실행 순서 제어

Promise Barrier나 Test Hook을 활용해 특정 Worker를 의도한 지점에서 멈출 수 있다.

## 8. Unit Test — 상태 전이 검증

### ✅ 64. State Machine부터 테스트한다

Workflow Engine의 가장 기본적인 부분은 상태 전이다.

### ✅ 65. 상태 전이 함수 예시

```typescript
type WorkflowStatus =
  | 'READY'
  | 'RUNNING'
  | 'WAITING_APPROVAL'
  | 'RETRY_WAIT'
  | 'RECOVERY_REQUIRED'
  | 'SUCCEEDED'
  | 'FAILED'
  | 'CANCELLED';

type WorkflowEvent =
  | 'START'
  | 'REQUEST_APPROVAL'
  | 'APPROVE'
  | 'RETRY'
  | 'COMPLETE'
  | 'FAIL';

function transition(
  status: WorkflowStatus,
  event: WorkflowEvent,
): WorkflowStatus {
  if (status === 'READY' && event === 'START') {
    return 'RUNNING';
  }

  if (
    status === 'RUNNING' &&
    event === 'REQUEST_APPROVAL'
  ) {
    return 'WAITING_APPROVAL';
  }

  if (
    status === 'WAITING_APPROVAL' &&
    event === 'APPROVE'
  ) {
    return 'READY';
  }

  if (
    status === 'RETRY_WAIT' &&
    event === 'RETRY'
  ) {
    return 'READY';
  }

  if (
    status === 'RUNNING' &&
    event === 'COMPLETE'
  ) {
    return 'SUCCEEDED';
  }

  if (
    status === 'RUNNING' &&
    event === 'FAIL'
  ) {
    return 'FAILED';
  }

  throw new Error(
    `INVALID_TRANSITION: ${status} -> ${event}`,
  );
}
```

설명용 최소 예시이며 모든 업무 상태를 포함하지 않는다.

## 9. Recovery Decision의 Unit Test

### ✅ 69. Recovery Classifier

장애 이후 어떤 방식으로 복구할지 결정하는 함수다.

### ✅ 70. Step 유형

```typescript
type StepKind =
  | 'READ_ONLY'
  | 'COMPUTE'
  | 'LLM_CALL'
  | 'EXTERNAL_WRITE';
```

### ✅ 71. Recovery Decision

```typescript
type RecoveryDecision =
  | 'SAFE_TO_RETRY'
  | 'RECONCILIATION_REQUIRED'
  | 'MANUAL_REVIEW_REQUIRED';
```

### ✅ 72. 결정 함수 예시

```typescript
interface RecoveryInput {
  kind: StepKind;

  externalRequestStarted: boolean;

  checkpointCompleted: boolean;

  providerSupportsReconciliation: boolean;
}

function decideRecovery(
  input: RecoveryInput,
): RecoveryDecision {
  if (input.checkpointCompleted) {
    return 'SAFE_TO_RETRY';
  }

  if (input.kind === 'EXTERNAL_WRITE') {
    if (!input.externalRequestStarted) {
      return 'SAFE_TO_RETRY';
    }

    if (input.providerSupportsReconciliation) {
      return 'RECONCILIATION_REQUIRED';
    }

    return 'MANUAL_REVIEW_REQUIRED';
  }

  return 'SAFE_TO_RETRY';
}
```

여기서 `checkpointCompleted`일 때의 `SAFE_TO_RETRY`는 **완료된 Step을 다시 실행한다는 뜻이 아니라 저장된 Checkpoint부터 다음 작업을 안전하게 진행한다는 의미**로 해석해야 한다.

실제 구현에서는 `RESUME_FROM_CHECKPOINT` 같은 별도 상태를 두는 편이 더 명확하다.

### ✅ 73. 안전성 테스트

```typescript
describe('Recovery Classification', () => {
  it('외부 Write 결과가 불명확하면 결과 확인이 필요하다', () => {
    const result = decideRecovery({
      kind: 'EXTERNAL_WRITE',
      externalRequestStarted: true,
      checkpointCompleted: false,
      providerSupportsReconciliation: true,
    });

    expect(result).toBe('RECONCILIATION_REQUIRED');
  });

  it('결과 조회가 불가능하면 수동 검토한다', () => {
    const result = decideRecovery({
      kind: 'EXTERNAL_WRITE',
      externalRequestStarted: true,
      checkpointCompleted: false,
      providerSupportsReconciliation: false,
    });

    expect(result).toBe('MANUAL_REVIEW_REQUIRED');
  });
});
```

### ✅ 74. 중요한 한계

`externalRequestStarted`라는 DB 값만으로 실제 네트워크 요청이 전송되지 않았다는 사실을 완벽하게 증명할 수는 없다.

외부 Write 여부를 보수적으로 판단할 수 있는 영속적 Operation Ledger가 필요하다.

### ✅ 124. 테스트용 Fake Provider

```typescript
class FakeNotificationProvider {
  private accepted = new Map<string, string>();

  private loseNextResponse = true;

  async send(
    idempotencyKey: string,
  ): Promise<{ providerId: string }> {
    const existing = this.accepted.get(idempotencyKey);

    if (existing) {
      return { providerId: existing };
    }

    const providerId = 'mock-send-001';

    this.accepted.set(idempotencyKey, providerId);

    if (this.loseNextResponse) {
      this.loseNextResponse = false;

      throw new Error('RESPONSE_LOST');
    }

    return { providerId };
  }

  lookup(idempotencyKey: string): string | undefined {
    return this.accepted.get(idempotencyKey);
  }

  getAcceptedCount(): number {
    return this.accepted.size;
  }
}
```

이 Provider는 동일 Idempotency Key의 재요청을 중복 처리하지 않는 가상 서비스다.

실제 카카오 또는 외부 Provider가 이런 동작을 지원한다고 가정해서는 안 된다.

```typescript
  await expect(
    provider.send(key),
  ).rejects.toThrow('RESPONSE_LOST');

  expect(confirmedId).toBe('mock-send-001');

```

## 20. Outbox 장애 테스트

### ✅ 152. Outbox의 역할

Workflow 상태 변경과 외부 발송 요청을 같은 DB Transaction에서 기록할 수 있도록 한다.

### ✅ 153. 장애 시나리오

```text
↓
```

### ✅ 154. 기대 결과

### ✅ 155. 발행 중복

### ✅ 156. Consumer Idempotency

### ✅ 157. Outbox Test

```text

↓

↓

Dispatcher 재시도

↓
```

를 검증한다.

### ✅ 158. 검증 조건


### ✅ 159. Outbox 자체가 Exactly-once를 보장하지 않는다

Producer의 DB 기록을 안전하게 만드는 기술과 Consumer의 중복 처리 방지는 별도 문제다.

## 21. Deterministic Replay란?

### ✅ 160. Replay의 의미

저장된 실행 이력을 사용해 과거 Workflow 상태를 다시 구성하는 것이다.

### ✅ 161. 단순 재실행과 다르다

**Re-execution**

```text
원래 함수를 다시 실행
```

**Replay**

```text
기록된 실행 결과를 사용해
상태와 흐름을 재구성
```

### ✅ 162. 왜 필요한가?

장애 이후 어디까지 작업이 완료됐는지 확인하고 코드 변경 이후에도 기존 Workflow와 호환되는지 테스트하기 위해서다.

### ✅ 163. Event History 예시

```text
WORKFLOW_CREATED

STEP_STARTED: READ_GIT

STEP_SUCCEEDED: READ_GIT

STEP_STARTED: GENERATE_REPORT

STEP_SUCCEEDED: GENERATE_REPORT

APPROVAL_REQUESTED

APPROVAL_GRANTED

STEP_STARTED: PUBLISH_NOTION
```

### ✅ 164. 이력만 보면

`PUBLISH_NOTION`이 시작됐다는 사실은 알 수 있다.

하지만 실제 업로드 성공 여부까지 확정할 수는 없다.

### ✅ 165. Replay가 알 수 없는 것

DB에 기록되지 않은 외부 Side Effect는 단순 Event Replay로 복원할 수 없다.

### ✅ 166. 따라서 Replay와 Reconciliation을 구분한다

```text
Replay
내부 상태 재구성

Reconciliation
외부 실제 상태 확인
```

### ✅ 167. 직접 구현한 Workflow와 Temporal의 차이

Temporal은 Event History를 기반으로 Workflow 코드를 결정적으로 재실행해 상태를 재구성하는 엔진이다.

PostgreSQL에 이벤트를 저장한다고 자동으로 Temporal과 같은 Replay 엔진이 되는 것은 아니다.

### ✅ 168. 현재 프로젝트의 현실적인 Replay

처음에는 순수한 상태 전이 함수에 저장된 이벤트를 적용해 상태를 재구성하는 수준부터 시작할 수 있다.

## 22. Event Reducer를 통한 상태 재구성

### ✅ 169. Event Reducer

이전 상태와 이벤트를 받아 다음 상태를 계산하는 순수 함수다.

### ✅ 170. 단순 예시

```typescript
type ReplayStatus =
  | 'READY'
  | 'RUNNING'
  | 'WAITING_APPROVAL'
  | 'SUCCEEDED';

type ReplayEvent =
  | { type: 'WORKFLOW_CREATED' }
  | { type: 'STEP_STARTED' }
  | { type: 'APPROVAL_REQUESTED' }
  | { type: 'APPROVAL_GRANTED' }
  | { type: 'WORKFLOW_SUCCEEDED' };

function replayReducer(
  status: ReplayStatus | null,
  event: ReplayEvent,
): ReplayStatus {
  switch (event.type) {
    case 'WORKFLOW_CREATED':
      return 'READY';

    case 'STEP_STARTED':
      if (status !== 'READY') {
        throw new Error('INVALID_REPLAY_EVENT');
      }
      return 'RUNNING';

    case 'APPROVAL_REQUESTED':
      if (status !== 'RUNNING') {
        throw new Error('INVALID_REPLAY_EVENT');
      }
      return 'WAITING_APPROVAL';

    case 'APPROVAL_GRANTED':
      if (status !== 'WAITING_APPROVAL') {
        throw new Error('INVALID_REPLAY_EVENT');
      }
      return 'READY';

    case 'WORKFLOW_SUCCEEDED':
      if (status !== 'RUNNING') {
        throw new Error('INVALID_REPLAY_EVENT');
      }
      return 'SUCCEEDED';
  }
}
```

### ✅ 171. Replay 함수

```typescript
function replayWorkflow(
  events: ReplayEvent[],
): ReplayStatus | null {
  return events.reduce<ReplayStatus | null>(
    (status, event) => replayReducer(status, event),
    null,
  );
}
```

### ✅ 172. Test

```typescript
it('이벤트 이력으로 완료 상태를 복원한다', () => {
  const events: ReplayEvent[] = [
    { type: 'WORKFLOW_CREATED' },
    { type: 'STEP_STARTED' },
    { type: 'APPROVAL_REQUESTED' },
    { type: 'APPROVAL_GRANTED' },
    { type: 'STEP_STARTED' },
    { type: 'WORKFLOW_SUCCEEDED' },
  ];

  expect(replayWorkflow(events)).toBe('SUCCEEDED');
});
```

### ✅ 173. Deterministic Replay 조건

동일한 초기 상태와 동일한 이벤트가 주어지면 동일한 결과를 반환해야 한다.

### ✅ 174. Reducer 안에서 하지 말아야 할 것

```text
현재 시간 직접 조회

Random Number 생성

외부 HTTP 요청

DB Query

LLM 호출

파일 수정
```

등이다.

### ✅ 175. 외부 결과는 이벤트에 포함한다

예:

```json
{
  "type": "STEP_SUCCEEDED",
  "stepKey": "GENERATE_REPORT",
  "outputRef": "report-v1.md"
}
```

### ✅ 176. 중요한 보완

실제 Workflow에는 Step ID·실행 횟수·Workflow Version 등이 필요하다.

위 코드는 Replay 개념을 설명하기 위한 최소 예시다.

### ✅ 181. Replay Testing

기존 Workflow History를 새 코드로 Replay하여 호환성을 검증할 수 있다.

### ✅ 182. Temporal TypeScript 테스트

```text
↓
```

```text

↓

↓
```

```text
↓

Recovery
```

### ✅ 194. 두 상황을 각각 테스트한다

정상 종료 시 정상적으로 동작해도 강제 종료 시 문제가 나타날 수 있기 때문이다.

## 📌 요약

1022에서는 장기 실행 AI Workflow의 내구성을 설계했다.

```text
Workflow Request
       ↓
Persistent State
       ↓
Task Lease
       ↓
Step Execution
       ↓
Checkpoint
       ↓
Crash Recovery
       ↓
Resume
```

1023에서는 이러한 설계가 **실제 장애 상황에서도 안전하게 작동하는지 테스트하는 방법**을 다뤘다.

가장 중요한 질문은 다음과 같다.

**첫 번째 — Worker가 종료되면 작업은 복구되는가?**

```text
Worker Crash
      ↓
Lease Expiration
      ↓
Recovery
      ↓
Saved Checkpoint
      ↓
Safe Resume
```

**두 번째 — 완료된 작업이 중복 실행되지 않는가?**

```text
외부 API 처리 완료
       ↓
응답 유실
       ↓
OUTCOME_UNKNOWN
       ↓
Reconciliation
       ↓
중복 실행 방지
```

**세 번째 — 승인 대기 후에도 권한과 업무 조건이 유지되는가?**

```text
WAITING_APPROVAL
       ↓
서버 재시작
       ↓
관리자 승인
       ↓
Grant Revalidation
       ↓
Payload Verification
       ↓
Resume
```

**네 번째 — 오래된 Worker가 현재 상태를 변경하지 못하는가?**

```text
Worker A
Epoch 10

↓

Lease 만료

↓

Worker B
Epoch 11

↓

Worker A의 늦은 Checkpoint

↓

DENY
```

**다섯 번째 — 복구 성공을 실제 업무 결과로 검증하는가?**

```text
Internal Workflow State

+

External Provider State

+

Approval / Permission

+

Idempotency

+

Audit
```

이를 통해 실제 Recovery Success를 판단한다.

전체 테스트 전략은 다음과 같이 정리할 수 있다.

```text
Workflow Definition
         ↓
Unit Tests
         ↓
PostgreSQL Integration Tests
         ↓
Worker Concurrency Tests
         ↓
Fault Injection
         ↓
Crash Recovery
         ↓
External Side Effect Verification
         ↓
Approval Resume Tests
         ↓
Replay / History Validation
         ↓
Recovery Report
         ↓
CI Release Gate
```

현재 프로젝트에서는 처음부터 복잡한 Chaos Engineering 플랫폼이나 대규모 Workflow Test Engine을 만들 필요는 없다.

기존 NestJS·PostgreSQL·Jest·OrbStack 환경을 활용해 다음 순서부터 시작하는 것이 현실적이다.

```text

2. Request Key 중복 생성 테스트

4. Lease Expiration Test

5. Stale Worker Checkpoint Test

6. Checkpoint Crash Test

7. Provider Response Loss Test

8. Approval Double-submit Test

9. Worker Process Crash Test

10. Recovery Verification Report
```

특히 카카오 상담 자동화와 주문 상태 변경에서는 **동일 메시지가 중복 발송되지 않는지, 다른 고객의 주문이 처리되지 않는지, 승인되지 않은 작업이 실행되지 않는지**를 먼저 검증해야 한다.

Git → Local LLM → Markdown → Notion 자동화에서는 Checkpoint와 중복 업로드 방지가 가장 현실적인 출발점이다.

그리고 이번 편에서 기억해야 할 가장 중요한 원칙은 다음과 같다.

**장애 복구 로직은 정상 상황에서 잘 동작한다는 이유만으로 신뢰할 수 없다. 실제로 중단하고, 실패시키고, 재실행한 뒤에도 업무 데이터와 외부 실행 결과가 올바른지 검증했을 때 비로소 안전한 복구 시스템이라고 판단할 수 있다.**
