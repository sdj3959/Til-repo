## 1. 정책을 정상적으로 배포했는데도 운영 환경이 달라질 수 있다

### ✅ 1. 1028과의 연결

1028에서는 운영 정책을 명시적으로 정의하고 검증하는 방법을 다뤘다.

```text
Policy Definition
       ↓
Policy Testing
       ↓
Impact Analysis
       ↓
Change Approval
       ↓
Policy Deployment
       ↓
Audit
```

그러나 정책을 정상적으로 배포했다고 해서 운영 환경이 계속 해당 정책을 준수한다는 보장은 없다.

### ✅ 2. 실제 운영에서 발생할 수 있는 문제

예를 들어 다음과 같은 상황을 생각해 보자.

```text
Git Repository

notification.autoSend = false
```

그런데 실제 운영 환경에서는:

```text
Production Runtime

notification.autoSend = true
```

상태로 실행되고 있다.

Git에는 자동 발송이 비활성화돼 있지만 실제 운영에서는 활성화된 상태다.

### ✅ 3. 이러한 차이를 Drift라고 한다

Drift는 기대하는 상태와 실제 상태 사이에 발생한 불일치다.

```text
Expected State
       ≠
Actual State
```

### ✅ 4. Policy Drift란?

승인된 운영 정책과 실제 시스템에 적용된 정책이 일치하지 않는 현상이다.

### ✅ 5. Configuration Drift란?

애플리케이션과 인프라의 실제 설정이 정의된 기준 설정에서 벗어난 현상이다.

### ✅ 6. Drift는 코드뿐 아니라 인프라에서도 발생한다

예:

```text
AWS IAM Permission

EC2 Security Group

RDS Backup Setting

S3 Bucket Policy

CloudFront Configuration

Feature Flag

Workflow Retry Policy

LLM Tool Permission
```

등이다.

### ✅ 7. 정상적인 변경도 Drift가 될 수 있다

운영 장애를 해결하기 위해 AWS Console에서 임시로 설정을 변경했다고 하자.

```text
Production Incident
       ↓
AWS Console에서 설정 변경
       ↓
서비스 정상화
       ↓
Git 설정은 변경되지 않음
```

긴급 변경 자체는 정당했을 수 있다.

그러나 Git과 실제 운영 설정의 차이를 나중에 정리하지 않으면 문제가 된다.

### ✅ 8. Drift가 곧 보안 사고는 아니다

다음은 서로 구분해야 한다.

```text
승인된 긴급 변경

정상적인 배포 진행 중 상태

설정 반영 지연

승인되지 않은 변경

설정 조회 실패

잠재적인 보안 위반
```

### ✅ 9. 핵심 질문

**실제 운영 환경이 승인된 상태와 다르다면, 무엇이 달라졌고 왜 달라졌으며 현재 상태가 안전한지 어떻게 판단할 것인가?**

### ✅ 10. 이번 편의 목표

```text
Policy Drift Detection

Configuration Integrity

Desired / Actual State

Continuous Compliance

AWS Configuration Monitoring

GitOps / IaC Drift

Runtime Configuration Verification

Policy Version Verification

Audit Evidence

Risk-based Remediation

Drift Dashboard

NestJS / PostgreSQL 구현

Codex 실전 프롬프트
```

을 다룬다.

## 2. Desired State와 Actual State

### ✅ 11. Desired State

시스템이 유지해야 하는 승인된 목표 상태다.

예:

```text
주문 상태 변경
관리자 권한 필요

고객 알림 발송
승인 필요

Production DB
외부 직접 접근 제한
```

### ✅ 12. Actual State

실제 운영 환경에서 확인된 상태다.

### ✅ 13. 두 상태를 비교한다

```text
Desired State
        ↓
Configuration Collector
        ↓
Actual State
        ↓
Drift Detector
        ↓
Difference Report
```

### ✅ 14. Desired State의 출처

```text
Git Repository

Approved Policy Registry

Infrastructure as Code

Approved Configuration

Security Baseline
```

등이다.

### ✅ 15. Actual State의 출처

```text
Runtime Configuration

AWS API

Database Configuration

Feature Flag Provider

Worker Metadata

IAM Policy

Deployment Metadata
```

등이다.

### ✅ 16. 중요한 원칙

**Git에 적힌 값이 있다고 해서 실제 운영 환경에 적용됐다고 판단하지 않는다.**

### ✅ 17. 코드와 Runtime은 다르다

```text
Git Commit
A
```

인데 실제 EC2에서 실행되는 애플리케이션은:

```text
Deployed Commit
B
```

일 수 있다.

### ✅ 18. 같은 코드에서도 설정이 다를 수 있다

```text
Build Version
동일

Environment Variables
다름
```

인 경우다.

### ✅ 19. 배포 Version과 정책 Version도 다르다

```text
Application Version

Policy Version

Configuration Version

Workflow Definition Version

Prompt Version
```

은 서로 구분해야 한다.

### ✅ 20. Configuration Source of Truth

설정마다 신뢰할 수 있는 기준을 정해야 한다.

예:

| 설정 | 기준 상태 |
|---|---|
| 애플리케이션 코드 | 승인된 Git Commit |
| 운영 정책 | ACTIVE Policy Version |
| AWS 리소스 | 승인된 IaC 또는 운영 Baseline |
| Feature Flag | 승인된 Flag Configuration |
| Secret | 승인된 Secret 저장소와 버전 메타데이터 |
| Workflow | 승인된 Workflow Definition |

### ✅ 21. 모든 설정의 기준이 Git일 필요는 없다

운영 중 변경 가능한 Feature Flag나 긴급 차단 설정은 별도의 승인된 Configuration Registry를 사용할 수도 있다.

### ✅ 22. 중요한 것은 기준이 명확해야 한다는 점이다

기준이 여러 개이고 우선순위가 없다면 어떤 값이 올바른지 판단하기 어렵다.

## 3. Drift 유형 구분하기

### ✅ 23. Infrastructure Drift

AWS 등의 인프라 설정이 변경된 경우다.

### ✅ 24. Application Configuration Drift

애플리케이션 환경변수나 Runtime 설정이 변경된 경우다.

### ✅ 25. Authorization Drift

역할이나 접근권한이 승인된 범위와 달라진 경우다.

### ✅ 26. Policy Drift

정책 엔진의 실제 적용 버전이 승인된 버전과 다른 경우다.

### ✅ 27. Workflow Drift

Workflow 단계·Retry·승인 정책이 기대 상태와 달라진 경우다.

### ✅ 28. Agent Configuration Drift

AI Agent의 Tool 목록이나 실행 권한이 변경된 경우다.

### ✅ 29. Feature Flag Drift

승인된 기능 활성화 상태와 실제 Flag 상태가 다른 경우다.

### ✅ 30. Deployment Drift

실행 중인 애플리케이션 버전이 승인된 배포 버전과 다른 경우다.

### ✅ 31. Security Baseline Drift

암호화·접근 통제·로깅·백업 등의 보안 기준이 유지되지 않는 경우다.

### ✅ 32. Drift 유형별 예시

| 유형 | Desired | Actual |
|---|---|---|
| Deployment | Commit A | Commit B |
| IAM | S3 읽기 전용 | 쓰기 권한 추가 |
| Feature Flag | 자동 발송 OFF | ON |
| Workflow | Retry 최대 3회 | 10회 |
| Approval | 발송 승인 필수 | 승인 없이 실행 |
| Database | 승인된 접근 범위 | 더 넓은 접근 범위 |
| Policy | Version 5 | Version 4 |

### ✅ 33. 모든 불일치를 동일한 위험으로 취급하지 않는다

예:

```text
보고서 Retry Delay 차이
```

와:

```text
고객정보 접근권한 확대
```

는 위험 수준이 다르다.

## 4. Drift Detection과 Continuous Compliance의 차이

### ✅ 34. Drift Detection

기준 상태와 실제 상태가 다른지 확인한다.

### ✅ 35. Continuous Compliance

시스템이 정의된 운영·보안 기준을 지속적으로 준수하는지 검사한다.

### ✅ 36. 두 개념은 비슷하지만 다르다

Drift Detection:

```text
Git 설정과 운영 설정이 같은가?
```

Continuous Compliance:

```text
운영 설정이 보안 기준을 만족하는가?
```

### ✅ 37. 예시

Git에 다음 설정이 있다.

```text
Security Group

Inbound:
0.0.0.0/0
```

실제 AWS에도 동일하게 설정돼 있다고 하자.

### ✅ 38. Drift 결과

```text
IN_SYNC
```

일 수 있다.

### ✅ 39. 하지만 보안 정책 결과는?

해당 포트가 외부에 공개돼서는 안 되는 포트라면:

```text
NON_COMPLIANT
```

일 수 있다.

### ✅ 40. 중요한 원칙

**기준 상태와 일치한다는 사실이 해당 설정이 안전하다는 뜻은 아니다.**

### ✅ 41. 따라서 두 검사를 수행한다

```text
Configuration Comparison
           ↓
Drift Result

+

Security / Business Policy Evaluation
           ↓
Compliance Result
```

### ✅ 42. 결과를 별도로 기록한다

```text
Drift Status:
IN_SYNC

Compliance Status:
NON_COMPLIANT
```

도 가능한 결과다.

## 5. Drift 상태 설계

### ✅ 43. 모든 비교를 Boolean으로 처리하지 않는다

다음 두 가지는 다르다.

```text
설정이 서로 다름
```

```text
실제 설정을 조회할 수 없음
```

### ✅ 44. Drift Status

```text
IN_SYNC

DRIFTED

NOT_VERIFIED

APPROVED_EXCEPTION

PENDING_ROLLOUT
```

처럼 구분할 수 있다.

### ✅ 45. IN_SYNC

승인된 기대값과 관측된 값이 일치한다.

### ✅ 46. DRIFTED

기대값과 실제 관측값이 다르다.

### ✅ 47. NOT_VERIFIED

실제 설정을 확인하지 못했다.

### ✅ 48. APPROVED_EXCEPTION

승인된 예외가 존재한다.

### ✅ 49. PENDING_ROLLOUT

배포 과정에서 허용된 시간 안에 설정이 반영되기를 기다리는 상태다.

### ✅ 50. NOT_VERIFIED를 정상으로 처리하지 않는다

예:

```text
AWS API 호출 실패
       ↓
설정 조회 불가
       ↓
IN_SYNC
```

로 기록해서는 안 된다.

### ✅ 51. 조회 실패와 Drift를 구분한다

```text
Collector Error

Permission Denied

Timeout

Unsupported Resource
```

는 불일치와 다른 상태다.

### ✅ 52. 승인된 예외도 무제한 허용하지 않는다

예외에는 담당자, 사유, 범위, 만료일이 필요하다.

### ✅ 54. Desired State Registry

### ✅ 62. Remediation

### ✅ 63. Evidence

어떤 상태를 확인하고 어떻게 조치했는지 근거를 남긴다.

## 7. Configuration Normalization

### ✅ 64. 정규화가 필요한 이유

같은 설정이라도 API에 따라 표현이 다를 수 있다.

예:

```json
{
  "enabled": true
}
```

```json
{
  "enabled": "true"
}
```

### ✅ 65. 타입을 명확하게 관리한다

Boolean 설정은 Boolean으로 정규화한다.

### ✅ 66. 문자열로 무조건 비교하지 않는다

```text
"10"

10
```

은 실제 Schema에 따라 같은 의미일 수도 있고 서로 다른 값일 수도 있다.

### ✅ 67. 배열 순서

일부 설정은 순서와 무관할 수 있다.

예:

```text
Allowed Roles

ADMIN, STAFF
```

### ✅ 68. 반대로 순서가 중요한 설정도 있다

```text
Middleware Execution Order
```

는 순서를 변경하면 실제 동작이 달라질 수 있다.

### ✅ 69. 따라서 정규화 규칙도 Schema별로 정의한다

모든 배열을 정렬하거나 모든 값을 문자열로 변환해서는 안 된다.

### ✅ 70. 무시해야 하는 메타데이터

예:

```text
LastFetchedAt

CollectorRunId
```

는 설정의 실제 의미와 관계없는 수집 메타데이터일 수 있다.

### ✅ 71. 하지만 중요한 필드를 무시하면 안 된다

```text
IAM Permission

Resource Policy

Backup Enabled

External Access
```

같은 필드는 실제 보안 기준에 포함해야 한다.

## 8. TypeScript 최소 Drift Detector

### ✅ 72. 처음에는 단순한 설정 비교부터 시작한다

다음 코드는 비밀값이 아닌 명시적인 설정을 비교하는 최소 예시다.

### ✅ 73. 데이터 타입

```typescript
type ConfigValue =
  | string
  | number
  | boolean
  | null;

type DriftStatus =
  | 'IN_SYNC'
  | 'DRIFTED'
  | 'NOT_VERIFIED';

interface ConfigCheck {
  key: string;
  expected: ConfigValue;
  actual?: ConfigValue;
}

interface DriftResult {
  key: string;
  status: DriftStatus;
  expected: ConfigValue;
  actual?: ConfigValue;
}
```

### ✅ 74. 비교 함수

```typescript
function detectDrift(
  check: ConfigCheck,
): DriftResult {
  if (check.actual === undefined) {
    return {
      key: check.key,
      status: 'NOT_VERIFIED',
      expected: check.expected,
    };
  }

  if (check.expected !== check.actual) {
    return {
      key: check.key,
      status: 'DRIFTED',
      expected: check.expected,
      actual: check.actual,
    };
  }

  return {
    key: check.key,
    status: 'IN_SYNC',
    expected: check.expected,
    actual: check.actual,
  };
}
```

### ✅ 75. 중요한 부분

```typescript
if (check.actual === undefined)
```

는 실제 설정을 확인하지 못한 경우를 나타낸다.

### ✅ 76. 실제 설정이 null이라면?

```typescript
actual: null
```

은 조회 실패가 아니라 명시적으로 관측된 null 값이다.

### ✅ 77. 테스트 데이터

```typescript
const checks: ConfigCheck[] = [
  {
    key: 'notification.autoSend',
    expected: false,
    actual: true,
  },
  {
    key: 'workflow.maxRetries',
    expected: 3,
    actual: 3,
  },
  {
    key: 'security.auditEnabled',
    expected: true,
    actual: undefined,
  },
];

const results = checks.map(detectDrift);
```

### ✅ 78. 기대 결과

```text
notification.autoSend
DRIFTED

workflow.maxRetries
IN_SYNC

security.auditEnabled
NOT_VERIFIED
```

### ✅ 79. 실제 구현 시 필요한 보완

```text
Schema Validation

Array / Object Normalization

Source Verification

Configuration Version

Risk Classification

Sensitive Field Handling

Evidence
```

### ✅ 80. 이 코드의 역할

Drift Detection의 핵심 비교 개념을 보여준다.

실제 AWS 리소스 설정이나 IAM 정책의 의미적 동등성까지 판단하지는 않는다.

## 9. 설정 무결성과 Checksum

### ✅ 81. Configuration Integrity

승인된 설정이 변경되지 않았다는 사실을 검증하는 것이다.

### ✅ 82. Content Hash

설정의 정규화된 내용을 SHA-256 등으로 Hash할 수 있다.

### ✅ 83. 예시

```text
Approved Configuration
       ↓
Canonical Serialization
       ↓
SHA-256
       ↓
Expected Checksum
```

### ✅ 84. Runtime 비교

```text
Runtime Configuration
       ↓
Canonical Serialization
       ↓
SHA-256
       ↓
Actual Checksum
```

### ✅ 85. Checksum 비교

```text
Expected Hash

vs

Actual Hash
```

### ✅ 86. Hash가 같다면?

동일한 정규화 기준으로 계산했다는 전제에서 비교 대상 데이터가 같다는 강한 근거가 된다.

### ✅ 87. 하지만 Hash만으로 안전을 보장하지 않는다

공격자가 설정과 함께 기준 Hash까지 바꿀 수 있다면 검증 의미가 약해진다.

### ✅ 88. 신뢰할 수 있는 기준이 필요하다

예:

```text
Protected Git Branch

Approved Build Artifact

Verified Deployment Manifest

Signed Policy Bundle
```

### ✅ 89. Signature

디지털 서명을 사용하면 승인된 발급자의 설정인지 검증하는 데 도움이 된다.

### ✅ 90. Secret 원문 Hash 주의

비밀번호나 짧은 API Secret의 단순 Hash를 저장·공개하면 값 추측 공격에 악용될 수 있다.

### ✅ 91. Secret은 별도 정책

가능하면 다음 메타데이터를 확인한다.

```text
Secret Identifier

Approved Version

Rotation Status

Access Permission

Last Modified Metadata
```

### ✅ 92. Secret Version이 일치하면 충분할까?

항상 그렇지는 않다.

같은 Version이라도 실제 실행 환경에서 잘못된 Secret을 참조하거나 이전 캐시를 사용할 수 있다.

따라서 Version 확인과 실제 인증·연결 테스트를 목적에 따라 구분한다.

### ✅ 93. Secret을 Drift Report에 출력하지 않는다

```text
Expected Secret:
원문

Actual Secret:
원문
```

처럼 출력해서는 안 된다.

## 11. AWS CloudFormation Drift Detection

### ✅ 101. CloudFormation

AWS 리소스를 Template으로 정의하고 관리하는 IaC 서비스다.

### ✅ 102. CloudFormation Drift Detection

Stack Template에 정의된 기대 상태와 실제 리소스 상태의 차이를 확인한다.

### ✅ 103. 구조

```text
CloudFormation Template
          ↓
Expected Resource State
          ↓
AWS Resource
          ↓
Actual Resource State
          ↓
Drift Detection
```

### ✅ 104. 결과

```text
IN_SYNC

DRIFTED

NOT_CHECKED
```

등을 반환할 수 있다.

### ✅ 105. 중요한 제약

CloudFormation은 Drift Detection을 지원하는 리소스와 속성에 대해서만 검사할 수 있다.

### ✅ 106. Template에 명시한 속성

특히 Template에 명시적으로 설정된 속성이 비교 대상이다.

기본값으로 생략된 속성까지 모두 검증한다고 가정해서는 안 된다.

### ✅ 107. 예시

```text
Template
Security Group Rule A

Actual
Security Group Rule A + Rule B
```

처럼 관리 대상 속성이 변경됐다면 Drift로 확인할 수 있다.

### ✅ 108. 반대로 확인되지 않는 설정도 있다

지원하지 않는 리소스나 속성은 별도 방식으로 검증해야 한다.

### ✅ 109. CloudFormation을 사용하지 않는다면?

CloudFormation Drift Detection을 사용하기 위해 현재 인프라를 무조건 이전할 필요는 없다.

### ✅ 110. 현재 추천

실제 CloudFormation Stack으로 관리 중인 리소스에만 해당 기능을 우선 적용한다.

## 12. AWS Config와 Continuous Compliance

### ✅ 111. AWS Config란?

AWS 리소스의 구성 상태를 기록하고 정의된 규칙에 따라 준수 여부를 평가할 수 있는 서비스다.

### ✅ 112. 기본 구조

```text
AWS Resource
      ↓
Configuration Recorder
      ↓
Configuration History
      ↓
AWS Config Rule
      ↓
Compliance Result
```

### ✅ 113. AWS Config의 용도

```text
리소스 설정 변경 확인

구성 이력 조회

보안 규칙 평가

Compliance 상태 확인

운영 감사 지원
```

### ✅ 114. Continuous Recording

설정 변경을 지속적으로 기록하는 방식이다.

### ✅ 115. Daily Recording

일부 리소스 유형에 대해 일 단위 기록 방식을 선택할 수 있다.

### ✅ 116. 두 방식의 차이

Continuous Recording은 변경에 대한 관측 세분도가 높다.

Daily Recording은 비용을 줄일 수 있지만 하루 동안 발생한 개별 변경을 모두 같은 수준으로 기록하지 않을 수 있다.

### ✅ 117. 기록 범위가 중요하다

Recorder가 특정 리소스 유형을 기록하지 않는다면 해당 리소스의 구성 변화가 누락될 수 있다.

### ✅ 118. Config Rule

특정 설정이 정책을 준수하는지 평가한다.

예:

```text
암호화 설정

공개 접근 제한

로깅 활성화

백업 설정
```

### ✅ 119. Compliance 결과

```text
COMPLIANT

NON_COMPLIANT

NOT_APPLICABLE

INSUFFICIENT_DATA
```

등의 상태가 사용될 수 있다.

### ✅ 120. 비용

AWS Config는 기록한 Configuration Item과 Rule Evaluation 등 사용량에 따라 비용이 발생한다.

### ✅ 121. 처음부터 모든 리소스를 수집할까?

현재 규모에서는 실제 비용과 필요한 보안 기준을 먼저 확인하는 것이 좋다.

### ✅ 122. 추천 접근

```text
중요 리소스 선정

↓

보안 기준 정의

↓

기록 범위 검토

↓

비용 예상

↓

필요한 Rule 활성화

↓

Compliance 확인
```

### ✅ 123. AWS Config가 모든 문제를 검출하지는 않는다

애플리케이션 내부 주문 승인 정책이나 AI Tool Permission은 별도 애플리케이션 검증이 필요하다.

## 13. AWS CloudTrail로 변경 원인 조사하기

### ✅ 124. CloudTrail의 역할

AWS 계정에서 발생한 API 작업과 관리 활동을 추적하는 데 도움을 준다.

### ✅ 125. CloudTrail과 AWS Config의 차이

CloudTrail:

```text
누가 어떤 API 작업을 수행했는가?
```

AWS Config:

```text
리소스 구성이 어떤 상태였는가?
```

### ✅ 126. 함께 사용하면?

```text
AWS Resource Drift
       ↓
변경 발생 시점 확인
       ↓
CloudTrail Event 검색
       ↓
관련 Actor / API 확인
       ↓
Change Approval 대조
```

### ✅ 127. CloudTrail Event History

CloudTrail의 Event History에서는 기본적으로 최근 90일의 관리 이벤트를 조회할 수 있다.

### ✅ 128. 중요한 제약

Event History는 Region별이며 Data Event 전체를 기본적으로 제공하지 않는다.

### ✅ 129. 장기 이력

90일을 초과하는 장기 보관이나 상세 데이터 이벤트 추적이 필요하다면 Trail 또는 CloudTrail Lake 등 별도 구성을 검토해야 한다.

### ✅ 130. 비용 주의

추가 Trail, 데이터 이벤트, CloudTrail Lake, S3 저장 등은 실제 구성에 따라 비용이 발생할 수 있다.

### ✅ 131. 읽기 전용 확인 예시

```bash
aws sts get-caller-identity
```

현재 AWS CLI가 어느 자격증명으로 실행되는지 확인한다.

결과에 계정 ID와 ARN 등이 포함될 수 있으므로 외부에 무분별하게 공유하지 않는다.

### ✅ 132. CloudTrail 조회 예시

```bash
aws cloudtrail lookup-events \
  --lookup-attributes \
  AttributeKey=EventName,AttributeValue=AuthorizeSecurityGroupIngress \
  --max-results 20
```

특정 API 작업의 이력을 조사하는 예시다.

### ✅ 133. 주의

해당 명령은 현재 AWS CLI Profile과 Region을 기준으로 실행된다.

실제 변경이 발생한 계정·Region과 일치하는지 확인해야 한다.

### ✅ 134. 조사 결과를 단정하지 않는다

특정 API 이벤트가 발견됐다고 해서 그 이벤트만이 현재 설정 차이의 유일한 원인이라고 확정할 수는 없다.

이후 변경 이력과 실제 리소스 상태를 함께 확인한다.

## 14. IAM Permission Drift

### ✅ 135. IAM Drift는 위험도가 높을 수 있다

IAM Role이나 Policy가 변경되면 애플리케이션이 접근할 수 있는 AWS 리소스 범위가 달라질 수 있다.

### ✅ 136. 예시

Desired:

```text
AI Report Worker

s3:GetObject
```

Actual:

```text
AI Report Worker

s3:GetObject
s3:PutObject
s3:DeleteObject
```

### ✅ 137. 위험

AI 보고서 작업에 필요하지 않은 쓰기·삭제 권한이 추가됐을 수 있다.

### ✅ 138. 단순 JSON 비교만으로 충분하지 않다

IAM은 다음을 함께 고려해야 한다.

```text
Identity-based Policy

Resource-based Policy

Session Policy

Permission Boundary

SCP / RCP

Explicit Deny

Condition
```

### ✅ 139. Effective Permission

실제로 허용되는 작업은 여러 정책의 평가 결과에 따라 결정된다.

### ✅ 140. IAM Access Analyzer

AWS IAM Access Analyzer는 외부 접근이나 미사용 접근 등을 분석하는 데 도움을 준다.

### ✅ 141. 주요 활용

```text
외부 Principal 접근

과도한 Resource Sharing

예상하지 않은 권한 변경

Policy Validation
```

### ✅ 142. 중요한 주의

IAM Access Analyzer의 Finding이 없다는 사실만으로 모든 IAM 설정이 안전하다고 확정할 수는 없다.

### ✅ 143. 초기 점검 대상

```text
EC2 Application Role

GitHub Actions Deployment Role

Developer AWS SSO Role

S3 Resource Policy
```

등 실제 존재하는 권한부터 확인한다.

### ✅ 144. 권한 차이 발견 시

즉시 삭제하기 전에 실제 서비스 의존성과 승인된 변경 여부를 확인해야 한다.

### ✅ 152. 실제 연결 테스트

### ✅ 153. 중요한 원칙

**Secret의 무결성 검증과 Secret 원문 노출은 구분해야 한다.**

## 16. Feature Flag Drift

### ✅ 154. Feature Flag도 운영 정책이다

예:

```text
AI 자동 상담

알림 자동 발송

사전예약 안내 기능

신규 신청 모달

Bulk Redrive
```

등을 Flag로 제어할 수 있다.

### ✅ 155. Desired Flag

```text
bulkRedrive.enabled = false
```

### ✅ 156. Actual Flag

```text
bulkRedrive.enabled = true
```

### ✅ 157. 왜 위험할까?

관리자가 승인하지 않은 대량 재처리 기능이 활성화될 수 있다.

### ✅ 158. Flag Source of Truth

Git, DB, 외부 Flag Provider 중 실제 운영 기준을 정한다.

### ✅ 159. Flag Version

Flag 변경 이력과 승인자를 기록한다.

### ✅ 160. OpenFeature

OpenFeature는 다양한 Feature Flag Provider를 추상화해 애플리케이션에서 사용할 수 있는 표준 API를 제공한다.

### ✅ 161. Evaluation Context

일부 Flag는 다음 조건에 따라 서로 다른 값을 반환한다.

```text
Environment

User

Tenant

Application

Targeting Key
```

### ✅ 162. 단순 Flag 값만 비교하면 부족할 수 있다

예:

```text
기본값
false
```

이지만 특정 관리자 계정에만:

```text
true
```

가 적용될 수 있다.

### ✅ 163. 따라서 중요한 Flag는 Context별로 확인한다

```text
Default

Production

Staff

Admin

Specific Test Group
```

### ✅ 164. 안전한 기본값

고위험 자동 실행 Flag는 Provider 조회 실패 시 안전한 기본값을 사용하도록 설계할 수 있다.

### ✅ 165. Feature Flag로 Authorization을 대체하지 않는다

Flag가 true라고 해서 인증·권한·업무 검증을 생략해서는 안 된다.

### ✅ 166. 1020·1021과 연결

AI Agent는 사용할 수 있는 Tool이 늘어나면서 실제 실행 범위도 커질 수 있다.

### ✅ 167. Desired Tool List

```text

public_faq.read
```

### ✅ 168. Actual Tool List

```text
CustomerSupportAgent

public_product.read

public_faq.read

order.update_status
```

### ✅ 169. 위험

승인되지 않은 Write Tool이 연결됐을 수 있다.

### ✅ 170. Drift 검사 대상

```text

Allowed Actions

MCP Server

Credential Scope

```

### ✅ 171. Tool Description도 변경될 수 있다

MCP Server나 외부 Tool이 업데이트되면서 Tool 설명이나 Arguments가 변경될 수 있다.

### ✅ 172. Tool Schema Version

### ✅ 173. 새 Tool이 자동 등록된다면?

기본적으로 별도의 승인과 검증 없이는 고위험 Tool을 활성화하지 않는 구조가 안전하다.

### ✅ 174. Agent Identity와 Tool Permission 비교

```text
Expected Agent Capability

vs

Actual Registered Capability
```

를 점검한다.

### ✅ 175. Policy Enforcement

실제 Tool Gateway에서 허용되지 않은 Tool 호출을 거부해야 한다.

Drift 감지는 추가적인 감시 계층이다.

## 18. Workflow Policy Drift

### ✅ 176. Workflow에도 정책 Version이 있다

예:

```text

Step Definition

Timeout

Redrive Policy
```

### ✅ 177. 예시

Desired:

```text
notification.send

maxRetries = 3
```

Actual:

```text
notification.send

maxRetries = 10
```

### ✅ 178. 위험

외부 알림 Provider에 과도한 요청이 전달될 수 있다.

### ✅ 179. 또 다른 예시

Desired:

```text
SEND_MESSAGE
Human Approval Required
```

Actual:

```text
SEND_MESSAGE
Auto Execution
```

### ✅ 180. 위험도

이런 차이는 고객에게 직접 영향을 줄 수 있어 높은 위험으로 분류해야 한다.

### ✅ 181. Active Workflow Version

이미 실행 중인 Workflow가 구버전 정의를 사용하는 상황일 수 있다.

### ✅ 182. 모든 구버전을 Drift로 간주하지 않는다

Workflow가 시작 당시의 Version을 유지하도록 의도적으로 설계됐다면 승인된 Version Pinning일 수 있다.

### ✅ 183. 중요한 구분

```text
Approved Pinned Version

Unapproved Old Version

Current Mandatory Security Policy
```

를 구분한다.

### ✅ 184. 실행 전 재검증

기존 Workflow 정의를 유지하더라도 현재 필수 보안 정책이나 권한 철회를 우회해서는 안 된다.

## 19. Drift 탐지 주기

### ✅ 185. 매초 모든 설정을 확인해야 할까?

그럴 필요는 없다.

### ✅ 186. Event-driven Detection

변경 이벤트가 발생하면 관련 설정을 검사하는 방식이다.

### ✅ 187. Periodic Detection

일정 주기로 설정을 점검하는 방식이다.

### ✅ 188. 두 방식을 함께 사용할 수 있다

```text
Change Event
     ↓
Immediate Check
```

```text
Scheduled Verification
     ↓
Periodic Full Check
```

### ✅ 189. Event-driven의 장점

변경 이후 빠르게 검사를 시작할 수 있다.

### ✅ 190. Event-driven의 한계

이벤트를 놓치거나 전달이 지연될 수 있다.

### ✅ 191. Periodic의 장점

이벤트 유실이 있어도 주기적으로 실제 상태를 다시 확인할 수 있다.

### ✅ 192. Periodic의 한계

검사 간격 동안 Drift가 유지될 수 있다.

### ✅ 193. 위험도별 예시 주기

```text
Critical Permission
이벤트 기반 + 주기 검사

Workflow Config
배포 후 + 정기 검사

일반 보고서 설정
일 단위 검사
```

실제 주기는 시스템 규모, 비용, 요구 복구 시간에 맞춰 정한다.

### ✅ 194. 모든 AWS API를 짧은 간격으로 호출하지 않는다

API 제한, 비용, 권한 관리, 로그량을 고려한다.

## 21. 자동 복구를 하면 안 되는 이유

### ✅ 202. 가장 쉬운 자동 복구

```text
Desired State와 다름
        ↓
즉시 Desired State로 변경
```

이다.

### ✅ 203. 하지만 위험할 수 있다

예를 들어 장애 대응 중 네트워크 설정을 긴급 변경했다고 하자.

### ✅ 204. Drift Detector가 발견한다

```text
Desired
설정 A

Actual
설정 B
```

### ✅ 205. 자동 복구

```text
Actual → 설정 A
```

로 되돌린다.

### ✅ 206. 결과

장애 대응을 위해 적용한 설정이 사라지면서 서비스가 다시 중단될 수 있다.

### ✅ 207. 따라서 원인을 먼저 확인한다

```text
Drift Detected
       ↓
Change History
       ↓
Approval / Emergency Change
       ↓
Business Impact
       ↓
Risk Classification
       ↓
Remediation Decision
```

### ✅ 208. Remediation 유형

```text
REPORT_ONLY

ALERT

REQUIRE_APPROVAL

AUTOMATED_SAFE_REMEDIATION

MANUAL_REVIEW
```

### ✅ 209. 자동 복구가 적합할 수 있는 경우

영향 범위가 좁고, 재실행해도 안전하며, 명시적으로 승인된 복구 절차가 있는 경우다.

### ✅ 210. 자동 복구가 위험한 경우

```text
Production DB 변경

IAM 권한 대량 수정

네트워크 설정 변경

활성 고객 업무 변경

진행 중인 장애 대응 설정 변경
```

등이다.

### ✅ 211. 권장 초기 정책

**처음에는 Report-only Detection으로 시작하고, 실제 위험과 복구 절차가 충분히 검증된 항목만 자동 복구한다.**

## 23. Audit Evidence란?

### ✅ 218. Evidence의 의미

특정 시점에 시스템이 어떤 상태였고 어떤 검증을 수행했는지 뒷받침하는 기록이다.

### ✅ 219. 단순 로그와의 차이

로그:

```text
Drift Check Completed
```

Evidence:

```text
무엇을 검사했는가?

어떤 기준과 비교했는가?

실제 결과는 무엇인가?

어느 Version이 적용됐는가?

누가 검토했는가?
```

를 포함한다.

### ✅ 220. Evidence 예시

```json
{
  "checkId": "check-001",

  "resource": "notification-policy",

  "expectedVersion": "v5",

  "observedVersion": "v5",

  "driftStatus": "IN_SYNC",

  "complianceStatus": "COMPLIANT",

  "checkedAt": "2026-10-29T00:00:00Z"
}
```

가상 데이터 예시다.

### ✅ 221. Evidence에 포함할 주요 정보

```text
Check ID

Control ID

Resource Reference

Expected Version

Observed Version

Collector Version

Check Result

Timestamp

Source Reference
```

### ✅ 222. Drift를 발견했다면?

추가로 다음을 기록한다.

```text
Finding ID

Difference Summary

Risk Level

Related Change Request

Remediation Decision

Verification Result
```

### ✅ 223. Evidence는 검증 가능한 형태여야 한다

단순히 AI가:

```text
보안 설정 정상
```

이라고 작성한 문장은 독립적인 설정 검증의 근거가 아니다.

### ✅ 224. 실제 API 결과

신뢰된 Collector가 수집한 설정과 검증 결과를 기록해야 한다.

### ✅ 225. 원본 보관

필요하다면 Raw Snapshot을 접근 제한된 저장소에 별도 보관한다.

단 개인정보·Secret 등이 포함되지 않도록 검토해야 한다.

## 24. Evidence Integrity

### ✅ 226. Evidence도 변경될 수 있다

감사 기록 자체가 수정된다면 신뢰성이 떨어진다.

### ✅ 227. 무결성 보호 방법

```text
Access Control

Versioning

Checksum

Signed Manifest

Restricted Deletion

Audit Logging
```

등이다.

### ✅ 228. S3 저장

AWS S3를 사용한다면 Evidence Artifact를 버전 관리할 수 있다.

### ✅ 229. S3 Object Lock

특정 보존 요구에 따라 Object Lock을 검토할 수 있다.

### ✅ 230. 하지만 무조건 적용하지 않는다

Object Lock은 데이터 삭제와 보관정책에 영향을 줄 수 있다.

적용 전 비용, 보존 의무, 운영 절차를 확인해야 한다.

### ✅ 231. Hash Chain

이벤트별 Hash를 연결해 기록의 변경을 탐지하는 방식도 설계할 수 있다.

### ✅ 232. 하지만 Hash Chain만으로 완전한 감사 보장이 되지는 않는다

기준 Hash를 신뢰할 수 있는 위치에 보관하고 수정 권한을 제한해야 한다.

### ✅ 233. 중요한 원칙

**Evidence의 무결성은 Hash 계산만이 아니라 접근 통제·보관정책·변경 이력·신뢰된 수집 과정에 의해 확보된다.**

```text
    ↓

    ↓

    ↓

    ↓

    ↓
```

정해진 시각에 검사 작업을 생성한다.

### ✅ 318. 예시 Jest 테스트

```typescript
describe('Drift Detector', () => {
  it('설정 차이를 감지한다', () => {
    const result = detectDrift({
      key: 'notification.autoSend',
      expected: false,
      actual: true,
    });

    expect(result.status).toBe('DRIFTED');
  });

  it('설정 조회 실패를 정상으로 처리하지 않는다', () => {
    const result = detectDrift({
      key: 'security.auditEnabled',
      expected: true,
      actual: undefined,
    });

    expect(result.status).toBe('NOT_VERIFIED');
  });

  it('설정이 같으면 IN_SYNC다', () => {
    const result = detectDrift({
      key: 'workflow.maxRetries',
      expected: 3,
      actual: 3,
    });

    expect(result.status).toBe('IN_SYNC');
  });
});
```

### ✅ 319. 중요한 제한

이 테스트는 설정 비교 함수를 검증한다.

실제 Production의 AWS 보안 준수 여부를 검증한 것은 아니다.

## 📌 요약

1028에서는 Policy as Code를 통해 운영 규칙을 일관되게 관리하는 방법을 다뤘다.

```text
Policy Definition
        ↓
Policy Test
        ↓
Impact Analysis
        ↓
Approval
        ↓
Deployment
```

1029에서는 이 정책이 실제 운영 환경에서도 계속 적용되는지 검증하는 방법을 다뤘다.

```text
Approved Configuration
          ↓
Desired State
          ↓
Read-only Collector
          ↓
Actual State
          ↓
Drift Detection
          ↓
Compliance Evaluation
          ↓
Risk Classification
          ↓
Finding
          ↓
Review / Remediation
          ↓
Re-verification
          ↓
Audit Evidence
```

이번 편에서 가장 중요한 원칙은 다음과 같다.

**첫 번째 — Git에 적힌 설정과 실제 운영 설정은 다를 수 있다.**

```text
Git:
Auto Send OFF

Production:
Auto Send ON
```

이라면 실제 운영 설정을 확인해야 한다.

**두 번째 — Drift와 Compliance는 다른 개념이다.**

```text
Drift:
기대 상태와 다른가?

Compliance:
정해진 기준을 준수하는가?
```

기대 상태와 실제 상태가 같더라도 그 설정 자체가 잘못됐을 수 있다.

**세 번째 — 확인되지 않은 상태를 정상으로 처리하지 않는다.**

```text
Collector Failure

↓

NOT_VERIFIED
```

로 관리한다.

**네 번째 — Drift를 발견했다고 무조건 자동 복구하지 않는다.**

```text
Drift

↓

Change History

↓

Risk Analysis

↓

Approval if Required

↓

Safe Remediation
```

이 필요하다.

**다섯 번째 — Evidence를 남긴다.**

단순히 설정이 정상이라고 보고하는 것이 아니라 어떤 상태를 어떤 기준으로 확인했는지 추적할 수 있어야 한다.

**여섯 번째 — 모든 검사는 비용과 운영 부담을 고려한다.**

현재 1인 개발 환경에서 AWS Config·OPA·전문 Compliance Platform을 한꺼번에 도입할 필요는 없다.

기존 NestJS·PostgreSQL·GitHub Actions와 AWS의 읽기 전용 API를 이용해 중요한 설정부터 검증할 수 있다.

현재 프로젝트의 현실적인 적용 순서는 다음과 같다.

```text
1. 중요 설정 목록 작성

2. Source of Truth 정의

3. Runtime Version 기록

4. Read-only Collector

5. Drift Comparison

6. Critical Security Checks

7. Finding / Alert

8. Periodic Verification

9. Audit Evidence

10. 필요한 경우 Controlled Remediation
```

특히 고객 주문·알림 발송·AI Tool Calling·AWS IAM과 연결된 설정은 우선순위가 높다.

반면 중요도가 낮은 UI Flag나 보고서 출력 설정은 간단한 주기 검사만으로 충분할 수 있다.

최종적으로 기억해야 할 원칙은 다음과 같다.

**정책을 코드로 정의하고 배포하는 것은 시작일 뿐이다. 운영 시스템이 실제로 승인된 정책을 따르고 있는지 지속적으로 확인하고, 차이가 발생했다면 원인과 영향을 검증한 뒤 안전하게 수정할 수 있어야 한다.**

이를 통해 시스템의 현재 상태를 추측하지 않고 실제 관측 결과와 감사 근거로 운영할 수 있다.

```text
Configuration Verified
        ↓
Synthetic Business Check
        ↓
Authentication / Authorization
        ↓
Application Workflow Verification
        ↓
External Dependency Check
        ↓
Result Validation
        ↓
Alert / Evidence
```

특히 다음 내용을 중심으로 정리한다.

- 설정 검증과 실제 기능 검증의 차이
- Synthetic Monitoring과 Business Transaction Monitoring
- 관리자 주문 검색·신청 모달·상품정보 API 검증
- 고객 알림 발송의 안전한 Mock 또는 Test 경로
- 인증·권한 회귀 테스트
- 외부 API 의존성 검사
- Production에서 Side Effect를 발생시키지 않는 검증 구조
- 배포 후 Smoke Test
- Canary Verification과 Release Gate
- 자동 증거 수집 및 운영 보고서
- NestJS·PostgreSQL·AWS·GitHub Actions 기반 구현
- Codex를 활용한 실전 테스트 자동화 프롬프트

목표는 단순히 서버가 살아 있다는 사실이 아니라 **실제 고객과 관리자가 사용하는 핵심 업무 흐름이 정상적으로 동작하고 있다는 근거를 지속적으로 확보하는 것**이다.
