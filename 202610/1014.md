# 1014 운영 자동화/AI 워크플로우 심화 (38/N): Data Lineage, Change Impact Analysis, Dependency Graph와 Blast Radius 관리

## 1. 코드 한 줄의 수정이 여러 기능에 영향을 줄 수 있다

### ✅ 1. 변경 자체보다 영향 범위를 모르는 것이 위험하다

예를 들어 NestJS에서 다음 필드를 수정한다고 하자.

```ts
visitorId: string | null;
```

개발자는 단순히 주문에 저장되는 방문자 식별자라고 생각할 수 있다.

그런데 실제로는:

```text
Frontend
광고 유입 추적
       ↓
신청 Modal
       ↓
Order API
       ↓
NestJS DTO
       ↓
Order Service
       ↓
PostgreSQL
       ↓
Admin 주문 목록
       ↓
유입 분석 Report
       ↓
AI Marketing Insight
```

로 연결돼 있을 수 있다.

이때 필드를 삭제하거나 의미를 변경하면 주문 생성은 정상적으로 동작하더라도 관리자 분석과 AI Report의 정확도가 떨어질 수 있다.

**1014의 핵심은 코드를 변경하기 전에 그 변경이 어디까지 전파되는지 알아내는 것이다.**

### ✅ 2. 직접적인 영향과 간접적인 영향은 다르다

예:

```text
orders.visitorId 삭제
```

직접 영향:

```text
Prisma Model

Order DTO

Order Service
```

간접 영향:

```text
Admin Filtering

유입 통계

광고 성과 분석

AI Insight
```

이다.

직접 영향은 컴파일 오류로 나타날 수 있지만 간접 영향은 조용히 발생할 수 있다.

### ✅ 3. TypeScript가 모든 영향을 찾아주지는 않는다

TypeScript는 정적 타입으로 표현된 코드의 문제를 발견하는 데 도움이 된다.

하지만 다음은 별도 확인이 필요할 수 있다.

```text
Raw SQL

Dynamic Property Access

외부 API Payload

CSV / Excel Column

네이버 EP

S3 JSON Artifact

Database View

Runtime Configuration

AI Prompt Input
```

따라서:

```text
TypeScript Build Success
```

와:

```text
Change Impact Fully Verified
```

는 다른 상태다.

## 2. Data Lineage란?

### ✅ 4. Data Lineage의 의미

Data Lineage는 데이터가 어디에서 생성돼 어떤 처리 과정을 거쳐 어디에서 사용되는지를 추적하는 것이다.

간단히:

```text
Origin
  ↓
Transformation
  ↓
Storage
  ↓
Consumer
```

의 흐름이다.

### ✅ 5. 예: 광고 유입정보

```text
Naver Advertising URL
        ↓
Frontend Landing Page
        ↓
Tracking Parameter Parser
        ↓
Application Form
        ↓
POST /orders
        ↓
NestJS Order DTO
        ↓
Order Service
        ↓
orders.attribution_source
        ↓
Admin Report
        ↓
Marketing Insight
```

이것이 하나의 Data Lineage다.

### ✅ 6. Lineage가 해결하는 질문

예:

```text
이 필드는 어디에서 만들어지는가?

값을 변경하는 코드는 어디인가?

어떤 테이블에 저장되는가?

어떤 API가 이 값을 반환하는가?

어떤 Report에서 사용하는가?

이 값이 없어지면 무엇이 깨지는가?
```

를 답할 수 있어야 한다.

### ✅ 7. Data Flow와 Data Lineage

Data Flow:

```text
현재 값이 시스템 안에서
어떻게 전달되는가?
```

Data Lineage:

```text
데이터의 출처·변환·소비 관계가
어떻게 연결되는가?
```

이다.

Lineage는 단순 호출 흐름뿐 아니라 데이터의 의미와 변환 관계까지 포함한다.

### ✅ 8. Lineage에는 여러 수준이 있다

```text
System Level

Dataset Level

Table Level

Column Level

Transformation Level
```

이다.

### ✅ 9. System Level

```text
React
→ NestJS
→ PostgreSQL
→ Reporting
```

처럼 서비스 단위로 연결한다.

### ✅ 10. Table Level

```text
orders

↓

daily_order_stats
```

처럼 테이블 단위 관계를 추적한다.

### ✅ 11. Column Level

```text
orders.attribution_source

↓

daily_order_stats.naver_order_count
```

처럼 특정 컬럼이 어떤 계산 결과에 영향을 주는지 추적한다.

### ✅ 12. Transformation Level

예:

```sql
COUNT(*) FILTER (
  WHERE attribution_source = 'NAVER'
)
```

라는 계산 규칙까지 기록한다.

이렇게 해야 단순히 두 컬럼이 연결됐다는 사실뿐 아니라 **어떤 방식으로 결과에 기여하는지** 알 수 있다.

## 3. Dependency Graph

### ✅ 13. Dependency Graph란?

시스템의 구성 요소와 의존 관계를 그래프로 표현한 것이다.

```text
Node
=
구성 요소

Edge
=
의존 관계
```

이다.

### ✅ 14. Node로 사용할 수 있는 대상

예:

```text
Frontend Component

API Endpoint

DTO Field

Service Method

Prisma Model

Database Column

Event Type

Worker Job

Export Field

External Provider

AI Report Input
```

등이다.

### ✅ 15. Edge 예시

```text
A --PRODUCES--> B

A --TRANSFORMS_TO--> B

A --READ_BY--> B

A --PUBLISHES--> B

A --CONSUMED_BY--> B
```

처럼 관계의 의미를 표현할 수 있다.

### ✅ 16. 그래프 방향을 통일해야 한다

이번 시리즈에서는 다음 기준을 사용한다.

> A → B는 A의 데이터 또는 계약이 B에 영향을 줄 수 있다는 뜻이다.

예:

```text
orders.status
      ↓
AdminOrderTable
      ↓
StatusSummaryReport
```

이 경우 `orders.status`를 변경하면 아래쪽 Consumer가 영향받을 수 있다.

### ✅ 17. 단순 연결과 영향 관계는 다르다

예:

```text
OrderService
```

가 두 가지 작업을 한다.

```text
주문 생성

알림 Job 생성
```

그렇다고 주문 생성 함수의 모든 변경이 알림 Job에 반드시 영향을 주는 것은 아니다.

따라서 실제 데이터 필드와 처리 경로를 기준으로 관계를 생성해야 한다.

### ✅ 18. 너무 넓은 Graph의 문제

나쁜 예:

```text
OrderService
→ 모든 주문 관련 기능
```

이렇게 하면 영향 범위가 항상 지나치게 넓게 나온다.

좋은 예:

```text
orders.status
→ OrderStatusDTO.status
→ AdminStatusBadge
```

처럼 가능한 수준에서 구체화한다.

### ✅ 19. Column Level이 항상 필요한 것은 아니다

전 시스템을 컬럼 단위까지 분석하려면 유지보수 비용이 커진다.

따라서 현재 규모에서는 다음 정도가 현실적이다.

```text
핵심 주문·가격·추적 데이터
→ Field Level

일반 기능
→ API / Module Level

낮은 위험의 내부 구현
→ File / Function Level
```

## 4. Blast Radius — 변경의 영향 범위

### ✅ 20. Blast Radius란?

어떤 변경이나 장애가 영향을 줄 수 있는 범위를 의미한다.

예:

```text
상품 카드 CSS 수정
```

의 영향 범위는 일반적으로 해당 UI에 집중된다.

반면:

```text
주문 상태 Enum 변경
```

은 다음을 포함할 수 있다.

```text
Frontend

Backend

Admin

Database

Webhook

Notification

Export

Analytics
```

### ✅ 21. 변경 규모와 영향 범위는 비례하지 않는다

예:

```diff
- status: 'DONE'
+ status: 'COMPLETED'
```

단 한 줄을 변경했더라도 오래된 Consumer가 `DONE`을 기대하고 있다면 여러 기능에 영향을 줄 수 있다.

### ✅ 22. Blast Radius 평가 차원

| 평가 항목 | 질문 |
|---|---|
| Consumer Reach | 영향받는 기능은 몇 개인가? |
| Business Criticality | 주문·가격·개인정보에 영향을 주는가? |
| Change Compatibility | 기존 Client와 호환되는가? |
| Reversibility | 안전하게 되돌릴 수 있는가? |
| Observability | 잘못됐을 때 감지할 수 있는가? |
| Coverage | 테스트와 의존성 분석이 충분한가? |
| External Effect | 고객·외부 플랫폼에 실제 영향이 있는가? |

### ✅ 23. 영향받는 Node 수만으로 위험을 판단하지 않는다

예:

```text
영향 Node
20개
```

이더라도 단순한 UI 문구 변경일 수 있다.

반면:

```text
영향 Node
2개
```

인데 두 번째가 고객 결제 금액을 계산하는 함수라면 위험도가 높다.

### ✅ 24. Blast Radius가 커지는 대표적인 변경

```text
공통 DTO 변경

공통 Enum 변경

Database Column 삭제

공통 Authentication 변경

Global Configuration 변경

Event Schema 변경

외부 Provider Mapping 변경

AI Report Input 변경
```

등이다.

## 5. 변경 유형별 영향 분석

### ✅ 25. 변경을 유형별로 나눈다

```text
UI Change

API Change

Database Change

Event Change

Business Rule Change

External Contract Change

Configuration Change

Security Permission Change
```

각 변경은 검증 방법이 다르다.

### ✅ 26. UI 변경

예:

```text
신청 Modal Layout
```

의 직접 영향은 Frontend에 있을 수 있다.

하지만:

```text
선택 Dropdown 사용 불가
```

같은 문제가 발생하면 실제 신청 완료율에 영향을 준다.

따라서 UI 변경도 핵심 Customer Journey에 속한다면 업무 영향 검증이 필요하다.

### ✅ 27. API 변경

예:

```text
GET /orders/:id
```

응답에서 `applicantName`을 제거한다고 하자.

영향 후보:

```text
Admin Order Detail

Customer Status Page

Excel Export

API Client

Automation Script
```

등이다.

### ✅ 28. Database 변경

예:

```text
orders.status
```

컬럼의 타입이나 의미를 변경하면:

```text
Prisma

NestJS

Admin

Statistics

Notification Rules
```

이 영향을 받을 수 있다.

### ✅ 29. Event 변경

예:

```text
ORDER_COMPLETED
```

이벤트 Payload가 변경된다면:

```text
Notification Consumer

Analytics Consumer

Audit Consumer

External Integration
```

등을 확인한다.

### ✅ 30. Configuration 변경

예:

```text
NOTIFICATION_ENABLED=false
```

라면 코드 수정 없이도 업무 동작이 바뀔 수 있다.

### ✅ 31. Security Permission 변경

예:

```text
S3 PutObject 권한 제거
```

는 소스 코드가 전혀 변경되지 않아도 Export Worker 장애를 유발할 수 있다.

### ✅ 32. 변경은 코드 Diff만으로 완전히 설명되지 않는다

실제 운영 동작에 영향을 주는 요소는 다음까지 포함한다.

```text
Source Code

Database Schema

Data

Environment Variables

AWS IAM

Feature Flags

External API Configuration

Scheduler

AI Prompt / Model Configuration
```

## 6. 실제 사례 ① — visitorId 변경

### ✅ 33. 가정할 변경

```text
orders.visitorId
```

를 삭제하거나 다른 식별자로 변경한다고 하자.

실제 프로젝트에 해당 필드가 있는지는 먼저 확인해야 한다.

### ✅ 34. Data Lineage

```text
Frontend Landing
        ↓
Tracking Service
        ↓
Order Application Request
        ↓
NestJS DTO
        ↓
Order Entity
        ↓
orders.visitor_id
        ↓
Admin Order Search
        ↓
Acquisition Report
        ↓
AI Marketing Insight
```

### ✅ 35. 직접적인 영향

```text
Prisma Schema

Order DTO

Order Service

Order Repository
```

### ✅ 36. 간접적인 영향

```text
관리자 필터

광고 성과 집계

유입 채널 분석

보고서

AI 마케팅 제안
```

### ✅ 37. 개인정보 영향도 확인해야 한다

방문자 식별자를 변경하면 다음 문제가 생길 수 있다.

```text
기존 방문자와 신규 방문자 연결

추적 동의 범위

Retention Policy

삭제 요청 처리

비식별화 여부
```

따라서 단순 리팩터링이 아니라 Data Lifecycle 변경일 수 있다.

### ✅ 38. 삭제 전에 질문할 것

```text
실제로 어느 기능에서 사용 중인가?

대체 필드가 존재하는가?

기존 데이터 Backfill이 필요한가?

이전 Client도 해당 필드를 전송하는가?

기존 Report 기준이 바뀌는가?

개인정보 보관 정책도 바뀌는가?
```

### ✅ 39. 권장 변경 방식

예:

```text
Old Field
visitorId

New Field
trackingSessionId
```

로 바꾼다면:

```text
1. 새 필드 추가

2. 신규 Request에서 새 필드 수집

3. 기존 Consumer 호환

4. 기존 데이터와 Mapping 검증

5. Report 전환

6. 구버전 Client 확인

7. 기존 필드 제거
```

방식으로 진행한다.

### ✅ 40. 이름만 바꾼다고 같은 데이터는 아니다

`visitorId`와 `trackingSessionId`가 실제로 다른 개념이라면 단순 이름 변경으로 처리하면 안 된다.

다음 차이를 확인한다.

```text
Identifier Scope

Lifetime

Uniqueness

Consent

Session Boundary

Cross-device Behavior
```

이것이 1013에서 다룬 Semantic Contract와 연결된다.

## 7. 실제 사례 ② — 주문 상태 Enum 변경

### ✅ 41. 예시 변경

```text
APPLICATION_SENT
```

를:

```text
DOCUMENT_SENT
```

로 바꾼다고 하자.

### ✅ 42. 직접 영향

```text
Prisma Enum

Order DTO

Order Service

Order State Machine
```

### ✅ 43. 간접 영향

```text
관리자 상태 필터

상태 변경 이력

알림톡 발송 조건

고객 진행 현황 페이지

상태 통계

Excel Export

Webhook Consumer
```

### ✅ 44. 가장 위험한 부분은 의미 변경이다

예:

```text
APPLICATION_SENT
=
공식 신청서 URL 전달 완료
```

였는데:

```text
DOCUMENT_SENT
=
고객이 신청서 작성 완료
```

라면 단순 Label 변경이 아니다.

업무 의미 자체가 변경됐다.

### ✅ 45. DB에 과거 Enum 값이 남아 있을 수 있다

예:

```text
Old DB Rows
APPLICATION_SENT

New Code
DOCUMENT_SENT
```

이렇게 되면 신규 코드에서 과거 데이터를 제대로 처리하지 못할 수 있다.

### ✅ 46. Event와 History에도 과거 값이 남는다

```text
order_status_histories

outbox_events

workflow_runs

audit_logs
```

등에 기존 상태값이 기록돼 있을 수 있다.

따라서 현재 `orders.status`만 변경해서는 부족하다.

### ✅ 47. 과거 Audit 이력을 무조건 변경하지 않는다

과거 당시의 실제 상태명을 기록한 Audit이라면 역사적 사실로 보존할 수 있다.

UI 표현을 새 용어로 보여주더라도 원본 이력의 의미는 유지해야 한다.

### ✅ 48. Consumer-first Migration

권장:

```text
Consumer
새 Enum 이해

↓

Producer
새 Enum 발행

↓

기존 데이터 정리

↓

Legacy Consumer 제거
```

순서다.

### ✅ 49. Rollback Compatibility도 확인

신규 값으로 데이터를 저장하기 시작한 뒤 구버전 서버로 Rollback하면 구버전이 그 값을 이해하지 못할 수 있다.

따라서:

```text
Code Rollback
가능
```

이라고:

```text
Data Rollback
가능
```

인 것은 아니다.

## 8. 실제 사례 ③ — 상품 가격 변경

### ✅ 50. 가격은 영향도가 높은 Domain이다

예:

```text
products.price
```

또는 실제 가격 계산 필드를 변경한다고 하자.

### ✅ 51. 영향 범위

```text
Pricing Source
      ↓
Product API
      ↓
Product Detail UI
      ↓
Application Form
      ↓
Order Snapshot
```

그리고 별도 경로로:

```text
Pricing Source
      ↓
Naver EP Generator
      ↓
External Shopping Platform
```

가 있을 수 있다.

### ✅ 52. 중요한 것은 가격의 출처가 하나인지 확인하는 것이다

잘못된 구조:

```text
Frontend에서 가격 계산

Backend에서 가격 계산

EP에서 별도 가격 계산
```

각각 다른 Logic을 쓰면 불일치 위험이 높다.

### ✅ 53. Source of Truth

예:

```text
Pricing Service / Pricing Policy
```

가 공식 기준이라면 모든 Consumer가 해당 기준을 활용하도록 설계한다.

### ✅ 54. 가격 변경 시 확인할 항목

```text
단말기 금액

요금제

지원금

선택약정

공시지원금

프로모션

부가서비스 조건

네이버 EP

고객 신청 Snapshot
```

실제 가격 모델과 상품 판매 정책에 맞춰 검증한다.

### ✅ 55. 주문 Snapshot은 현재 상품 가격과 다를 수 있다

예:

```text
신청 당시 가격
100,000원

현재 상품 가격
120,000원
```

이라고 하자.

이때 과거 주문의 가격을 현재 가격에 맞춰 자동 수정해서는 안 된다.

### ✅ 56. Historical Snapshot과 Live Pricing을 구분한다

```text
Current Product Price
현재 판매 조건

Order Price Snapshot
신청 당시 조건
```

이다.

### ✅ 57. 영향 분석은 관계의 의미까지 포함해야 한다

```text
Current Price Changed
```

라는 이유로:

```text
Existing Order Snapshot
```

을 전부 업데이트하도록 제안하면 위험하다.

따라서 Edge에는 단순 연결뿐 아니라:

```text
READS_LIVE_VALUE

COPIES_SNAPSHOT

CALCULATES_FROM

HISTORICAL_REFERENCE
```

같은 의미를 부여할 수 있다.

## 11. PostgreSQL에서 의존성 확인하기

### ✅ 74. PostgreSQL도 내부 Dependency를 관리한다

PostgreSQL은 다음 객체 사이의 의존 관계를 관리한다.

```text
Table

Column

Foreign Key

View

Function

Trigger

Constraint
```

등이다.

### ✅ 75. pg_depend

PostgreSQL의 `pg_depend` 카탈로그는 DB 객체 사이의 의존 관계를 기록한다.

하지만 다음까지 자동으로 알 수 있는 것은 아니다.

```text
React Component

NestJS Service

AI Prompt

Naver EP Generator
```

즉 DB 내부 Dependency와 Application Dependency는 구분해야 한다.

### ✅ 76. Foreign Key Dependency 조회 예시

```sql
SELECT
  con.conname AS constraint_name,
  con.conrelid::regclass AS dependent_table,
  con.confrelid::regclass AS referenced_table
FROM pg_constraint con
WHERE con.contype = 'f'
  AND con.confrelid = 'public.orders'::regclass;
```

이 쿼리는 `public.orders` 테이블을 참조하는 외래 키를 조회하는 예시다.

실제 Schema에 맞춰 사용한다.

### ✅ 77. View Dependency도 확인해야 한다

예:

```text
orders

↓

order_summary_view
```

가 있다면 `orders` 컬럼 제거 시 View가 영향을 받을 수 있다.

### ✅ 78. DROP CASCADE의 위험

PostgreSQL은 의존 객체가 있는 경우 단순 DROP을 막을 수 있다.

이때:

```sql
DROP TABLE orders CASCADE;
```

같은 방식으로 강제로 진행하면 의존 객체까지 제거될 수 있다.

**운영 Migration에서 Dependency Error가 발생했다고 무조건 CASCADE를 추가해서는 안 된다.**

### ✅ 79. Prisma Migration도 완전한 Dependency Analysis는 아니다

Prisma의 Schema Diff는 지원되는 DB 구조 차이를 비교하는 데 유용하다.

그러나 모든 PostgreSQL 기능이나 Application Consumer까지 분석하는 것은 아니다.

특히 Prisma 버전별 CLI와 지원 범위가 달라질 수 있으므로 현행 버전을 먼저 확인해야 한다.

### ✅ 80. DB 변경 전에 확인할 것

```text

Migration History

Constraints

Foreign Keys

Views

Functions

Triggers

Raw SQL

Application Consumers
```

이다.

## 14. Graph Traversal — 영향받는 기능 찾기

### ✅ 99. 직접 영향과 전파 영향

예:

```text
A → B → C → D
```

에서 A를 변경한다면:

```text
Direct Impact
B
```

```text
Transitive Impact
C, D
```

가 된다.

### ✅ 100. Forward Impact Analysis

특정 데이터가 어디에서 사용되는지 찾는다.

```text
Source

↓

Consumers
```

방향이다.

### ✅ 101. Backward Lineage Analysis

반대로 특정 Report가 어디에서 데이터를 가져오는지 찾는다.

```text
Report

↑

Sources
```

방향이다.

### ✅ 102. 둘은 질문이 다르다

Forward:

```text
이 필드를 바꾸면
무엇이 영향받는가?
```

Backward:

```text
이 Report 숫자는
어디에서 왔는가?
```

이다.

### ✅ 103. 간단한 TypeScript 예시

```ts
interface Edge {
  from: string;
  to: string;
}

function getImpactedNodes(
  start: string,
  edges: Edge[],
): string[] {
  const graph = new Map<string, string[]>();

  for (const edge of edges) {
    const targets = graph.get(edge.from) ?? [];

    targets.push(edge.to);

    graph.set(edge.from, targets);
  }

  const visited = new Set<string>([start]);

  const queue = [start];

  while (queue.length > 0) {
    const current = queue.shift()!;

    for (const next of graph.get(current) ?? []) {
      if (visited.has(next)) {
        continue;
      }

      visited.add(next);
      queue.push(next);
    }
  }

  visited.delete(start);

  return [...visited];
}
```

이 코드는 Graph에 명시적으로 등록된 Edge를 따라가는 단순 예시다.

### ✅ 104. 사용 예시

```ts
const edges = [
  {
    from: 'db.orders.attribution_source',
    to: 'report.acquisition',
  },
  {
    from: 'report.acquisition',
    to: 'ai.marketing_insight',
  },
];

const impacted = getImpactedNodes(
  'db.orders.attribution_source',
  edges,
);

console.log(impacted);
```

예상 결과:

```text
report.acquisition

ai.marketing_insight
```

### ✅ 105. 이 알고리즘이 모든 영향을 발견하는 것은 아니다

Graph에 등록되지 않은 Consumer는 찾을 수 없다.

따라서 결과는:

```text
Known Impact
```

이지:

```text
Complete Impact
```

가 아니다.

### ✅ 106. 순환 관계도 고려한다

예:

```text
A → B

B → C

C → A
```

같은 순환이 존재할 수 있다.

위 예시에서는 `visited`를 사용해 무한 반복을 피한다.

### ✅ 107. Edge Type에 따라 전파 규칙이 달라질 수 있다

예:

```text
Snapshot Copy
```

관계는 현재 원본 값 변경이 과거 Snapshot에 직접 전파되지 않을 수 있다.

따라서 실제 Impact Analyzer는 변경 유형과 Edge 의미를 함께 확인해야 한다.

### ✅ 111. Change Risk는 근거 기반으로 판단한다

예:

```text
LOW

MEDIUM

HIGH

CRITICAL
```

로 분류할 수 있다.

### ✅ 112. HIGH Risk 조건 예

```text
고객 주문 경로 변경

금액 계산 변경

개인정보 처리 변경

기존 API 필수 필드 제거

DB Column 삭제

알림 발송 조건 변경
```

등이다.

### ✅ 113. CRITICAL Risk 조건 예

```text
데이터 손실 가능 Migration

핵심 주문 상태와 이력의 동시 변경

Production 전체 인증 정책 변경

검증되지 않은 외부 Side Effect 변경
```

등이다.

### ✅ 114. LOW Risk 조건 예

```text
독립적인 UI 문구 변경

영향받는 Contract 없음

관련 테스트 확인
```

같은 경우다.

단 실제 영향 범위가 확인됐다는 전제가 필요하다.

### ✅ 115. Unknown Consumer가 있다면 위험도에 반영한다

```text
Unknown
=
Low Risk
```

가 아니다.

중요한 Domain에서 소비자가 확인되지 않았다면 분석 범위가 부족하다는 뜻일 수 있다.

## 16. Change Impact와 테스트 범위

### ✅ 116. 모든 변경마다 전체 테스트를 실행해야 할까?

이상적으로는 충분한 전체 회귀 테스트가 좋다.

그러나 테스트 규모가 커지면:

```text
실행 시간

비용

개발 속도
```

부담이 생긴다.

따라서 영향 범위를 이용해 우선 테스트를 선정할 수 있다.

### ✅ 117. Change-based Test Selection

예:

```text
Changed Field
orders.status

↓

Impacted Nodes
Order API
Admin
Notification

↓

Selected Tests
Order Service Test
Admin Contract Test
Notification Rule Test
```

이다.

### ✅ 118. 직접 Unit Test만으로는 부족할 수 있다

예:

```text
Order Service Unit Test
PASS
```

하더라도:

```text
Admin Order Filter
FAIL
```

이 발생할 수 있다.

### ✅ 119. 테스트를 네 수준으로 나눈다

```text
Unit Test

Integration Test

Contract Test

End-to-End Test
```

다.

### ✅ 120. Unit Test

변경된 함수의 직접적인 로직을 검사한다.

### ✅ 121. Integration Test

DB, Service, Repository 간 관계를 검사한다.

### ✅ 122. Contract Test

API·Event·외부 Provider 경계의 호환성을 검사한다.

### ✅ 123. E2E Test

실제 사용자가 경험하는 업무 흐름을 검사한다.

예:

```text
상품 조회

↓

신청 Modal

↓

신청 접수

↓

관리자 주문 확인
```

이다.

### ✅ 124. 어떤 변경에서 E2E가 중요할까?

예:

```text
주문 생성

고객 인증

신청 Form

결제/가격

주문 상태 변경
```

같은 핵심 업무 경로다.

### ✅ 125. Impact Graph가 누락됐을 수도 있다

따라서 영향 분석이 아무 문제도 발견하지 못했다고 핵심 회귀 테스트를 생략하는 것은 위험하다.

핵심 경로에는 별도의 상시 Smoke Test가 필요하다.

## 17. CI/CD Change Impact Gate

### ✅ 126. Git Diff를 시작점으로 활용한다

예:

```bash
git diff --name-only BASE_SHA HEAD_SHA
```

로 변경 파일을 확인한다.

`BASE_SHA`, `HEAD_SHA`는 실제 비교할 Commit으로 지정한다.

### ✅ 127. 변경 파일만으로는 충분하지 않다

예:

```text
prisma/schema.prisma
```

파일이 변경됐다.

이 사실만으로 어떤 Model 또는 필드가 변경됐는지는 알 수 없다.

따라서:

```text
File Diff

↓

Symbol / Contract Diff

↓

Dependency Graph Lookup
```

으로 분석한다.

### ✅ 128. Change Classifier

예:

```text
UI_ONLY

API_CONTRACT

DATABASE_SCHEMA

EVENT_CONTRACT

BUSINESS_RULE

CONFIGURATION

SECURITY
```

로 구분한다.

### ✅ 129. 변경 분류를 잘못하면 위험하다

예:

```text
OrderService.ts
```

수정이 항상 Business Rule 변경인 것은 아니다.

단순 로그 문구 변경일 수도 있다.

반대로 작은 DTO 수정은 API Contract 변경일 수 있다.

따라서 파일 경로 기반 분류만으로 최종 위험을 결정하지 않는다.

### ✅ 130. 자동 분석의 초기 목표

처음에는:

```text
Change Impact Report 생성
```

만 수행한다.

곧바로 배포 차단 Gate로 연결하지 않는다.

### ✅ 131. 왜 처음부터 Blocking하지 않을까?

Graph가 불완전하면 정상적인 변경도 계속 차단할 수 있기 때문이다.

먼저 Report와 실제 영향을 비교해 신뢰도를 높인다.

### ✅ 132. 점진적인 Gate 강화

```text
Phase 1
Read-only Report

↓

Phase 2
Warning

↓

Phase 3
Critical Contract Gate

↓

Phase 4
High-risk Approval
```

방식이 현실적이다.

### ✅ 133. Critical Contract Gate 예

다음 변경이 감지되면 검토한다.

```text
API 필수 필드 삭제

주문 상태 Enum 제거

가격 단위 변경

Database DROP

Event Version 호환성 파괴
```

### ✅ 134. 실패 조건을 명확히 한다

예:

```text
API Contract Breaking Change

AND

Consumer Compatibility Not Verified
```

이면:

```text
Release Gate
FAIL
```

로 처리할 수 있다.

### ✅ 135. Unknown은 별도로 취급한다

예:

```text
Graph Coverage
UNKNOWN

Critical Consumer
UNVERIFIED
```

이라면 자동으로 PASS하지 않는다.

필요하면 수동 검토를 요구한다.

## 18. 배포 순서까지 포함하는 영향 분석

### ✅ 136. 영향받는 기능을 찾는 것만으로는 부족하다

예:

```text
새 DB Column

새 API

새 Frontend
```

모두 수정했다.

하지만 배포 순서가 잘못되면 장애가 발생할 수 있다.

### ✅ 137. Expand-Migrate-Contract

1002와 연결한다.

```text
Expand

↓

Compatible Application

↓

Backfill

↓

Consumer Migration

↓

Contract
```

방식이다.

### ✅ 138. API 변경 예

```text
New Response Field
```

를 추가한다면:

```text
Backend 먼저 배포

↓

Consumer 지원

↓

기존 필드 Deprecation

↓

Legacy 제거
```

순서를 고려한다.

### ✅ 139. Event 변경 예

```text
Event v1
```

에서:

```text
Event v2
```

로 바뀐다면 기존 Consumer를 먼저 호환시킬 수 있다.

### ✅ 140. Frontend는 구버전이 남을 수 있다

배포 직후 모든 사용자가 최신 Frontend를 실행하는 것은 아니다.

브라우저 Cache, 열린 탭, Service Worker 등이 영향을 줄 수 있다.

따라서 신규 Backend는 일정 기간 구버전 Client와 호환돼야 할 수 있다.

### ✅ 141. 외부 Consumer는 배포 통제가 어렵다

내부 Frontend는 직접 업데이트할 수 있지만 외부 시스템은 그렇지 않을 수 있다.

따라서 외부 계약 변경에는:

```text
Versioning

Deprecation Notice

Compatibility Period

Consumer Verification
```

이 필요하다.

## 19. Release와 Rollback 영향 분석

### ✅ 142. 변경 전 Forward Impact

질문:

```text
새 변경을 적용하면
무엇이 달라지는가?
```

이다.

### ✅ 143. Rollback Impact

질문:

```text
새 변경을 적용한 이후
이전 코드로 되돌려도 안전한가?
```

이다.

### ✅ 144. Rollback이 위험한 사례

예:

```text
New Enum
DOCUMENT_SENT
```

을 DB에 저장하기 시작했다.

그런데 구버전 Application은:

```text
APPLICATION_SENT
```

만 이해한다.

### ✅ 145. 코드 Rollback만으로 해결되지 않는다

```text
Application Rollback
SUCCESS

Data Compatibility
FAIL
```

일 수 있다.

### ✅ 146. Roll-forward가 더 안전할 수도 있다

이미 새로운 데이터 형식이 Production에 기록됐다면, 이전 버전으로 되돌리기보다 새 코드의 문제를 수정하는 Roll-forward가 더 적합할 수 있다.

상황에 따라 판단한다.

### ✅ 147. 외부 Side Effect는 Rollback되지 않는다

예:

```text
알림톡 전송

외부 API 호출

네이버 EP 발행
```

은 Application Rollback으로 자동 취소되지 않는다.

### ✅ 148. 따라서 Rollback Plan에도 External Impact가 필요하다

```text
이미 발송된 메시지

이미 생성된 주문

외부로 전달된 데이터

이미 처리된 Webhook
```

을 확인해야 한다.

## 20. Change Impact의 정확도 관리

### ✅ 149. False Positive

실제로 영향이 없는데 영향이 있다고 보고하는 경우다.

예:

```text
공통 DTO를 참조하는 코드

하지만 변경 필드를 사용하지 않음
```

일 수 있다.

### ✅ 150. False Negative

실제로 영향이 있는데 찾지 못하는 경우다.

예:

```text
Raw SQL에서 특정 컬럼 사용

그래프에는 누락
```

됐다.

### ✅ 151. 중요한 시스템에서는 False Negative가 특히 위험하다

영향이 없다고 판단해 테스트를 생략할 수 있기 때문이다.

### ✅ 152. Coverage Report

예:

```text
Known Consumer
8개

Verified Consumer
6개

Unverified
2개
```

처럼 기록한다.

### ✅ 153. Coverage가 낮으면 결론도 제한한다

예:

```text
Impact Assessment
INCOMPLETE
```

로 표시한다.

### ✅ 154. No Impact라는 결론을 쉽게 내리지 않는다

```text
Search Result
0
```

은:

```text
No Dependency Proven
```

과 다르다.

### ✅ 155. Graph Freshness

예:

```text
Last Verified
2026-08-01

Current Release
2026-10-14
```

라면 최근 코드 변경이 반영됐는지 확인한다.

### ✅ 156. Release별 Graph Snapshot

예:

```text
Graph Version
commit abc123
```

처럼 현재 소스와 맞는 버전을 저장할 수 있다.

## 📌 요약

1013에서는:

```text
Data Contract

↓

Data Quality Monitoring

↓

Anomaly Detection

↓

Schema Drift
```

를 다뤘다.

1014에서는 그다음 질문을 다뤘다.

```text
어떤 필드나 API를 변경할 때

우리는 그 변경이

어디까지 영향을 주는지

알고 있는가?
```

가장 중요한 개념은 **Data Lineage**다.

```text
Source
    ↓
Transformation
    ↓
Storage
    ↓
Consumer
```

데이터의 흐름을 추적한다.

그다음 **Dependency Graph**로 관계를 표현한다.

```text
A → B → C → D
```

이 상태에서 A를 변경하면:

```text
Direct Impact
B

Transitive Impact
C, D
```

를 찾는다.

그리고 **Blast Radius**로 실제 위험을 평가한다.

```text
Consumer 수

Business Criticality

Compatibility

Rollback Safety

External Side Effect
```

를 함께 본다.

여기서 중요한 것은 단순히 변경 파일 개수를 세는 것이 아니다.

예:

```text
변경 파일
1개
```

라도:

```text
공통 주문 상태 Enum
```

을 바꾼다면:

```text
Frontend

Admin

Order Service

Database

Notification

Export

Analytics
```

전반에 영향을 줄 수 있다.

반면:

```text
변경 파일
10개
```

라도 독립적인 UI 개선이라면 위험이 상대적으로 낮을 수 있다.

현재 프로젝트에서 가장 현실적인 구조는:

```text
Git Diff

↓

Changed Symbol

↓

Static Search

↓

Dependency Manifest

↓

Forward Impact Analysis

↓

Risk Classification

↓

Required Tests

↓

Release Plan

↓

Post-deploy Monitoring
```

이다.

처음부터 Graph Database나 복잡한 CodeQL Pipeline을 구축할 필요는 없다.

우선:

```text
1. Order Status

2. Order Tracking

3. Product Pricing

4. Notification

5. Naver EP
```

이 다섯 개의 핵심 Data Lineage를 문서화한다.

이후 Codex가 Git Diff를 분석할 때 해당 문서를 참조하도록 구성하면 된다.

중요한 주의점은:

```text
코드 검색 결과 없음
≠
영향받는 Consumer 없음
```

이라는 것이다.

외부 API, Raw SQL, Runtime Configuration, AI Prompt처럼 Repository 검색으로 완전히 파악하기 어려운 경로가 존재할 수 있다.

따라서 결과를:

```text
CONFIRMED

POTENTIAL

UNKNOWN
```

으로 구분해야 한다.

또한 영향 분석의 최종 목적은 문서를 예쁘게 만드는 것이 아니다.

**분석 결과를 실제 테스트·배포·Rollback·Monitoring 결정에 연결하는 것**이 중요하다.

전체 운영 흐름은 다음과 같다.

```text
Change Request
       ↓
Change Classification
       ↓
Data Lineage
       ↓
Dependency Graph
       ↓
Blast Radius Analysis
       ↓
Contract Compatibility
       ↓
Test Selection
       ↓
Deployment Plan
       ↓
Release Gate
       ↓
Post-deployment Verification
       ↓
Graph / Documentation Update
```

결국 1014의 핵심은 다음과 같다.

> **좋은 변경 관리는 코드를 수정한 뒤 문제가 발생하는지 기다리는 것이 아니라, 수정 전에 어떤 데이터와 기능이 연결돼 있는지 파악하고, 그 영향에 맞는 검증·배포·복구 계획을 준비하는 것이다.**

현재처럼 한 명이 Frontend·Backend·Admin·Database·AWS를 함께 관리하는 환경에서는 이런 영향 분석이 특히 중요하다.

모든 코드를 직접 알고 있어야 하는 부담을 줄이고, AI를 활용한 코드 변경 과정에서도 중요한 업무 규칙과 연결 관계를 놓칠 가능성을 줄일 수 있기 때문이다.
