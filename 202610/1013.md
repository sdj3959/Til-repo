## 1013 운영 자동화/AI 워크플로우 심화 (37/N): Data Quality Monitoring, Anomaly Detection, Data Contracts와 Schema Drift

## 1. 데이터 오류가 발생하지 않아도 서비스는 잘못된 판단을 할 수 있다

### ✅ 1. API가 정상이라는 것과 데이터가 정확하다는 것은 다르다

예를 들어 투게더몰에서 다음과 같은 상태라고 하자.

```text
NestJS API
200 OK

PostgreSQL
HEALTHY

관리자 주문 목록
정상 조회

CloudFront
정상
```

그런데 실제 데이터에는 문제가 발생했다.

```text
어제 주문
120건

오늘 주문
35건

광고 클릭
거의 동일

방문자 수
거의 동일
```

이 경우 서버에는 명확한 장애가 없지만, 실제 고객 신청 흐름에 문제가 발생했을 가능성이 있다.

또 다른 사례도 있다.

```text
주문 생성
SUCCESS

visitorId
NULL

광고 유입코드
NULL

utm_source
NULL
```

주문은 정상적으로 생성됐다.

하지만 광고 성과 분석은 점점 부정확해진다.

**1013의 핵심은 데이터가 저장됐는지만 확인하는 것이 아니라, 데이터가 실제 업무 판단에 사용할 만큼 신뢰할 수 있는지 지속적으로 확인하는 것이다.**

### ✅ 2. Data Integrity와 Data Quality의 차이

1012의 Data Integrity는 주로 다음에 집중했다.

```text
외래 키가 올바른가?

동일 요청이 중복 주문을 만들지 않았는가?

주문 상태와 변경 이력이 일치하는가?

허용되지 않은 상태 전이가 없는가?
```

1013의 Data Quality는 더 넓은 범위를 다룬다.

```text
필요한 정보가 누락되지 않았는가?

평소와 비교해 데이터가 급격하게 감소하지 않았는가?

데이터가 제때 도착하고 있는가?

외부 API 값의 의미가 달라지지 않았는가?

분석 결과를 신뢰할 수 있는가?
```

### ✅ 3. 대표적인 Data Quality 문제

```text
Data Missing
필수 데이터 누락

Data Delay
데이터 반영 지연

Volume Anomaly
데이터량 급증/급감

Distribution Shift
값의 분포 변화

Schema Drift
필드와 타입 변화

Semantic Drift
값의 의미 변화

Contract Violation
데이터 계약 위반
```

이다.

### ✅ 4. 실제 서비스에서 더 위험한 것은 조용한 오류일 수 있다

명확한 오류:

```text
500 Internal Server Error
```

는 탐지하기 쉽다.

반면 다음 문제는 탐지하기 어렵다.

```text
주문 성공

↓

광고 유입정보 누락

↓

매출 집계에서는 자연유입으로 분류

↓

광고 성과가 실제보다 낮게 계산

↓

잘못된 광고 운영 판단
```

시스템은 전부 정상 응답을 반환한다.

하지만 잘못된 데이터가 운영 의사결정을 바꾼다.

## 2. Data Quality의 핵심 평가 기준

### ✅ 5. 데이터 품질을 하나의 숫자로 판단하지 않는다

보통 다음 차원을 구분한다.

| 차원 | 의미 | 투게더몰 예시 |
|---|---|---|
| Completeness | 필요한 값이 존재하는가? | 광고 유입코드 누락률 |
| Validity | 형식과 범위가 올바른가? | 잘못된 요금제 코드 |
| Uniqueness | 의도치 않은 중복이 없는가? | 동일 요청의 주문 중복 |
| Consistency | 시스템 간 값이 일치하는가? | 주문·알림 상태 불일치 |
| Timeliness | 제때 반영되는가? | 주문 접수 후 관리자 반영 지연 |
| Accuracy | 실제 사실과 맞는가? | 실제 판매가격과 EP 가격 일치 |
| Volume | 데이터량이 정상 범위인가? | 시간별 주문 건수 급감 |
| Distribution | 값의 분포가 비정상적으로 변했는가? | 유입 채널이 갑자기 전부 DIRECT |

### ✅ 6. Completeness — 완전성

예:

```text
주문 1,000건

유입경로 기록
900건

누락
100건
```

이면 유입경로 완전성은 90%다.

다만 모든 주문에 유입정보가 필수인지는 먼저 판단해야 한다.

추적 동의 여부, 브라우저 차단, 직접 접속 등으로 특정 값이 의도적으로 존재하지 않을 수 있다.

### ✅ 7. Null과 빈 문자열을 구분한다

예:

```text
visitorId = NULL
```

과:

```text
visitorId = ""
```

은 DB 저장 형태가 다르다.

그러나 분석 목적에서는 둘 다 유효하지 않은 값으로 취급해야 할 수 있다.

따라서 Completeness 정의에 다음을 포함한다.

```text
NULL

Empty String

Whitespace Only

Placeholder Value

Unknown
```

### ✅ 8. Validity — 유효성

예:

```text
discountAmount = -100000
```

이 저장됐다.

실제 업무에서 할인액이 음수를 허용하지 않는다면 Validation 오류다.

반면 환불액이나 정산 조정값처럼 음수가 정상인 항목도 있다.

따라서 데이터 타입만으로 업무상 유효성을 결정할 수는 없다.

### ✅ 9. Timeliness — 적시성

예:

```text
고객 신청 시각
10:00

관리자 주문 생성 시각
10:12
```

이라면 관리자에 반영되기까지 12분이 걸렸다.

이 지연이 정상인지 판단하려면 업무 기준이 필요하다.

```text
목표
30초 이내

실제
12분
```

이라면 이상 현상으로 볼 수 있다.

### ✅ 10. Accuracy — 정확성

예:

```text
홈페이지 실제 판매가격
100,000원

네이버 EP 가격
90,000원
```

이라면 두 데이터가 불일치한다.

하지만 정확성을 확인하려면 어느 쪽이 기준 데이터인지 알아야 한다.

```text
Product Pricing Domain
Source of Truth
```

를 명시해야 한다.

### ✅ 11. Consistency — 일관성

예:

```text
상품 DB
판매중

EP
판매중

홈페이지
판매중
```

이면 일치한다.

반면:

```text
상품 DB
판매중지

EP
판매중
```

이면 데이터 반영 지연이나 동기화 실패 가능성이 있다.

### ✅ 12. 데이터 품질은 업무 중요도에 따라 다르게 관리한다

예:

```text
주문 ID
정확성 매우 중요

상품 이미지 순서
상대적으로 낮음

광고 유입코드
마케팅 분석 중요

알림톡 발송 상태
고객 안내 중요
```

따라서 모든 데이터에 동일한 품질 목표를 설정하지 않는다.

## 3. Data Contract — 데이터의 의미를 명확하게 약속하기

### ✅ 13. Data Contract란?

데이터를 생산하는 시스템과 소비하는 시스템 사이의 약속이다.

예:

```text
Producer
투게더몰 Frontend

↓

Data Contract

↓

Consumer
NestJS / Analytics
```

이때 계약에는 다음을 정의할 수 있다.

```text
어떤 데이터인가?

필수 값은 무엇인가?

타입은 무엇인가?

어떤 의미인가?

언제 생성되는가?

어떤 값이 허용되는가?

변경 시 누가 영향을 받는가?
```

### ✅ 14. TypeScript 타입만 있으면 충분할까?

예:

```ts
interface OrderCreatedEvent {
  orderId: string;
  amount: number;
}
```

이 타입은 컴파일 시점에는 도움이 된다.

하지만 외부 API 또는 Webhook으로 받은 JSON은 실제로 다음과 같을 수 있다.

```json
{
  "orderId": "order_123",
  "amount": "100000"
}
```

`amount`가 문자열로 변경됐다.

TypeScript 인터페이스만으로 런타임 JSON이 실제 계약을 준수하는지 보장할 수 없다.

### ✅ 15. Runtime Validation이 필요한 이유

외부 데이터를 받을 때:

```text
External JSON

↓

Runtime Schema Validation

↓

Domain Mapping

↓

Business Logic
```

흐름을 사용한다.

### ✅ 16. Data Contract에는 타입 이상의 정보가 필요하다

예:

```text
amount
number
```

라고만 정의하면 다음이 모호하다.

```text
원 단위?

천 원 단위?

월 납부금?

단말기 총가격?

부가세 포함?
```

데이터 타입이 같아도 의미가 전혀 다를 수 있다.

### ✅ 17. Contract 예시

```yaml
contract: order-created
version: 1

producer: togethermall-api
consumer:
  - order-admin
  - order-report

fields:
  orderId:
    type: string
    required: true
    description: 주문 식별자

  submittedAt:
    type: datetime
    required: true
    timezone: UTC

  acquisitionChannel:
    type: string
    required: false
    description: 추적 정책에 따라 확인된 유입 채널

  totalAmount:
    type: integer
    required: true
    unit: KRW
```

설명용 계약이다.

실제 필드는 현재 DB와 주문 업무 모델에 맞춰야 한다.

### ✅ 18. Producer와 Consumer를 명시한다

예:

```text
Data Product
ORDER_ACQUISITION

Producer
NestJS Order Domain

Consumers
Admin Dashboard
Marketing Report
AI Insight
```

같이 정의한다.

이렇게 해야 필드가 바뀔 때 영향을 받는 기능을 추적하기 쉽다.

### ✅ 19. Contract Owner

데이터 변경 책임자를 명확히 한다.

1인 개발 환경이라도:

```text
Business Owner

Technical Owner

External Provider
```

를 구분할 수 있다.

외부 API 형식 변경은 직접 통제할 수 없지만, 내부 Contract와 Adapter는 관리할 수 있다.

### ✅ 20. Contract Version

예:

```text
order-created/v1
```

에서:

```text
order-created/v2
```

로 변경한다.

단 모든 사소한 변경에 반드시 새 Major Version이 필요한 것은 아니다.

기존 Consumer를 깨뜨리는 변경인지가 중요하다.

## 4. Breaking Change와 Non-breaking Change

### ✅ 21. 필드 추가

기존:

```json
{
  "orderId": "order_123"
}
```

변경:

```json
{
  "orderId": "order_123",
  "channel": "NAVER"
}
```

새 필드가 선택 사항이고 Consumer가 알 수 없는 필드를 허용한다면 호환될 수 있다.

그러나 Consumer가 추가 필드를 엄격하게 거부하는 경우에는 Breaking Change가 될 수 있다.

### ✅ 22. 필드 삭제

기존:

```json
{
  "orderId": "order_123",
  "visitorId": "visitor_456"
}
```

변경:

```json
{
  "orderId": "order_123"
}
```

`visitorId`를 필수로 사용하는 Consumer가 있다면 문제가 된다.

### ✅ 23. 타입 변경

기존:

```json
{
  "price": 120000
}
```

변경:

```json
{
  "price": "120000"
}
```

TypeScript에서 숫자 변환이 가능하더라도 계약이 변경된 것이다.

특히:

```text
"120000"

"120,000"

"120000 KRW"
```

는 서로 다른 파싱 규칙이 필요하다.

### ✅ 24. Enum 값 추가

기존:

```text
DIRECT

NAVER

GOOGLE
```

변경:

```text
DIRECT

NAVER

GOOGLE

INSTAGRAM
```

기존 Consumer가 모든 값을 처리할 수 없다면 문제가 생긴다.

### ✅ 25. 모르는 Enum 값을 정상 값으로 강제 변환하지 않는다

나쁜 예:

```ts
const channel = knownChannels.includes(input)
  ? input
  : 'DIRECT';
```

이렇게 하면 새로운 유입 채널이 전부 직접 유입으로 분류된다.

서버에는 오류가 없지만 마케팅 분석은 잘못된다.

### ✅ 26. UNKNOWN은 DIRECT와 다르다

```text
DIRECT
직접 유입으로 확인됨

UNKNOWN
유입 정보를 확인할 수 없음
```

이다.

이 차이를 유지해야 한다.

### ✅ 27. Unknown Value 정책

예:

```text
Unknown Enum

↓

Contract Warning

↓

UNKNOWN으로 별도 분류

↓

원본 코드 메타데이터 기록

↓

관리자 검토
```

같은 방식이다.

단 주문 승인이나 금액 계산처럼 안전이 중요한 필드에서는 UNKNOWN으로 계속 처리하기보다 해당 작업을 차단해야 할 수 있다.

### ✅ 28. Nullability 변경도 Breaking Change가 될 수 있다

기존:

```text
phoneNumber
항상 String
```

변경:

```text
phoneNumber
String | null
```

이라고 하자.

Consumer가 `null`을 예상하지 못하면 런타임 오류가 발생할 수 있다.

### ✅ 29. 변경 전 Consumer 영향 분석

```text
Field
acquisitionChannel

↓

Used by

Admin Order List
Daily Report
Marketing Insight
Export
```

처럼 영향을 받는 곳을 파악한다.

### ✅ 30. Data Contract 변경 승인 기준

예:

```text
필수 필드 삭제

데이터 타입 변경

가격 단위 변경

상태 Enum 의미 변경

Timestamp 기준 변경
```

은 명시적 변경 검토가 필요한 항목이다.

## 5. NestJS에서 Data Contract 검증하기

### ✅ 31. 외부 입력을 그대로 Domain에 전달하지 않는다

나쁜 흐름:

```text
External API

↓

JSON 그대로 DB 저장

↓

여러 기능에서 직접 참조
```

좋은 흐름:

```text
External API

↓

Contract Validation

↓

Provider Adapter

↓

Internal Domain Model

↓

Database
```

이다.

### ✅ 32. Zod 예시

프로젝트에 이미 `class-validator`, DTO ValidationPipe 등 검증 체계가 있다면 이를 재사용한다.

새로운 Validator를 중복 도입할 필요는 없다.

다음은 Zod를 사용하는 경우의 예시다.

```ts
import { z } from 'zod';

const ExternalProductSchema = z.object({
  id: z.string().min(1),
  price: z.number().finite().nonnegative(),
  name: z.string().min(1),
}).passthrough();

type ExternalProduct =
  z.infer<typeof ExternalProductSchema>;
```

### ✅ 33. Validation 실행

```ts
const result =
  ExternalProductSchema.safeParse(payload);

if (!result.success) {
  // 계약 위반 기록
  // 원본 PII / Secret은 로그에 남기지 않음
  // 해당 데이터의 반영 중단 또는 격리
  return;
}

const product: ExternalProduct = result.data;
```

여기서 중요한 것은 단순 유효성 검사 성공뿐 아니라 **검증 결과를 내부 Domain Model로 명시적으로 변환하는 것**이다.

### ✅ 34. Unknown Field 처리

추가 필드에 대한 정책은 데이터 종류에 따라 달라진다.

```text
알 수 없는 선택 필드
→ 무시하거나 별도 추적

알 수 없는 필수 의미 필드
→ 계약 검토

알 수 없는 상태값
→ UNKNOWN 또는 처리 중단
```

외부 Provider가 필드를 추가했다고 모든 업무가 중단되는 것도 좋지 않다.

반대로 모르는 값을 무조건 무시해 중요한 의미 변화까지 놓쳐서도 안 된다.

### ✅ 35. Adapter에서 내부 필드만 Mapping

```ts
const internalProduct = {
  externalId: result.data.id,
  title: result.data.name,
  priceKrw: result.data.price,
};
```

이렇게 하면 외부 Provider의 응답 구조가 내부 전반으로 전파되는 것을 줄일 수 있다.

### ✅ 36. Contract Validation 실패와 HTTP 실패는 다르다

예:

```text
HTTP
200 OK

JSON Parse
SUCCESS

Contract Validation
FAILED
```

라면 요청 자체는 성공했지만 유효한 데이터를 받지 못한 것이다.

따라서:

```text
external_request_success
```

와:

```text
contract_validation_success
```

를 별도 Metric으로 관리할 수 있다.

### ✅ 37. Invalid Payload 처리

예:

```text
External Payload

↓

Validation Failed

↓

Invalid Record 격리

↓

Contract Violation 기록

↓

Alert / Review
```

로 처리한다.

민감 데이터가 포함되면 격리 저장소의 접근권한과 보관기간을 엄격히 관리한다.

### ✅ 38. Webhook에서는 응답 정책도 중요하다

외부 Webhook이 들어온 경우:

```text
Signature Validation

↓

Durable Inbox 저장

↓

빠른 Response

↓

Background Contract Validation
```

같은 구조를 사용할 수 있다.

다만 인증되지 않은 요청까지 성공 처리해서는 안 된다.

유효하지 않은 서명은 거절하고, 계약 위반 데이터는 Provider의 재전송 방식과 내부 격리 정책에 따라 응답을 결정한다.

### ✅ 39. 계약 위반을 무한 재시도하지 않는다

예:

```text
price = "unknown"
```

처럼 구조 자체가 바뀐 경우에는 같은 요청을 수십 번 재시도해도 해결되지 않는다.

이때는:

```text
NON_RETRYABLE_CONTRACT_VIOLATION
```

등으로 분류하는 것이 낫다.

## 6. Schema Drift — 실제 데이터 구조가 예상과 달라지는 문제

### ✅ 40. Schema Drift란?

기대한 Schema와 실제 Schema가 달라지는 현상이다.

예:

```text
Prisma Schema

Order.visitorId
String?
```

그런데 실제 DB에서는:

```text
visitor_id
컬럼 삭제
```

됐다면 문제가 된다.

### ✅ 41. Drift가 발생하는 경로

```text
Production DB 직접 수정

Migration 누락

수동 Hotfix

환경별 Schema 차이

외부 Provider 필드 변경

CSV Header 변경
```

등이다.

### ✅ 42. Database Schema Drift

예:

```text
Git Migration History
v12

Production DB
수동 DDL 적용
```

이라고 하자.

코드의 Migration History와 실제 DB 구조가 달라졌다.

### ✅ 43. Prisma Migration 적용 성공과 Drift 검사는 다르다

Prisma ORM의 일반적인 `migrate deploy` 워크플로우는 대기 중인 Migration을 적용하지만, 기존 Production DB의 모든 수동 Schema 변경을 자동 탐지하지 않는다.

따라서 별도의 Read-only Schema 비교가 필요하다.

또한 Prisma ORM 버전에 따라 Migration CLI와 명령 구성이 달라질 수 있으므로 현재 프로젝트에 설치된 버전을 먼저 확인해야 한다.

### ✅ 44. PostgreSQL Information Schema

테이블 구조를 읽기 전용으로 확인할 수 있다.

```sql
SELECT
  column_name,
  data_type,
  is_nullable,
  column_default
FROM information_schema.columns
WHERE table_schema = 'public'
  AND table_name = 'orders'
ORDER BY ordinal_position;
```

이는 구조 비교에 활용할 수 있다.

### ✅ 45. Information Schema로 모든 Schema를 알 수 있는 것은 아니다

예:

```text
Index

Constraint

Trigger

Extension

Function

Column Collation
```

등을 정확하게 비교하려면 PostgreSQL 시스템 카탈로그와 Schema Diff 도구를 함께 사용할 수 있다.

### ✅ 46. Schema Snapshot

예:

```text
Expected Schema

↓

Canonical Representation

↓

Fingerprint
```

를 만든다.

실제 DB 구조도 동일한 방식으로 정규화한 뒤 비교한다.

### ✅ 47. Schema Fingerprint

예:

```text
expectedSchemaHash
abc123

actualSchemaHash
abc123
```

이면 같은 구조라고 판단할 수 있다.

단 Hash가 같다는 것은 정규화·비교 대상에 포함된 Schema 요소가 같다는 뜻이지 DB 데이터의 정합성까지 보장하는 것은 아니다.

### ✅ 48. Schema Drift 탐지 결과

예:

```text
Table
orders

Expected Column
visitor_id

Actual Column
missing

Severity
HIGH
```

처럼 기록한다.

### ✅ 49. Drift 탐지 후 자동으로 DB를 수정하지 않는다

위험한 방식:

```text
Schema Drift 발견

↓

자동 db push

↓

Production 구조 변경
```

이다.

Schema Drift는 원인을 조사해야 한다.

정상적인 Emergency Hotfix인지, Migration 누락인지, 잘못된 직접 수정인지 판단해야 한다.

### ✅ 50. Prisma DB Reset은 Production에서 금지

Production에서 Schema 문제를 해결하려고:

```text
migrate reset
```

을 실행해서는 안 된다.

개발 DB 초기화용 절차와 운영 DB 복구 절차를 명확히 구분한다.

### ✅ 51. Schema Drift 검사는 배포 전후에 유용하다

```text
Before Deployment
Schema Compatibility Check

↓

Migration Apply

↓

Post-migration Verification

↓

Application Readiness
```

흐름으로 연결할 수 있다.

## 7. Expand and Contract — 호환성을 유지하며 변경하기

### ✅ 52. Breaking Schema 변경을 한 번에 배포하면 위험하다

예:

```text
기존
customer_name

신규
applicant_name
```

로 변경한다고 하자.

컬럼 이름만 바로 바꾸면 구버전 Application이 실패할 수 있다.

### ✅ 53. Expand 단계

먼저 새 필드를 추가한다.

```text
customer_name

applicant_name
```

둘 다 존재하도록 만든다.

### ✅ 54. Transition 단계

새 Application에서:

```text
기존 데이터 읽기

새 필드 Backfill

Write 경로 전환

Consumer 검증
```

을 수행한다.

구버전과 신버전이 공존하는 동안 양쪽이 같은 의미의 데이터를 사용할 수 있어야 한다.

### ✅ 55. Contract 단계

모든 Consumer가 새 필드로 이전한 것을 확인한 뒤:

```text
customer_name
삭제
```

한다.

### ✅ 56. Schema 변경은 Application 배포 순서와 연결된다

예:

```text
Migration A
새 Column 추가

↓

Application v2
새 Column 지원

↓

Backfill

↓

Application v3
기존 Column 미사용

↓

Migration B
기존 Column 삭제
```

이다.

### ✅ 57. Backfill도 Data Quality 검사 대상이다

예:

```text
기존 데이터
100,000건

Backfill 성공
99,200건

누락
800건
```

이라면 Contract 단계를 진행하면 안 된다.

### ✅ 58. Backfill Validation

```text
Source Count

Target Count

Null Count

Mismatch Count

Sample Comparison

Checkpoint
```

를 검증한다.

### ✅ 59. 데이터 의미 변경은 Column Migration보다 어려울 수 있다

예:

```text
price
기존: 단말기 총가격

price
신규: 월 납부금
```

은 타입도 이름도 같지만 의미가 완전히 달라졌다.

이런 변경은 단순 Schema Diff에서 발견되지 않을 수 있다.

## 8. Semantic Drift — 형식은 같은데 의미가 바뀌는 문제

### ✅ 60. Semantic Drift란?

데이터의 형태는 그대로지만 값의 의미나 생성 기준이 바뀌는 현상이다.

예:

```text
amount
100000
```

이 기존에는:

```text
단말기 총가격
```

이었는데 새로운 Provider에서는:

```text
월 납부금
```

이 됐다.

타입 검증은 통과한다.

하지만 업무적으로 완전히 잘못된 값이 된다.

### ✅ 61. 가장 위험한 유형 중 하나다

```text
HTTP 200

Schema Valid

Database Insert Success

하지만 잘못된 금액
```

상태가 발생할 수 있기 때문이다.

### ✅ 62. Semantic Contract

필드마다 다음을 명시한다.

```text
Field Name

Business Meaning

Unit

Currency

Timezone

Calculation Rule

Nullable Reason

Source of Truth
```

### ✅ 63. 가격 필드 예

```yaml
field: monthlyPaymentKrw

type: integer
unit: KRW
meaning: 고객 월 납부 예상액
taxIncluded: true
```

같이 정의할 수 있다.

단 실제 업무 기준에 맞는 필드인지 확인해야 한다.

### ✅ 64. Timestamp 의미 변화

예:

```text
createdAt
```

이 기존에는:

```text
고객 신청 버튼을 누른 시각
```

이었는데 신규 시스템에서는:

```text
관리자 DB에 저장된 시각
```

이 됐다고 하자.

두 시각이 같지 않을 수 있다.

### ✅ 65. 지표가 조용히 달라진다

```text
신청 후 처리시간
=
processedAt - createdAt
```

이라는 지표는 `createdAt`의 정의가 바뀌면 비교가 어려워진다.

### ✅ 66. Analytics Metric Definition도 Contract다

예:

```text
submitted_orders
```

라는 지표에:

```text
고객 신청 완료 기준

공식 신청서 제출 기준

관리자 접수 생성 기준
```

중 어떤 정의를 사용하는지 명확히 해야 한다.

### ✅ 67. Metric Versioning

예:

```text
submitted_orders/v1
홈페이지 신청 완료

submitted_orders/v2
공식 신청서 작성 완료
```

처럼 구분할 수 있다.

기존 Dashboard 값과 신규 Dashboard 값을 아무 설명 없이 연결해서는 안 된다.

## 9. 주문량 급감 Anomaly Detection

### ✅ 68. Anomaly Detection이란?

관측값이 정상적인 패턴에서 벗어났는지 탐지하는 것이다.

예:

```text
평소 같은 시간대
주문 100건

오늘
주문 40건
```

이라면 이상 현상일 수 있다.

### ✅ 69. 하지만 주문이 줄었다고 바로 장애는 아니다

가능한 원인:

```text
광고 집행 중지

공휴일

날씨

상품 출시 일정

재고 부족

영업 정책 변경

실제 수요 감소

주문 API 문제
```

등이다.

즉 Anomaly는 사고 확정이 아니라 조사 신호다.

### ✅ 70. 단순 전일 비교의 한계

예:

```text
일요일
주문 20건

월요일
주문 80건
```

이 정상적인 패턴일 수 있다.

그러므로:

```text
오늘 vs 어제
```

만 비교하면 오탐지가 발생할 수 있다.

### ✅ 71. Same Weekday Baseline

예:

```text
최근 월요일
70

80

75

90
```

이면 월요일 기준 Baseline을 만들 수 있다.

### ✅ 72. Hourly Baseline

사전예약이나 광고 유입은 시간대의 영향을 크게 받을 수 있다.

```text
오전 10시
평균 20건

새벽 3시
평균 1건
```

을 같은 기준으로 비교해서는 안 된다.

### ✅ 73. 예시 Threshold

```text
Expected
100

Actual
40

Deviation
-60%
```

이 경우 주문량 급감을 감지할 수 있다.

하지만 실제 Threshold는 지난 운영 데이터의 변동성과 업무 영향에 따라 결정한다.

### ✅ 74. 절대 건수 조건도 필요하다

예:

```text
Expected
2

Actual
0
```

이면 감소율은 100%지만 표본이 매우 적다.

반대로:

```text
Expected
200

Actual
20
```

이면 훨씬 중요한 이상 현상일 수 있다.

### ✅ 75. Volume과 Ratio를 같이 본다

예시 조건:

```text
Expected >= 30

AND

Actual < Expected × 0.5
```

같은 룰을 사용할 수 있다.

숫자는 예시이며 실제 적용 전 Baseline 검증이 필요하다.

### ✅ 76. 최소 Sample Size

방문자 5명 중 1명 주문한 것과 방문자 5,000명 중 1,000명 주문한 것은 같은 20% 전환율이어도 통계적으로 의미가 다르다.

따라서 충분한 관측 수를 확보하지 못하면 이상 판단을 보류할 수 있다.

### ✅ 77. 변경점 탐지

다음처럼 주문량이 지속해서 낮아질 수 있다.

```text
월요일
100

화요일
95

수요일
85

목요일
70

금요일
55
```

단일 시점의 급격한 Spike는 없지만 추세가 바뀌고 있다.

이런 변화도 모니터링 대상이다.

### ✅ 78. Spike Detection

반대로 주문량이 갑자기 증가하는 경우도 살펴본다.

```text
평소
시간당 10건

현재
시간당 300건
```

정상적인 광고 캠페인 효과일 수도 있지만 중복 주문 생성 Bug일 수도 있다.

### ✅ 79. 이상 탐지는 양방향이다

```text
Unexpected Drop

Unexpected Spike
```

둘 다 본다.

## 10. PostgreSQL로 데이터 품질 Metric 계산하기

### ✅ 80. 일별 주문 건수

예시 Schema:

```text
orders.created_at
TIMESTAMPTZ
```

라고 가정한다.

```sql
SELECT
  (created_at AT TIME ZONE 'Asia/Seoul')::date
    AS business_date,
  COUNT(*) AS order_count
FROM orders
WHERE created_at >=
  (CURRENT_TIMESTAMP - INTERVAL '14 days')
GROUP BY business_date
ORDER BY business_date;
```

주문 건수는 주문 생성 기준의 지표다.

신청 완료 건수와 혼동하지 않는다.

### ✅ 81. Business Timezone이 중요하다

같은 시각이라도:

```text
UTC
10월 11일

Asia/Seoul
10월 12일
```

일 수 있다.

따라서 매출·주문 일별 지표는 업무 기준 시간대를 명확히 정의한다.

### ✅ 82. 범위 검색에서는 인덱스를 고려한다

예를 들어 KST 기준 특정 날짜의 주문은 날짜 경계를 UTC 시점으로 변환한 뒤 원본 `created_at`에 범위 조건을 적용할 수 있다.

```sql
SELECT COUNT(*)
FROM orders
WHERE created_at >=
  ('2026-10-11'::date::timestamp
    AT TIME ZONE 'Asia/Seoul')
  AND created_at <
  ('2026-10-12'::date::timestamp
    AT TIME ZONE 'Asia/Seoul');
```

이 방식은 컬럼 자체에 매 Row마다 날짜 변환 함수를 적용하는 필터보다 일반적인 `created_at` 인덱스를 활용하기 유리할 수 있다.

실제 실행계획은 `EXPLAIN`으로 확인한다.

### ✅ 83. 유입정보 누락률

예시로 `orders.visitor_id`가 존재한다고 가정한다.

```sql
SELECT
  COUNT(*) AS total_orders,

  COUNT(*) FILTER (
    WHERE visitor_id IS NULL
       OR BTRIM(visitor_id) = ''
  ) AS missing_visitor_id,

  ROUND(
    100.0 * COUNT(*) FILTER (
      WHERE visitor_id IS NULL
         OR BTRIM(visitor_id) = ''
    ) / NULLIF(COUNT(*), 0),
    2
  ) AS missing_rate_percent
FROM orders
WHERE created_at >=
  CURRENT_TIMESTAMP - INTERVAL '1 day';
```

실제 필드명과 유입정보 수집 정책에 맞춰 변경해야 한다.

### ✅ 84. 분모가 0이면 어떻게 할까?

예:

```text
Total Orders
0
```

인 경우:

```text
Missing Rate
0%
```

라고 표시하는 것은 부정확할 수 있다.

계산할 데이터 자체가 없기 때문이다.

따라서:

```text
NOT_AVAILABLE

NO_SAMPLES
```

등으로 구분한다.

### ✅ 85. 0과 Missing은 다르다

이 차이는 매우 중요하다.

```text
주문 수 = 0
→ 정상적으로 집계했고 실제 주문이 없음
```

```text
Metric 없음
→ 집계가 실행되지 않았을 수 있음
```

```text
Metric Stale
→ 마지막 성공값이 오래됨
```

서로 다르다.

### ✅ 86. Source Freshness도 함께 검사

예:

```text
lastReceivedAt

lastProcessedAt

lastBusinessEventAt
```

를 구분한다.

주문이 없는 새벽이라고 데이터 파이프라인이 죽은 것은 아닐 수 있다.

### ✅ 87. Heartbeat와 Business Event 구분

```text
Pipeline Heartbeat
매 5분

Business Event
발생 시에만
```

형태라면 실제 업무 이벤트가 없어도 파이프라인이 정상인지 확인할 수 있다.

다만 추가 Heartbeat 자체가 비용이나 시스템 복잡도를 과도하게 높이지 않게 한다.

## 11. 퍼널 데이터 품질

### ✅ 88. 주문량만 보면 원인을 찾기 어렵다

예:

```text
방문자 감소
→ 주문 감소
```

와:

```text
방문자 정상
→ 주문만 감소
```

는 서로 다른 문제다.

### ✅ 89. Funnel Monitoring

예:

```text
Page View
    ↓
Product Detail
    ↓
Apply Modal Open
    ↓
Application Submitted
    ↓
Order Created
    ↓
Official Application Completed
```

각 단계의 건수를 측정한다.

### ✅ 90. 퍼널 단계의 정의가 중요하다

예:

```text
Apply Modal Open
```

이 버튼 클릭인지, 모달 렌더링 성공인지 구분해야 한다.

또 한 사용자가 여러 번 모달을 열 수 있으므로 단순 Event Count와 Unique User Count를 혼동하지 않는다.

### ✅ 91. 예: 신청 모달 오류

```text
방문자
정상

상품 상세 진입
정상

신청 모달 열기
정상

신청 완료
급감
```

이라면 신청 과정에서 문제가 발생했을 가능성이 있다.

### ✅ 92. UI Error와 Data Quality를 함께 본다

예:

```text
Modal Dropdown Error

+

Application Submitted 급감
```

이 동시에 발생했다면 원인 파악에 도움이 된다.

### ✅ 93. 그러나 추적 이벤트 자체가 고장 났을 수도 있다

예:

```text
실제 신청
정상

Tracking Event
누락
```

이라면 퍼널에서 신청 완료가 감소한 것으로 보일 수 있다.

따라서 중요한 지표는 가능한 경우 서버 측 주문 데이터와 비교한다.

### ✅ 94. Client Event는 신뢰도 한계가 있다

브라우저 차단, 네트워크 연결 문제, 사용자 동의 정책 등으로 일부 이벤트가 누락될 수 있다.

따라서:

```text
Analytics Event
```

와:

```text
Business Transaction
```

은 같은 종류의 데이터로 취급하지 않는다.

### ✅ 95. Conversion Rate의 분모를 명확히 한다

예:

```text
Orders / Sessions
```

과:

```text
Unique Applicants / Unique Visitors
```

는 서로 다른 지표다.

비교하려는 값의 단위를 맞춰야 한다.

### ✅ 96. Source별 Conversion을 비교할 때

```text
NAVER

GOOGLE

DIRECT

UNKNOWN
```

각 채널별 방문자 수와 주문 건수의 정의가 같아야 한다.

특히 UNKNOWN을 DIRECT에 합쳐놓으면 분석 결과가 왜곡될 수 있다.

## 12. 광고 유입 데이터 품질

### ✅ 98. 외부 클릭 수와 내부 주문 수를 1:1로 비교하지 않는다

광고 클릭은 중복될 수 있고, 신청까지 이어지지 않을 수 있다.

따라서 직접 동일해야 하는 값으로 판단하면 안 된다.

대신 추세와 연결률을 확인한다.

등이다.

### ✅ 100. Tracking Parameter 보존

를 사용할 수 있다.

다만 실제 필요성과 개인정보·동의 정책에 따라 수집 범위를 결정한다.

### ✅ 101. Parameter Loss Point

```text
↓

Product Detail
유지

↓

유지

누락
```

### ✅ 103. Lineage가 중요한 이유

지표가 잘못됐을 때:

```text
어느 단계에서 값이 바뀌었는가?
```

를 찾을 수 있기 때문이다.

### ✅ 104. 데이터 흐름별 Contract

```text

Tracking Contract

Metric Definition

Insight Input Contract
```

으로 나눈다.

## 13. 네이버 EP 데이터 품질

### ✅ 105. EP는 일반 상품 데이터보다 더 엄격히 검증할 가치가 있다

상품 데이터가 외부 플랫폼에 전달되기 때문이다.

예:

```text
상품 ID

상품명

가격

상품 URL

이미지 URL

판매 상태

분류
```

등이 포함될 수 있다.

정확한 필수 항목과 형식은 현재 사용하는 네이버 EP 연동 규격을 기준으로 확인한다.

### ✅ 106. EP는 정상 생성돼도 잘못될 수 있다

예:

```text
EP File
생성 성공

HTTP
200

하지만 상품 가격 오류
```

가 발생할 수 있다.

### ✅ 107. EP Data Contract

예:

```text
ID
Unique / Nonempty

Price
허용된 숫자 범위

Product URL
유효한 목적지

Image URL
사용 가능한 이미지

Availability
내부 상품 상태와 일치
```

다.

### ✅ 108. EP Item Count Anomaly

예:

```text
어제 EP 상품
850개

오늘 EP 상품
120개
```

라면 이상 현상일 수 있다.

단 정상적인 상품 판매 종료나 필터 정책 변경일 수도 있다.

### ✅ 109. EP ID Churn

예:

```text
어제 Product ID
A001

오늘 동일 상품
B999
```

가 됐다면 외부 플랫폼에서 다른 상품으로 인식될 수 있다.

따라서 ID의 안정성도 검사할 수 있다.

### ✅ 110. EP Diff

```text
Before EP

↓

After EP

↓

Added

Removed

Changed Price

Changed URL

Changed Availability

Changed Category
```

형태로 비교한다.

### ✅ 111. EP의 모든 변경이 오류는 아니다

정상적인 가격 변경이나 판매 종료도 존재한다.

따라서:

```text
Expected Change

Unexpected Change
```

를 구분한다.

### ✅ 112. EP Publish Gate

예:

```text
Contract Valid

Item Count Range Valid

Critical URL Valid

Pricing Rule Valid

Unexpected Removal Reviewed
```

조건을 만족했을 때만 새 EP를 게시할 수 있다.

단 경고 하나 때문에 모든 EP 갱신을 중단하는 과도한 정책은 피한다.

### ✅ 113. 이전 정상 EP 유지

새 EP 생성 결과가 명백히 잘못됐다면:

```text
Last Known Good EP
```

를 유지하는 전략을 고려할 수 있다.

다만 상품가격이나 판매 상태가 변경됐는데 이전 EP를 계속 제공하면 최신 정보와 불일치할 수 있으므로, 이전 버전을 유지할 수 있는 최대 시간과 긴급 갱신 정책이 필요하다.

## 14. Anomaly Detection의 구현 방식

### ✅ 114. 처음부터 Machine Learning이 필요한 것은 아니다

현재 규모에서 먼저 사용할 수 있는 방법:

```text
Static Threshold

Baseline Comparison

Rolling Average

Same Weekday Comparison

Rate Change

Missingness Trend
```

등이다.

### ✅ 115. Static Threshold

예:

```text
유입정보 누락률
30% 초과
```

이면 경고한다.

단 기준은 실제 정상 운영 데이터로 검증해야 한다.

### ✅ 116. Rolling Average

예:

```text
최근 7일 평균
```

과 현재 값을 비교한다.

다만 일별·주별 패턴이 강한 데이터에는 단순 이동평균이 부적절할 수 있다.

### ✅ 117. Seasonal Baseline

예:

```text
월요일 10시

과거 월요일 10시 데이터
```

를 기준으로 비교한다.

### ✅ 118. Change-point Detection

값이 갑자기 새로운 수준으로 바뀌는 지점을 탐지하는 방식이다.

예:

```text
Unknown Channel Rate

5%

7%

6%

↓

45%

48%

46%
```

가 됐다면 Tracking 로직이 변경됐을 가능성이 있다.

### ✅ 119. Anomaly Detection은 오류의 종류를 확정하지 않는다

```text
Unknown Rate 급증
```

이 발견됐더라도:

```text
Frontend Bug

광고 파라미터 변경

브라우저 정책 변화

사용자 동의율 변화
```

중 무엇이 원인인지는 추가 확인해야 한다.

### ✅ 120. CloudWatch Anomaly Detection

AWS CloudWatch는 과거 Metric을 바탕으로 예상 정상 범위를 학습하고, 값이 그 범위를 벗어나면 Alarm을 생성하는 기능을 제공한다.

시간·요일별 패턴을 고려할 수 있다.

하지만 Metric이 충분히 정확해야 하고 추가 비용 및 모델 학습 조건을 검토해야 한다.

### ✅ 121. 현재는 기존 Metric부터 제대로 만든다

처음부터 CloudWatch Anomaly Detection을 도입하기보다:

```text
Metric Definition

↓

Correct Collection

↓

Baseline

↓

Static/Relative Rule

↓

Alert Quality Review
```

순서가 낫다.

### ✅ 122. 최소 Detection Result

예:

```ts
interface DataAnomaly {
  metric: string;

  expected: number;

  actual: number;

  deviationPercent: number;

  detectedAt: Date;

  severity: 'HIGH' | 'MEDIUM' | 'LOW';

  baselineVersion: string;
}
```

실제 시스템에서는 분모·표본 수·시간 범위·데이터 신선도도 함께 기록하는 것이 좋다.

## 15. Alert Fatigue 방지

### ✅ 123. 모든 이상값에 Alert를 보내면 문제가 생긴다

예:

```text
주문 1건 감소

↓

Alert
```

이 매시간 발생하면 알림을 신뢰하지 않게 된다.

### ✅ 124. 최소 Sample 조건

예:

```text
Minimum Sample
30
```

이상일 때 비율 변동을 평가할 수 있다.

정확한 기준은 데이터 종류에 따라 달라진다.

### ✅ 125. Consecutive Breach

예:

```text
1회 이상
관찰

3회 연속 이상
Alert
```

처럼 설정할 수 있다.

하지만 주문 생성이 완전히 중단된 상황처럼 심각한 경우에는 여러 번 기다릴 필요가 없을 수 있다.

### ✅ 126. Alert Deduplication

동일 문제가 계속 발생하면:

```text
Alert #1

Alert #2

Alert #3
```

을 생성하는 대신 하나의 활성 Incident로 묶을 수 있다.

### ✅ 127. Alert Grouping

예:

```text
Data Source
Order Attribution

Metric
Unknown Rate

Incident
dq_001
```

로 관리한다.

### ✅ 128. Deployment Correlation

예:

```text
09:00
Frontend Release

09:15
visitorId Missing Rate 증가
```

가 발생했다면 두 사건을 함께 조사한다.

하지만 시간상 가까웠다는 사실만으로 배포가 원인이라고 확정하지 않는다.

### ✅ 129. Marketing Campaign Context

예:

```text
대규모 광고 시작
```

이후 방문자 수가 급증했다면 정상 변화일 수 있다.

Anomaly Rule에서 다음을 참고할 수 있다.

```text
Campaign Event

Release

Holiday

Promotion

Maintenance
```

### ✅ 130. Silence와 Suppression은 신중하게 사용한다

배포 중 경고를 잠시 억제할 수 있지만, 실제 주문 손실까지 감추면 안 된다.

특히 Critical Business Metric은 일괄 Silence하지 않는 것이 좋다.

## 16. 데이터 품질 SLO

### ✅ 131. Data Quality도 목표를 둘 수 있다

예:

```text
Order Attribution Coverage

Target
95% 이상
```

같이 정의할 수 있다.

그러나 수집 동의 여부나 실제 데이터 특성상 해당 목표가 가능한지 확인해야 한다.

### ✅ 132. Timeliness SLO

예:

```text
주문 생성 후
관리자 조회 가능

95%
30초 이내
```

같이 정의할 수 있다.

### ✅ 133. Freshness SLO

예:

```text
상품 EP
정상 갱신 주기 기준
지정된 시간 이내 생성
```

처럼 둔다.

업데이트가 예정되지 않은 시간대까지 무조건 신선도 위반으로 보지 않는다.

### ✅ 134. Completeness SLO

예:

```text
신청 완료된 주문의
필수 업무 필드

99.9% 이상 유효
```

등이다.

### ✅ 135. Metric Availability SLO

데이터값 자체뿐 아니라 Monitoring Pipeline의 작동 상태도 검증한다.

```text
Daily Metric Calculation
정상 완료 여부
```

등이다.

### ✅ 136. 품질 SLO 위반과 실제 장애는 다를 수 있다

예:

```text
Attribution Coverage
95% → 90%
```

는 마케팅 분석 품질 저하이지만, 모든 고객 주문이 실패하는 상황과 같은 심각도로 다룰 필요는 없다.

### ✅ 137. 업무 영향에 따라 Severity를 정한다

예:

| 상황 | 예시 우선순위 |
|---|---|
| 주문이 저장되지 않음 | P0 |
| 가격 데이터가 잘못 전송됨 | P0~P1 |
| 유입정보 누락률 급증 | P1~P2 |
| 일부 분석 Dashboard 지연 | P2 |
| 재생성 가능한 통계의 소규모 차이 | P3 |

실제 우선순위는 영향 고객 수, 금전 영향, 지속 시간에 따라 조정한다.

## 17. Data Quality 아키텍처

### ✅ 138. 최소 구조

```text
Data Source

↓

Contract Validator

↓

Normalizer / Adapter

↓

Database / Event

↓

Quality Metric Collector

↓

Baseline Evaluator

↓

Anomaly Detector

↓

Finding / Alert

↓

Investigation

↓

Repair / Rollback / Contract Update
```

### ✅ 139. Data Contract와 Anomaly Detection 역할은 다르다

Data Contract:

```text
이 데이터가
허용된 형태와 의미를 지키는가?
```

Anomaly Detection:

```text
이 데이터의
양과 패턴이 평소와 다른가?
```

이다.

둘은 서로 보완 관계다.

### ✅ 140. Contract Validator

역할:

```text
필수 값 검사

타입 검사

Enum 검사

허용 범위 검사

Contract Version 확인
```

이다.

### ✅ 141. Normalizer

역할:

```text
External Schema

↓

Internal Domain Schema
```

변환이다.

예:

```text
외부 product_no

↓

내부 externalProductId
```

처럼 Mapping한다.

### ✅ 142. Quality Metric Collector

역할:

```text
Volume

Missing Rate

Invalid Rate

Freshness

Distribution
```

등을 집계한다.

### ✅ 143. Baseline Evaluator

역할:

```text
최근 정상 데이터

요일

시간대

캠페인

과거 지표
```

를 기준으로 예상 범위를 계산한다.

### ✅ 144. Anomaly Detector

역할:

```text
Actual vs Expected

Severity

Confidence

Minimum Sample Check
```

이다.

### ✅ 145. Finding Repository

1012의 Integrity Finding 구조를 재사용할 수 있다.

예:

```text
Finding Type
CONTRACT_VIOLATION

Finding Type
VOLUME_ANOMALY

Finding Type
SCHEMA_DRIFT
```

처럼 구분한다.

### ✅ 146. 별도 Finding 테이블이 반드시 필요한 것은 아니다

기존 Incident나 Audit 구조가 있다면 이를 확장할 수 있다.

중복 플랫폼을 만들지 않는 것이 중요하다.

### ✅ 174. Data Contract 최소 구현 프롬프트

```text
현재 프로젝트에 최소한의
Data Contract 관리 구조를 설계해줘.

먼저 기존 DTO, ValidationPipe,
class-validator, Zod, Prisma Schema,
API Client, Provider Adapter를 확인한다.

기존 Validation 도구를 우선 활용하고
중복 Framework를 도입하지 않는다.

대상 Contract 후보:

1. Order Tracking
2. Order Created Event
3. Naver EP
4. External Product / Provider Response

- Contract ID
- Version
- Producer
- Consumer
- 필수 필드
- 타입
- Nullable
- Enum
- Business Meaning
- Unit
- Timezone
- Unknown Value Policy
- Breaking Change Policy

Runtime Validation을 추가한다.

외부 데이터는 다음 순서로 처리한다.

External Input
→ Validation
→ Adapter
→ Internal Domain

계약 위반 시:

- Contract ID
- Version
- Error Code
- Field Path
- Timestamp

등만 Structured Log에 남긴다.

개인정보와 Secret 원문은 남기지 않는다.

알 수 없는 필드를 모두 무조건 거부하지 않는다.

반면 알 수 없는 주문 상태나
금액 의미 변화는 조용히 정상값으로 변환하지 않는다.

Consumer Contract Test를 작성한다.

테스트:

- 정상 Payload
- 필수 필드 누락
- Null
- Empty String
- 숫자/문자열 타입 변경
- 새로운 Enum 값
- 알 수 없는 추가 필드
- 이전 Contract Version
- Semantic Meaning 변경
- Provider API 200이지만 Contract Invalid

Production Raw Data를 대량 복사하지 않고
더미 Fixture로 테스트한다.
```

### ✅ 175. Anomaly Detection 구현 프롬프트

```text
현재 NestJS + PostgreSQL 기반 프로젝트에
최소한의 Data Quality Anomaly Detection을
추가하는 방안을 분석하고 설계해줘.

초기에는 복잡한 ML Model을 만들지 않는다.

대상 Metric:

1. 시간별 주문 건수
2. 유입경로 누락률
3. UNKNOWN 유입 비율
4. 네이버 EP 상품 건수
5. EP 생성 지연
6. External Contract Validation 실패율

실제 Schema에 없는 Metric은
구현하지 말고 필요한 데이터부터 명시한다.

각 Metric마다:

- Source of Truth
- 집계 기준
- Timezone
- Time Window
- Sample Count
- Baseline
- Minimum Sample
- Alert Condition
- Grace Period
- Severity
- Related Runbook

을 정의한다.

Anomaly 방법은 우선 다음만 사용한다.

- Static Threshold
- Relative Change
- Rolling Baseline
- Same Weekday / Hour Baseline

주문량 0과 Metric Missing을 구분한다.

Metric STALE 상태도 별도로 관리한다.

데이터가 부족할 때는
강제로 NORMAL이라고 판단하지 않는다.

최근 Release와 Marketing Campaign을
조사 Context로 연결한다.

동일 Anomaly가 반복될 때
Alert가 무한 생성되지 않게 한다.

Alert 결과에는:

- Metric
- Expected
- Actual
- Deviation
- Sample Count
- Baseline Version
- Detected At
- Related Release

를 포함한다.

AI는 원인 후보 분석만 수행하고,
자동 데이터 수정은 하지 않는다.

기존 Scheduler/Worker/Incident/Monitoring을
가능하면 재사용한다.

초기에는 Dashboard보다
정확한 Metric과 Alert부터 구현해줘.
```

### ✅ 177. 네이버 EP 품질 검사 프롬프트

```text

네이버 EP 파일과 관련 코드의

실제 EP 명세와 현재 Export 결과를

만들어내지 않는다.

- 출력 인코딩
- 상품 수
- 기존 EP와 변경된 EP의 차이

- Added
- Removed
- Changed Price
- Changed URL
- Changed Availability
- Changed Category
- Contract Invalid

새 EP 발행을 보류할 수 있는
Validation Gate를 설계한다.

기존 정상 EP 유지 전략도 검토하지만
가격·판매 상태가 오래된 데이터로

코드 수정 전 분석 보고서를 작성해줘.
```

- [ ] 0, Missing, Stale을 각각 다르게 처리하는가?

### Data Contract

- [ ] Producer와 Consumer가 명확한가?
- [ ] 필수 필드와 선택 필드를 정의했는가?
- [ ] 타입뿐 아니라 의미·단위·시간대도 정의했는가?
- [ ] Unknown Value 정책이 있는가?
- [ ] Contract Version을 관리하는가?
- [ ] 변경 시 Consumer 영향 분석을 수행하는가?

### Runtime Validation

- [ ] 외부 JSON을 런타임에서 검증하는가?
- [ ] Raw Response를 내부 Domain에 직접 전달하지 않는가?
- [ ] Contract Invalid를 일반 HTTP 오류와 구분하는가?
- [ ] 계약 위반 데이터를 안전하게 격리할 수 있는가?
- [ ] PII·Secret을 Error Log에 남기지 않는가?

### Schema Drift

- [ ] Prisma Schema와 실제 DB 구조를 비교할 수 있는가?
- [ ] 운영 Migration History를 확인하는가?
- [ ] 수동 DDL 변경을 파악할 수 있는가?
- [ ] Drift 발견 시 DB를 자동 수정하지 않는가?
- [ ] Expand-and-Contract 방식이 필요한지 검토하는가?
- [ ] Backfill 결과를 검증하는가?

### Anomaly Detection

- [ ] 주문량 Baseline이 있는가?
- [ ] 같은 요일·시간대 특성을 고려하는가?
- [ ] 최소 Sample 조건이 있는가?
- [ ] Spike와 Drop을 모두 보는가?
- [ ] 캠페인·공휴일·배포를 조사 Context로 활용하는가?
- [ ] Anomaly와 확정 장애를 구분하는가?

### Order / Tracking

- [ ] 신청 생성 지표와 신청 완료 지표를 구분하는가?
- [ ] 주문 수와 Tracking Event 수를 동일시하지 않는가?
- [ ] visitorId 누락률을 볼 수 있는가?
- [ ] UNKNOWN과 DIRECT를 구분하는가?
- [ ] 유입정보가 어디에서 누락되는지 추적 가능한가?
- [ ] 개인정보 수집·동의 정책을 준수하는가?

### Naver EP

- [ ] 상품 ID가 안정적인가?
- [ ] 중복 ID가 없는가?
- [ ] 가격 의미와 형식이 일치하는가?
- [ ] 상품 URL이 올바른가?
- [ ] EP Item Count가 급변하는지 보는가?
- [ ] 이전 EP와 Diff를 비교하는가?
- [ ] Critical Contract Violation을 감지하는가?

### Monitoring

- [ ] Data Metric의 마지막 갱신 시각을 알 수 있는가?
- [ ] Data Quality Failure를 Alert로 볼 수 있는가?
- [ ] 동일 Alert를 Deduplicate하는가?
- [ ] Alert False Positive를 검토하는가?
- [ ] Metric Label에 PII를 사용하지 않는가?

### AI

- [ ] AI가 실제 관측값과 추측을 구분하는가?
- [ ] AI에 필요한 최소 데이터만 제공하는가?
- [ ] AI가 이상 탐지 결과의 원인을 임의 확정하지 않는가?
- [ ] AI가 가격·주문·고객 데이터를 자동 수정하지 않는가?
- [ ] 실제 조치는 검증된 코드와 권한 정책을 사용하는가?

### 📌 요약

1012에서는:

```text
Business Invariant

↓

Consistency Audit

↓

Finding

↓

Safe Repair
```

를 다뤘다.

1013에서는 그보다 넓은 문제를 다뤘다.

```text
데이터가 규칙을 지키고 있더라도

그 데이터가 정말 신뢰할 수 있는가?
```

예를 들어:

```text
Order Created
SUCCESS

Database Insert
SUCCESS
```

이지만:

```text
visitorId
NULL

campaignCode
NULL
```

이라면 주문은 정상이고 광고 분석 데이터는 불완전할 수 있다.

또:

```text
외부 API
200 OK

Schema Validation
SUCCESS
```

라도:

```text
price
단말기 가격 → 월 납부금
```

처럼 의미가 바뀌었다면 잘못된 계산이 발생할 수 있다.

따라서 핵심은 다음 네 가지다.

**첫 번째, Data Contract**

```text
Producer

↓

Contract

↓

Consumer
```

사이에서 데이터의 형식과 의미를 명확히 정의한다.

**두 번째, Data Quality Metric**

```text
Completeness

Validity

Timeliness

Accuracy

Volume

Distribution
```

등을 측정한다.

**세 번째, Anomaly Detection**

```text
Current Metric

vs

Expected Baseline
```

을 비교해 조용한 이상 현상을 탐지한다.

**네 번째, Schema Drift Detection**

```text
Expected Schema

vs

Actual Schema
```

를 비교하고 예상하지 못한 변경을 발견한다.

중요한 것은 모든 Anomaly를 즉시 장애라고 판단하지 않는 것이다.

```text
주문량 감소
```

의 원인은:

```text
실제 수요 감소

광고 집행 중단

Frontend 오류

Tracking 누락

Backend 오류
```

중 하나일 수 있다.

따라서:

```text
Detect

↓

Verify Data Freshness

↓

Compare Related Metrics

↓

Check Recent Changes

↓

Investigate

↓

Fix

↓

Validate
```

흐름으로 접근한다.

현재 투게더몰과 같은 구조에서는 우선 다음 순서가 현실적이다.

```text
1. Order / Tracking Metric 정의

2. 유입정보 누락률 측정

3. 주문량 Baseline 확보

4. 네이버 EP Validation / Diff

5. 외부 API Contract Validation

6. Schema Drift 점검

7. Data Quality Alert

8. AI 기반 원인 후보 요약
```

처음부터 ML 기반 데이터 분석 플랫폼을 만들 필요는 없다.

기존:

```text
PostgreSQL

NestJS

Scheduler

Worker

CloudWatch

관리자 Dashboard
```

만으로도 중요한 Data Quality Monitoring을 시작할 수 있다.

전체 흐름을 연결하면:

```text
Data Producer
       ↓
Data Contract
       ↓
Runtime Validation
       ↓
Domain Mapping
       ↓
Database / Event
       ↓
Quality Metric
       ↓
Baseline Comparison
       ↓
Anomaly Detection
       ↓
Finding / Alert
       ↓
Investigation
       ↓
Correction / Contract Update
       ↓
Quality Verification
```

이 된다.

**Data Quality의 핵심은 데이터를 많이 모으는 것이 아니라, 어떤 데이터가 어떤 의미를 가지고 있으며, 그 데이터가 정상적으로 수집되고 있는지 계속 확인하는 것이다.**

그리고 가장 중요한 원칙은 다음과 같다.

> **“에러가 발생하지 않는 시스템”과 “정확한 데이터를 제공하는 시스템”은 다르다. 데이터의 형식·의미·양·신선도·분포를 지속적으로 검증해야 비로소 운영 지표와 자동화 결과를 신뢰할 수 있다.**
