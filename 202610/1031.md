## 1. 서버가 정상이어도 매출에는 문제가 생길 수 있다

### ✅ 1. 1030과의 연결

1030에서는 실제 고객이 사용하는 주요 기능을 지속적으로 검증하는 방법을 다뤘다.

**기술적으로 발생한 오류가 실제 고객의 신청 완료율과 회사의 업무 성과에 얼마나 영향을 미쳤는지 어떻게 측정할까?**

### ✅ 2. 일반적인 기술 지표

```text

20%

99.9%

정상
```

### ✅ 3. 그러나 실제 상황은?

```text

↓

정상
```

### ✅ 4. 반대 상황도 있다


**Technical Reliability**

```text

```

**Business Reliability**

```text
고객이 중요한 업무를 정상적으로 완료할 수 있는가?
```

### ✅ 6. Business Reliability의 목적

고객의 실제 목표에 영향을 미치는 오류를 탐지하고, 기술적 개선의 우선순위를 결정하는 것이다.

```text

Incident Impact

Business Observability
```

### ✅ 8. 가장 중요한 원칙

**전환율이 낮아졌다는 사실만으로 시스템 장애라고 단정하지 않는다.**

광고 품질, 상품 가격, 재고, 고객 의사, 계절성, UX, 기술적 오류 등 여러 원인이 존재할 수 있기 때문이다.

## 2. Technical SLI와 Business SLI의 차이

### ✅ 9. SLI란?

Service Level Indicator의 약자로 서비스 품질을 측정하는 지표다.

### ✅ 10. Technical SLI

예:

```text
성공한 API 요청

÷

전체 API 요청
```

### ✅ 11. Business SLI

예:

```text
정상 완료된 유효 신청 시도

÷

전체 유효 신청 시도
```

단 어떤 신청을 유효한 시도로 분류할지 명확히 정의해야 한다.

### ✅ 12. Technical SLI의 문제

HTTP 200 응답이 반환됐다는 사실이 실제 업무 성공을 보장하지는 않는다.

예:

```json
{
  "success": false,
  "error": "ORDER_SAVE_FAILED"
}
```

위 응답이 HTTP 200으로 반환된다면 단순 HTTP 성공률로는 오류를 발견하기 어렵다.

### ✅ 13. Business SLI의 장점

실제 업무가 완료됐는지에 초점을 맞출 수 있다.

### ✅ 14. Business SLI의 한계

정확한 업무 이벤트와 성공 조건이 정의돼 있지 않으면 결과를 잘못 측정할 수 있다.

### ✅ 15. 세 가지 지표를 구분한다

| 지표 | 측정 대상 | 예시 |
|---|---|---|
| Technical SLI | 서버 기능의 안정성 | API 성공률 |
| Journey SLI | 고객의 핵심 동작 성공 | 유효 신청 요청 처리 성공률 |
| Conversion KPI | 고객 행동과 비즈니스 성과 | 방문 대비 신청 완료율 |

### ✅ 16. 중요

**Conversion KPI 자체를 기술적 신뢰성 SLI로 그대로 사용하지 않는다.**

고객이 마음을 바꿔 신청하지 않는 것은 시스템 오류가 아니기 때문이다.

## 3. Customer Journey 정의

### ✅ 17. Customer Journey란?

고객이 특정 목표를 이루기 위해 거치는 행동의 흐름이다.

### ✅ 18. 휴대폰 온라인몰의 Journey

```text
Homepage
     ↓
Product List
     ↓
Product Detail
     ↓
Application Modal
     ↓
Application Started
     ↓
Submit Attempt
     ↓
Server Accepted
     ↓
Application Created
```

### ✅ 19. 실제 신청 이후에도 업무가 이어진다

```text
Application Created
        ↓
상담 / 확인
        ↓
신청서 발송
        ↓
개통 진행
        ↓
개통 완료
```

### ✅ 20. 한 번에 전체 Journey를 분석해야 할까?

그럴 필요는 없다.

처음에는 고객 홈페이지의 신청 완료까지 측정하고, 이후 관리자 업무 및 실제 개통 단계로 확장한다.

### ✅ 21. 주요 Journey를 나눈다

```text
JOURNEY_PRODUCT_DISCOVERY

JOURNEY_PRODUCT_SELECTION

JOURNEY_APPLICATION

JOURNEY_ORDER_PROCESSING

JOURNEY_ACTIVATION
```

### ✅ 22. Journey의 시작점과 끝점을 정한다

예:

```text
Application Journey 시작:
신청 모달을 연 시점

Application Journey 종료:
서버에서 주문 생성이 확정된 시점
```

### ✅ 23. 시작점이 달라지면 전환율도 달라진다

```text
상품 상세 조회 → 신청 완료
```

와:

```text
신청 모달 열기 → 신청 완료
```

는 서로 다른 지표다.

### ✅ 24. 따라서 지표 이름에 분모를 명확히 반영한다

예:

```text
Product View to Application Rate

Modal Open to Application Rate

Submit Attempt Success Rate
```

## 4. Conversion Funnel 설계

### ✅ 25. Conversion Funnel이란?

고객이 목표를 이루기까지의 주요 행동을 단계별로 측정하는 구조다.

### ✅ 26. 예시

```text
상품 상세 조회
12,000

      ↓

신청 모달 열기
2,400

      ↓

신청 제출 시도
1,000

      ↓

정상 신청 완료
900
```

모두 설명을 위한 가상 데이터다.

### ✅ 27. 단계별 전환율

| 단계 | 건수 | 이전 단계 대비 |
|---|---:|---:|
| 상품 상세 조회 Journey | 12,000 | — |
| 신청 모달 열기 | 2,400 | 20.0% |
| 제출 시도 | 1,000 | 41.7% |
| 신청 완료 | 900 | 90.0% |

### ✅ 28. 전체 전환율

```text
신청 완료
900

÷

상품 상세 조회 Journey
12,000

=

7.5%
```

### ✅ 29. 여기서 중요한 점

12,000이라는 수치가 단순 페이지 조회 횟수인지, 고유 사용자 수인지, 고유 Journey 수인지에 따라 결과의 의미가 달라진다.

### ✅ 30. 권장 기준

초기 Funnel에서는 동일한 단위를 일관되게 사용한다.

예:

```text
하나의 Journey에서
각 단계 최초 도달만 집계
```

### ✅ 31. 중복 조회

고객 한 명이 같은 상세페이지를 다섯 번 열었다고 다섯 명의 고객으로 계산해서는 안 된다.

### ✅ 32. 다중 상품 탐색

반대로 한 고객이 서로 다른 상품을 비교한 경우는 상품별 Journey 분석이 필요할 수 있다.

### ✅ 33. 따라서 식별 단위가 중요하다

```text
User

Session

Journey

Product Journey

Application Attempt

Order
```

를 구분한다.

## 5. Funnel의 실패는 모두 기술적 실패인가?

### ✅ 34. 아니다

예:

```text
상품 상세 조회
12,000

↓

신청 모달 열기
2,400
```

차이인 9,600건을 시스템 오류라고 해석해서는 안 된다.

### ✅ 35. 단순 이탈

고객이 상품을 살펴본 뒤 구매하지 않기로 결정했을 수 있다.

### ✅ 36. 상품 경쟁력 문제

가격이나 요금제 조건이 고객의 기대와 맞지 않을 수 있다.

### ✅ 37. UX 문제

신청 버튼을 찾지 못했거나 모달이 사용하기 어려웠을 수 있다.

### ✅ 38. 기술적 실패

JavaScript 오류나 API 장애 때문에 신청 절차로 진입하지 못했을 수 있다.

### ✅ 39. 원인을 구분한다

```text
CUSTOMER_ABANDONMENT

BUSINESS_MISMATCH

UX_FRICTION

TECHNICAL_FAILURE

UNKNOWN
```

### ✅ 40. Abandonment와 Error의 차이

**Abandonment**

고객이 다음 단계로 진행하지 않은 상태다.

**Technical Error**

시스템의 결함 때문에 의도한 작업을 정상적으로 수행할 수 없었던 상태다.

### ✅ 41. 단순 이탈은 오류 증거가 아니다

이벤트가 발생하지 않았다는 이유만으로 기술적 실패로 분류하면 안 된다.

### ✅ 42. 그러나 오류가 발생했는데 이벤트도 남지 않을 수 있다

예:

```text
상품 상세 진입

↓

JavaScript 초기화 오류

↓

Tracking Script도 실행 실패

↓

이벤트 없음
```

### ✅ 43. 따라서 이벤트 수집과 기술적 오류 모니터링을 함께 사용한다

```text
Funnel Events

+

Frontend Error Logs

+

API Errors

+

Synthetic Monitoring
```

## 6. Business SLI를 위한 성공·실패 정의

### ✅ 44. 핵심은 결과 분류다

신청 제출 시도를 예로 들어보자.

### ✅ 45. 결과 상태

```text
SUCCEEDED

TECHNICAL_FAILED

BUSINESS_REJECTED

PENDING

UNKNOWN
```

### ✅ 46. SUCCEEDED

서버가 실제 주문 생성 또는 신청 접수를 확정한 상태다.

### ✅ 47. TECHNICAL_FAILED

DB 저장 실패, 서버 장애, 처리 중 내부 오류 등 기술적 원인으로 신청을 완료하지 못한 상태다.

### ✅ 48. BUSINESS_REJECTED

정상적인 업무 규칙에 따라 요청을 거부한 상태다.

예:

```text
필수 입력값 오류

지원하지 않는 가입 조건

유효하지 않은 상품 선택
```

### ✅ 49. PENDING

신청 처리가 진행 중이며 결과가 아직 확정되지 않은 상태다.

### ✅ 50. UNKNOWN

제출 요청 이후 실제 성공·실패 결과를 확정할 수 없는 상태다.

### ✅ 51. 중요

```text
BUSINESS_REJECTED
```

를 언제나 정상으로 분류하는 것은 아니다.

### ✅ 52. 예를 들어

프론트엔드 오류 때문에 유효한 고객 입력이 잘못된 형식으로 전송됐다면 실제로는 기술적 결함이다.

### ✅ 53. 따라서 오류 코드만으로 판단하지 않는다

```text
HTTP Status

Application Error Code

Validation Rule

Current Business State

Request Trace
```

를 함께 확인한다.

## 7. 신청 처리 신뢰성 SLI

### ✅ 54. 정의 예시

**유효한 제출 시도 중 고객의 신청이 정상적으로 완료된 비율**

### ✅ 55. 기본 공식

```text
Application Submission SLI

=

Confirmed Successful Attempts
─────────────────────────────
Eligible Submission Attempts
```

### ✅ 56. Eligible Attempt

업무적으로 유효하며 실제 신청 처리를 요청한 논리적 시도다.

### ✅ 57. 정상적인 업무 거부는 별도 관리

정상적인 Validation Reject는 기술적 신뢰성 분모에서 제외할 수 있다.

다만 해당 거부가 올바른지 검증해야 한다.

### ✅ 58. 결과 불명 상태

충분한 결과 확정 시간이 지났음에도 UNKNOWN이라면 보수적으로 실패 측에 포함할 수 있다.

### ✅ 59. PENDING 처리

아직 정상 처리 중인 작업을 즉시 실패로 단정하지 않는다.

### ✅ 60. 결과 확정 시간

예:

```text
Application Attempt

↓

24시간 이내 결과 확정
```

과 같이 명확한 기간을 정의할 수 있다.

24시간은 설명용이며 실제 신청 처리 방식에 맞게 정해야 한다.

### ✅ 61. 단 즉시 접수 API라면?

대부분의 정상 응답이 몇 초 안에 완료되는 API라면 더 짧은 결과 확인 기준이 적절할 수 있다.

### ✅ 62. 지표 정의서에 반드시 기록한다

```text
Eligible Attempt 기준

Success 기준

Failure 기준

Unknown 처리

Pending 처리

Result Maturity Window

Deduplication 기준
```

## 8. 실제 수치 예시

### ✅ 63. 가상 신청 결과

| 상태 | 건수 |
|---|---:|
| SUCCEEDED | 900 |
| TECHNICAL_FAILED | 60 |
| BUSINESS_REJECTED | 40 |
| 합계 | 1,000 |

### ✅ 64. 유효한 기술 처리 대상

```text
SUCCEEDED
900

+

TECHNICAL_FAILED
60

=

960건
```

### ✅ 65. Business SLI

```text
900 ÷ 960

=

93.75%
```

### ✅ 66. 전체 제출 대비 완료율

```text
900 ÷ 1,000

=

90.0%
```

### ✅ 67. 두 수치는 다르다

**93.75%**

유효 신청의 기술적 처리 성공률이다.

**90.0%**

전체 제출 시도 대비 신청 완료율이다.

### ✅ 68. 상품 상세 Journey 대비 신청 완료율

```text
900 ÷ 12,000

=

7.5%
```

### ✅ 69. 세 가지 지표

| 지표 | 값 | 의미 |
|---|---:|---|
| 신청 처리 SLI | 93.75% | 기술적 처리 신뢰성 |
| 제출 대비 신청 완료율 | 90.0% | 제출 단계의 전체 완료율 |
| 상세 Journey 대비 신청 완료율 | 7.5% | 고객 전환 성과 |

### ✅ 70. 결론

**한 가지 전환율로 서버 안정성, 고객 행동, 비즈니스 성과를 모두 판단해서는 안 된다.**

## 9. 이벤트를 어떻게 설계할까?

### ✅ 71. Funnel을 측정하려면 이벤트가 필요하다

예:

```text
product_viewed

application_modal_opened

application_started

application_submit_attempted

application_created

application_rejected

application_technical_failed
```

### ✅ 72. 이벤트 발생 시점을 정확하게 정의한다

### ✅ 73. product_viewed

고객이 상품 상세 정보를 확인한 시점이다.

### ✅ 74. application_modal_opened

실제로 신청 모달이 표시된 시점이다.

### ✅ 75. application_started

고객이 신청 절차의 의미 있는 입력을 시작한 시점으로 정의할 수 있다.

### ✅ 76. application_submit_attempted

고객이 신청 제출 동작을 수행한 시점이다.

### ✅ 77. application_created

서버에서 실제 신청 생성이 확정된 시점이다.

### ✅ 78. application_rejected

업무 규칙에 따라 제출이 거부된 시점이다.

### ✅ 79. application_technical_failed

확인된 기술적 오류로 제출에 실패한 시점이다.

### ✅ 80. 주의

서버가 처리하지 못한 요청은 서버에 실패 이벤트가 남지 않을 수도 있다.

### ✅ 81. 따라서 Client Attempt와 Server Outcome을 구분한다

```text
Client
SUBMIT_ATTEMPTED

↓

Network

↓

Server
APPLICATION_CREATED
```

### ✅ 82. 네트워크가 끊기면?

```text
Client Attempt

↓

Request Lost

↓

Server Event 없음
```

일 수 있다.

### ✅ 83. 따라서 서버 이벤트만으로 전체 실패를 완벽히 측정할 수는 없다

실제 사용자의 클라이언트 측 오류도 관측해야 한다.

## 10. Event Taxonomy

### ✅ 84. Event Taxonomy란?

이벤트 이름, 의미, 발생 시점, 필드, 중복 처리 기준을 정의한 규칙이다.

### ✅ 85. 예시 표

| Event | 발생 위치 | 성공의 근거 |
|---|---|---|
| product_viewed | Frontend | 실제 상세 노출 |
| modal_opened | Frontend | 모달 렌더링 완료 |
| submit_attempted | Frontend | 제출 요청 시도 |
| application_created | Backend | DB 신청 생성 확정 |
| application_rejected | Backend | 업무 규칙 거부 |
| submit_network_failed | Frontend | 요청 결과 수신 실패 |

### ✅ 86. 모든 이벤트를 동일한 신뢰도로 보지 않는다

Frontend Event는 브라우저 환경, 광고 차단, 네트워크 상태의 영향을 받을 수 있다.

### ✅ 87. Backend Event

실제 서버에서 확정된 업무 상태를 확인하기에 상대적으로 적합하다.

### ✅ 88. Source of Truth

```text
실제 신청 건수:
Backend Order / Lead DB
```

### ✅ 89. GA4 Event

광고 및 사용자 행동 분석에 적합하다.

### ✅ 90. 내부 운영 지표

신청 접수 여부와 기술적 성공·실패를 확인하는 데 사용한다.

### ✅ 91. 중요한 원칙

**광고 분석 도구의 전환 이벤트 수와 실제 주문 DB의 건수를 동일하다고 가정하지 않는다.**

```text

≠
```

### ✅ 114. TypeScript Event Type

```typescript
type JourneyEventName =
  | 'product_viewed'
  | 'application_modal_opened'
  | 'application_started'
  | 'application_submit_attempted'
  | 'application_submit_network_failed';

interface JourneyEvent {
  eventId: string;

  journeyId: string;

  eventName: JourneyEventName;

  productCode?: string;

  deviceClass?: 'desktop' | 'mobile' | 'tablet';

  occurredAt: string;
}
```

### ✅ 115. 이벤트 생성 예시

```typescript
function createJourneyEvent(
  journeyId: string,
  eventName: JourneyEventName,
  productCode?: string,
): JourneyEvent {
  return {
    eventId: crypto.randomUUID(),

    journeyId,

    eventName,

    productCode,

    occurredAt: new Date().toISOString(),
  };
}
```

### ✅ 116. 중요한 주의

`crypto.randomUUID()`는 임의 식별자를 생성하는 용도다.

고객정보를 ID에 직접 포함하지 않는다.

### ✅ 117. Journey ID의 수명

브라우저 Session, 상품 탐색, 신청 절차 중 어느 단위로 유지할지 사전에 정의해야 한다.

### ✅ 118. Client Event를 신뢰할 수 있을까?

분석용 참고 정보로 활용할 수 있다.

하지만 클라이언트가 전송한 이벤트를 결제·주문·권한의 증거로 사용해서는 안 된다.

### ✅ 119. Server Validation

이벤트 수집 Endpoint에도 다음을 적용한다.

```text
Schema Validation

Rate Limit

Payload Size Limit

Allowed Event Names

Input Sanitization
```

### ✅ 120. 이벤트 수집 실패

분석 이벤트가 전송되지 않았다고 실제 고객 신청 절차를 불필요하게 막지 않는 것이 일반적으로 바람직하다.

### ✅ 121. 다만 중요한 업무 상태 기록은 별도다

실제 신청 생성과 그에 필요한 업무 감사 기록은 올바른 DB Transaction 및 Outbox 설계로 관리한다.

## 15. Application Attempt Ledger

### ✅ 131. 실제 실패를 측정하려면 시도 기록도 필요하다

성공 주문만 저장하면 실패한 제출 시도의 수를 알기 어렵다.

### ✅ 132. Attempt Ledger

논리적 신청 시도와 최종 결과를 기록하는 구조다.

### ✅ 133. 기본 상태

```text
PENDING

SUCCEEDED

TECHNICAL_FAILED

BUSINESS_REJECTED

UNKNOWN
```

### ✅ 134. PostgreSQL Schema 예시

```sql
CREATE TABLE application_attempt_metrics (
  id UUID PRIMARY KEY,

  attempt_key TEXT NOT NULL UNIQUE,

  journey_id UUID,

  product_code TEXT,

  acquisition_channel TEXT,

  device_class TEXT,

  outcome TEXT NOT NULL CHECK (
    outcome IN (
      'PENDING',
      'SUCCEEDED',
      'TECHNICAL_FAILED',
      'BUSINESS_REJECTED',
      'UNKNOWN'
    )
  ),

  error_code TEXT,

  started_at TIMESTAMPTZ NOT NULL,

  finalized_at TIMESTAMPTZ,

  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

### ✅ 135. 위 Schema의 목적

하나의 논리적 제출 시도에 하나의 최종 결과를 기록하는 것이다.

### ✅ 136. 개인정보 저장 최소화

Metric 테이블에 고객 이름이나 전화번호를 중복 저장하지 않는다.

### ✅ 137. 실제 주문과의 연결

필요하다면 제한된 내부 Reference로 연결하고 접근 권한을 분리한다.

### ✅ 138. 중복 Attempt

같은 `attempt_key`가 다시 전달되면 새로운 시도로 중복 생성하지 않는다.

### ✅ 139. 최종 결과가 변경될 수 있다

처음에는 UNKNOWN이었지만 실제 주문이 생성된 사실이 확인될 수 있다.

### ✅ 140. 따라서 상태 전이를 정의한다

```text
PENDING
   ↓
UNKNOWN
   ↓
SUCCEEDED
```

처럼 Reconciliation 결과에 따라 변경할 수 있다.

### ✅ 141. 감사 이력

결과가 수정된 이유와 시각을 별도 기록한다.

### ✅ 142. 중요한 한계

Backend에 도달하지 못한 제출 시도는 이 테이블만으로 측정할 수 없다.

따라서 Client Event와 Frontend Error Monitoring이 필요하다.

## 16. PostgreSQL Business SLI Query

### ✅ 143. 목표

일자별 유효 신청의 기술적 처리 성공률을 계산한다.

### ✅ 144. 가정

- 하나의 Row가 하나의 논리적 제출 시도다.
- `outcome`은 확인된 최신 상태다.
- 정상적인 업무 거부는 기술 처리 SLI에서 제외한다.
- 충분한 결과 확정 시간이 지난 시도만 분석한다.

### ✅ 145. SQL 예시

```sql
SELECT
  DATE_TRUNC(
    'day',
    started_at AT TIME ZONE 'Asia/Seoul'
  )::date AS local_date,

  COUNT(*) FILTER (
    WHERE outcome = 'SUCCEEDED'
  ) AS succeeded,

  COUNT(*) FILTER (
    WHERE outcome = 'TECHNICAL_FAILED'
  ) AS technical_failed,

  COUNT(*) FILTER (
    WHERE outcome = 'UNKNOWN'
  ) AS outcome_unknown,

  COUNT(*) FILTER (
    WHERE outcome = 'BUSINESS_REJECTED'
  ) AS business_rejected,

  COUNT(*) FILTER (
    WHERE outcome = 'PENDING'
  ) AS pending,

  ROUND(
    100.0
    * COUNT(*) FILTER (
        WHERE outcome = 'SUCCEEDED'
      )
    / NULLIF(
        COUNT(*) FILTER (
          WHERE outcome IN (
            'SUCCEEDED',
            'TECHNICAL_FAILED',
            'UNKNOWN'
          )
        ),
        0
      ),
    2
  ) AS application_sli_percent

FROM application_attempt_metrics

WHERE started_at >= $1
  AND started_at < $2

  AND started_at < NOW() - INTERVAL '24 hours'

GROUP BY local_date

ORDER BY local_date;
```

### ✅ 146. 이 SQL의 SLI 정의

```text
SUCCEEDED

÷

SUCCEEDED
+
TECHNICAL_FAILED
+
UNKNOWN
```

이다.

### ✅ 147. UNKNOWN 처리

결과 확정 기준을 초과한 UNKNOWN은 보수적으로 미완료에 포함한다.

### ✅ 148. PENDING 주의

충분한 시간이 지났는데도 PENDING으로 남은 Row가 있다면 별도 데이터 품질 오류로 보고 조사해야 한다.

### ✅ 149. PENDING을 분모에서 계속 제외하면?

장기간 결과가 확정되지 않은 작업 때문에 SLI가 실제보다 좋게 보일 수 있다.

### ✅ 150. 운영 권장

결과 확정 기한이 지나면 Recovery Process가 PENDING을 조사하고 UNKNOWN 등으로 분류하도록 설계한다.

### ✅ 151. SQL 실행 전 확인

현재 프로젝트의 실제 Prisma Schema, Timestamp, 업무 상태 정의에 맞게 수정해야 한다.

### ✅ 152. 중요한 점

위 SQL은 **실제 운영 데이터에 대한 측정 결과가 아니라 구현 예시**다.

## 17. Funnel Query 설계

### ✅ 153. Funnel 계산에는 이벤트 수집 구조가 필요하다

예를 들어 다음 테이블을 가정한다.

```text
customer_journey_events
```

### ✅ 154. 이벤트 필드

```text
event_id

journey_id

event_name

occurred_at

product_code

acquisition_channel

device_class
```

### ✅ 155. 핵심 조건

하나의 Journey가 같은 단계를 여러 번 기록하더라도 한 번만 계산한다.

### ✅ 156. PostgreSQL 예시

```sql
WITH steps AS (
  SELECT
    journey_id,

    MIN(occurred_at) FILTER (
      WHERE event_name = 'product_viewed'
    ) AS viewed_at,

    MIN(occurred_at) FILTER (
      WHERE event_name = 'application_modal_opened'
    ) AS modal_at,

    MIN(occurred_at) FILTER (
      WHERE event_name = 'application_submit_attempted'
    ) AS attempted_at

  FROM customer_journey_events

  WHERE occurred_at >= $1
    AND occurred_at < $2

  GROUP BY journey_id
)

SELECT
  COUNT(*) FILTER (
    WHERE viewed_at IS NOT NULL
  ) AS viewed_journeys,

  COUNT(*) FILTER (
    WHERE viewed_at IS NOT NULL
      AND modal_at >= viewed_at
  ) AS modal_journeys,

  COUNT(*) FILTER (
    WHERE viewed_at IS NOT NULL
      AND modal_at >= viewed_at
      AND attempted_at >= modal_at
  ) AS attempted_journeys

FROM steps;
```

### ✅ 157. 위 SQL의 한계

각 Journey의 최초 이벤트를 기준으로 계산한다.

### ✅ 158. 복잡한 반복 Journey

다음 상황에서는 별도 Funnel 정의가 필요하다.

```text
상품 A 상세 조회

↓

신청 모달 열기

↓

상품 B 이동

↓

다시 신청 시작
```

### ✅ 159. 또 다른 문제

기간 시작 전에 발생한 Journey의 이전 단계가 누락될 수 있다.

### ✅ 160. 따라서 실제 분석에서는

```text
Journey Cohort

Attribution Window

Event Order

Deduplication

Cross-session Rule
```

을 명확히 정의해야 한다.

### ✅ 161. 신청 완료는 Backend 기준으로 연결한다

Frontend의 `application_created` 유사 이벤트가 아니라 실제 신청 DB에서 확정한 결과와 연결하는 것이 중요하다.

## 18. Funnel Cohort와 기간 문제

### ✅ 162. 고객은 같은 날 신청하지 않을 수 있다

예:

```text
10월 29일

10월 31일
신청 완료
```

### ✅ 163. 일자별 이벤트 수만 나누면?

서로 다른 날짜의 고객 행동을 혼합하면서 전환율이 왜곡될 수 있다.

### ✅ 164. Cohort 방식

특정 날짜에 Journey를 시작한 고객들을 하나의 그룹으로 묶는다.

### ✅ 165. 예시

```text
10월 29일
상품 상세 최초 조회

↓

7일 이내
신청 완료 여부 확인
```

### ✅ 166. Conversion Window

Journey 시작 이후 신청 완료로 인정할 기간이다.

### ✅ 167. 7일은 예시다

실제 고객이 상품을 비교하고 신청하는 데 걸리는 시간을 분석해 정해야 한다.

### ✅ 168. Immature Cohort

전환 인정 기간이 아직 끝나지 않은 그룹이다.

### ✅ 169. 잘못된 비교

```text
지난달의 7일 전환율

vs

오늘의 7일 전환율
```

오늘 시작한 Journey는 아직 7일이 지나지 않았으므로 직접 비교할 수 없다.

### ✅ 170. 해결 방법

```text
Matured Cohort Only
```

또는 동일한 경과 시간 기준으로 비교한다.

### ✅ 171. 지표에 기간을 명시한다

예:

```text
7-day Product View to Application Rate
```

### ✅ 174. 주의

어떤 채널을 통해 들어왔다고 해서 해당 채널이 전환을 단독으로 만들어냈다고 단정할 수는 없다.

### ✅ 175. First Touch

고객의 최초 관측 유입 경로다.

### ✅ 176. Last Touch

전환 직전 또는 규정된 기준에 따른 마지막 관측 유입 경로다.

### ✅ 177. Session Source

현재 세션의 유입 경로다.

```text
Naver Shopping

Direct

Application Created
```


또는:

```text

```

### ✅ 180. 여러 관점으로 비교할 수도 있다

하지만 한 보고서 안에서 서로 다른 Attribution 규칙의 숫자를 무분별하게 합산해서는 안 된다.

### ✅ 182. 개인정보 주의

UTM Parameter에도 고객 이름이나 전화번호 같은 정보를 넣지 않는다.

### ✅ 183. 광고 플랫폼별 숫자가 다를 수 있다

클릭 집계, Attribution Window, Bot Filtering, Cookie, Consent, Conversion Definition이 서로 다르기 때문이다.

### ✅ 184. 따라서 구분한다


### ✅ 185. 실제 신청 건수의 기준

내부 주문 또는 Lead DB를 Source of Truth로 사용한다.

## 20. 채널별 분석을 잘못하면 발생하는 문제

### ✅ 186. 예시

| 채널 | 상품 Journey | 신청 완료 | 전환율 |
|---|---:|---:|---:|
| Naver Paid | 5,000 | 200 | 4.0% |
| Organic | 3,000 | 210 | 7.0% |
| Direct | 2,000 | 160 | 8.0% |

가상 데이터다.

### ✅ 187. 단순 해석

Direct가 가장 전환율이 높다고 판단할 수 있다.

### ✅ 188. 하지만 고객 특성이 다르다

Direct 유입은 이미 상품을 비교하고 다시 방문한 고객이 많을 수 있다.

### ✅ 189. 광고의 역할

광고가 최초 고객 유입에 기여한 뒤 고객이 직접 재방문해 신청했을 수도 있다.

### ✅ 190. 따라서

채널별 전환율만으로 광고 효율을 확정하지 않는다.

### ✅ 191. 분석 기준

```text
First / Last Touch

Campaign

Landing Page

Device

Product

New / Returning

Attribution Window
```

을 명확히 관리한다.

### ✅ 192. Simpson's Paradox

전체 전환율은 좋아졌는데 특정 기기·채널에서는 오히려 나빠지는 현상이 발생할 수 있다.

### ✅ 193. 주의

분석 세그먼트를 너무 많이 쪼개면 표본 수가 부족해 우연한 차이가 크게 보일 수 있다.

### ✅ 200. 단 수정 후 전환율이 상승했다고?

그 변화가 코드 수정 때문에 발생했다고 단정하기 전에 유입 구성이나 프로모션 변경 등을 확인한다.

필요하면 1017의 A/B Test 설계를 적용한다.

## 22. Frontend Error와 Funnel 연결

### ✅ 201. Frontend Error Monitoring

브라우저에서 발생한 JavaScript 오류를 수집한다.

### ✅ 202. 예시

```text
TypeError

Chunk Load Failure

Unhandled Promise Rejection

Form Validation Exception

Network Error
```

### ✅ 203. 단순 오류 건수의 한계

모든 오류가 고객의 구매를 막는 것은 아니다.

### ✅ 204. Journey Impact

오류가 발생한 Journey에서 실제 구매 흐름이 중단됐는지 분석한다.

### ✅ 205. 예시

```text
Journey A

상품 상세 조회

↓

Modal Open

↓

Frontend Error

↓

Submit Attempt 없음
```

### ✅ 206. 이런 경우

기술적 원인과 전환 실패의 연관성을 조사할 수 있다.

### ✅ 207. 그러나 단일 이벤트만으로 원인을 확정하지 않는다

고객이 오류 이후 스스로 이탈했을 수도 있다.

### ✅ 208. 필요한 정보

```text

Error Category

Component

Route

Application Version

Occurred At

```

### ✅ 209. 개인정보 주의

JavaScript 오류 메시지에 고객 입력이나 API Response가 포함될 수 있으므로 그대로 저장하지 않는다.

### ✅ 210. Session Replay

사용자 행동 분석에 도움이 될 수 있지만 민감한 입력과 화면 내용의 기록 위험이 있다.

현재 단계에서는 이벤트 기반 진단부터 도입하는 편이 단순하고 안전하다.

## 23. Web Vitals와 Conversion의 관계

### ✅ 211. 성능도 고객 경험에 영향을 줄 수 있다

대표적인 Core Web Vitals는 다음과 같다.

```text
LCP

INP

CLS
```

### ✅ 212. LCP

Largest Contentful Paint.

주요 콘텐츠가 표시되기까지 걸리는 시간을 측정한다.

### ✅ 213. INP

Interaction to Next Paint.

사용자 상호작용에 대한 응답성을 측정한다.

### ✅ 214. CLS

Cumulative Layout Shift.

예상하지 못한 화면 배치 변경을 측정한다.

### ✅ 215. Google의 권장 기준

| 지표 | Good 기준 |
|---|---|
| LCP | 2.5초 이하 |
| INP | 200ms 이하 |
| CLS | 0.1 이하 |

일반적으로 실제 사용자 데이터의 75백분위수를 기준으로 평가한다.

### ✅ 216. 모바일과 데스크톱

별도로 분석하는 것이 중요하다.

### ✅ 217. 성능과 전환율

```text
Page Performance

↓

User Experience

↓

Journey Behavior

↓

Conversion
```

의 관계를 분석할 수 있다.

### ✅ 218. 중요한 한계

페이지가 느리다는 사실과 전환율 감소 사이에 인과관계가 있다고 자동으로 확정할 수는 없다.

### ✅ 219. 올바른 분석

```text
느린 페이지 그룹

vs

빠른 페이지 그룹
```

의 전환 차이를 비교하되 Device, Channel, Product 등을 고려한다.

### ✅ 220. 더 강한 검증

가능하다면 성능 개선 전후의 동등한 집단 비교 또는 통제된 실험을 검토한다.

## 24. Business SLO란?

### ✅ 221. SLO란?

Service Level Objective.

정해진 기간 동안 달성하려는 신뢰성 목표다.

### ✅ 222. 예시

```text
Application Submission SLI

목표:
99.5%

기간:
Rolling 28 Days
```

### ✅ 223. 의미

정해진 유효 신청 시도의 99.5% 이상이 정상적으로 처리되도록 목표를 설정한 것이다.

### ✅ 224. 99.5%는 예시다

실제 서비스의 데이터, 장애 빈도, 고객 영향도에 따라 목표를 정해야 한다.

### ✅ 225. 목표가 높을수록 좋은가?

무조건 그렇지는 않다.

### ✅ 226. 지나치게 높은 목표

현재 인프라와 업무 구조에서 달성하기 어려운 목표를 설정하면 모든 개발을 안정화 작업에만 사용하게 될 수 있다.

### ✅ 227. 지나치게 낮은 목표

고객이 반복적으로 피해를 입어도 운영상 문제가 없는 것으로 판단할 수 있다.

### ✅ 228. 따라서 합의가 필요하다

```text
Business Importance

Customer Impact

Historical Reliability

Operational Capability

Development Cost
```

를 고려한다.

## 25. Error Budget 계산

### ✅ 229. Error Budget이란?

SLO에서 허용하는 실패의 범위다.

### ✅ 230. 예시 SLO

```text
99.5%
```

### ✅ 231. 허용 실패율

```text
100% - 99.5%

=

0.5%
```

### ✅ 232. 유효 신청 시도 10,000건

```text
10,000 × 0.005

=

50건
```

### ✅ 233. 의미

28일 동안 유효 신청 시도 10,000건이 발생했다면 실패 50건까지가 예시 SLO의 Error Budget에 해당한다.

### ✅ 234. 실제 실패 20건

```text
허용:
50건

실제:
20건

남은 Budget:
30건
```

### ✅ 235. 실제 실패 70건

```text
허용:
50건

실제:
70건

초과:
20건
```

### ✅ 236. 중요한 점

Error Budget은 실패를 일부러 발생시켜도 된다는 허가가 아니다.

### ✅ 237. 목적

서비스 안정성과 신규 기능 개발 사이의 우선순위를 데이터로 조정하는 것이다.

### ✅ 238. SLO가 깨졌다면?

```text
신규 기능 개발 속도 조정

문제 원인 분석

Regression Test 강화

위험한 배포 제한

복구 자동화 개선
```

등을 검토할 수 있다.

## 26. Error Budget Burn Rate

### ✅ 239. Burn Rate란?

실제 실패율이 SLO의 허용 실패율보다 얼마나 빠르게 발생하는지를 나타낸다.

### ✅ 240. 공식

```text
Burn Rate

=

Observed Failure Rate
─────────────────────
Allowed Failure Rate
```

### ✅ 241. 예시

허용 실패율:

```text
0.5%
```

현재 관측 실패율:

```text
5.0%
```

### ✅ 242. 계산

```text
5.0% ÷ 0.5%

=

10배
```

### ✅ 243. 의미

현재 실패율이 예산을 소진하는 기준 속도의 10배라는 뜻이다.

### ✅ 244. 하지만 단기 데이터는 주의한다

10분 동안 신청 시도가 2건이고 1건이 실패했다면 실패율은 50%다.

### ✅ 245. 작은 표본 문제

이를 장기간 안정성이 50%라고 해석하면 안 된다.

### ✅ 246. Low Traffic Service

신청량이 적은 시간대에는 백분율보다 실패 건수와 개별 고객 영향을 함께 확인해야 한다.

### ✅ 247. Multiwindow Alert

짧은 시간과 긴 시간의 실패율을 함께 확인할 수 있다.

### ✅ 248. 예시

```text
최근 5분

+

최근 1시간
```

### ✅ 249. 하지만 현재 규모에서는

처음부터 복잡한 Burn Rate Alert를 구현하기보다 명확한 P0 기술 오류와 신청 실패율부터 모니터링하는 편이 현실적이다.

## 27. Conversion Rate가 내려갔을 때

### ✅ 250. 가장 흔한 오류

전환율이 떨어졌다고 곧바로 서버 문제라고 판단하는 것이다.

### ✅ 251. 원인 분류

```text
Traffic Quality

Marketing Campaign

Product Competitiveness

Pricing / Promotion

Inventory

UX

Performance

Technical Failure

Measurement Error
```

### ✅ 252. 진단 순서

```text
Conversion Drop
       ↓
Measurement Integrity Check
       ↓
Traffic Composition Check
       ↓
Funnel Stage Comparison
       ↓
Technical Error Correlation
       ↓
Business Rule / Price Check
       ↓
Root Cause Investigation
```

### ✅ 253. 첫 번째 — 데이터 품질

이벤트 수집 자체가 변경되지 않았는지 확인한다.

### ✅ 254. 두 번째 — 유입 구성

광고비나 유입 채널 비율이 변경됐는지 확인한다.

### ✅ 255. 세 번째 — 단계별 이탈

어느 구간에서 전환율이 하락했는지 확인한다.

### ✅ 256. 네 번째 — 기술적 오류

같은 시간대에 Frontend 또는 Backend 오류가 증가했는지 확인한다.

### ✅ 257. 다섯 번째 — 업무 조건

요금제, 할인 조건, 재고, 프로모션 변경이 있었는지 확인한다.

### ✅ 258. 최종 결론

기술적인 근거가 충분하지 않다면 단순히:

```text
Conversion Drop Detected
Root Cause Unknown
```

으로 기록한다.

원인을 억지로 확정하지 않는다.



### ✅ 262. 확인된 실패와 결과 불명 구분

결과를 알 수 없는 신청을 무조건 실패 건수로 확정하지 않는다.

다만 신뢰성 SLI에서는 보수적으로 미완료 취급할 수 있다.

### ✅ 263. 복구 이후

## 29. 전환 손실은 어떻게 추정할까?

```text
×
```

```text
25%
```


### ✅ 272. 중요

실제 발생한 확정 매출 손실로 보고해서는 안 된다.

### ✅ 273. 공헌이익을 사용한다

상품 판매금액 전체보다 비용을 고려한 공헌이익이 사업 영향 평가에 더 유용할 수 있다.

### ✅ 275. 신뢰구간 또는 시나리오

```text

기준

낙관적
```

### ✅ 276. AI의 역할

하지만 실제 수치를 임의로 생성하거나 추정치를 확정 실적으로 표현해서는 안 된다.

## 33. PostgreSQL 채널별 신청 신뢰성 조회

### ✅ 303. 목적

어느 유입 채널에서 제출 실패가 많이 발생했는지 확인한다.

### ✅ 304. SQL 예시

```sql
SELECT
  COALESCE(
    acquisition_channel,
    'unknown'
  ) AS channel,

  COUNT(*) FILTER (
    WHERE outcome = 'SUCCEEDED'
  ) AS succeeded,

  COUNT(*) FILTER (
    WHERE outcome = 'TECHNICAL_FAILED'
  ) AS technical_failed,

  COUNT(*) FILTER (
    WHERE outcome = 'UNKNOWN'
  ) AS outcome_unknown,

  ROUND(
    100.0
    * COUNT(*) FILTER (
        WHERE outcome = 'SUCCEEDED'
      )
    / NULLIF(
        COUNT(*) FILTER (
          WHERE outcome IN (
            'SUCCEEDED',
            'TECHNICAL_FAILED',
            'UNKNOWN'
          )
        ),
        0
      ),
    2
  ) AS submission_sli_percent

FROM application_attempt_metrics

WHERE started_at >= $1
  AND started_at < $2

  AND started_at < NOW() - INTERVAL '24 hours'

GROUP BY
  COALESCE(acquisition_channel, 'unknown')

ORDER BY succeeded DESC;
```

### ✅ 305. 주의

이 SQL은 채널별 제출 처리 신뢰성을 계산한다.

상품 상세 방문 대비 전환율은 계산하지 않는다.

### ✅ 306. 전환율 계산

각 채널별로 동일한 Attribution 기준을 사용한 Journey 분모가 별도로 필요하다.

### ✅ 307. Unknown Channel

유입 정보를 알 수 없는 경우를 임의로 Direct로 처리하지 않는다.

### ✅ 308. 작은 표본

채널별 Attempt가 적다면 비율만으로 순위를 결정하지 않는다.

## 📌 요약

1030에서는 실제 서비스 기능이 정상적으로 동작하는지 검증하는 방법을 다뤘다.

```text
Production
    ↓
Synthetic Monitoring
    ↓
Business Verification
    ↓
Evidence
```

1031에서는 그 결과를 실제 고객 행동과 연결해 서비스 신뢰성이 비즈니스에 미치는 영향을 분석하는 방법을 다뤘다.

```text
Customer Journey
        ↓
Funnel Events
        ↓
Submit Attempt
        ↓
Server-side Result
        ↓
Business SLI
        ↓
Conversion KPI
        ↓
SLO / Error Budget
        ↓
Incident Impact
        ↓
Improvement Priority
```

핵심 원칙은 일곱 가지다.

**첫 번째 — 서버 성공과 비즈니스 성공은 다르다.**

```text
API 200 OK
```

라고 해서 고객이 신청에 성공한 것은 아니다.

**두 번째 — 전환율과 기술적 신뢰성을 구분한다.**

```text
Conversion KPI:
고객이 얼마나 신청하는가?

Business SLI:
유효한 신청 요청을
시스템이 얼마나 정상 처리하는가?
```

**세 번째 — 실제 신청 성공은 Backend를 기준으로 측정한다.**

```text
Submit Button Click
≠
Application Created
```

이다.

**네 번째 — Client Event와 Server Event를 함께 사용한다.**

서버에 도달하지 못한 오류는 Backend Log에 남지 않을 수 있다.

**다섯 번째 — 전환율 하락을 무조건 기술적 장애라고 판단하지 않는다.**

광고 유입, 상품 조건, 가격, 재고, UX, 기술적 오류를 함께 검토한다.

**여섯 번째 — Error Budget을 통해 안정화의 우선순위를 정한다.**

기술적 실패가 고객의 신청을 막는다면 신규 기능 개발보다 안정화 작업을 우선해야 할 수 있다.

**일곱 번째 — 매출 손실은 확인된 사실과 추정치를 구분한다.**

기술 실패가 있었다고 해당 건수가 모두 실제 매출 손실인 것은 아니다.

현재 투게더몰에서는 다음 다섯 가지부터 시작하는 것이 가장 현실적이다.

```text
1. 실제 신청 완료 기준 정의

2. 제출 시도와 기술 실패 기록

3. 상품 → 모달 → 제출 → 완료 Funnel

4. 모바일 / 광고 채널별 분석

5. 기술 오류와 전환율 변화를 연결한 Dashboard
```

처음부터 복잡한 데이터 웨어하우스나 전문 분석 플랫폼을 도입할 필요는 없다.

현재 운영 중인 NestJS·PostgreSQL·React·광고 추적 구조를 정리하는 것만으로도 중요한 측정 기반을 만들 수 있다.

특히 기존 주문관리 시스템과 광고 분석 기능을 연결하면 다음 질문에 점차 근거를 갖고 답할 수 있다.

```text
어떤 채널에서 신청이 많이 발생하는가?

어떤 기종에서 신청이 중단되는가?

모바일 고객은 어느 단계에서 이탈하는가?

신청 API 장애가 실제로 몇 건의 접수에 영향을 줬는가?

어떤 기술적 문제를 먼저 수정해야
고객 피해를 줄일 수 있는가?
```

**최종적으로 기억해야 할 원칙은 다음과 같다.**

> 서비스의 신뢰성은 서버가 얼마나 오래 살아 있었는지만으로 판단할 수 없다. 실제 고객이 중요한 업무를 얼마나 안정적으로 완료할 수 있었는지, 실패가 발생했을 때 어느 단계에서 무엇이 잘못됐는지, 그리고 그 문제가 비즈니스에 얼마나 영향을 미쳤는지 측정할 수 있어야 한다.
