# 1017 운영 자동화/AI 워크플로우 심화 (41/N)
## Experiment Design, Statistical Guardrails, Metric Attribution, A/A Test와 신뢰할 수 있는 A/B 테스트

**날짜: 2026년 10월 17일**

## 1. 실험 결과가 좋아 보여도 믿을 수 없는 이유

### ✅ 1. 1016과의 연결

1016에서는 새로운 기능을 일부 사용자에게 공개하고 점진적으로 확대하는 Progressive Delivery를 다뤘다.

```text
Production Deployment
        ↓
Feature Flag
        ↓
Limited Rollout
        ↓
Canary Analysis
        ↓
Promotion / Rollback
```

1017에서는 다음 질문을 다룬다.

**신규 기능을 적용한 뒤 신청 완료율이 올라갔다면, 정말 그 기능 때문에 개선된 것일까?**

실제로는 광고 유입, 요금제 조건, 상품 출시, 요일, 고객 구성, 데이터 수집 오류 때문에 좋아 보이는 결과가 나타날 수 있다.

### ✅ 2. 배포 전후 비교의 문제

예를 들어 신규 신청 모달을 배포했다고 하자.

| 구분 | 기존 모달 | 신규 모달 |
|---|---:|---:|
| 방문자 | 1,000명 | 1,000명 |
| 신청 완료 | 100명 | 120명 |
| 신청 완료율 | 10% | 12% |

표면적으로는 신청 완료율이 10%에서 12%로 증가했다.

- 절대 증가: 2%p
- 상대 증가: 20%

하지만 기존 모달은 평일에 운영했고, 신규 모달은 신제품 사전예약 첫날에 운영했다면 어떨까?

실제로는 모달 개선 때문이 아니라 구매 의향이 높은 고객이 많이 유입돼서 완료율이 올라갔을 수 있다.

### ✅ 3. Correlation과 Causation

Correlation(상관관계)은 두 현상이 함께 나타났다는 뜻이다.

```text
신규 모달 배포
       ↓
신청 완료율 상승
```

Causation(인과관계)은 신규 모달 자체가 신청 완료율에 영향을 미쳤다는 뜻이다.

A/B 테스트는 무작위 배정을 통해 다른 요인들을 평균적으로 균형 있게 만들고, 변경의 인과적 효과를 추정하는 방법이다.

### ✅ 4. 단순 전후 비교의 문제

```text
월요일
일반 광고 운영
기존 신청 모달
완료율 10%

금요일
사전예약 시작
신규 신청 모달
완료율 15%
```

이 경우 완료율이 상승한 이유는 여러 가지일 수 있다.

```text
신규 모달

광고 고객 구성 변화

신제품 출시

프로모션

요일 차이

상품 조건 변경
```

이러한 요소를 구분하지 않은 채 신규 모달이 신청 완료율을 50% 개선했다고 주장하면 부정확하다.

### ✅ 5. A/B 테스트의 기본 구조

같은 기간에 실험 대상 사용자를 두 그룹으로 나눈다.

```text
실험 대상 사용자
        ↓
    Randomization
        ↓
   ┌───────────────┐
   │               │
Control        Treatment
기존 모달       신규 모달
   │               │
   └───────┬───────┘
           ↓
     동일한 Metric 비교
           ↓
     데이터 품질 검증
           ↓
       통계 분석
           ↓
       의사결정
```

두 그룹은 서로 다른 기능을 경험하지만 같은 기간의 외부 환경에 노출된다.

### ✅ 6. Randomization의 목적

무작위 배정을 제대로 수행하면 다음 특성이 두 그룹에 평균적으로 균형 있게 분포하도록 기대할 수 있다.

```text
네이버 유입 고객

Google 유입 고객

신규 방문자

재방문자

모바일 사용자

데스크톱 사용자
```

다만 표본이 작으면 우연한 불균형이 발생할 수 있다.

### ✅ 7. A/B 테스트만으로 충분하지 않다

다음 문제가 있으면 결과가 왜곡될 수 있다.

```text
중복 사용자 집계

실험군별 데이터 유실

사용자 ID 변경

잘못된 Exposure 기록

Metric 정의 변경

실험 중 배정 정책 변경
```

따라서 실험 설계뿐 아니라 데이터 수집 시스템 자체도 검증해야 한다.

## 2. Experiment Design — 실험 전에 결정해야 할 것

### ✅ 8. 좋은 실험은 결과를 보기 전에 설계한다

나쁜 방식:

```text
신규 모달 배포

↓

여러 Metric 확인

↓

좋아진 Metric 발견

↓

해당 Metric을 성과로 발표
```

이렇게 하면 어떤 성과를 검증하려던 실험인지 불명확하다.

### ✅ 9. Experiment Hypothesis

가설을 측정 가능한 형태로 작성한다.

예:

**신규 신청 모달에서 불필요한 입력 단계를 줄이면, 기존 모달보다 신청 완료율이 증가할 것이다.**

### ✅ 10. Experiment Definition

최소한 다음 항목이 필요하다.

```text
Experiment ID

Hypothesis

Control

Treatment

Eligibility

Randomization Unit

Primary Metric

Guardrail Metrics

Minimum Detectable Effect

Sample Size

Experiment Duration

Stopping Rule

Decision Criteria
```

### ✅ 11. Control

기존 기능을 제공하는 그룹이다.

```text
CONTROL
기존 신청 모달
```

### ✅ 12. Treatment

새로운 변경을 적용하는 그룹이다.

```text
TREATMENT
신규 신청 모달
```

### ✅ 13. Primary Metric

실험의 성공 여부를 판단하는 주 지표다.

예:

```text
application_completion_rate
```

처음에는 중요한 Primary Metric 하나를 선정하는 편이 단순하다.

### ✅ 14. Secondary Metric

부가적인 분석 지표다.

예:

```text
Form Completion Time

Validation Error Rate

Modal Abandonment Rate
```

Primary Metric 변화를 이해하는 데 활용한다.

### ✅ 15. Guardrail Metric

새 기능이 중요한 업무를 손상시키지 않았는지 확인하는 지표다.

예:

```text
Duplicate Order Rate

Order Creation Failure Rate

Incorrect Application Rate

Client Exception Rate
```

### ✅ 16. 실험 성공의 기본 조건

```text
Primary Metric 개선 근거

AND

Guardrail 위반 없음
```

을 확인해야 한다.

### ✅ 17. Eligibility

어떤 사용자가 실험 대상인지 정의한다.

예:

```text
신청 가능한 상품 상세페이지에
진입한 일반 방문자
```

제외 대상:

```text
관리자 테스트 계정

자동화 Bot

내부 QA 계정

지원되지 않는 Client Version
```

단 실험 처리 이후의 행동으로 대상을 임의 제외하면 편향이 발생할 수 있다.

### ✅ 18. 실험 대상 조건은 사전에 고정한다

실험 시작 후 결과가 불리하다는 이유로 특정 고객군을 분석에서 제외하지 않는다.

대상 조건을 변경해야 한다면 새로운 실험 버전으로 관리한다.

## 3. Randomization — 올바른 실험군 배정

### ✅ 19. Randomization Unit

실험 대상을 어떤 단위로 배정할지 결정한다.

```text
User

Anonymous Visitor

Session

Application Journey

Store / Branch
```

### ✅ 20. 온라인몰에서 적절한 기준

신청 UI 실험이라면 안정적인 방문자 또는 신청 여정 식별자를 사용할 수 있다.

다만 익명 방문자에게 장기간 유지되는 식별자를 발급하는 경우 개인정보 및 추적 동의 정책을 확인해야 한다.

### ✅ 21. IP 주소는 적절한 사용자 식별자가 아니다

```text
회사 Wi-Fi

가족 공유기

이동통신 NAT
```

환경에서는 서로 다른 사람이 동일한 공인 IP를 사용할 수 있다.

### ✅ 22. 전화번호도 실험 ID로 사용하지 않는다

전화번호는 개인정보이며, 신청 이전에 수집하지 않았을 수도 있다.

실험을 위해 불필요한 개인정보 수집을 확대하지 않는다.

### ✅ 23. Sticky Assignment

같은 사용자에게 동일한 Variant를 지속적으로 제공하는 방식이다.

```text
Experiment ID

+

Stable Subject ID

↓

Deterministic Hash

↓

Control / Treatment
```

### ✅ 24. 매 요청마다 무작위 배정하면 안 된다

나쁜 예:

```typescript
const variant =
  Math.random() < 0.5
    ? 'CONTROL'
    : 'TREATMENT';
```

이 코드가 매 요청마다 실행되면 같은 고객이 신청 도중 다른 UI를 볼 수 있다.

### ✅ 25. Assignment 기록

```json
{
  "experimentId": "application_modal_v2",
  "subjectKey": "anonymous_subject_123",
  "variant": "TREATMENT",
  "assignmentVersion": 1
}
```

실제 저장에는 필요한 최소한의 가명 식별자를 사용한다.

### ✅ 26. 중복 Assignment 방지

다음 조합에 대해 유일성을 보장할 수 있다.

```text
experimentId

+

subjectKey
```

동일한 실험에서 사용자가 동시에 두 그룹에 배정되지 않도록 한다.

### ✅ 27. Experiment Crossover

```text
사용자 A

월요일
CONTROL

화요일
TREATMENT
```

처럼 같은 실험 기간에 다른 Variant를 경험하는 현상이다.

Crossover는 실험 결과의 해석을 어렵게 할 수 있다.

### ✅ 28. Rollout 비율과 실험 배정 비율의 차이

기능 Rollout이 5%라면:

```text
95%
기존 기능

5%
신규 기능
```

일 수 있다.

하지만 본격적인 A/B 실험에서는 실험 대상 모집단을 50:50으로 나눌 수도 있다.

기능 공개 비율과 실험 배정 비율은 다른 개념이다.

### ✅ 29. 배정 정책 변경

실험 도중:

```text
1일 차
10:90

2일 차
50:50
```

로 비율을 변경했다면 이를 기록해야 한다.

시간대별 실험군 비율 변화가 통계 분석에 영향을 줄 수 있기 때문이다.

### ✅ 30. Assignment Version

```text
Experiment Version 1

Experiment Version 2
```

를 구분한다.

실험 처리 방식이나 모집단이 실질적으로 바뀌었다면 동일한 Treatment로 취급하지 않을 수 있다.

## 4. A/A Test — 실험 시스템부터 검증하기

### ✅ 31. A/A Test란?

두 그룹에 동일한 기능을 제공하는 실험이다.

```text
Randomization
       ↓
   ┌───────────┐
   │           │
 A Group     A' Group
 기존 모달    기존 모달
   │           │
   └─────┬─────┘
         ↓
     Metric 비교
```

### ✅ 32. 목적

A/A 테스트는 다음을 검증한다.

```text
Random Assignment

Exposure Logging

Event Collection

Identity Mapping

Metric Calculation

Analysis Pipeline
```

### ✅ 33. 두 그룹의 결과가 정확히 같아야 할까?

그렇지 않다.

같은 기능을 제공하더라도 표본의 우연한 변동으로 차이가 발생할 수 있다.

중요한 것은 체계적인 편향이 존재하는지 확인하는 것이다.

### ✅ 34. Assignment 이상 사례

```text
CONTROL
1,000명

A'
700명
```

이라면 배정 정책과 기록 시스템을 조사할 필요가 있다.

### ✅ 35. Exposure 유실 사례

```text
실제 배정
500 : 500

기록된 Exposure
500 : 350
```

이라면 한쪽 그룹에서 이벤트가 누락됐을 가능성이 있다.

### ✅ 36. A/A 통과가 모든 오류를 배제하지는 않는다

실제 Treatment에서만 발생하는 JavaScript 오류나 데이터 유실은 A/A 테스트에서 발견되지 않을 수 있다.

따라서 A/B 테스트 중에도 계속 데이터 품질을 검사한다.

### ✅ 37. 현재 규모에서의 최소 A/A 테스트

```text
동일 UI

↓

Control / A' 배정

↓

중복 Assignment 검사

↓

Exposure 비교

↓

SRM 검사

↓

Metric 비교
```

정도로 시작하면 된다.

## 5. SRM — Sample Ratio Mismatch

### ✅ 38. SRM이란?

설정한 실험군 비율과 실제 관측된 비율이 우연한 변동으로 설명하기 어려울 정도로 다른 현상이다.

예:

```text
Expected
50 : 50

Observed
60 : 40
```

### ✅ 39. 작은 비율 차이가 무조건 오류는 아니다

예:

```text
대상
20명

CONTROL
11명

TREATMENT
9명
```

은 50:50 배정에서도 충분히 나타날 수 있다.

따라서 관측 표본 수를 고려해야 한다.

### ✅ 40. Chi-square Test

SRM 검증에는 카이제곱 적합도 검정을 사용할 수 있다.

계산식:

```text
χ² = Σ((Observed - Expected)² / Expected)
```

여기서:

```text
Observed
실제 배정 수

Expected
설정 비율에 따른 예상 배정 수
```

이다.

### ✅ 41. 예시

```text
Total
10,000

Expected
5,000 / 5,000

Observed
5,300 / 4,700
```

이라면 SRM 검정을 수행한다.

### ✅ 42. SRM 원인 후보

```text
Hash / Bucketing 오류

Subject ID 변경

Treatment JavaScript Crash

Exposure Event 유실

Bot Filtering 차이

실험 중 Allocation 변경

잘못된 SQL JOIN

중복 사용자 집계

일부 Client Version 누락
```

### ✅ 43. 어느 단계에서 불균형이 시작됐는가?

```text
Eligibility

↓

Assignment

↓

Exposure

↓

Ingestion

↓

Analysis
```

각 단계별 인원을 비교한다.

### ✅ 44. Assignment SRM과 Exposure SRM 구분

```text
Assignment
50 : 50

Exposure
50 : 30
```

이라면 배정보다 노출 또는 이벤트 수집 경로의 문제일 수 있다.

### ✅ 45. Treatment Crash 문제

새 모달이 특정 브라우저에서 Crash를 일으키면 Exposure Event 자체가 전송되지 않을 수 있다.

실패한 사용자가 분석에서 빠지면 Treatment의 성과가 실제보다 좋아 보일 수도 있다.

### ✅ 46. SRM 발견 시

```text
Result
UNTRUSTWORTHY

↓

Assignment 조사

↓

Logging 조사

↓

Filtering 조사

↓

원인 수정

↓

필요 시 재실험
```

### ✅ 47. 단순 가중치로 무조건 해결하지 않는다

SRM의 원인을 모르면 표본 수를 임의로 맞추거나 가중치를 적용해도 신뢰성이 회복되지 않을 수 있다.

## 6. Metric Definition — 숫자의 의미부터 고정하기

### ✅ 48. 신청 완료율 정의

예:

```text
신청 완료율
=
신청 완료 사용자 수
/
실험에 배정된 적격 사용자 수
```

또 다른 정의:

```text
신청 완료율
=
신청 완료 건수
/
신청 버튼 클릭 수
```

두 지표는 다르다.

### ✅ 49. 실험 단위와 Metric 단위를 맞춘다

User 단위 실험인데 주문 건수를 독립적인 사용자 수처럼 분석하면 안 된다.

한 사람이 여러 주문을 생성할 수 있기 때문이다.

### ✅ 50. Binary Conversion Metric

```text
사용자 A
신청 완료
1

사용자 B
```

## 7. Statistical Significance — 관측된 차이를 믿을 수 있을까?

### ✅ 61. 예시 데이터

Control:

```text
1,000명

전환 100명

전환율 10%
```

Treatment:

```text
1,000명

전환 120명

전환율 12%
```

### ✅ 62. Absolute Lift

```text
12% - 10%
=
+2%p
```

### ✅ 63. Relative Lift

```text
(12% - 10%) / 10% × 100
=
+20%
```

### ✅ 64. 두 값을 구분한다

보고서에서는 다음처럼 표현한다.

```text
신청 완료율

10% → 12%

절대 +2%p

상대 +20%
```

### ✅ 65. 관측된 차이는 실제 효과와 다를 수 있다

표본이 제한되어 있으면 우연히 큰 차이가 나타날 수 있다.

따라서 신뢰구간과 통계적 검정을 활용한다.

### ✅ 66. Confidence Interval

두 독립 집단의 전환율 차이를 추정한다고 하자.

```text
Delta
=
Treatment Conversion
-
Control Conversion
```

정규근사 표준오차:

```text
SE ≈ sqrt(
  pT × (1 - pT) / nT
  +
  pC × (1 - pC) / nC
)
```

95% 근사 신뢰구간:

```text
Delta ± 1.96 × SE
```

단 표본이 작거나 전환율이 극단적인 경우에는 더 적절한 통계 방법이 필요하다.

### ✅ 67. 각 그룹 1,000명 예시

```text
Control
100 / 1000
10%

Treatment
120 / 1000
12%

Observed Lift
+2%p
```

근사 95% 신뢰구간:

```text
-0.74%p ~ +4.74%p
```

0을 포함한다.

따라서 이 결과만으로 개선 효과가 명확하다고 단정하기 어렵다.

### ✅ 68. 각 그룹 5,000명 예시

```text
Control
500 / 5000
10%

Treatment
600 / 5000
12%
```

근사 95% 신뢰구간:

```text
+0.77%p ~ +3.23%p
```

0을 포함하지 않는다.

앞선 사례보다 개선에 대한 통계적 근거가 강하다.

### ✅ 69. Confidence Interval 해석

95% 신뢰구간은 동일한 추정 절차를 반복했을 때 약 95%의 구간이 실제 모수 차이를 포함하도록 설계된 방법이다.

특정 구간을 계산한 후 실제 효과가 그 안에 있을 확률이 95%라고 직접 해석하는 것은 일반적인 빈도주의 통계에서는 정확하지 않다.

### ✅ 70. p-value

귀무가설이 참이라는 가정하에 현재 관측한 것만큼 또는 더 극단적인 결과가 나타날 확률이다.

### ✅ 71. 흔한 오해

```text
p = 0.03
```

이라고:

```text
새 기능이 좋을 확률
97%
```

라는 뜻은 아니다.

### ✅ 72. Statistical Significance

통계적 유의성은 관측된 차이가 귀무가설과 얼마나 양립하기 어려운지 판단하는 기준이다.

### ✅ 73. Practical Significance

실제로 의미 있는 비즈니스 개선인지 판단하는 개념이다.

예:

```text
10.00% → 10.05%
```

가 매우 큰 표본에서 통계적으로 유의할 수 있더라도, 개발 및 운영 비용을 고려하면 실질적으로 중요하지 않을 수 있다.

### ✅ 74. 실제 판단 기준

```text
Effect Size

Confidence Interval

Business Value

Guardrail

Implementation Cost
```

를 함께 검토한다.

Minimum Detectable Effect는 실험에서 탐지하고자 하는 최소 효과 크기다.

```text

10%
```

```text

```

는:

```text

2%p

20%
```

이다.

### ✅ 78. Statistical Power

실제로 미리 정한 효과가 존재할 때 이를 검출할 확률이다.

예:

```text
Power
80%
```

로 계획할 수 있다.

### ✅ 79. 표본 수 예시

가정:

```text

10%

Treatment Target
12%

Alpha
0.05

Power
80%

Allocation
50:50
```

일반적인 독립 두 비율 검정의 정규근사에서는 대략:

```text

약 3,841명

Treatment
약 3,841명

Total
약 7,682명
```

정도가 필요하다.

정확한 필요 표본은 사용하는 계산법과 분석 설계에 따라 달라진다.

### ✅ 80. 하루 실험 대상이 300명이라면

```text
Required Sample
약 7,682명

Daily Eligible Users
300명
```

이면 필요한 표본을 모으는 데 약 26일이 걸린다.

Conversion Window까지 고려하면 최종 분석 시점은 더 늦어질 수 있다.

### ✅ 81. 방문자 수와 실험 대상 수는 다르다

```text
하루 방문자
1,000명
```

이라도 실제로 신청 모달을 사용하는 사용자가 100명이라면 실험 규모를 그 기준에 맞춰 판단해야 한다.

### ✅ 82. MDE가 작으면 표본 수가 증가한다

```text
10% → 12%
```

를 탐지하는 실험보다:

```text
10% → 10.5%
```

를 탐지하는 실험은 일반적으로 훨씬 더 큰 표본을 필요로 한다.

### ✅ 83. 표본 부족은 그대로 기록한다

실험이 충분히 진행되지 않았다면:

```text
INSUFFICIENT_DATA
```

또는:

```text
INSUFFICIENT_POWER
```

로 결론 내릴 수 있어야 한다.

### ✅ 84. 현재 규모에 맞는 판단

트래픽이 충분하지 않다면 작은 UX 개선을 모두 정식 통계 실험으로 검증하려는 것은 비효율적일 수 있다.

그 대신 사용성 평가, 기능 오류율, 고객 문의 감소, 단계적 공개를 활용할 수 있다.

단 통계적으로 검증되지 않은 개선을 확정적인 인과효과라고 주장하지 않는다.

## 9. Peeking Problem — 결과를 계속 확인하는 문제

### ✅ 85. 실험 결과를 매일 확인하면?

```text
1일 차
p = 0.30

2일 차
p = 0.12

3일 차
p = 0.04
```

3일 차에 바로 실험을 종료하고 성공이라고 발표하고 싶을 수 있다.

### ✅ 86. 왜 문제일까?

고정된 한 번의 검정을 전제로 한 통계 방법을 여러 번 반복하고, 유리한 결과가 나오는 순간 중단하면 거짓 양성 위험이 커질 수 있다.

### ✅ 87. 운영 안전성 확인과 성과 판단을 구분한다

운영 안전성:

```text
주문 금액 오류

개인정보 노출

심각한 API 장애

중복 주문
```

은 언제든 확인하고 즉시 대응해야 한다.

실험 성과:

```text
신청 완료율 개선 여부
```

는 사전에 정한 분석 및 중단 기준에 따라 판단해야 한다.

### ✅ 88. Fixed Horizon

처음에 다음을 정한다.

```text
Minimum Sample

Experiment Duration

Analysis Time

Stopping Rule
```

이후 계획된 시점에 분석한다.

### ✅ 89. Sequential Testing

중간 결과를 반복 확인하면서도 통계적 오류를 관리하는 방법이다.

대표적인 접근:

```text
Alpha Spending

Group Sequential Testing

Always-valid Inference
```

등이다.

### ✅ 90. 초기에는 직접 구현하지 않는다

현재 규모에서는 고정 기간과 표본 수를 사용하는 실험이 단순하고 운영하기 쉽다.

## 11. Metric Attribution — 광고 유입과 실험 효과

### ✅ 99. 그룹별 유입 구성 차이

```text
TREATMENT
네이버 80%

```

```text

Device

Browser

New / Returning

Landing Page

```

등이다.

### ✅ 101. Pre-treatment Variable

실험의 영향을 받기 전에 측정된 변수다.

예:

```text
실험 이전 유입 경로

```

분석과 층화에 활용할 수 있다.

### ✅ 103. Simpson's Paradox

그룹별 결과와 전체 결과가 다르게 나타나는 현상이다.

예:

| 유입 채널 | Control 완료율 | Treatment 완료율 |
|---|---:|---:|
| 네이버 | 20% | 21% |
| 직접 유입 | 5% | 6% |

각 채널에서는 Treatment가 높지만, 두 그룹의 채널 구성 비율에 따라 전체 결과는 다르게 보일 수 있다.

### ✅ 104. 전체 결과와 Segment 결과를 구분한다

```text
Overall Treatment Effect

+

Predefined Segment Analysis
```

를 함께 확인한다.

### ✅ 105. 광고 Attribution과 A/B 효과는 다르다

A/B 테스트는 UI 변경의 인과적 효과를 추정한다.

광고 Attribution은 주문이나 전환을 어떤 유입 경로와 연결할지 정한다.

서로 관련되지만 같은 분석은 아니다.

### ✅ 106. Last Click Attribution

마지막으로 확인된 유입 채널에 전환을 배정하는 방식이다.

이 결과를 해당 광고 채널의 인과적 기여도라고 그대로 해석해서는 안 된다.

### ✅ 107. Experiment와 Tracking 연결

```json
  "acquisitionChannel": "NAVER",
```

같은 분석이 가능하다.

UNKNOWN을 DIRECT로 강제 변환하면 실험군별 유입 구성 분석도 왜곡될 수 있다.

## 12. Experiment Contamination — 다른 실험과의 간섭

### ✅ 109. 동시에 여러 실험을 진행한다면?

```text
Experiment A
신규 신청 모달

Experiment B
상품 상세 디자인

Experiment C
셀프 상담
```

같은 고객의 구매 여정에 여러 실험이 영향을 줄 수 있다.

### ✅ 110. Interaction Effect

신규 모달의 효과가 상품 상세 디자인에 따라 달라질 수 있다.

### ✅ 124. Conversion Window SQL

다음은 개념 설명용이다.

실제 `orders` 테이블에 `experiment_subject_key`, `submitted_at`이 존재한다고 가정한다.

```sql
WITH matured_assignments AS (
  SELECT
    experiment_id,
    subject_key,
    variant,
    assigned_at
  FROM experiment_assignments
  WHERE experiment_id = 'application_modal_v2'
    AND assigned_at <=
      TIMESTAMPTZ '2026-10-16 00:00:00+00'
      - INTERVAL '7 days'
),

subject_outcomes AS (
  SELECT
    a.subject_key,
    a.variant,

    EXISTS (
      SELECT 1
      FROM orders o
      WHERE o.experiment_subject_key = a.subject_key
        AND o.submitted_at >= a.assigned_at
        AND o.submitted_at <
          a.assigned_at + INTERVAL '7 days'
    ) AS converted

  FROM matured_assignments a
)

SELECT
  variant,

  COUNT(*) AS assigned_subjects,

  COUNT(*) FILTER (
    WHERE converted
  ) AS converted_subjects,

  ROUND(
    COUNT(*) FILTER (
      WHERE converted
    )::numeric
    / NULLIF(COUNT(*), 0),
    4
  ) AS conversion_rate

FROM subject_outcomes
GROUP BY variant;
```

```text

Conversion Window

주문 중복 기준

```

## 30. 최종 실무 체크리스트

### Experiment Design

- [ ] 실험 가설이 명확한가?
- [ ] Control과 Treatment가 정의됐는가?
- [ ] Eligibility가 확정됐는가?
- [ ] Randomization Unit이 명확한가?
- [ ] Primary Metric을 사전에 정했는가?
- [ ] Guardrail을 정의했는가?
- [ ] MDE와 Sample Size를 계획했는가?
- [ ] Stopping Rule이 있는가?

- [ ] Sticky Assignment가 보장되는가?
- [ ] 매 요청 Randomization을 하지 않는가?
- [ ] 사용자 중복 배정이 없는가?
- [ ] 실험 중 Allocation 변경을 기록하는가?
- [ ] Crossover를 탐지할 수 있는가?
- [ ] 불필요한 개인정보를 수집하지 않는가?

### Data Quality

- [ ] A/A 테스트를 진행했는가?
- [ ] SRM을 확인하는가?
- [ ] Assignment와 Exposure를 구분하는가?
- [ ] Variant별 이벤트 유실을 검사하는가?
- [ ] Metric Staleness를 확인하는가?
- [ ] UNKNOWN과 DIRECT를 구분하는가?
- [ ] 테스트 계정 및 Bot 처리 기준이 있는가?

### Statistical Analysis

- [ ] Absolute Lift와 Relative Lift를 구분하는가?
- [ ] Confidence Interval을 함께 제시하는가?
- [ ] p-value를 정확하게 설명하는가?
- [ ] Sample Size와 Power를 확인하는가?
- [ ] Peeking 문제를 고려하는가?
- [ ] Multiple Testing 문제를 고려하는가?
- [ ] 표본이 부족할 때 성공을 확정하지 않는가?

- [ ] 광고 유입 경로 구성이 비교 가능한가?
- [ ] 사용자와 주문 건수를 구분하는가?

- [ ] 다른 실험이나 캠페인과의 충돌을 검토했는가?

- [ ] 실험의 데이터 품질이 검증됐는가?

## 📌 요약

1016에서는 다음을 다뤘다.

```text
Production Deployment
        ↓
Feature Flag
        ↓
Limited Rollout
        ↓
Canary Analysis
        ↓
Promotion / Rollback
```

1017에서는 **실험군에 신규 기능을 제공한 뒤 관찰된 개선이 정말 그 기능 때문인지, 결과를 믿을 만큼 검증했는지** 다뤘다.

가장 중요한 세 가지 질문은 다음과 같다.

**첫 번째 — 실험군이 공정하게 배정됐는가?**

```text
Randomization

Sticky Assignment

A/A Test

SRM Check
```

**두 번째 — 올바른 데이터를 측정했는가?**

```text
Assignment

Exposure

Conversion

Conversion Window

Data Freshness
```

**세 번째 — 관측된 차이가 신뢰할 수 있는 개선인가?**

```text
Effect Size

Confidence Interval

Sample Size

Power

Guardrail
```

예를 들어:

```text
Control
10%

Treatment
12%
```

라면 상대 개선은 20%다.

하지만 이것만으로 신규 기능이 성공했다고 확정할 수 없다.

각 그룹에 1,000명씩 있는 경우와 5,000명씩 있는 경우는 같은 2%p 차이를 관찰하더라도 통계적 불확실성이 다르다.

또 실험 데이터에 오류가 있다면 표본이 수십만 명이어도 결과를 신뢰하기 어려울 수 있다.

따라서 실험의 순서는 다음과 같다.

```text
Hypothesis
      ↓
Experiment Design
      ↓
Metric Definition
      ↓
Randomization
      ↓
A/A Validation
      ↓
A/B Experiment
      ↓
Assignment / SRM Check
      ↓
Data Quality Check
      ↓
Statistical Analysis
      ↓
Business Guardrail
      ↓
Decision
      ↓
Release / Hold / Rerun
      ↓
Experiment Report
```

현재 투게더몰에서는 **신규 신청 모달 한 개의 실험을 정확하게 설계하는 것**부터 시작하는 것이 현실적이다.

독립적인 실험 플랫폼을 구축하기보다 기존 NestJS·PostgreSQL·Feature Flag·Audit 구조를 활용하면 된다.

**결국 데이터 기반 의사결정의 핵심은 숫자가 있다는 사실이 아니라, 그 숫자가 올바르게 수집되고 비교 가능한 집단에서 측정됐으며, 불확실성과 업무 위험까지 검토됐는지 확인하는 것이다.**
