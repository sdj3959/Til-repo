## 1011 운영 자동화/AI 워크플로우 심화 (35/N): Disaster Recovery, RPO/RTO, Backup Validation과 Business Continuity

---

### ✅ 1. Backup이 있다고 복구할 수 있는 시스템은 아니다

많은 서비스가 다음 상태를 보고 안심한다.

```text
RDS Automated Backup
Enabled

Backup Retention
7 Days

Last Backup
Successful
```

하지만 실제 장애가 발생하면 다른 문제가 나타난다.

```text
Backup은 있음

↓

복원 방법을 모름

↓

새 DB Endpoint가 달라짐

↓

Application 연결 실패

↓

Secret 변경 누락

↓

Worker가 잘못된 DB에 접근

↓

복원은 성공했지만 서비스는 중단
```

즉:

> Backup의 존재와 서비스 복구 능력은 다르다.

이번 내용은 Backup을 만드는 것보다 **Backup을 이용해 실제 업무를 정상 상태로 되돌리는 능력**에 집중한다.

## 1. Disaster Recovery의 기본 개념

### ✅ 2. Disaster Recovery란?

Disaster Recovery, 줄여서 DR은 중대한 장애나 재해 이후 시스템을 복구하기 위한 계획과 실행 체계다.

예:

```text
Database Corruption

Accidental Data Deletion

Infrastructure Failure

Region Outage

Ransomware

Compromised Production Environment
```

등이다.

일반적인 Error Handling보다 범위가 크다.

단일 API 오류를 복구하는 것을 넘어 서비스와 데이터의 신뢰 가능한 상태를 다시 확보해야 한다.

### ✅ 3. Backup·High Availability·Disaster Recovery 차이

| 개념 | 주요 목적 | 대표적인 방법 |
|---|---|---|
| Backup | 데이터 복구 지점 확보 | RDS Snapshot, PITR |
| High Availability | 장애 중 서비스 중단 최소화 | Multi-AZ, 다중 Instance |
| Disaster Recovery | 대규모 장애 이후 업무 복구 | 복구 환경, Runbook, Restore Drill |

서로 보완 관계지만 같은 기술은 아니다.

### ✅ 4. Multi-AZ가 Backup을 대체하지 않는다

예를 들어 RDS Multi-AZ를 사용한다고 하자.

```text
Primary DB
     ↓
Standby DB
```

Primary 장애 시 Failover에 도움을 준다.

하지만 Application이 실수로 다음 SQL을 실행한다면:

```sql
DELETE FROM orders;
```

정상적인 데이터 변경으로 처리되어 Standby에도 반영될 수 있다.

따라서 Multi-AZ는 일반적인 인프라 장애에 대한 가용성 전략이지, 잘못된 데이터 변경 이전 시점으로 되돌리는 Backup 대체 수단이 아니다.

### ✅ 5. Read Replica도 독립적인 Backup이 아니다

Read Replica는 읽기 부하 분산이나 일부 장애 대응에 활용할 수 있다.

하지만:

```text
Primary 데이터 삭제

↓

Replication

↓

Replica에서도 삭제 반영
```

될 수 있다.

그래서 논리적 데이터 손상에 대비하려면 별도 복구 지점이 필요하다.

## 2. RPO와 RTO

### ✅ 6. RPO — Recovery Point Objective

RPO는 **허용 가능한 최대 데이터 손실 시간**을 의미한다.

예:

```text
RPO = 15분
```

이라면 장애 시점 이전 최대 15분 범위의 데이터 손실을 감수할 수 있다는 업무 목표다.

단, RPO를 15분으로 적었다고 실제로 보장되는 것은 아니다.

Backup 구성과 복구 테스트 결과로 검증해야 한다.

### ✅ 7. RTO — Recovery Time Objective

RTO는 **서비스 중단 후 복구까지 허용 가능한 최대 시간**이다.

예:

```text
RTO = 2시간
```

이면 장애 발생 후 2시간 안에 서비스를 복구해야 한다는 목표다.

여기서 복구 완료가 단순히 서버 기동인지, 실제 주문 접수 정상화인지도 정의해야 한다.

### ✅ 8. 시간 흐름으로 이해하기

```text
14:53
마지막 복구 지점

15:00
장애 발생

15:10
장애 탐지

15:20
복구 시작

16:40
서비스 정상화
```

이 경우:

```text
실제 데이터 복구 간격
7분

실제 서비스 복구 시간
1시간 40분
```

이다.

RPO는 복원한 데이터 시점을 기준으로, RTO는 서비스 중단부터 정상화까지의 시간을 기준으로 평가한다.

### ✅ 9. RTO와 MTTR은 다르다

MTTR은 여러 장애에서 관측한 평균 복구 시간 등으로 사용한다.

RTO는 개별 재해에 대해 조직이 허용하는 목표다.

예를 들어 평소 평균 복구가 20분이라고 하더라도, 지역 장애에서 5시간 걸릴 수 있다.

따라서 MTTR이 짧다는 이유로 RTO가 충족된다고 단정하지 않는다.

### ✅ 10. RPO 0이 가장 좋은 목표일까?

데이터 손실이 전혀 없는 복구가 이상적이기는 하다.

하지만 RPO를 0에 가깝게 만들수록 일반적으로 다음 비용이 증가한다.

```text
Replication

Infrastructure

Network

Recovery Coordination

운영 복잡도
```

실제로 필요한 수준은 업무 피해를 기준으로 결정해야 한다.

### ✅ 11. 현재 프로젝트의 업무별 중요도

예시로 다음처럼 구분할 수 있다.

| 데이터·기능 | 중요도 | 복구 판단 |
|---|---|---|
| 고객 주문/신청 | 최상 | 손실 최소화, 누락 건 복원 필수 |
| 관리자 주문 상태 | 최상 | 변경 이력과 정합성 검증 |
| 고객 개인정보 | 최상 | 무결성·기밀성 함께 고려 |
| 상품·요금제 설정 | 높음 | 이전 정상 설정 복원 |
| 알림톡 Job | 높음 | 중복 발송 없이 재개 |
| 관리자 Export 파일 | 보통 | 재생성 가능한지 확인 |
| AI 분석 결과 | 상대적으로 낮음 | 재실행 또는 Artifact 재사용 |

같은 RPO/RTO를 모든 시스템에 적용할 필요는 없다.

### ✅ 12. 현재 규모에서 검토할 초기 목표

다음은 확정된 운영 기준이 아니라 검토용 예시다.

```text
고객 주문 Database

RPO
15분 이내 목표

RTO
4시간 이내 목표
```

```text
AI Report

RPO
마지막 성공 Artifact 기준

RTO
다음 업무일까지 허용 가능
```

고객 주문의 15분 손실도 실제 영업에서는 매우 클 수 있다.

따라서 회사가 허용 가능한 손실 수준을 정하고, 테스트를 통해 이 목표가 가능한지 확인해야 한다.

## 3. Disaster Scenario 정의

### ✅ 13. 모든 장애에 같은 복구 방법을 사용하지 않는다

Disaster Scenario를 나누어야 한다.

```text
SCENARIO A
EC2 Process 장애

SCENARIO B
EC2 Instance 손실

SCENARIO C
RDS 장애

SCENARIO D
주문 데이터 실수 삭제

SCENARIO E
잘못된 Migration

SCENARIO F
S3 객체 삭제

SCENARIO G
AWS Region 장애

SCENARIO H
Credential Compromise
```

장애 범위마다 최적의 복구 방식이 다르다.

### ✅ 14. EC2 Process 장애

예:

```text
NestJS Process Crash
```

하지만 DB와 저장소는 정상이다.

이 경우:

```text
Process Restart

Health Check

Readiness

Traffic Recovery
```

정도로 해결될 수 있다.

굳이 RDS를 복원할 이유는 없다.

### ✅ 15. EC2 Instance 손실

예:

```text
EC2 Instance 장애

EBS 문제

OS 손상
```

이다.

이 경우:

```text
새 EC2 생성

↓

Application 배포

↓

SSM / IAM 연결

↓

RDS / S3 연결

↓

Health Verification
```

이 필요하다.

중요한 질문은 다음이다.

**기존 EC2 내부에만 있는 파일이나 설정이 있는가?**

### ✅ 16. EC2에 중요한 파일을 직접 저장하면 복구가 어려워진다

예:

```text
/uploads

/export

/config

/local-secret
```

등을 EC2에만 저장했다면 Instance 손실 시 데이터가 함께 사라질 수 있다.

그래서 다음 역할을 구분한다.

```text
Application Code
→ Git / Verified Artifact

Application Config
→ SSM / Secret Store

Business Data
→ RDS

Object Storage
→ S3

Temporary Files
→ 재생성 가능
```

### ✅ 17. RDS 인프라 장애

RDS 자체가 정상 동작하지 않는 상황이다.

우선:

```text
AWS RDS 상태

CloudWatch

RDS Event

Network

Connection

Storage
```

를 확인한다.

원인이 일시적 연결 문제인지, 인스턴스 장애인지, 데이터 손상인지에 따라 대응이 달라진다.

### ✅ 18. 논리적 데이터 손상

예:

```text
잘못된 SQL

잘못된 Migration

대량 Update Bug

관리자 Bulk Action 실수
```

이다.

서버 자체는 정상일 수 있다.

```text
Health Check
200 OK
```

가 나오더라도 데이터는 이미 손상됐을 수 있다.

이 경우 단순 재시작이나 Multi-AZ Failover로 해결되지 않는다.

### ✅ 19. Region 장애

예:

```text
서울 Region 내 핵심 서비스 이용 불가
```

같은 광범위한 상황이다.

이때는 다른 Region의 Backup이나 대기 환경이 필요한지 검토해야 한다.

단일 Region 안에서만 보관한 복구 자원으로는 일부 지역 장애를 감당하지 못할 수 있다.

## 4. AWS RDS Backup 전략

### ✅ 20. RDS Automated Backup

RDS는 자동 백업과 트랜잭션 로그를 이용한 복구 기능을 제공한다.

설정에 따라 백업 보관 기간을 지정할 수 있다.

RDS DB 인스턴스는 일반적으로 0~35일 범위이며, 0은 자동 백업 비활성화를 의미한다. Multi-AZ DB 클러스터에는 다른 최소값이 적용된다.

실제 설정은 AWS Console에서 확인해야 한다.

### ✅ 21. 현재 RDS Backup 설정 확인

읽기 전용 AWS CLI 예시:

```bash
aws rds describe-db-instances \
  --db-instance-identifier YOUR_DB_IDENTIFIER \
  --query 'DBInstances[0].{
    Status:DBInstanceStatus,
    Retention:BackupRetentionPeriod,
    LatestRestorableTime:LatestRestorableTime,
    MultiAZ:MultiAZ
  }' \
  --output json
```

AWS Profile과 Region은 해당 환경에 맞게 지정한다.

확인할 것:

```text
BackupRetentionPeriod

LatestRestorableTime

MultiAZ

DBInstanceStatus
```

여기서 특히 중요한 것이 `LatestRestorableTime`이다.

### ✅ 22. Backup Retention을 0으로 변경하지 않는다

자동 백업을 비활성화하면 복구 능력이 크게 떨어진다.

또 RDS DB 인스턴스에서 백업 보관 기간을 0과 0이 아닌 값 사이로 변경할 때 서비스 중단이 발생할 수 있다.

따라서 비용을 줄이려고 백업 기능을 임의로 비활성화하지 않는다.

### ✅ 23. PITR — Point-in-Time Recovery

PITR은 지정한 시점으로 데이터베이스를 복구하는 기능이다.

예:

```text
14:00
정상

14:10
정상

14:17
잘못된 DELETE 실행

14:20
문제 발견
```

이 경우 실제 복원 가능 범위와 로그를 확인해:

```text
14:16:59
```

같은 사고 직전 시점을 선택할 수 있다.

단 정확한 복구 가능 시점은 `LatestRestorableTime`과 백업 보관 범위 안에 있어야 한다.

### ✅ 24. PITR의 핵심은 새 DB 생성

중요하다.

```text
기존 RDS
production-db

↓

PITR

↓

새 RDS
recovery-db
```

가 생성된다.

기존 Production DB가 자동으로 덮어써지는 것이 아니다.

### ✅ 25. PITR 이후 자동으로 서비스가 복구되지 않는다

새 RDS에는 일반적으로 새로운 Endpoint가 있다.

기존:

```text
DATABASE_URL
→ production-db
```

새 복구 DB:

```text
DATABASE_URL
→ recovery-db
```

이므로 실제 서비스 연결 전환이 필요하다.

### ✅ 26. 복원 DB 설정도 검증해야 한다

확인 항목:

```text
VPC

Subnet Group

Security Group

Parameter Group

Port

Encryption / KMS

Database User

Storage

Backup Retention

Network Access
```

복원 과정에서 원본의 모든 사용자 지정 설정이 자동으로 동일하게 유지된다고 가정해서는 안 된다.

### ✅ 27. RDS Snapshot

Snapshot은 특정 시점의 DB 상태를 복구하는 데 사용한다.

예:

```text
Major Migration 직전

중요 Release 직전

대규모 데이터 변경 직전
```

에 수동 Snapshot을 생성할 수 있다.

### ✅ 28. Automated Backup과 Manual Snapshot의 차이

| 항목 | Automated Backup | Manual Snapshot |
|---|---|---|
| 생성 | 자동 | 수동 또는 별도 자동화 |
| 보관 | 설정한 기간에 따라 관리 | 삭제 전까지 보관 가능 |
| PITR | 지원 조건 충족 시 가능 | Snapshot 시점 중심 |
| 용도 | 일상 복구 | 주요 변경 전 복구 지점 |

Manual Snapshot 역시 백업 저장 비용이 발생한다.

### ✅ 29. Migration 전 Snapshot만 믿으면 안 된다

예를 들어:

```text
09:00
Snapshot

09:20
Migration

09:30
오류 발견
```

이때 09:00 Snapshot으로 전체 복구하면 그동안 들어온 정상 주문도 복구 과정에서 잃을 수 있다.

따라서:

```text
Snapshot
+
PITR
+
Forward-compatible Migration
+
데이터 정합성 검증
```

을 함께 고려해야 한다.

## 5. 실제 데이터 복구 전략

### ✅ 30. 전체 DB 복구와 일부 데이터 복구

복구 방식은 크게 두 가지다.

**전체 데이터베이스 복구**

```text
전체 DB 상태를
과거 시점으로 교체
```

**선별적 데이터 복구**

```text
과거 DB에서
손상된 데이터만 추출

↓

현재 DB에 검증 후 반영
```

이다.

### ✅ 31. 실제 주문 서비스에서는 선별적 복구가 더 안전할 때가 많다

예:

```text
14:00
Snapshot

14:30
주문 100건 신규 생성

14:40
일부 주문 상태 잘못 변경

14:45
문제 발견
```

전체 DB를 14:00으로 되돌리면 14:00 이후 정상 주문도 사라진다.

따라서 다음 방식이 유리할 수 있다.

```text
과거 DB 별도 복원

↓

손상된 주문 식별

↓

현재 DB와 Diff

↓

필요한 Row만 검증 후 복구
```

### ✅ 32. Selective Recovery

예:

```text
Current DB
orders

Recovered DB
orders
```

를 비교한다.

기준:

```text
orderId

status

updatedAt

version

audit history
```

등이다.

### ✅ 33. 하지만 단순 Row Copy는 위험하다

주문 테이블이 다른 테이블과 연결돼 있을 수 있다.

예:

```text
Order

OrderStatusHistory

Consult

NotificationJob

AuditLog
```

상태를 함께 확인해야 한다.

### ✅ 34. 업무 단위로 복구해야 한다

예:

```text
주문 123번

Current
COMPLETED

Expected
WAITING
```

이라고 하자.

상태값만 직접 수정하기보다:

```text
복구 대상 확인

↓

원래 업무 상태 검증

↓

관련 데이터 정합성 확인

↓

복구 트랜잭션

↓

Recovery Audit
```

흐름으로 처리한다.

### ✅ 35. Recovery도 Transaction과 Audit가 필요하다

예:

```text
RECOVERY_APPLIED
```

Event를 남긴다.

```json
{
  "incidentId": "dr_001",
  "resourceType": "ORDER",
  "resourceId": "order_123",
  "action": "RESTORE_STATUS",
  "reason": "INCORRECT_BULK_UPDATE"
}
```

중요 데이터 복구는 직접 수정보다 검증 가능한 Application/DB 복구 절차로 수행한다.

### ✅ 36. Recovery 작업도 Dry Run부터

예:

```text
Dry Run

Affected Orders
128

Restore Candidates
112

Conflict
16
```

처럼 결과를 미리 확인한다.

### ✅ 37. Conflict는 자동 덮어쓰지 않는다

예:

```text
복원 시점
WAITING

현재
COMPLETED
```

인데 실제 고객 개통이 완료된 상태라면 이전 값으로 되돌리면 안 된다.

따라서:

```text
CONFLICT

MANUAL_REVIEW_REQUIRED
```

로 분리한다.

## 6. S3와 파일 복구

### ✅ 38. S3 Versioning

S3 Versioning이 켜져 있으면 파일의 이전 버전을 보관할 수 있다.

예:

```text
banner.webp
v1

banner.webp
v2
```

실수로 새 파일을 덮어썼을 때 이전 버전으로 복구할 수 있다.

### ✅ 39. S3 삭제와 Delete Marker

Versioning이 활성화된 일반 목적 버킷에서는 Version ID를 지정하지 않은 일반 삭제 요청이 기존 객체를 즉시 영구 삭제하는 대신 Delete Marker를 만들 수 있다.

이 경우 이전 버전이 남아 있다면 복구할 수 있다.

하지만 특정 Version이 영구 삭제됐거나 Lifecycle 규칙으로 이전 버전이 제거됐다면 복구할 수 없을 수 있다.

### ✅ 40. Versioning이 Backup의 전부는 아니다

S3 Versioning만으로 모든 재해에 대비할 수 있는 것은 아니다.

예:

```text
권한이 있는 공격자의 버전 삭제

잘못된 Lifecycle Policy

Account Compromise
```

등을 별도로 고려해야 한다.

중요 데이터에는 필요에 따라 별도 Backup 계정·리전 또는 Object Lock을 검토한다.

### ✅ 41. Object Lock

S3 Object Lock은 설정된 보관 기간 동안 객체 버전의 삭제·덮어쓰기를 제한하는 데 도움을 준다.

하지만 잘못된 보관 정책은 스토리지 비용과 데이터 삭제 의무에 영향을 줄 수 있다.

따라서 모든 파일에 무조건 적용하기보다:

```text
Backup

Security Evidence

중요 Archive
```

처럼 명확한 목적의 데이터에 고려한다.

### ✅ 42. S3 복구 우선순위

현재 상품몰 기준으로:

```text
고객 업로드 원본

↓

계약/업무상 보관 필수 파일

↓

상품 이미지

↓

배너

↓

재생성 가능한 Export
```

처럼 중요도에 따라 나눈다.

### ✅ 43. CDN도 함께 확인

S3 객체가 정상 복원됐더라도 CloudFront에서:

```text
이전 Content

404 Cache

잘못된 URL
```

이 남아 있을 수 있다.

따라서:

```text
S3 Restore

↓

Origin Object 확인

↓

CloudFront 응답 확인

↓

Client 확인
```

까지 수행한다.

## 7. Restore Drill — 복구 훈련

### ✅ 44. Restore Drill이란?

실제 서비스에 장애를 만들지 않고 Backup을 복원해 보는 훈련이다.

목적은:

```text
Backup이 존재하는가?
```

뿐 아니라:

```text
정상적으로 복원되는가?

얼마나 걸리는가?

데이터는 정확한가?

Application이 연결되는가?

업무 기능은 작동하는가?
```

를 확인하는 것이다.

### ✅ 45. 반드시 Production과 분리된 환경에서 수행한다

```text
Production RDS
       │
       │ Restore
       ▼
Isolated Recovery RDS
       │
       ▼
Test Application
```

형태가 안전하다.

### ✅ 46. 복구 테스트에서 가장 주의할 것

복원된 DB에 실제 고객 데이터가 포함돼 있을 수 있다.

따라서:

```text
외부 접근 차단

최소 권한

접근 기록

보관 기간 제한

테스트 종료 후 안전한 정리
```

가 필요하다.

복구 테스트라는 이유로 Production 개인정보를 로컬 PC로 내려받거나 임의 공유하지 않는다.

### ✅ 47. 복원 DB에 실제 Worker를 연결하지 않는다

이 부분은 특히 중요하다.

복원된 데이터에는 다음 Job이 남아 있을 수 있다.

```text
NotificationJob
PENDING

WebhookEvent
RETRY_PENDING

ExportJob
PROCESSING
```

테스트 Worker가 이를 실행하면 실제 고객에게 알림이 발송될 위험이 있다.

### ✅ 48. Side Effect를 차단한다

Recovery Test 환경에서는 다음을 기본적으로 차단한다.

```text
실제 알림톡 발송

실제 외부 Webhook

실제 결제/주문 외부 연동

Production S3 Write

Production API Write

Scheduler 실행
```

필요한 경우 Mock Provider를 사용한다.

### ✅ 49. Test Environment Flag만 믿으면 부족할 수 있다

```text
NODE_ENV=test
```

라고 설정했더라도 환경변수가 잘못 전달되면 Production API를 호출할 수 있다.

따라서:

```text
Network Egress 제한

IAM Permission 제한

Provider Credential 분리

Application Policy
```

같은 여러 방어선을 사용하는 것이 좋다.

## 8. RDS Restore Drill의 실제 절차

### ✅ 50. 1단계 — 복구 대상 선정

예:

```text
Source
Production RDS

Recovery Type
PITR

Target
Isolated Recovery DB
```

원본 DB를 수정하지 않는다.

### ✅ 51. 2단계 — 복원 가능 시점 확인

AWS Console 또는 읽기 전용 CLI에서:

```text
Backup Retention

Latest Restorable Time

Available Snapshots
```

를 확인한다.

복원 가능한 시점이 예상보다 오래됐다면 원인을 조사한다.

### ✅ 52. 3단계 — Recovery Point 선택

예:

```text
Restore Point
2026-10-10 14:00 KST
```

같이 정한다.

실제 CLI/API에 전달할 때는 UTC 변환 및 형식을 확인한다.

### ✅ 53. 4단계 — 새 DB 인스턴스 생성

AWS RDS의 PITR 기능을 이용한다.

```text
Source
production-db

Target
recovery-test-db
```

중요한 것은 Target Identifier가 원본과 구분되는 새 값이어야 한다는 점이다.

현재 Production 연결 설정은 변경하지 않는다.

### ✅ 54. 5단계 — Recovery DB의 네트워크 격리

복원된 DB에 다음 접근만 허용한다.

```text
Recovery Test Application

Authorized Recovery Operator
```

일반 고객 서비스가 해당 DB에 연결하지 못하게 한다.

### ✅ 55. 6단계 — 복구 상태 확인

RDS Status가:

```text
available
```

이 됐다고 끝이 아니다.

직접 연결해 다음을 확인한다.

```text
Database Connection

Schema

Required Tables

Extensions

Permissions

Record Counts
```

### ✅ 56. 7단계 — Prisma Schema Compatibility 확인

현재 Application은:

```text
Schema v12
```

를 기대하는데 복원한 DB는:

```text
Schema v10
```

일 수 있다.

따라서 복구 시점에 대응하는 Application Release와 Migration 상태를 확인해야 한다.

### ✅ 57. 복구 중 Migration을 무조건 실행하지 않는다

예:

```bash
prisma migrate deploy
```

를 복원 직후 무조건 실행하는 방식은 위험하다.

복구하려는 시점의 데이터와 현재 코드가 호환되는지 먼저 확인해야 한다.

### ✅ 58. 8단계 — 읽기 전용 검증

초기 검증은 읽기 중심으로 수행한다.

예:

```sql
SELECT COUNT(*)
FROM orders;
```

또는:

```sql
SELECT status, COUNT(*)
FROM orders
GROUP BY status;
```

등이다.

주문 수만 맞는다고 모든 데이터가 올바른 것은 아니므로 관련 테이블과 업무 제약도 확인한다.

### ✅ 59. 9단계 — Application 연결 테스트

Recovery 전용 NestJS를 실행한다.

```text
Recovery API

↓

Recovery DB
```

에만 연결한다.

### ✅ 60. 10단계 — Smoke Test

예:

```text
상품 목록 조회

상품 상세 조회

관리자 주문 목록 조회

주문 상세 조회

상태 변경 이력 조회
```

등을 테스트한다.

실제 Write 테스트가 필요하면 격리된 DB에서 테스트용 데이터만 대상으로 하고 외부 Side Effect를 차단한다.

### ✅ 61. 11단계 — Recovery Duration 기록

예:

```text
Restore Started
10:00

RDS Available
10:42

Application Connected
10:50

Business Smoke Test Passed
11:05
```

이다.

복구 완료까지:

```text
65분
```

이 걸렸다고 기록한다.

단 이것은 사전에 준비된 격리 환경에서의 복원 시간이며, 실제 사고 탐지·의사결정·고객 트래픽 전환에 드는 시간까지 모두 포함한 RTO와 같지는 않을 수 있다.

### ✅ 62. 12단계 — Cleanup

복구 테스트가 끝나면:

```text
Recovery DB

Temporary Test Server

Temporary Credentials

Temporary Snapshot
```

등을 정리한다.

단 Incident Evidence나 별도 보관 요구가 있는 데이터는 임의 삭제하지 않는다.

### ✅ 63. Backup Restore 성공 기준

단순:

```text
RDS Instance Available
```

가 아니다.

다음 조건을 만족해야 한다.

```text
DB 복원 성공

Schema 정상

업무 데이터 정상

Application 연결 정상

외부 Side Effect 차단 확인

복구 시간 기록

테스트 Resource 정리
```

## 9. AWS Backup Restore Testing

### ✅ 64. Restore Drill을 자동화할 수도 있다

AWS Backup에는 Restore Testing 기능이 있다.

주기적으로 복구 테스트를 실행하고 복원 작업의 성공 여부와 소요 시간을 확인할 수 있다.

지원 리소스에는 RDS, S3, EC2 등의 유형이 포함된다.

다만 지원 방식과 설정 조건은 리소스 유형마다 다르다.

### ✅ 65. Restore Testing 기능을 사용한다고 업무 검증까지 자동 완료되지는 않는다

AWS가:

```text
Restore Job
SUCCESS
```

라고 판단하더라도:

```text
NestJS 연결

Prisma 호환성

주문 데이터 정합성

외부 API 차단
```

은 별도로 검증해야 한다.

자동 복원 이후 검증 작업을 추가하는 것이 중요하다.

### ✅ 66. 현재 규모에서 도입 판단

초기에는:

```text
분기 1회 수동 Restore Drill
```

정도로 시작할 수 있다.

복구 요구가 높아지거나 여러 리소스를 관리하게 되면 AWS Backup Restore Testing 같은 자동화를 검토한다.

복원 테스트도 새로운 RDS·스토리지·서비스 사용량을 발생시키므로 비용을 확인해야 한다.

## 10. Business Continuity

### ✅ 67. Disaster Recovery와 Business Continuity는 다르다

Disaster Recovery:

```text
기술 시스템을 어떻게 복구할까?
```

Business Continuity:

```text
시스템이 복구되기 전
업무를 어떻게 지속할까?
```

다.

온라인 판매몰에서는 둘 다 중요하다.

### ✅ 68. 주문 시스템 중단 시

예:

```text
고객 상품 조회
가능

주문 신청
불가능

관리자 상담
가능
```

상태라면 반드시 전체 홈페이지를 닫아야 하는 것은 아니다.

대신 기능별 운영 방식을 나눌 수 있다.

### ✅ 69. Read-only Mode

DB Write가 불가능한 경우:

```text
상품 조회
허용

FAQ 조회
허용

새 주문 접수
제한

관리자 수정
제한
```

형태로 운영할 수 있다.

단 실제로 조회가 안전한 경우에만 적용한다.

### ✅ 70. 고객에게 잘못된 성공 메시지를 제공하지 않는다

주문 접수가 불가능한데:

```text
신청이 완료되었습니다!
```

라고 보여주는 것은 매우 위험하다.

이 경우:

```text
현재 신청 접수가 일시적으로 제한되고 있습니다.
```

처럼 명확하게 안내한다.

### ✅ 71. 임시 접수 시스템을 만들면 해결될까?

장애 중 주문을 별도로 받아서 나중에 처리하는 방식을 생각할 수 있다.

하지만 다음 문제가 생긴다.

```text
개인정보 저장 위치

중복 주문

신청 시점 조건

유실 가능성

사후 이관

고객 동의
```

따라서 준비되지 않은 임시 Google Sheet나 개인 메신저로 고객정보를 수집하는 것은 위험하다.

### ✅ 72. Alternative Intake는 사전에 설계해야 한다

필요하다면:

```text
독립된 접수 경로

접근 통제

암호화

입력 검증

Idempotency

접수 시각

운영 책임자

복구 후 Reconciliation
```

이 있어야 한다.

작은 조직에서는 이런 별도 시스템을 급하게 만드는 것보다 안전하게 접수를 중단하고 고객에게 안내하는 편이 나을 수도 있다.

### ✅ 73. 관리자의 수동 업무도 Continuity Plan에 포함

예:

```text
현재 주문 목록
마지막 확인 시점

고객 문의 처리

장애 공지

복구 후 처리 우선순위
```

를 정리한다.

다만 개인정보가 포함된 임시 Export나 로컬 복사본은 보안과 보관 정책을 준수해야 한다.

## 11. 복구 시 발생하는 Consistency 문제

### ✅ 74. DB를 과거 시점으로 복구하면 외부 시스템과 어긋날 수 있다

예:

```text
14:20
주문 완료

14:21
알림톡 발송 성공

14:30
DB 장애

14:15
시점으로 복구
```

이 경우:

```text
외부 Provider
알림톡 발송 완료

복원된 DB
알림톡 Job 없음
```

일 수 있다.

### ✅ 75. DB만 복구해서는 전체 업무가 복구되지 않는다

다음 시스템의 상태를 함께 확인해야 한다.

```text
RDS

S3

외부 Notification Provider

Webhook

주문 상태

고객 접수 정보

Queue

Audit
```

### ✅ 76. Notification Reconciliation

복구 후:

```text
NotificationJob

Provider Message ID

SentAt

Order Status
```

등을 확인한다.

발송 여부가 불명확한 알림을 무조건 다시 보내지 않는다.

### ✅ 77. Outbox와 Disaster Recovery

1001에서 다룬 Outbox는 DB와 이벤트 전달 간의 불일치를 줄여준다.

하지만 DB 자체를 과거 시점으로 복구한다면, 장애 이후에 생성된 Outbox 기록도 사라질 수 있다.

따라서 Outbox가 있다는 사실만으로 재해 복구 중 이벤트 유실이 완전히 해결되는 것은 아니다.

### ✅ 78. Recovery 이후 Reconciliation 단계

```text
DB Restore
    ↓
External State 조회
    ↓
Order/Notification 대조
    ↓
Missing / Duplicate / Conflict 식별
    ↓
Safe Repair
    ↓
Manual Review
```

로 연결한다.

### ✅ 79. 복구 후 Worker를 바로 켜지 않는다

복원된 Queue/Job 정보가 과거 상태라면 이미 처리된 Job이 다시 실행될 수 있다.

따라서:

```text
Application Readiness

↓

Job State Reconciliation

↓

Worker 재개 승인

↓

Controlled Drain
```

순서가 안전하다.

### ✅ 80. Scheduler도 동일하다

복구 후 오래된 Cron Job이 한꺼번에 실행될 수 있다.

예:

```text
Missed Job 100개
```

를 모두 실행할지, 일부만 실행할지 정책이 필요하다.

0929 Scheduler와 1005 Backpressure에서 다룬 원칙을 적용한다.

## 12. Failover와 Traffic 전환

### ✅ 81. Failover는 Backup Restore와 다르다

Failover:

```text
Primary 장애

↓

준비된 Standby로 전환
```

Backup Restore:

```text
Recovery Point 선택

↓

새 환경 생성

↓

데이터/서비스 복구
```

이다.

둘의 목표와 소요 시간이 다르다.

### ✅ 82. Route53과 Endpoint 전환

다른 서버로 트래픽을 보내야 한다면 DNS 또는 Load Balancer 설정이 중요해진다.

하지만 DNS만 변경해도:

```text
Application Config

Database Endpoint

Secret

Worker

Webhook Callback
```

이 모두 자동으로 바뀌는 것은 아니다.

### ✅ 83. DNS 변경 전 검증

```text
New API Healthy?

New DB Connected?

Correct Release?

SSL/TLS 정상?

Worker 안전?

고객 데이터 정상?
```

등을 확인한다.

### ✅ 84. Split-brain 위험

Old System과 New System이 동시에 Write를 받으면 위험하다.

```text
Old DB
주문 A

New DB
주문 B
```

처럼 서로 다른 Source of Truth가 생길 수 있기 때문이다.

### ✅ 85. Traffic 전환 전 Write 경계를 명확히 한다

예:

```text
Old System
Write Disabled

↓

New System
Write Enabled
```

같은 명확한 전환 절차를 고려한다.

실제 네트워크 단절이나 클라이언트 재시도 등으로 중복 요청이 발생할 수 있으므로 Idempotency도 유지해야 한다.

### ✅ 86. Rollback 역시 단순하지 않다

New DB에서 신규 주문을 받기 시작했다면 Old DB로 다시 돌아가는 것도 데이터 손실 위험이 있다.

따라서 DR 전환 후 Rollback은 일반적인 Application Rollback보다 훨씬 신중해야 한다.

## 13. DR 전략의 비용 수준

### ✅ 87. 대표적인 DR 전략

일반적으로 다음과 같이 분류할 수 있다.

```text
Backup & Restore

Pilot Light

Warm Standby

Multi-region Active-Active
```

이다.

### ✅ 88. Backup & Restore

장애 후 Backup을 이용해 새 환경을 만든다.

장점:

```text
상대적으로 낮은 상시 비용

구조 단순
```

단점:

```text
복구 시간이 길 수 있음

복원 작업 필요

환경 전환 필요
```

이다.

### ✅ 89. Pilot Light

다른 Region에 핵심 데이터와 최소한의 복구 기반을 유지한다.

장애 발생 시 나머지 시스템을 확장한다.

Backup & Restore보다 빠르게 복구하도록 설계할 수 있지만 상시 비용과 운영 복잡도가 늘어난다.

### ✅ 90. Warm Standby

다른 Region에 축소된 서비스 환경을 미리 실행해 둔다.

장애 발생 시 확장해 트래픽을 전환한다.

빠른 복구에 유리하지만 비용이 증가한다.

### ✅ 91. Active-Active

여러 Region에서 실제 서비스를 동시에 운영한다.

매우 높은 가용성을 목표로 할 수 있지만:

```text
Data Consistency

Cross-region Replication

Traffic Routing

Conflict Resolution
```

이 복잡해진다.

### ✅ 92. 현재 규모에 대한 판단

지금과 같은 소규모 운영 구조라면 먼저:

```text
RDS Automated Backup

PITR

수동 Snapshot

S3 Versioning

Clean Redeploy

Restore Drill

Recovery Runbook
```

을 제대로 운영하는 것이 우선이다.

처음부터 Multi-region Active-Active를 도입할 필요는 없다.

단 사업상 리전 전체 장애에서도 매우 짧은 RTO를 요구한다면, 그 목표에 맞는 별도 DR 설계가 필요하다.

## 14. Backup Security

### ✅ 93. Backup도 공격 대상이다

1010의 Credential Compromise와 연결된다.

공격자가 Production AWS 계정에 광범위한 권한을 확보했다면 Backup 삭제도 시도할 수 있다.

따라서 중요한 Backup은 운영 계정의 단일 권한 경계에만 의존하지 않는 전략을 고려한다.

### ✅ 94. Cross-account / Cross-region Backup

예:

```text
Production Account
서울 Region

↓

Backup Account
별도 권한 경계
```

또는:

```text
Primary Region

↓

Secondary Region
```

처럼 분리할 수 있다.

다만 Cross-account와 Cross-region은 각각 목적이 다르다.

전자는 계정 침해와 권한 분리에, 후자는 리전 장애에 대한 복구 가능성에 도움이 된다.

### ✅ 95. AWS Backup Vault

AWS Backup을 통해 백업 정책과 보관을 중앙 관리할 수 있다.

강한 백업 보호가 필요하면 Vault Lock이나 Logically Air-gapped Vault 등을 검토할 수 있다.

다만 이러한 기능은 리소스 지원 여부, 암호화 방식, 보관 규칙 및 비용을 확인해야 한다.

### ✅ 96. KMS Key도 복구에 필요할 수 있다

암호화된 Backup을 복구할 때 필요한 KMS Key에 접근하지 못하면 문제가 발생할 수 있다.

따라서:

```text
Backup Exists
```

뿐 아니라:

```text
Decrypt Permission Available

Required KMS Key Available
```

여부도 확인해야 한다.

### ✅ 97. Recovery Credential은 Production Credential과 구분한다

복구용 Role을 별도로 정의할 수 있다.

예:

```text
READ_BACKUP

RESTORE_TO_ISOLATED_ENV

VERIFY_RECOVERY

APPROVE_CUTOVER
```

등이다.

AI Agent나 일반 Application Role이 Production Backup을 무제한 삭제할 수 있게 해서는 안 된다.

## 15. Disaster Recovery Automation

### ✅ 98. DR 자동화의 목표는 복구 절차를 반복 가능하게 만드는 것이다

예:

```text
Recovery Plan

↓

Backup Availability Check

↓

Restore Request

↓

Infrastructure Validation

↓

Schema Validation

↓

Application Smoke Test

↓

Recovery Report
```

까지는 상당 부분 자동화할 수 있다.

### ✅ 99. 하지만 Production Cutover는 별도 승인

예:

```text
Recovery DB 생성
```

과:

```text
Production DATABASE_URL 변경
```

은 위험도가 다르다.

전자는 격리된 환경에서 자동화가 가능할 수 있지만, 후자는 고객 주문 데이터와 실제 업무에 영향을 준다.

따라서 Cutover는 명확한 승인과 검증을 거치게 한다.

### ✅ 100. DR Workflow 상태

```text
PLANNED

↓

PRECHECKING

↓

RESTORING

↓

VALIDATING

↓

READY_FOR_APPROVAL

↓

CUTTING_OVER

↓

VERIFYING

↓

COMPLETED
```

예외 상태:

```text
FAILED

MANUAL_REQUIRED

ABORTED
```

를 둘 수 있다.

### ✅ 101. RestoreJob Metadata

```ts
interface DisasterRecoveryRun {
  id: string;

  scenario: string;

  sourceResource: string;

  recoveryPoint: Date;

  status: string;

  startedAt: Date;

  restoredAt?: Date;

  validatedAt?: Date;

  completedAt?: Date;

  approvedBy?: string;
}
```

정도다.

### ✅ 102. Recovery Run 자체도 Idempotency 필요

이미 동일한 복구 작업이 진행 중인데 버튼을 두 번 눌렀다고 Recovery DB가 두 개 생성되면 비용과 운영 혼란이 생긴다.

따라서:

```text
Incident ID

Recovery Plan Version

Recovery Point

Target Environment
```

조합을 이용해 중복 복구 실행을 방지할 수 있다.

### ✅ 103. DR 자동화도 Checkpoint를 사용한다

예:

```text
BACKUP_VERIFIED
SUCCESS

RDS_RESTORED
SUCCESS

SCHEMA_VALIDATED
SUCCESS

APPLICATION_VALIDATED
PENDING
```

이면 앞 단계의 결과를 재사용할 수 있다.

### ✅ 104. 실패한 복구를 처음부터 무조건 다시 실행하지 않는다

RDS 복원이 이미 끝났다면:

```text
RDS Restore 재실행
```

이 아니라:

```text
Application Validation부터 재개
```

하는 편이 효율적이다.

### ✅ 105. 복구 결과가 UNKNOWN이면 먼저 확인

AWS Restore API 호출 후 응답을 받지 못했다면 실제로 리소스가 생성됐을 수 있다.

따라서:

```text
AWS Resource 조회

↓

기존 Restore Job 확인

↓

Resume 또는 Reconcile
```

한다.

```text
현재 Prisma Schema와 Order Domain을 분석해서
일부 주문 데이터가 잘못 변경되거나 삭제됐을 때
선별적으로 복구하는 방법을 설계해줘.

복구 대상:

- Order
- OrderStatusHistory
- Consult
- NotificationJob
- AuditLog

실제 Schema를 기준으로 관련 테이블을 식별한다.

목표는 전체 RDS를 과거 시점으로 되돌리지 않고
복구 DB와 현재 DB의 차이를 비교해
손상된 데이터만 안전하게 복원할 수 있게 하는 것이다.

반드시 다음 단계로 설계한다.

1. Recovery DB 연결

2. Current DB와 Recovery DB는
   읽기 전용으로 비교

3. 대상 주문 ID 식별

4. Row Diff 생성

5. 관련 테이블 정합성 검증

6. 복구할 필드/레코드 후보 제시

7. Conflict 구분

8. Dry Run Report

9. Human Approval

10. 제한된 Transaction으로 복구

11. Recovery Audit

12. 사후 Business Validation

절대 자동으로 과거 데이터를 현재 DB에
무조건 덮어쓰지 않는다.

복원 시점 이후 정상 생성된 주문은 보존한다.

외부 Notification Provider 상태와
DB Job 상태가 어긋날 수 있으므로
Reconciliation 단계도 설계한다.

코드 수정 전 분석 보고서부터 작성한다.
```

- [ ] 목표를 실제 Drill로 검증했는가?

### 📌 요약

1010에서는 보안 침해가 발생했을 때:

```text
Detect

↓

Contain

↓

Investigate

↓

Trusted Recovery
```

를 다뤘다.

1011에서는 더 넓은 질문을 다뤘다.

```text
Production 전체 또는
핵심 데이터가 손상된다면

어디까지 복구할 수 있는가?
```

가장 먼저 기억할 것은:

**Backup과 Disaster Recovery는 다르다.**

```text
Backup Exists
```

만으로:

```text
Business Recoverable
```

이 보장되지 않는다.

RPO는:

```text
얼마나 이전의 데이터까지
손실을 허용할 수 있는가?
```

를 의미한다.

RTO는:

```text
서비스 중단 후
얼마 만에 정상화해야 하는가?
```

를 의미한다.

두 목표 모두 실제 복구 훈련으로 검증해야 한다.

또한:

```text
Multi-AZ

Read Replica
```

는 Backup을 완전히 대체할 수 없다.

실수로 삭제하거나 잘못 수정한 데이터가 복제될 수 있기 때문이다.

RDS PITR도 중요하다.

```text
기존 DB
↓
PITR
↓
새 DB 생성
```

방식이므로 복구 후에는:

```text
Endpoint

Network

Secret

Schema

Application

Worker

Scheduler
```

를 다시 검증해야 한다.

실제 주문 서비스에서 가장 주의해야 할 부분은:

```text
과거 시점으로 전체 복구
```

할 때 정상 주문까지 사라질 수 있다는 것이다.

따라서:

```text
전체 DB Restore
```

가 필요한지:

```text
일부 데이터 Selective Recovery
```

가 가능한지 먼저 판단한다.

또 DB가 정상 복원됐다고 끝이 아니다.

```text
Notification Provider

Webhook

Outbox

Queue
```

같은 외부 시스템은 이미 작업을 완료했을 수 있다.

따라서:

```text
Restore

↓

Reconciliation

↓

Worker Controlled Resume
```

가 필요하다.

그리고 가장 중요한 실무 작업은:

**실제로 RDS를 새로운 격리 환경에 복원해 보는 것**이다.

최소한 한 번은:

```text
Backup 확인
↓
Recovery Point 선택
↓
별도 RDS Restore
↓
Prisma Schema 검증
↓
주문 데이터 조회
↓
Application 연결
↓
복구 시간 측정
↓
결과 기록
```

을 수행해야 한다.

현재 프로젝트에서의 현실적인 우선순위는 다음과 같다.

```text
P0
RDS Backup/PITR 설정 점검

P0
EC2와 Secret 재구축 경로 확인

P1
실제 Restore Drill

P1
주문 데이터 정합성 검증

P1
외부 Side Effect 차단

P2
Selective Recovery 도구

P2
정기적인 Drill

P3
Cross-region / Warm Standby 검토
```

처음부터 복잡한 Multi-region DR 시스템을 만들 필요는 없다.

전체 흐름을 연결하면:

```text
Backup Policy
      ↓
Recovery Objective
      ↓
Recovery Point
      ↓
Restore
      ↓
Data Validation
      ↓
Application Validation
      ↓
Reconciliation
      ↓
Cutover
      ↓
Monitoring
      ↓
Restore Drill
      ↓
Improvement
```

이 된다.

결국 Disaster Recovery의 핵심은:

> **“백업을 얼마나 많이 보유하고 있는가”가 아니라, 예상치 못한 장애 이후 신뢰할 수 있는 데이터를 기준으로 실제 고객 업무를 얼마나 안전하고 빠르게 복구할 수 있는지 검증해 두는 것**이다.
