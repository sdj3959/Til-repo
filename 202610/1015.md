# 1015 운영 자동화/AI 워크플로우 심화 (39/N): Change Management, Release Approval, Operational Readiness Review와 안전한 배포 운영

---

## 1. 배포 성공과 변경 성공은 다르다

### ✅ 1. CI/CD가 성공했다고 서비스가 정상인 것은 아니다

예를 들어 다음과 같은 상황이다.

```text
GitHub Actions
SUCCESS

Build
SUCCESS

EC2 Deployment
SUCCESS

NestJS Health Check
200 OK
```

기술적으로는 배포가 완료됐다.

그런데 실제 고객은 다음 문제를 겪고 있다.

```text
상품 상세 조회
정상

신청 모달
정상

신청 버튼 클릭
정상

주문 생성
FAILED
```

이 경우 배포 파이프라인은 성공했지만 변경은 실패했다.

**Deployment Success와 Business Success는 별도의 기준으로 평가해야 한다.**

### ✅ 2. Change Management란?

Change Management는 운영 시스템의 변경을 계획하고, 위험을 평가하고, 필요한 승인을 받은 뒤, 검증 가능한 방식으로 적용하고 기록하는 절차다.

쉽게 표현하면:

```text
무엇을 바꾸는가?

↓

왜 바꾸는가?

↓

어디에 영향을 주는가?

↓

어떤 위험이 있는가?

↓

언제 배포할 것인가?

↓

어떻게 검증할 것인가?

↓

문제가 생기면 어떻게 대응할 것인가?
```

를 체계적으로 관리하는 것이다.

### ✅ 3. 변경 관리는 배포를 느리게 만드는 절차가 아니다

잘못 설계하면 다음과 같다.

```text
버튼 문구 수정

↓

변경 신청서 작성

↓

승인 대기

↓

회의

↓

배포
```

이런 방식은 소규모 개발 환경에서 비효율적이다.

좋은 방식은 위험도가 낮은 변경은 자동 검증으로 빠르게 통과시키고, 실제 장애나 데이터 손실 위험이 높은 변경에 집중하는 것이다.

### ✅ 4. Change와 Deployment는 다르다

**Change**

```text
무엇을 바꾸려는가?
```

**Deployment**

```text
어떤 Artifact를 운영 환경에 설치하는가?
```

이다.

하나의 Change가 여러 번 배포될 수도 있다.

반대로 하나의 Deployment에 여러 Change가 포함될 수도 있다.

### ✅ 5. Deployment와 Release도 다르다

예:

```text
신규 AI 상담 기능

Production 배포
완료

Feature Flag
OFF
```

라면 코드는 운영 서버에 존재하지만 고객에게 기능은 아직 공개되지 않은 상태다.

따라서:

```text
Deployment
코드 설치

Release / Activation
기능 사용 허용
```

을 구분할 수 있다.

### ✅ 6. 변경 관리의 전체 흐름

```text
Change Request
       ↓
Impact Analysis
       ↓
Risk Classification
       ↓
Implementation
       ↓
Pre-release Testing
       ↓
Operational Readiness Review
       ↓
Approval
       ↓
Deployment
       ↓
Technical Verification
       ↓
Business Verification
       ↓
Monitoring
       ↓
Release Closure
```

중간에 실패하면 해당 단계에 맞춰 변경을 보류하거나 복구한다.

### ✅ 7. 배포 완료가 최종 상태는 아니다

다음 상태를 구분한다.

```text
DEPLOYED
운영 환경에 코드 설치

VERIFIED
기술·업무 검증 통과

COMPLETED
관찰 기간과 기록 완료
```

배포가 끝났다고 즉시 `COMPLETED`로 처리하지 않는다.

### ✅ 8. 현재 규모에서 중요한 원칙

1인 개발 환경에서는 다음 네 가지가 특히 중요하다.

```text
작은 변경

재현 가능한 배포

명확한 검증

안전한 복구
```

이 네 가지가 확보되면 복잡한 승인 시스템 없이도 운영 위험을 크게 줄일 수 있다.

## 2. Change 유형 분류

### ✅ 9. 모든 변경을 같은 절차로 처리하지 않는다

변경을 크게 세 유형으로 나눈다.

```text
STANDARD

NORMAL

EMERGENCY
```

### ✅ 10. Standard Change

위험도가 낮고 반복적으로 수행하는 변경이다.

예:

```text
단순 문구 수정

검증된 이미지 교체

작은 UI 스타일 수정

안전성이 확인된 정기 작업
```

실제 업무 영향이 없거나 매우 제한적이라는 것이 확인된 경우다.

### ✅ 11. Standard Change는 사전 승인된 절차를 사용할 수 있다

예:

```text
Standard Change

↓

자동 Type Check

↓

자동 Build

↓

기본 Smoke Test

↓

Deployment
```

처럼 처리한다.

단 Standard라는 이유만으로 모든 변경을 무검증 배포하는 것은 아니다.

### ✅ 12. Normal Change

일반적인 신규 기능이나 기존 기능 수정이다.

예:

```text
신청 모달 기능 변경

관리자 주문 필터 추가

새로운 API Endpoint

Notification 조건 변경

상품 조회 구조 변경
```

이다.

변경 영향도에 따라 필요한 검증을 선택한다.

### ✅ 13. Emergency Change

현재 발생한 장애 또는 보안 문제를 빠르게 해결하기 위해 필요한 변경이다.

예:

```text
주문 생성 장애 수정

Production Secret 유출 대응

가격 계산 오류 수정

알림톡 중복 발송 차단
```

이다.

### ✅ 14. Emergency는 무조건 승인 생략이라는 뜻이 아니다

긴급하다는 이유로:

```text
테스트 생략

영향 분석 생략

기록 생략

무분별한 Production 직접 수정
```

을 해서는 안 된다.

대신 필수 검증만 남기고 절차를 축소한다.

### ✅ 15. Emergency Change의 최소 조건

```text
문제와 영향 확인

↓

수정 범위 최소화

↓

관련 테스트 실행

↓

복구 가능성 확인

↓

긴급 적용

↓

실제 장애 정상화 확인

↓

사후 변경 기록
```

이다.

### ✅ 16. 긴급 변경과 일반 변경을 분리하는 이유

장애 대응 중에 unrelated 기능까지 함께 배포하면 위험하다.

예:

```text
P0
주문 접수 장애

+

P2
관리자 디자인 개선
```

을 한 번에 배포하지 않는다.

긴급 변경은 가능한 한 독립된 작은 범위로 유지한다.

## 3. 변경 위험도 평가

### ✅ 17. Change Type과 Risk Level은 별개다

예:

```text
NORMAL Change
```

여도:

```text
CRITICAL Risk
```

일 수 있다.

반대로 일반적인 기능 개선이라도 영향 범위가 제한적이면 Low Risk일 수 있다.

### ✅ 18. Risk Level

```text
LOW

MEDIUM

HIGH

CRITICAL
```

네 단계로 운영할 수 있다.

### ✅ 19. LOW Risk

예:

```text
독립적인 UI 문구 변경

기존 기능과 연결되지 않은 스타일 수정

검증된 정적 이미지 교체
```

이다.

단 신청 완료 버튼이나 계약 조건 문구처럼 실제 업무·법적 의미에 영향을 주는 콘텐츠는 단순 문구 수정으로 보지 않는다.

### ✅ 20. MEDIUM Risk

예:

```text
관리자 검색 옵션 추가

독립적인 API Response 필드 추가

기존 로직을 유지하는 UI 개선
```

이다.

### ✅ 21. HIGH Risk

예:

```text
주문 생성 Logic 수정

알림톡 발송 조건 변경

API 필수 필드 변경

상품 가격 계산 변경

Prisma Migration 적용
```

이다.

### ✅ 22. CRITICAL Risk

예:

```text
Production 데이터 삭제 가능성

핵심 주문 상태 모델 전면 변경

기존 Consumer 호환성 파괴

인증·권한 체계 변경

대규모 Backfill

복구 방법이 검증되지 않은 DB 변경
```

이다.

### ✅ 23. 위험도는 변경 파일 개수로 결정하지 않는다

예:

```text
변경 파일
1개

내용
주문 금액 계산 방식 변경
```

이라면 High Risk일 수 있다.

반면:

```text
변경 파일
20개

내용
독립된 UI 컴포넌트 스타일 개선
```

이라면 영향 범위 확인 후 낮은 위험도로 분류할 수 있다.

### ✅ 24. Risk Assessment 기준

| 기준 | 질문 |
|---|---|
| Business Impact | 실제 고객 주문에 영향을 주는가? |
| Data Risk | 데이터 손상이나 유실 가능성이 있는가? |
| Blast Radius | 변경이 여러 서비스로 전파되는가? |
| Compatibility | 구버전 Client가 정상 동작하는가? |
| External Side Effect | 외부 발송·연동이 변경되는가? |
| Reversibility | 안전한 Rollback이 가능한가? |
| Observability | 문제 발생 시 감지할 수 있는가? |
| Confidence | 영향 분석과 테스트가 충분한가? |

### ✅ 25. 위험도를 단순 합산 점수로만 결정하지 않는다

예:

```text
데이터 손실 가능성
HIGH
```

인데 다른 항목이 모두 낮다고 평균 점수를 LOW로 만들면 안 된다.

특정 위험은 단독으로 높은 등급을 결정해야 한다.

### ✅ 26. Critical Override

예:

```text
Destructive Migration
TRUE
```

라면 다른 항목에 관계없이 최소 HIGH 또는 CRITICAL로 분류할 수 있다.

### ✅ 27. 미확인 항목도 위험에 반영한다

예:

```text
External Consumer
UNKNOWN

Rollback Plan
NOT_VERIFIED
```

인 경우 자동으로 LOW로 판단하면 안 된다.

1014의 Change Impact와 연결된다.

## 4. Change Record — 무엇을 기록할 것인가?

### ✅ 28. Change Record는 변경의 기준 문서다

단순 Git Commit 메시지 이상의 정보를 담는다.

예:

```text
Change ID

Title

Reason

Scope

Risk

Affected Components

Release SHA

Tests

Approval

Deployment

Verification

Rollback
```

이다.

### ✅ 29. 최소 Change Record

```yaml
changeId: CHG-20261014-001

title: 관리자 주문 상태 필터 개선

type: NORMAL

risk: MEDIUM

repository: togethermall-platform

affected:
  - admin
  - backend

databaseMigration: false

externalSideEffect: false

rollback:
  strategy: previous-artifact
```

실제 Repository 이름과 필드는 확인 후 적용한다.

### ✅ 30. Change ID와 Release ID를 구분한다

예:

```text
CHG-001
주문 필터 개선

REL-010
첫 배포

REL-011
동일 변경의 Hotfix 배포
```

처럼 하나의 변경에 여러 배포가 연결될 수 있다.

### ✅ 31. Commit SHA는 필수적인 식별자다

예:

```text
Release
v2.5.0

Commit
abc123...
```

Version만으로는 어떤 코드를 배포했는지 충분히 식별하지 못할 수 있다.

가능하면 전체 Git Commit SHA와 실제 배포 Artifact를 함께 기록한다.

### ✅ 32. Artifact Digest

Container Image나 Build Artifact를 사용하는 경우 Hash를 기록할 수 있다.

```text
Git Commit
abc123

Artifact Digest
sha256:...
```

이렇게 하면 같은 Source Revision이라도 Build 산출물을 더 정확하게 식별할 수 있다.

### ✅ 33. Git Commit과 실제 배포 코드는 다를 수 있다

예:

```text
GitHub main
Commit A

Production
Commit B
```

상황이 발생할 수 있다.

따라서 실제 배포된 Revision을 확인해야 한다.

### ✅ 34. Release Record 예시

```json
{
  "releaseId": "REL-010",
  "changeId": "CHG-001",
  "environment": "production",
  "commitSha": "FULL_COMMIT_SHA",
  "status": "DEPLOYED",
  "deployedAt": "2026-10-14T01:00:00Z"
}
```

### ✅ 35. Change Record는 반드시 DB에 저장해야 할까?

그럴 필요는 없다.

현재 규모에서는 다음으로도 충분하다.

```text
GitHub Pull Request

GitHub Actions Run

Release Markdown

Change Manifest
```

서로 연결할 수만 있으면 된다.

### ✅ 36. 처음부터 별도 Change Management Admin을 만들 필요 없다

예:

```text
/docs/releases/

2026-10-14-order-filter.md
```

처럼 시작할 수 있다.

## 5. Operational Readiness Review — ORR

### ✅ 37. ORR이란?

Operational Readiness Review는 새로운 기능이나 변경을 운영할 준비가 됐는지 확인하는 절차다.

중요한 질문은 다음과 같다.

```text
코드가 완성됐는가?
```

가 아니라:

```text
문제가 발생해도
우리가 이 기능을 운영하고 복구할 수 있는가?
```

다.

### ✅ 38. ORR은 출시 전에 한 번만 하는 행사가 아니다

중요 기능 추가, 아키텍처 변경, 운영 사고 이후에도 검토할 수 있다.

특히 이전 Incident에서 발견한 문제를 ORR Checklist에 반영하는 것이 중요하다.

### ✅ 39. ORR의 핵심 영역

```text
Architecture

Release Safety

Observability

Security

Data Integrity

Capacity

Recovery

External Dependencies

Operational Ownership
```

등이다.

### ✅ 40. Architecture Readiness

확인:

```text
현재 구조와 호환되는가?

불필요한 새 Infrastructure가 생기는가?

외부 의존성이 증가하는가?

Single Point of Failure가 생기는가?
```

### ✅ 41. Release Readiness

확인:

```text
Test를 통과했는가?

Migration이 필요한가?

구버전과 호환되는가?

Rollback 가능한가?

Feature Flag가 필요한가?
```

### ✅ 42. Monitoring Readiness

확인:

```text
실패하면 어떤 Metric이 달라지는가?

Alert가 있는가?

로그에서 원인을 추적할 수 있는가?

배포 전후를 비교할 수 있는가?
```

### ✅ 43. Security Readiness

확인:

```text
새 IAM Permission이 필요한가?

개인정보가 새 경로로 전달되는가?

새 Secret이 필요한가?

권한이 과도하게 확장되지 않는가?
```

### ✅ 44. Data Readiness

확인:

```text
Schema 변경이 있는가?

Backfill이 필요한가?

과거 데이터를 읽을 수 있는가?

새로운 Business Invariant가 있는가?
```

### ✅ 45. Capacity Readiness

확인:

```text
DB Query 수가 증가하는가?

Worker Concurrency가 증가하는가?

외부 API Rate Limit을 초과할 수 있는가?

Peak Traffic을 고려했는가?
```

### ✅ 46. Recovery Readiness

확인:

```text
문제가 생기면 어떤 기능을 중단할 수 있는가?

Application Rollback이 가능한가?

DB 복구가 필요한가?

고객 주문을 유실하지 않는가?
```

### ✅ 47. ORR Checklist는 100개보다 핵심 20개가 나을 수 있다

현재처럼 혼자 개발과 운영을 담당한다면 모든 변경마다 긴 설문을 작성하는 것은 비효율적이다.

우선 중요한 질문만 선정한다.

### ✅ 48. 최소 ORR Checklist

```text
1. 변경 목적이 명확한가?

2. 영향받는 기능이 확인됐는가?

3. 테스트를 통과했는가?

4. 외부 Side Effect가 있는가?

5. DB Migration이 필요한가?

6. 구버전과 호환되는가?

7. Rollback 가능한가?

8. 새 Secret이 필요한가?

9. 보안 권한이 변경되는가?

10. 고객 개인정보 영향이 있는가?

11. Monitoring이 가능한가?

12. Error Alert가 있는가?

13. Feature Flag가 필요한가?

14. 배포 순서가 안전한가?

15. 배포 후 Smoke Test가 있는가?

16. Business Validation 방법이 있는가?

17. 문제가 생기면 누가 대응하는가?

18. Recovery Runbook이 있는가?

19. 적절한 배포 시간인가?

20. 모든 필수 검증이 끝났는가?
```

### ✅ 49. 모든 항목을 PASS/FAIL로만 표현하지 않는다

다음 상태를 사용할 수 있다.

```text
PASS

FAIL

NOT_APPLICABLE

NOT_VERIFIED
```

### ✅ 50. NOT_APPLICABLE과 NOT_VERIFIED는 다르다

예:

```text
DB Migration
NOT_APPLICABLE
```

은 실제로 해당 사항이 없다는 뜻이다.

반면:

```text
Rollback
NOT_VERIFIED
```

는 복구 가능성을 아직 확인하지 않았다는 뜻이다.

### ✅ 51. Critical 검증이 NOT_VERIFIED라면 승인하지 않는다

예:

```text
Production DB Migration
YES

Recovery Plan
NOT_VERIFIED
```

이면 배포 보류가 타당하다.

### ✅ 52. ORR 결과는 기록한다

```text
ORR Status
PASS

Reviewer
Technical Owner

Verified At
...

Known Risks
...
```

형태다.

팀이 작더라도 누가 무엇을 확인했는지는 남긴다.

## 6. Pre-deployment Validation

### ✅ 53. 배포 전 검증의 목표

새로운 코드가 적어도 다음 조건을 충족하는지 확인하는 것이다.

```text
Build 가능

Type 안전성

테스트 통과

Contract 호환

Migration 검토

Secret 안전성

배포 Artifact 확인
```

### ✅ 54. 첫 번째 — Git Working Tree 확인

로컬에서 배포를 진행하는 구조라면:

```bash
git status --short
```

로 수정 사항을 확인할 수 있다.

다만 CI에서 지정된 Commit과 Artifact를 배포한다면 로컬 Working Tree 상태를 배포의 Source of Truth로 사용하지 않는다.

### ✅ 55. 두 번째 — 정확한 Commit 확인

```bash
git rev-parse HEAD
```

실제 배포 대상 Revision과 일치하는지 확인한다.

### ✅ 56. 세 번째 — Type Check

예:

```bash
pnpm typecheck
```

단 해당 Script가 존재하는 경우에만 실행한다.

프로젝트 구조에 따라:

```text
Frontend

Admin

Backend
```

의 Type Check를 각각 수행할 수 있다.

### ✅ 57. 네 번째 — Lint

```bash
pnpm lint
```

프로젝트에서 실제 사용 중인 Lint 설정에 맞춘다.

### ✅ 58. 다섯 번째 — Test

```bash
pnpm test
```

또는 프로젝트의 실제 Test Script를 사용한다.

### ✅ 59. 테스트가 없는데 PASS로 처리하면 안 된다

예:

```text
Test Script
NOT_FOUND
```

이면:

```text
Tests Passed
```

라고 기록하지 않는다.

다음처럼 남긴다.

```text
Automated Tests
NOT_AVAILABLE

Manual Verification
REQUIRED
```

### ✅ 60. 여섯 번째 — Build

실제 Production Build가 가능한지 검증한다.

예:

```bash
pnpm build
```

Build 대상과 Script는 Repository 설정을 기준으로 결정한다.

### ✅ 61. 일곱 번째 — Dependency 변경

다음 파일이 변경됐다면 추가 확인한다.

```text
package.json

pnpm-lock.yaml

package-lock.json
```

### ✅ 62. Dependency 변경에서 확인할 것

```text
새 Package

Version 변경

Install Script

Security Advisory

Node 호환성

Build 결과
```

등이다.

### ✅ 63. 여덟 번째 — Secret Scan

다음 항목이 Repository에 포함되지 않았는지 확인한다.

```text
.env

AWS Key

DB Password

API Token

Private Key
```

### ✅ 64. 아홉 번째 — Contract Test

1013과 연결된다.

예:

```text
Order API

Notification Event

External Provider Adapter

Naver EP
```

의 계약 호환성을 확인한다.

### ✅ 65. 열 번째 — Change Impact Test

1014와 연결된다.

예:

```text
변경:
orders.status

영향:
Admin
Notification
Report
```

라면 관련 테스트를 선정한다.

## 7. Database Migration Gate

### ✅ 66. DB Migration은 일반 코드 변경보다 신중해야 한다

예:

```text
새 Column 추가
```

와:

```text
기존 Column 삭제
```

는 위험도가 다르다.

### ✅ 67. Migration 유형 분류

```text
ADDITIVE

DATA_BACKFILL

MODIFYING

DESTRUCTIVE
```

로 구분할 수 있다.

### ✅ 68. Additive Migration

예:

```sql
ALTER TABLE orders
ADD COLUMN new_field TEXT;
```

기존 Application과 호환되도록 설계한다면 비교적 안전할 수 있다.

하지만 대규모 테이블에서는 잠금·성능 영향도 고려해야 한다.

### ✅ 69. Destructive Migration

예:

```sql
ALTER TABLE orders
DROP COLUMN old_field;
```

는 기존 데이터를 제거할 수 있다.

특히 구버전 Consumer나 Raw SQL이 존재하면 장애로 이어질 수 있다.

### ✅ 70. Migration 전 확인

```text
Schema Diff

Affected Tables

Affected Rows

Lock Risk

Index Impact

Existing Consumers

Backfill

Rollback / Roll-forward

Backup / Recovery Point
```

이다.

### ✅ 71. Prisma의 Production Migration

Prisma에서 `migrate deploy`는 미적용 Migration을 운영·스테이징 환경에 반영하는 용도로 사용한다.

하지만 이 명령만으로 Production의 모든 수동 Schema 변경이나 Drift를 탐지하지는 않는다.

따라서 별도 Drift 검증과 Migration Review가 필요하다.

### ✅ 72. 자동 Migration 실행은 검토 후

현재 CI/CD 구조에 Migration이 이미 포함되어 있다면 이를 확인한다.

새로운 Migration 자동화를 중복 추가하지 않는다.

### ✅ 73. Prisma migrate reset은 Production에서 금지

운영 DB의 문제를 해결한다는 이유로 개발용 초기화 명령을 실행하지 않는다.

### ✅ 74. Migration Rollback은 일반 Code Rollback과 다르다

예:

```text
기존 Column 삭제

↓

Application Rollback
```

을 하더라도 삭제된 DB 데이터는 자동 복구되지 않는다.

### ✅ 75. Roll-forward도 준비한다

이미 신규 Schema에 데이터가 저장됐다면 이전 상태로 되돌리는 것보다 호환 가능한 수정 코드를 배포하는 편이 안전할 수 있다.

### ✅ 76. Migration 자체의 성공도 Business Validation과 구분한다

```text
Migration Applied
SUCCESS
```

여도:

```text
Order Create
FAILED
```

일 수 있다.

따라서 Migration 이후 실제 핵심 Query와 업무 흐름을 검증한다.

## 8. Release Approval

### ✅ 77. 승인에는 서로 다른 종류가 있다

```text
Technical Approval

Business Approval

Production Execution Authorization
```

을 구분할 수 있다.

### ✅ 78. Technical Approval

다음 사항을 확인한다.

```text
코드가 적절한가?

테스트를 통과했는가?

호환성이 유지되는가?

Migration이 안전한가?

복구 계획이 있는가?
```

### ✅ 79. Business Approval

예:

```text
상품 가격 정책 변경

사전예약 신청 절차 변경

알림톡 문구/발송 조건 변경

고객 안내 정책 변경
```

은 비즈니스 책임자의 확인이 필요할 수 있다.

### ✅ 80. Production Execution Authorization

실제로 운영 서버를 변경할 수 있는 권한이다.

코드 수정 권한과 배포 권한은 반드시 동일해야 하는 것은 아니다.

### ✅ 81. 1인 개발자에게 승인자가 없다면?

현실적으로 다음처럼 구분할 수 있다.

```text
Technical Review
자동 검증 + 자기 점검

Business-sensitive Change
업무 책임자 확인

Production Deployment
권한 있는 운영자가 실행
```

### ✅ 82. 독립적인 승인과 자기 확인은 다르다

혼자 작성한 코드를 혼자 승인했다면:

```text
Self Review
```

이지:

```text
Independent Review
```

라고 기록해서는 안 된다.

### ✅ 83. 자동 테스트가 독립적인 코드 리뷰를 완전히 대체하지는 않는다

하지만 소규모 조직에서는 테스트와 체크리스트를 이용해 실수를 줄일 수 있다.

특히 위험도가 높은 변경은 별도의 책임자 확인이나 추가 검토를 권장한다.

### ✅ 84. GitHub Branch Protection

GitHub는 보호된 Branch에 다음과 같은 조건을 설정할 수 있다.

```text
Pull Request Review

Required Status Checks

Conversation Resolution

Merge Restrictions
```

등이다.

### ✅ 85. GitHub Environment Approval

GitHub Actions의 Environment에는 배포 보호 규칙을 사용할 수 있다.

예:

```text
Environment
production

Required Reviewer
...
```

같은 방식이다.

단 **GitHub Free·Pro·Team의 Required Reviewers는 공개 저장소에서만 지원**되는 등 요금제 및 Repository 공개 여부에 따른 제약이 있다.

따라서 비공개 저장소에서 해당 기능을 사용할 수 있다고 가정하지 않는다.

### ✅ 86. Private Repository에서 사용할 수 없는 경우

대안:

```text
Protected Branch

Required CI

Workflow Dispatch

Restricted Deploy Permission

Release Record
```

등을 조합한다.

필요하면 별도 승인 시스템을 사용할 수도 있지만 작은 규모에서는 과한 구조를 피한다.

### ✅ 87. Approval 대상은 정확한 Release여야 한다

나쁜 방식:

```text
main Branch 배포 승인
```

이다.

승인 후 `main`에 다른 Commit이 추가되면 예상과 다른 코드가 배포될 수 있다.

### ✅ 88. 정확한 Commit을 승인한다

```text
Approved Commit SHA

Build Artifact Digest

Environment

Change ID
```

를 묶어 승인한다.

### ✅ 89. 배포 시 승인된 SHA를 검증한다

Release 요청에 적힌 SHA와 실제 Checkout·Build·배포된 Artifact가 일치해야 한다.

### ✅ 90. 승인 후 변경이 생겼다면 재검증한다

예:

```text
Commit A
승인 완료

↓

Commit B
추가
```

라면 기존 승인이 B까지 자동으로 포함되는 것은 아니다.

## 9. GitHub Actions 배포 구조

### ✅ 91. CI와 Production Deployment를 분리한다

예:

```text
Pull Request
    ↓
CI Test
    ↓
Merge
    ↓
Release Candidate
    ↓
Production Deployment
```

이다.

### ✅ 92. 현재 규모에서 추천하는 최소 구조

```text
CI Workflow

↓

Manual Production Dispatch

↓

Preflight

↓

Deployment

↓

Post-deployment Verification
```

이다.

### ✅ 93. 배포 자동화가 이미 있다면 재사용한다

현재:

```text
GitHub Actions

EC2

SSM

Shell Script
```

등으로 배포하고 있다면 그 구조를 우선 분석한다.

새로운 CD 플랫폼을 만드는 것이 목표가 아니다.

### ✅ 94. Manual Dispatch

GitHub Actions는 `workflow_dispatch`를 이용한 수동 실행을 지원한다.

변경 ID와 Release SHA 등을 입력받을 수 있다.

### ✅ 95. Deployment Concurrency

동시에 두 개의 Production 배포가 실행되면 충돌할 수 있다.

예:

```text
Release A
Migration 진행

Release B
Deployment 시작
```

이다.

### ✅ 96. Concurrency Lock

GitHub Actions의 `concurrency`를 사용할 수 있다.

```yaml
concurrency:
  group: production-deploy
  cancel-in-progress: false
```

이는 동일 그룹의 동시 실행을 제한하는 데 도움이 된다.

다만 GitHub의 Concurrency는 엄격한 선입선출 배포 큐를 보장하지 않으며, 대기 작업 처리 방식도 고려해야 한다.

### ✅ 97. 실행 중인 Deployment를 자동 취소하지 않는 이유

예:

```text
Migration 시작

↓

새 Release 요청

↓

기존 Deployment 취소
```

가 발생하면 상태가 불명확해질 수 있다.

Production에서는 배포 실행 중 자동 취소를 신중하게 다뤄야 한다.

### ✅ 98. GitHub Actions 기본 설계 예시

아래는 **배포 권한과 실행 조건을 보여주기 위한 골격**이다. 실제 배포 명령은 포함하지 않는다.

```yaml
name: Production Release

on:
  workflow_dispatch:
    inputs:
      release_sha:
        description: "Reviewed commit SHA"
        required: true
        type: string

      change_id:
        description: "Approved change ID"
        required: true
        type: string

permissions:
  contents: read

concurrency:
  group: production-deploy
  cancel-in-progress: false

jobs:
  preflight:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout release
        uses: actions/checkout@v4
        with:
          ref: ${{ inputs.release_sha }}
          fetch-depth: 0

      - name: Verify release belongs to main
        env:
          RELEASE_SHA: ${{ inputs.release_sha }}
        run: |
          set -euo pipefail

          git fetch origin main

          test "$(git rev-parse HEAD)" = "$RELEASE_SHA"

          git merge-base --is-ancestor \
            "$RELEASE_SHA" origin/main

      - name: Release information
        env:
          CHANGE_ID: ${{ inputs.change_id }}
          RELEASE_SHA: ${{ inputs.release_sha }}
        run: |
          echo "Change: $CHANGE_ID"
          echo "Commit: $RELEASE_SHA"

  deploy:
    needs: preflight
    runs-on: ubuntu-latest

    environment: production

    steps:
      - name: Deployment placeholder
        run: |
          echo "Real deployment steps are not configured."
          exit 1
```

이 상태로는 실제 배포가 진행되지 않는다.

`preflight`에는 실제 테스트·승인 기록 대조가 추가돼야 하며, `deploy`에는 현재 AWS 인증과 배포 스크립트에 맞는 검증된 절차가 들어가야 한다.

### ✅ 99. Branch에 포함된 Commit이라는 것만으로 충분하지 않다

```text
main에 존재
```

한다는 이유로 해당 SHA가 배포 승인된 것은 아니다.

따라서 필요한 경우:

```text
Change Approval Record

Release SHA

Required CI Result
```

를 별도로 대조한다.

### ✅ 100. AWS 인증은 OIDC를 검토한다

GitHub Actions에서 AWS에 접근한다면 OIDC를 활용해 장기 AWS Access Key 저장을 줄일 수 있다.

하지만:

```text
Repository 제한

Branch 제한

Environment 제한

IAM Role Permission
```

을 적절히 설정해야 한다.

### ✅ 101. Production Deployment Role은 최소 권한

배포 과정에서:

```text
S3 전체 삭제

IAM Administrator

RDS 삭제
```

같은 불필요한 권한을 주지 않는다.

### ✅ 102. Deployment Role과 Migration Role 분리

가능하다면 다음을 구분한다.

```text
Application Deploy

Database Migration

Infrastructure Change
```

위험도가 다르기 때문이다.

다만 현재 아키텍처에서 권한 분리가 과도한 운영 복잡도를 만들지 않도록 실제 필요성을 검토한다.

## 10. 배포 전략

### ✅ 103. In-place Deployment

기존 서버의 Application을 직접 교체하는 방식이다.

장점:

```text
단순

저비용

구현 쉬움
```

이다.

단점:

```text
교체 중 잠깐 중단 가능

복구 방식 제한

잘못된 배포의 영향 범위 큼
```

이다.

### ✅ 104. Rolling Deployment

여러 Instance를 순차적으로 교체한다.

```text
Instance A
New Version

Instance B
Old Version
```

상태가 일시적으로 공존할 수 있다.

따라서 API·DB 호환성이 중요하다.

### ✅ 105. Blue/Green Deployment

예:

```text
Blue
현재 Production

Green
새 Release
```

를 준비한다.

새 환경을 검증한 뒤 트래픽을 전환한다.

### ✅ 106. Canary Deployment

새 Version에 일부 트래픽만 보낸다.

```text
Old
95%

New
5%
```

같은 방식이다.

### ✅ 107. 단일 EC2라면 Canary가 어려울 수 있다

현재 Production 서버가 한 대라면 실제 트래픽 분산형 Canary를 구현하려면 추가 인프라가 필요하다.

무조건 Canary를 도입할 필요는 없다.

### ✅ 108. Feature Flag가 더 적합할 수도 있다

예:

```text
신규 신청 모달

배포
완료

Feature Flag
OFF
```

이후 내부 검증을 진행하고 고객에게 공개할 수 있다.

### ✅ 109. Feature Flag가 모든 배포 문제를 해결하지는 않는다

예:

```text
DB Migration

IAM Permission

Server Startup

Dependency Conflict
```

등은 Flag를 끈다고 해결되지 않을 수 있다.

### ✅ 110. 현재 추천 전략

현재 같은 소규모 EC2 운영 구조에서는:

```text
Verified Artifact

+

짧은 Deployment

+

Health Check

+

Business Smoke Test

+

Rollback / Kill Switch
```

조합이 현실적이다.

## 11. 배포 전 최종 Preflight

### ✅ 111. Release 직전에는 환경 상태를 확인한다

예:

```text
현재 서비스 정상?

이미 장애가 진행 중인가?

DB Connection 정상?

Queue Backlog 심각?

AWS Health Issue 존재?

다른 Deployment 진행 중?
```

### ✅ 112. 기존 장애와 신규 배포를 구분한다

이미:

```text
API p95
4초
```

인 상태에서 신규 배포를 진행하면 배포 이후 지연의 원인을 구분하기 어려울 수 있다.

긴급 수정이 아니라면 기존 문제를 먼저 확인한다.

### ✅ 113. 배포 전 Baseline 기록

예:

```text
Pre-deploy

API p95
180ms

5xx Rate
0.1%

Order Success Rate
99.8%

Queue Oldest Age
20s
```

실제 관측값을 기록한다.

### ✅ 114. Baseline 없이 배포 후 비교하면 어렵다

배포 이후:

```text
API p95
400ms
```

이 됐다고 해도 이전 값이 없으면 변화량을 판단하기 어렵다.

### ✅ 115. 외부 Provider 상태 확인

예:

```text
Kakao Provider

SMS Provider

External API
```

가 이미 장애 상태라면 해당 기능의 검증 결과가 배포 때문인지 구분해야 한다.

### ✅ 116. 배포 시간도 중요하다

예:

```text
사전예약 오픈 직전

광고 캠페인 시작 직전

주문이 몰리는 시간
```

에는 불필요한 High-risk 변경을 피하는 것이 좋다.

### ✅ 117. Change Freeze

특정 업무 이벤트 기간에 불필요한 변경을 제한하는 정책이다.

예:

```text
사전예약 오픈

↓

고위험 변경 제한

↓

긴급 수정만 허용

↓

이벤트 종료 후 정상 배포
```

이다.

다만 Change Freeze가 너무 길면 오히려 많은 변경을 한 번에 배포하게 되는 문제가 생길 수 있다.


### ✅ 121. Monitoring과 연결한다

예:


같은 관계를 확인할 수 있도록 한다.

예:

```text

```

또는:

```text

```

등을 이용할 수 있다.

1006과 연결된다.

```text
Readiness
```

## 14. Post-deployment Business Verification

### ✅ 133. 가장 중요한 단계다

투게더몰 같은 서비스에서는 다음 기능을 확인한다.

```text
상품 목록

상품 상세

신청 모달

주문 접수

관리자 주문 조회

상태 변경

알림 Job

네이버 EP
```

### ✅ 134. 모든 기능을 실제 Production 데이터로 테스트하지 않는다

특히:

```text
실제 고객 주문

실제 알림톡 발송

실제 외부 계약 처리
```

는 부작용이 있을 수 있다.

### ✅ 135. Synthetic Transaction

실제 고객에게 영향을 주지 않는 테스트 요청을 이용해 핵심 경로를 확인할 수 있다.

예:

```text
Staging Test User

Test Product

Mock Provider

Isolated Order
```

등이다.

### ✅ 136. Production Synthetic Test는 별도 보호 필요

Production에서 테스트 주문을 만든다면:

```text
명확한 Test 식별

실제 고객과 분리

외부 발송 방지

정리 정책

통계 제외 정책
```

이 필요하다.

이 구조가 준비되지 않았다면 Production Write 테스트를 무리하게 수행하지 않는다.

### ✅ 137. 실제 주문 성공률도 관찰한다

예:

```text
최근 30분

주문 시도
100건

성공
99건
```

같이 볼 수 있다.

### ✅ 138. 하지만 트래픽이 없을 수도 있다

예:

```text
새벽 03:00

주문 시도
0건
```

이라면 성공률을 계산할 수 없다.

이때:

```text
Success Rate
100%
```

라고 표시하지 않는다.

### ✅ 139. NO_SAMPLE

다음처럼 표시한다.

```text
Order Success Rate
NO_SAMPLE
```

추가적인 검증이 필요할 수 있다.

### ✅ 140. Low Traffic과 Healthy는 구분한다

```text
주문 실패 없음
```

과:

```text
정상 주문 성공 확인
```

은 서로 다른 증거다.

### ✅ 141. 관리자 기능 검증

예:

```text
주문 목록 조회

검색

필터

상세 보기

상태 변경
```

을 확인한다.

### ✅ 142. 상태 변경은 안전한 데이터에서만

실제 고객 주문을 임의로 변경하지 않는다.

Staging 또는 검증용 데이터로 테스트한다.

### ✅ 143. 알림톡 기능 검증

예:

```text
Job 생성

Queue 처리

Provider Adapter

상태 기록
```

을 확인한다.

실제 고객에게 중복 메시지를 보내지 않도록 한다.

### ✅ 144. 네이버 EP 검증

상품 및 가격 관련 배포라면:

```text
EP 생성

Schema Validation

ID 안정성

가격

URL

상품 수
```

를 검사한다.

새 EP를 바로 외부로 공개하기 전에 검증할 수 있다.

## 15. Verification Window

### ✅ 145. 배포 직후 1회 검증으로 끝내지 않는다

일부 문제는 시간이 지나야 발견된다.

예:

```text
Cron 실행 시점

Queue 처리량 증가

Cache 만료

실제 고객 주문 증가

외부 Webhook 도착
```

등이다.

### ✅ 146. 관찰 시간을 변경 유형별로 정한다

예:

```text
LOW
짧은 기술 검증

MEDIUM
기술 + 업무 검증

HIGH
추가 모니터링

CRITICAL
강화된 운영 관찰과 승인
```

이다.

### ✅ 147. 고정된 30분이 모든 배포에 적절한 것은 아니다

예를 들어 하루 한 번 실행되는 Scheduler를 변경했다면 30분간 정상이라고 성공을 확정할 수 없다.

### ✅ 148. Delayed Verification

예:

```text
Deployment
SUCCESS

Immediate Verification
PASS

Scheduled Job Verification
PENDING
```

처럼 후속 검증을 남긴다.

### ✅ 149. 배포 후 검증 결과

```text
PASS

FAIL

NO_SAMPLE

NOT_VERIFIED

PENDING
```

로 구분할 수 있다.

### ✅ 150. Release Closure 조건

```text
필수 기술 검증 완료

필수 업무 검증 완료

Critical Alert 없음

필수 후속 검증 일정 등록

배포 기록 완료
```

를 만족해야 한다.

## 16. Rollback Decision

### ✅ 151. Rollback은 문제가 발생한 뒤 처음 고민하면 늦다

배포 전부터 다음을 알아야 한다.

```text
이전 Artifact 위치

이전 Commit

DB 호환성

Feature Flag

Worker Version

복구 소요 시간
```

### ✅ 152. Rollback Trigger

예:

```text
주문 생성 실패율 급증

핵심 API 5xx 증가

가격 계산 오류

관리자 주문 수정 불가

알림톡 중복 발송
```

등이다.

### ✅ 153. Trigger는 실제 업무 위험에 맞춘다

예:

```text
전체 API p95
500ms 초과
```

하나만으로 Rollback을 결정하기보다 해당 변경과 관계있는 기능인지 확인한다.

### ✅ 154. 단 Critical Business Failure는 즉시 대응

예:

```text
주문 금액이 잘못 계산됨
```

이라면 충분한 표본 수를 기다릴 이유가 없을 수 있다.

### ✅ 155. Rollback과 Kill Switch

예:

```text
AI 상담 기능 오류
```

이고 Feature Flag를 안전하게 끌 수 있다면 전체 Application Rollback보다 빠를 수 있다.

### ✅ 156. Rollback을 수행할 수 없는 변경도 있다

예:

```text
새 DB Enum 저장

기존 Column 삭제

External Notification 전송
```

등이다.

### ✅ 157. 이 경우 Roll-forward 또는 별도 복구

예:

```text
기존 Application
새 데이터 형식 미지원
```

이라면 이전 코드로 되돌리면 더 큰 문제가 생길 수 있다.

### ✅ 158. Rollback 후에도 검증한다

```text
Rollback Execution
SUCCESS

↓

Technical Verification

↓

Business Verification

↓

Monitoring
```

이다.

### ✅ 159. Rollback Success와 Incident Resolved는 다르다

코드를 이전 버전으로 되돌렸더라도:

```text
중복 주문

잘못된 가격

이미 발송된 알림

손상된 DB 데이터
```

가 남아 있을 수 있다.

### ✅ 160. Data Reconciliation이 필요할 수 있다

1012와 연결된다.

```text
Rollback

↓

Affected Data Identification

↓

Consistency Audit

↓

Repair / Manual Review
```

이다.

## 17. Emergency Change 운영

### ✅ 161. Emergency Change는 빠른 판단이 핵심

예:

```text
Production 주문 생성 오류
```

가 발생했다면 다음 순서로 대응한다.

```text
Incident 선언

↓

영향 범위 확인

↓

문제 기능 격리

↓

원인 후보 검증

↓

최소 수정

↓

관련 테스트

↓

긴급 배포

↓

업무 정상화 확인
```

### ✅ 162. Emergency Change ID

예:

```text
EMG-20261014-001
```

처럼 구분할 수 있다.

### ✅ 163. 긴급 변경에는 Incident ID 연결

```text
Incident
INC-001

Emergency Change
EMG-001

Release
REL-011
```

로 연결한다.

### ✅ 164. Emergency Release에는 unrelated 변경을 포함하지 않는다

긴급 문제를 해결하기 위한 최소한의 변경만 반영한다.

### ✅ 165. 긴급 배포 후 사후 Review

```text
왜 긴급 변경이 필요했는가?

사전에 발견할 수 있었는가?

어떤 검증을 생략했는가?

생략된 검증은 언제 완료했는가?

재발 방지책은 무엇인가?
```

를 정리한다.

### ✅ 166. 긴급 변경이 잦다면 시스템 개선 신호다

정기적으로 Emergency Release가 반복된다면:

```text
Test 부족

Release Gate 부족

Monitoring 부족

변경 규모 과다
```

등을 검토한다.

## 18. Release Metrics

### ✅ 167. 변경 관리의 목적은 승인 건수를 늘리는 것이 아니다

핵심은 변경을 더 안전하게 만드는 것이다.

따라서 다음 지표를 관찰한다.

```text
Deployment Frequency

Change Failure Rate

Recovery Time

Rollback Frequency

Release Verification Coverage
```

### ✅ 168. Deployment Frequency

일정 기간 동안 Production에 얼마나 자주 배포하는지 나타낸다.

많을수록 무조건 좋지는 않다.

작고 안전한 변경이 자주 배포되는지 함께 봐야 한다.

### ✅ 169. Change Failure Rate

배포 후 고객이나 업무에 영향을 미치는 실패가 얼마나 발생하는지 측정한다.

단 무엇을 실패로 분류하는지 정의해야 한다.

### ✅ 170. Recovery Time

배포 문제로 서비스 장애가 발생했을 때 얼마나 빠르게 복구했는지 측정한다.

### ✅ 171. Rollback Frequency

Rollback이 얼마나 자주 발생하는지 볼 수 있다.

하지만 Rollback이 많다고 무조건 나쁜 것은 아니다.

안전한 Rollback이 빠르게 이루어진 것은 오히려 좋은 대응일 수 있다.

### ✅ 172. Release Verification Coverage

예:

```text
Required Checks
10개

Verified
8개

Not Verified
2개
```

처럼 필수 검증의 완료 여부를 나타낸다.

### ✅ 173. AI Release Report

기존 Git 자동화와 연결할 수 있다.

```text
Git Diff

↓

Change Impact

↓

CI Result

↓

Release Record

↓

Monitoring Summary

↓

AI Release Report
```

### ✅ 174. 단 AI는 확인되지 않은 결과를 PASS로 작성하지 않는다

예:

```text
Monitoring Data
Unavailable
```

이면:

```text
Post-deployment Monitoring
NOT_VERIFIED
```

로 기록해야 한다.

## 19. 1인 개발 환경에 맞는 최소 도입 전략

### ✅ 175. 처음부터 ITSM 플랫폼을 만들 필요는 없다

예:

```text
ServiceNow

대형 CAB Workflow

복잡한 Approval Portal
```

까지 도입할 필요는 없다.

### ✅ 176. 현재 필요한 것은 다음 네 가지다

```text
GitHub PR / Commit

CI Result

Release Checklist

Post-deployment Report
```

### ✅ 177. P0 — 변경 기록 통일

최소한:

```text
변경 목적

위험도

영향 범위

Commit SHA

Test 결과

Rollback 방법
```

을 남긴다.

### ✅ 178. P0 — Production 변경 전에 확인

```text
현재 Production 정상

배포 대상 Revision 명확

Build 정상

핵심 테스트 정상

Migration 검토

Rollback 준비
```

를 점검한다.

### ✅ 179. P1 — 위험도별 Gate

## 📌 요약

1014에서는:

```text
Change

↓

Data Lineage

↓

Dependency Graph

↓

Blast Radius
```

를 다뤘다.

1015에서는 그다음 질문을 다뤘다.

```text
영향 범위를 확인했다면

어떤 조건에서

누가 승인하고

어떻게 배포하며

무엇을 확인해야

성공으로 판단할 것인가?
```

가장 중요한 원칙은 다음과 같다.

**배포 성공은 변경 성공이 아니다.**

```text
Build
SUCCESS

Deploy
SUCCESS

Health
SUCCESS
```

여도:

```text
Order Create
FAILED
```

일 수 있다.

따라서:

```text
Deployment Verification

+

Business Verification
```

을 구분한다.

또한 모든 변경에 동일한 절차를 적용하지 않는다.

```text
LOW Risk
기본 자동 검증

MEDIUM Risk
관련 기능 검증

HIGH Risk
영향 분석 및 강화된 테스트

CRITICAL Risk
명시적 승인과 복구 준비
```

처럼 운영한다.

여기서 ORR이 중요하다.

ORR은 단순히:

```text
코드가 완성됐는가?
```

를 확인하는 것이 아니다.

```text
이 기능을 실제 운영할 준비가 됐는가?

문제가 생기면 발견할 수 있는가?

문제가 생기면 안전하게 복구할 수 있는가?
```

를 확인한다.

Release Approval에서도:

```text
Technical Approval

Business Approval

Production Authorization
```

을 구분한다.

특히 정확한 Commit SHA를 기준으로 승인하고, 실제 배포된 Artifact가 승인 대상과 일치하는지 확인한다.

배포는 가능한 한:

```text
작게

자주

복구 가능하게
```

수행한다.

그리고 배포 이후에는:

```text
Technical Verification
↓
Business Verification
↓
Monitoring
↓
Release Closure
```

까지 진행한다.

문제가 발생했다면:

```text
Rollback

Kill Switch

Roll-forward

Manual Recovery
```

중 적절한 대응을 선택한다.

단 DB와 외부 Side Effect가 포함된 변경에서는 단순 Application Rollback만으로 정상 상태가 복구되지 않을 수 있다는 점을 반드시 고려해야 한다.

현재 프로젝트에 적용한다면 다음 순서가 현실적이다.

```text
1. Change Record 통일

2. 위험도 분류

3. 기존 CI 검증 정리

4. ORR Checklist

5. 배포 SHA / Artifact 기록

6. Production 배포 전 Preflight

7. 기술 검증

8. 주문·관리자·알림 업무 검증

9. Monitoring

10. Release Report 자동화
```

최종 구조는 다음과 같다.

```text
Change Request
       ↓
Impact Analysis
       ↓
Risk Classification
       ↓
Implementation
       ↓
CI / Contract Tests
       ↓
Operational Readiness Review
       ↓
Release Approval
       ↓
Production Deployment
       ↓
Technical Verification
       ↓
Business Verification
       ↓
Monitoring
       ↓
Release Record
       ↓
Lessons Learned
```

결국 Change Management의 핵심은:

> **“배포를 얼마나 엄격하게 통제하는가”가 아니라, 실제 위험에 맞는 검증과 승인 절차를 적용하고, 변경 결과를 확인하며, 문제가 생겼을 때 신뢰할 수 있는 방법으로 복구할 수 있게 만드는 것**이다.

혼자서 Frontend·Backend·Admin·Database·AWS까지 관리하는 환경일수록, 이런 구조는 불필요한 행정 절차가 아니라 실수를 예방하고 작업을 재현할 수 있게 만드는 운영 장치가 된다.
