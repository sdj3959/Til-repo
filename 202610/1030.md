## 1. 서버가 정상이라고 실제 서비스까지 정상인 것은 아니다

### ✅ 1. 1029와의 연결

1029에서는 승인된 운영 설정과 실제 운영 설정이 일치하는지 확인하는 방법을 다뤘다.

```text
Approved Configuration
        ↓
Desired State
        ↓
Runtime Configuration
        ↓
Drift Detection
        ↓
Compliance Evaluation
        ↓
Audit Evidence
```

1030에서는 한 단계 더 나아간다.

**운영 설정이 정확하더라도 실제 고객이 사용하는 기능이 정상적으로 동작한다고 확신할 수 있을까?**

### ✅ 2. 일반적인 서버 상태 확인

```text
EC2
RUNNING

NestJS Process
RUNNING

Database
CONNECTED

HTTP Response
200 OK
```

이 모든 조건이 충족돼도 서비스가 정상이라고 확정할 수는 없다.

### ✅ 3. 실제 고객에게 발생할 수 있는 문제

```text
상품 목록은 열림

↓

상품 상세페이지 진입

↓

신청 모달 열림

↓

통신사 선택 Dropdown이 모달 아래에 가려짐

↓

고객이 선택할 수 없음

↓

신청 진행 불가능
```

서버는 정상일 수 있지만 고객의 핵심 업무는 실패한 상태다.

### ✅ 4. 또 다른 사례

```text
상품 API
200 OK

↓

가격 데이터 반환

↓

Frontend 가격 계산 오류

↓

잘못된 구매 조건 표시
```

HTTP 응답 상태만으로는 발견하기 어렵다.

### ✅ 5. 관리자 시스템에서도 발생한다

```text
관리자 로그인
정상

↓

주문 검색
정상

↓

주문 상태 변경
실패

↓

업무 처리 불가
```

### ✅ 6. Health Check의 한계

Health Check는 서버나 의존성의 상태를 확인한다.

그러나 실제 고객이 기능을 수행할 수 있는지 전부 검증하지는 않는다.

### ✅ 7. 필요한 변화

```text
기존 관점:

Server is alive.
```

```text
새로운 관점:

Customer can complete the intended journey.
```

### ✅ 8. Continuous Verification이란?

배포 이후에도 중요한 기능과 업무 조건이 실제로 유지되고 있는지 지속적으로 검증하는 접근이다.

### ✅ 9. 핵심 구조

```text
Production Deployment
        ↓
Runtime Verification
        ↓
Synthetic Monitoring
        ↓
Business Assertions
        ↓
Security Assertions
        ↓
External Dependency Verification
        ↓
Result Classification
        ↓
Alert / Evidence
```

### ✅ 10. 중요한 전제

**실제 운영 환경에서 테스트한다는 이유로 고객 주문을 생성하거나 알림톡을 발송해서는 안 된다.**

### ✅ 11. 이번 편의 주요 목표

```text
Health Check vs Business Verification

Synthetic Monitoring

Browser User Journey

Business Transaction Monitoring

Production Read-only Tests

Staging Write Tests

Authentication / Authorization

External Provider Safety

Post-deployment Smoke Tests

Canary Verification

Release Gate

Continuous Evidence

NestJS / Playwright / AWS

Codex 실전 프롬프트
```

## 2. Continuous Verification의 종류

### ✅ 12. 모든 테스트가 같은 것은 아니다

실제 서비스를 검증하는 방법은 여러 단계로 나뉜다.

### ✅ 13. Liveness Check

애플리케이션 프로세스가 살아 있는지 확인한다.

```text
Process Running?
```

### ✅ 14. Readiness Check

애플리케이션이 요청을 처리할 준비가 됐는지 확인한다.

```text
Application Ready?
```

### ✅ 15. Dependency Check

필요한 의존 서비스가 정상인지 확인한다.

```text
Database Connected?

External API Reachable?
```

### ✅ 16. API Contract Check

응답 형식이 클라이언트에서 기대하는 구조와 일치하는지 확인한다.

```text
Expected Schema

vs

Actual Response
```

### ✅ 17. Business Invariant Check

실제 업무 규칙이 유지되는지 확인한다.

예:

```text
할인금액은 허용된 계산 규칙을 따른다.

취소된 주문은 발송 완료 상태로 변경할 수 없다.
```

### ✅ 18. Synthetic Monitoring

시스템이 실제 사용자와 유사한 요청을 발생시켜 서비스의 동작을 검사한다.

### ✅ 19. End-to-End Test

브라우저 또는 API를 통해 여러 구성 요소가 연결된 전체 흐름을 검증한다.

### ✅ 20. Post-deployment Smoke Test

새 버전을 배포한 직후 핵심 기능이 정상인지 빠르게 확인한다.

### ✅ 21. Continuous Business Verification

핵심 업무 조건을 주기적으로 검사한다.

### ✅ 22. Security Verification

인증, 권한, 개인정보 접근 제한 등이 실제로 적용되는지 확인한다.

### ✅ 23. 각각의 역할

| 검사 | 확인하는 것 | 발견할 수 있는 문제 |
|---|---|---|
| Liveness | 프로세스 실행 | 서버 프로세스 중단 |
| Readiness | 요청 처리 준비 | 초기화 미완료 |
| Dependency | 외부 의존성 | DB 연결 실패 |
| Contract | API 응답 구조 | 필드 누락·형식 오류 |
| Business | 업무 결과 | 가격·상태 규칙 오류 |
| Synthetic | 사용자 흐름 | UI 및 연결 문제 |
| Security | 실행 권한 | 인증·권한 우회 |
| Smoke | 배포 후 핵심 기능 | 신규 배포 회귀 |

### ✅ 24. 서로 대체할 수 없다

브라우저 테스트가 통과했다고 DB 백업이 정상이라고 판단할 수 없다.

반대로 DB 연결이 정상이어도 신청 모달은 고장 날 수 있다.

## 3. White-box Monitoring과 Black-box Monitoring

### ✅ 25. White-box Monitoring

애플리케이션 내부 정보를 이용한 모니터링이다.

예:

```text
CPU

Memory

Database Pool

Application Errors

Queue Backlog

Internal Metrics
```

### ✅ 26. Black-box Monitoring

외부 사용자의 관점에서 시스템을 검사한다.

예:

```text
홈페이지 접속

상품 목록 조회

상품 상세 확인

신청 모달 열기
```

### ✅ 27. White-box의 장점

시스템 내부에서 발생하는 문제를 상세하게 파악하기 쉽다.

### ✅ 28. White-box의 한계

내부 Metric이 정상이어도 고객 화면에서 오류가 발생할 수 있다.

### ✅ 29. Black-box의 장점

실제 서비스 이용 과정의 실패를 발견할 수 있다.

### ✅ 30. Black-box의 한계

실패한 원인을 정확하게 찾으려면 내부 로그나 Trace가 필요할 수 있다.

### ✅ 31. 두 방식을 연결한다

```text
Synthetic Check
      ↓
상품 상세 로딩 실패
      ↓
Request ID
      ↓
NestJS Trace
      ↓
Database Query
      ↓
Error Cause
```

### ✅ 32. 권장 운영 구조

```text
Black-box
실제 기능 이상 탐지

+

White-box
내부 원인 조사
```

### ✅ 33. 0921~0923과 연결

이전에 다룬 Correlation ID, SLI/SLO, Incident Runbook이 여기서 활용된다.

## 4. Synthetic Monitoring이란?

### ✅ 34. 기본 개념

실제 고객이 접속하지 않더라도 자동화된 검사 프로그램이 주기적으로 서비스를 이용해 본다.

### ✅ 35. 가장 단순한 Synthetic Check

```text
GET /
      ↓
HTTP Status 확인
```

### ✅ 36. 조금 더 발전한 검사

```text
GET /products
      ↓
Response Schema 확인
      ↓
상품 목록 존재 확인
```

### ✅ 37. Browser Synthetic Monitoring

```text
Browser 실행
      ↓
홈페이지 접속
      ↓
상품 검색
      ↓
상세페이지 진입
      ↓
신청 모달 열기
      ↓
필수 요소 확인
```

### ✅ 38. 실제 고객과 비슷하게 동작한다

브라우저의 JavaScript 실행, 화면 렌더링, 사용자 상호작용을 함께 확인할 수 있다.

### ✅ 39. Synthetic Monitoring은 실제 사용자 모니터링과 다르다

Synthetic Monitoring:

```text
자동으로 생성한 검사 요청
```

Real User Monitoring:

```text
실제 고객의 이용 결과
```

### ✅ 40. Synthetic Monitoring의 장점

```text
트래픽이 적어도 검사 가능

배포 직후 검사 가능

반복 가능한 경로

정해진 조건으로 비교 가능

장애 조기 발견
```

### ✅ 41. Synthetic Monitoring의 한계

검사하지 않은 고객 행동이나 환경까지 모두 정상이라고 보장할 수는 없다.

### ✅ 42. 따라서

```text
Synthetic Monitoring

+

Real User Error Monitoring

+

Application Metrics
```

를 함께 사용하는 것이 좋다.

## 5. 가장 중요한 원칙 — Production Test의 안전성

### ✅ 43. 실제 Production에서 모든 E2E 테스트를 실행하면 안 된다

특히 다음 작업은 고객에게 영향을 줄 수 있다.

```text
실제 주문 생성

고객정보 변경

고객 알림 발송

쿠폰 발급

결제 요청

광고비 수정

관리자 주문 상태 변경
```

### ✅ 44. 환경에 따라 허용 범위를 나눈다

```text
Local / Test
검증된 테스트 데이터로 기능 테스트

Staging
Mock Provider를 이용한 전체 흐름 테스트

Production
기본적으로 읽기 전용 핵심 기능 검사
```

### ✅ 45. Production Read-only Test

주요 업무 데이터에 변경을 일으키지 않는 검사를 의미한다.

예:

```text
공개 상품 목록 조회

공개 상품 상세 조회

신청 모달 열기

입력 Validation 확인

읽기 전용 관리자 조회
```

### ✅ 46. 주의할 점

HTTP GET이라고 해서 무조건 Side Effect가 없는 것은 아니다.

애플리케이션은 방문 로그, Analytics Event, Session 등을 기록할 수 있다.

### ✅ 47. 따라서 Read-only의 의미를 정확히 정의한다

**고객 주문·결제·발송·쿠폰·업무 상태에 의도적인 변경을 발생시키지 않는 검사**를 기본으로 한다.

### ✅ 48. Production Synthetic의 금지 작업

```text
실제 신청 완료

실제 고객 메시지 전송

실제 결제

실제 쿠폰 사용

실제 관리자 Write

Production DB 직접 수정
```

### ✅ 49. 허용할 수 있는 작업

```text
페이지 로딩

검색

필터

상품 선택

모달 표시

입력 검증

공개 API 응답 확인
```

### ✅ 50. 최종 실행 전 검토

해당 버튼을 클릭했을 때 실제 Backend에서 어떤 작업이 실행되는지 확인해야 한다.

### ✅ 51. 예를 들어

```text
신청하기 버튼
```

은 단순히 신청 모달을 여는 버튼일 수도 있다.

반면:

```text
신청 완료
```

는 실제 주문을 저장하는 버튼일 수 있다.

### ✅ 52. 버튼 이름만으로 Side Effect를 판단하지 않는다

실제 Click Handler와 API 호출 경로를 확인한다.

## 6. Test Environment 분리

### ✅ 53. 환경별 권한

| 환경 | 공개 조회 | 테스트 주문 생성 | 외부 발송 |
|---|---|---|---|
| Local | 허용 | 테스트 DB만 | Mock |
| Staging | 허용 | Synthetic Data만 | Mock / Sandbox |
| Production | 허용 | 기본 금지 | 기본 금지 |

### ✅ 54. Staging은 Production과 분리돼야 한다

Staging이라는 이름만 붙어 있고 실제 고객 DB에 Write한다면 안전한 테스트 환경이 아니다.

### ✅ 55. 확인할 항목

```text
Database Endpoint

AWS Account / Role

External API Credential

Notification Provider

Storage Bucket

Webhook Target
```

### ✅ 56. Staging의 데이터

가상 고객과 가상 주문을 사용한다.

### ✅ 57. Synthetic Data 식별

예:

```text
isSynthetic = true

source = "E2E_TEST"

testRunId = "..."
```

### ✅ 58. 주의

`isSynthetic=true`라는 클라이언트 입력만으로 인증이나 권한 검증을 생략하지 않는다.

### ✅ 59. 테스트 데이터의 목적

```text
실제 고객과 구분

조회 범위 제한

테스트 종료 후 정리

Analytics 제외

업무 통계 오염 방지
```

### ✅ 60. Production Test Account

운영 환경에서 인증 기반 Read-only 검사가 꼭 필요하다면 별도의 낮은 권한을 가진 검사 계정을 검토할 수 있다.

### ✅ 61. 권한 제한

```text
정해진 Synthetic Resource 읽기

고객 개인정보 조회 불가

주문 수정 불가

메시지 발송 불가

관리자 권한 없음
```

### ✅ 62. 일반 관리자 계정을 Canary에서 사용하지 않는다

실제 관리자 전체 권한을 가진 Credential을 스케줄러에 보관하면 위험이 커진다.

## 7. 어떤 업무 흐름을 검증해야 할까?

### ✅ 63. 모든 기능을 테스트하려면 비용이 커진다

따라서 실제 사용자와 회사 업무에 중요한 경로부터 선정한다.

### ✅ 64. Customer Journey

고객이 서비스에서 목표를 이루기 위해 거치는 단계다.

### ✅ 65. 휴대폰 온라인몰의 주요 Journey

```text
홈페이지 진입

↓

상품 검색 / 선택

↓

상품 상세 확인

↓

가입 유형 선택

↓

요금제 / 할인 조건 확인

↓

신청 모달 열기

↓

입력 항목 확인

↓

신청 진행
```

### ✅ 66. Production에서 검증할 경계

실제 주문이 생성되기 전까지의 안전한 단계만 실행한다.

### ✅ 67. Staging에서 검증할 경계

독립된 테스트 DB와 Mock 외부 서비스가 준비돼 있다면 가상 신청 완료까지 검증할 수 있다.

### ✅ 68. 관리자 Journey

```text
관리자 로그인

↓

주문 목록

↓

검색 / 필터

↓

주문 상세 조회

↓

상태 변경 검증
```

### ✅ 69. Production에서

실제 주문 상태 변경은 수행하지 않는다.

### ✅ 70. Staging에서

테스트 주문의 상태를 변경하고 결과를 검증할 수 있다.

### ✅ 71. 업무 자동화 Journey

```text
Workflow 생성

↓

Step 실행

↓

승인 대기

↓

승인

↓

외부 Mock 호출

↓

상태 완료
```

### ✅ 72. Production에서

실제 외부 Write를 포함한 전체 경로를 자동 실행하지 않는다.

## 8. 중요도별 Synthetic Test Matrix

### ✅ 73. P0 — 고객의 구매 여정

```text
홈페이지 진입

상품 상세페이지

조건 선택

신청 모달 접근
```

### ✅ 74. P0 — 판매 조건 정합성

```text
상품 코드

모델명

통신사

가입 유형

요금제

금액
```

```typescript
import { z } from 'zod';

const PublicProductSchema = z.object({
```

```typescript
const result = ProductListSchema.safeParse(responseBody);
```

## 16. Business Assertion

### ✅ 151. Assertion이란?

실제 결과가 기대 조건을 만족하는지 확인하는 검사다.

### ✅ 152. 기본 Assertion

```text
상품명이 존재한다.
```

### ✅ 153. 더 중요한 Assertion

```text
Frontend에 표시된 상품 조건이
Backend의 승인된 상품 조건과 일치한다.
```

### ✅ 154. 가격 계산

검증된 계산 로직을 이용한다.

### ✅ 155. 주문 상태

허용된 상태 전이만 수행되는지 확인한다.

### ✅ 156. 사용자 권한

다른 고객의 주문에 접근하지 못하는지 확인한다.

### ✅ 157. 알림 발송

승인된 Payload만 실행될 수 있는지 검증한다.

### ✅ 158. 중요도별 Assertion

```text
P0
금액·개인정보·권한·주문 상태

P1
신청 흐름·상품 선택·검색

P2
리뷰·FAQ·부가 기능
```

### ✅ 159. 중요한 원칙

**실제 업무 규칙을 확인하지 않는 Synthetic Test는 단순한 화면 확인에 머물 수 있다.**

## 18. Synthetic Monitoring의 실행 구조

### ✅ 173. 전체 아키텍처

```text
Scheduler / CI
       ↓
Synthetic Test Runner
       ↓
Browser / API Client
       ↓
Production Read-only Endpoint
       ↓
Result Collector
       ↓
Business Assertion
       ↓
Evidence
       ↓
Metric / Alert
```

### ✅ 174. Runner

검사 스크립트를 실행한다.

### ✅ 175. Browser

실제 화면 렌더링과 사용자 상호작용을 확인한다.

### ✅ 176. API Client

HTTP API 응답과 구조를 확인한다.

### ✅ 177. Assertion Layer

기대 조건을 검증한다.

### ✅ 178. Result Collector

### ✅ 179. Alert

## 20. Playwright 안전한 기본 설정

### ✅ 188. 설정 파일 예시

```typescript
// playwright.synthetic.config.ts

import { defineConfig, devices } from '@playwright/test';

const baseURL = process.env.SYNTHETIC_BASE_URL;

if (!baseURL) {
  throw new Error('SYNTHETIC_BASE_URL_REQUIRED');
}

const targetOrigin = new URL(baseURL).origin;

const allowedOrigin =
  process.env.SYNTHETIC_ALLOWED_ORIGIN;

if (!allowedOrigin) {
  throw new Error('SYNTHETIC_ALLOWED_ORIGIN_REQUIRED');
}

if (targetOrigin !== allowedOrigin) {
  throw new Error('SYNTHETIC_TARGET_NOT_ALLOWED');
}

const isProduction =
  process.env.SYNTHETIC_ENV === 'production';

export default defineConfig({
  testDir: './tests/synthetic',

  timeout: 30_000,

  retries: 1,

  workers: 1,

  use: {
    baseURL,

    trace: isProduction
      ? 'off'
      : 'retain-on-failure',

    screenshot: 'off',

    video: 'off',
  },

  projects: [
    {
      name: 'desktop',
      use: {
        ...devices['Desktop Chrome'],
      },
    },

    {
      name: 'mobile',
      use: {
        ...devices['iPhone 13'],
      },
    },
  ],
});
```

### ✅ 189. 설정 목적

검사 대상 URL을 명시하고 예상하지 못한 주소로 실행하는 문제를 줄이기 위한 것이다.

### ✅ 190. URL Allowlist

정확하게 승인된 Origin만 허용한다.

### ✅ 191. URL Allowlist의 한계

최초 접속 주소가 허용됐더라도 페이지가 외부 주소로 이동하거나 다른 API를 호출할 수 있다.

따라서 실제 테스트 코드, Redirect, 외부 요청도 검토해야 한다.

### ✅ 192. Production에서는 Trace 기본 비활성화

민감한 화면이나 네트워크 정보가 Artifact에 남을 수 있기 때문이다.

### ✅ 193. 실제 디버깅

가능하면 Staging에서 Trace를 수집해 분석한다.

### ✅ 194. 브라우저 설정 검증

사용 중인 Playwright Version에서 해당 Device와 옵션을 지원하는지 확인한다.

### ✅ 195. 테스트 코드도 검토해야 한다

위 설정만으로 Production Write가 자동 차단되는 것은 아니다.

실제 테스트 코드와 서버 측 권한 제한이 함께 필요하다.

## 21. Playwright 공개 화면 Smoke Test

### ✅ 196. 예시 테스트

```typescript
// tests/synthetic/public-smoke.spec.ts

import { test, expect } from '@playwright/test';

test('홈페이지가 렌더링된다', async ({ page }) => {
  const response = await page.goto('/');

  expect(response).not.toBeNull();

  expect(response?.ok()).toBe(true);

  await expect(
    page.locator('body'),
  ).not.toBeEmpty();

  await expect(
    page.getByRole('main'),
  ).toBeVisible();
});
```

### ✅ 197. 이 코드의 전제

실제 홈페이지에 `main` Landmark가 존재해야 한다.

현재 React 구조에 맞게 확인 후 사용한다.

### ✅ 198. 중요한 한계

본문이 존재하고 `main`이 보인다는 사실만으로 상품 구매가 가능하다고 확정할 수는 없다.

### ✅ 199. 따라서 다음 단계

실제 상품 목록과 신청 흐름을 검증하는 Test를 추가한다.

### ✅ 200. Client-side Error

필요하다면 예상하지 못한 JavaScript Exception도 검사한다.

다만 외부 광고·Analytics Script의 오류를 핵심 앱 오류와 구분하는 정책이 필요하다.

### ✅ 201. 테스트의 성공 기준

단순 페이지 접속이 아니라 명확한 사용자 행동의 성공으로 정의한다.

## 24. NestJS Readiness와 Business Verification

### ✅ 219. 기본 Readiness

```text
NestJS Initialized

```

### ✅ 220. Business Readiness

```text
상품 목록을 실제로 조회할 수 있는가?

주요 공개 API가 정상적인 응답을 반환하는가?
```

### ✅ 221. 두 검사 분리

```text
/health/live

/health/ready
```

같은 Endpoint를 설계할 수 있다.

경로는 예시다.

### ✅ 222. 중요한 설계

Business Verification을 모든 Liveness 요청에 포함하지 않는다.

### ✅ 223. 이유

특정 외부 API의 일시적인 장애 때문에 전체 애플리케이션이 살아 있지 않다고 잘못 판단할 수 있기 때문이다.

### ✅ 224. NestJS의 Dependency Injection

검사 로직을 별도 Service로 구성하면 Mock Provider와 테스트용 DB를 이용해 검증하기 쉽다.

### ✅ 225. Conceptual Service

```typescript
import { Injectable } from '@nestjs/common';

interface ReadinessResult {
  status: 'ok' | 'degraded';
  checks: {
    database: boolean;
    publicCatalog: boolean;
  };
}

@Injectable()
export class BusinessReadinessService {
  constructor(
    private readonly checker: ReadinessChecker,
  ) {}

  async check(): Promise<ReadinessResult> {
    const [database, publicCatalog] =
      await Promise.all([
        this.checker.database(),
        this.checker.publicCatalog(),
      ]);

    return {
      status:
        database && publicCatalog
          ? 'ok'
          : 'degraded',

      checks: {
        database,
        publicCatalog,
      },
    };
  }
}
```

`ReadinessChecker`는 프로젝트에 맞게 구현해야 하는 추상화다.

### ✅ 226. 실제 구현에서는 Timeout이 필요하다

DB나 외부 API가 무한히 응답을 기다리게 해서는 안 된다.

### ✅ 227. Endpoint 응답

공개 Health Endpoint에 내부 DB 주소나 Secret 같은 정보를 포함하지 않는다.

### ✅ 228. 보호된 검사

상세한 내부 검사 결과는 인증된 운영자나 내부 Collector에게만 제공할 수 있다.

## 25. Synthetic Check 결과 모델

### ✅ 229. 성공과 실패만으로 부족하다

테스트 결과를 다음처럼 분류할 수 있다.

```text
PASS

FAIL

NOT_VERIFIED

SKIPPED
```

### ✅ 230. PASS

실제 실행한 Assertion이 통과했다.

### ✅ 231. FAIL

검사 대상 기능이 기대 조건을 만족하지 못했다.

### ✅ 232. NOT_VERIFIED

검사 자체를 완료하지 못했거나 결과가 불분명하다.

### ✅ 233. SKIPPED

검사 정책에 따라 실행 대상에서 제외됐다.

### ✅ 234. NOT_VERIFIED 예시

```text
Canary Credential Expired

Collector Timeout

Test Runner Failure

Required Test Data Missing
```

### ✅ 235. SKIPPED 예시

```text
모바일 전용 Test를
데스크톱 실행에서 제외
```

### ✅ 236. FAIL과 NOT_VERIFIED를 구분한다

고객 서비스가 고장 난 것과 모니터링 시스템이 고장 난 것은 다른 문제다.

### ✅ 237. 하지만 둘 다 중요하다

모니터링 시스템이 고장 나면 실제 서비스 장애를 발견하지 못할 수 있기 때문이다.

## 28. SLI/SLO와 연결

### ✅ 261. 0922의 개념 재활용

SLI는 실제 서비스 품질을 측정하는 지표다.

SLO는 그 지표에 대한 목표다.

### ✅ 262. Synthetic SLI 예시

```text
5분마다 상품 상세 조회

↓

성공 비율 계산
```

### ✅ 263. 실제 사용자 SLI

```text
실제 고객의 상품 상세 요청 중
정상 처리 비율
```

### ✅ 264. 두 수치는 다를 수 있다

Synthetic Test가 정상이어도 특정 브라우저나 지역에서 실제 고객 장애가 발생할 수 있다.

### ✅ 265. 따라서 Synthetic 결과만으로 전체 고객 SLO를 대체하지 않는다

Synthetic은 실제 사용자 측정값을 보완하는 지표다.

### ✅ 266. 예시 목표

```text
핵심 공개 API

Synthetic Success Rate
99.5%
```

는 정책 설계 예시다.

### ✅ 267. 실제 목표 결정

현재 장애 기록, 업무 중요도, 검사 빈도와 실제 사용자 영향을 기준으로 정해야 한다.

### ✅ 268. 중요한 문제

1분마다 실행하는 Test가 자주 실패한다면 알림이 과도하게 발생할 수 있다.

### ✅ 269. Alert Rule

연속 실패, 시간 구간, 영향 범위를 고려한다.

### ✅ 270. 하지만 P0 보안 실패는 예외다

타인 주문 접근이 실제로 허용되는 등 중요한 보안 문제가 확인됐다면 단순 연속 실패 기준보다 즉각적인 사고 대응이 필요할 수 있다.

### ✅ 307. 비교

| 항목 | 직접 Playwright | CloudWatch Synthetics |
|---|---|---|
| 실행 환경 | 자체 관리 | AWS 관리형 |
| 브라우저 검증 | 가능 | 가능 |

## 33. Alert 설계

### ✅ 312. 모든 실패를 긴급 알림으로 보내지 않는다

일시적인 Network Timeout이나 Test Fixture 문제도 발생할 수 있기 때문이다.

### ✅ 313. 실패 유형

```text
APPLICATION_FAILURE

BUSINESS_ASSERTION_FAILURE

AUTHORIZATION_FAILURE

PROBE_FAILURE

DEPENDENCY_FAILURE
```

### ✅ 314. APPLICATION_FAILURE

실제 UI나 API가 기대대로 동작하지 않는 경우다.

### ✅ 315. BUSINESS_ASSERTION_FAILURE

업무 값이나 상태가 기대 조건과 다르다.

### ✅ 316. AUTHORIZATION_FAILURE

권한 정책이 의도와 다르게 동작한다.

### ✅ 317. PROBE_FAILURE

검사 도구 자체가 실패했다.

### ✅ 318. DEPENDENCY_FAILURE

외부 서비스나 의존성에 문제가 있다.

### ✅ 319. P0 Alert

```text
신청 경로 완전 장애

잘못된 가격 조건 확인

민감정보 접근 허용

고객 영향도가 큰 핵심 기능 실패
```

### ✅ 320. P1 Alert

```text
상품 조회 오류 증가

모바일 모달 기능 실패

관리자 조회 장애
```

### ✅ 321. P2 Alert

```text
일시적인 추가 지연

부가 기능 실패

검사 도구 설정 문제
```

### ✅ 322. Alert Grouping

동일 장애가 여러 검사에서 동시에 발생하면 관련 Alert를 묶는다.

### ✅ 323. 예시

```text
Product API Failure

↓

Product List Test FAIL

↓

Product Detail Test FAIL

↓

Search Test FAIL
```

세 개의 독립 사고로 단정하지 않는다.

### ✅ 324. Root Cause 조사

실제 공통 원인을 확인한다.

라고 기록하면 어떤 조건을 검사했는지 알기 어렵다.

### ✅ 328. 중요한 조건

실제로 실행하지 않은 Assertion은 `true`로 기록하지 않는다.

### ✅ 331. 하지만 LLM이 Evidence를 생성해서는 안 된다

실제 테스트 실행 결과가 Source of Truth다.

### ✅ 332. Redaction

스크린샷·Trace·로그에 개인정보가 포함되지 않도록 한다.

### ✅ 333. Retention

Evidence 보관기간은 업무 필요성과 개인정보 보호 기준에 맞춰 정한다.

### ✅ 334. Audit Integrity

중요한 Evidence는 수정·삭제 권한을 제한한다.

## 📌 요약

1029에서는 승인된 설정과 실제 운영 설정의 차이를 검증했다.

```text
Approved Configuration
          ↓
Runtime Configuration
          ↓
Drift Detection
          ↓
Compliance Verification
```

1030에서는 실제 고객과 관리자가 사용하는 업무 기능까지 검증하는 방법을 다뤘다.

```text
Production Deployment
          ↓
Runtime Verification
          ↓
API Contract Check
          ↓
Synthetic User Journey
          ↓
Business Assertion
          ↓
Authorization Verification
          ↓
External Dependency Check
          ↓
Result Classification
          ↓
Evidence / Alert
```

이번 편에서 중요한 것은 여섯 가지다.

**첫 번째 — HTTP 200은 업무 성공을 의미하지 않는다.**

상품 API가 정상이어도 잘못된 금액이 표시되거나 신청 모달이 작동하지 않을 수 있다.

**두 번째 — 실제 사용자 행동을 검증한다.**

```text
상품 선택

↓

상세 확인

↓

조건 선택

↓

신청 모달 진입
```

과 같은 주요 Journey를 브라우저에서 확인한다.

**세 번째 — Production 검사는 안전해야 한다.**

```text
Production:
Read-only

Staging:
Synthetic Write Test

External Provider:
Mock / Sandbox
```

를 기본으로 구분한다.

**네 번째 — 검증하지 못한 상태를 성공으로 처리하지 않는다.**

```text
PASS

FAIL

NOT_VERIFIED

SKIPPED
```

를 구분한다.

**다섯 번째 — 배포 성공과 실제 기능 검증 성공을 구분한다.**

```text
Deployment:
SUCCEEDED

Smoke:
FAILED
```

일 수 있다.

**여섯 번째 — 검증 결과를 실제 근거로 남긴다.**

```text
Test Run

+

Application Version

+

Expected / Actual

+

Business Assertion

+

Evidence
```

를 연결한다.

현재 투게더몰과 같은 1인 개발·운영 환경에서는 다음 순서가 현실적이다.

```text
1. 핵심 고객 Journey 선정

2. Production Read-only 경계 정의

3. Playwright 기본 Smoke Test

4. 상품 상세 및 신청 모달 검증

5. 모바일 반응형 테스트

6. API Contract / Business Assertion

7. Staging 인증·권한 테스트

8. Post-deployment Smoke Test

9. 실패 Evidence 및 Alert

10. Scheduled Synthetic Monitoring
```

특히 상품 상세와 신청 모달은 고객의 실제 구매 전환에 직접 연결되므로 우선 검증할 가치가 높다.

다만 처음부터 CloudWatch Synthetics, 다중 지역 모니터링, 복잡한 Release Canary를 모두 도입할 필요는 없다.

기존 GitHub Actions·NestJS·PostgreSQL 환경에 Playwright를 추가해 핵심 경로를 검증하는 것부터 시작해도 충분하다.

더 중요한 점은 **정기 검사를 수행한다는 사실보다 검사가 실제 고객의 중요한 문제를 발견할 수 있도록 설계돼 있는가**이다.

최종적으로 기억해야 할 원칙은 다음과 같다.

**운영 시스템의 신뢰성은 서버가 실행 중인지뿐 아니라 고객이 실제 업무를 완료할 수 있는지, 권한과 업무 규칙이 유지되는지, 문제가 발생했을 때 실제 근거로 확인할 수 있는지에 의해 판단해야 한다.**
