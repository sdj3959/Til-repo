# 1016 운영 자동화/AI 워크플로우 심화 (40/N): Progressive Delivery, Feature Experimentation, Canary Analysis와 안전한 Rollback 자동화

---

## 1. 기능을 배포했다고 모든 고객에게 공개할 필요는 없다

### ✅ 1. 기존 배포 방식의 문제

일반적인 배포는 다음과 같다.

```text
개발 완료
    ↓
테스트
    ↓
Production 배포
    ↓
모든 고객에게 새 기능 적용
```

이 방식은 단순하지만 문제가 있다.

새로운 신청 모달에 오류가 있다면 해당 시점에 접속한 모든 고객이 영향을 받을 수 있다.

### ✅ 2. Progressive Delivery의 핵심

새로운 기능을 한 번에 공개하지 않고 제한된 범위에서 시작해 점차 확대한다.

```text
개발 완료
    ↓
Production 배포
    ↓
내부 사용자
    ↓
일부 고객
    ↓
지표 검증
    ↓
노출 확대
    ↓
전체 공개
```

이 방식이 Progressive Delivery다.

### ✅ 3. 핵심 목표

단순히 사용자 5%에게 기능을 보여주는 것이 아니다.

```text
작은 범위에서 검증

+

이상 징후 조기 발견

+

피해 범위 제한

+

안전한 확대 결정
```

이 목표다.

### ✅ 4. Feature Flag가 필요한 이유

예를 들어 기존 신청 모달과 신규 신청 모달이 모두 존재한다고 하자.

```text
OldApplicationModal

NewApplicationModal
```

Feature Flag에 따라 선택한다.

```text
new_application_modal = false
    ↓
기존 신청 모달
```

```text
new_application_modal = true
    ↓
신규 신청 모달
```

### ✅ 5. 코드 배포와 기능 공개의 분리

```text
Deployment
새 코드 설치
```

```text
Feature Activation
고객에게 기능 노출
```

을 분리한다.

이렇게 하면 코드가 운영 서버에 존재하더라도 기능 자체는 공개하지 않을 수 있다.

### ✅ 6. 하지만 Feature Flag가 모든 기능을 안전하게 만들지는 않는다

예:

```text
Prisma Migration 실행

신규 Column 삭제

IAM Policy 변경
```

은 Feature Flag를 끈다고 원래 상태로 돌아가지 않는다.

Feature Flag는 **이미 배포된 코드 안에서 특정 실행 경로를 선택하는 수단**이다.

### ✅ 7. Feature Flag가 유용한 기능

현재 프로젝트를 기준으로 다음과 같은 기능을 생각할 수 있다.

```text
신규 신청 모달

셀프 상담

새로운 상품 추천 UI

AI 리뷰 분석

관리자 신규 주문 필터

AI 마케팅 인사이트

신규 주문 상태 조회 화면
```

### ✅ 8. Feature Flag가 적절하지 않을 수 있는 영역

예:

```text
개인정보 접근 권한

관리자 인증

주문 필수 Validation

가격 무결성 검사

필수 Audit 기록
```

이러한 보안·업무 필수 제어를 단순 Flag 활성화 여부에 맡기면 안 된다.

### ✅ 9. 기능 노출과 권한은 다른 문제다

예:

```text
Feature Flag
ON
```

이라고 해서:

```text
관리자 권한 없음
```

인 사용자가 관리자 기능에 접근할 수 있어서는 안 된다.

서버에서 권한을 먼저 검증해야 한다.

### ✅ 10. Progressive Delivery 전체 흐름

```text
Code Review
      ↓
Change Impact
      ↓
CI / Contract Test
      ↓
Operational Readiness Review
      ↓
Production Deployment
      ↓
Feature Flag OFF
      ↓
Internal Validation
      ↓
Limited Rollout
      ↓
Canary Analysis
      ↓
Promote / Hold / Stop
      ↓
Full Rollout
      ↓
Stabilization
      ↓
Flag Cleanup
```

1015의 변경 승인 프로세스와 직접 연결된다.

## 2. Feature Flag 유형 구분

### ✅ 11. 모든 Feature Flag가 같은 목적은 아니다

대표적으로 다음을 구분한다.

```text
Release Flag

Experiment Flag

Operational Flag

Emergency Kill Switch
```

### ✅ 12. Release Flag

새로운 기능을 단계적으로 공개하는 데 사용한다.

예:

```text
self_consult_v2_enabled
```

### ✅ 13. Experiment Flag

서로 다른 기능이나 UI를 비교한다.

예:

```text
application_modal_variant
```

값:

```text
CONTROL

VARIANT_A
```

### ✅ 14. Operational Flag

운영 상태를 제어한다.

예:

```text
ai_insight_generation_enabled
```

AI API 비용 급증이나 Provider 장애 시 새로운 작업 생성을 제한할 수 있다.

### ✅ 15. Emergency Kill Switch

장애 발생 시 특정 기능을 즉시 제한한다.

예:

```text
notification_bulk_send_enabled = false
```

대량 발송을 중지한다.

### ✅ 16. Release Flag와 Kill Switch는 다르다

Release Flag:

```text
신규 기능 노출 여부
```

Kill Switch:

```text
위험한 작업 자체를 중단
```

하는 목적이다.

### ✅ 17. 두 역할을 하나의 Flag에 무조건 합치지 않는다

예:

```text
new_notification_v2_enabled
```

가 단순 신규 로직 선택 Flag라면 이를 끄는 순간 기존 로직으로 전환될 수 있다.

하지만 장애 상황에서는:

```text
모든 신규 알림 발송을 중단
```

해야 할 수도 있다.

따라서 운영 중단 Flag는 별도로 둘 수 있다.

### ✅ 18. 우선순위

예:

```text
Emergency Kill Switch
        ↓
Permission Policy
        ↓
Feature Availability
        ↓
Experiment Assignment
```

순서로 평가한다.

실제 비즈니스 권한 검사는 어느 Feature Flag보다 독립적으로 보장돼야 한다.

### ✅ 19. Flag Lifecycle

```text
PROPOSED

↓

IMPLEMENTED

↓

INTERNAL

↓

ROLLING_OUT

↓

FULLY_ENABLED

↓

STABILIZING

↓

REMOVED
```

중간에:

```text
PAUSED

DISABLED
```

상태가 발생할 수 있다.

### ✅ 20. Flag를 영구적으로 남겨두면 안 된다

예:

```ts
if (featureA) {
  // 신규 로직
} else {
  // 기존 로직
}
```

을 수년 동안 유지하면 코드 복잡도가 증가한다.

새 기능이 안정화되면 구버전 분기를 제거하는 계획이 필요하다.

### ✅ 21. Operational Kill Switch는 예외다

실제 운영 중 반복적으로 사용되는 Kill Switch는 장기적으로 유지할 가치가 있을 수 있다.

그러나 목적·Owner·기본값·실행 영향을 문서화해야 한다.

## 3. Feature Flag 데이터 설계

### ✅ 22. 최소 Flag Metadata

```text
Key

Type

Environment

Enabled

Rollout Percentage

Owner

Default Value

Created At

Updated At

Expires At
```

정도부터 시작할 수 있다.

### ✅ 23. 예시

```json
{
  "key": "self_consult_v2",
  "environment": "production",
  "enabled": true,
  "rolloutBasisPoints": 500,
  "defaultValue": false,
  "owner": "web-platform",
  "expiresAt": "2026-12-31T00:00:00Z"
}
```

여기서:

```text
500 Basis Points
=
5%
```

다.

### ✅ 24. 왜 Basis Points를 사용할까?

퍼센트를 정수로 표현하기 위해서다.

```text
10000
100%

5000
50%

500
5%

100
1%
```

처럼 사용할 수 있다.

소수 퍼센트도 표현하기 쉽다.

### ✅ 25. 처음에는 Boolean Flag만으로 충분할 수도 있다

현재 특정 기능을 내부에서만 테스트한다면:

```text
enabled = true / false
```

만으로도 충분하다.

처음부터 복잡한 세그먼트와 확률 엔진을 만들 필요는 없다.

### ✅ 26. 환경별 Flag 분리

예:

```text
development
ON

staging
ON

production
OFF
```

이다.

Staging에서 활성화됐다고 Production에서도 자동 활성화되지 않도록 한다.

### ✅ 27. Config Source

선택지는 다음과 같다.

```text
Environment Variable

Database

AWS AppConfig

External Feature Flag Service
```

### ✅ 28. 환경변수 방식

예:

```text
SELF_CONSULT_V2_ENABLED=false
```

장점:

```text
구조 단순

외부 의존성 없음
```

단점:

```text
변경 시 재배포/재시작 필요할 수 있음

사용자별 Rollout 어려움
```

### ✅ 29. DB 방식

예:

```text
feature_flags
```

테이블을 운영한다.

장점:

```text
런타임 변경 가능

사용자별 정책 가능
```

단점:

```text
Caching 필요 가능

설정 조회 실패 대응 필요

관리 권한 필요
```

### ✅ 30. AWS AppConfig

AWS AppConfig는 설정 및 Feature Flag 배포, 단계적 전개, CloudWatch Alarm 기반 되돌리기 기능을 제공한다.

다만 서비스 구성과 사용량에 따라 비용이 발생할 수 있다.

현재 규모에서는 기존 Config 구조가 충분한지 먼저 확인한다.

### ✅ 31. 현재 권장 방식

초기:

```text
기존 환경변수 또는
단순 관리형 설정
```

을 사용한다.

이후 실제 필요가 생기면:

```text
사용자별 Targeting

Runtime Rollout

Flag Audit

자동 Rollback
```

을 추가한다.

## 4. 사용자별 Percentage Rollout

### ✅ 32. 5% Rollout은 무엇의 5%인가?

이 질문이 중요하다.

가능한 기준:

```text
사용자 5%

세션 5%

요청 5%

주문 5%

특정 지역 사용자 5%
```

는 서로 다르다.

### ✅ 33. Request 단위 Random은 위험할 수 있다

나쁜 예:

```ts
const enabled = Math.random() < 0.05;
```

이 코드를 매 요청마다 실행한다고 하자.

같은 고객이:

```text
첫 번째 요청
신규 모달

두 번째 요청
기존 모달

세 번째 요청
신규 모달
```

을 볼 수 있다.

### ✅ 34. Sticky Assignment

같은 대상에게 같은 Variant를 지속적으로 제공하는 방식이다.

예:

```text
Customer A
신규 기능

Customer B
기존 기능
```

으로 결정했다면 Rollout 동안 해당 결과가 안정적으로 유지되도록 한다.

### ✅ 35. Stable Identifier

로그인 사용자는:

```text
User ID
```

를 사용할 수 있다.

익명 방문자는:

```text
Session ID

First-party Anonymous ID
```

등을 고려할 수 있다.

단 개인정보 및 추적 동의 정책에 맞게 처리해야 한다.

### ✅ 36. 전화번호를 직접 Hash Key로 사용하지 않는다

```text
Phone Number

Email

Resident Identifier
```

같은 개인정보 원문을 Flag 평가·로그에 불필요하게 넣지 않는다.

SHA-256으로 변환했다고 자동으로 익명화되는 것도 아니다.

### ✅ 37. Deterministic Bucketing

동일한 사용자와 Flag Key에 대해 항상 같은 Bucket을 계산할 수 있다.

```text
Flag Key

+

Stable Subject Key

↓

Hash

↓

Bucket

↓

Rollout Decision
```

### ✅ 38. TypeScript 예시

```ts
import { createHash } from 'node:crypto';

export function isInRollout(
  flagKey: string,
  subjectKey: string | undefined,
  basisPoints: number,
): boolean {
  if (!subjectKey) {
    return false;
  }

  if (
    !Number.isInteger(basisPoints) ||
    basisPoints < 0 ||
    basisPoints > 10000
  ) {
    return false;
  }

  const hash = createHash('sha256')
    .update(`${flagKey}\0${subjectKey}`)
    .digest('hex')
    .slice(0, 12);

  const bucket =
    Number.parseInt(hash, 16) % 10000;

  return bucket < basisPoints;
}
```

이 코드는 개념 설명을 위한 구현이다.

실제 운영에서는 테스트, Bucketing Version, Config Validation 및 Subject ID 정책이 추가로 필요하다.

### ✅ 39. 사용 예시

```ts
const enabled = isInRollout(
  'self_consult_v2',
  'anonymous-session-123',
  500,
);
```

500은 5%를 의미한다.

### ✅ 40. Bucket의 장점

같은 대상과 Flag Key라면 동일한 Bucket을 얻는다.

```text
A
Bucket 120

B
Bucket 7800
```

5% Rollout에서는 A만 포함된다.

### ✅ 41. 5% → 10% 확대

기준:

```text
5%
Bucket 0~499
```

확대:

```text
10%
Bucket 0~999
```

이면 기존에 포함된 A는 계속 포함된다.

### ✅ 42. 단 Hash 입력이 바뀌면 Cohort가 달라진다

예:

```text
self_consult_v2
```

에서:

```text
self_consult_v3
```

로 Flag Key를 바꾸면 다른 Bucket이 계산될 수 있다.

따라서 Rollout 중 식별 키나 Hash Algorithm을 임의 변경하지 않는다.

### ✅ 43. 여러 기기 간 Sticky Assignment

익명 Session을 기준으로 하면 같은 사람이:

```text
iPhone

MacBook
```

에서 서로 다른 Variant에 배정될 수 있다.

이것이 허용 가능한지 업무 기준으로 판단해야 한다.

### ✅ 44. User ID가 없는 경우

개인정보를 과도하게 수집하면서까지 완벽한 Cross-device Sticky Assignment를 구현할 필요는 없다.

중요한 것은 실험과 업무 흐름에 적절한 식별 단위를 명확히 정하는 것이다.

### ✅ 45. 고객 신청 진행 중 Variant 변경은 위험하다

예:

```text
상품 선택
신규 UI

↓

신청서 작성
기존 UI

↓

주문 접수
신규 API
```

처럼 섞이면 문제가 발생할 수 있다.

### ✅ 46. Journey-level Assignment

신청 프로세스가 시작됐을 때:

```text
applicationFlowVersion
```

을 결정하고 해당 신청이 끝날 때까지 유지할 수 있다.

### ✅ 47. 주문 생성 이후에도 필요한 경우 기록

예:

```text
Order

applicationFlowVersion = v2
```

같이 남길 수 있다.

단 실제 업무 데이터로 의미가 있는 경우에만 저장하고, 개인정보나 실험 식별자를 불필요하게 장기 보관하지 않는다.

## 5. Frontend와 Backend Flag를 일치시키기

### ✅ 48. Frontend Flag만으로 충분할까?

예:

```text
Frontend
신규 모달 노출

Backend
신규 처리 로직 비활성화
```

라면 문제가 발생한다.

### ✅ 49. Frontend와 Backend의 일관성

```text
Feature Assignment

↓

Frontend Rendering

↓

Backend Validation

↓

Business Processing
```

이 모두 일치해야 한다.

### ✅ 50. Backend-authoritative Decision

업무상 중요한 Flag는 서버에서 결정하는 편이 안전하다.

예:

```text
GET /feature-decisions
```

응답:

```json
{
  "applicationModal": "V2",
  "selfConsult": false
}
```

### ✅ 51. Frontend는 해당 결정으로 UI를 표시한다

```text
applicationModal = V2
```

이면 신규 모달을 렌더링한다.

### ✅ 52. Backend도 같은 정책을 검증한다

Frontend에서 다음 값을 임의로 보내더라도:

```json
{
  "applicationModal": "V2"
}
```

서버는 해당 사용자의 실제 할당과 업무 정책을 확인해야 한다.

클라이언트 입력만 믿지 않는다.

### ✅ 53. Client에 모든 Flag를 노출하지 않는다

내부 운영 Flag나 민감한 실험 조건은 공개할 필요가 없다.

예:

```text
Admin Security Policy

Fraud Detection Threshold

Internal API Endpoint
```

등을 Frontend Flag Response에 넣지 않는다.

### ✅ 54. Flag 평가 실패 시 기본값

새 기능의 일반적인 기본값은:

```text
OFF
```

가 안전할 수 있다.

하지만 무조건 모든 기능을 OFF로 처리하면 안 된다.

### ✅ 55. 핵심 주문 기능은 기존 정상 경로를 유지해야 한다

예:

```text
Flag Provider 장애
```

가 발생했을 때:

```text
전체 주문 접수 중단
```

이 아니라:

```text
검증된 기존 신청 경로 사용
```

하도록 설계하는 것이 유리하다.

단 기존 경로가 안전하고 실제로 계속 운영할 수 있다는 전제가 필요하다.

### ✅ 56. 보안 권한은 별도 Fail-safe

관리자 권한 검증에 실패한다면 Feature Flag 기본값과 무관하게 접근을 거부해야 한다.

### ✅ 57. Flag Config Cache

런타임 Config를 DB에서 조회한다면 요청마다 DB를 직접 조회하지 않도록 단기 Cache를 활용할 수 있다.

### ✅ 58. Cache에는 갱신 지연이 있다

예:

```text
Kill Switch
OFF
```

로 변경했어도 기존 Cache 때문에 일부 서버가 예전 값을 사용할 수 있다.

### ✅ 59. 긴급 차단의 전파 시간

다음 값을 알아야 한다.

```text
Config Refresh Interval

Cache TTL

Propagation Delay

Worker Polling Interval
```

### ✅ 60. Kill Switch는 즉각적인 완전 중단을 보장하지 않는다

이미 실행 중인 작업은 계속 진행될 수 있다.

따라서 긴급 중단 설계에서는 다음을 구분한다.

```text
New Requests

Queued Jobs

In-flight Jobs

External Provider Requests
```

## 6. Progressive Rollout 단계

### ✅ 61. 처음부터 임의의 5%로 공개할 필요는 없다

추천 순서는 다음과 같다.

```text
Production Deployment

↓

Flag OFF

↓

Internal Allowlist

↓

Limited Production Exposure

↓

Metrics Review

↓

Rollout Expansion
```

### ✅ 62. Internal Allowlist

예:

```text
Developer

담당 관리자

QA 담당자
```

에게만 공개한다.

이 단계에서는 실제 업무를 확인한다.

### ✅ 63. Allowlist 식별자는 서버에서 검증

단순히 Frontend에서:

```text
isAdmin=true
```

를 보내는 방식으로 내부 사용자 여부를 판단하지 않는다.

### ✅ 64. 단계별 확대 예시

```text
0%
Internal Only

↓

1%

↓

5%

↓

20%

↓

50%

↓

100%
```

이 수치는 예시다.

서비스 트래픽이 적다면 1%에서는 아무런 의미 있는 데이터를 확보하지 못할 수 있다.

### ✅ 65. Rollout 단계는 시간보다 증거가 중요하다

나쁜 방식:

```text
1시간 경과
→ 5% 확대
```

좋은 방식:

```text
필수 검증 통과

+

충분한 관측

+

Critical Issue 없음

↓

다음 단계
```

### ✅ 66. Rollout Decision

```text
PROMOTE
다음 단계 확대

HOLD
현재 단계 유지

PAUSE
신규 노출 중단

DISABLE
기능 비활성화
```

등으로 표현할 수 있다.

### ✅ 67. 판단할 데이터가 없다면 HOLD

예:

```text
Canary Users
2명

Order Attempts
0건
```

인 경우:

```text
모든 지표 정상
```

이라고 할 수 없다.

### ✅ 68. NO_SAMPLE

```text
Business Verification
NO_SAMPLE
```

로 표시한다.

### ✅ 69. 일반 사용자에게 공개하기 전 실제 Business Scenario를 테스트한다

예:

```text
상품 조회

↓

신청 모달

↓

기종·요금제 선택

↓

신청 정보 검증

↓

주문 접수
```

경로를 Staging이나 안전한 검증 환경에서 확인한다.

### ✅ 70. Canary 확대는 되돌릴 수 있어야 한다

최소한:

```text
현재 Rollout %

이전 Rollout %

변경자

변경 시각

변경 이유
```

를 기록한다.

### ✅ 71. Rollout Policy Version

예:

```text
self_consult_v2
Policy Version 4
```

처럼 변경 이력을 남길 수 있다.

### ✅ 72. 동시에 너무 많은 실험을 진행하지 않는다

예:

```text
신규 신청 모달

신규 상품 가격 UI

신규 상담 기능
```

을 같은 사용자에게 동시에 공개하면 성과나 오류의 원인을 구분하기 어려워질 수 있다.

특히 같은 전환 퍼널을 변경하는 실험은 충돌 가능성을 검토해야 한다.

## 7. Canary Analysis — 무엇을 비교해야 할까?

### ✅ 73. Canary는 일부에게 적용한 변경을 평가하는 과정이다

예:

```text
Control
기존 신청 모달

Canary
신규 신청 모달
```

을 비교한다.

### ✅ 74. Canary에는 두 종류의 지표가 필요하다

```text
Technical Guardrails

Business Guardrails
```

이다.

### ✅ 75. Technical Guardrail

예:

```text
HTTP 5xx Rate

API p95

JavaScript Error

NestJS Exception

DB Error

Memory

Queue Lag
```

이다.

### ✅ 76. Business Guardrail

예:

```text
Order Submission Success Rate

Duplicate Order Rate

Application Completion

Notification Error

고객 문의 증가
```

등이다.

### ✅ 77. 단순 Page View만으로 성공을 판단하지 않는다

신규 모달이 많이 열렸다고 신청 성공률이 높아졌다는 뜻은 아니다.

### ✅ 78. 신청 모달에서 볼 지표

```text
Modal Opened

Form Started

Validation Failed

Submit Attempted

Submit Succeeded

Submit Failed
```

같이 측정할 수 있다.

### ✅ 79. 최종 Business Metric

예:

```text
Application Completion Rate
```

를 사용할 수 있다.

하지만 분모를 명확히 해야 한다.

### ✅ 80. 예시

```text
신청 시작
1,000건

신청 완료
600건

완료율
60%
```

이다.

사용자 단위인지, Session 단위인지, 신청 시도 단위인지 정의해야 한다.

### ✅ 81. 비교 대상은 같은 시간대가 유리하다

예:

```text
월요일 Control

화요일 Canary
```

만 비교하면 광고량·요일·상품 출시 영향이 섞일 수 있다.

### ✅ 82. Concurrent Control

같은 기간에:

```text
Control

Canary
```

를 운영하면 일부 시간적 영향을 줄일 수 있다.

단 사용자 집단 구성과 시스템 공유 의존성을 고려해야 한다.

### ✅ 83. Sample Size

예:

```text
Canary
10명

Control
1,000명
```

이면 두 집단의 수치 차이를 신뢰성 있게 해석하기 어려울 수 있다.

### ✅ 84. 소규모 서비스에서는 안정성 검증과 성과 검증을 분리한다

```text
Canary
위험한 오류가 없는지 확인
```

```text
A/B Experiment
성과 개선 여부 검증
```

이다.

### ✅ 85. 비정상적 오류는 적은 표본에서도 중단 근거가 될 수 있다

예:

```text
Canary 주문 1건

실제 주문 금액 잘못 저장
```

이면 해당 오류의 심각성에 따라 즉시 기능을 중단할 수 있다.

### ✅ 86. 하지만 오류가 없다는 결론은 다르다

```text
Canary 주문 1건

오류 0건
```

이라고 기능 전체가 안전하다는 증거는 아니다.

### ✅ 87. 전체 지표만 보면 문제를 놓칠 수 있다

예:

```text
Global Order Success Rate
정상
```

하지만:

```text
Canary Order Success Rate
급감
```

할 수 있다.

### ✅ 88. Variant별 Metric

예:

```text
application_submit_total{
  variant="control"
}
```

```text
application_submit_total{
  variant="v2"
}
```

처럼 구분한다.

Metric Label에는 사용자 ID 같은 고유 개인정보를 넣지 않는다.

### ✅ 89. Shared Infrastructure 문제

Canary가 DB 부하를 크게 증가시키면 Control 사용자도 느려질 수 있다.

이 경우 단순 Control과 Canary 비교만으로 문제를 완전히 탐지하지 못할 수 있다.

### ✅ 90. Global Guardrail도 함께 확인한다

```text
Global DB CPU

Global Connection Pool

Global API Error

Queue Lag
```

등이다.

### ✅ 91. Canary의 판단 기준

```text
Canary-specific Metric

+

Global Platform Metric

+

Business Critical Metric
```

을 함께 본다.

## 8. A/B Experiment — 기능의 효과를 측정하기

### ✅ 92. Canary와 A/B Experiment의 차이

Canary의 주요 목적:

```text
이 변경을 안전하게 확대할 수 있는가?
```

A/B Experiment의 주요 목적:

```text
새로운 변경이 기존 방식보다
실제로 더 좋은 결과를 만드는가?
```

이다.

### ✅ 93. A/B Experiment 예시

가설:

```text
신청 모달의 입력 단계를 줄이면
신청 완료율이 개선될 것이다.
```

### ✅ 94. Control

```text
기존 신청 모달
```

### ✅ 95. Treatment

```text
신규 간소화 모달
```

### ✅ 96. Primary Metric

예:

```text
Application Completion Rate
```

이다.

### ✅ 97. Guardrail Metric

예:

```text
Duplicate Orders

Invalid Applications

Customer Support Complaints

Server Error Rate
```

등이다.

### ✅ 98. Primary Metric만 보면 안 된다

예:

```text
신청 완료율
+10%
```

하지만:

```text
잘못된 신청
+50%
```

이라면 좋은 변경이라고 판단하기 어렵다.

### ✅ 99. Randomization Unit

실험 대상을 무엇으로 무작위 배정할지 정해야 한다.

```text
User

Session

Order Journey
```

등이다.

### ✅ 100. 매 요청 Randomization은 피한다

동일한 사용자가 매번 다른 Variant를 경험하면 측정이 왜곡될 수 있다.

### ✅ 101. Experiment Exposure

Variant에 배정됐다는 사실과 실제 기능을 봤다는 사실을 구분한다.

```text
Assigned
Variant A

Exposed
실제 Variant A 화면 사용
```

### ✅ 102. Exposure Event

예:

```json
{
  "experiment": "application_modal_v2",
  "variant": "treatment",
  "event": "EXPOSED"
}
```

실제 Event에는 필요한 최소 Metadata만 포함한다.

### ✅ 103. Exposure를 매 Render마다 무한 기록하지 않는다

React Re-render 때문에 같은 사용자의 노출 이벤트가 중복 기록될 수 있다.

분석 단위에 맞는 Deduplication 정책이 필요하다.

### ✅ 104. Assignment와 Exposure를 함께 보존한다

실험 목적에 따라:

```text
Assigned Population
```

기준 분석과:

```text
Exposed Population
```

기준 분석의 해석이 달라질 수 있다.

실제 노출 여부를 기준으로 대상을 선택할 때 선택 편향이 생길 수도 있으므로 실험 설계에서 이를 고려해야 한다.

### ✅ 105. Sample Ratio Mismatch

예:

```text
설계
50:50

실제 배정
80:20
```

이라면 Randomization 또는 데이터 수집 문제를 의심할 수 있다.

### ✅ 106. A/A Test

동일한 기능을 두 그룹에 배정해 측정 체계가 정상인지 확인한다.

예:

```text
A
기존 모달

A'
기존 모달
```

이다.

### ✅ 107. 실험 기간을 결과에 따라 무작정 조기 종료하지 않는다

매시간 전환율을 확인하면서 유리한 결과가 나오면 즉시 승리라고 선언하는 방식은 통계적 오류를 증가시킬 수 있다.

따라서 사전에:

```text
Primary Metric

Minimum Sample

Experiment Duration

Stopping Rule
```

을 정한다.

### ✅ 108. 실험 결과가 통계적으로 불명확할 수 있다

예:

```text
Control
61%

Treatment
62%
```

차이가 있더라도 실제 개선이라고 판단할 근거가 부족할 수 있다.

### ✅ 109. 소규모 서비스의 현실적인 결론

주문량이 충분하지 않다면 정교한 A/B 결과보다:

```text
기능 안정성

사용성 테스트

실제 고객 불편

운영 부담

기본 전환 지표
```

를 근거로 제품 판단을 할 수 있다.

단 통계적으로 검증되지 않은 결과를 확정적인 성과 개선이라고 주장하지 않는다.

### ✅ 110. 가격 조건 실험은 특히 신중해야 한다

휴대폰 판매몰에서 고객별로 다른 가격이나 조건을 임의로 제공하는 실험은 소비자 신뢰, 표시·광고 및 계약상 문제를 만들 수 있다.

초기 실험은:

```text
정보 배치

입력 편의성

상품 설명

안내 방식
```

같은 비가격 UX부터 시작하는 편이 낫다.

## 9. 자동 Rollback 판단

### ✅ 111. 자동 Rollback을 무조건 구현하면 위험하다

예:

```text
Canary Error Rate 증가

↓

즉시 Production 전체 Rollback
```

은 지나치게 공격적인 자동화일 수 있다.

### ✅ 112. 자동 대응 단계를 분리한다

```text
DETECT

↓

EVALUATE

↓

HOLD

↓

PAUSE

↓

DISABLE

↓

ROLLBACK REQUEST
```

로 구분한다.

### ✅ 113. 가장 안전한 초기 자동화

```text
이상 징후 탐지

↓

신규 Rollout 확대 중지

↓

운영자 알림
```

이다.

Production Code 자체를 자동으로 바꾸는 것보다 위험이 작다.

### ✅ 114. 단순 Flag Rollback

예:

```text
self_consult_v2

20%

↓

0%
```

로 변경한다.

이 경우 신규 사용자에게 새 기능을 제공하지 않을 수 있다.

### ✅ 115. 이미 진행 중인 Session 처리

새 기능이 비활성화됐다고 진행 중인 모든 Session을 즉시 다른 Flow로 옮기면 위험할 수 있다.

예:

```text
신청서 작성 중

↓

Rollout 0%

↓

다음 페이지에서 구버전으로 전환
```

되는 문제가 생긴다.

### ✅ 116. In-flight Policy

다음 중 하나를 명시적으로 선택한다.

```text
신규 진입만 차단

기존 Journey 완료 허용

진행 중 작업 안전 중단

관리자 검토로 전환
```

### ✅ 117. 업무에 따라 정책이 다르다

UI 문제라면 기존 Journey 완료를 허용할 수 있다.

반면 잘못된 금액 저장 문제라면 진행 중 요청도 차단해야 할 수 있다.

### ✅ 118. Kill Switch는 Queue에도 적용해야 할 수 있다

예:

```text
AI Insight
Kill Switch OFF
```

했는데:

```text
Queue
1000 Pending Jobs
```

가 있다면 Worker가 계속 실행할 수 있다.

### ✅ 119. Admission과 Execution을 분리한다

```text
New Job Creation
차단

Existing Queue
정책에 따라 처리

In-flight
취소 가능 여부 확인
```

이다.

### ✅ 120. 외부 API는 되돌릴 수 없다

예:

```text
알림톡 발송 성공
```

이후 Flag를 OFF로 해도 이미 발송한 메시지는 취소되지 않는다.

### ✅ 121. 데이터 변경도 자동 복원되지 않는다

```text
Order Status 변경

DB Row 생성

External Webhook 전송
```

은 Feature Flag Rollback과 별도의 복구 문제다.

### ✅ 122. Rollback Trigger에 최소 관측 조건 필요

예:

```text
Canary Requests
100 이상

AND

Error Rate
기준 초과
```

처럼 할 수 있다.

단 주문 금액 오류나 개인정보 유출처럼 심각한 사고는 표본 수와 무관하게 대응할 수 있어야 한다.

### ✅ 123. Consecutive Breach

예:

```text
3개 관측 Window 연속
Latency 기준 초과
```

이면 Rollout을 중단할 수 있다.

그렇지만 기준은 실제 Traffic과 지표 특성에 맞춰 검증해야 한다.

### ✅ 124. 자동 중단 정책 예시

```text
IF

Critical Business Error Detected

THEN

DISABLE NEW EXPOSURE
```

```text
IF

Insufficient Samples

THEN

HOLD
```

```text
IF

Guardrails Pass

AND

Required Verification Pass

THEN

PROMOTION_REVIEW
```

### ✅ 125. PROMOTE까지 처음부터 자동화하지 않는다

현재 규모에서는:

```text
자동 Detection

자동 Hold

자동 Alert

관리자 Promotion Approval
```

이 적합하다.

### ✅ 126. 안전한 자동화를 위한 Decision Model

```ts
type RolloutDecision =
  | 'PROMOTE_REVIEW'
  | 'HOLD'
  | 'PAUSE'
  | 'DISABLE'
  | 'MANUAL_REVIEW_REQUIRED';

interface RolloutEvaluation {
  flagKey: string;
  currentBasisPoints: number;

  sampleCount: number;

  technicalStatus:
    | 'PASS'
    | 'FAIL'
    | 'NOT_VERIFIED';

  businessStatus:
    | 'PASS'
    | 'FAIL'
    | 'NO_SAMPLE'
    | 'NOT_VERIFIED';

  decision: RolloutDecision;

  reason: string;
}
```

### ✅ 127. DISABLE과 Application Rollback을 구분한다

```text
Flag Disable
새 기능 경로 중지
```

```text
Application Rollback
이전 코드 Artifact 재배포
```

이다.

### ✅ 128. 자동 Application Rollback은 더 엄격해야 한다

DB Schema나 외부 Side Effect가 있는 경우 자동 Rollback이 새로운 오류를 만들 수 있다.

따라서 배포 Artifact와 데이터 호환성이 검증된 경우에만 제한적으로 자동화한다.

### ✅ 130. AWS AppConfig의 역할

AppConfig는 설정의 버전과 배포 전략을 관리할 수 있다.

또 설정 Validator를 사용하고 CloudWatch Alarm과 연결해 설정 배포를 되돌리는 기능을 제공한다.

### ✅ 131. 중요한 구분

AWS AppConfig의 일반적인 설정 배포 전략과 사용자별 Feature Targeting은 서로 관련되지만 동일한 개념이 아니다.

사용자나 세그먼트 기반 점진적 전개는 해당 기능을 지원하는 AppConfig Agent와 설정이 필요하다.

### ✅ 132. AWS AppConfig Bake Time

Bake Time은 설정 전개가 끝난 후에도 지정된 기간 동안 Alarm을 관찰하는 개념이다.

예:

```text

100%

↓

Bake Time

↓

Alarm 확인

↓

완료 또는 Rollback
```

이다.

### ✅ 133. Bake Time이 보장하지 않는 것

```text
주문 데이터 복구

발송된 메시지 취소

외부 API 처리 취소

모든 Business Error 탐지
```

를 자동으로 보장하지 않는다.

### ✅ 134. CloudWatch Alarm 연결

예:

```text
API 5xx

p95 Latency

Order Error Metric

Queue Lag
```

를 Alarm에 사용할 수 있다.

실제 Alarm 평가 기간과 임계값은 운영 데이터 기준으로 정한다.

### ✅ 135. INSUFFICIENT_DATA도 정책적으로 다룬다

관측 데이터가 부족한 상황은 정상과 다르다.

AWS AppConfig의 Alarm 기반 자동 Rollback은 특정 조건에서 `ALARM`뿐 아니라 `INSUFFICIENT_DATA` 상태도 고려할 수 있다.

따라서 지표 수집 자체의 신뢰성도 검증해야 한다.

### ✅ 136. AWS CodeDeploy

CodeDeploy는 배포 실패 또는 지정된 Monitoring 조건에 따라 이전 정상 Revision을 재배포하는 Rollback 기능을 제공한다.

하지만 이 역시 **Application Revision 복구**다.

### ✅ 137. DB 복구와 다르다

```text
CodeDeploy Rollback
Application Revision
```

```text

Database Recovery Point
```

이다.

### ✅ 138. 현재 프로젝트에서 도입 순서

```text

2. App-level Feature Flag

3. Rollout Metric

4. Manual Kill Switch

5. 자동 HOLD / Alert

6. 필요할 때 AppConfig

정도가 현실적이다.

### ✅ 139. 추가 AWS 서비스를 무조건 도입하지 않는다

단일 EC2와 NestJS 중심 운영에서 기존 기능만으로 요구를 충족할 수 있다면 그것이 더 단순하고 비용 효율적일 수 있다.

## 14. 네이버 EP와 Progressive Delivery

### ✅ 163. 모든 데이터 연동에 Percentage Rollout을 적용할 수 있는 것은 아니다

네이버 EP 생성

### ✅ 164. 이 경우 사용자별 5% 공개가 적절하지 않을 수 있다

### ✅ 166. 상품 가격 자체를 무작위로 변경하는 실험은 신중해야 한다

특히 신청 당시 약속한 판매 조건과 외부 광고 가격을 일치시키는 것이 중요하다.

### ✅ 176. Feature Flag OFF Test

Flag OFF

Flag ON

```

을 확인한다.

### ✅ 178. Missing Config Test

Flag 설정이 없는 경우 안전한 기본 경로를 사용해야 한다.

### ✅ 179. Flag Provider Failure Test

DB나 외부 Flag Provider가 실패한 경우에도 핵심 업무가 예상한 방식으로 동작하는지 검증한다.

### ✅ 180. Sticky Assignment Test

동일한 Subject Key로 여러 번 평가해도 동일한 결과를 반환해야 한다.

### ✅ 181. Percentage Expansion Test

5%에 포함된 대상은 동일한 Bucketing 규칙을 유지한 상태에서 10%로 확대해도 계속 포함돼야 한다.

### ✅ 182. Invalid Percentage Test

```text
-1

10001

NaN
```

같은 잘못된 설정을 거부하거나 안전한 기본값으로 처리한다.

### ✅ 183. Unknown Subject Test

식별 가능한 대상이 없는 경우 신규 기능을 무작위로 활성화하지 않도록 한다.

실제 익명 사용자 정책에 맞춰 처리한다.

### ✅ 184. Concurrent Session Test

같은 고객의 여러 요청이 서로 다른 Variant를 사용하지 않는지 검증한다.

### ✅ 185. Journey Consistency Test

신청 Flow 중간에 Flag가 바뀌어도 진행 중인 신청이 안전하게 처리되는지 검증한다.

### ✅ 186. Kill Switch Test

새로운 작업이 차단되는지 확인한다.

### ✅ 187. Queue Kill Switch Test

이미 대기 중인 작업이 정책에 따라 처리되는지 확인한다.

### ✅ 188. In-flight Test

외부 발송 또는 DB 변경 중 Kill Switch가 활성화됐을 때 결과를 검증한다.

### ✅ 189. Metrics Missing Test

Canary Metric이 수집되지 않을 때:

```text
PASS
```

가 아니라:

```text
NOT_VERIFIED
```

또는:

```text
HOLD
```

로 처리되는지 검증한다.

### ✅ 190. False Positive Test

한 번의 일시적인 지연으로 불필요하게 전체 Application Rollback이 실행되지 않는지 확인한다.

### ✅ 191. Critical Error Test

주문 금액 오류 같은 심각한 문제가 발견되면 표본 수와 관계없이 안전한 중단 절차가 작동하는지 확인한다.

### ✅ 192. Rollback Compatibility Test

Flag를 OFF로 했을 때 구버전 경로가 새로운 DB Schema에서도 정상 동작하는지 확인한다.

### ✅ 193. Post-rollout Cleanup Test

Flag 제거 후 구버전 코드와 설정이 안전하게 정리됐는지 확인한다.

## 23. Progressive Delivery 최종 체크리스트

### Feature Flag

- [ ] Flag의 목적이 명확한가?
- [ ] Release Flag와 Kill Switch를 구분하는가?
- [ ] 기본값이 안전한가?
- [ ] Flag Provider 실패 시 동작이 정의돼 있는가?
- [ ] Owner와 Expiration이 있는가?
- [ ] Flag 변경 Audit가 있는가?

### Assignment

- [ ] Randomization Unit이 명확한가?
- [ ] 요청마다 무작위로 Variant가 바뀌지 않는가?
- [ ] Stable Subject Key를 사용하는가?
- [ ] 개인정보 원문을 사용하지 않는가?
- [ ] Rollout 확대 시 기존 사용자가 유지되는가?
- [ ] 신청 Journey 중 Variant가 바뀌지 않는가?

### Frontend / Backend

- [ ] 서버가 최종 권한을 검사하는가?
- [ ] Frontend와 Backend Variant가 일치하는가?
- [ ] Client에서 보낸 Flag를 그대로 신뢰하지 않는가?
- [ ] 구버전 Flow가 계속 정상 동작하는가?
- [ ] 이전 Client와 호환되는가?

### Rollout

- [ ] Internal Allowlist 테스트를 완료했는가?
- [ ] 제한된 Production 노출을 계획했는가?
- [ ] 단계별 확대 기준이 있는가?
- [ ] NO_SAMPLE을 PASS로 처리하지 않는가?
- [ ] 다른 실험과 충돌하지 않는가?
- [ ] Rollout Policy Version이 기록되는가?

### Canary

- [ ] Technical Guardrail이 있는가?
- [ ] Business Guardrail이 있는가?
- [ ] Global Platform Metric을 보는가?
- [ ] 실제 Exposure를 측정하는가?
- [ ] Sample Size를 확인하는가?
- [ ] 주요 고객 업무 흐름을 검증하는가?

### Experiment

- [ ] Hypothesis를 명확히 정의했는가?
- [ ] Control과 Treatment를 구분하는가?
- [ ] Primary Metric이 명확한가?
- [ ] Guardrail Metric이 있는가?
- [ ] Sample Ratio를 확인하는가?
- [ ] 통계적으로 불충분한 결과를 개선으로 주장하지 않는가?

### Kill Switch

- [ ] 새 요청을 차단할 수 있는가?
- [ ] In-flight 작업 정책이 있는가?
- [ ] Queue에 남은 Job을 고려하는가?
- [ ] Config 전파 지연을 알고 있는가?
- [ ] 외부 Side Effect가 자동으로 취소되지 않는다는 점을 고려하는가?

### Rollback

- [ ] Flag OFF와 Application Rollback을 구분하는가?
- [ ] 기존 Artifact가 있는가?
- [ ] DB 호환성을 확인하는가?
- [ ] Rollback 후 Business Verification을 수행하는가?
- [ ] Data Reconciliation이 필요한지 확인하는가?

### Operations

- [ ] Rollout Record가 존재하는가?
- [ ] 배포 Commit과 Flag Policy가 연결되는가?
- [ ] Rollout 변경자가 기록되는가?
- [ ] 자동 HOLD와 수동 PROMOTE를 구분하는가?
- [ ] 전체 공개 후 Flag Cleanup 계획이 있는가?
- [ ] 장애 발생 시 Runbook이 있는가?

## 📌 요약

1015에서는 다음을 다뤘다.

```text
Change Impact

↓

Risk Classification

↓

Release Approval

↓

Deployment

↓

Technical Verification

↓

Business Verification
```

1016에서는 여기에 새로운 단계를 추가했다.

```text
Deployment

↓

Feature Flag OFF

↓

Internal Validation

↓

Limited Rollout

↓

Canary Analysis

↓

Promotion Decision

↓

Full Rollout
```

가장 중요한 것은 다음과 같다.

**새로운 기능을 Production에 배포하는 것과 모든 고객에게 공개하는 것은 별개의 작업이다.**

예를 들어:

```text
신규 신청 모달
Production 배포 완료
```

이후에도:

```text
Feature Flag
OFF
```

로 유지할 수 있다.

그리고:

```text
Internal Users

↓

5% Customers

↓

20% Customers

↓

50% Customers

↓

100% Customers
```

처럼 확대할 수 있다.

단 이 비율은 정해진 정답이 아니다.

트래픽이 적다면 5%에서는 유의미한 데이터가 없을 수 있다.

그래서:

```text
Elapsed Time
```

보다:

```text
Verified Evidence
```

가 중요하다.

Canary Analysis에서도 다음을 구분한다.

```text
Technical Guardrails

Business Guardrails

Global Platform Guardrails
```

예를 들어:

```text
API Error
정상
```

이어도:

```text
주문 완료율
급감
```

했다면 성공적인 기능이라고 판단하기 어렵다.

반대로:

```text
주문 완료율
증가
```

했더라도:

```text
중복 주문
급증
```

했다면 기능 확대를 중단해야 할 수 있다.

A/B Experiment에서는 또 다른 질문을 한다.

```text
안전한가?
```

를 넘어서:

```text
실제로 더 좋은가?
```

를 검증한다.

이때:

```text
Control

Treatment

Assignment

Exposure

Primary Metric

Guardrail
```

을 명확하게 정의해야 한다.

그리고 Rollback에도 차이가 있다.

```text
Flag Disable
새 기능 비활성화
```

```text
Application Rollback
이전 Code Revision 배포
```

```text
Data Recovery
변경된 데이터 복구
```

```text
Reconciliation
외부 상태와 내부 상태 대조
```

는 서로 다른 절차다.

따라서:

```text
Feature Flag OFF
```

가 모든 복구를 완료한다는 의미는 아니다.

특히 이미:

```text
주문 생성

알림톡 발송

외부 Webhook 전달

DB 상태 변경
```

이 발생했다면 별도 확인이 필요하다.

현재 프로젝트에서의 현실적인 우선순위는 다음과 같다.

```text
1. 신규 기능별 Feature Flag

2. 안전한 기본 경로

3. Internal Allowlist

4. Sticky Assignment

5. Backend Flag Enforcement

6. Technical / Business Metric

7. Rollout History

8. 수동 Promotion

9. 자동 HOLD / Alert

10. Kill Switch 검증
```

그다음에야 AWS AppConfig, 자동 Rollback, 고급 실험 분석 도입을 검토하면 된다.

전체 구조로 연결하면:

```text
Code Change
      ↓
Change Impact
      ↓
Release Approval
      ↓
Production Deployment
      ↓
Feature Flag OFF
      ↓
Internal Validation
      ↓
Stable User Assignment
      ↓
Limited Rollout
      ↓
Canary Metrics
      ↓
Business Guardrails
      ↓
PROMOTE / HOLD / DISABLE
      ↓
Full Rollout
      ↓
Stabilization
      ↓
Flag Cleanup
```

이 된다.

결국 Progressive Delivery의 핵심은 다음과 같다.

> **좋은 배포는 새로운 코드를 한 번에 모든 고객에게 제공하는 것이 아니라, 변경의 위험을 제한하고 실제 운영 데이터를 확인하면서 안전하다는 증거가 쌓인 만큼 점진적으로 공개하는 것이다.**

또한 모든 단계를 자동화하는 것이 목표는 아니다.

1인 개발 환경에서는 오히려:

```text
자동 Detection

자동 Metric 수집

자동 HOLD

수동 Promotion Approval

검증된 Kill Switch
```

구조가 단순하면서도 안전할 수 있다.
