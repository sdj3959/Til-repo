## Experiment Design·Statistical Guardrails·Metric Attribution·A/A Test와 신뢰할 수 있는 실험 분석

## 1. 새로운 기능의 성과를 어떻게 증명할 것인가?

### ✅ 1. 1016과의 연결

1016에서는 새로운 기능을 한 번에 모든 사용자에게 공개하지 않고 단계적으로 활성화하는 Progressive Delivery를 다뤘다.

```text
Production Deployment
        ↓
Feature Flag
        ↓
Internal Validation
        ↓
Limited Rollout
        ↓
Canary Analysis
        ↓
Full Rollout / Rollback
```

1018에서는 다음 질문으로 넘어간다.

**새로운 기능을 적용한 뒤 전환율이 높아졌다면, 정말 그 기능 때문에 좋아진 것일까?**

### ✅ 2. 단순 전후 비교의 문제

예를 들어 신규 신청 모달을 개발했다고 하자.

| 구분 | 기존 모달 | 신규 모달 |
|---|---:|---:|
| 방문자 | 1,000명 | 1,000명 |
| 신청 완료 | 100명 | 120명 |
| 완료율 | 10% | 12% |

표면적으로는 다음과 같다.

- 절대 개선: +2%p
- 상대 개선: +20%

하지만 실제로 신규 모달을 배포한 날에 아이폰 사전예약이 시작됐다면 어떨까?

신청 완료율 상승은 UI 개선이 아니라 구매 의향이 높은 고객의 유입 때문일 수 있다.

### ✅ 3. Correlation과 Causation

Correlation은 두 현상이 함께 나타난다는 뜻이다.

```text
신규 모달 배포
       ↓
신청 완료율 상승
```

Causation은 새로운 기능이 실제로 결과에 영향을 주었다는 뜻이다.

```text
신규 모달 적용
       ↓
다른 조건이 비교 가능하다는 전제
       ↓
신청 완료율 상승
```

실험의 핵심은 단순한 상관관계를 넘어 인과효과를 추정하는 것이다.

### ✅ 4. 실험하지 않고 전후 비교하면 발생하는 문제

```text
배포 전
일반적인 평일
광고비 30만 원
완료율 8%

배포 후
신제품 사전예약
광고비 100만 원
완료율 14%
```

이런 상황에서 UI 개선만으로 완료율이 75% 증가했다고 주장할 수 없다.

광고비, 상품, 고객 구성, 시즌 효과가 모두 달라졌기 때문이다.

### ✅ 5. A/B Test의 기본 원리

같은 시점에 사용자를 무작위로 두 그룹에 배정한다.

```text
전체 실험 대상
       ↓
  Randomization
       ↓
 ┌───────────────┐
 │               │
Control       Treatment
기존 기능      신규 기능
 │               │
 └───────┬───────┘
         ↓
   동일한 지표 비교
         ↓
 데이터 신뢰성 검사
         ↓
    통계적 분석
         ↓
     최종 판단
```

### ✅ 6. Randomization의 효과

제대로 된 무작위 배정은 다음 특성을 두 그룹에 평균적으로 균형 있게 분포시키는 데 도움이 된다.

```text
네이버 광고 유입

직접 유입

신규 고객

재방문 고객

모바일 사용자

PC 사용자

상품 구매 의향
```

다만 표본이 작으면 우연한 불균형은 여전히 발생할 수 있다.

### ✅ 7. A/B Test가 모든 것을 해결하는 것은 아니다

실험 과정에서 다음 문제가 발생하면 결과가 왜곡될 수 있다.

```text
잘못된 사용자 배정

중복 사용자 집계

한 그룹의 Tracking 유실

실험 도중 Variant 변경

부정확한 전환 지표

통계적 표본 부족

여러 지표 중 유리한 것만 선택
```

따라서 실험의 설계와 데이터 수집 체계를 모두 검증해야 한다.

## 2. Experiment Design — 실험 설계

### ✅ 8. 먼저 가설을 정의한다

예:

**신규 신청 모달에서 입력 단계를 줄이면 기존 모달보다 신청 완료율이 증가할 것이다.**

이 문장은 다음을 명확하게 포함한다.

```text
변경 대상
신청 모달

변경 내용
입력 단계 간소화

예상 결과
신청 완료율 증가
```

### ✅ 9. 실험 목적이 모호하면 안 된다

나쁜 예:

```text
신규 모달이 더 좋은지 알아보자.
```

좋은 예:

```text
신청 절차를 5단계에서 3단계로 줄였을 때
사용자당 신청 완료율이 개선되는지 검증한다.
```

### ✅ 10. Experiment Definition

실험 시작 전에 다음 항목을 정의한다.

```text
Experiment ID

Hypothesis

Control

Treatment

Target Population

Randomization Unit

Primary Metric

Secondary Metrics

Guardrail Metrics

Minimum Detectable Effect

Required Sample Size

Conversion Window

Experiment Duration

Stopping Rule

Success Criteria
```

### ✅ 11. Control

기존 기능을 경험하는 그룹이다.

```text
CONTROL

기존 신청 모달
```

### ✅ 12. Treatment

개선된 기능을 경험하는 그룹이다.

```text
TREATMENT

신규 신청 모달
```

### ✅ 13. Primary Metric

실험 성공을 판단하는 핵심 지표다.

예:

```text
application_completion_rate
```

처음에는 핵심 지표 하나로 시작하는 것이 좋다.

### ✅ 14. Secondary Metric

Primary Metric을 보완하는 지표다.

```text
신청서 작성 시간

필수 입력 오류율

신청 과정 이탈률

상담 연결 비율
```

### ✅ 15. Guardrail Metric

신규 기능이 다른 업무를 망가뜨리지 않는지 확인한다.

예:

```text
중복 주문 발생률

잘못된 신청 정보

주문 생성 실패율

프론트엔드 오류율

고객 문의 증가
```

### ✅ 16. Primary Metric 개선만으로 성공은 아니다

예:

```text
신청 완료율
10% → 14%

중복 주문
0.1% → 3%
```

이라면 신청 완료율은 증가했지만 심각한 운영 문제가 발생한 것이다.

### ✅ 17. 실험 성공의 기본 조건

```text
Primary Metric 개선 근거
          +
데이터 품질 정상
          +
Guardrail 위반 없음
          +
업무적으로 의미 있는 효과
```

를 함께 확인한다.

### ✅ 18. Experiment Eligibility

누가 실험에 참여할 수 있는지 정의한다.

예:

```text
일반 방문자

신청 가능한 상품 진입

지원되는 브라우저

실험 대상 화면 접근
```

### ✅ 19. 제외 대상

```text
개발자 테스트 계정

내부 관리자

자동화 Bot

명시적으로 지원되지 않는 환경
```

등을 사전에 정의한다.

### ✅ 20. 실험 결과를 보고 대상을 변경하지 않는다

예를 들어 Treatment의 결과가 좋지 않다고 특정 브라우저 사용자를 뒤늦게 제외하면 결과가 왜곡될 수 있다.

필요하다면 새로운 실험 버전으로 분리한다.

## 3. Randomization — 사용자 배정

### ✅ 21. Randomization Unit

사용자를 어떤 기준으로 배정할지 정한다.

```text
User

Anonymous Visitor

Session

Application Journey
```

### ✅ 22. 방문자 기준 배정

예:

```text
Visitor A
CONTROL

Visitor B
TREATMENT

Visitor C
CONTROL
```

### ✅ 23. Session 기준 배정

한 세션에서는 같은 기능을 제공하지만 새로운 세션에서는 다른 Variant에 배정될 수 있다.

실험 목적에 따라 적절할 수도 있지만 장기간 반복 사용 기능에는 부적합할 수 있다.

### ✅ 24. IP 기반 배정은 피한다

다른 사용자가 같은 공인 IP를 사용하는 경우가 많다.

```text
회사 Wi-Fi

가정용 공유기

이동통신 NAT
```

때문이다.

### ✅ 25. 전화번호도 실험 ID로 사용하지 않는다

개인정보를 불필요하게 사용하는 데다 신청 이전에는 확보할 수 없는 값일 수 있다.

### ✅ 26. Sticky Assignment

같은 사용자에게 동일한 Variant를 유지하는 방식이다.

```text
Experiment ID
      +
Stable Subject ID
      ↓
Deterministic Hash
      ↓
Bucket
      ↓
CONTROL / TREATMENT
```

### ✅ 27. 잘못된 무작위 배정

```typescript
const variant =
  Math.random() < 0.5
    ? 'CONTROL'
    : 'TREATMENT';
```

이를 매 요청마다 실행하면 사용자의 Variant가 계속 변경될 수 있다.

### ✅ 28. 신청 도중 UI 변경 문제

```text
상품 선택
신규 모달

↓

정보 입력
기존 모달

↓

신청 완료
신규 모달
```

과 같은 혼란을 방지해야 한다.

### ✅ 29. Assignment Persistence

배정한 Variant를 안정적으로 유지한다.

예:

```json
{
  "experimentId": "application_modal_v2",
  "subjectKey": "anonymous_123",
  "variant": "TREATMENT",
  "assignmentVersion": 1
}
```

### ✅ 30. Assignment Unique Constraint

다음 조합의 유일성을 보장할 수 있다.

```text
experimentId + subjectKey
```

### ✅ 31. Crossover

동일 사용자가 실험 기간에 Control과 Treatment를 모두 경험하는 것이다.

```text
월요일
CONTROL

수요일
TREATMENT
```

이를 감지하고 실험 분석에 반영해야 한다.

### ✅ 32. Rollout과 Experiment Allocation

다음은 서로 다르다.

```text
Feature Rollout
전체 대상 중 5%에게 신규 기능 공개
```

```text
A/B Allocation
실험 모집단을 50:50으로 분리
```

### ✅ 33. Allocation 변경 시

```text
1일 차
10:90

2일 차
50:50
```

처럼 변경했다면 이력을 기록한다.

변경 전후 데이터를 무조건 하나의 50:50 실험으로 취급해서는 안 된다.

## 4. A/A Test — 실험 측정 시스템 검증

### ✅ 34. A/A Test란?

서로 다른 두 그룹에 동일한 기능을 제공하는 실험이다.

```text
Randomization
       ↓
 ┌───────────────┐
 │               │
Group A         Group A'
기존 모달        기존 모달
 │               │
 └───────┬───────┘
         ↓
    데이터 비교
```

### ✅ 35. 목적

A/A 테스트는 다음을 검증한다.

```text
Assignment

Exposure Logging

Tracking Event

Identity Mapping

Metric Calculation

Analysis Pipeline
```

### ✅ 36. 결과가 정확히 같아야 할까?

아니다.

동일한 기능을 제공해도 표본의 우연한 변동으로 두 그룹의 수치가 달라질 수 있다.

### ✅ 37. 이상 사례

```text
Assignment

CONTROL
1,000명

A'
700명
```

이라면 배정이나 집계에 문제가 있는지 확인해야 한다.

### ✅ 38. Exposure 유실

```text
실제 Assignment
500 : 500

Exposure Event
500 : 350
```

이라면 이벤트 수집 과정의 문제일 수 있다.

### ✅ 39. A/A에서 확인할 것

```text
배정 비율

중복 사용자

Variant Crossover

노출 이벤트 누락

Tracking 누락률

Metric 집계 일관성
```

### ✅ 40. A/A 통과 이후에도 검증은 계속된다

실제 신규 기능에서만 발생하는 JavaScript 오류나 이벤트 유실은 A/A 단계에서 발견되지 않을 수도 있다.

## 5. SRM — Sample Ratio Mismatch

### ✅ 41. SRM의 의미

설정한 그룹 비율과 관측된 그룹 비율이 우연한 변동으로 보기 어려울 만큼 다른 현상이다.

```text
Expected
50 : 50

Observed
60 : 40
```

### ✅ 42. 모든 차이가 오류는 아니다

```text
전체 대상
20명

CONTROL
11명

TREATMENT
9명
```

은 정상적인 50:50 무작위 배정에서도 발생할 수 있다.

### ✅ 43. Chi-square Test

SRM을 확인하는 대표적 방법이다.

```text
χ² = Σ((Observed - Expected)² / Expected)
```

### ✅ 44. 예시

```text
Total
10,000명

Expected
5,000 / 5,000

Observed
5,300 / 4,700
```

이라면 카이제곱 검정을 통해 비율 차이를 평가한다.

### ✅ 45. SRM 원인

```text
Hash Algorithm 오류

사용자 ID 변경

Tracking Event 누락

특정 Variant의 Crash

Bot Filtering 차이

Allocation 설정 변경

중복 사용자 집계

잘못된 SQL JOIN
```

### ✅ 46. Assignment SRM

실제 배정 자체의 비율이 예상과 다른 문제다.

### ✅ 47. Exposure SRM

배정은 정상인데 실제 노출 기록의 비율이 다른 문제다.

예:

```text
Assignment
50:50

Exposure
50:30
```

### ✅ 48. 원인 탐색 순서

```text
Eligibility
     ↓
Assignment
     ↓
Exposure
     ↓
Event Ingestion
     ↓
Metric Aggregation
```

어느 단계부터 차이가 발생했는지 확인한다.

### ✅ 49. SRM을 발견하면?

```text
실험 신뢰성 경고

↓

배정 로직 확인

↓

이벤트 유실 확인

↓

집계 오류 확인

↓

원인 수정

↓

재실험 여부 결정
```

### ✅ 50. SRM을 임의로 보정하지 않는다

두 그룹의 비율이 다르다고 데이터를 삭제해 숫자를 맞추면 안 된다.

먼저 근본 원인을 찾아야 한다.

## 6. Metric Definition — 지표 정의

### ✅ 51. 신청 완료율에는 여러 정의가 있다

예:

```text
신청 완료 사용자 수
/
실험 배정 사용자 수
```

또는:

```text
신청 완료 건수
/
신청 버튼 클릭 수
```

이다.

두 값은 서로 다른 의미를 가진다.

### ✅ 52. 사용자 기준과 주문 건수 기준 구분

한 명의 사용자가 주문 3건을 생성했다고 하자.

사용자당 전환 여부를 측정하면:

```text
Converted
1
```

주문 수를 측정하면:

```text
Order Count
3
```

이다.

### ✅ 53. 신청 단계 구분

온라인 판매몰에서는 다음이 서로 다른 상태일 수 있다.

```text
홈페이지 접수

공식 신청서 작성

관리자 접수 확인

실제 개통 완료
```

### ✅ 54. Funnel 정의

```text
Eligible
   ↓
Modal Open
   ↓
Form Started
   ↓
Submit Attempted
   ↓
Order Created
   ↓
Application Completed
```

### ✅ 55. Primary Metric 정의 예시

```yaml
metric: application_completion_rate
version: 1

unit: eligible_assigned_subject

numerator:
  unique_subjects_with_completed_application

denominator:
  eligible_assigned_subjects

conversion_window:
  days: 7

timezone: UTC
```

### ✅ 56. Conversion Window

실험 배정 후 얼마의 기간 안에 전환을 인정할지 정한다.

예:

```text
10월 10일
실험 배정

10월 13일
신청 완료
```

이 경우 7일 Conversion Window라면 전환으로 인정될 수 있다.

### ✅ 57. Matured Cohort

관측 기간이 충분히 끝난 사용자 집단이다.

```text
Assigned
10월 1일

Analysis
10월 10일

Conversion Window
7일

Matured
YES
```

## 7. Statistical Significance — 통계적 유의성

### ✅ 62. 기본 데이터

```text
CONTROL
100 / 1,000
전환율 10%

TREATMENT
120 / 1,000
전환율 12%
```

### ✅ 63. Absolute Lift

```text
12% - 10%
=
+2%p
```

### ✅ 64. Relative Lift

```text
(12% - 10%) / 10% × 100
=
+20%
```

### ✅ 65. 숫자 표현 주의

다음처럼 작성한다.

```text
전환율

10% → 12%

절대 증가
+2%p

상대 증가
+20%
```

### ✅ 66. 신뢰구간

독립적인 두 집단의 전환율 차이에 대한 간단한 정규근사는 다음과 같다.

```text
Delta = pT - pC

SE ≈ sqrt(
  pT × (1 - pT) / nT
  +
  pC × (1 - pC) / nC
)

95% CI ≈ Delta ± 1.96 × SE
```

작은 표본이나 극단적인 전환율에서는 더 적절한 추정 방법을 검토한다.

### ✅ 67. 각 그룹 1,000명

```text
CONTROL
100 / 1,000

TREATMENT
120 / 1,000

Observed Lift
+2%p
```

근사 95% 신뢰구간:

```text
-0.74%p ~ +4.74%p
```

0을 포함하므로 개선이 확실하다고 결론 내리기 어렵다.

### ✅ 68. 각 그룹 5,000명

```text
CONTROL
500 / 5,000

TREATMENT
600 / 5,000
```

근사 95% 신뢰구간:

```text
+0.77%p ~ +3.23%p
```

같은 차이라도 더 많은 표본으로 관측했기 때문에 불확실성이 줄어든다.

### ✅ 69. p-value

귀무가설이 참이라는 가정하에 현재 관측한 것만큼 또는 더 극단적인 결과가 나타날 확률이다.

### ✅ 70. 흔한 오해

```text
p = 0.03
```

이라고:

```text
신규 기능이 더 좋을 확률
97%
```

라는 뜻은 아니다.

### ✅ 71. Statistical Significance

통계적으로 관측된 차이가 귀무가설과 양립하기 어려운지를 판단한다.

### ✅ 72. Practical Significance

실제 비즈니스에서 의미 있는 개선인지 판단한다.

예:

```text
10.00% → 10.05%
```

가 통계적으로 유의하더라도 운영 비용과 구현 복잡도를 고려하면 실질적인 가치가 작을 수 있다.


를 함께 고려한다.

### ✅ 119. Conversion 집계 SQL

`orders.experiment_subject_key`, `orders.submitted_at` 등이 존재한다고 가정한 설명용 예시다.

```sql
WITH matured_assignments AS (
  SELECT
    experiment_id,
    subject_key,
    variant,
    assigned_at

  FROM experiment_assignments

  WHERE experiment_id = 'application_modal_v2'

    AND assigned_at <=
      TIMESTAMPTZ '2026-10-16 00:00:00+00'
      - INTERVAL '7 days'
),

subject_outcomes AS (
  SELECT
    a.subject_key,
    a.variant,

    EXISTS (
      SELECT 1
      FROM orders o

      WHERE o.experiment_subject_key = a.subject_key

        AND o.submitted_at >= a.assigned_at

        AND o.submitted_at <
          a.assigned_at + INTERVAL '7 days'
    ) AS converted

  FROM matured_assignments a
)

SELECT
  variant,

  COUNT(*) AS assigned_subjects,

  COUNT(*) FILTER (
    WHERE converted
  ) AS converted_subjects,

  ROUND(
    COUNT(*) FILTER (
      WHERE converted
    )::numeric
    / NULLIF(COUNT(*), 0),
    4
  ) AS conversion_rate

FROM subject_outcomes

GROUP BY variant;
```

## 17. Experiment Decision

### ✅ 129. 실험 결과 상태

```text
IMPROVEMENT_SUPPORTED

NO_CLEAR_DIFFERENCE

GUARDRAIL_FAILED

INSUFFICIENT_DATA

INVALID_EXPERIMENT

MANUAL_REVIEW_REQUIRED
```

### ✅ 130. IMPROVEMENT_SUPPORTED

사전에 정의한 기준에서 개선 근거가 있고 필수 Guardrail이 정상인 상태다.

### ✅ 131. NO_CLEAR_DIFFERENCE

명확한 차이를 확인하지 못한 상태다.

두 기능이 동일하다고 확정한 것은 아니다.

### ✅ 132. INSUFFICIENT_DATA

표본이나 관측 기간이 부족한 상태다.

### ✅ 133. INVALID_EXPERIMENT

잘못된 배정, 심각한 SRM, Metric 누락 등으로 실험 결과를 신뢰할 수 없는 상태다.

### ✅ 134. GUARDRAIL_FAILED

예:

```text
신청 완료율
+2%p

중복 주문률
급증
```

이라면 기능 확대를 중단할 수 있다.

### ✅ 135. Rollout 결정은 별도로 수행한다

실험 결과가 개선을 지지하더라도 Production 전체 공개까지 자동으로 실행하지 않는다.


```text

10%

12%
```

```text
      ↓

      ↓

      ↓

      ↓
Statistical Analysis
      ↓
Business Guardrail
      ↓
Decision
      ↓

      ↓
Experiment Report
```

현재 투게더몰과 같은 환경에서는 **신규 신청 모달 한 개를 대상으로 정확한 실험 체계를 만드는 것**부터 시작하는 것이 가장 현실적이다.

기존 NestJS·PostgreSQL·Feature Flag·Audit 구조를 활용하면 별도의 대규모 Experiment Platform 없이도 시작할 수 있다.

**결국 데이터 기반 의사결정이란 숫자를 비교하는 것이 아니라, 그 숫자가 신뢰할 수 있는 과정에서 만들어졌는지 검증한 뒤 불확실성과 업무 위험까지 고려해 판단하는 것이다.**
