## 1012 운영 자동화/AI 워크플로우 심화 (36/N): Data Integrity, Consistency Audit, Business Invariants와 Automated Repair

## 1. 데이터가 존재한다는 것과 올바르다는 것은 다르다

### ✅ 1. Database가 정상이라고 데이터까지 정상인 것은 아니다

예를 들어 다음 상태라고 하자.

```text
PostgreSQL
HEALTHY

NestJS API
200 OK

RDS Backup
SUCCESS
```

서버와 DB는 정상이다.

그런데 실제 주문 데이터에는 다음 문제가 발생할 수 있다.

```text
주문 현재 상태
COMPLETED

마지막 상태 변경 이력
WAITING

알림톡 발송 이력
SUCCESS

실제 Provider 발송 상태
UNKNOWN
```

각 테이블에 데이터가 존재하더라도 서로 의미가 맞지 않는다.

따라서:

**시스템 가용성과 데이터 정합성은 별도로 관리해야 한다.**

### ✅ 2. Data Integrity란?

데이터가 정해진 규칙을 지키며 정확하고 일관된 상태를 유지하는 특성이다.

대표적으로:

```text
Structural Integrity
구조적 무결성

Referential Integrity
참조 무결성

Business Integrity
업무 규칙의 무결성

Cross-system Consistency
시스템 간 상태 일치
```

로 나누어 생각할 수 있다.

### ✅ 3. 구조적 무결성

예:

```text
Order ID
필수

Status
허용된 값

CreatedAt
유효한 날짜
```

처럼 필드 자체가 유효해야 한다.

PostgreSQL에서는 `NOT NULL`, `CHECK`, 타입 제약 등을 활용한다.

### ✅ 4. 참조 무결성

예:

```text
NotificationJob
orderId = 123
```

인데:

```text
Order 123
존재하지 않음
```

이라면 참조 문제가 된다.

외래 키(Foreign Key)는 이러한 문제를 데이터베이스 차원에서 예방하는 대표적인 장치다.

### ✅ 5. 업무 무결성

구조와 참조가 모두 정상이어도 업무 규칙이 틀릴 수 있다.

예:

```text
Order
CANCELLED

NotificationJob
ORDER_COMPLETED 발송 대기
```

이런 상태가 무조건 오류인지는 실제 정책에 따라 다르지만, 확인할 가치가 높은 불일치 후보다.

### ✅ 6. 시스템 간 정합성

예:

```text
우리 DB
NotificationJob = FAILED

외부 Provider
Message = ACCEPTED
```

일 수 있다.

네트워크 Timeout이나 응답 유실로 인해 DB와 외부 시스템의 관측 상태가 달라진 것이다.

이 문제는 DB 제약조건만으로 해결할 수 없다.

## 2. Business Invariant — 항상 지켜야 하는 규칙

### ✅ 7. Business Invariant란?

Invariant는 특정 업무에서 반드시 유지해야 하는 조건이다.

예:

```text
하나의 논리적 주문 생성 요청은
중복 주문을 만들면 안 된다.
```

또는:

```text
권한 없는 관리자는
주문 상태를 변경할 수 없다.
```

같은 규칙이다.

다만 업무 정책마다 예외가 있으므로 실제 코드·DB·운영 절차에서 확인한 규칙만 Invariant로 확정한다.

### ✅ 8. 단순 Validation과 Invariant의 차이

Validation:

```text
Status 필드가 비어 있지 않은가?
```

Invariant:

```text
현재 상태에서 다음 상태로
변경하는 것이 허용되는가?
```

이다.

전자는 필드의 유효성이고 후자는 업무의 유효성이다.

### ✅ 9. Order Domain Invariant 후보

예:

```text
ORDER_001
주문 ID는 유일해야 한다.

ORDER_002
존재하지 않는 주문에
알림 Job이 연결돼서는 안 된다.

ORDER_003
허용되지 않은 상태 전이는
실행되면 안 된다.

ORDER_004
동일한 Idempotency Key가
중복 주문을 생성하면 안 된다.
```

실제 프로젝트에 적용하기 전에는 현재 주문 모델과 상태 전이 정책을 확인한다.

### ✅ 10. Status Transition Invariant

예시로 다음 상태 모델이 있다고 하자.

```text
RECEIVED
   ↓
APPLICATION_SENT
   ↓
PROCESSING
   ↓
COMPLETED
```

그리고:

```text
CANCELLED
```

가 있다고 하자.

다음 전이가 항상 가능한 것은 아니다.

```text
CANCELLED
   ↓
COMPLETED
```

이 전이가 허용되는지는 업무 정책에 따라 다르다.

따라서 State Transition Matrix가 필요하다.

### ✅ 11. 상태 전이 규칙은 중앙화한다

예:

```ts
const allowedTransitions = {
  RECEIVED: [
    'APPLICATION_SENT',
    'CANCELLED',
  ],
  APPLICATION_SENT: [
    'PROCESSING',
    'CANCELLED',
  ],
  PROCESSING: [
    'COMPLETED',
    'CANCELLED',
  ],
  COMPLETED: [],
  CANCELLED: [],
};
```

위 코드는 설명용이다.

실제 상태 이름과 허용 전이는 현행 업무 프로세스를 기준으로 정의한다.

### ✅ 12. Invariant는 변경될 수도 있다

업무 정책이 바뀌면:

```text
Rule Version
v1 → v2
```

가 될 수 있다.

따라서 과거 데이터가 현재 규칙과 다르다고 해서 무조건 손상된 데이터는 아니다.

### ✅ 13. Rule Version이 중요한 이유

예:

```text
2026년 8월
취소 후 재접수 불가

2026년 10월
일부 조건에서 재접수 허용
```

이라고 하자.

과거 데이터를 최신 상태 전이 규칙으로 검사하면 잘못된 오류가 발생할 수 있다.

그래서 검증 규칙에는 적용 시작 시점과 버전을 관리할 수 있다.

### ✅ 14. Invariant Registry

예:

```ts
interface IntegrityRule {
  id: string;
  version: number;
  domain: string;
  severity: 'CRITICAL' | 'HIGH' | 'MEDIUM' | 'LOW';
  enabled: boolean;
  gracePeriodMs?: number;
}
```

처럼 정의할 수 있다.

처음부터 DB에 별도 Rule Engine을 만들 필요는 없다.

정적 코드 Registry부터 시작하는 편이 단순하다.

## 3. 현재 상태와 이력의 정합성

### ✅ 15. Order와 OrderStatusHistory

다음 두 데이터를 관리한다고 가정하자.

```text
orders

order_status_histories
```

주문 상태가 변경될 때:

```text
Order.status
```

와:

```text
OrderStatusHistory
```

가 일치해야 한다.

### ✅ 16. 잘못된 구현

```text
1. orders.status UPDATE
   SUCCESS

2. status_history INSERT
   FAILED
```

이렇게 되면 현재 상태는 바뀌었지만 이력이 없다.

### ✅ 17. Transaction으로 예방한다

```ts
await prisma.$transaction(async (tx) => {
  await tx.order.update({
    where: { id: orderId },
    data: { status: nextStatus },
  });

  await tx.orderStatusHistory.create({
    data: {
      orderId,
      previousStatus,
      nextStatus,
    },
  });
});
```

위 예시는 기본적인 원자성 설명용이다.

실제 구현에는 다음도 필요할 수 있다.

```text
권한 검증

허용된 상태 전이

동시성 제어

Version Check

Audit
```

### ✅ 18. Transaction이 해결하는 것과 해결하지 못하는 것

Transaction은 같은 DB 트랜잭션 안에 포함된 변경을 원자적으로 처리한다.

하지만:

```text
DB UPDATE

+

외부 알림톡 발송
```

을 하나의 일반 PostgreSQL Transaction으로 묶을 수 있는 것은 아니다.

그래서 Outbox와 Reconciliation이 필요하다.

### ✅ 19. 현재 상태와 마지막 이력 비교

예를 들어 다음과 같은 데이터가 있다고 하자.

```text
orders

id
status
```

```text
order_status_histories

id
order_id
previous_status
next_status
changed_at
```

상태가 변경될 때마다 이력이 반드시 기록되는 정책이라면 마지막 이력과 현재 상태를 비교할 수 있다.

### ✅ 20. PostgreSQL 검증 쿼리

```sql
SELECT
  o.id,
  o.status AS current_status,
  h.next_status AS last_history_status
FROM orders o
JOIN LATERAL (
  SELECT next_status
  FROM order_status_histories
  WHERE order_id = o.id
  ORDER BY changed_at DESC, id DESC
  LIMIT 1
) h ON TRUE
WHERE o.status IS DISTINCT FROM h.next_status
LIMIT 100;
```

`IS DISTINCT FROM`은 `NULL`을 포함한 차이도 명확하게 비교할 때 유용하다.

다만 이 쿼리에는 조건이 있다.

- 모든 상태 변경이 이력에 기록돼야 한다.
- 이력의 순서가 정확해야 한다.
- 초기 생성 상태에 대한 정책이 있어야 한다.
- 주문과 이력을 일관된 시점에서 읽어야 한다.

실제 테이블과 컬럼명은 현재 Prisma Schema에 맞춰 변경한다.

### ✅ 21. 마지막 이력이 없다고 무조건 오류는 아니다

예:

```text
Order 생성
status = RECEIVED

아직 상태 변경 없음
```

이라면 이력이 없는 것이 정상일 수 있다.

초기 주문 생성 이력까지 저장하는 정책인지 확인해야 한다.

### ✅ 22. 이력은 단순 현재 상태의 복사본이 아니다

상태 변경 이력에는:

```text
누가

언제

어떤 이유로

어떤 상태에서

어떤 상태로
```

변경했는지가 들어갈 수 있다.

이걸 현재 상태만 보고 임의로 재생성해서는 안 된다.

### ✅ 23. 누락된 Audit을 조작해서 메우지 않는다

예:

```text
주문 현재 상태
COMPLETED

상태 변경 이력
없음
```

이라고 하자.

여기서 자동으로:

```text
과거에 관리자가
COMPLETED로 변경한 것처럼
이력 생성
```

하면 실제로 확인되지 않은 사건을 만들어내는 것이다.

따라서:

```text
HISTORY_MISSING
```

으로 표시하고 확인된 사실만 별도 복구 기록에 남겨야 한다.

## 4. 중복과 참조 무결성

### ✅ 24. Duplicate는 업무마다 의미가 다르다

예를 들어:

```text
동일 이름
동일 연락처
```

로 신청했다고 해서 무조건 중복 주문은 아니다.

동일 고객이 다른 기기를 신청하거나 기존 주문을 취소한 뒤 재신청할 수도 있다.

### ✅ 25. Business Duplicate와 Technical Duplicate를 구분한다

Technical Duplicate:

```text
같은 Idempotency Key로
동일한 논리적 생성 요청이
두 번 처리됨
```

Business Duplicate Candidate:

```text
동일 고객으로 보이는
여러 주문이 존재
```

이다.

첫 번째는 기술적 규칙으로 강하게 막을 수 있다.

두 번째는 업무 검토가 필요하다.

### ✅ 26. PostgreSQL Unique Constraint

동일한 생성 요청의 중복을 막는 데 유용하다.

예:

```sql
CREATE UNIQUE INDEX
  orders_request_key_unique
ON orders (request_key);
```

위 예시는 하나의 `request_key`가 하나의 주문만 생성해야 한다는 정책이 있을 때 적용한다.

이미 중복 데이터가 존재하면 인덱스 생성이 실패할 수 있으므로 먼저 검증해야 한다.

### ✅ 27. Partial Unique Index

상태 등 특정 조건에만 유일성을 강제하는 경우 PostgreSQL의 Partial Unique Index를 검토할 수 있다.

다만:

```text
같은 고객은
활성 주문을 한 개만 가질 수 있다
```

같은 규칙은 통신사·개통번호·주문 유형 등에 따라 잘못된 제한일 수 있다.

업무 규칙이 명확하지 않다면 Unique Index를 만들지 않는다.

### ✅ 28. Foreign Key 검증

예:

```sql
SELECT n.id, n.order_id
FROM notification_jobs n
LEFT JOIN orders o
  ON o.id = n.order_id
WHERE o.id IS NULL
LIMIT 100;
```

이 쿼리는 연결되지 않은 주문 참조가 있는지 확인하는 예시다.

이미 유효한 Foreign Key 제약이 있다면 이러한 상태를 DB 차원에서 예방할 수 있다.

### ✅ 29. Soft Delete를 고려한다

주문이 Soft Delete됐다면:

```text
orders.deleted_at
값 존재
```

한다고 해서 반드시 참조가 깨진 것은 아니다.

따라서:

```text
DB Reference Missing
```

과:

```text
Referenced Order Soft Deleted
```

를 구분한다.

### ✅ 30. Orphan Data 자동 삭제는 위험하다

예:

```text
NotificationJob

연결된 Order 없음
```

이라고 해당 Job을 즉시 삭제하지 않는다.

원인은 다음 중 하나일 수 있다.

```text
과거 Migration

데이터 복구 중 누락

Soft Delete 정책

이전 Version의 Schema

실제 손상
```

확인 후 처리한다.

## 5. Current State와 Derived State

### ✅ 31. 모든 데이터가 Source of Truth인 것은 아니다

예:

```text
orders
원본 주문 데이터
```

```text
daily_order_stats
주문 집계 데이터
```

라고 하자.

일반적으로 주문 원본에서 집계를 다시 계산할 수 있다면 후자는 Derived Data다.

### ✅ 32. Derived Data는 복구가 상대적으로 쉽다

예:

```text
오늘 주문 수
123

집계 테이블
121
```

이면 원본 주문 데이터가 신뢰 가능하다는 전제에서 재집계할 수 있다.

### ✅ 33. 하지만 집계 기준이 동일해야 한다

예:

```text
오늘 주문 수
```

라는 값도 기준에 따라 달라진다.

```text
createdAt 기준?

submittedAt 기준?

취소 주문 포함?

중복 신청 제외?

Asia/Seoul 기준?
```

정의가 다르면 서로 다른 값이 모두 정상일 수 있다.

### ✅ 34. Metric Definition을 고정한다

예:

```text
Metric
daily_submitted_orders

Timezone
Asia/Seoul

Date Field
submittedAt

Cancellation
포함

Version
v1
```

처럼 정의한다.

### ✅ 35. Watermark

데이터를 어느 시점까지 검사했는지 표시한다.

예:

```text
watermarkAt
2026-10-12 00:00:00 KST
```

이라고 하자.

검증 대상은 이 시점까지의 데이터로 제한한다.

### ✅ 36. Watermark가 없으면 거짓 불일치가 발생할 수 있다

예:

```text
10:00:00
집계 조회

10:00:01
새 주문 생성

10:00:02
원본 DB 조회
```

원본과 집계의 조회 시점이 다르므로 값이 어긋날 수 있다.

이걸 오류라고 단정하면 안 된다.

### ✅ 37. Snapshot Consistency

여러 Query를 논리적으로 같은 시점에서 비교해야 한다면 PostgreSQL의 `REPEATABLE READ` 같은 트랜잭션 격리 수준을 검토할 수 있다.

다만 장시간 트랜잭션은 DB에 부담을 줄 수 있으므로 큰 데이터 검증에서는 짧은 배치, 고정 Watermark, 데이터 Version 또는 별도 검증 환경을 활용하는 편이 안전할 수 있다.

### ✅ 38. Read Replica Lag도 고려한다

예:

```text
Primary DB
주문 100건

Read Replica
주문 98건
```

일 수 있다.

Replication Lag 때문에 생긴 차이를 데이터 손상으로 오인하면 안 된다.

중요한 검증에서는 Primary와 Replica의 특성을 고려한다.

### ✅ 39. 집계 복구는 재계산이 기본

```text
Derived Data Mismatch

↓

Source 검증

↓

Recalculate

↓

Compare

↓

Replace
```

방식이 적합하다.

하지만 원본 자체가 손상됐다면 Derived Data를 다시 계산해도 잘못된 값만 생성한다.

### ✅ 40. Cache도 Derived Data다

1004와 연결된다.

```text
PostgreSQL
Source of Truth

Redis
Cache
```

라면 Cache 불일치 발생 시:

```text
Cache Invalidate

↓

Source에서 Rebuild
```

방식이 기본이다.

Cache 값을 이용해 PostgreSQL 원본을 수정하지 않는다.

## 6. External System Reconciliation

### ✅ 41. 외부 시스템과 상태가 다른 것은 항상 장애가 아니다

예:

```text
NotificationJob
PROCESSING

Provider
ACCEPTED
```

가 잠깐 발생할 수 있다.

외부 API 호출과 내부 DB 업데이트 사이에는 시간차가 존재하기 때문이다.

### ✅ 42. Eventual Consistency

한 시스템에서 변경된 내용이 다른 시스템에 조금 늦게 반영되는 특성이다.

따라서 다음 질문이 중요하다.

```text
얼마나 오래 불일치가
허용 가능한가?
```

### ✅ 43. Grace Period

예:

```text
발송 요청 직후
30초 이내
```

라면 상태 차이를 당장 경고하지 않을 수 있다.

```text
30초 초과
검증 대상
```

으로 설정할 수 있다.

정확한 유예 시간은 실제 Provider의 처리 특성을 측정해 결정한다.

### ✅ 44. Notification 상태를 명확히 구분한다

예:

```text
QUEUED

SENDING

ACCEPTED

DELIVERED

FAILED

UNKNOWN
```

같은 상태를 생각할 수 있다.

여기서:

```text
ACCEPTED
```

는 Provider가 요청을 수락했다는 뜻일 수 있지만:

```text
DELIVERED
```

와 동일한 의미는 아니다.

Provider가 어떤 상태까지 제공하는지 확인해야 한다.

### ✅ 45. Provider 응답 유실

예:

```text
우리 Worker
발송 요청

↓

Provider
요청 수락

↓

Network Timeout

↓

우리 DB
UNKNOWN
```

이 발생할 수 있다.

### ✅ 46. 이 상태에서 바로 재발송하면 위험하다

실제로는 이미 발송됐을 수 있기 때문이다.

따라서:

```text
Provider Message ID

Idempotency Key

Provider 조회 API

Callback

Webhook
```

등을 활용해 확인한다.

### ✅ 47. 외부 Provider가 상태 조회를 지원하지 않는 경우

모든 서비스가 개별 요청 조회 API를 제공하는 것은 아니다.

이 경우:

```text
UNKNOWN

↓

증거 부족

↓

MANUAL_REVIEW
```

가 더 안전할 수 있다.

중복 발송이 고객에게 영향을 주는 경우 무조건 자동 재시도하지 않는다.

### ✅ 48. Webhook과 외부 Event

외부에서 이벤트를 재전송하거나 순서가 바뀌어 도착할 수 있다.

예:

```text
Event A
PROCESSING

Event B
COMPLETED
```

그런데 수신 순서는:

```text
Event B

Event A
```

일 수 있다.

### ✅ 49. 수신 순서와 업무 발생 순서는 다를 수 있다

따라서:

```text
마지막으로 받은 Webhook
=
현재 업무 상태
```

라고 단순하게 판단하지 않는다.

Provider의 이벤트 버전, 발생 시각, Sequence 또는 내부 상태 전이 규칙을 활용한다.

### ✅ 50. Webhook 중복 제거

예:

```text
provider

providerEventId
```

조합이 유일하다면 Unique Constraint를 적용할 수 있다.

단 실제 Provider가 `eventId`의 유일성을 어떻게 보장하는지 확인해야 한다.

### ✅ 51. Outbox와 Inbox 비교

예:

```text
Outbox
ORDER_COMPLETED
Published = TRUE
```

그런데:

```text
Downstream Processing
기록 없음
```

이라면 확인할 가치가 있다.

하지만 Outbox에서 Publish 성공이 Downstream의 업무 처리 성공까지 의미하지는 않는다.

### ✅ 52. 단계별 상태가 필요하다

```text
Outbox Created

↓

Published

↓

Consumer Received

↓

Consumer Processed

↓

Business Applied
```

각 단계는 다른 의미를 가진다.

### ✅ 53. Provider Reconciliation과 Business Reconciliation은 다르다

Provider Reconciliation:

```text
메시지가 실제 발송됐는가?
```

Business Reconciliation:

```text
현재 주문 상태에서
그 메시지가 발송되는 것이
올바른가?
```

다.

메시지가 실제 발송됐어도 업무적으로 잘못된 발송일 수 있다.

## 7. Consistency Audit 설계

### ✅ 54. Consistency Audit란?

정의된 규칙에 따라 데이터를 검사하고 불일치 후보를 기록하는 과정이다.

중요한 것은 단순 SQL 오류 탐지가 아니라 **업무상 의미 있는 차이를 찾는 것**이다.

### ✅ 55. Rule Severity

예:

| 등급 | 예시 | 처리 |
|---|---|---|
| Critical | 주문 ID 중복 생성 확인 | 즉시 조사 |
| High | 주문 상태와 핵심 이력 불일치 | 빠른 검토 |
| Medium | 알림 Provider 상태 확인 지연 | 재조회 |
| Low | 재생성 가능한 집계값 불일치 | 재집계 후보 |

실제 Severity는 발생 건수와 고객 영향에 따라 달라질 수 있다.

### ✅ 56. Audit Finding

불일치 발견 결과를 Finding으로 저장한다.

예:

```json
{
  "ruleId": "ORDER_STATUS_HISTORY_MISMATCH",
  "ruleVersion": 1,
  "resourceType": "ORDER",
  "resourceId": "order_123",
  "severity": "HIGH",
  "status": "OPEN"
}
```

### ✅ 57. Finding은 원본 데이터와 분리한다

예:

```text
orders

order_status_histories

integrity_findings
```

로 분리한다.

불일치를 발견했다고 원본 테이블에 바로 수정 플래그를 무분별하게 추가하지 않는다.

### ✅ 58. Finding에 필요한 정보

예:

```text
Finding ID

Rule ID / Version

Resource Type / ID

Detected At

Observed Version

Expected State

Actual State

Evidence Reference

Severity

Status
```

다만 민감한 데이터 원문을 중복 저장하지 않도록 한다.

### ✅ 59. Finding Lifecycle

```text
OPEN

↓

INVESTIGATING

↓

REPAIR_PROPOSED

↓

APPROVED

↓

REPAIRED

↓

VERIFIED

↓

CLOSED
```

또는:

```text
FALSE_POSITIVE

WAIVED

MANUAL_REQUIRED
```

등이 있을 수 있다.

### ✅ 60. 중복 Finding을 계속 만들면 안 된다

같은 주문에서 같은 문제가 1시간마다 발견된다고 하자.

```text
10:00
Finding #1

11:00
Finding #2

12:00
Finding #3
```

이렇게 무한 생성하면 관리하기 어렵다.

### ✅ 61. Finding Fingerprint

예:

```text
ruleId

ruleVersion

resourceType

resourceId
```

를 기준으로 활성 Finding을 하나만 유지할 수 있다.

다만 같은 문제가 해결된 뒤 다시 발생하면 새로운 발생으로 기록할 수 있어야 한다.

### ✅ 62. Finding의 재확인

검사 시 다시 정상으로 확인됐다고 무조건 과거 Finding을 삭제하지 않는다.

```text
Finding
OPEN

↓

재검사

↓

현재 정상

↓

RESOLVED / VERIFIED
```

처럼 이력을 남긴다.

### ✅ 63. False Positive

불일치가 발견됐지만 실제로는 정상인 경우다.

예:

```text
상태 변경 이력이 없음
```

하지만:

```text
해당 주문은 초기 생성 후
상태 변경이 없었음
```

이면 정상일 수 있다.

### ✅ 64. False Positive 비율도 중요한 Metric

검사 결과의 대부분이 정상 데이터라면 운영자가 알림을 무시하게 될 수 있다.

따라서 Rule을 개선해야 한다.

## 8. 검증 시점과 Scan 전략

### ✅ 65. 모든 데이터를 매분 검사할 필요는 없다

현재 주문이 수십만 건이라고 하자.

```text
매분

전체 주문

전체 상태 이력

전체 알림 이력
```

을 JOIN한다면 DB에 부담이 될 수 있다.

### ✅ 66. 검사를 세 종류로 나눈다

```text
On-write Validation

Incremental Audit

Full Audit
```

이다.

### ✅ 67. On-write Validation

상태 변경 직전에 업무 규칙을 검사한다.

예:

```text
상태 변경 허용 여부

중복 처리 방지

권한 검사
```

이다.

가장 빠르게 오류를 막을 수 있다.

### ✅ 68. Incremental Audit

최근 변경된 데이터만 검사한다.

예:

```text
최근 1시간 동안
상태가 변경된 주문
```

을 대상으로 한다.

### ✅ 69. Full Audit

전체 또는 광범위한 데이터를 검사한다.

다음 경우에 유용하다.

```text
대규모 Migration 이후

DR Restore 이후

새 Invariant 도입

중요 Release 이후

정기적인 전체 검증
```

### ✅ 70. Full Audit은 별도 시간대에 수행할 수 있다

고객이 많이 접속하는 시간에 무거운 검증을 실행하면 서비스 성능에 영향을 줄 수 있다.

따라서:

```text
Batch Size

Query Timeout

Concurrency Limit

Throttle
```

을 정한다.

### ✅ 71. Cursor 기반 Scan

예:

```text
Order ID
1~1000

다음
1001~2000
```

처럼 순서대로 검사한다.

실제 구현에서는 ID 형식과 정렬 기준에 맞게 안정적인 Cursor를 선택한다.

### ✅ 72. Offset Pagination만으로 대량 Scan하면 문제가 생길 수 있다

데이터가 추가되거나 삭제되면 페이지가 밀릴 수 있다.

큰 테이블에서는 안정적인 정렬 키를 이용한 Keyset/Cursor 방식이 유리할 수 있다.

### ✅ 73. Scan Checkpoint

예:

```json
{
  "runId": "audit_run_001",
  "ruleId": "ORDER_HISTORY",
  "cursor": "order_50000",
  "processed": 50000,
  "status": "RUNNING"
}
```

처럼 저장할 수 있다.

### ✅ 74. Scan 중 Process가 죽어도 Resume 가능해야 한다

```text
Audit Started

↓

50,000건 검사

↓

Worker Crash

↓

Checkpoint 확인

↓

다음 Batch부터 재개
```

한다.

### ✅ 75. Cursor만으로 동일 시점 비교가 보장되지는 않는다

Scan 도중 주문이 바뀔 수 있다.

따라서:

```text
Run Watermark

UpdatedAt

Record Version

Snapshot 기준
```

을 함께 고려해야 한다.

### ✅ 76. UpdatedAt만으로 완벽한 변경 추적은 어렵다

모든 Write가 `updatedAt`을 정확하게 갱신하지 않을 수도 있고, 같은 시각에 여러 Row가 변경될 수도 있다.

따라서 증분 검사에 사용할 때는:

```text
updatedAt + id
```

같은 안정적인 정렬 기준과 충분한 재검사 구간을 고려한다.

중요한 경우 별도 변경 이력 또는 이벤트 로그를 활용하는 편이 더 확실할 수 있다.

## 9. Automated Repair — 어디까지 자동으로 고칠 수 있을까?

### ✅ 77. 모든 불일치를 자동 수정하면 안 된다

예:

```text
Order.status
COMPLETED

History
WAITING
```

어느 쪽이 맞는지 알 수 없는 경우가 있다.

따라서:

```text
최근 값으로 무조건 덮어쓰기
```

는 위험하다.

### ✅ 78. Repair Risk Level

자동 복구를 세 단계로 나눌 수 있다.

**Level A — 자동 복구 후보**

```text
Cache Invalidation

검증된 Derived Data 재생성

유실된 임시 집계 Rebuild
```

**Level B — 조건부 자동 복구**

```text
확인된 상태의 Job Metadata 보정

검증된 Event의 안전한 재처리
```

**Level C — 관리자 승인 필수**

```text
Order Status 변경

고객정보 수정

외부 알림 재발송

주문 삭제/복원

데이터베이스 복구
```

### ✅ 79. 자동 복구 판단 기준

최소한 다음을 확인한다.

```text
Source of Truth가 명확한가?

현재 상태를 신뢰할 수 있는가?

복구가 Idempotent한가?

외부 Side Effect가 없는가?

실패 시 Rollback 가능한가?

변경 범위가 제한되어 있는가?
```

### ✅ 80. Safe Repair 예: Cache

예:

```text
Product Cache
오래된 데이터
```

원본 DB가 정상이라는 것이 확인됐다면:

```text
Cache Delete

↓

Next Read Rebuild
```

할 수 있다.

### ✅ 81. Safe Repair 예: Derived Summary

예:

```text
Daily Order Summary
실제 주문 수와 불일치
```

집계 규칙과 검증 시점이 명확하고 원본 데이터가 신뢰 가능하다면 재계산할 수 있다.

다만 계산 이후 원본 데이터가 변경될 수 있으므로 버전·검증 시점·원자적 교체 조건을 고려한다.

### ✅ 82. Dangerous Repair 예: 주문 상태

```text
Order
CANCELLED

History
COMPLETED
```

라면:

```text
History에 맞춰
Order를 COMPLETED로 변경
```

해서는 안 된다.

고객 요청으로 취소됐지만 이력 기록이 누락됐을 수도 있다.

### ✅ 83. Dangerous Repair 예: 알림톡

```text
Notification
UNKNOWN
```

이라고:

```text
무조건 재발송
```

하면 중복 안내가 발생할 수 있다.

### ✅ 84. Repair Plan

수정하기 전에 계획을 만든다.

예:

```json
{
  "findingId": "finding_123",
  "action": "REBUILD_DERIVED_SUMMARY",
  "target": "daily_order_summary",
  "mode": "DRY_RUN",
  "requiresApproval": false
}
```

### ✅ 85. Repair Plan에 Before/After 포함

예:

```text
Target
2026-10-11 Order Summary

Before
120

Expected
123

Change
+3
```

처럼 기록한다.

### ✅ 86. Dry Run

실제 수정 없이 다음을 확인한다.

```text
변경할 Resource 수

변경할 Field

예상 결과

충돌 가능성

외부 Side Effect

Rollback 가능 여부
```

### ✅ 87. Repair 실행 직전 재검증

Dry Run 이후 실제 데이터가 바뀌었을 수 있다.

따라서 실행 직전에:

```text
Current Value

Observed Version

Expected Source State
```

를 다시 검사해야 한다.

### ✅ 88. Optimistic Concurrency Control

예:

```text
Finding 발견 시
Order.version = 12

Repair 실행 시
Order.version = 13
```

이면 누군가 중간에 변경했다는 뜻이다.

이때는 무조건 덮어쓰지 않고:

```text
REVALIDATION_REQUIRED
```

로 처리한다.

### ✅ 89. 조건부 Update

설명용 예시:

```ts
const result = await prisma.someDerivedRecord.updateMany({
  where: {
    id: recordId,
    version: observedVersion,
  },
  data: {
    value: recalculatedValue,
    version: {
      increment: 1,
    },
  },
});

if (result.count !== 1) {
  throw new Error('REVALIDATION_REQUIRED');
}
```

이 방식은 대상 레코드가 바뀌었는지 확인하는 데 도움이 된다.

하지만 원본 집계 대상 데이터까지 변경되지 않았는지 별도 확인해야 한다.

### ✅ 90. Repair Transaction

여러 DB 변경이 하나의 복구 작업이라면 Transaction을 사용할 수 있다.

예:

```text
Derived Summary UPDATE

Repair Audit INSERT

Finding Status UPDATE
```

를 하나로 묶는다.

### ✅ 91. Transaction이 길어지지 않게 한다

대량 복구를 하나의 거대한 Transaction으로 실행하면:

```text
Lock 증가

DB 부하

Rollback 비용

Timeout
```

문제가 생길 수 있다.

따라서 Batch 단위로 처리한다.

### ✅ 92. Repair Idempotency

같은 Repair 요청이 두 번 실행돼도 결과가 중복 적용되지 않아야 한다.

예:

```text
repairPlanId
```

를 Idempotency Key로 활용할 수 있다.

### ✅ 93. Repair 실행 후 반드시 Verify

```text

↓

↓

PASS

↓

Finding Closed
```

이다.

수정 API가 성공했다는 사실만으로 Finding을 닫지 않는다.

### ✅ 94. Verify 실패 시

```text

```

으로 남긴다.

무한 반복해서 자동 수정하지 않는다.

### ✅ 95. Repair Budget

예:


## 12. PostgreSQL 제약조건을 이용한 예방

### ✅ 108. 검사보다 더 좋은 것은 잘못된 데이터가 생성되지 않게 하는 것이다

예:

```text
Integrity Audit
하루 한 번 오류 발견
```

보다는:

```text
DB Constraint
잘못된 Write 즉시 차단
```

이 유리한 경우가 많다.

### ✅ 109. NOT NULL

필수 값 누락 방지.

### ✅ 110. UNIQUE

확정된 유일성 규칙을 DB에서 보장한다.

### ✅ 111. FOREIGN KEY

관련 레코드의 참조 관계를 보장한다.

### ✅ 112. CHECK

하나의 Row에 적용 가능한 조건을 검증한다.

예:

```sql
ALTER TABLE orders
ADD CONSTRAINT orders_valid_amount
CHECK (amount >= 0);
```

단 `amount`가 실제 존재하고 음수가 허용되지 않는 업무 규칙이어야 한다.

### ✅ 113. CHECK가 모든 Business Invariant를 해결하지는 못한다

예:

```text
주문 상태 변경 시
반드시 이력을 기록한다.
```

는 여러 테이블에 걸친 규칙이다.

단순 CHECK 하나로 처리하기 어렵다.

이 경우:

```text
Use Case

Transaction

DB Constraint

Consistency Audit
```

을 조합한다.

### ✅ 114. 기존 테이블에 제약조건 추가

오래된 운영 테이블에는 이미 잘못된 데이터가 있을 수 있다.

PostgreSQL에서는 `CHECK`와 `FOREIGN KEY` 제약에 대해 `NOT VALID`로 추가한 뒤 기존 데이터를 별도로 검증하는 방법을 사용할 수 있다.

예:

```sql
ALTER TABLE orders
ADD CONSTRAINT orders_amount_nonnegative
CHECK (amount >= 0) NOT VALID;
```

이후 기존 데이터를 정리하고:

```sql
ALTER TABLE orders
VALIDATE CONSTRAINT orders_amount_nonnegative;
```

를 수행할 수 있다.

다만 Lock과 테이블 스캔 비용을 검토해야 하며, `NOT VALID`가 모든 제약조건에 적용되는 것은 아니다. 특히 `UNIQUE` 제약에 그대로 적용할 수는 없다.

### ✅ 115. Constraint Migration도 Release Gate 대상

예:

```text
Constraint 추가

↓

기존 데이터와 충돌

↓

Production Migration 실패
```

가 발생할 수 있다.

따라서:

```text
사전 불일치 검사

영향 건수

Migration Plan

Lock Impact

Rollback/Roll-forward Plan
```

이 필요하다.

## 13. Consistency Audit 운영 정책

### ✅ 116. 검사 주기를 위험도별로 구분한다

예:

| 검사 대상 | 운영 주기 예시 |
|---|---|
| 상태 전이 Validation | 변경 시 즉시 |
| 최근 주문 상태/이력 | 10~30분 |
| Notification UNKNOWN | 유예 시간 이후 |
| 주문 집계 | 일 1회 |
| 전체 참조 정합성 | 주간/월간 |
| DR 이후 데이터 검증 | 복구 직후 |

실제 트래픽과 요구사항에 따라 조정한다.

### ✅ 117. Audit 자체에도 Rate Limit이 필요하다

1005에서 다룬 Backpressure를 적용한다.

```text
Audit Job
LOW Priority

DB 부하 높음
→ Pause

업무 Peak
→ Throttle
```

처럼 운영한다.

### ✅ 118. Critical Audit은 별도로 구분한다

예:

```text
주문 생성 중복
```

같은 중요한 오류는 일괄 검사만 기다리지 않도록 On-write Validation과 Alert를 강화한다.

### ✅ 119. Scan이 DB를 압박하면 안 된다

예:

```text
SELECT *
FROM orders;
```

로 전체 데이터를 Application Memory에 올리는 것은 피한다.

필요한 컬럼만 조회하고 Batch 처리한다.

### ✅ 120. Alert 기준

예:

```text
CRITICAL Finding
1건 이상
→ 즉시 확인
```

```text
MEDIUM Finding
지속 증가
→ 운영 검토
```

처럼 정의할 수 있다.

단 단일 False Positive 때문에 모든 알림이 Critical이 되지 않게 한다.

### ✅ 121. Silent Failure

검사 시스템이 조용하다고 데이터가 정상인 것은 아니다.

예:

```text
Integrity Scanner
3일째 실행되지 않음

Finding
0건
```

이라면 문제가 없다는 뜻이 아니다.

따라서:

```text
lastSuccessfulAuditAt

auditDuration

auditFailure

watermarkLag
```

도 확인해야 한다.

### ✅ 122. Finding Metric

예:

```text
integrity_findings_open

integrity_findings_new_total

integrity_findings_resolved_total

integrity_audit_duration

integrity_repair_failed_total

integrity_audit_watermark_lag
```

등을 볼 수 있다.

### ✅ 123. Metric Label은 제한한다

예:

```text
ruleId

severity

status
```

정도를 사용한다.

`orderId`, `customerId` 등을 Metric Label에 넣으면 Cardinality가 지나치게 증가할 수 있다.

### ✅ 139. Consistency Audit 최소 구현 프롬프트

```text
현재 프로젝트에 최소한의
Consistency Audit 구조를 구현해줘.

먼저 기존 코드에서 다음이 존재하는지 확인한다.

- Scheduler
- Queue / Worker
- AuditLog
- Incident
- Notification Reconciliation
- Prisma Transaction
- 기존 Admin Dashboard

이미 존재하는 구조를 우선 재사용한다.

새로운 범용 Data Quality Platform을 만들지 않는다.

요구사항:

1. Business Invariant Registry

Rule마다 다음을 정의한다.

- id
- version
- domain
- severity
- enabled
- gracePeriod

2. Integrity Audit는 기본 Read-only로 실행한다.

3. 첫 Audit Rule은 실제 Schema를 확인한 뒤
다음 후보 중 유효한 것만 선택한다.

- Order Status / History
- NotificationJob / Order 참조
- Technical Duplicate Order

4. Scan은 Batch로 처리한다.

5. Cursor / Checkpoint를 지원한다.

6. Run Watermark를 기록한다.

7. 동일 대상에서 동일 활성 Finding을
무한 생성하지 않는다.

8. Finding에 다음을 기록한다.

- ruleId
- ruleVersion
- resourceType
- resourceId
- severity
- status
- detectedAt
- evidenceRef

9. PII 원문을 중복 저장하지 않는다.

10. 검사 시점 차이로 발생하는
False Positive를 줄인다.

11. 외부 Provider 상태는
Grace Period 이후 검사한다.

12. Provider 상태 조회가 불가능한 경우
UNKNOWN을 자동 SUCCESS로 변경하지 않는다.

13. Repair 구조는 별도 분리한다.

Scanner와 Repair Executor를
하나의 Service에 섞지 않는다.

14. 초기 자동 Repair는 다음 후보만 고려한다.

- Cache Invalidation
- Derived Summary Rebuild

15. Order Status 및 고객정보 수정은
자동 Repair 대상에서 제외한다.

16. Repair 전 Dry Run을 지원한다.

17. Repair 직전 현재 Version과 상태를 재검증한다.

18. Repair 실행 후 같은 Rule을 다시 검사한다.

19. Repair 성공과 검증 성공을 구분한다.

20. Repair Audit를 남긴다.

21. 다음 Metric을 제공한다.

- open findings
- audit duration
- audit failure
- watermark lag
- repair failure

22. Scanner는 Low Priority Job으로 실행한다.

23. DB 부하가 높으면
Full Scan을 Pause할 수 있게 한다.

24. 검사 자체가 Production 성능을
악화시키지 않게 Query Timeout과
Batch Size를 설정한다.

25. 처음에는 새로운 관리자 페이지 전체를 만들지 말고
기존 관리자 화면에 간단한 Finding List를 연결한다.

26. 다음 테스트를 작성한다.

- 정상 Order
- 상태/이력 불일치
- 초기 상태 이력 없음
- 중복 요청
- 실제 중복이 아닌 재신청
- Soft Delete
- Provider 상태 지연
- UNKNOWN Provider Result
- Scan 중 Worker Crash
- Watermark 이후 데이터 변경
- Duplicate Finding
- False Positive
- Repair Dry Run
- Repair 동시성 충돌
- Repair 후 Verify 실패

27. 실제 Production Data를 수정하는
자동 Repair는 구현하거나 실행하지 않는다.

28. 필요하다면 구현 전에
분석 보고서와 변경 계획부터 제시한다.

목표:

데이터를 무조건 자동으로 고치는 것이 아니라
정확하게 발견하고,
원인을 구분하고,
안전한 범위에서만 복구하는 것이다.
```

### ✅ 140. DR 복구 후 정합성 검증 프롬프트

```text
현재 시스템의 RDS Disaster Recovery 이후
Data Integrity Verification Plan을 작성해줘.

상황:

RDS PITR 또는 Snapshot에서
격리된 Recovery DB를 복원한 상태라고 가정한다.

실제 Production 환경은 수정하지 않는다.

검증 대상:

1. Prisma Schema
2. Order
3. Consult
4. OrderStatusHistory
5. NotificationJob
6. Outbox
7. Webhook
8. AuditLog
9. Derived Summary
10. External Provider State

각 항목마다:

## Source of Truth

## 검증할 Invariant

## 필요한 SQL / Application Check

## 복구 시점 차이로 발생할 수 있는 문제

## External Consistency Risk

## Severity

## PASS 조건

## FAIL 조건

## NOT_VERIFIED 조건

을 정리한다.

반드시 다음 위험을 고려한다.

- 복구 시점 이후 생성된 정상 주문 누락
- 과거 NotificationJob 재실행
- 중복 알림 발송
- Webhook 재처리
- Outbox Event 손실
- 상태 변경 이력 누락
- 기존 관리자 변경 내역과 복구 DB 차이
- 잘못된 Derived Summary

검증 결과를:

PASS
FAIL
NOT_VERIFIED

로 구분한다.

Critical Rule이 실패하면
Production Cutover를 승인하지 않도록 제안한다.

복구 이후 Worker와 Scheduler를
무조건 즉시 재개하지 않는다.

Reconciliation과 Controlled Resume 절차를 포함해줘.
```

### ✅ 141. Automated Repair 안전성 검증 프롬프트

```text
현재 데이터 정합성 자동 복구 구조를
안전성 관점에서 검토해줘.

코드는 수정하지 않는다.

다음 항목을 검토한다.

1. Source of Truth가 명확한가?

2. Repair 대상이 Derived Data인가?

3. Repair가 Idempotent한가?

4. Dry Run이 있는가?

5. Concurrent Update를 감지하는가?

6. Before/After가 기록되는가?

7. External Side Effect가 발생하는가?

8. Approval이 필요한가?

9. Repair 실패 시 Rollback 또는
   Reconciliation이 가능한가?

10. Repair 후 동일 Rule을 재검사하는가?

특히 다음 작업은 위험하게 분류한다.

- 주문 현재 상태 수정
- 고객 개인정보 수정
- 알림톡 재발송
- 과거 Audit 이력 생성
- DB Row 삭제
- Production Snapshot 복구

각 Repair Action을 다음으로 분류한다.

AUTO_SAFE

CONDITIONAL

APPROVAL_REQUIRED

FORBIDDEN

마지막에 현재 규모에서
실제로 자동화 가치가 높은
Safe Repair 3개만 추천해줘.
```

## 18. 실무 체크리스트

### Business Invariant

- [ ] 주문 상태 전이 규칙이 명확한가?
- [ ] 기술적 중복과 업무상 중복을 구분하는가?
- [ ] 현재 상태와 변경 이력의 관계가 정의돼 있는가?
- [ ] 과거 데이터의 예외 규칙을 고려하는가?
- [ ] Rule Version을 구분할 수 있는가?

### Database

- [ ] Foreign Key가 필요한 곳에 있는가?
- [ ] Unique Constraint가 올바르게 적용돼 있는가?
- [ ] 여러 테이블 변경을 Transaction으로 처리하는가?
- [ ] 중요한 상태 변경의 동시성을 제어하는가?
- [ ] 운영 Migration 전 기존 데이터의 충돌을 검사하는가?

### Audit

- [ ] 검사 대상과 Watermark가 명확한가?
- [ ] 변경 중인 데이터로 인한 False Positive를 고려하는가?
- [ ] 증분 검사와 전체 검사를 구분하는가?
- [ ] Scan Checkpoint가 있는가?
- [ ] Audit 자체가 DB에 과도한 부하를 주지 않는가?

### Finding

- [ ] 불일치 결과를 원본 데이터와 분리하는가?
- [ ] 같은 활성 Finding이 무한 생성되지 않는가?
- [ ] Severity가 정의돼 있는가?
- [ ] Evidence Reference가 있는가?
- [ ] FALSE_POSITIVE와 NOT_VERIFIED를 구분하는가?

### External Consistency

- [ ] Provider 발송 수락과 실제 전달을 구분하는가?
- [ ] UNKNOWN을 무조건 Retry하지 않는가?
- [ ] Webhook 중복과 순서 역전을 고려하는가?
- [ ] External API 지연에 Grace Period가 있는가?
- [ ] 상태 조회 API가 없을 때 수동 검토 경로가 있는가?

### Automated Repair

- [ ] 원본과 Derived Data를 구분하는가?
- [ ] Dry Run이 있는가?
- [ ] Repair 직전 상태를 재검증하는가?
- [ ] Idempotency가 있는가?
- [ ] Concurrent Update를 막는가?
- [ ] 수정 후 동일 Rule로 검증하는가?
- [ ] 중요한 주문/고객 데이터는 승인 없이 수정하지 않는가?

### Disaster Recovery

- [ ] 복구된 DB의 상태를 실제 업무 기준으로 검사하는가?
- [ ] 복구 시점 이후 정상 주문 누락을 확인하는가?
- [ ] Notification/Outbox/Inbox를 Reconcile하는가?
- [ ] Worker를 Controlled Resume하는가?
- [ ] Critical Finding이 남아 있으면 Cutover를 보류할 수 있는가?

### Operations

- [ ] Audit Run의 마지막 성공 시각을 확인하는가?
- [ ] Finding 추이를 볼 수 있는가?
- [ ] False Positive 비율을 추적하는가?
- [ ] Repair 실패를 알 수 있는가?
- [ ] AI가 분석과 실제 수정을 분리해서 수행하는가?

### 📌 요약

1011에서는:

```text
데이터베이스가 손상됐을 때

어떤 Backup으로

어느 시점까지

얼마나 빠르게 복구할 것인가?
```

를 다뤘다.

1012에서는 그다음 질문인:

```text
복구된 데이터가

실제 업무 기준으로도

올바른 상태인가?
```

를 다뤘다.

가장 중요한 원칙은:

**Database가 정상이라는 것과 Business Data가 정확하다는 것은 다르다.**

예를 들어:

```text
Order
COMPLETED

Status History
WAITING

Notification
UNKNOWN
```

이라면 각각의 테이블은 정상적으로 조회되지만 업무 상태는 불분명하다.

이를 해결하기 위해 먼저:

```text
Business Invariant
```

를 정의한다.

즉:

```text
어떤 상태가 정상이고

어떤 관계가 반드시 유지돼야 하는가?
```

를 업무 규칙으로 정한다.

그다음:

```text
On-write Validation

Database Constraint

Transaction

Consistency Audit
```

으로 오류를 예방하고 발견한다.

하지만 불일치를 발견했다고 바로 수정하면 안 된다.

예:

```text
현재 상태
COMPLETED

마지막 이력
WAITING
```

일 때 무엇이 진짜 올바른 상태인지 모를 수 있기 때문이다.

따라서:

```text
Detect
↓
Collect Evidence
↓
Classify
↓
Plan Repair
↓
Dry Run
↓
Approval
↓
Execute
↓
Verify
```

흐름이 필요하다.

특히 자동 수정은:

```text
Cache Invalidation

Derived Summary Rebuild
```

처럼 원본 업무 데이터를 변경하지 않는 작업부터 시작하는 것이 안전하다.

반대로:

```text
주문 상태 수정

고객정보 복구

알림톡 재발송

과거 Audit 이력 생성
```

등은 훨씬 엄격한 검증과 승인이 필요하다.

또한 Consistency Audit 자체가 새로운 장애 원인이 되어서는 안 된다.

따라서:

```text
Incremental Scan

Cursor

Watermark

Checkpoint

Batch Size

Rate Limit
```

을 이용해 DB에 부담을 주지 않도록 설계한다.

현재 프로젝트에서는 우선:

```text
1. 상태 변경 Transaction 확인

2. 핵심 DB Constraint 점검

3. Order / History 정합성 검사

4. Notification / Order 참조 검사

5. Technical Duplicate 검사

6. Finding 저장

7. 관리자 Review

8. Safe Repair만 자동화
```

순서가 현실적이다.

전체 구조를 연결하면:

```text
Business Rule
      ↓
Application Validation
      ↓
Database Constraint
      ↓
Transaction
      ↓
Consistency Audit
      ↓
Finding
      ↓
Evidence
      ↓
Repair Plan
      ↓
Dry Run / Approval
      ↓
Safe Repair
      ↓
Verification
      ↓
Audit / Monitoring
```

이 된다.

1011과 연결하면:

```text
Disaster
↓
Backup Restore
↓
Data Integrity Audit
↓
External Reconciliation
↓
Safe Repair
↓
Business Validation
↓
Worker Resume
↓
Production Recovery
```

라는 흐름이 완성된다.

결국 Data Integrity와 Automated Repair의 핵심은:

> **“데이터가 서로 다르면 자동으로 맞춰주는 것”이 아니라, 무엇이 신뢰할 수 있는 원본인지 확인하고, 어떤 규칙이 깨졌는지 증명한 뒤, 실제 업무 기록과 고객에게 피해를 주지 않는 방식으로만 복구하는 것**이다.
