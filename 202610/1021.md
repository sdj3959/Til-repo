# 1021 운영 자동화/AI 워크플로우 심화 (45/N)
## Agent Identity·Delegated Authorization·Capability Tokens·Approval Lifecycle와 Multi-Agent 권한 위임

**시리즈 날짜: 2026년 10월 21일**

## 1. 여러 AI Agent가 협업할 때 권한은 어떻게 관리할까?

### ✅ 1. 1020과의 연결

1020에서는 AI Agent가 악의적인 입력을 받거나 잘못된 판단을 내리더라도 실제 시스템에 피해를 주지 않도록 만드는 보안 구조를 다뤘다.

```text
Untrusted Input
       ↓
AI Agent
       ↓
Tool Call Proposal
       ↓
Tool Gateway
       ↓
Authentication
       ↓
Authorization
       ↓
Business Validation
       ↓
Human Approval
       ↓
Execution
       ↓
Audit
```

1021에서는 이 구조를 여러 Agent가 협업하는 환경으로 확장한다.

### ✅ 2. Single Agent와 Multi-Agent의 차이

Single Agent:

```text
User
 ↓
AI Agent
 ↓
Tool Gateway
 ↓
Database / External API
```

Multi-Agent:

```text
User
 ↓
Supervisor Agent
 ├── Research Agent
 ├── Database Agent
 ├── Report Agent
 └── Execution Agent
           ↓
       Tool Gateway
           ↓
       External System
```

여러 Agent가 역할을 나누면 복잡한 작업을 병렬 또는 순차적으로 처리할 수 있다.

그러나 권한을 관리하지 않으면 새로운 보안 문제가 발생한다.

### ✅ 3. Multi-Agent에서 발생하는 핵심 위험

예를 들어 관리자가 다음과 같이 요청했다고 하자.

```text
지난 일주일간 주문 통계를 분석하고
개선사항을 보고서로 작성해줘.
```

AI는 주문 통계를 읽고 분석할 필요가 있다.

그런데 다음과 같이 동작한다면 문제가 된다.

```text
Supervisor Agent
       ↓
Database Agent에게
관리자 DB Credential 전체 전달
       ↓
Database Agent
전체 고객정보 조회
       ↓
외부 LLM에게 전송
```

원래 요청에는 개인정보 전체 조회나 외부 전송이 포함되지 않았다.

### ✅ 4. 작업 위임과 권한 위임의 차이

**Task Delegation**

```text
이 보고서를 작성해줘.
```

**Authorization Delegation**

```text
이 보고서를 작성하는 데 필요한
특정 데이터의 읽기 권한을
제한된 기간 동안 허용한다.
```

이 둘은 다른 개념이다.

### ✅ 5. 작업을 받았다고 권한을 얻는 것은 아니다

Supervisor Agent가 Worker Agent에게 명령을 내렸다는 이유로 Worker가 자동으로 관리자 권한을 보유해서는 안 된다.

### ✅ 6. Multi-Agent 보안의 기본 원칙

**하위 Agent가 사용할 수 있는 권한은 정식으로 허용된 범위를 초과해서는 안 된다.**

예:

```text
Supervisor
order.read
report.generate

↓

Worker
order.read
```

은 가능할 수 있다.

하지만:

```text
Supervisor
order.read

↓

Worker
order.delete
```

는 허용해서는 안 된다.

### ✅ 7. 핵심 구조

```text
Authenticated User
        ↓
Supervisor Agent
        ↓
Delegation Request
        ↓
Delegation Policy
        ↓
Scoped Grant
        ↓
Worker Agent
        ↓
Tool Gateway
        ↓
Authorization
        ↓
Execution
        ↓
Audit Chain
```

### ✅ 8. 이번 편에서 다룰 내용

```text
Agent Identity

Principal / Actor 구분

Delegated Authorization

Permission Attenuation

Capability Tokens

OAuth Token Exchange

MCP Authorization

Approval Lifecycle

Revocation

Multi-Agent Audit

NestJS 구현

AWS IAM 연동

Codex 실전 프롬프트
```

## 2. Agent Identity — AI Agent의 신원을 구분하기

### ✅ 9. Agent Identity란?

어떤 Agent가 작업을 요청하고 실행하는지 식별하기 위한 신원 정보다.

예:

```text
supervisor-agent

order-reader-agent

report-writer-agent

notification-sender-agent
```

### ✅ 10. Agent ID만으로 인증을 완료한 것은 아니다

예:

```json
{
  "agentId": "admin-agent"
}
```

같은 값을 LLM이 생성했다고 실제 관리자 Agent라고 인정해서는 안 된다.

### ✅ 11. Identity와 Authentication

Identity:

```text
나는 누구인가?
```

Authentication:

```text
정말 그 신원임을 어떻게 증명하는가?
```

Authorization:

```text
그 신원으로 어떤 작업을 할 수 있는가?
```

를 구분한다.

### ✅ 12. Human Identity

실제 사용자의 신원이다.

예:

```text
관리자 A

운영 담당자 B

고객 C
```

### ✅ 13. Service Identity

실제 애플리케이션이나 서비스를 나타내는 신원이다.

예:

```text
togethermall-backend

report-worker

notification-service
```

### ✅ 14. Agent Identity

AI 작업을 수행하는 Agent 인스턴스 또는 역할의 식별자다.

예:

```text
agentType
order-reader

agentInstanceId
worker-run-001
```

### ✅ 15. Agent Type과 Agent Instance를 구분한다

Agent Type:

```text
ReportWriter
```

Agent Instance:

```text
오늘 실행된 ReportWriter 작업 #123
```

이다.

### ✅ 16. 같은 역할의 Agent도 실행별로 구분할 수 있어야 한다

```text
ReportWriter Run A

ReportWriter Run B
```

가 서로 다른 요청에서 실행됐다면 각각의 실행 경로를 추적할 수 있어야 한다.

### ✅ 17. Agent Identity에 필요한 정보

```text
Agent Type

Agent Instance ID

Service Identity

Requested By

Task ID

Parent Agent

Execution Environment

Created At
```

등이다.

### ✅ 18. Principal이란?

보안 시스템에서 권한 판단의 대상이 되는 신원이다.

사용자, 서비스 계정, 역할을 수임한 주체 등이 Principal이 될 수 있다.

### ✅ 19. Subject와 Actor

**Subject**

작업이 누구를 대신해 수행되는지 나타낸다.

**Actor**

실제로 작업을 수행하는 주체를 나타낸다.

예:

```text
Subject
관리자 A

Actor
ReportWriter Agent
```

### ✅ 20. 사용자 대신 실행하는 작업과 서비스 자체 작업은 다르다

사용자 대신 실행:

```text
관리자 A가 요청한
주문 보고서 생성
```

서비스 자체 작업:

```text
매일 새벽 정해진 정책에 따라
시스템 상태 점검
```

두 작업은 권한의 출처가 다르다.

### ✅ 21. Scheduled Agent

스케줄러가 실행한 Agent는 실제 로그인 사용자가 없을 수도 있다.

이 경우 다음과 같이 관리한다.

```text
Service Principal
report-scheduler

Authorized Purpose
daily-report

Execution Policy
read-only
```

### ✅ 22. 가상의 Human Identity를 만들지 않는다

사용자가 요청하지 않은 Scheduled Job을 특정 관리자 계정이 직접 실행했다고 기록하면 안 된다.

### ✅ 23. 신원 관련 주요 필드

```typescript
type AgentExecutionIdentity = {
  runId: string;
  taskId: string;

  agentType: string;
  agentInstanceId: string;

  servicePrincipalId: string;

  humanSubjectId?: string;
  parentRunId?: string;
};
```

이 구조는 신원에 대한 설명 정보다.

실제 인증은 서버가 검증한 세션 또는 서비스 자격증명으로 수행해야 한다.

## 3. Delegated Authorization — 권한 위임의 원칙

### ✅ 24. Delegation이란?

기존에 권한을 가진 주체가 다른 주체에게 특정 작업을 수행할 권한을 제한적으로 위임하는 것이다.

### ✅ 25. 정상적인 권한 위임

예:

```text
Supervisor 권한

order.read
report.generate
```

Worker에게:

```text
order.read
```

만 위임한다.

### ✅ 26. 잘못된 권한 위임

```text
Supervisor
order.read

↓

Worker
order.read
order.update
order.delete
```

Supervisor가 갖지 않은 권한을 Worker에게 새로 부여하는 것이다.

### ✅ 27. Permission Attenuation

상위 권한을 더 제한된 권한으로 축소하는 개념이다.

예:

```text
Parent Permissions
    {READ, EXPORT}
          ↓
Requested Permissions
       {READ}
          ↓
Effective Delegation
       {READ}
```

### ✅ 28. 권한 위임 시 고려할 요소

```text
Action

Resource

Environment

Audience

Time

Usage Limit

Task

Policy Version
```

등이다.

### ✅ 29. Action Scope

예:

```text
order.read

order.update

order.delete
```

처럼 허용된 작업을 정의한다.

### ✅ 30. Resource Scope

예:

```text
모든 주문
```

이 아니라:

```text
특정 주문 1건
```

으로 제한한다.

### ✅ 31. Environment Scope

예:

```text
staging
```

에서 허용된 권한은:

```text
production
```

으로 자동 확장되지 않아야 한다.

### ✅ 32. Audience Scope

권한이 어느 서비스에서 사용될 수 있는지 제한한다.

예:

```text
Audience
order-tool-gateway
```

이다.

### ✅ 33. Time Scope

위임된 권한이 언제까지 유효한지 지정한다.

예:

```text
유효기간
5분
```

단 실제 업무에 적합한 TTL을 정해야 한다.

### ✅ 34. Usage Limit

예:

```text
최대 실행
1회
```

로 제한할 수 있다.

### ✅ 35. Task Binding

권한을 특정 Task와 연결한다.

예:

```text
Task ID
TASK-001

Permission
order.read
```

### ✅ 36. 하위 Agent의 재위임

Worker가 또 다른 Agent에게 작업을 위임하는 경우다.

```text
Supervisor
      ↓
Worker A
      ↓
Worker B
```

이때 Worker B의 권한은 Worker A에게 실제로 허용된 위임 가능 권한을 넘을 수 없어야 한다.

### ✅ 37. 모든 Agent에게 재위임 권한을 줄 필요는 없다

예:

```text
OrderReader

canDelegate
false
```

처럼 설정할 수 있다.

### ✅ 38. 권한 상속과 재위임 가능 권한은 다르다

특정 Agent에게 조회 권한이 있다고 해서 그 조회 권한을 다른 Agent에게 전달할 수 있다는 뜻은 아니다.

### ✅ 39. Effective Permission

개념적으로 다음 조건을 모두 충족해야 한다.

```text
Original Authorization

AND

Parent Delegation

AND

Worker Policy

AND

Resource Policy

AND

Current Business State
```

### ✅ 40. Deny Override

어느 필수 보안 정책에서든 명시적으로 거부하면 실행하지 않는다.

### ✅ 41. 권한 제한은 실제 Gateway에서 적용한다

권한 정보가 JSON 문서에 적혀 있다는 사실만으로 실행이 차단되는 것은 아니다.

Tool Gateway가 모든 실행 요청에서 정책을 검증해야 한다.

## 4. Capability — 특정 작업에 대한 제한된 권한

### ✅ 42. Capability란?

특정 리소스에 특정 작업을 수행할 수 있는 권한을 표현하는 개념이다.

실제로는 토큰, 서버 측 Grant, 핸들 등 여러 형태로 구현할 수 있다.

### ✅ 43. Capability 예시

```json
{
  "action": "order.read",
  "resource": "order:12345",
  "audience": "order-tool-gateway",
  "maxUses": 1
}
```

이 JSON은 권한 내용을 설명하는 예시다.

**이 문서 자체는 인증된 Capability Token이 아니다.**

### ✅ 44. Capability Token

발급 기관이 위변조를 방지하고, 수신 서비스가 유효성을 검증할 수 있도록 만든 권한 증명이다.

### ✅ 45. Bearer Token

토큰을 가진 사람이 사용할 수 있는 형태다.

탈취되면 유효기간과 권한 범위 내에서 악용될 수 있다.

### ✅ 46. Sender-constrained Token

특정 클라이언트 또는 키 소유자에게 사용을 제한하는 방식이다.

예:

```text
DPoP

mTLS-bound Access Token
```

등이 있다.

### ✅ 47. 모든 Agent에게 직접 토큰을 전달해야 할까?

그럴 필요는 없다.

현재 규모에서는 실제 Credential을 Tool Gateway가 보관하고, Agent는 제한된 작업 요청만 제출하는 방식이 더 단순하고 안전할 수 있다.

### ✅ 48. 추천 구조

```text
Worker Agent
      ↓
Tool Call Proposal
      ↓
Execution Context ID
      ↓
Tool Gateway
      ↓
Server-side Grant Lookup
      ↓
Authorization
      ↓
Execution
```

### ✅ 49. Opaque Grant 방식

외부에서 내용을 직접 해석할 수 없는 무작위 식별자를 사용한다.

서버가 해당 식별자에 연결된 권한과 상태를 조회한다.

### ✅ 50. 장점

```text
권한 회수 용이

1회 실행 제한 가능

Approval 연동 용이

서버 측 상태 검증

Audit 연결
```

이다.

### ✅ 51. 단점

서버 측 저장소 조회가 필요하다.

분산 환경에서는 캐시 및 일관성 관리가 필요할 수 있다.

### ✅ 52. Signed Token 방식

JWT 등 서명된 토큰에 일부 권한을 포함할 수도 있다.

### ✅ 53. Signed Token의 장점

수신 서비스가 서명과 Claim을 검증할 수 있다.

### ✅ 54. Signed Token의 어려움

```text
즉시 회수

One-time Use

권한 변경

키 관리

Replay 방지
```

에 별도의 설계가 필요하다.

### ✅ 55. 현재 추천

1인 개발·단일 Backend 중심 구조에서는 처음부터 별도 Token Issuer를 개발하기보다 **서버 측 Delegation Grant와 Tool Gateway**를 먼저 구축하는 것이 현실적이다.

## 5. Capability Grant에 포함할 정보

### ✅ 56. 최소 Grant 구조

```typescript
interface DelegationGrant {
  id: string;

  taskId: string;
  parentGrantId?: string;

  subjectId?: string;

  delegatorId: string;
  delegateeId: string;

  audience: string;

  action: string;
  resourceId: string;

  environment: 'staging' | 'production';

  expiresAt: Date;

  maxUses: number;
  usedCount: number;

  revokedAt?: Date;

  policyVersion: number;
}
```

### ✅ 57. Subject

원래 업무 요청과 연결되는 사용자 또는 서비스 주체다.

### ✅ 58. Delegator

권한 위임을 요청한 주체다.

### ✅ 59. Delegatee

위임받는 주체다.

### ✅ 60. Parent Grant

상위 권한 위임 기록이다.

### ✅ 61. Audience

해당 Grant를 사용할 수 있는 대상 Tool Gateway다.

### ✅ 62. Action

허용된 업무다.

### ✅ 63. Resource

허용된 업무 대상이다.

### ✅ 64. Expiration

권한의 만료 시각이다.

### ✅ 65. Usage Counter

허용된 실행 횟수다.

### ✅ 66. Revocation

권한이 명시적으로 취소됐는지 나타낸다.

### ✅ 67. Policy Version

해당 권한을 발급할 때 사용한 정책 버전이다.

단 현재 더 엄격한 정책이 적용됐다면 오래된 정책이 실행 권한을 유지하게 만들어서는 안 된다.

### ✅ 68. Delegation Depth

필요하면 몇 단계까지 권한을 위임할 수 있는지 제한한다.

예:

```text
Supervisor → Worker

허용

Worker → Another Worker

금지
```

### ✅ 69. Grant는 권한을 증명하는 최종 수단이 아니다

실제 요청자의 인증 상태, 서비스 Identity, 현재 권한 정책, 리소스 상태를 함께 확인해야 한다.

## 6. OAuth Token Exchange — 표준 기반 위임

### ✅ 70. OAuth 2.0 Token Exchange

RFC 8693은 하나의 보안 토큰을 다른 토큰으로 교환하는 프로토콜을 정의한다.

이를 통해 사용자 대신 동작하는 서비스나 Agent의 위임 관계를 표현할 수 있다.

### ✅ 71. 기본 개념

```text
Original Token
       ↓
Authorization Server
       ↓
Exchanged Token
       ↓
Target Service
```

### ✅ 72. Subject Token

누구를 대신하는 요청인지를 나타내는 토큰이다.

### ✅ 73. Actor Token

누가 위임받아 행동하는지 나타내는 토큰이다.

### ✅ 74. RFC 8693의 Actor Claim

JWT에서는 `act` Claim으로 실제 실행 주체를 표현할 수 있다.

예:

```json
{
  "sub": "user-123",
  "act": {
    "sub": "report-worker"
  }
}
```

이는 개념 예시다.

실제 Access Token에는 발급자, 대상 서비스, 만료, 유효한 서명 등 필요한 검증 요소가 포함돼야 한다.

### ✅ 75. 중요한 것은 Actor Claim만으로 권한이 생기지 않는다는 점이다

토큰에:

```json
{
  "act": {
    "sub": "admin-agent"
  }
}
```

가 있다고 해서 관리자 권한을 인정할 수 있는 것은 아니다.

실제 토큰의 발급자·서명·Audience·권한·정책을 검증해야 한다.

### ✅ 76. Delegation Chain

예:

```text
User A
  ↓
Supervisor Agent
  ↓
Report Worker
```

처럼 여러 단계의 실행 관계를 표현할 수 있다.

### ✅ 77. Actor Chain의 역할

누가 최종적으로 실행했고 어떤 위임 경로를 거쳤는지 기록하는 데 도움이 된다.

단 RFC 8693에서는 과거 Actor 기록을 모두 현재의 권한 판단 근거로 삼지 않는다.

### ✅ 78. Delegation과 Impersonation

Delegation은 원래 Subject와 실제 Actor의 관계를 드러내는 방식이다.

Impersonation은 특정 주체의 신원으로 행동하는 방식이다.

현재 AI Agent 구조에서는 가능하면 실제 실행 주체를 구분해 감사 가능성을 유지하는 편이 안전하다.

### ✅ 79. 모든 OAuth Provider가 Token Exchange를 지원하지는 않는다

RFC 8693이라는 표준이 존재한다고 해서 현재 사용하는 인증 서비스에 해당 기능이 자동으로 제공되는 것은 아니다.

실제 지원 여부와 정책을 확인해야 한다.

### ✅ 80. 현재 구현 권장

기존 사용자 인증과 Tool Gateway가 충분하다면 OAuth Token Exchange 서버를 새로 구현할 필요는 없다.

여러 독립 서비스 사이의 위임이 실제로 필요해질 때 검토한다.

## 7. Scope·Audience·Resource를 함께 제한하기

### ✅ 81. Scope

어떤 종류의 작업을 할 수 있는가?

예:

```text
order:read
```

### ✅ 82. Audience

어느 서비스에서 사용할 수 있는가?

예:

```text
order-api
```

### ✅ 83. Resource

어느 리소스에 접근할 수 있는가?

예:

```text
order:12345
```

### ✅ 84. 세 조건이 모두 중요하다

```text
Scope:
order:read

Audience:
order-api

Resource:
order:12345
```

이면 특정 서비스의 특정 주문만 조회할 수 있도록 설계할 수 있다.

### ✅ 85. 잘못된 권한 예시

```text
Scope:
admin:all

Audience:
*

Resource:
*
```

와 같은 광범위한 권한은 피한다.

### ✅ 86. Rich Authorization Requests

RFC 9396은 세부적인 권한 정보를 표현하는 `authorization_details`를 정의한다.

예를 들어 리소스와 작업을 구조적으로 표현할 수 있다.

### ✅ 87. 구조화된 권한의 장점

```text
어떤 리소스인가?

어떤 작업인가?

어느 서비스인가?

어떤 제한이 있는가?
```

를 명확하게 표현할 수 있다.

### ✅ 88. 하지만 OAuth Scope와 업무 검증은 다르다

`order:read` Scope가 있어도 다른 고객 주문까지 읽을 권한이 자동으로 생기는 것은 아니다.

서버에서 Order Ownership과 업무 범위를 검증해야 한다.

### ✅ 89. MCP Client와 MCP Server

### ✅ 90. MCP의 Authorization은 전송 방식에 따라 다르다

HTTP 기반 MCP에서 보호된 서비스에 접근하는 경우 OAuth 기반 Authorization을 사용할 수 있다.

로컬 STDIO 기반 서버는 다른 방식으로 Credential을 전달하는 경우가 많다.

### ✅ 91. MCP Tool을 연결했다고 자동으로 권한이 제한되지는 않는다

Tool 자체의 실제 접근 권한과 연결 방식을 확인해야 한다.

```text

       ↓

       ↓
같은 Token을 그대로

```

MCP 서버는 자신에게 발급된 토큰인지 확인해야 한다.

다른 API용으로 발급된 토큰을 그대로 받아들이면 안 된다.

### ✅ 94. 서비스별 토큰 분리

```text

       ↓

       ↓
```


는 서로 다른 권한이다.

### ✅ 96. MCP Server의 Tool 목록이 아니라 실행 권한을 검증한다

목록에 Tool이 있다고 해서 모든 사용자가 실행할 수 있어서는 안 된다.

### ✅ 97. Confused Deputy

원래 권한이 낮은 주체가 더 높은 권한을 가진 서비스를 이용해 허용되지 않은 작업을 수행하게 만드는 문제다.

### ✅ 98. Multi-Agent에서의 Confused Deputy

```text

          ↓
High-privilege Supervisor
          ↓
Production API
```

Worker가 Supervisor의 권한을 악용할 수 있다면 위험하다.

### ✅ 99. 방어 원칙

각 실행 요청의 원래 Subject, 현재 Actor, Scope, Resource, Audience를 확인한다.

### ✅ 100. MCP와 Agent의 역할 구분

MCP는 Tool 연결을 표준화하는 데 도움이 되지만 애플리케이션의 모든 업무 권한과 승인 절차를 자동으로 해결하지 않는다.

## 9. Approval Lifecycle — 승인의 생명주기

### ✅ 101. 1020에서의 Human Approval

1020에서는 위험한 Tool 실행에 사람의 승인이 필요하다는 점을 다뤘다.

1021에서는 승인이 실제로 얼마나 오래, 어떤 범위에서 유효한지 관리한다.

### ✅ 102. 승인 상태

```text
PENDING

APPROVED

REJECTED

EXPIRED

REVOKED

EXECUTING

EXECUTED

FAILED
```

### ✅ 103. PENDING

승인을 기다리는 상태다.

### ✅ 104. APPROVED

실행이 허용됐지만 아직 수행되지 않은 상태다.

### ✅ 105. REJECTED

승인자가 거부한 상태다.

### ✅ 106. EXPIRED

승인 유효기간이 지나 실행할 수 없는 상태다.

### ✅ 107. REVOKED

승인 후 명시적으로 취소된 상태다.

### ✅ 108. EXECUTING

승인된 작업을 실행 중인 상태다.

### ✅ 109. EXECUTED

실행이 완료된 상태다.

### ✅ 110. FAILED

실행 중 실패했거나 완료 여부가 확정되지 않은 경우다.

완료 여부를 알 수 없는 외부 API Timeout은 단순 실패로 간주하고 무조건 재실행해서는 안 된다.

### ✅ 111. 승인과 실행은 별개의 작업이다

```text
APPROVED
≠
EXECUTED
```

### ✅ 112. 실행과 검증도 다르다

```text
EXECUTED
≠
BUSINESS_VERIFIED
```

외부 알림 발송을 예로 들면 API 요청 성공과 실제 고객 수신은 다른 상태다.

### ✅ 113. Approval에 포함할 정보

```text
Approval ID

Task ID

Requesting Actor

Approver

Action

Target Resource

Arguments Digest

Expiration

Status

Policy Version
```

### ✅ 114. Approval Binding

승인은 정확한 작업 내용에만 유효해야 한다.

예:

```text
주문 12345
상태 변경
APPLICATION_SENT
```

를 승인했다면:

```text
주문 67890
상태 변경
CANCELLED
```

에는 사용할 수 없다.

### ✅ 115. 승인 내용 변조 방지

서버가 보관하는 승인 대상 Payload와 실제 실행 요청이 동일한지 검증한다.

### ✅ 116. Canonical Payload

JSON 필드 순서 등에 따라 해시가 달라지지 않도록 정규화된 작업 표현을 사용한다.

실제 구현에서는 검증된 Canonicalization 방법을 선택해야 한다.

### ✅ 117. Approval TTL

예:

```text
승인 후 5분간 유효
```

처럼 설정할 수 있다.

### ✅ 118. Approval One-time Use

승인은 최대 한 번의 실제 작업에만 소비되도록 설계한다.

### ✅ 119. Replay 방지

이미 사용한 Approval을 다시 제출하면 거부한다.

### ✅ 120. Parent Revocation

상위 위임 Grant가 취소되면 해당 Grant에 의존하는 하위 작업도 재검증하고 필요한 경우 차단해야 한다.

### ✅ 121. Approval Revocation

승인자가 이미 승인한 작업을 실행 전에 취소할 수 있어야 한다.

### ✅ 122. 실행 중 취소 문제

이미 실행 중인 작업은 취소 요청만으로 완전히 되돌아가지 않을 수 있다.

따라서 신규 실행 차단, Queue 처리, 외부 Side Effect 복구를 구분한다.

## 10. Approval과 Delegation의 차이

### ✅ 123. Delegation Grant

Agent가 어떤 작업을 수행할 수 있는지 정하는 권한이다.

### ✅ 124. Approval

특정 고위험 작업의 실행을 승인하는 기록이다.

### ✅ 125. 둘 다 필요한 경우

예:

```text
Worker 권한

notification.send
```

이 있다고 하자.

그렇다고 실제 고객에게 모든 알림을 자동 발송할 수 있는 것은 아니다.

### ✅ 126. 실행 조건

```text
Worker Capability
유효

AND

Human Approval
유효

AND

Business Policy
PASS

AND

Execution Limit
허용
```

이어야 한다.

### ✅ 127. Approval로 존재하지 않는 권한을 만드는 것은 아니다

Worker에게 주문 삭제 권한이 없다면 Human Approval만 받았다고 주문 삭제를 허용해서는 안 된다.

권한 부여와 실행 승인은 별개로 관리한다.

### ✅ 128. Delegation으로 Approval을 우회하지 않는다

Supervisor가 Worker에게 알림 발송 권한을 위임했다고 해서 원래 필요한 승인 절차가 사라지지 않는다.

## 11. NestJS 기반 Delegation Policy 구현

### ✅ 129. 처음에는 복잡한 Token 발급보다 정책 검증부터 시작한다

기존 인증과 Tool Gateway를 활용한다.

### ✅ 130. 권한 타입

```typescript
type CapabilityAction =
  | 'order.read'
  | 'order.update_status'
  | 'report.generate'
  | 'notification.send';
```

### ✅ 131. 제한된 위임 요청

```typescript
interface DelegationRequest {
  taskId: string;

  parentGrantId: string;

  delegateeId: string;

  action: CapabilityAction;

  resourceId: string;

  audience: string;

  requestedExpiresAt: Date;
}
```

### ✅ 132. 중요한 보안 조건

`parentGrantId`를 클라이언트가 제출했다고 해서 유효한 상위 권한이 있다고 간주해서는 안 된다.

서버는 인증된 현재 Actor가 실제로 해당 Grant를 보유했는지 확인한다.

### ✅ 133. Scope 축소 함수

다음은 핵심 원칙을 보여주는 개념 코드다.

```typescript
interface GrantPolicy {
  actions: CapabilityAction[];

  resourceIds: string[];

  audience: string;

  expiresAt: Date;

  canDelegate: boolean;
}

function canDelegate(
  parent: GrantPolicy,
  requested: GrantPolicy,
): boolean {
  if (!parent.canDelegate) {
    return false;
  }

  if (requested.canDelegate) {
    return false;
  }

  if (requested.audience !== parent.audience) {
    return false;
  }

  if (requested.expiresAt > parent.expiresAt) {
    return false;
  }

  if (
    !requested.actions.every(
      (action) => parent.actions.includes(action),
    )
  ) {
    return false;
  }

  if (
    !requested.resourceIds.every(
      (resourceId) =>
        parent.resourceIds.includes(resourceId),
    )
  ) {
    return false;
  }

  return true;
}
```

### ✅ 134. 위 코드의 한계

이 코드는 권한 축소 개념만 검사한다.

다음을 처리하지 않는다.

```text
실제 Actor Authentication

Parent Grant 소유권

서버 측 Grant 유효성

Grant Revocation

Business Authorization

동시성

Audience Identity

Policy Version

Token Authenticity
```

따라서 실제 보안 시스템으로 그대로 사용해서는 안 된다.

### ✅ 135. 중요한 구현 순서

```text
Authenticated Actor
        ↓
Server-side Parent Grant Lookup
        ↓
Parent Validity Check
        ↓
Delegation Permission Check
        ↓
Subset Validation
        ↓
Target Resource Validation
        ↓
Create Child Grant
        ↓
Audit
```

### ✅ 136. Grant 저장 예시

```text
delegation_grants

id

parent_grant_id

task_id

subject_id

delegator_id

delegatee_id

action

resource_id

audience

expires_at

used_count

revoked_at

created_at
```

### ✅ 137. 실제 구현에서는 제약조건이 필요하다

예:

```text
max_uses > 0

used_count >= 0

expires_at > created_at

audience NOT NULL

action NOT NULL
```

### ✅ 138. Parent Grant Chain 검사

상위 Grant가 취소되거나 만료되면 하위 Grant의 사용을 허용하지 않도록 설계한다.

### ✅ 139. 재위임 깊이 제한

예:

```text
Maximum Delegation Depth
1
```

로 설정하면 Supervisor에서 Worker로 한 단계만 위임할 수 있다.

### ✅ 140. 순환 위임 방지

```text
Agent A
→ Agent B
→ Agent A
```

처럼 순환 구조가 생기지 않도록 검사한다.

### ✅ 141. 기존 시스템에서는 단순한 역할 분리가 더 나을 수 있다

모든 Agent에 Grant를 발급하기보다:

```text
Read-only Agent

Draft-only Agent

```

처럼 고정 역할로 분리하면 충분한 경우도 많다.

## 13. One-time Capability와 동시성

### ✅ 151. 단순 사용 횟수 비교의 위험

예:

```text
maxUses
1

usedCount
0
```

인 Grant가 있다고 하자.

동시에 두 Worker가 실행을 요청한다면 둘 다 `usedCount=0`을 읽을 수 있다.

### ✅ 152. Race Condition

```text
Worker A
사용 가능 확인

Worker B
사용 가능 확인

Worker A
실행

Worker B
실행
```

으로 중복 실행될 수 있다.

### ✅ 153. 원자적 사용권 확보

DB Transaction 또는 조건부 Update를 사용해 하나의 Worker만 실행권을 확보하도록 해야 한다.

### ✅ 154. PostgreSQL 개념 예시

```sql
UPDATE delegation_grants
SET used_count = used_count + 1
WHERE id = $1
  AND revoked_at IS NULL
  AND expires_at > NOW()
  AND used_count < max_uses
RETURNING id;
```

이 SQL은 일부 조건만 보여주는 예시다.

실제 실행 전에 Actor·Audience·Action·Resource·Parent Grant 등 모든 정책이 서버에서 검증돼야 한다.

### ✅ 155. Usage Claim과 실제 Side Effect는 다르다

사용권을 확보한 직후 외부 API가 실패할 수도 있다.

### ✅ 156. 재시도 정책

다음 상태를 구분한다.

```text
CLAIMED

EXECUTING

SUCCEEDED

FAILED_RETRYABLE

FAILED_FINAL

OUTCOME_UNKNOWN
```

### ✅ 157. 외부 API Timeout

요청을 보냈지만 응답을 받지 못한 경우 실제 처리가 성공했을 수도 있다.

### ✅ 158. 중복 실행 방지

가능하면 Idempotency Key를 사용한다.

### ✅ 159. 상태 조회 및 Reconciliation

외부 시스템이 결과 조회를 지원한다면 기존 실행 결과를 먼저 확인한 뒤 재시도한다.

### ✅ 160. Exactly-once 실행을 쉽게 보장할 수는 없다

분산된 외부 시스템까지 포함하면 완전한 Exactly-once 처리는 어렵다.

중복 요청 방지, 멱등성, 결과 확인, 보상 처리 등을 조합한다.


### ✅ 163. 메시지 내용이 변경됐다면

이미 승인된 알림톡에서 문구나 수신자가 변경되면 기존 승인을 재사용하지 않아야 한다.

### ✅ 164. 승인 대상 Hash

승인 요청의 정규화된 Payload를 Hash하여 실행 내용과 비교할 수 있다.

단 Hash만으로 사용자 인증·승인자 권한·토큰 무결성 검증이 해결되지는 않는다.

### ✅ 165. Approval Replay

같은 승인으로 동일한 발송 요청이 반복되면 차단해야 한다.

### ✅ 166. Approval Expiration

유효기간이 지난 승인은 재사용하지 않는다.

### ✅ 167. Approval Revocation

승인자가 발송 전에 취소하면 해당 실행이 시작되지 않도록 한다.

### ✅ 168. Approval 이후 상태 변경

예:

```text

↓

Approval 생성

↓

다른 관리자가 상태 변경

↓

AI 실행
```

이 경우 현재 주문 상태를 다시 검증해야 한다.

### ✅ 169. 최종 실행 조건

```text
Grant Valid

AND

Actor Valid

AND

Approval Valid

AND

Payload Match

AND

Business State Valid

AND

Idempotency Check
```

이어야 한다.

## 18. AWS IAM과 권한 위임

### ✅ 201. AWS Role

AWS에서는 IAM Role을 이용해 특정 권한을 가진 임시 세션을 생성할 수 있다.

### ✅ 202. STS AssumeRole

허용된 주체가 Role을 수임하면 임시 Credential을 발급받을 수 있다.

### ✅ 203. Session Policy

AssumeRole 시 Session Policy를 사용해 해당 Role Session의 권한을 추가로 제한할 수 있다.

### ✅ 204. 중요한 규칙

Session Policy는 원래 Role에 없는 권한을 추가하지 않는다.

유효한 세션 권한은 Role 권한과 Session Policy의 교집합으로 제한되며, 다른 적용 가능한 IAM 정책과 명시적 Deny도 고려해야 한다.

### ✅ 205. 예시

```text
IAM Role

s3:GetObject
s3:PutObject
```

Session Policy:

```text
s3:GetObject
```

이면 세션 권한을 조회로 제한할 수 있다.

### ✅ 206. Session Tags

AWS STS의 Session Tag를 사용해 실행 컨텍스트 정보를 전달하고 정책 조건에 활용할 수 있다.

### ✅ 207. Source Identity

AWS에서 지원하는 Source Identity를 활용하면 누가 역할 세션을 시작했는지 감사 추적에 도움이 될 수 있다.

### ✅ 208. Role Chaining

Role을 수임한 자격증명으로 다른 Role을 수임하는 구조다.

### ✅ 209. Role Chaining의 세션 제한

AWS STS의 일반적인 Role Chaining은 세션 기간이 최대 1시간으로 제한된다.

단 EC2 Instance Profile 등 일부 경로에는 별도 예외가 있으므로 실제 구조를 확인해야 한다.

### ✅ 210. AWS Role이 애플리케이션 업무 권한을 대신하지는 않는다

예를 들어 AWS IAM에서 RDS에 접근할 수 있다고 해서 특정 고객 주문에 대한 업무적 수정 권한이 자동으로 생기는 것은 아니다.

### ✅ 211. 두 권한 계층

```text
AWS IAM

Infrastructure Permission
```

```text
NestJS Authorization

Business Permission
```

을 구분한다.

### ✅ 212. 현재 추천 구조

```text
Developer
AWS SSO

GitHub Actions
Restricted Deployment Role

EC2 Backend
Application IAM Role

AI Worker
Task-specific Tool Gateway
```

### ✅ 213. AI Worker에게 직접 AWS Administrator를 제공하지 않는다

실제 AWS 작업이 필요하면 목적이 정해진 서버 측 서비스와 IAM Role을 통해 수행하도록 설계한다.

## 19. Revocation — 위임된 권한을 회수하기

### ✅ 214. 만료와 취소의 차이

Expiration:

```text
정해진 시간이 지나 무효
```

Revocation:

```text
유효기간이 남았어도 명시적으로 무효
```

다.

### ✅ 215. Parent Revocation

```text
Supervisor Grant
REVOKED
```

라면 해당 Grant에 의존하는 Worker Grant도 실행 시점에 무효로 처리해야 한다.

### ✅ 216. Cascading Revocation

위임 체인을 따라 하위 Grant를 회수하는 방식이다.

### ✅ 217. 하지만 실제 구현은 단순하지 않을 수 있다

다음 문제가 있다.

```text
Cache

In-flight Job

Queued Job

External Side Effect

Distributed Worker
```

### ✅ 218. Queued Job

Job이 생성될 때 Grant가 유효했다고 해서 실행 시점에도 유효한 것은 아니다.

### ✅ 219. Execution-time Validation

Worker가 실제로 작업을 시작하기 전에 Grant와 Approval을 다시 검증한다.

### ✅ 220. In-flight Job

이미 외부 API 요청이 전송된 경우 Grant 취소만으로 작업을 되돌릴 수는 없다.

### ✅ 221. Cancellation Policy

```text
새 실행
즉시 차단

대기 작업
취소 또는 재검증

진행 중 작업
안전한 중단 시도

외부 처리 완료
Reconciliation
```

로 구분한다.

### ✅ 222. 캐시의 문제

캐시된 Grant가 여전히 유효하다고 판단하면 취소 직후에도 실행될 수 있다.

### ✅ 223. Critical Write

중요한 변경에서는 실행 직전 서버의 최신 권한 상태를 확인하도록 설계한다.

### ✅ 224. Token Revocation

자체 서명 토큰처럼 독립적으로 검증되는 토큰은 즉각적인 회수가 어렵다.

짧은 TTL, 중앙 Revocation Check, Token Introspection 등의 구조를 검토할 수 있다.

### ✅ 225. 단순한 해결책

현재 작은 시스템에서는 Server-side Grant 방식이 즉시 취소 및 One-time Execution을 구현하기 더 쉬울 수 있다.

```text
Scoped Grant
        ↓
Worker Agent
        ↓
Tool Gateway
        ↓
Authorization
        ↓
Human Approval if Required
        ↓
Execution
        ↓
Audit Chain
```

이번 편에서 가장 중요한 것은 세 가지다.

**첫 번째 — 작업 위임과 권한 위임을 구분한다.**

```text
작업:
주문 보고서를 작성해줘.

권한:
허용된 주문 통계만 조회할 수 있다.
```

는 다르다.

**두 번째 — 위임된 권한은 원래 권한보다 넓어져서는 안 된다.**

```text
Parent
order.read

↓

Child
order.read
```

은 가능할 수 있다.

```text
Parent
order.read

↓

Child
order.delete
```

는 허용해서는 안 된다.

**세 번째 — 위임된 권한과 실제 실행 승인은 별개다.**

```text
Capability
작업할 수 있는 권한

Approval
특정 작업을 실행하라는 승인
```

이다.

따라서 실제 고위험 실행은 다음 조건을 확인해야 한다.

```text
Authenticated Actor

+

Valid Delegation

+

Correct Action / Resource

+

Correct Audience

+

Business Authorization

+

Human Approval

+

Idempotency
```

또한 권한 위임은 한 번 생성한 뒤 계속 사용하는 정적인 정보가 아니다.

```text
ISSUED

↓

ACTIVE

↓

USED / EXPIRED / REVOKED
```

와 같은 생명주기를 가진다.

특히 Queue 작업은 생성 당시 권한이 유효했더라도 실행 시점에 다시 검증해야 한다.

현재 프로젝트에서는 당장 복잡한 OAuth 기반 Multi-Agent 구조를 만드는 것보다 다음 순서가 적합하다.

```text
1. Agent Identity 구분

2. Read / Write Tool 분리

3. Tool Gateway 권한 검증

4. 고위험 작업 Approval

5. Audit Chain

6. One-time Execution

7. 필요 시 Delegation Grant

8. Revocation

9. Security Evaluation

10. Multi-Agent 확장
```

예를 들어 카카오 상담 자동화에서도 AI Agent를 여러 개 만드는 것이 목표가 아니다.

**고객 주문을 조회하는 작업, 조건 이미지를 추천하는 작업, 메시지를 작성하는 작업, 실제 전송하는 작업의 권한과 책임을 명확하게 구분하는 것**이 먼저다.

최종적으로 기억해야 할 원칙은 다음과 같다.

> **AI Agent는 작업을 다른 Agent에게 위임할 수 있지만, 그 과정에서 새로운 권한을 만들어내서는 안 된다. 모든 권한은 확인된 주체·허용된 작업·제한된 리소스·유효기간에 연결되어야 하며, 실제 실행 시 서버에서 다시 검증돼야 한다.**

이 구조가 확보되면 Codex·Claude Code·Local LLM·업무 자동화 프로그램을 함께 사용하더라도 각 Agent의 책임과 권한을 통제하기 쉬워진다.

**1022 운영 자동화/AI 워크플로우 심화 (46/N): Durable Agent Execution·Checkpoint·Task Lease·Crash Recovery·Human-in-the-Loop Resume와 장기 실행 AI 워크플로우**

1021에서는 여러 Agent가 협업할 때 신원과 권한을 어떻게 제한할지 다뤘다.

1022에서는 AI 작업이 장시간 실행되거나 중간에 중단되는 상황을 다룬다.

예를 들어:

```text
사용자 요청
      ↓
Supervisor Agent
      ↓
작업 계획
      ↓
Worker 실행
      ↓
Human Approval 대기
      ↓
서버 재시작
      ↓
작업 재개
```

같은 상황에서 **어디까지 작업했는지 기억하고, 중복 실행을 방지하고, 만료된 권한을 재검증하고, 장애 이후에도 안전하게 이어서 실행하는 구조**를 다룬다.

특히 NestJS·PostgreSQL·Scheduler·Queue·Local LLM을 활용해 별도의 대규모 Workflow Engine 없이 구현할 수 있는 Durable Agent Workflow를 중심으로 정리한다.
