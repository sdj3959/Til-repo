## 0829 백엔드 아키텍처 고도화 (6/N): Permission Policy, 관리자 권한과 접근 제어

---

### ✅ 1. 관리자 권한이 중요한 이유

* 관리자 화면은 고객 화면보다 더 위험합니다.
* 고객 화면은 주로 조회와 신청이 중심이지만, 관리자 화면은 상담 상태 변경, 상품 수정, 지원금 변경, 엑셀 다운로드, 알림 재발송, 관리자 계정 관리처럼 실제 운영 데이터에 직접 영향을 줍니다.
* 그래서 관리자 권한은 단순히 “로그인했는가?”만 보면 부족합니다.

```txt id="admin-permission-basic"
관리자 로그인
  ↓
상담 목록 조회
  ↓
상태 변경
  ↓
상품 수정
  ↓
엑셀 다운로드
  ↓
알림톡 재발송
  ↓
관리자 계정 관리
```

#### ➕ 1-1. 권한 설계가 없을 때 생기는 문제

```txt id="no-permission-problems"
모든 관리자가 모든 기능 사용 가능
실수로 상품/지원금 수정 가능
권한 없는 상담 데이터 열람 가능
개인정보가 담긴 엑셀 다운로드 가능
삭제/복구 같은 위험 작업 제한 불가
누가 어떤 권한으로 작업했는지 추적 어려움
```

* 관리자 기능은 편의성보다 안전성이 먼저입니다.
* 특히 엑셀 다운로드, 개인정보 조회, 상품 가격/지원금 수정, 삭제/복구는 반드시 권한을 나누는 것이 좋습니다.

---

### ✅ 2. 인증 Authentication과 인가 Authorization

* 관리자 권한을 이해하려면 인증과 인가를 구분해야 합니다.

| 개념             | 의미             | 예시            |
| -------------- | -------------- | ------------- |
| Authentication | 누구인지 확인        | 관리자 로그인       |
| Authorization  | 무엇을 할 수 있는지 확인 | 엑셀 다운로드 가능 여부 |

```txt id="auth-authz"
Authentication:
너는 누구인가?

Authorization:
너는 이 작업을 해도 되는가?
```

#### ➕ 2-1. 예시

```txt id="auth-example"
관리자 A 로그인 성공
  ↓
Authentication 성공

관리자 A가 상품 가격 수정 요청
  ↓
PRODUCT_UPDATE 권한 확인
  ↓
Authorization 성공/실패
```

* 로그인했다고 모든 작업을 해도 되는 것은 아닙니다.
* 로그인은 시작이고, 실제 기능마다 권한 확인이 필요합니다.

---

### ✅ 3. RBAC와 Permission

* 관리자 권한 설계에서 가장 흔한 방식은 **RBAC(Role-Based Access Control)**입니다.
* 역할을 만들고, 역할에 권한을 부여한 뒤, 관리자가 역할을 갖는 구조입니다.

```txt id="rbac-basic"
AdminUser
  ↓
Role
  ↓
Permission
```

#### ➕ 3-1. 예시

```txt id="role-permission-example"
SUPER_ADMIN:
모든 권한

MANAGER:
상담 조회/상태 변경/엑셀 다운로드

STAFF:
상담 조회/메모 작성/일부 상태 변경

MARKETER:
상품/배너 조회, 유입 통계 조회

VIEWER:
조회만 가능
```

#### ➕ 3-2. Permission 예시

```txt id="permission-list"
CONSULT_READ
CONSULT_UPDATE_STATUS
CONSULT_MEMO_WRITE
CONSULT_EXPORT
PRODUCT_READ
PRODUCT_CREATE
PRODUCT_UPDATE
PRODUCT_DELETE
PRODUCT_RESTORE
BANNER_UPDATE
NOTIFICATION_RESEND
ADMIN_USER_MANAGE
AUDIT_LOG_READ
```

* Role은 사람에게 붙는 묶음입니다.
* Permission은 실제 기능 단위입니다.
* 실무에서는 Role보다 Permission을 기준으로 코드를 작성하는 것이 더 유연합니다.

---

### ✅ 4. 권한을 Role 이름으로만 판단하면 생기는 문제

* 코드에서 `admin.role === 'SUPER_ADMIN'` 같은 조건이 많아지면 나중에 권한 변경이 어려워집니다.

#### ➕ 4-1. 나쁜 예시

```ts id="bad-role-check"
if (admin.role !== 'SUPER_ADMIN') {
  throw new ForbiddenException();
}
```

문제:

```txt id="bad-role-check-problems"
MANAGER에게 일부 권한만 주기 어려움
역할이 늘어날수록 if문 증가
권한 정책이 코드 곳곳에 흩어짐
운영 중 권한 조정이 어려움
```

#### ➕ 4-2. 더 나은 방식

```ts id="permission-check-example"
if (!admin.permissions.includes('PRODUCT_UPDATE')) {
  throw new ForbiddenException('상품 수정 권한이 없습니다.');
}
```

#### ➕ 4-3. 기준

```txt id="permission-better-standard"
Role:
권한 묶음

Permission:
실제 기능 접근 기준

코드:
Permission 기준으로 판단
```

* 권한 확인은 Role보다 Permission 단위로 하는 것이 좋습니다.
* Role은 Permission을 묶어주는 관리 편의 구조로 두면 됩니다.

---

### ✅ 5. 권한 테이블 설계

* 관리자 권한이 단순하면 `admin_users.role` 하나로 시작할 수 있습니다.
* 하지만 기능이 많아지면 roles, permissions, role_permissions 구조가 더 유연합니다.

#### ➕ 5-1. 단순 구조

```prisma id="simple-admin-role-prisma"
model AdminUser {
  id        Int       @id @default(autoincrement())
  email     String    @unique
  name      String
  role      AdminRole
  isActive  Boolean   @default(true)
  createdAt DateTime  @default(now())
  updatedAt DateTime  @updatedAt
}

enum AdminRole {
  SUPER_ADMIN
  MANAGER
  STAFF
  VIEWER
}
```

장점:

```txt id="simple-role-benefit"
구현이 쉬움
초기 서비스에 충분
관리 화면 단순
```

단점:

```txt id="simple-role-risk"
권한 세부 조정 어려움
역할이 늘어나면 코드 수정 많아짐
운영 중 개별 권한 부여 어려움
```

---

#### ➕ 5-2. 확장 구조

```prisma id="rbac-prisma"
model AdminUser {
  id        Int       @id @default(autoincrement())
  email     String    @unique
  name      String
  isActive  Boolean   @default(true)

  roleId    Int
  role      Role      @relation(fields: [roleId], references: [id])

  createdAt DateTime  @default(now())
  updatedAt DateTime  @updatedAt
  disabledAt DateTime?
}

model Role {
  id          Int              @id @default(autoincrement())
  code        String           @unique
  name        String
  description String?

  users       AdminUser[]
  permissions RolePermission[]

  createdAt   DateTime         @default(now())
  updatedAt   DateTime         @updatedAt
}

model Permission {
  id          Int              @id @default(autoincrement())
  code        String           @unique
  name        String
  description String?

  roles       RolePermission[]

  createdAt   DateTime         @default(now())
  updatedAt   DateTime         @updatedAt
}

model RolePermission {
  roleId       Int
  permissionId Int

  role         Role       @relation(fields: [roleId], references: [id])
  permission   Permission @relation(fields: [permissionId], references: [id])

  @@id([roleId, permissionId])
}
```

#### ➕ 5-3. 현재 프로젝트 기준

```txt id="rbac-current-standard"
초기:
AdminRole enum + 코드상 permission mapping

확장:
roles / permissions 테이블

권장:
처음에는 단순하게 시작하되 permission code 기준으로 설계
```

* 처음부터 너무 복잡한 RBAC 테이블을 만들 필요는 없습니다.
* 다만 코드에서는 권한명을 Permission 단위로 생각해두는 것이 좋습니다.

### ✅ 6. Permission Code 설계

* Permission Code는 기능 단위로 명확해야 합니다.
* 너무 추상적이거나 너무 세밀하면 관리가 어려워집니다.

#### ➕ 6-1. 좋은 Permission Code

```txt id="good-permission-codes"
CONSULT_READ
CONSULT_DETAIL_READ
CONSULT_UPDATE_STATUS
CONSULT_MEMO_WRITE
CONSULT_EXPORT

PRODUCT_READ
PRODUCT_CREATE
PRODUCT_UPDATE
PRODUCT_DELETE
PRODUCT_RESTORE

BANNER_READ
BANNER_UPDATE

NOTIFICATION_READ
NOTIFICATION_RESEND

EXPORT_JOB_READ
EXPORT_JOB_DOWNLOAD

AUDIT_LOG_READ

ADMIN_USER_READ
ADMIN_USER_CREATE
ADMIN_USER_UPDATE
ADMIN_USER_DISABLE
ADMIN_PERMISSION_MANAGE
```

#### ➕ 6-2. 나쁜 Permission Code

```txt id="bad-permission-codes"
ADMIN
USER
DATA
MANAGE
UPDATE
READ_ALL
DO_ANYTHING
```

문제:

```txt id="bad-permission-code-problems"
무엇을 허용하는지 불명확
기능별 제어 어려움
감사 로그에서 의미 파악 어려움
운영자가 이해하기 어려움
```

#### ➕ 6-3. 설계 기준

```txt id="permission-code-standard"
도메인_행위 형태
기능 단위로 명확하게
운영자가 봐도 이해 가능하게
너무 세부적인 버튼 단위는 지양
위험 작업은 별도 권한으로 분리
```

* `CONSULT_EXPORT`처럼 위험도가 높은 기능은 별도 권한으로 빼야 합니다.
* 조회 권한과 다운로드 권한은 반드시 분리하는 것이 좋습니다.

### ✅ 8. Guard의 역할

* NestJS에서 Guard는 요청이 Controller에 도달하기 전에 접근 가능 여부를 판단합니다.
* 인증 Guard와 권한 Guard를 나눌 수 있습니다.

```txt id="guard-flow"
Request
  ↓
AuthGuard
  ↓
PermissionGuard
  ↓
Controller
  ↓
Use Case
```

#### ➕ 8-1. AuthGuard

```txt id="auth-guard-role"
JWT 확인
관리자 세션 확인
관리자 활성 상태 확인
CurrentAdmin 세팅
```

#### ➕ 8-2. PermissionGuard

```txt id="permission-guard-role"
Route에 필요한 permission metadata 확인
현재 관리자 permission 확인
없으면 403 반환
```

#### ➕ 8-3. 기준

```txt id="guard-standard"
로그인 여부:
AuthGuard

기본 permission:
PermissionGuard

세부 비즈니스 권한:
Use Case/Policy
```

* Guard는 공통 접근 제어에 좋습니다.
* 다만 “이 상담을 이 관리자가 바꿀 수 있는가?” 같은 세부 정책은 Use Case/Policy에서 확인하는 것이 좋습니다.

---

### ✅ 9. Permission Decorator

* Controller route에 필요한 권한을 명시하기 위해 Decorator를 만들 수 있습니다.

#### ➕ 9-1. Decorator 예시

```ts id="permission-decorator"
export const PERMISSIONS_KEY = 'permissions';

export const RequirePermissions = (...permissions: PermissionCode[]) =>
  SetMetadata(PERMISSIONS_KEY, permissions);
```

#### ➕ 9-2. Controller 사용 예시

```ts id="permission-controller-example"
@Get()
@RequirePermissions('CONSULT_READ')
findConsults() {
  return this.getConsultListUseCase.execute();
}

@Post(':id/status')
@RequirePermissions('CONSULT_UPDATE_STATUS')
updateStatus() {
  return this.updateConsultStatusUseCase.execute();
}

@Post('export')
@RequirePermissions('CONSULT_EXPORT')
requestExport() {
  return this.requestConsultExportUseCase.execute();
}
```

#### ➕ 9-3. 장점

```txt id="permission-decorator-benefit"
Route별 필요한 권한이 명확함
Controller에서 권한 요구사항 확인 가능
PermissionGuard에서 공통 처리 가능
```

* 권한 Decorator는 문서 역할도 합니다.
* 어떤 API가 어떤 권한을 요구하는지 코드만 봐도 알 수 있습니다.

### ✅ 10. PermissionGuard 구현 예시

```ts id="permission-guard-example"
@Injectable()
export class PermissionGuard implements CanActivate {
  constructor(private readonly reflector: Reflector) {}

  canActivate(context: ExecutionContext): boolean {
    const requiredPermissions =
      this.reflector.getAllAndOverride<PermissionCode[]>(
        PERMISSIONS_KEY,
        [context.getHandler(), context.getClass()],
      ) ?? [];

    if (requiredPermissions.length === 0) {
      return true;
    }

    const request = context.switchToHttp().getRequest();
    const admin = request.user as CurrentAdmin;

    if (!admin) {
      throw new UnauthorizedException();
    }

    if (admin.permissions.includes('*')) {
      return true;
    }

    const hasPermission = requiredPermissions.every((permission) =>
      admin.permissions.includes(permission),
    );

    if (!hasPermission) {
      throw new ForbiddenException('접근 권한이 없습니다.');
    }

    return true;
  }
}
```

#### ➕ 10-1. `every`와 `some`

```txt id="permission-every-some"
every:
필요한 권한을 모두 가져야 함

some:
필요한 권한 중 하나만 있으면 됨
```

#### ➕ 10-2. 기준

```txt id="permission-check-mode-standard"
대부분:
every

여러 권한 중 하나 허용:
RequireAnyPermission 같은 별도 decorator
```

* 권한 체크 방식은 명확해야 합니다.
* `모든 권한 필요`인지 `하나만 있으면 되는지`를 섞어 쓰면 혼란이 생깁니다.

### ✅ 11. CurrentAdmin 설계

* 요청마다 현재 관리자 정보를 가져와야 합니다.
* JWT payload 또는 세션에서 관리자 ID를 확인하고, 필요한 권한 정보를 붙입니다.

#### ➕ 11-1. CurrentAdmin 타입

```ts id="current-admin-type"
export type CurrentAdmin = {
  id: number;
  email: string;
  name: string;
  role: AdminRole;
  permissions: PermissionCode[];
  isActive: boolean;
};
```

#### ➕ 11-2. Decorator 예시

```ts id="current-admin-decorator"
export const CurrentAdmin = createParamDecorator(
  (_data: unknown, ctx: ExecutionContext) => {
    const request = ctx.switchToHttp().getRequest();

    return request.user;
  },
);
```

#### ➕ 11-3. 주의

```txt id="current-admin-caution"
JWT에 너무 많은 권한 정보를 넣으면 변경 반영이 늦을 수 있음
권한 변경 즉시 반영 필요하면 DB/cache 조회 필요
비활성화된 관리자 차단 필요
권한 정보가 오래된 경우 대응 필요
```

* 권한을 JWT에 넣으면 빠르지만 권한 변경 반영이 늦을 수 있습니다.
* 관리자 수가 많지 않다면 요청 시 DB/cache에서 권한을 읽는 것도 현실적입니다.

---

### ✅ 12. 권한 캐싱

* 매 요청마다 DB에서 권한을 조회하면 비용이 생깁니다.
* Redis나 메모리 캐시를 사용할 수 있지만, 초기에는 단순하게 시작해도 됩니다.

#### ➕ 12-1. 캐싱 후보

```txt id="permission-cache-candidates"
adminId별 permissions
role별 permissions
permission code 목록
```

#### ➕ 12-2. 캐싱 주의점

```txt id="permission-cache-caution"
권한 변경 시 cache invalidation 필요
비활성 관리자 즉시 차단 필요
캐시가 오래되면 권한 오류 가능
관리자 수가 적으면 DB 조회로도 충분
```

#### ➕ 12-3. 현재 기준 추천

```txt id="permission-cache-recommend"
초기:
JWT + DB 확인 또는 단순 DB 조회

규모 증가:
role permission cache

권한 변경이 잦음:
cache invalidation 구조 필요
```

* 캐시는 성능을 위해 쓰지만, 권한에서는 정확성이 더 중요합니다.
* 지금 규모에서는 복잡한 캐시보다 명확한 권한 구조가 먼저입니다.

### ✅ 13. 세부 비즈니스 권한 Policy

* Guard는 “이 API를 호출할 권한이 있는가?”를 확인합니다.
* 하지만 실제 업무에서는 더 세부적인 조건이 필요할 수 있습니다.

```txt id="business-policy-need"
CONSULT_UPDATE_STATUS 권한은 있음
  ↓
하지만 CONVERTED 상태로 변경할 수 있는가?
  ↓
이 상담이 본인 담당 상담인가?
  ↓
이미 최종 상태인데 변경 가능한가?
```

#### ➕ 13-1. Policy 예시

```ts id="consult-permission-policy"
@Injectable()
export class ConsultPermissionPolicy {
  canChangeStatus(params: {
    admin: CurrentAdmin;
    currentStatus: ConsultStatus;
    nextStatus: ConsultStatus;
    assignedAdminId?: number | null;
  }) {
    if (params.admin.permissions.includes('*')) {
      return true;
    }

    if (!params.admin.permissions.includes('CONSULT_UPDATE_STATUS')) {
      return false;
    }

    if (params.nextStatus === 'CONVERTED') {
      return params.admin.permissions.includes('CONSULT_MARK_CONVERTED');
    }

    if (
      params.assignedAdminId &&
      params.assignedAdminId !== params.admin.id &&
      !params.admin.permissions.includes('CONSULT_UPDATE_OTHERS')
    ) {
      return false;
    }

    return true;
  }
}
```

#### ➕ 13-2. Use Case에서 사용

```ts id="policy-in-use-case"
const canChange = this.consultPermissionPolicy.canChangeStatus({
  admin: command.admin,
  currentStatus: consult.status,
  nextStatus: command.nextStatus,
  assignedAdminId: consult.assignedAdminId,
});

if (!canChange) {
  throw new ForbiddenException('해당 상담 상태를 변경할 권한이 없습니다.');
}
```

* 세부 정책은 Guard보다 Use Case에서 처리하는 것이 좋습니다.
* Use Case는 현재 데이터 상태를 알고 있기 때문입니다.

### ✅ 14. 권한과 상태 전이의 차이

* 권한과 상태 전이는 서로 다른 개념입니다.

| 구분    | 질문                        |
| ----- | ------------------------- |
| 권한    | 이 관리자가 이 작업을 해도 되는가?      |
| 상태 전이 | 이 상태에서 저 상태로 바뀌는 것이 가능한가? |

```txt id="permission-vs-transition"
관리자가 권한 있음
  ↓
하지만 상태 전이가 불가능할 수 있음

상태 전이는 가능함
  ↓
하지만 관리자가 권한이 없을 수 있음
```

#### ➕ 14-1. 예시

```txt id="permission-transition-example"
현재 상태:
CANCELED

요청:
CONVERTED로 변경

관리자:
SUPER_ADMIN

결과:
권한은 있어도 상태 전이 규칙상 불가로 처리할 수 있음
```

#### ➕ 14-2. 처리 순서

```txt id="permission-transition-order"
1. 상담 조회
2. 권한 확인
3. 상태 전이 검증
4. 상태 변경
```

또는:

```txt id="permission-transition-order-2"
1. 상담 조회
2. 상태 전이 검증
3. 권한 확인
4. 상태 변경
```

#### ➕ 14-3. 기준

```txt id="permission-transition-standard"
둘 다 통과해야 상태 변경 가능
권한 실패는 403
상태 전이 실패는 400
정책상 보안을 우선하면 권한 먼저 확인
```

* 권한과 상태 전이를 하나의 if문으로 섞지 않는 것이 좋습니다.
* `ConsultPermissionPolicy`와 `ConsultStatusService`로 분리하면 관리가 쉬워집니다.

### ✅ 22. 권한 변경과 세션 무효화

* 관리자의 권한이 바뀌었는데 기존 JWT가 계속 유효하면 문제가 될 수 있습니다.
* 특히 권한을 제거했는데 이전 토큰으로 계속 기능을 사용할 수 있으면 위험합니다.

#### ➕ 22-1. 해결 방식 후보

```txt id="permission-session-solutions"
Access Token 짧게 유지
권한 변경 시 tokenVersion 증가
요청마다 관리자 isActive/roleVersion 확인
Redis/session store 사용
강제 로그아웃 처리
```

#### ➕ 22-2. tokenVersion 방식

```txt id="token-version-flow"
admin_users.tokenVersion = 3

JWT payload:
tokenVersion = 3

권한 변경:
admin_users.tokenVersion = 4

기존 JWT:
tokenVersion = 3
  ↓
요청 시 불일치
  ↓
재로그인 필요
```

#### ➕ 22-3. 기준

```txt id="session-invalidation-standard"
초기:
access token 만료 시간을 짧게

권한 변경이 민감:
tokenVersion 도입

관리자 수가 적음:
요청 시 DB 확인도 가능
```

* 관리자 권한은 일반 사용자 권한보다 민감합니다.
* 권한 제거가 빠르게 반영되는 구조를 고려해야 합니다.

```txt id="codex-permission-prompt"
NestJS 관리자 API에 Permission 기반 접근 제어를 추가해줘.

조건:
1. Role 이름만으로 권한을 판단하지 말고 PermissionCode 기준으로 설계해줘
2. PermissionCode 타입을 만들고 CONSULT_READ, CONSULT_UPDATE_STATUS, CONSULT_EXPORT, PRODUCT_UPDATE, ADMIN_USER_MANAGE 등을 정의해줘
3. RequirePermissions decorator를 만들어줘
4. PermissionGuard에서 route metadata의 permission을 확인하게 해줘
5. CurrentAdmin에는 id, email, role, permissions를 포함해줘
6. /me API에서 현재 관리자 권한 목록을 내려주게 해줘
7. 상담 상태 변경 API에는 CONSULT_UPDATE_STATUS 권한을 적용해줘
8. 상담 엑셀 다운로드 요청 API에는 CONSULT_EXPORT 권한을 적용해줘
9. 상품 수정 API에는 PRODUCT_UPDATE 권한을 적용해줘
10. 관리자 계정 관리 API에는 ADMIN_USER_MANAGE 권한을 적용해줘
11. 프론트 버튼 숨김은 보조 수단이고 백엔드 API에서 반드시 403을 반환하게 해줘
12. 권한 변경 작업은 Audit Log에 남길 수 있도록 구조를 제안해줘
13. 변경 후 테스트 케이스와 QA 체크리스트를 정리해줘
```

### 📌 요약

* 관리자 권한 설계는 단순 로그인 확인이 아니라, 어떤 관리자가 어떤 기능을 실행할 수 있는지 제어하는 구조입니다.
* 인증은 “누구인지 확인”이고, 인가는 “무엇을 할 수 있는지 확인”입니다.
* Role은 권한 묶음이고 Permission은 실제 기능 단위이므로, 코드에서는 Role 이름보다 PermissionCode 기준으로 판단하는 것이 유연합니다.
* 현재 프로젝트에서는 `CONSULT_READ`, `CONSULT_UPDATE_STATUS`, `CONSULT_EXPORT`, `PRODUCT_UPDATE`, `PRODUCT_DELETE`, `NOTIFICATION_RESEND`, `AUDIT_LOG_READ`, `ADMIN_USER_MANAGE` 같은 권한을 먼저 정의할 수 있습니다.
* NestJS에서는 `RequirePermissions` decorator와 `PermissionGuard`를 사용해 route별 권한을 공통으로 검증할 수 있습니다.
* Guard는 API 호출 권한을 확인하고, “이 상담을 이 관리자가 특정 상태로 바꿀 수 있는가?” 같은 세부 정책은 Use Case 내부의 Policy에서 처리하는 것이 좋습니다.
* 상담 상태 변경에서는 권한 검증과 상태 전이 검증을 분리해야 합니다. 권한은 관리자 기준이고, 상태 전이는 데이터 상태 기준입니다.
* 엑셀 다운로드는 일반 조회보다 훨씬 민감하므로 `CONSULT_READ`와 `CONSULT_EXPORT`를 분리하고, 다운로드 요청과 실제 다운로드를 Audit Log에 남기는 것이 좋습니다.
* 관리자 계정 생성, 비활성화, 권한 변경은 가장 위험한 기능이므로 극소수에게만 허용하고, 마지막 SUPER_ADMIN 비활성화 같은 상황을 막아야 합니다.
* 프론트에서 권한 없는 메뉴와 버튼을 숨기는 것은 UX 개선일 뿐이며, 실제 보안은 백엔드 API의 Guard/Policy가 담당해야 합니다.
* 권한 변경 후 기존 token/session이 계속 유효하면 위험할 수 있으므로 access token 만료 시간, tokenVersion, 강제 로그아웃 같은 기준을 고려해야 합니다.
