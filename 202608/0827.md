## 0827 백엔드 아키텍처 고도화 (4/N): Queue/Worker, ExportJob과 알림톡 발송 구조

---

### ✅ 1. Queue/Worker가 필요한 이유

* 백엔드 API는 사용자의 요청을 받고 빠르게 응답해야 합니다.
* 하지만 모든 작업을 API 요청 안에서 바로 처리하면 응답이 느려지고, 실패했을 때 복구하기 어렵습니다.
* 특히 엑셀 다운로드, 알림톡/SMS 발송, 이미지 처리, 외부 API 연동, 대량 데이터 처리 같은 작업은 API 요청과 분리하는 것이 좋습니다.

```txt id="queue-worker-basic"
API 요청
  ↓
DB에 작업 생성
  ↓
빠르게 응답
  ↓
Worker가 뒤에서 작업 처리
  ↓
작업 결과 DB에 저장
```

#### ➕ 1-1. API 안에서 바로 처리하면 생기는 문제

```txt id="sync-processing-problems"
API 응답이 느려짐
timeout 발생 가능
외부 API 장애가 고객 요청에 직접 영향
엑셀 생성 중 서버 메모리 사용 증가
작업 실패 시 재시도 어려움
작업 진행 상태를 관리자에게 보여주기 어려움
```

* 고객 상담 신청은 빠르게 저장되어야 합니다.
* 알림톡 발송이 실패하더라도 상담 신청 자체가 실패하면 안 됩니다.

---

### ✅ 2. Queue와 Worker 개념

* **Queue**는 처리해야 할 작업을 쌓아두는 대기열입니다.
* **Worker**는 Queue에 쌓인 작업을 하나씩 가져와 실행하는 프로세스입니다.
* DB 기반 Job 테이블로 시작할 수도 있고, Redis/BullMQ 같은 전문 Queue를 사용할 수도 있습니다.

```txt id="queue-worker-flow"
Producer:
작업 생성

Queue:
작업 대기

Worker:
작업 실행

Job Table:
작업 상태 기록
```

#### ➕ 2-1. 역할 정리

| 역할          | 설명                    |
| ----------- | --------------------- |
| Producer    | 작업을 생성하는 API Use Case |
| Queue       | 작업을 대기시키는 공간          |
| Worker      | 작업을 처리하는 실행자          |
| Job         | 처리해야 할 작업 단위          |
| Retry       | 실패한 작업 재시도            |
| Dead Letter | 반복 실패한 작업 격리          |

#### ➕ 2-2. 현재 프로젝트 기준 후보

```txt id="project-queue-candidates"
상담 접수 알림톡 발송
상태 변경 알림톡 발송
관리자 엑셀 Export
네이버/당근 EP 생성
대량 상품 이미지 처리
유입 분석 집계
외부 Webhook 재시도
```

* 처음부터 모든 작업을 Queue로 뺄 필요는 없습니다.
* 오래 걸리거나 실패 가능성이 높은 작업부터 분리하면 됩니다.

### ✅ 3. 동기 처리와 비동기 처리

* 동기 처리는 API 요청 안에서 바로 끝내는 방식입니다.
* 비동기 처리는 요청 시 작업만 등록하고, 실제 처리는 Worker가 나중에 하는 방식입니다.

#### ➕ 3-1. 동기 처리

```txt id="sync-processing"
요청
  ↓
상담 저장
  ↓
알림톡 API 호출
  ↓
알림톡 응답 대기
  ↓
응답 반환
```

장점:

```txt id="sync-benefits"
흐름이 단순함
결과를 바로 알 수 있음
초기 구현이 쉬움
```

단점:

```txt id="sync-risks"
외부 API가 느리면 전체 요청이 느림
외부 API 실패가 원본 저장 실패로 이어질 수 있음
재시도 구조가 약함
```

---

#### ➕ 3-2. 비동기 처리

```txt id="async-processing"
요청
  ↓
상담 저장
  ↓
notification_job 생성
  ↓
응답 반환
  ↓
Worker가 알림톡 발송
  ↓
결과 저장
```

장점:

```txt id="async-benefits"
API 응답이 빨라짐
외부 API 장애와 원본 저장 분리
재시도 가능
작업 상태 추적 가능
```

단점:

```txt id="async-risks"
구조가 조금 복잡해짐
Worker 운영 필요
작업 상태 관리 필요
```

* 실무에서는 고객 요청의 핵심 저장은 동기적으로 처리하고, 부가 작업은 비동기로 분리하는 방식이 안정적입니다.

### ✅ 4. Queue/Worker 도입 기준

* 모든 작업을 무조건 Worker로 빼는 것은 과합니다.
* 아래 조건에 해당하면 Queue/Worker 후보로 보면 됩니다.

```txt id="queue-adoption-standard"
처리 시간이 오래 걸림
외부 API를 호출함
실패 시 재시도가 필요함
작업 진행 상태를 보여줘야 함
대량 데이터를 처리함
파일 생성/업로드가 필요함
API timeout 가능성이 있음
```

#### ➕ 4-1. Worker로 빼기 좋은 작업

```txt id="good-worker-tasks"
엑셀 파일 생성
알림톡/SMS 발송
대량 상품 업데이트
외부 API 동기화
EP 파일 생성
통계 집계
S3 파일 정리
만료된 Export 파일 삭제
```

#### ➕ 4-2. API 안에서 바로 처리해도 되는 작업

```txt id="sync-ok-tasks"
단순 상담 저장
단순 목록 조회
단순 상태 변경
단순 메모 저장
짧은 validation
권한 확인
```

* 기준은 “작업이 오래 걸리거나 실패했을 때 다시 처리해야 하는가”입니다.
* 재시도가 필요한 작업은 Worker로 빼는 것이 좋습니다.

### ✅ 5. DB 기반 Job Table로 시작하기

* 처음부터 Redis Queue를 도입하지 않아도 됩니다.
* 현재 규모에서는 DB에 `jobs` 또는 도메인별 Job 테이블을 만들고, Worker가 주기적으로 처리하는 방식으로 시작할 수 있습니다.

```txt id="db-job-basic"
notification_jobs
export_jobs
ep_generation_jobs
cleanup_jobs
```

#### ➕ 5-1. DB 기반 Job의 장점

```txt id="db-job-benefits"
구현이 비교적 단순함
현재 PostgreSQL만으로 시작 가능
관리자 화면에서 작업 상태 확인 쉬움
트랜잭션과 함께 Job 생성 가능
작업 이력이 DB에 남음
```

#### ➕ 5-2. DB 기반 Job의 단점

```txt id="db-job-risks"
처리량이 많아지면 DB 부하
Worker 간 동시 처리 제어 필요
실시간성이 Redis Queue보다 약함
polling 구조가 필요할 수 있음
```

* 1인 개발자 프로젝트에서는 DB Job으로 시작하는 것이 현실적입니다.
* 처리량이 많아지고 Worker가 많아지면 BullMQ/Redis 같은 구조로 확장할 수 있습니다.

### ✅ 6. Job 상태 설계

* Job은 반드시 상태를 가져야 합니다.
* 그래야 관리자 화면에서 작업이 대기 중인지, 처리 중인지, 완료됐는지, 실패했는지 볼 수 있습니다.

```txt id="job-status-flow"
PENDING
  ↓
PROCESSING
  ↓
DONE

PROCESSING
  ↓
FAILED

FAILED
  ↓
RETRYING
  ↓
PROCESSING
```

#### ➕ 6-1. 기본 상태

| 상태           | 의미     |
| ------------ | ------ |
| `PENDING`    | 처리 대기  |
| `PROCESSING` | 처리 중   |
| `DONE`       | 처리 완료  |
| `FAILED`     | 처리 실패  |
| `RETRYING`   | 재시도 대기 |
| `CANCELED`   | 취소됨    |
| `EXPIRED`    | 만료됨    |

#### ➕ 6-2. 상태 설계 기준

```txt id="job-status-standard"
작업 흐름을 추적할 수 있어야 함
실패 사유를 저장해야 함
재시도 횟수를 저장해야 함
처리 시작/완료 시간을 저장해야 함
Worker가 죽어도 복구 가능해야 함
```

* Job 상태는 운영 화면과 장애 대응에 매우 중요합니다.
* 단순히 성공/실패만 두기보다 처리 중, 재시도, 만료까지 고려하는 것이 좋습니다.

### ✅ 7. ExportJob 테이블 설계

* 관리자 엑셀 다운로드는 대표적인 Worker 대상입니다.
* 일반 목록 API에서 `limit=100000`으로 한 번에 내려주는 방식은 위험합니다.
* 검색 조건을 snapshot으로 저장하고 Worker가 파일을 생성하는 구조가 좋습니다.

```txt id="export-job-flow"
관리자 엑셀 다운로드 요청
  ↓
export_jobs row 생성
  ↓
API는 jobId 반환
  ↓
Worker가 파일 생성
  ↓
S3 업로드
  ↓
export_jobs.status = DONE
  ↓
관리자 다운로드
```

#### ➕ 7-1. ExportJob 컬럼 후보

#### ➕ 7-2. Prisma Schema 예시

```prisma id="export-job-prisma"
model ExportJob {
  id                 Int             @id @default(autoincrement())
  type               ExportJobType
  status             JobStatus        @default(PENDING)

  requestedByAdminId Int
  requestedByAdmin   AdminUser        @relation(fields: [requestedByAdminId], references: [id])

  filterSnapshot     Json
  fileKey            String?
  fileUrl            String?
  errorCode          String?
  errorMessage       String?
  retryCount         Int              @default(0)

  requestedAt        DateTime         @default(now())
  startedAt          DateTime?
  finishedAt         DateTime?
  expiresAt          DateTime?

  createdAt          DateTime         @default(now())
  updatedAt          DateTime         @updatedAt

  @@index([status, createdAt])
  @@index([requestedByAdminId, createdAt])
}

enum ExportJobType {
  CONSULT_LIST
  ORDER_LIST
  AUDIT_LOG
}

enum JobStatus {
  PENDING
  PROCESSING
  DONE
  FAILED
  RETRYING
  CANCELED
  EXPIRED
}
```

#### ➕ 7-3. 설계 포인트

```txt id="export-job-design-point"
검색 조건을 filterSnapshot으로 저장
요청 관리자 ID 저장
상태와 실패 사유 저장
파일 만료 시간 저장
status + createdAt 인덱스 필요
```

* ExportJob은 단순 다운로드 기록이 아닙니다.
* “누가 어떤 조건으로 어떤 파일을 만들었는지”를 추적하는 운영 데이터입니다.

### ✅ 8. ExportJob 요청 Use Case

* ExportJob 요청 API는 실제 엑셀 파일을 만들지 않습니다.
* 권한 확인, 검색 조건 검증, ExportJob 생성, Audit Log 저장만 하고 응답합니다.

```txt id="request-export-use-case-flow"
권한 확인
  ↓
검색 조건 검증
  ↓
filterSnapshot 생성
  ↓
export_jobs 생성
  ↓
audit_logs 생성
  ↓
jobId 반환
```

#### ➕ 8-1. Use Case 예시

```ts id="request-consult-export-use-case"
@Injectable()
export class RequestConsultExportUseCase {
  constructor(
    private readonly prisma: PrismaService,
    private readonly exportJobRepository: ExportJobRepository,
    private readonly auditLogRepository: AuditLogRepository,
    private readonly exportPermissionPolicy: ExportPermissionPolicy,
  ) {}

  async execute(command: RequestConsultExportCommand) {
    if (!this.exportPermissionPolicy.canExportConsults(command.adminRole)) {
      throw new ForbiddenException('엑셀 다운로드 권한이 없습니다.');
    }

    return this.prisma.$transaction(async (tx) => {
      const job = await this.exportJobRepository.create(
        {
          type: 'CONSULT_LIST',
          status: 'PENDING',
          requestedByAdminId: command.adminId,
          filterSnapshot: command.filter,
          expiresAt: addDays(new Date(), 3),
        },
        tx,
      );

      await this.auditLogRepository.create(
        {
          actorType: 'ADMIN',
          actorId: command.adminId,
          action: 'EXPORT_DOWNLOAD_REQUEST',
          targetType: 'EXPORT_JOB',
          targetId: String(job.id),
          afterValue: {
            type: 'CONSULT_LIST',
          },
          requestId: command.requestId,
          ipAddress: command.ipAddress,
          userAgent: command.userAgent,
        },
        tx,
      );

      return {
        jobId: job.id,
        status: job.status,
      };
    });
  }
}
```

#### ➕ 8-2. 주의

```txt id="request-export-caution"
API에서 엑셀 파일을 바로 만들지 않기
검색 조건을 그대로 문자열 로그에 남기지 않기
개인정보 필터값은 Audit Log에 최소화
권한 없는 관리자 다운로드 차단
```

* ExportJob 요청은 빠르게 끝나야 합니다.
* 실제 파일 생성은 Worker가 담당합니다.

### ✅ 9. Export Worker 구조

* Export Worker는 대기 중인 ExportJob을 가져와 엑셀 파일을 만들고 S3에 업로드합니다.
* 작업 성공/실패를 DB에 기록해야 합니다.

```txt id="export-worker-flow"
PENDING job 조회
  ↓
PROCESSING으로 변경
  ↓
filterSnapshot 기준 데이터 조회
  ↓
엑셀 파일 생성
  ↓
S3 업로드
  ↓
DONE 처리
```

#### ➕ 9-1. Worker 예시 흐름

```ts id="export-worker-pseudo"
async processNextExportJob() {
  const job = await this.exportJobRepository.claimNextPendingJob();

  if (!job) {
    return;
  }

  try {
    const rows = await this.consultRepository.findForExport(
      job.filterSnapshot,
    );

    const file = await this.excelService.createConsultExcel(rows);

    const uploaded = await this.s3Adapter.upload({
      key: `exports/consults/${job.id}.xlsx`,
      body: file,
    });

    await this.exportJobRepository.markDone({
      jobId: job.id,
      fileKey: uploaded.key,
      fileUrl: uploaded.url,
      finishedAt: new Date(),
    });
  } catch (error) {
    await this.exportJobRepository.markFailed({
      jobId: job.id,
      errorCode: 'EXPORT_FAILED',
      errorMessage: getSafeErrorMessage(error),
    });
  }
}
```

#### ➕ 9-2. Worker에서 중요한 것

```txt id="export-worker-important"
Job 선점 처리
중복 처리 방지
실패 사유 저장
재시도 횟수 관리
파일 생성 중 메모리 사용 주의
S3 업로드 실패 처리
개인정보 파일 보안
```

* Worker는 조용히 돌아가기 때문에 로그와 상태 기록이 중요합니다.
* 실패했는데 아무 기록이 없으면 운영자가 원인을 알 수 없습니다.

### ✅ 10. Job 선점 Claim 처리

* Worker가 여러 개일 경우 같은 Job을 동시에 처리하면 안 됩니다.
* DB Job에서는 `PENDING` 상태를 `PROCESSING`으로 바꾸는 과정을 안전하게 처리해야 합니다.

```txt id="job-claim-basic"
Worker A:
PENDING job 조회

Worker B:
같은 PENDING job 조회

문제:
둘 다 같은 파일 생성 가능
```

#### ➕ 10-1. 상태 조건 update

```ts id="job-claim-update-many"
const result = await prisma.exportJob.updateMany({
  where: {
    id: jobId,
    status: 'PENDING',
  },
  data: {
    status: 'PROCESSING',
    startedAt: new Date(),
  },
});

if (result.count === 0) {
  return null;
}
```

#### ➕ 10-2. PostgreSQL `FOR UPDATE SKIP LOCKED`

```sql id="for-update-skip-locked"
SELECT id
FROM export_jobs
WHERE status = 'PENDING'
ORDER BY created_at ASC
LIMIT 1
FOR UPDATE SKIP LOCKED;
```

#### ➕ 10-3. 기준

```txt id="job-claim-standard"
초기:
status 조건 update로 시작 가능

Worker가 여러 개:
FOR UPDATE SKIP LOCKED 고려

처리량 증가:
Redis Queue/BullMQ 고려
```

* 처음에는 단일 Worker라면 단순하게 시작해도 됩니다.
* 하지만 Worker를 여러 개 띄우는 순간 Job 선점 처리가 중요해집니다.

### ✅ 11. NotificationJob 테이블 설계

```prisma id="notification-job-prisma"
  targetType          String

  channel             NotificationChannel
  templateCode        String
  recipientMasked     String?
  recipientEncrypted  String?
  payload             Json

  providerMessageId   String?
  errorCode           String?
  errorMessage        String?
  retryCount          Int          @default(0)

  scheduledAt         DateTime?
  startedAt           DateTime?
  sentAt              DateTime?

  createdAt           DateTime     @default(now())
  updatedAt           DateTime     @updatedAt

  @@index([status, scheduledAt])
  @@index([targetType, targetId, createdAt])
}

enum NotificationChannel {
  ALIMTALK
  SMS
  EMAIL
}
```

#### ➕ 11-3. 주의

```txt id="notification-job-caution"
전화번호 원본 저장 주의
recipientEncrypted 또는 별도 보안 기준 필요
recipientMasked는 관리자 화면 표시용
payload에 개인정보 과다 저장 금지
외부 API Secret 저장 금지
```

* NotificationJob에는 수신자 정보가 들어갈 수 있으므로 개인정보 관리가 중요합니다.
* 관리자 화면에는 마스킹된 번호만 보여주는 것이 좋습니다.

### ✅ 12. 상담 신청과 NotificationJob 생성

* 상담 신청 Use Case에서는 알림톡을 실제로 보내지 않고, Job만 생성합니다.
* 상담 저장과 Job 생성은 같은 transaction으로 묶는 것이 좋습니다.

```txt id="consult-notification-transaction"
Transaction 시작
  ↓
consults 생성
  ↓
notification_jobs 생성
  ↓
commit
  ↓
Worker가 발송
```

#### ➕ 12-1. Use Case 예시

```ts id="create-consult-with-notification-job"
await this.prisma.$transaction(async (tx) => {
  const consult = await this.consultRepository.createWithSnapshot(
    {
      customerName: command.customerName,
      phoneMasked: command.phoneMasked,
      phoneEncrypted: command.phoneEncrypted,
      productId: product.id,
      productNameSnapshot: product.modelName,
      carrierSnapshot: product.carrier,
      source: command.source,
      visitorId: command.visitorId,
    },
    tx,
  );

  await this.notificationJobRepository.create(
    {
      type: 'CONSULT_RECEIVED',
      targetType: 'CONSULT',
      targetId: String(consult.id),
      channel: 'ALIMTALK',
      templateCode: 'CONSULT_RECEIVED',
      recipientMasked: command.phoneMasked,
      recipientEncrypted: command.phoneEncrypted,
      payload: {
        consultId: consult.id,
        productName: product.modelName,
      },
    },
    tx,
  );

  return consult;
});
```

#### ➕ 12-2. 설계 포인트

```txt id="consult-notification-design-point"
상담 저장 실패 시 Job도 생성되지 않음
Job 생성 실패 시 상담 저장도 rollback 여부 결정
실제 발송은 transaction 밖에서 Worker가 처리
payload에는 필요한 값만 저장
```

* 일반적으로 상담 접수 알림 Job 생성은 상담 저장과 함께 성공해야 합니다.
* 하지만 실제 발송 실패는 상담 저장 실패로 이어지면 안 됩니다.

### ✅ 13. Notification Worker

* Notification Worker는 `PENDING` 상태의 알림 Job을 가져와 외부 알림톡/SMS API를 호출합니다.
* 성공하면 `DONE` 또는 `SENT`, 실패하면 `FAILED` 또는 `RETRYING`으로 바꿉니다.

```txt id="notification-worker-flow"
PENDING notification job 조회
  ↓
PROCESSING으로 변경
  ↓
recipient 복호화
  ↓
알림톡 API 호출
  ↓
성공/실패 결과 저장
```

#### ➕ 13-1. Worker 예시

```ts id="notification-worker-pseudo"
async processNextNotificationJob() {
  const job = await this.notificationJobRepository.claimNextPendingJob();

  if (!job) {
    return;
  }

  try {
    const recipient = this.cryptoService.decrypt(job.recipientEncrypted);

    const result = await this.alimtalkAdapter.send({
      phone: recipient,
      templateCode: job.templateCode,
      payload: job.payload,
    });

    await this.notificationJobRepository.markSent({
      jobId: job.id,
      providerMessageId: result.messageId,
      sentAt: new Date(),
    });
  } catch (error) {
    await this.notificationJobRepository.markFailedOrRetry({
      jobId: job.id,
      errorCode: getProviderErrorCode(error),
      errorMessage: getSafeErrorMessage(error),
    });
  }
}
```

#### ➕ 13-2. 주의

```txt id="notification-worker-caution"
수신 전화번호 로그 출력 금지
외부 API 응답에 개인정보 포함 여부 확인
실패 메시지에 Secret 포함되지 않게 필터링
재시도 횟수 제한
동일 알림 중복 발송 방지
```

* 알림 Worker는 개인정보와 외부 API를 동시에 다루므로 특히 조심해야 합니다.
* 로그에 전화번호 원본을 남기지 않는 기준이 필요합니다.

### ✅ 14. Retry 설계

* 외부 API는 언제든 실패할 수 있습니다.
* 일시적인 실패는 재시도할 수 있어야 하지만, 무한 재시도는 안 됩니다.

```txt id="retry-basic"
1차 실패
  ↓
retryCount 증가
  ↓
일정 시간 후 재시도
  ↓
최대 횟수 초과 시 FAILED
```

#### ➕ 14-1. 재시도할 수 있는 실패

```txt id="retryable-errors"
외부 API 일시 장애
네트워크 timeout
rate limit
일시적인 서버 오류
```

#### ➕ 14-2. 재시도하면 안 되는 실패

```txt id="non-retryable-errors"
잘못된 전화번호
잘못된 템플릿 코드
권한/인증 정보 오류
필수 변수 누락
수신 거부
```

#### ➕ 14-3. 재시도 정책 예시

```txt id="retry-policy-example"
최대 재시도:
3회

간격:
1분 → 5분 → 15분

최종 실패:
FAILED 상태 저장
관리자 화면에서 실패 사유 표시
```

#### ➕ 14-4. Backoff

```txt id="retry-backoff"
재시도할수록 간격을 늘림
외부 API 장애 중 무리한 반복 호출 방지
```

* 모든 실패를 재시도하면 오히려 문제가 커질 수 있습니다.
* 실패 유형별로 재시도 가능 여부를 구분해야 합니다.

---

### ✅ 15. Idempotency와 중복 발송 방지

* Worker는 같은 Job을 두 번 처리할 수 있는 상황을 항상 고려해야 합니다.
* 서버 재시작, Worker 중복 실행, 네트워크 timeout 때문에 실제 발송은 됐지만 결과 저장이 실패하는 경우가 생길 수 있습니다.

```txt id="duplicate-send-risk"
Worker가 알림톡 발송 성공
  ↓
DB markSent 전에 서버 죽음
  ↓
Job은 PROCESSING 또는 PENDING 상태
  ↓
재시도 시 같은 알림 다시 발송 가능
```

#### ➕ 15-1. 대응 방향

```txt id="idempotency-notification"
provider idempotency key 사용 가능 여부 확인
Job ID를 외부 요청 고유키로 사용
발송 전 중복 여부 확인
targetType + targetId + type unique 고려
상태 transition 조건 update 사용
```

#### ➕ 15-2. Unique 후보

```sql id="notification-job-unique-example"
CREATE UNIQUE INDEX uniq_notification_target_type
ON notification_jobs (target_type, target_id, type)
WHERE status IN ('PENDING', 'PROCESSING', 'DONE');
```

#### ➕ 15-3. 주의

```txt id="idempotency-caution"
같은 상담에 같은 알림을 여러 번 보내야 하는 경우도 있음
재발송 기능과 자동 중복 방지를 구분
수동 재발송은 별도 type 또는 resendGroup 사용 고려
```

* 알림은 중복 발송되면 고객 경험이 나빠집니다.
* 하지만 수동 재발송까지 막으면 운영이 불편할 수 있으므로 정책을 구분해야 합니다.

### ✅ 16. Job Timeout과 Stuck Job 처리

* Worker가 작업 중 죽으면 Job이 `PROCESSING` 상태에 영원히 남을 수 있습니다.
* 이런 Job을 **Stuck Job**이라고 볼 수 있습니다.

```txt id="stuck-job-example"
Job status = PROCESSING
startedAt = 3시간 전
Worker는 이미 종료됨
결과:
작업이 다시 처리되지 않음
```

#### ➕ 16-1. 처리 기준

```txt id="stuck-job-solution"
PROCESSING 상태가 일정 시간 이상 지속되면 감지
retryCount 확인
RETRYING 또는 FAILED로 변경
관리자 화면에 표시
```

#### ➕ 16-2. 예시

```ts id="stuck-job-cleanup"
await prisma.exportJob.updateMany({
  where: {
    status: 'PROCESSING',
    startedAt: {
      lt: subMinutes(new Date(), 30),
    },
  },
  data: {
    status: 'RETRYING',
    errorCode: 'JOB_TIMEOUT',
    errorMessage: '작업 시간이 초과되어 재시도 대기 상태로 변경되었습니다.',
    retryCount: {
      increment: 1,
    },
  },
});
```

#### ➕ 16-3. 주의

```txt id="stuck-job-caution"
긴 작업과 멈춘 작업을 구분해야 함
작업별 timeout 기준 다르게 설정
엑셀 대량 생성은 더 긴 timeout 가능
알림톡 발송은 짧은 timeout 가능
```

* Worker 운영에서는 Job이 멈춰 있는지 확인하는 장치가 필요합니다.
* 관리자 화면에서 오래 걸리는 작업을 확인할 수 있으면 좋습니다.

### ✅ 17. Worker 실행 방식

* Worker는 여러 방식으로 실행할 수 있습니다.
* NestJS 애플리케이션 안에서 interval로 돌릴 수도 있고, 별도 프로세스로 분리할 수도 있습니다.

#### ➕ 17-1. API 서버 내부 interval

```txt id="worker-in-api-server"
API 서버 안에서 setInterval 또는 Schedule 사용
```

장점:

```txt id="worker-in-api-benefit"
구현이 쉬움
별도 배포가 필요 없음
초기 단계에 적합
```

단점:

```txt id="worker-in-api-risk"
API 서버와 Worker 부하가 섞임
서버 여러 대일 때 중복 처리 위험
장기 작업이 API 서버에 영향
```

---

#### ➕ 17-2. 별도 Worker 프로세스

```txt id="worker-separate-process"
API 서버:
요청 처리

Worker 서버:
Job 처리
```

장점:

```txt id="worker-separate-benefit"
API 부하와 작업 부하 분리
Worker만 재시작 가능
작업 종류별 확장 가능
```

단점:

```txt id="worker-separate-risk"
배포/운영 복잡도 증가
로그/모니터링 추가 필요
```

#### ➕ 17-3. 현재 기준 추천

```txt id="worker-current-recommend"
초기:
NestJS Schedule 또는 간단한 Worker 프로세스

작업량 증가:
별도 Worker 프로세스 분리

처리량 증가:
Redis Queue/BullMQ 도입 검토
```

* 지금 단계에서는 단순 DB Job + 별도 Worker 프로세스 또는 Schedule로 시작해도 충분합니다.
* 단, 중복 처리 방지와 실패 상태 기록은 처음부터 고려해야 합니다.

### ✅ 18. BullMQ/Redis를 쓰는 경우

* 작업량이 많아지거나 실시간성이 필요하면 Redis 기반 Queue인 BullMQ를 고려할 수 있습니다.
* 다만 Redis 운영 비용과 복잡도가 추가됩니다.

```txt id="bullmq-basic"
API
  ↓
BullMQ Queue
  ↓
Redis
  ↓
Worker
```

#### ➕ 18-1. BullMQ 장점

```txt id="bullmq-benefit"
Queue 기능이 풍부함
retry/backoff 지원
delayed job 지원
concurrency 설정 가능
job progress 관리 가능
```

#### ➕ 18-2. BullMQ 단점

```txt id="bullmq-risk"
Redis 운영 필요
장애 지점 증가
초기 구조 복잡도 증가
DB Job과 상태 중복 관리 가능성
```

#### ➕ 18-3. 실무 기준

```txt id="bullmq-standard"
DB Job으로 충분:
작업량 적음
관리자 Export 위주
알림 발송량 적음

BullMQ 고려:
작업량 많음
재시도/예약/동시성 제어가 중요
여러 Worker 확장이 필요
```

* 처음부터 BullMQ를 쓰는 것이 항상 정답은 아닙니다.
* 현재 규모에서는 DB Job으로 시작하고, 병목이 생기면 Redis Queue를 검토하는 편이 현실적입니다.

```md id="worker-failure-runbook"
- finishedAt:
- 최근 배포:
- 외부 API 장애 여부:

## 확인 절차
1. Worker 로그 확인
2. Job row 상태 확인
3. 같은 유형의 실패가 여러 건인지 확인
4. 외부 API 상태 확인
5. S3 업로드/권한 문제 확인
6. retry 가능한 오류인지 판단
7. 수동 retry 또는 FAILED 유지 결정
8. 필요 시 Worker 재시작
9. 관리자 화면 안내

## 주의
- 알림 중복 발송 여부 확인
- Export 파일 중복 생성 여부 확인
- 개인정보 로그 노출 여부 확인
- 수동 재시도 권한 확인
```

* Worker는 실패했을 때 조치 기준이 중요합니다.
* 특히 알림톡은 중복 발송 여부를 반드시 확인해야 합니다.

### 📌 요약

* Queue/Worker 구조는 API 요청 안에서 오래 걸리거나 실패 가능성이 높은 작업을 분리해 응답 속도와 운영 안정성을 높이는 방식입니다.
* 엑셀 Export, 알림톡/SMS 발송, EP 생성, 대량 처리, 외부 API 연동, 파일 업로드는 Worker로 분리하기 좋은 후보입니다.
* 처음부터 Redis/BullMQ를 도입하지 않아도 되고, 현재 규모에서는 PostgreSQL 기반 `export_jobs`, `notification_jobs` 테이블로 시작하는 것이 현실적입니다.
* Job은 `PENDING`, `PROCESSING`, `DONE`, `FAILED`, `RETRYING`, `EXPIRED` 같은 상태를 가져야 하며, 실패 사유와 retryCount를 저장해야 합니다.
* 관리자 엑셀 다운로드는 일반 목록 API에서 대량 데이터를 직접 내려주지 말고, `ExportJob`을 생성한 뒤 Worker가 검색 조건 snapshot 기준으로 파일을 생성하는 구조가 안전합니다.
* Export 파일은 개인정보가 포함될 수 있으므로 S3 private bucket, pre-signed URL, 만료 시간, 권한 확인, 다운로드 Audit Log, 파일 삭제 정책이 필요합니다.
* 상담 신청 후 알림톡 발송은 상담 저장 transaction 안에서 `NotificationJob` row만 생성하고, 실제 외부 API 호출은 Worker가 처리해야 합니다.
* Worker는 같은 Job을 중복 처리하지 않도록 status 조건 update, `FOR UPDATE SKIP LOCKED`, 또는 Queue 시스템의 claim 기능을 사용해야 합니다.
* 외부 API 실패는 재시도 가능한 실패와 재시도하면 안 되는 실패로 구분하고, retry/backoff와 maxRetry 기준을 둬야 합니다.
* 알림톡/SMS Worker는 전화번호 원본, 외부 API Secret, Authorization header, pre-signed URL이 로그에 남지 않도록 특히 조심해야 합니다.
* Worker 구조를 도입하면 관리자 화면에서 Job 상태, 실패 사유, 재시도 횟수, 다운로드 버튼, 만료 여부를 확인할 수 있게 만들어야 운영이 편해집니다.
