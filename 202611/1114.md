## 1. 신청 API가 느려졌는데 정확히 어디가 문제일까?

### ✅ 1. 1113과의 연결

1113에서는 코드 변경 이후 기존보다 성능이 악화됐는지 확인하는 Performance Regression Detection을 다뤘다.

```text
Code Change
       ↓
Baseline Benchmark
       ↓
Candidate Benchmark
       ↓
Performance Regression
       ↓
Bottleneck Investigation
```

1114에서는 마지막 단계인 **Bottleneck Investigation을 실제 요청 처리 경로를 기반으로 수행하는 방법**을 다룬다.

### ✅ 2. 실제 운영 상황

고객이 휴대폰 신청서를 작성한 뒤 신청 버튼을 누른다.

```text
신청 버튼 클릭
       ↓
React Frontend
       ↓
NestJS API
       ↓
Order Service
       ↓
Prisma
       ↓
PostgreSQL
       ↓
Notification Preparation
       ↓
Response
```

### ✅ 3. 문제 발생

평소에는 신청 요청이 빠르게 완료됐지만 최근에는 응답까지 3초 이상 걸린다고 가정한다.

### ✅ 4. 일반적인 조사

```text
EC2 CPU 확인

RDS Connection 확인

NestJS Error Log 확인

Prisma Query 확인
```

### ✅ 5. 그러나 CPU는 정상이다

```text
CPU:
25%

Memory:
정상 범위

HTTP Error:
거의 없음
```

### ✅ 6. 그렇다면 무엇이 문제일까?

가능한 원인은 여러 가지다.

```text
Authentication Delay

Database Connection Wait

Slow SQL Query

Lock Contention

External API Timeout

Repeated Pricing Calculation

Event Loop Blocking
```

### ✅ 7. 기존 로그만으로 조사하는 문제

각 구성 요소에서 발생한 로그를 개발자가 직접 찾아 연결해야 한다.

어떤 DB Query가 특정 고객의 신청 요청에 해당하는지 알기 어려울 수도 있다.

### ✅ 8. 개선된 구조

```text

       ↓

       ↓
Trace Visualization
```

### ✅ 9. 이번 편의 핵심 질문

**하나의 고객 요청이 처리되는 전체 경로를 연결하고, 그 과정에서 가장 많은 지연이 발생하는 작업을 어떻게 찾을 수 있을까?**


### ✅ 11. 가장 중요한 원칙

**성능 문제를 추측으로 해결하지 말고 실제 요청이 거쳐 간 처리 경로와 각 단계의 실행시간을 근거로 조사한다.**

## 2. Observability와 Distributed Tracing

### ✅ 12. Observability

시스템 내부 상태를 외부에서 관측할 수 있는 데이터를 통해 이해하는 능력이다.

### ✅ 13. 대표적인 관측 데이터

```text
Metrics

Logs

Traces
```

### ✅ 14. Metrics

여러 요청을 집계한 수치다.

예:

```text
API Request Count

Error Rate

p95 Latency

CPU Utilization

Database Connections
```

### ✅ 15. Logs

특정 시점에 발생한 사건과 실행 결과를 기록한 데이터다.

### ✅ 16. Traces

하나의 요청 또는 연결된 작업이 여러 처리 단계를 거치는 과정과 시간 정보를 나타낸다.

### ✅ 17. 비교

| 관측 방식 | 핵심 질문 |
|---|---|
| Metrics | 얼마나 많이 발생했는가? |
| Logs | 어떤 사건이 발생했는가? |
| Traces | 어떤 경로로 처리됐는가? |

### ✅ 18. 예시

```text
Metric:
신청 API p95 증가

Log:
DB Query Timeout 발생

Trace:
Order Service 내부 DB 조회에서 지연
```

### ✅ 19. 중요한 점

Trace가 있다고 Metrics와 Logs가 필요 없어지는 것은 아니다.

### ✅ 20. 중요한 원칙

**Metrics로 이상을 발견하고, Trace로 관련 처리 경로를 좁히고, Logs와 DB 증거로 실제 원인을 검증한다.**

---

## 3. Distributed Tracing이란?

### ✅ 21. 정의

하나의 논리적 요청이 여러 서비스나 구성 요소를 거치면서 수행한 작업을 연결해 추적하는 기술이다.

### ✅ 22. 일반적인 예시

```text
API Gateway
       ↓
Order Service
       ↓
Payment Service
       ↓
Database
```

### ✅ 23. 하지만 Microservice에서만 사용할까?

아니다.

하나의 NestJS 애플리케이션 내부에서도 여러 처리 단계에 Span을 추가할 수 있다.

### ✅ 24. 현재 투게더몰에 적용하면

```text
React Customer Frontend
       ↓
NestJS Backend
       ↓
Application Service
       ↓
Pricing Service
       ↓
Prisma
       ↓
PostgreSQL
```

### ✅ 25. 외부 연동까지 연결하면

```text
Backend
   ├── PostgreSQL
   ├── External Product Provider
   ├── Notification Provider
   └── Background Worker
```

### ✅ 26. 중요한 점

현재 시스템이 Monolith라는 이유만으로 Distributed Tracing의 필요성이 없는 것은 아니다.

### ✅ 27. 중요한 원칙

**Trace는 마이크로서비스 전용 기술이 아니라 하나의 업무가 여러 처리 단계를 거치는 상황에서 유용한 관측 구조다.**

---

## 4. Trace란?

### ✅ 28. Trace

서로 연결된 작업들의 실행 흐름이다.

### ✅ 29. 예시

고객이 상품 상세페이지를 조회한다.

```text
Trace A
   ├── HTTP Request
   ├── Product Service
   ├── Product Query
   ├── Plan Query
   └── Response Serialization
```

### ✅ 30. Trace ID

이 작업들을 하나의 흐름으로 연결하는 식별자다.

### ✅ 31. 동일한 Trace에 여러 Span이 포함된다

각 Span은 서로 다른 작업을 나타낸다.

### ✅ 32. 중요한 점

Trace가 반드시 고객의 전체 방문 세션을 의미하지는 않는다.

### ✅ 33. 예를 들어

고객 한 명이 상품 목록을 조회하고 상품 상세페이지로 이동한 뒤 신청을 제출하면 여러 Trace가 생성될 수 있다.

```text
Customer Journey
       ├── Trace A: 상품 목록 조회
       ├── Trace B: 상품 상세 조회
       └── Trace C: 신청 제출
```

### ✅ 34. 중요한 원칙

**Trace는 연결된 실행 작업의 단위이며 고객 세션 전체와 같은 의미가 아니다.**

---

## 5. Span이란?

### ✅ 35. 정의

Trace 안에서 하나의 개별 작업을 나타내는 관측 단위다.

### ✅ 36. 예시

```text
상품 상세 API 처리:
800ms

상품 데이터 조회:
100ms

요금제 데이터 조회:
500ms

가격 계산:
120ms
```

### ✅ 37. 각 작업을 Span으로 기록할 수 있다

```text
Span A:
HTTP GET /products/:id

Span B:
product.getDetail

Span C:
catalog.loadProduct

Span D:
pricing.loadPlans

Span E:
pricing.calculate
```

### ✅ 38. Span의 주요 정보

```text
Trace ID

Span ID

Parent Span ID

Span Name

Start Time

End Time

Attributes

Events

Status

Links
```

### ✅ 39. Span Duration

작업 시작부터 종료까지 걸린 시간이다.

### ✅ 40. 중요한 점

Span이 종료되지 않으면 정상적인 실행시간을 기록하거나 Export하는 과정에 문제가 생길 수 있다.

### ✅ 41. 중요한 원칙

**Span은 단순 로그 한 줄이 아니라 시작과 종료, 실행 정보와 관계를 가진 작업 단위다.**

---

## 6. Trace ID와 Span ID

### ✅ 42. Trace ID

연결된 Trace 전체를 식별한다.

### ✅ 43. Span ID

Trace 내부에서 개별 작업을 식별한다.

### ✅ 44. 구조 예시

```text
Trace ID: TRACE-A

HTTP Request
Span ID: SPAN-1

Product Service
Span ID: SPAN-2

Database Query
Span ID: SPAN-3
```

### ✅ 45. 실제 OpenTelemetry Trace ID

일반적으로 16바이트 식별자를 32자리 16진수로 표현한다.

### ✅ 46. Span ID

8바이트 식별자를 16자리 16진수로 표현한다.

### ✅ 47. 중요한 점

위의 `TRACE-A`, `SPAN-1`은 설명용 표현이다.

실제 OpenTelemetry ID 형식이 아니다.

### ✅ 48. ID 생성

개발자가 고객 전화번호나 주문번호를 이용해 직접 Trace ID를 만들지 않는다.

SDK의 정상적인 ID 생성 방식을 사용한다.

### ✅ 49. 중요한 원칙

**Trace ID와 Span ID는 관측 데이터의 상관관계를 위한 식별자이며 업무 식별자나 인증 정보가 아니다.**

---

## 7. Parent Span과 Child Span

### ✅ 50. Parent Span

다른 작업을 시작하거나 포함하는 상위 Span이다.

### ✅ 51. Child Span

상위 작업에 연결된 하위 작업이다.

### ✅ 52. 예시

```text
HTTP Request
       │
       └── application.submit
                 │
                 ├── application.validate
                 │
                 ├── pricing.calculate
                 │
                 └── order.persist
                           │
                           └── Prisma Query
```

### ✅ 53. Parent-Child 관계의 장점

어떤 업무 작업이 어떤 하위 작업을 호출했는지 파악하기 쉽다.

### ✅ 54. 예시

가격 계산이 느려졌다면 가격 계산 Span 내부의 DB 조회를 조사할 수 있다.

### ✅ 55. 중요한 주의

Parent와 Child의 실행시간을 단순히 더하면 중복 계산할 수 있다.

### ✅ 56. 예시

```text
Parent:
1,000ms

Child A:
600ms

Child B:
300ms
```

전체 실행시간이 1,900ms인 것은 아니다.

### ✅ 57. 이유

Parent Duration에 Child 실행시간이 이미 포함될 수 있기 때문이다.

### ✅ 58. 중요한 원칙

**Span의 계층 구조와 실제 실행시간의 포함 관계를 이해해야 올바른 병목 분석이 가능하다.**

---

## 8. Span Kind

### ✅ 59. OpenTelemetry에는 Span Kind가 있다

작업의 성격을 표현하는 정보다.

| Span Kind | 의미 |
|---|---|
| INTERNAL | 애플리케이션 내부 작업 |
| SERVER | 외부 요청을 처리하는 서버 작업 |
| CLIENT | 외부 시스템을 호출하는 작업 |
| PRODUCER | 메시지 생성 또는 발행 |
| CONSUMER | 메시지 수신 이후 처리 |

### ✅ 60. SERVER Span 예시

NestJS가 고객의 HTTP 요청을 수신한다.

### ✅ 61. INTERNAL Span 예시

가격 정책을 계산한다.

### ✅ 62. CLIENT Span 예시

PostgreSQL 또는 외부 API를 호출한다.

### ✅ 63. PRODUCER Span 예시

알림 처리 Job을 Queue에 발행한다.

### ✅ 64. CONSUMER Span 예시

Worker가 전달된 Job을 처리한다.

### ✅ 65. 중요한 점

Queue의 구체적인 Span Kind와 작업 관계는 사용 중인 메시징 기술 및 OpenTelemetry Semantic Conventions에 맞게 적용해야 한다.

### ✅ 66. 중요한 원칙

**Span Kind를 적절하게 구분하면 서비스 간 호출과 내부 업무 작업을 더 명확하게 분석할 수 있다.**

---

## 9. Span Name 설계

### ✅ 67. 잘못된 Span Name

```text
getProduct-TEST-PRODUCT-001

createOrder-ORDER-12345

customer-010XXXXXXXX
```

### ✅ 68. 문제

요청마다 이름이 달라지고 개인정보가 포함될 수 있다.

### ✅ 69. 권장 Span Name

```text
product.getDetail

pricing.calculate

application.validate

order.persist

notification.process
```

### ✅ 70. HTTP Route

가능하면 실제 상품 ID가 포함된 전체 URL이 아니라 Route Template을 사용한다.

```text
GET /products/:id
```

### ✅ 71. 중요한 이유

같은 업무 작업을 그룹화하고 성능을 비교하기 쉽다.

### ✅ 72. 중요한 원칙

**Span Name은 특정 고객이나 특정 주문을 나타내는 이름이 아니라 반복적으로 수행되는 업무 Operation을 나타내야 한다.**

## 10. Span Attributes

### ✅ 73. Attribute

Span을 설명하는 추가적인 Key-Value 데이터다.

### ✅ 74. 안전한 업무 Attribute 예시

```typescript
span.setAttributes({
  'app.operation': 'APPLICATION_SUBMIT',

  'app.channel': 'CUSTOMER_WEB',

  'app.carrier': 'LGU',

  'app.outcome': 'CREATED',
});
```

### ✅ 75. 사용 목적

같은 Operation을 통신사나 업무 채널, 결과 상태별로 분석할 수 있다.

### ✅ 76. 주의할 Attribute

```text
Customer Name

Phone Number

Resident Registration Number

Address

Access Token

Authorization Header

Request Body

Database URL
```

### ✅ 77. 실제 업무 결과를 기록하고 싶다면?

개인정보 대신 제한된 상태 코드를 사용한다.

```text
CREATED

REJECTED

FAILED

OUTCOME_UNKNOWN
```

### ✅ 78. Semantic Conventions

OpenTelemetry에서 HTTP·DB·Messaging 등의 공통 Attribute 이름과 의미를 표준화한다.

### ✅ 79. 자체 Attribute

서비스 고유 업무 정보에는 일관된 자체 Namespace를 사용할 수 있다.

예:

```text
app.operation

app.outcome

app.carrier
```

### ✅ 80. 중요한 원칙

**Trace를 자세하게 만든다는 이유로 고객의 신청서 원문이나 인증 정보를 Attribute에 저장하지 않는다.**

---

## 11. Span Events

### ✅ 81. Span Event

Span이 실행되는 동안 발생한 특정 사건을 기록한다.

### ✅ 82. 예시

```typescript
span.addEvent('pricing.validation.completed');

span.addEvent('order.transaction.committed');
```

### ✅ 83. 실제 업무에 적용하면

```text
application.submit Span

00ms:
validation.started

30ms:
validation.completed

90ms:
pricing.calculated

200ms:
order.transaction.committed
```

### ✅ 84. Span과 Event의 차이

Span은 실행시간을 가진 작업이다.

Event는 작업 도중 발생한 특정 시점을 표현한다.

### ✅ 85. 중요한 주의

Transaction이 실제 Commit되기 전에 `transaction.committed` Event를 기록해서는 안 된다.

### ✅ 86. 또 다른 주의

Event 수를 무제한으로 증가시키면 Trace 크기와 비용이 증가한다.

### ✅ 87. 중요한 원칙

**별도의 실행시간 분석이 필요한 작업은 Span으로, 의미 있는 상태 변화는 Event로 기록한다.**

---

## 12. Span Status

### ✅ 88. 대표적인 상태

```text
UNSET

OK

ERROR
```

### ✅ 89. UNSET

명시적인 성공 또는 실패 상태가 설정되지 않은 기본 상태다.

### ✅ 90. OK

작업이 정상적으로 완료됐음을 명시적으로 표현할 수 있다.

### ✅ 91. ERROR

작업에서 오류가 발생했음을 나타낸다.

### ✅ 92. 중요한 점

업무상 정상적인 거부가 항상 기술적인 ERROR인 것은 아니다.

### ✅ 93. 예시

고객이 가입 조건을 충족하지 않아 신청이 거부됐다.

```text
Business Outcome:
REJECTED
```

이것은 정의된 업무 규칙에 따른 정상적인 처리일 수 있다.

### ✅ 94. 반대로

DB 연결이 실패해 주문을 생성하지 못했다.

```text
Business Outcome:
FAILED

Span Status:
ERROR
```

### ✅ 95. 중요한 원칙

**기술적 실행 오류와 정상적인 업무 거부를 구분해서 기록해야 Trace 분석이 실제 서비스 품질을 반영할 수 있다.**

---

## 13. Request ID와 Trace ID의 차이

### ✅ 96. Request ID

개별 HTTP 요청을 식별하기 위한 ID다.

### ✅ 97. Trace ID

해당 요청과 연결된 여러 작업을 추적하기 위한 ID다.

### ✅ 98. 예시

```text
Customer API Request

Request ID:
REQ-001

Trace ID:
TRACE-A
```

### ✅ 99. 외부 API 호출이 추가되면

```text
Customer API
Request ID: REQ-001
Trace ID: TRACE-A

        ↓

Internal Service API
Request ID: REQ-002
Trace ID: TRACE-A
```

### ✅ 100. 의미

각 HTTP 요청의 Request ID는 다르지만 하나의 Trace에 포함될 수 있다.

### ✅ 101. 현재 프로젝트에서는

1113 이전부터 다뤘던 Request ID 기반 로그 Correlation을 유지하고 Trace ID를 추가하는 방식이 적합하다.

### ✅ 102. 중요한 원칙

**기존 Request ID를 무조건 Trace ID로 교체하지 않고 각각의 역할에 맞게 함께 활용한다.**

---

## 14. Journey ID와 Operation Key

### ✅ 103. Journey ID

고객의 특정 업무 여정을 연결하기 위한 식별자다.

### ✅ 104. Operation Key

하나의 논리적인 업무 작업을 구분하기 위한 키다.

### ✅ 105. 전체 구분

| 식별자 | 식별 범위 |
|---|---|
| Request ID | 개별 HTTP 요청 |
| Trace ID | 연결된 실행 경로 |
| Span ID | 개별 처리 작업 |
| Journey ID | 고객의 업무 여정 |
| Idempotency Key | 동일한 논리적 실행 요청 |
| Release ID | 실제 배포 버전 |

### ✅ 106. 예시

```text
Journey A

상품 상세 조회
Trace A

신청 제출
Trace B

네트워크 오류 후 재시도
Trace C
```

### ✅ 107. 신청 재시도

Trace ID는 달라질 수 있지만 같은 논리적 신청이라면 Idempotency Key는 유지해야 할 수 있다.

### ✅ 108. 중요한 주의

Trace ID를 DB의 중복 주문 방지 Key로 사용하면 안 된다.

### ✅ 109. 이유

재시도마다 새로운 Trace가 생성될 수 있기 때문이다.

### ✅ 110. 중요한 원칙

**관측을 위한 식별자와 실제 업무의 멱등성을 보장하기 위한 식별자를 분리한다.**

---

## 15. Context Propagation

### ✅ 111. Context

현재 실행 중인 작업과 관련된 정보를 전달하기 위한 구조다.

### ✅ 112. Context Propagation

한 작업의 실행 Context를 다음 작업이나 다른 서비스에 전달하는 과정이다.

### ✅ 113. 예시

```text
HTTP Server Span
       ↓
Application Service
       ↓
Pricing Service
       ↓
Database Query
```

### ✅ 114. Context가 정상적으로 전달되면

각 작업이 동일한 Trace에 연결될 수 있다.

### ✅ 115. Context가 유실되면?

```text
HTTP Request:
TRACE-A

Pricing Service:
TRACE-B

Database Query:
TRACE-C
```

처럼 관련 작업이 서로 다른 Trace로 분리될 수 있다.

### ✅ 116. 중요한 원인 후보

```text
SDK Initialization Failure

Unsupported Library

Async Context Loss

Incorrect Manual Instrumentation

Message Context Missing
```

### ✅ 117. 중요한 원칙

**Trace의 핵심은 개별 Span을 많이 만드는 것이 아니라 관련 작업들이 올바른 Context로 연결되도록 만드는 것이다.**

---

## 16. Node.js와 Async Context

### ✅ 118. JavaScript의 비동기 처리

NestJS에서는 여러 요청이 비동기적으로 처리된다.

### ✅ 119. 잘못된 구현

```typescript
let currentTraceId: string;

async function handleRequest() {
  currentTraceId = createTraceId();

  await someAsyncOperation();
}
```

### ✅ 120. 문제

여러 요청이 동시에 실행되면 전역 변수가 다른 요청의 값으로 변경될 수 있다.

### ✅ 121. 필요한 구조

Async Context를 사용해 현재 실행 흐름의 정보를 유지한다.

### ✅ 122. Node.js

`AsyncLocalStorage`를 활용해 비동기 실행 Context를 관리할 수 있다.

### ✅ 123. OpenTelemetry

Node.js 환경에서 Context Manager를 이용해 현재 활성 Span을 추적한다.

### ✅ 124. 중요한 점

SDK를 올바르게 초기화하고 활성 Context를 유지하는 API를 사용해야 한다.

### ✅ 125. 중요한 원칙

**현재 요청 정보를 전역 변수에 저장하는 방식으로 Trace Context를 구현하지 않는다.**

## 17. W3C Trace Context

### ✅ 126. 서비스 간 Context 전달


### ✅ 128. traceparent 예시


### ✅ 129. 구성


### ✅ 133. 중요한 원칙

**서비스 간 Trace 연결은 자체 Header 형식을 임의로 만들기보다 W3C Trace Context와 SDK의 Propagation 기능을 사용하는 것이 적절하다.**

## 18. Trace Context의 보안

### ✅ 134. 고객 브라우저에서 전달된 traceparent

외부 입력값이다.

### ✅ 135. 따라서

```text
traceparent 존재

≠

인증된 요청
```

이다.

### ✅ 136. 위험한 설계

Trace ID가 일치한다는 이유로 고객의 주문 정보에 접근하도록 허용하는 것이다.

### ✅ 137. 또 다른 위험

외부 요청이 샘플링 플래그를 강제로 설정해 대량의 Trace를 생성하도록 유도할 수 있다.

### ✅ 138. 필요한 보호

```text
Header Validation

Request Rate Limiting

Sampling Policy

Trust Boundary

Resource Limits
```

### ✅ 139. Public API

신뢰할 수 없는 외부 Trace Context를 그대로 이어받을지, 새로운 내부 Trace를 시작할지 정책을 정한다.

### ✅ 140. 중요한 구현 조건

HTTP 자동 Instrumentation이 Header를 읽기 전에 신뢰 경계 정책이 적용돼야 한다.

이미 HTTP Span이 생성된 뒤 Middleware에서 Header만 지운다고 기존 Span의 Parent 관계가 자동으로 변경되지는 않는다.

### ✅ 141. 중요한 원칙

**Trace Context는 관측 연결을 위한 외부 입력이며 인증·권한 검증이나 실행 승인 수단으로 사용할 수 없다.**

여러 서비스에 걸쳐 추가적인 Key-Value Context를 전달할 수 있는 기능이다.

### ✅ 147. 현재 추천

### ✅ 148. 중요한 원칙

**서비스 간 전파되는 Context에는 반드시 전달할 필요가 있는 최소한의 비민감 정보만 포함한다.**

## 20. OpenTelemetry란?

### ✅ 149. 정의

Trace·Metric·Log 등의 관측 데이터를 생성하고 처리하며 전달하기 위한 오픈소스 표준 및 도구 생태계다.

### ✅ 150. OpenTelemetry의 주요 구성

```text
API

SDK

Instrumentation

Context Manager

Propagator

Exporter

Collector

Semantic Conventions
```

### ✅ 151. API

애플리케이션 코드에서 Span을 생성하거나 현재 Context를 조회하는 기능을 제공한다.

### ✅ 152. SDK

실제 관측 데이터 생성과 샘플링, 처리, Export 기능을 구현한다.

### ✅ 153. Instrumentation

HTTP·DB·Framework 등의 실행을 관측 데이터로 연결한다.

### ✅ 154. Exporter

생성한 Trace를 외부 수집 시스템으로 전달한다.

### ✅ 155. Collector

관측 데이터를 수신하고 가공해 적절한 Backend로 전송한다.

### ✅ 156. 중요한 구분

OpenTelemetry 자체가 반드시 장기 저장소와 분석 대시보드까지 제공하는 것은 아니다.

### ✅ 157. 일반적인 구성

```text
Application
       ↓
OpenTelemetry SDK
       ↓
OTLP Exporter
       ↓
OpenTelemetry Collector
       ↓
Observability Backend
       ↓
Trace Search / Visualization
```

### ✅ 158. 중요한 원칙

**OpenTelemetry는 관측 데이터를 표준화하고 전달하는 기반이며 실제 저장과 조회를 담당할 Backend는 별도로 결정해야 한다.**

---

### ✅ 159. 처음부터 모든 구성 요소를 추적할 필요는 없다

### ✅ 160. 최소 구조

```text
       ↓

       ↓

       ↓

       ↓
```

### ✅ 161. 우선 추적할 대상

```text

```

### ✅ 162. 이유

고객 경험과 업무 처리에 직접적인 영향을 주는 기능이기 때문이다.

### ✅ 163. Frontend OpenTelemetry는 나중에 도입해도 된다

기존 RUM과 Request ID를 통해 Frontend 오류와 Backend Trace를 연결할 수 있다.

### ✅ 164. 현재 추천

기존 NestJS Logger와 CloudWatch 로그를 유지하면서 Backend Tracing을 추가한다.

### ✅ 165. 중요한 원칙

**기존 관측 구조를 전부 교체하기보다 실제 장애 분석에 필요한 추적 기능부터 점진적으로 추가한다.**

## 22. Automatic Instrumentation

### ✅ 166. 자동 Instrumentation

지원되는 라이브러리의 작업을 별도의 수동 Span 없이 추적하도록 도와주는 기능이다.

### ✅ 167. 예시

```text
Node.js HTTP

Express

Fastify

Database Driver

AWS SDK

Supported Messaging Client
```

### ✅ 168. 장점

모든 Controller와 HTTP Client에 직접 추적 코드를 작성하지 않아도 된다.

### ✅ 169. 중요한 한계

모든 라이브러리가 자동으로 추적되는 것은 아니다.

### ✅ 170. 예시

Node.js의 기본 `http` 호출과 `fetch()`는 내부 구현 및 Instrumentation 종류가 다를 수 있다.

HTTP Instrumentation만 설치했다고 모든 `fetch()` 호출이 추적된다고 가정하지 않는다.

### ✅ 171. 또 다른 문제

자동으로 생성된 Span과 수동 Span이 중복될 수 있다.

### ✅ 172. 중요한 원칙

**Automatic Instrumentation을 활성화한 뒤 실제 어떤 Span이 생성되는지 확인하고 필요한 작업에만 Manual Instrumentation을 추가한다.**

---

## 23. Manual Instrumentation

### ✅ 173. 수동 Instrumentation

업무적으로 중요한 작업에 개발자가 직접 Span을 생성하는 방식이다.

### ✅ 174. 자동 추적만으로 부족한 경우

```text
HTTP POST /applications
Duration: 1,500ms
```

이 결과만으로 가격 계산, 주문 검증, DB 저장 중 무엇이 느린지 모를 수 있다.

### ✅ 175. 수동 Span 추가

```text
HTTP POST /applications
       └── application.submit
                 ├── application.validate
                 ├── pricing.calculate
                 └── order.persist
```

### ✅ 176. 장점

애플리케이션의 업무 의미를 Trace에 표현할 수 있다.

### ✅ 177. 주의

모든 작은 함수에 Span을 생성하면 관측 비용과 복잡도가 증가한다.

### ✅ 178. 중요한 원칙

**Manual Instrumentation은 내부 함수의 개수보다 고객 업무의 중요한 경계와 병목 분석에 필요한 단위를 기준으로 적용한다.**

## 26. NestJS OpenTelemetry SDK 예시

### ✅ 193. 초기 구현

다음 코드는 CommonJS로 빌드되는 NestJS 애플리케이션에서 사용할 수 있는 로컬 실험용 예시다.

운영 환경에는 개인정보 제거 및 Sampling 정책을 검증한 뒤 적용한다.

```typescript
// src/instrumentation.ts

import { NodeSDK } from '@opentelemetry/sdk-node';

import {
  resourceFromAttributes,
} from '@opentelemetry/resources';

import {
  OTLPTraceExporter,
} from '@opentelemetry/exporter-trace-otlp-http';

import {
  HttpInstrumentation,
} from '@opentelemetry/instrumentation-http';

import {
  PrismaInstrumentation,
} from '@prisma/instrumentation';

const traceExporter = new OTLPTraceExporter({
  url:
    process.env.OTEL_EXPORTER_OTLP_TRACES_ENDPOINT
    ?? 'http://127.0.0.1:4318/v1/traces',
});

export const telemetrySdk = new NodeSDK({
  resource: resourceFromAttributes({
    'service.name': 'togethermall-backend',

    'service.version':
      process.env.APP_COMMIT_SHA ?? 'local',

    'deployment.environment.name':
      process.env.APP_ENV ?? 'development',
  }),

  traceExporter,

  instrumentations: [
    new HttpInstrumentation({
      // 초기에는 들어오는 HTTP 요청 중심으로 검증한다.
      // 외부 호출 자동 전파는 별도 정책을 정한 뒤 활성화한다.
      disableOutgoingRequestInstrumentation: true,

      ignoreIncomingRequestHook: (request) => {
        const path =
          request.url?.split('?')[0];

        return (
          path === '/health/live' ||
          path === '/health/ready'
        );
      },
    }),

    new PrismaInstrumentation(),
  ],
});

telemetrySdk.start();

export async function shutdownTelemetry() {
  await telemetrySdk.shutdown();
}
```

### ✅ 194. 주요 정보

`service.name`은 어떤 서비스에서 발생한 Span인지 구분한다.

### ✅ 195. service.version

실제 실행되는 Build의 Commit SHA를 연결하는 데 활용할 수 있다.

### ✅ 196. deployment.environment.name

Production과 Staging, Development 데이터를 구분하는 데 활용한다.

### ✅ 197. OTLP Exporter

Trace 데이터를 Collector 또는 지원되는 Observability Backend로 전달한다.

### ✅ 198. 중요한 주의

이 예시의 Prisma 자동 Instrumentation은 SQL 관련 정보를 포함할 수 있다.

따라서 실제 고객 데이터를 사용하는 환경에 그대로 적용하지 않는다.

### ✅ 199. 또 다른 주의

운영에서는 환경변수의 유효성을 확인하고 필요한 정보가 누락됐을 때 잘못된 환경 이름이나 Endpoint로 Export하지 않도록 해야 한다.

### ✅ 200. 중요한 원칙

**초기 SDK 구성은 가능한 한 단순하게 유지하고 자동 생성되는 Trace 내용을 확인한 뒤 필요한 Instrumentation만 활성화한다.**

## 28. SDK 종료와 Graceful Shutdown

### ✅ 209. Trace는 Batch 단위로 Export될 수 있다

일부 Span이 메모리에 대기 중일 수 있다.

### ✅ 210. 위험한 상황

```text
Application Shutdown

↓

Process Immediately Exits

↓

Buffered Spans Lost
```

### ✅ 211. 따라서

OpenTelemetry SDK의 Shutdown 처리를 고려한다.

### ✅ 212. NestJS Lifecycle 활용 예시

```typescript
import {
  Injectable,
  OnApplicationShutdown,
} from '@nestjs/common';

import {
  shutdownTelemetry,
} from './instrumentation';

@Injectable()
export class TelemetryLifecycle
  implements OnApplicationShutdown {

  async onApplicationShutdown(): Promise<void> {
    await shutdownTelemetry();
  }
}
```

### ✅ 213. 실제 사용 조건

위 Provider를 NestJS Module에 등록하고 필요한 Shutdown Hook을 활성화해야 한다.

```typescript
app.enableShutdownHooks();
```

### ✅ 214. 중요한 주의

실제 요청과 Worker가 종료되기 전에 Telemetry SDK를 먼저 종료하면 마지막 처리 작업의 Span이 유실될 수 있다.

### ✅ 215. 종료 순서

```text
New Traffic Stop

↓

In-flight Requests / Jobs Drain

↓

Application Cleanup

↓

Telemetry Flush / Shutdown

↓

Process Exit
```

### ✅ 216. 중요한 점

Collector가 응답하지 않아도 애플리케이션 종료가 무한정 지연되지 않도록 전체 종료 Timeout을 설계한다.

### ✅ 217. 중요한 원칙

**OpenTelemetry Shutdown을 기존 Graceful Shutdown과 연결하되 업무 처리 종료를 방해하지 않도록 구성한다.**

## 29. 첫 번째 Manual Span

### ✅ 218. 상품 상세 업무에 Span을 추가한다

```typescript
import {
  trace,
  SpanStatusCode,
} from '@opentelemetry/api';

const tracer = trace.getTracer(
  'togethermall.product',
);

export async function getProductDetail(
  productId: string,
) {
  return tracer.startActiveSpan(
    'product.getDetail',

    async (span) => {
      try {
        span.setAttribute(
          'app.operation',
          'PRODUCT_DETAIL',
        );

        const product =
          await productRepository.findDetail(
            productId,
          );

        span.setAttribute(
          'app.outcome',
          product ? 'FOUND' : 'NOT_FOUND',
        );

        return product;
      } catch (error) {
        span.setStatus({
          code: SpanStatusCode.ERROR,
        });

        span.addEvent('operation.failed', {
          'app.error_code':
            'PRODUCT_DETAIL_FAILED',
        });

        throw error;
      } finally {
        span.end();
      }
    },
  );
}
```

### ✅ 219. 중요한 전제

`productRepository`는 실제 프로젝트의 Repository 또는 PrismaService에 맞춰 연결해야 한다.

### ✅ 220. startActiveSpan

생성한 Span을 Callback 실행 Context의 활성 Span으로 설정하는 데 활용한다.

### ✅ 221. try / catch / finally

작업 오류를 기록하면서도 모든 실행 경로에서 Span이 종료되도록 한다.

### ✅ 222. 개인정보 보호

위 예시는 상품 ID나 SQL Parameter를 Attribute에 넣지 않는다.

### ✅ 223. 오류 처리

`error.message`와 Stack 전체를 무조건 기록하지 않고 안전하게 정의한 오류 코드부터 수집한다.

### ✅ 224. 중요한 원칙

**수동 Span을 추가하더라도 기존 서비스의 반환값과 예외 처리 동작을 변경하지 않는다.**

## 30. 공통 withSpan Helper

### ✅ 225. 여러 Service에 반복 코드를 넣을 필요가 있을까?

공통 Helper를 이용해 일관된 Span 생성과 종료를 관리할 수 있다.

### ✅ 226. 타입 예시

```typescript
import {
  trace,
  SpanStatusCode,
  type Span,
} from '@opentelemetry/api';

type Operation =
  | 'product.getDetail'
  | 'application.validate'
  | 'application.submit'
  | 'pricing.calculate'
  | 'order.persist'
  | 'admin.orderSearch'
  | 'notification.prepare';

const tracer = trace.getTracer(
  'togethermall.business',
);

export function withSpan<T>(
  operation: Operation,

  execute: (span: Span) => Promise<T>,

): Promise<T> {
  return tracer.startActiveSpan(
    operation,

    async (span) => {
      try {
        return await execute(span);
      } catch (error) {
        span.setStatus({
          code: SpanStatusCode.ERROR,
        });

        span.addEvent('operation.failed', {
          'app.operation': operation,
        });

        throw error;
      } finally {
        span.end();
      }
    },
  );
}
```

### ✅ 227. 장점

작업 이름의 종류를 제한하고 모든 Span에서 동일한 종료 정책을 적용할 수 있다.

### ✅ 228. 중요한 한계

현재 Helper는 던져진 예외를 기술 오류로 기록하는 단순 예시다.

### ✅ 229. 실제 적용

정상적인 업무 거부도 Exception으로 구현된 프로젝트라면 오류 분류 정책을 추가해야 한다.

### ✅ 230. 중요한 원칙

**공통 Instrumentation Helper를 사용하더라도 각 업무의 성공과 실패 의미를 정확하게 유지해야 한다.**

## 31. 신청 처리 전체 Span 구성

### ✅ 231. 신청 Service 예시

```typescript
async function submitApplication(
  input: ApplicationInput,
) {
  return withSpan(
    'application.submit',

    async (span) => {
      const validated = await withSpan(
        'application.validate',

        async () => {
          return validateApplication(input);
        },
      );

      const pricing = await withSpan(
        'pricing.calculate',

        async () => {
          return calculatePricing(validated);
        },
      );

      const result = await withSpan(
        'order.persist',

        async () => {
          return persistOrder({
            application: validated,
            pricing,
          });
        },
      );

      span.setAttribute(
        'app.outcome',
        'CREATED',
      );

      return result;
    },
  );
}
```

### ✅ 232. 예상 Trace 구조

```text
HTTP POST /applications
       └── application.submit
                 ├── application.validate
                 ├── pricing.calculate
                 └── order.persist
                           └── Prisma Query
```

### ✅ 233. 중요한 점

`persistOrder()`의 정상 반환이 실제 Commit된 주문을 의미하는지 확인해야 한다.

### ✅ 234. Transaction

### ✅ 235. 따라서

실제 Commit 성공을 확인할 수 있는 업무 경계에서 최종 성공 상태를 기록한다.

### ✅ 236. 중요한 원칙

**Trace의 업무 성공 Attribute는 실제 주문 생성과 Transaction 결과를 근거로 설정한다.**

## 32. Request ID Middleware와 Trace Correlation

### ✅ 237. 기존 Request ID 구조를 활용한다

NestJS가 요청마다 서버에서 생성한 Request ID를 응답 Header에 포함하도록 할 수 있다.

### ✅ 238. Express 기반 Middleware 예시

```typescript
import {
  Injectable,
  NestMiddleware,
  Logger,
} from '@nestjs/common';

import {
  randomUUID,
} from 'node:crypto';

import {
  performance,
} from 'node:perf_hooks';

import {
  trace,
  isSpanContextValid,
} from '@opentelemetry/api';

import type {
  Request,
  Response,
  NextFunction,
} from 'express';

@Injectable()
export class RequestCorrelationMiddleware
  implements NestMiddleware {

  private readonly logger =
    new Logger('RequestCorrelation');

  use(
    req: Request,
    res: Response,
    next: NextFunction,
  ) {
    const requestId = randomUUID();

    const startedAt = performance.now();

    const activeSpan =
      trace.getActiveSpan();

    const spanContext =
      activeSpan?.spanContext();

    const validTraceContext =
      spanContext &&
      isSpanContextValid(spanContext);

    res.setHeader(
      'X-Request-ID',
      requestId,
    );

    activeSpan?.setAttribute(
      'app.request_id',
      requestId,
    );

    res.once('finish', () => {
      this.logger.log(
        JSON.stringify({
          event: 'http.request.completed',

          requestId,

          traceId: validTraceContext
            ? spanContext.traceId
            : undefined,

          spanId: validTraceContext
            ? spanContext.spanId
            : undefined,

          operation:
            `${req.method}:${req.route?.path ?? 'unknown'}`,

          statusCode:
            res.statusCode,

          durationMs:
            Math.round(
              performance.now() - startedAt,
            ),
        }),
      );
    });

    next();
  }
}
```

### ✅ 239. 중요한 특징

현재 활성 Span의 Trace ID와 Span ID를 요청 완료 로그에 함께 기록한다.

### ✅ 240. Request ID

외부에서 받은 임의의 Header를 그대로 신뢰하지 않고 서버에서 새로 생성한다.

### ✅ 241. 주의

이 Middleware가 실행될 때 HTTP Instrumentation의 활성 Span이 존재해야 Trace ID가 연결된다.

### ✅ 242. 또 다른 주의

응답의 `finish` Event는 응답 데이터가 서버 측에서 전송 처리됐음을 나타내지만 고객 브라우저가 실제로 응답을 받았다는 보장은 아니다.

### ✅ 243. 중간 연결 종료

필요한 경우 `close` Event도 별도로 처리해 정상 완료와 연결 중단을 구분해야 한다.

### ✅ 244. 중요한 원칙

**로그와 Trace를 연결하는 ID는 실제 실행 Context에서 가져오고 HTTP 응답 완료와 고객 수신 완료를 구분한다.**

## 33. Frontend와 Backend 요청 연결

### ✅ 245. 초기에는 Browser SDK가 없어도 된다

기존 Fetch Wrapper에서 서버의 Request ID를 읽을 수 있다.

### ✅ 246. React API Client 예시

```typescript
export async function fetchProductDetail(
  productId: string,
) {
  const response = await fetch(
    `/api/products/${encodeURIComponent(productId)}`,
  );

  const requestId =
    response.headers.get('X-Request-ID');

  if (!response.ok) {
    reportFrontendError({
      operation: 'PRODUCT_DETAIL',

      errorCode: 'PRODUCT_DETAIL_HTTP_ERROR',

      requestId:
        requestId ?? undefined,

      statusCode:
        response.status,
    });

    throw new Error(
      'PRODUCT_DETAIL_REQUEST_FAILED',
    );
  }

  return response.json();
}
```

### ✅ 247. 연결 구조

```text
Frontend Error
       ↓
Request ID
       ↓
Backend Structured Log
       ↓
Trace ID
       ↓
Backend Trace
```

### ✅ 248. 중요한 전제

`reportFrontendError()`는 기존 RUM 또는 오류 수집 구조에 맞춰 구현해야 한다.

### ✅ 249. 네트워크 자체가 실패한 경우

서버 응답을 받지 못하므로 Request ID도 얻지 못할 수 있다.

### ✅ 250. 이런 경우

기존 Journey ID·클라이언트 Attempt ID·요청 시각·Operation Key 등의 별도 근거가 필요하다.

### ✅ 251. 중요한 원칙

**Frontend 오류 추적은 모든 상황에서 서버 Request ID를 얻을 수 있다고 가정하지 않는다.**

## 34. CORS와 Trace Header

### ✅ 252. Frontend와 Backend의 Origin이 다르면?

브라우저의 CORS 정책을 고려해야 한다.

### ✅ 253. Request ID 응답 Header

다른 Origin에서 JavaScript가 해당 Header를 읽으려면 노출 정책이 필요할 수 있다.

### ✅ 254. NestJS 설정 예시

```typescript
app.enableCors({
  origin: [
    'https://customer.example.com',
    'https://admin.example.com',
  ],

  credentials: true,

  exposedHeaders: [
    'X-Request-ID',
  ],

  allowedHeaders: [
    'Content-Type',
    'Authorization',
    'traceparent',
    'tracestate',
  ],
});
```

### ✅ 255. 중요한 전제

위 Domain은 설명용이다.

실제 허용 Origin으로 교체해야 한다.

### ✅ 256. traceparent

브라우저가 직접 Trace Context를 전송하는 구조라면 요청 Header 허용 설정이 필요할 수 있다.

### ✅ 257. 중요한 주의

기존 CORS 설정을 위 코드로 무조건 덮어쓰면 다른 필수 Header가 누락될 수 있다.

### ✅ 258. 추가 확인

기존 인증 방식과 CORS 정책, CloudFront 또는 Reverse Proxy의 Header 전달 방식을 함께 검증한다.

### ✅ 259. 중요한 원칙

**Trace Header를 추가하기 위해 기존 인증과 CORS 보안 정책을 완화하지 않는다.**


### ✅ 282. 중요한 원칙

**DB Client Span의 실행시간과 PostgreSQL 서버가 실제로 SQL을 실행한 시간은 항상 같은 값이 아니다.**

## 39. DB Lock Wait 조사

### ✅ 291. 특정 주문 저장 Span이 오래 걸린다

원인 후보 중 하나는 Lock 대기다.

### ✅ 292. 읽기 전용 진단 SQL

```sql
SELECT
  pid,

  state,

  wait_event_type,

  wait_event,

  clock_timestamp() - query_start
    AS elapsed,

  pg_blocking_pids(pid)
    AS blocking_pids

FROM pg_stat_activity

WHERE datname = current_database()

  AND pid <> pg_backend_pid()

  AND state = 'active'

  AND wait_event_type = 'Lock'

ORDER BY elapsed DESC

LIMIT 20;
```

### ✅ 293. 확인할 수 있는 정보

현재 Lock을 기다리는 DB 세션과 차단하고 있는 세션의 후보를 확인할 수 있다.

### ✅ 294. 중요한 제한

이 Query는 실행 시점의 상태를 조회한다.

이미 종료된 과거 Lock 대기를 항상 확인할 수 있는 것은 아니다.

### ✅ 295. 권한

다른 세션의 통계 조회 범위는 PostgreSQL Role에 따라 제한될 수 있다.

### ✅ 296. 위험한 대응

지연 Span이 발생했다는 이유만으로 차단 세션을 자동 종료한다.

### ✅ 297. 중요한 원칙

**Lock 대기를 확인했더라도 실제 업무 Transaction에 미치는 영향을 조사한 뒤 필요한 조치를 결정해야 한다.**

### ✅ 299. 외부 API 지연의 문제

NestJS 내부 코드에는 문제가 없어도 외부 Provider 응답 때문에 전체 요청이 느려질 수 있다.

### ✅ 300. 수동 Span 예시

```typescript
import {
  trace,
  SpanKind,
  SpanStatusCode,
} from '@opentelemetry/api';

const tracer = trace.getTracer(
  'togethermall.external',
);

async function fetchExternalCatalog() {
  return tracer.startActiveSpan(
    'external.catalog.fetch',

    {
      kind: SpanKind.CLIENT,

      attributes: {
        'app.provider': 'CATALOG_PROVIDER',

        'app.operation':
          'EXTERNAL_CATALOG_FETCH',
      },
    },

    async (span) => {
      try {
        const response = await fetch(
          process.env.CATALOG_TEST_URL!,

          {
            signal: AbortSignal.timeout(
              3_000,
            ),
          },
        );

        span.setAttribute(
          'http.response.status_code',
          response.status,
        );

        if (!response.ok) {
          span.setStatus({
            code: SpanStatusCode.ERROR,
          });

          throw new Error(
            'CATALOG_PROVIDER_HTTP_ERROR',
          );
        }

        return await response.json();
      } catch (error) {
        span.setStatus({
          code: SpanStatusCode.ERROR,
        });

        span.addEvent(
          'external.request.failed',
          {
            'app.error_code':
              'CATALOG_FETCH_FAILED',
          },
        );

        throw error;
      } finally {
        span.end();
      }
    },
  );
}
```

### ✅ 301. 중요한 전제

`CATALOG_TEST_URL`은 격리된 테스트용 Provider URL을 가정한다.

### ✅ 302. 실제 구현

외부 URL Allowlist, 인증, Response Schema Validation과 기존 Retry 정책을 추가로 적용해야 한다.

### ✅ 303. Trace Context

신뢰하지 않는 외부 Provider에 내부 Baggage나 Trace Header를 무조건 전파하지 않는다.

### ✅ 304. 중요한 원칙

**외부 API는 지연과 실패를 관측하되 실제 Provider의 인증 정보와 고객 데이터를 Trace에 포함하지 않는다.**

## 43. Span Links

### ✅ 317. Span Link

한 Span을 다른 관련 Span의 Context와 연결하는 기능이다.

### ✅ 318. Parent와 Link의 차이

Parent는 하나의 직접적인 상위 작업 관계를 나타낸다.

Link는 별도의 Trace 또는 여러 관련 작업과의 관계도 표현할 수 있다.

### ✅ 319. 예시

```text
Order Creation Trace
       ↓
Notification Message Created
       ⋮
       ⋮ Span Link
       ⋮
Notification Processing Trace
```

### ✅ 320. 장점

고객 HTTP 요청이 이미 종료됐더라도 이후 실행된 Worker 작업과의 관련성을 유지할 수 있다.

### ✅ 321. Batch 처리

여러 Job을 한 번에 처리하는 Worker는 여러 Producer Span과 연결될 수 있다.

### ✅ 322. 중요한 점

하나의 Span은 여러 개의 Link를 가질 수 있지만 Parent는 하나다.

### ✅ 323. 현재 OpenTelemetry 메시징 설계

Producer와 Consumer를 연결할 때 Span Links를 기본적인 연결 방식으로 활용하는 Semantic Conventions를 참고할 수 있다.

### ✅ 324. 중요한 원칙

**시간적으로 분리된 비동기 업무를 무조건 하나의 긴 Parent-Child Trace로 구성하지 않고 실제 메시징 관계에 맞게 Span Link를 검토한다.**

### ✅ 326. Context 생성

```typescript
import {
  context,
  propagation,
} from '@opentelemetry/api';

function createJobTraceContext():
  NotificationJob['traceContext'] {

  const carrier: Record<string, string> = {};

  propagation.inject(
    context.active(),
    carrier,
  );

  if (!carrier.traceparent) {
    return undefined;
  }

  return {
    traceparent: carrier.traceparent,
```

## 45. Worker Span Link 예시

### ✅ 333. Consumer 측 처리

```typescript
import {
  trace,
  propagation,
  ROOT_CONTEXT,
  SpanKind,
  SpanStatusCode,
  isSpanContextValid,
} from '@opentelemetry/api';

const tracer = trace.getTracer(
  'togethermall.notification-worker',
);

async function processNotificationJob(
  job: NotificationJob,
) {
  const extracted = propagation.extract(
    ROOT_CONTEXT,

    job.traceContext ?? {},
  );

  const producerContext =
    trace.getSpanContext(extracted);

  const links =
    producerContext &&
    isSpanContextValid(producerContext)

      ? [
          {
            context: producerContext,
          },
        ]

      : [];

  return tracer.startActiveSpan(
    'notification.process',

    {
      kind: SpanKind.CONSUMER,

      links,

      attributes: {
        'app.operation':
          'NOTIFICATION_PROCESS',
      },
    },

    ROOT_CONTEXT,

    async (span) => {
      try {
        const result =
          await notificationService.process(
            job,
          );

        span.setAttribute(
          'app.outcome',
          result.outcome,
        );

        return result;
      } catch (error) {
        span.setStatus({
          code: SpanStatusCode.ERROR,
        });

        throw error;
      } finally {
        span.end();
      }
    },
  );
}
```

### ✅ 334. 핵심 특징

Worker 작업은 새로운 Root Span에서 시작하고 Producer의 Context를 Link로 연결한다.

### ✅ 335. 중요한 전제

이 코드는 특정 Queue 라이브러리에 의존하지 않는 자체 Job Handler 예시다.

### ✅ 336. 실제 Queue가 자동 Instrumentation을 제공한다면?

기존 Producer·Consumer Span과 중복되지 않도록 조정해야 한다.

### ✅ 337. 중요한 주의

Span Link가 존재한다고 Job이 반드시 정확히 한 번 처리됐다는 의미는 아니다.

### ✅ 338. 중요한 원칙

**비동기 Trace Correlation과 실제 업무의 멱등성·재시도·결과 확인은 별도의 안전장치로 관리한다.**

## 47. Critical Path Analysis

### ✅ 347. Critical Path란?

하나의 업무가 완료되기까지 전체 응답시간을 결정하는 작업 의존 경로다.

### ✅ 348. 단순히 가장 오래 걸린 Span일까?

아니다.

순차 실행과 병렬 실행, 실제 대기 관계를 함께 고려해야 한다.

### ✅ 349. 순차 실행 예시

```text
Validation:
100ms

↓

Database:
500ms

↓

Pricing:
200ms

↓

Response:
100ms
```

### ✅ 350. 총 소요시간

설명된 작업들이 순차적으로 실행되고 다른 비용이 없다고 가정하면 900ms다.

### ✅ 351. 이 경우

DB 조회를 500ms에서 250ms로 개선하면 전체 응답시간도 약 250ms 줄어들 수 있다.

### ✅ 352. 하지만 병렬 실행에서는?

가장 느린 작업과 실제 Join 지점을 함께 분석해야 한다.

### ✅ 353. 중요한 원칙

**Critical Path는 개별 Span의 실행시간만 비교하는 것이 아니라 해당 작업이 전체 업무 완료를 실제로 지연시키는지를 분석하는 개념이다.**

---

## 48. 병렬 실행과 Critical Path

### ✅ 354. 상황

상품 상세페이지에서 상품 정보와 요금제 정보를 동시에 조회한다.

```text
Start
  │
  ├── Product Query: 200ms
  │
  └── Plan Query: 600ms
          │
          ↓
      Join
          ↓
      Pricing: 100ms
```

### ✅ 355. 두 Query가 동시에 시작했다고 가정한다

전체 Query 대기시간은 약 600ms다.

### ✅ 356. 전체 처리시간

후속 가격 계산 100ms를 더하면 약 700ms다.

### ✅ 357. Product Query를 개선하면?

```text
200ms → 50ms
```

### ✅ 358. 그러나 Plan Query는 여전히 600ms다

다른 조건이 같다면 전체 완료시간은 크게 개선되지 않을 수 있다.

### ✅ 359. Plan Query를 개선하면?

```text
600ms → 300ms
```

### ✅ 360. 결과

전체 업무 처리시간을 줄이는 데 직접적인 효과를 기대할 수 있다.

### ✅ 361. 중요한 주의

병렬화는 DB Connection과 CPU 사용량을 증가시키거나 Lock 경쟁을 만들 수 있다.

### ✅ 362. 중요한 원칙

**Critical Path에 있는 작업을 우선 최적화하되 병렬 처리로 인한 자원 경쟁과 업무 의존성을 함께 검증한다.**

## 50. Inclusive Time과 Exclusive Time

### ✅ 369. Inclusive Time

하위 작업의 시간을 포함하는 Span 전체 실행시간이다.

### ✅ 370. Exclusive Time

분석 범위 안에서 하위 작업이 차지한 시간을 제외한 나머지 시간으로 볼 수 있다.

### ✅ 371. 예시

```text
Parent Span:
1,000ms

Child A:
300ms

Child B:
400ms
```

Child A와 B가 겹치지 않는다고 가정하면 Parent의 나머지 시간은 300ms다.

### ✅ 372. 병렬 실행이 있다면?

두 Child의 시간이 겹칠 수 있다.

### ✅ 373. 예시

```text
Child A:
100ms ~ 600ms

Child B:
300ms ~ 800ms
```

### ✅ 374. 각 Duration

각각 500ms다.

### ✅ 375. 하지만 실제로 차지한 시간의 합집합은?

100ms부터 800ms까지인 700ms다.

### ✅ 376. 중요한 의미

Child Duration을 단순 합산하면 겹친 시간이 중복 계산된다.

### ✅ 377. 중요한 원칙

**상위 Span의 나머지 시간을 계산할 때는 하위 Span의 중복 실행 구간과 실제 시간 범위를 고려한다.**

## 51. Exclusive Time 계산 코드

### ✅ 378. 개념 구현

다음 코드는 하나의 Parent Span 내부에서 직접 연결된 Child Span의 시간 합집합을 계산하는 최소 예시다.

```typescript
interface TimeInterval {
  startMs: number;

  endMs: number;
}

function calculateExclusiveTime(
  parent: TimeInterval,

  children: TimeInterval[],

): number {
  if (
    !Number.isFinite(parent.startMs) ||
    !Number.isFinite(parent.endMs) ||
    parent.endMs < parent.startMs
  ) {
    throw new Error(
      'INVALID_PARENT_INTERVAL',
    );
  }

  const intervals = children
    .filter(
      (child) =>
        Number.isFinite(child.startMs) &&
        Number.isFinite(child.endMs) &&
        child.endMs >= child.startMs,
    )
    .map((child) => ({
      startMs: Math.max(
        parent.startMs,
        child.startMs,
      ),

      endMs: Math.min(
        parent.endMs,
        child.endMs,
      ),
    }))
    .filter(
      (child) =>
        child.endMs > child.startMs,
    )
    .sort(
      (a, b) =>
        a.startMs - b.startMs,
    );

  let coveredMs = 0;

  let active:
    TimeInterval | undefined;

  for (const interval of intervals) {
    if (!active) {
      active = { ...interval };

      continue;
    }

    if (
      interval.startMs <= active.endMs
    ) {
      active.endMs = Math.max(
        active.endMs,

        interval.endMs,
      );
    } else {
      coveredMs +=
        active.endMs - active.startMs;

      active = { ...interval };
    }
  }

  if (active) {
    coveredMs +=
      active.endMs - active.startMs;
  }

  const parentDuration =
    parent.endMs - parent.startMs;

  return Math.max(
    0,

    parentDuration - coveredMs,
  );
}
```

### ✅ 379. 테스트 예시

```typescript
const result =
  calculateExclusiveTime(
    {
      startMs: 0,
      endMs: 1_000,
    },

    [
      {
        startMs: 100,
        endMs: 600,
      },

      {
        startMs: 300,
        endMs: 800,
      },
    ],
  );

console.log(result);

// 300
```

### ✅ 380. 중요한 한계

이 값은 관측된 Child Span 시간의 합집합을 제외한 시간이다.

실제 CPU 계산시간을 직접 측정한 값이 아니다.

### ✅ 381. 왜 그런가?

남은 시간에는 다음 작업이 포함될 수 있다.

```text
Uninstrumented I/O

Event Loop Delay

Scheduling

Application Logic

Missing Child Spans
```

### ✅ 382. 또한

서로 다른 서버의 Timestamp가 정확히 정렬되지 않으면 계산이 부정확해질 수 있다.

### ✅ 383. 중요한 원칙

**Exclusive Time은 관측된 하위 작업을 제외한 시간 추정치이며 실제 코드가 CPU를 사용한 시간으로 단정하지 않는다.**

## 52. Critical Path 자동 분석의 한계

### ✅ 384. Trace만 있으면 실제 Critical Path를 완벽하게 찾을 수 있을까?

항상 그렇지는 않다.

### ✅ 385. 이유

Trace에는 모든 실제 작업 의존성이 포함되지 않을 수 있다.

### ✅ 386. 예시

두 Span이 시간상 겹쳐 있다.

하지만 다음 단계가 두 작업 모두를 기다렸는지, 하나만 기다렸는지 Trace의 시간 정보만으로 확정하기 어려울 수 있다.

### ✅ 387. 추가로 필요한 정보

```text
Await Dependencies

Promise.all Join

Queue Wait

Task Scheduling

Actual Business Completion Condition
```

### ✅ 388. AI 분석

Trace에서 가장 긴 후보 작업과 겹치는 작업을 찾을 수 있다.

### ✅ 389. 그러나

실제 코드의 `await` 관계와 업무 실행 흐름을 확인해야 Critical Path를 더 정확하게 판단할 수 있다.

### ✅ 390. 중요한 원칙

**Trace Waterfall을 근거로 병목 후보를 찾되 실제 코드의 실행 의존성을 검증한 뒤 Critical Path를 확정한다.**

## 53. Trace Sampling

### ✅ 391. Sampling이란?

모든 요청의 Trace를 저장하지 않고 특정 기준에 따라 일부를 선택하는 방법이다.

### ✅ 392. 필요한 이유

모든 요청의 모든 Span을 수집하면 비용과 처리 부하가 증가할 수 있기 때문이다.

### ✅ 393. 예시

```text
전체 요청:
10,000건

샘플링 비율:
10%
```

약 1,000개의 Root Trace가 선택되는 상황을 기대할 수 있다.

### ✅ 394. 중요한 주의

실제 저장량은 Parent Sampling, Trace 구성, Export 실패와 Backend 정책에 따라 달라질 수 있다.

### ✅ 395. Sampling이 높을수록

더 많은 사례를 조사할 수 있지만 비용과 저장량이 증가한다.

### ✅ 396. Sampling이 낮을수록

드물게 발생하는 중요한 오류를 놓칠 수 있다.

### ✅ 397. 중요한 원칙

**Sampling은 비용을 줄이는 설정이면서 장애 분석에 사용할 수 있는 증거의 범위를 결정하는 운영 정책이다.**

## 54. Head Sampling

### ✅ 398. Head Sampling

Trace가 시작되는 초기 단계에서 수집 여부를 결정하는 방식이다.

### ✅ 399. 예시

```text

↓

Sampling Decision

↓

Record or Drop
```

### ✅ 400. 장점

구현이 비교적 단순하고 불필요한 데이터 생성을 초기부터 제한할 수 있다.

### ✅ 401. 단점

요청이 나중에 오류로 끝날지 느리게 처리될지 처음에는 알기 어렵다.

### ✅ 402. 예시

10% Head Sampling에서 선택되지 않은 요청이 나중에 심각한 오류를 발생시킬 수 있다.

### ✅ 403. 결과

해당 요청의 전체 Trace를 저장하지 못할 수 있다.

### ✅ 404. 중요한 원칙

**Head Sampling만으로 모든 오류 Trace가 반드시 저장되도록 보장할 수는 없다.**

### ✅ 412. 중요한 원칙

**Sampling 비율을 설정한 후에는 실제 저장된 Trace 수와 오류 Trace의 관측 가능성을 검증해야 한다.**

## 56. Tail Sampling

### ✅ 413. Tail Sampling

Trace의 여러 Span이 수집된 이후 전체 또는 상당 부분의 내용을 기준으로 보관 여부를 판단하는 방식이다.

### ✅ 414. 선택 기준 예시

```text
Contains Error

High Latency

Critical Operation

New Release

Random Sample
```

### ✅ 415. 장점

오류가 있는 Trace나 오래 걸린 Trace를 우선 보관하는 정책을 설계할 수 있다.

### ✅ 416. 단점

결정하기 전까지 Trace를 Collector에서 보관해야 할 수 있다.

### ✅ 417. 필요한 자원

```text
Collector Memory

Decision Wait

Trace Buffer

Processing Capacity
```

### ✅ 418. 중요한 한계

SDK의 Head Sampling에서 이미 버린 Span을 Collector의 Tail Sampling이 되살릴 수는 없다.

### ✅ 419. 여러 Collector를 사용할 경우

같은 Trace에 속한 Span들이 적절한 Sampling 처리 위치로 전달되도록 Routing을 검토해야 한다.

### ✅ 420. 현재 추천

처음에는 간단한 Sampling과 기존 오류 로그를 활용하고 실제 누락 문제가 확인되면 Tail Sampling을 검토한다.

### ✅ 421. 중요한 원칙

**Tail Sampling은 정교한 Trace 보관 전략이지만 Collector 자원과 데이터 전달 구조까지 함께 설계해야 한다.**

## 62. OpenTelemetry Collector란?

### ✅ 458. Collector

여러 애플리케이션에서 생성한 관측 데이터를 수신하고 처리하며 Export하는 구성 요소다.

### ✅ 459. 기본 구조

```text
Receivers

↓

Processors

↓

Exporters
```

### ✅ 460. Receiver

애플리케이션이 전송한 OTLP 데이터 등을 수신한다.

### ✅ 461. Processor

Batch 처리, Filtering, Sampling, 데이터 변환 등을 수행한다.

### ✅ 462. Exporter

처리한 관측 데이터를 분석 Backend로 전송한다.

### ✅ 463. OTLP

OpenTelemetry 데이터 전달을 위한 프로토콜이다.

### ✅ 464. 대표적인 기본 Port

```text
4317:
OTLP gRPC

4318:
OTLP HTTP
```

### ✅ 465. 중요한 주의

실제 사용 중인 Exporter 프로토콜과 Collector Receiver 설정이 일치해야 한다.

### ✅ 466. 중요한 원칙

**Collector는 애플리케이션과 관측 Backend 사이의 데이터 전달 및 처리 계층으로 활용한다.**

## 63. 로컬 Collector 설정

### ✅ 467. 최초 검증 목표

실제 운영 AWS에 연결하지 않고 로컬에서 Span이 정상적으로 수집되는지 확인한다.

### ✅ 468. 구성

```text
NestJS Test App
       ↓
127.0.0.1:4318
       ↓
Local OpenTelemetry Collector
       ↓
Debug Exporter
```

### ✅ 469. 설정 파일 예시

```yaml
# otel-collector.local.yaml

receivers:
  otlp:
    protocols:
      http:
        endpoint: 127.0.0.1:4318

processors:
  batch:

exporters:
  debug:
    verbosity: basic

service:
  pipelines:
    traces:
      receivers:
        - otlp

      processors:
        - batch

      exporters:
        - debug
```

### ✅ 470. 중요한 전제

사용하는 Collector Distribution과 설치 버전이 `debug` Exporter 등을 지원해야 한다.

### ✅ 471. 위 설정은 Host에서 실행되는 Collector 기준이다

### ✅ 472. Container에서 실행한다면

Container 내부 Listener와 Host Port Mapping을 별도로 구성해야 한다.

예를 들어 Container 내부에서는 수신 가능한 Interface에 Bind하되 Host에서는 `127.0.0.1`에만 Port를 공개할 수 있다.

### ✅ 473. 중요한 보안 조건

OTLP Port를 인터넷에 인증 없이 공개하지 않는다.

### ✅ 474. 중요한 주의

Debug Exporter는 실험용이다.

실제 고객 데이터의 상세 Trace를 운영 콘솔에 출력하는 목적으로 사용하지 않는다.

### ✅ 475. 중요한 원칙

**최초에는 격리된 로컬 환경에서 Trace 생성과 전달을 검증하고 수집 내용의 안전성을 확인한 뒤 운영 Exporter를 연결한다.**

## 79. In-memory Span Exporter 테스트

### ✅ 582. 외부 Collector 없이 Span을 확인할 수 있다

OpenTelemetry의 In-memory Exporter를 테스트에 활용할 수 있다.

### ✅ 583. SDK v2 계열 구성 예시

```typescript
import {
  trace,
} from '@opentelemetry/api';

import {
  NodeTracerProvider,
} from '@opentelemetry/sdk-trace-node';

import {
  InMemorySpanExporter,
  SimpleSpanProcessor,
} from '@opentelemetry/sdk-trace-base';

const exporter =
  new InMemorySpanExporter();

const provider =
  new NodeTracerProvider({
    spanProcessors: [
      new SimpleSpanProcessor(
        exporter,
      ),
    ],
  });

provider.register();
```

### ✅ 584. 테스트 예시

```typescript
it(
  '부모와 자식 Span이 동일한 Trace를 사용한다',

  async () => {
    const tracer =
      trace.getTracer('trace-test');

    await tracer.startActiveSpan(
      'application.submit',

      async (parent) => {
        try {
          await tracer.startActiveSpan(
            'pricing.calculate',

            async (child) => {
              try {
                expect(
                  child.spanContext().traceId,
                ).toBe(
                  parent.spanContext().traceId,
                );
              } finally {
                child.end();
              }
            },
          );
        } finally {
          parent.end();
        }
      },
    );

    await provider.forceFlush();

    const spans =
      exporter.getFinishedSpans();

    expect(
      spans.map((span) => span.name),
    ).toEqual(
      expect.arrayContaining([
        'application.submit',
        'pricing.calculate',
      ]),
    );
  },
);
```

### ✅ 585. 중요한 전제

실제 SDK 버전과 테스트 Framework에 맞춰 구성해야 한다.

### ✅ 586. 테스트 격리

다른 테스트나 실제 애플리케이션 SDK와 충돌하지 않도록 독립적인 Test Process와 Lifecycle을 구성한다.

### ✅ 587. Cleanup

### ✅ 588. 중요한 한계

실제 NestJS HTTP Instrumentation과 Prisma Integration은 별도 Integration Test로 검증해야 한다.

### ✅ 589. 중요한 원칙

**In-memory Trace 테스트는 SDK 연결과 Span 구성 검증에 활용하고 실제 애플리케이션 연동 테스트로 범위를 확장한다.**

## 📌 요약

1113에서는 새로운 코드가 기존보다 느려졌는지 확인하기 위해 Performance Regression Detection과 Continuous Benchmarking을 다뤘다.

```text
Code Change
       ↓
Baseline Benchmark
       ↓
Candidate Benchmark
       ↓
Performance Regression
```

1114에서는 성능 저하가 발견됐을 때 실제로 어느 처리 단계가 문제인지 추적하는 방법을 다뤘다.

```text
Customer Request
       ↓
Request ID
       ↓
Trace Context
       ↓
HTTP Server Span
       ↓
Business Service Spans
       ↓
Prisma / PostgreSQL Spans
       ↓
External API / Worker Spans
       ↓
OpenTelemetry Collector
       ↓
Trace Visualization
       ↓
Critical Path Analysis
       ↓
Bottleneck Hypothesis
       ↓
Controlled Benchmark
       ↓
Verified Optimization
```

이번 편에서 중요한 원칙은 다음과 같다.

**첫 번째 — Metrics·Logs·Traces는 각각 다른 역할을 수행한다.**

```text
Metrics:
얼마나 느리고 얼마나 실패하는가?

Logs:
무슨 사건이 발생했는가?

Traces:
어떤 작업 경로를 거쳤는가?
```

세 가지 관측 정보를 연결해야 실제 운영 장애를 효과적으로 조사할 수 있다.

**두 번째 — Trace ID와 Request ID를 구분한다.**

Request ID는 개별 HTTP 요청을 추적하고 Trace ID는 연결된 작업 전체를 추적한다.

Idempotency Key와 실제 주문번호도 별도의 목적을 가진다.

**세 번째 — OpenTelemetry 초기화 순서가 중요하다.**

NestJS와 Prisma 등의 대상 라이브러리가 로딩되기 전에 SDK와 Instrumentation을 초기화해야 한다.

**네 번째 — 자동 Instrumentation과 수동 Instrumentation을 함께 활용한다.**

HTTP와 Prisma의 자동 Span을 활용하고 실제 업무 의미를 설명할 필요가 있는 Service에만 수동 Span을 추가한다.

**다섯 번째 — Prisma Span의 Duration과 실제 DB 실행시간을 구분한다.**

DB Client에서 관측한 시간에는 연결 대기나 네트워크 통신, 결과 처리 시간이 포함될 수 있다.

PostgreSQL의 내부 통계와 함께 조사해야 한다.

**여섯 번째 — 비동기 Worker는 별도의 Context 연결이 필요하다.**

```text
Producer Context

↓

Message Context

↓

Consumer Span / Span Link
```

구조를 통해 고객 신청 이후 실행되는 후속 작업을 추적할 수 있다.

**일곱 번째 — Critical Path는 단순히 가장 긴 Span이 아니다.**

순차 실행, 병렬 실행, 작업 의존성, 실제 Join 지점을 고려해야 한다.

Parent와 Child Span의 Duration을 단순 합산해서도 안 된다.

**여덟 번째 — Sampling과 개인정보 보호가 필수다.**

모든 Trace를 무제한 수집하지 않고 업무 중요도와 관측 비용을 고려한다.

실제 고객정보와 Secret은 처음부터 관측 데이터에 포함하지 않는 것이 우선이다.

**아홉 번째 — AI 분석은 원인 후보를 제시하는 역할이다.**

AI가 Trace와 Git Diff를 연결해 분석할 수 있지만 실제 원인은 통제된 Benchmark와 업무 검증을 통해 확인해야 한다.

현재 투게더몰에 가장 적합한 도입 순서는 다음과 같다.

```text
1. 기존 Request ID 구조 확인

2. Frontend 오류와 Backend 로그 연결

3. 실제 Runtime Commit 기록

4. 주요 API Operation 선정

5. 로컬 OpenTelemetry SDK 초기화

6. HTTP Server Span 검증

7. 신청 / 가격 / 주문 Business Span 추가

8. Prisma Instrumentation 검증

9. Local Trace Visualization

10. 기존 CloudWatch 로그와 Trace 연결

11. 개인정보 및 Sampling 정책 검증

12. 필요하면 AWS Trace Export 도입

13. Performance Regression과 Trace 연결

14. AI 기반 병목 분석 자동화
```

특히 현재 1인 개발 환경에서는 처음부터 Browser SDK·Tail Sampling·Grafana Tempo·대규모 Collector Cluster를 모두 도입할 필요는 없다.

가장 먼저 구축할 것은 다음 구조다.

```text
Customer Error / Slow Request
       ↓
Request ID
       ↓
Backend Trace
       ↓
Business Service
       ↓
Prisma / External API
       ↓
Bottleneck Evidence
```

이 연결만 제대로 만들어도 고객이 신청 과정에서 오류를 경험했을 때 여러 로그를 무작정 조사하는 대신 해당 요청의 실제 처리 경로부터 확인할 수 있다.

또한 기존 Git Diff → Local LLM → Markdown → Notion 보고서 자동화에 Trace Evidence Pack을 연결하면 단순히 오늘 변경한 코드를 요약하는 것에서 나아가 **실제 성능 회귀가 발생한 업무와 그 원인 후보, 검증 결과를 함께 기록하는 기술 운영 보고서**로 발전시킬 수 있다.

최종적으로 기억해야 할 원칙은 다음과 같다.

**좋은 Distributed Tracing 시스템은 최대한 많은 Span을 생성하는 시스템이 아니다. 고객의 중요한 업무가 어떤 경로로 처리됐는지 안전하게 연결하고, 어느 작업이 전체 응답시간과 실패에 영향을 주는지 실제 근거로 확인하며, 개발자가 가장 효과적인 개선 지점을 찾아낼 수 있도록 지원하는 시스템이다.**
