## 1. 장애를 수정했는데 같은 문제가 다시 발생하는 이유

### ✅ 1. 1103과의 연결

1103에서는 AI가 장애 원인을 분석하고 안전하게 코드를 수정하는 절차를 다뤘다.

```text
Incident Evidence
       ↓
Root Cause Analysis
       ↓
Fix Proposal
       ↓
Isolated Patch
       ↓
Automated Validation
       ↓
Pull Request
       ↓
Human Approval
       ↓
Deployment Verification
```

1104에서는 여기서 한 단계 더 나아간다.

**한 번 해결했던 장애가 나중에 다른 코드 변경으로 다시 발생하지 않도록 만들 수 있을까?**

### ✅ 2. 실제로 발생하기 쉬운 상황

예를 들어 신청 모달에서 Dropdown이 가려지는 문제를 수정했다고 하자.

```text
10월 10일

신청 모달 Dropdown 오류
       ↓
CSS 수정
       ↓
정상 동작 확인
```

그런데 몇 주 뒤 공통 모달 디자인을 변경한다.

```text
11월 4일

공통 Modal 리팩터링
       ↓
Overflow 변경
       ↓
기존 Dropdown 오류 재발
```

### ✅ 3. 개발자는 과거에 같은 문제를 해결했다

하지만 해당 장애를 방지하는 테스트가 없다면 다시 발생할 수 있다.

### ✅ 4. 기존 개발 방식

```text
오류 발생
    ↓
AI에게 질문
    ↓
수정
    ↓
다음 작업
```

### ✅ 5. 개선된 개발 방식

```text
오류 발생
    ↓
원인 확인
    ↓
수정
    ↓
Regression Test
    ↓
Incident Knowledge
    ↓
Future Change Analysis
    ↓
Relevant Test Execution
```

### ✅ 6. 핵심 개념

**장애 해결 경험을 재사용 가능한 검증 규칙으로 축적한다.**

### ✅ 7. AI가 과거 장애를 기억하게 만드는 것만으로 충분할까?

아니다.

AI가 과거 사례를 검색하더라도 실제 테스트가 실행되지 않으면 같은 오류가 재발할 수 있다.

### ✅ 8. 따라서 두 종류의 지식이 필요하다

```text
Knowledge

무엇이 잘못됐고
왜 잘못됐는가?
```

```text
Executable Regression Test

동일한 문제가
다시 발생했는가?
```

### ✅ 9. 둘의 역할

Incident Knowledge는 문제를 이해하도록 돕는다.

Regression Test는 실제 코드가 요구조건을 만족하는지 검사한다.

### ✅ 10. 이번 편의 목표

```text

Regression Knowledge

Dependency Graph

Test Selection

Risk-based Test Coverage

Git Diff Analysis

Incident Knowledge Base

RAG Retrieval

Knowledge Validation

CI/CD Integration

Local LLM / Notion 연동

Regression Prevention
```

을 다룬다.

## 2. Regression이란?

### ✅ 11. Regression

기존에 정상적으로 동작하던 기능이 코드 변경 이후 다시 고장 나는 현상이다.

### ✅ 12. 예시

```text
기존:
상품 검색 정상

변경:
공통 API Client 수정

결과:
상품 검색 오류
```

### ✅ 13. Regression은 변경한 기능에서만 발생하지 않는다

공통 모듈을 수정하면 직접 수정하지 않은 기능에서도 문제가 발생할 수 있다.

### ✅ 14. 예시

```text
Shared HTTP Client
       ↓
Product API
       ↓
Admin Order API
       ↓
Notification API
```

공통 HTTP Client를 변경하면 여러 기능에 영향을 줄 가능성이 있다.

### ✅ 15. Regression Test

과거에 발생했던 결함이나 중요한 업무 규칙이 다시 깨지지 않았는지 검증하는 테스트다.

### ✅ 16. Regression Test의 핵심

```text
과거 장애
    ↓
실패 조건
    ↓
자동 검증 가능한 Assertion
```

으로 변환한다.

### ✅ 17. 중요한 주의

테스트 코드가 있다고 해서 같은 오류가 영원히 발생하지 않는다는 뜻은 아니다.

테스트가 실제 결함을 감지하도록 유지되고 실행돼야 한다.

## 3. Incident-to-Test란?

### ✅ 18. 기본 개념

실제 운영 장애를 회귀 테스트로 연결하는 절차다.

### ✅ 19. 전체 구조

```text
Production Incident
         ↓
Error Evidence
         ↓
Root Cause
         ↓
Verified Fix
         ↓
Regression Test
         ↓
Test Registry
         ↓
Future PR
         ↓
Automated Test Selection
```

### ✅ 20. Incident

실제 문제가 발생한 기록이다.

### ✅ 21. Root Cause

문제가 발생한 원인이다.

### ✅ 22. Verified Fix

검증된 코드 수정이다.

### ✅ 23. Regression Test

동일한 오류가 재발하지 않도록 검증하는 테스트다.

### ✅ 24. Test Registry

어떤 테스트가 어떤 업무 규칙과 장애를 검증하는지 관리한다.

### ✅ 25. Change Impact Analysis

새 코드 변경이 어떤 업무와 테스트에 영향을 줄 수 있는지 분석한다.

### ✅ 26. Test Selection

영향이 있을 가능성이 높은 테스트를 선택한다.

### ✅ 27. 중요한 원칙

**새로운 오류를 수정할 때마다 무조건 테스트 파일 하나를 추가하는 것이 아니라, 어떤 업무 불변조건이 깨졌는지 먼저 정의한다.**

## 4. Incident에서 무엇을 남겨야 할까?

### ✅ 28. 단순한 기록

```text
신청 모달 오류 수정 완료
```

만 남기면 나중에 활용하기 어렵다.

### ✅ 29. 좋은 Incident Record

```text
Incident ID

Affected Feature

Symptoms

Business Impact

Root Cause

Evidence

Fix Commit

Regression Test

Affected Components

Related Policies

Verification Result
```

### ✅ 30. Symptoms

고객이 경험한 현상이다.

### ✅ 31. Root Cause

실제 결함의 원인이다.

### ✅ 32. Evidence

오류 로그, 테스트 실패, 재현 결과 등의 근거다.

### ✅ 33. Fix Commit

어떤 변경으로 문제를 수정했는지 연결한다.

### ✅ 34. Regression Test

동일한 문제가 다시 발생하지 않도록 검사하는 테스트다.

### ✅ 35. Affected Components

관련 코드와 업무 기능을 나타낸다.

### ✅ 36. 예시

```text
Incident:
INC-20261104-001

Feature:
Application Modal

Symptom:
Dropdown 옵션이 모달 아래에 가려짐

Root Cause:
Overlay Container의 Overflow 설정

Fix:
Overlay Rendering 수정

Regression Test:
application-dropdown.spec.ts

Risk:
MEDIUM
```

### ✅ 37. 중요한 조건

Root Cause가 확인되지 않았다면 추정 원인을 확정 사실로 기록하지 않는다.

## 5. Incident Knowledge의 상태

### ✅ 38. 모든 기록을 동일하게 신뢰하지 않는다

```text
DRAFT

INVESTIGATING

CONFIRMED

RESOLVED

VERIFIED

SUPERSEDED
```

### ✅ 39. DRAFT

초기 장애 기록이다.

### ✅ 40. INVESTIGATING

원인을 조사 중이다.

### ✅ 41. CONFIRMED

실제 원인에 대한 증거가 확인됐다.

### ✅ 42. RESOLVED

수정 또는 운영 조치가 적용됐다.

### ✅ 43. VERIFIED

정해진 검증 기준을 통과했다.

### ✅ 44. SUPERSEDED

새로운 분석이나 시스템 변경으로 기존 설명이 더 이상 유효하지 않은 상태다.

### ✅ 45. AI Retrieval에서 중요한 점

과거의 추정 기록을 최신의 확정된 해결책처럼 제시해서는 안 된다.

### ✅ 46. 따라서 검색 결과에 포함한다

```text
Knowledge Status

Verified At

Application Version

Fix Commit

Test Reference
```

### ✅ 47. 중요한 원칙

**장애 지식베이스는 과거 기록의 모음이 아니라 신뢰 수준과 유효성을 관리하는 시스템이어야 한다.**

## 6. Incident Knowledge Markdown Template

### ✅ 48. 처음부터 DB를 만들 필요는 없다

기존 Markdown과 Notion 업무 기록을 활용할 수 있다.

### ✅ 49. 파일 예시

```text
docs/
  incidents/
    INC-20261104-001.md
```

### ✅ 50. Markdown Template

```markdown
# Incident: INC-20261104-001

## Metadata

- Status: VERIFIED
- Severity: P1
- Environment: Production
- Feature: Application Modal
- Root Cause Status: CONFIRMED

## Symptoms

모바일 신청 모달에서
Dropdown 옵션을 선택할 수 없었다.

## Customer Impact

특정 화면에서
요금제 선택을 완료할 수 없었다.

## Root Cause

Overlay Container의 Overflow 설정으로
Dropdown 목록이 잘렸다.

## Evidence

- Staging 재현 결과
- 실패한 Playwright Test
- 관련 CSS 변경 이력

## Fix

- 관련 Layout 구조 수정
- Overlay 표시 영역 검증

## Git References

- Fix Commit: <verified-commit-sha>
- Pull Request: <verified-pr-reference>

## Regression Test

- Test File: <verified-test-path>
- Test Name: 요금제 Dropdown 선택

## Affected Components

- ApplicationModal
- PlanSelector
- OverlayContainer

## Business Invariant

신청 모달에서
고객은 요금제 옵션을 선택할 수 있어야 한다.

## Verification

- Desktop: PASS
- Mobile: PASS
- Keyboard Interaction: PASS

## Prevention

공통 Overlay 변경 시
신청 모달 회귀 테스트를 실행한다.
```

### ✅ 51. 중요한 주의

실제 확인되지 않은 Git SHA나 Test Path는 임의로 작성하지 않는다.

### ✅ 52. Evidence Link

로그 원문 대신 접근권한이 제한된 증거 참조를 사용할 수 있다.

### ✅ 53. 개인정보

고객 이름, 전화번호, 신청서 원문을 장애 문서에 불필요하게 복사하지 않는다.

## 7. 장애를 테스트로 변환하는 방법

### ✅ 54. 가장 중요한 질문

**어떤 조건이 항상 유지돼야 하는가?**

### ✅ 55. 예시 ①

장애:

```text
Dropdown이 가려짐
```

불변조건:

```text
고객은 신청 모달에서
요금제 옵션을 선택할 수 있어야 한다.
```

### ✅ 56. 예시 ②

장애:

```text
동일 신청 중복 생성
```

불변조건:

```text
동일한 논리적 신청 시도가
중복 주문을 생성해서는 안 된다.
```

### ✅ 57. 예시 ③

장애:

```text
고객이 다른 고객 주문 조회
```

불변조건:

```text
인증된 고객은
허용된 자신의 주문만 조회할 수 있다.
```

### ✅ 58. 예시 ④

장애:

```text
쿠폰이 중복 발급됨
```

불변조건:

```text
동일한 발급 대상과 발급 정책에서
중복 발급이 발생하지 않아야 한다.
```

### ✅ 59. 테스트는 증상보다 불변조건을 검증한다

특정 오류 메시지가 사라졌다는 사실만 확인하면 실제 문제는 남아 있을 수 있다.

### ✅ 60. 좋은 Regression Test

문제가 발생했던 입력·상태·행동에서 잘못된 결과가 재발하는지 검사한다.

## 8. Regression Test Quality

### ✅ 61. 형식적인 테스트는 의미가 없다

```typescript
expect(true).toBe(true);
```

는 업무 동작을 검증하지 않는다.

### ✅ 62. 구현 결과를 그대로 기대값으로 사용하지 않는다

예:

```typescript
const actual = calculatePrice(input);

expect(actual).toBe(actual);
```

이 테스트는 가격 계산 오류를 감지하지 못한다.

### ✅ 63. 기대값의 출처

```text
Approved Business Rule

Known Test Fixture

Security Invariant

Verified Incident Behavior
```

등이어야 한다.

### ✅ 64. Red-Green 검증

가능하면 기존 오류 상태에서 테스트가 실패하는지 확인한다.

```text
Before Fix:
FAIL

After Fix:
PASS
```

### ✅ 65. 재현 불가능한 장애

실제 재현하지 못했다면 `NOT_REPRODUCED`라고 기록한다.

### ✅ 66. 테스트 범위

```text
Unit

Integration

Contract

Security

E2E
```

중 결함의 성격에 맞는 계층을 선택한다.

### ✅ 67. 중요한 원칙

**회귀 테스트는 과거 장애를 설명하는 문서가 아니라 미래 코드에서 결함을 탐지할 수 있는 실행 가능한 검증이어야 한다.**

## 9. 사례 ① — 신청 모달 UI 회귀 테스트

### ✅ 68. 장애

요금제 Dropdown이 화면 밖으로 잘린다.

### ✅ 69. 권장 테스트

실제 브라우저에서 다음 동작을 검증한다.

```text
Application Modal Open
       ↓
Plan Dropdown Open
       ↓
Option Visible
       ↓
Option Click
       ↓
Selection Updated
```

### ✅ 70. Playwright 예시

```typescript
import {
  test,
  expect,
} from '@playwright/test';

test(
  '신청 모달에서 요금제를 선택할 수 있다',
  async ({ page }) => {
    await page.goto('/test-product');

    await page.getByRole('button', {
      name: '신청하기',
    }).click();

    const dialog = page.getByRole('dialog');

    await expect(dialog).toBeVisible();

    await dialog.getByRole('combobox', {
      name: '요금제',
    }).click();

    const option = page.getByRole('option', {
      name: '테스트 요금제',
    });

    await expect(option).toBeVisible();

    await option.click();

    await expect(
      dialog.getByRole('combobox', {
        name: '요금제',
      }),
    ).toContainText('테스트 요금제');
  },
);
```

### ✅ 71. 코드 전제

Staging의 실제 Router·Accessible Name·컴포넌트 구조에 맞게 작성해야 한다.

### ✅ 72. Production에서 실행할까?

실제 주문을 생성하지 않는 안전한 UI 상호작용 검사에 한정한다.

### ✅ 73. 테스트 연결

```text
Incident:
Dropdown Clipped

Test:
application-dropdown.spec.ts

Affected Area:
Application Modal / Overlay
```

### ✅ 74. 향후 자동 선택

공통 Modal이나 Overlay 코드를 수정하면 이 테스트가 실행되도록 연결한다.

## 10. 사례 ② — 중복 신청 방지

### ✅ 75. 장애

같은 고객의 동일한 제출 시도가 중복 저장된다.

### ✅ 76. 위험한 해결

Frontend에서 버튼만 비활성화하는 것이다.

### ✅ 77. 실제 불변조건

```text
동일한 논리적 Attempt Key로
여러 요청이 들어와도
하나의 신청 결과만 생성한다.
```

### ✅ 78. 검증할 사례

```text
Sequential Duplicate

Concurrent Duplicate

Timeout After Commit

Repeated Retry

Different Valid Attempt
```

### ✅ 79. 중요한 구분

동일한 신청 시도와 고객의 별도 신청은 구분해야 한다.

### ✅ 80. 테스트 환경

Staging 또는 Test Database를 사용한다.

### ✅ 81. Production에서는

실제 중복 주문을 생성해 확인하지 않는다.

### ✅ 82. 테스트 종류

```text
Backend Integration Test

Database Constraint Test

Concurrency Test
```

가 적합하다.

### ✅ 83. 변경 영향

다음 파일 변경 시 관련 테스트를 실행해야 할 수 있다.

```text
Order Service

Lead Service

Idempotency Middleware

Database Constraint

Transaction Handling
```

## 11. 사례 ③ — 인증·권한 회귀 테스트

### ✅ 84. 장애

관리자 또는 고객의 주문 접근권한이 잘못 적용된다.

### ✅ 85. 불변조건

```text
고객 A는 고객 B의 주문을
조회할 수 없어야 한다.
```

### ✅ 86. 테스트 대상

```text
Authentication Guard

Authorization Guard

Order Access Policy

Resource Ownership

Session Validation
```

### ✅ 87. 기본 테스트

```text
Customer A → Order A
ALLOW

Customer A → Order B
DENY

Unauthenticated → Protected Order
DENY
```

### ✅ 88. 중요

성공적인 거부 응답뿐 아니라 개인정보가 반환되지 않았는지도 확인한다.

### ✅ 89. 관련 변경

공통 인증 Middleware를 수정했다면 주문 모듈을 직접 수정하지 않았더라도 권한 테스트가 필요하다.

### ✅ 90. 핵심

**변경된 파일만 기준으로 테스트를 선택하면 놓칠 수 있는 대표적인 사례다.**

## 13. Dependency Graph

### ✅ 98. Dependency Graph란?

모듈이나 파일 사이의 의존 관계를 그래프로 표현한 것이다.

### ✅ 99. 예시

```text
ApplicationPage
        ↓
ApplicationModal
        ↓
PlanSelector
        ↓
SharedDropdown
```

### ✅ 100. SharedDropdown 수정

해당 컴포넌트를 사용하는 여러 기능에 영향을 줄 수 있다.

### ✅ 101. 직접 의존성

A가 B를 직접 Import하는 관계다.

### ✅ 102. 간접 의존성

A가 B를 사용하고 B가 C를 사용한다면 A는 C의 영향을 받을 수 있다.

### ✅ 103. 예시

```text
ApplicationPage
        ↓
ApplicationModal
        ↓
SharedDropdown
```

`SharedDropdown` 수정은 간접적으로 ApplicationPage에 영향을 줄 수 있다.

### ✅ 104. Graph Traversal

변경된 모듈에 의존하는 다른 모듈을 추적한다.

### ✅ 105. 중요한 방향

단순히 변경 파일이 Import하는 모듈만 찾는 것이 아니다.

**변경된 파일을 사용하는 상위 모듈도 확인해야 한다.**

## 14. Dependency Graph의 한계

### ✅ 106. 정적 Import만으로 모든 의존성을 확인할 수 있을까?

아니다.

### ✅ 107. Dynamic Import

실행 중 조건에 따라 모듈이 로드될 수 있다.

### ✅ 108. Shared CSS

명시적으로 연결된 TypeScript Import가 없어도 공통 스타일 변경이 여러 화면에 영향을 줄 수 있다.

### ✅ 109. Environment Variables

공통 환경변수 수정은 여러 서비스의 동작을 변경할 수 있다.

### ✅ 110. Database Schema

Prisma Model이나 Migration 변경은 여러 서비스와 Worker에 영향을 줄 수 있다.

### ✅ 111. External API Contract

외부 API 응답 구조가 바뀌면 여러 기능이 동시에 실패할 수 있다.

### ✅ 112. Worker와 Scheduler

동일한 Domain Service를 HTTP Controller와 Background Worker가 함께 사용할 수 있다.

### ✅ 113. 따라서 Dependency 종류를 구분한다

```text
Static Import

Runtime Dependency

Database Dependency

Configuration Dependency

Workflow Dependency

External API Dependency

Business Rule Dependency
```

### ✅ 114. 중요한 원칙

**Dependency Graph는 영향 분석을 위한 중요한 도구지만 완전한 업무 영향도의 증명은 아니다.**

## 15. Git Diff를 어떻게 분석할까?

### ✅ 115. 변경 파일 목록부터 확인한다

```bash
git status --short

git branch --show-current
```

### ✅ 116. 비교 기준이 필요하다

PR 작업에서는 Base Branch와 현재 Head를 비교한다.

### ✅ 117. 예시

```bash
git fetch origin main

BASE=$(git merge-base origin/main HEAD)

git diff --name-status "$BASE" HEAD
```

### ✅ 118. 의미

`merge-base`는 두 Branch의 공통 조상 Commit을 찾는다.

### ✅ 119. 주의

위 명령은 현재 Working Tree의 미커밋 변경을 포함하지 않는다.

### ✅ 120. 미커밋 변경

별도로 `git diff`와 `git diff --cached`를 확인해야 한다.

### ✅ 121. GitHub Actions

CI에서 실제 PR의 Base·Head를 기준으로 비교하도록 설정한다.

### ✅ 122. Shallow Clone

일부 Git History가 없으면 정확한 Merge Base를 계산하지 못할 수 있다.

### ✅ 123. 따라서

필요한 범위의 Git History를 가져오도록 설정한다.

### ✅ 124. 변경 상태

```text
Added

Modified

Deleted

Renamed
```

를 구분한다.

### ✅ 125. 중요한 점

**삭제된 파일이나 이름이 변경된 파일도 테스트 영향 분석에서 빠뜨리면 안 된다.**

## 17. Test Selection이란?

### ✅ 132. 개념


를 실행하면 검증 범위가 넓어진다.

```text

     ↓

     ↓

```

변경 이후 빠르게 피드백을 받을 수 있다.

### ✅ 137. 위험

잘못된 Test Selection으로 중요한 검증이 누락될 수 있다.

### ✅ 138. 따라서 Test Selection은 최적화다

**정확성보다 실행 속도를 무조건 우선하지 않는다.**

### ✅ 139. 권장 구조

```text

+

Change-related Tests

+

Periodic Full Test Suite
```

### ✅ 140. 중요한 원칙

필수 보안·업무 검증은 AI가 관련성이 낮다고 판단했다는 이유만으로 제외하지 않는다.

## 24. TypeScript Test Selection 예시

### ✅ 198. 최소 구조

다음은 실제 Registry와 연동하기 전의 개념 코드다.

```typescript
type TestGroup =
  | 'lint'
  | 'typecheck'
  | 'application-e2e'
  | 'authorization'
  | 'order-integration'
  | 'pricing'
  | 'full-suite';

interface SelectionResult {
  groups: TestGroup[];
  reasons: string[];
}
```

### ✅ 199. Selection 함수

```typescript
function selectTests(
  changedFiles: string[],
): SelectionResult {
  const groups = new Set<TestGroup>([
    'lint',
    'typecheck',
  ]);

  const reasons: string[] = [];

  if (changedFiles.length === 0) {
    groups.add('full-suite');
    reasons.push('NO_CHANGE_DATA');
  }

  for (const rawFile of changedFiles) {
    const file = rawFile.replaceAll('\\', '/');

    if (
      file.startsWith(
        'apps/frontend/src/components/application/',
      )
    ) {
      groups.add('application-e2e');

      reasons.push(
        `APPLICATION_COMPONENT_CHANGED:${file}`,
      );

      continue;
    }

    if (
      file.startsWith(
        'apps/backend/src/auth/',
      )
    ) {
      groups.add('authorization');

      reasons.push(
        `AUTH_MODULE_CHANGED:${file}`,
      );

      continue;
    }

    if (
      file.startsWith(
        'apps/backend/src/orders/',
      )
    ) {
      groups.add('order-integration');

      reasons.push(
        `ORDER_MODULE_CHANGED:${file}`,
      );

      continue;
    }

    if (
      file.startsWith(
        'apps/backend/src/pricing/',
      )
    ) {
      groups.add('pricing');

      reasons.push(
        `PRICING_MODULE_CHANGED:${file}`,
      );

      continue;
    }

    groups.add('full-suite');

    reasons.push(
      `UNKNOWN_OR_SHARED_SCOPE:${file}`,
    );
  }

  return {
    groups: [...groups],
    reasons,
  };
}
```

### ✅ 200. 중요한 전제

위 경로는 예시다.

실제 Repository 구조에 맞춰 수정해야 한다.

### ✅ 201. 이 코드의 장점

알려진 일부 영역에서 필요한 테스트를 선택하고 불명확한 변경에서는 전체 테스트를 선택한다.

### ✅ 202. 이 코드의 한계

공통 CSS, 공유 Service, 동적 의존성을 완전하게 분석하지 않는다.

### ✅ 203. 추가 보완

실제 Module Graph와 Test Registry, 필수 업무 정책을 함께 사용해야 한다.

### ✅ 204. 중요

`full-suite`가 선택됐다면 실행 코드에서도 실제 전체 테스트를 실행해야 한다.

### ✅ 250. 하지만 주의

## 📌 요약

1103에서는 AI가 생성한 수정안을 안전하게 검증하고 배포하는 방법을 다뤘다.

```text
Incident
    ↓
AI Fix Proposal
    ↓
Minimal Patch
    ↓
Regression Test
    ↓
CI Validation
    ↓
Human Review
    ↓
Deployment
```

1104에서는 장애 경험을 미래의 코드 변경에 재사용하는 방법을 다뤘다.

```text
Past Incident
       ↓
Verified Root Cause
       ↓
Regression Test
       ↓
Incident Knowledge
       ↓
Test Registry
       ↓
────────────────────
       ↓
New Git Change
       ↓
Change Impact Analysis
       ↓
Relevant Test Selection
       ↓
Regression Validation
       ↓
Human Review
       ↓
Safe Deployment
```

이번 편의 핵심 원칙은 일곱 가지다.

**첫 번째 — 장애를 수정했다면 재발 방지 테스트를 남긴다.**

단순히 오류를 해결하고 다음 작업으로 넘어가지 않는다.

**두 번째 — 장애 문서와 테스트는 다르다.**

장애 문서는 원인을 설명하고 테스트는 실제 결함을 감지한다.

**세 번째 — 변경 파일만으로 영향 범위를 판단하지 않는다.**

공통 UI, 인증, DB, Worker, 외부 API처럼 간접적인 영향도 고려해야 한다.

**네 번째 — 선택적 테스트는 최적화 수단이다.**

AI가 관련성이 낮다고 판단했다는 이유로 중요한 보안·업무 테스트를 제외하지 않는다.

**다섯 번째 — 테스트가 없거나 영향 범위를 모르면 안전하다고 판단하지 않는다.**

```text
Unknown Impact

↓

Full Suite / Manual Review
```

가 기본적인 안전한 방향이다.

**여섯 번째 — 과거 장애 지식에도 신뢰 수준과 유효기간이 있다.**

예전 해결책이 현재 프로젝트에도 그대로 적용되는지 검증해야 한다.

**일곱 번째 — AI는 추가 테스트를 제안할 수 있지만 필수 검증을 제거하는 권한을 갖지 않는다.**

현재 투게더몰에서는 다음 순서가 가장 현실적이다.

```text
1. 과거 중요 장애 목록 정리

2. Business Invariant 정의

3. 핵심 Regression Test 작성

4. Incident Markdown Template

5. Test Registry

6. Git Diff 기반 Change Impact

7. Risk-based Test Selection

8. GitHub Actions Regression Gate

9. Local LLM / Notion Knowledge 연동

10. 필요하면 Semantic Search
```

특히 현재 1인 개발 환경에서는 처음부터 별도 지식 검색 서버나 복잡한 테스트 오케스트레이터를 구축할 필요가 없다.

기존 Git·Markdown·Jest 또는 Vitest·Playwright·GitHub Actions·Notion을 정리하는 것만으로도 충분히 시작할 수 있다.

예를 들어 신청 모달의 Dropdown 오류를 해결했다면:

```text
Incident 기록

+

Playwright Regression Test

+

Test Registry

+

공통 Modal 변경 시 자동 실행
```

로 연결한다.

주문 중복 생성 오류를 해결했다면:

```text
Incident 기록

+

Idempotency Integration Test

+

Order Service 변경 시 자동 실행
```

로 연결한다.

이 구조가 축적되면 개발자는 새로운 기능을 개발할 때마다 과거에 어떤 문제가 있었는지 처음부터 다시 기억할 필요가 줄어든다.

하지만 AI가 과거 사례를 찾았다는 사실만으로 자동 수정이 안전해지는 것은 아니다.

최종적으로 기억해야 할 원칙은 다음과 같다.

**좋은 개발 자동화는 AI가 더 많은 코드를 작성하게 만드는 시스템이 아니다. 과거 장애를 검증 가능한 테스트와 신뢰할 수 있는 지식으로 남겨, 미래의 코드 변경에서 같은 문제가 반복되지 않도록 만드는 시스템이다.**
