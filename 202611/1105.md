## 1. 테스트가 실패했는데 다시 실행하니 성공했다

### ✅ 1. 1104와의 연결

1104에서는 과거 장애를 회귀 테스트로 만들고, 새로운 코드 변경 시 필요한 테스트를 자동 선택하는 방법을 다뤘다.

```text

      ↓
Regression Test
      ↓
Test Registry
      ↓
Git Diff
      ↓
Change Impact Analysis
      ↓
Relevant Test Selection
      ↓
CI Validation
```

1105에서는 여기서 한 가지 더 중요한 문제를 다룬다.

**선택한 테스트 자체가 불안정하다면 자동 검증 결과를 믿을 수 있을까?**

### ✅ 2. 흔한 상황

```text

↓
```

### ✅ 4. 하지만 위험하다

예를 들어 신청서를 중복 생성하는 Race Condition이 발생했다가 다음 실행에서는 정상적으로 동작했을 가능성이 있다.

## 2. Flaky Test란?

### ✅ 10. 정의

Flaky Test는 동일한 코드와 테스트 조건에서 결과가 일관되지 않게 나타나는 테스트다.

### ✅ 11. 예시

```text
같은 Commit

같은 Test

PASS

FAIL

PASS

PASS

FAIL
```

### ✅ 12. 중요한 특징

코드를 변경하지 않았는데도 결과가 달라진다.

### ✅ 13. 하지만 Flaky Test의 원인은 하나가 아니다

```text
Test Timing

Shared State

Concurrency

Network Dependency

Clock / Timezone

Random Data

External Service

Actual Product Race Condition
```

### ✅ 14. Playwright의 Flaky 분류

Playwright는 첫 실행에 실패하고 재시도에서 성공한 테스트를 `flaky`로 분류한다.

### ✅ 15. 중요한 구분

Playwright의 `flaky`는 실행 결과에 대한 분류다.

그 자체가 **테스트 코드에 결함이 있다는 확정 진단은 아니다.**

### ✅ 16. 실제 제품 결함일 수도 있다

예:

```text
Order Service

Concurrent Requests
      ↓
Race Condition
      ↓
가끔 중복 주문 생성
```

### ✅ 17. 잘못된 판단

```text
Retry PASS

↓

테스트가 잘못된 것

↓

무시
```

라고 처리해서는 안 된다.

### ✅ 18. 올바른 판단

```text
Retry PASS
      ↓
Intermittent Failure Observed
      ↓
Root Cause Investigation
```

## 3. Deterministic Test와 Non-deterministic Test

### ✅ 19. Deterministic Test

동일한 입력과 통제된 조건에서 일관된 결과를 반환하는 테스트다.

### ✅ 20. 예시

```typescript
function add(a: number, b: number): number {
  return a + b;
}

test('두 수를 더한다', () => {
  expect(add(2, 3)).toBe(5);
});
```

### ✅ 21. Non-deterministic Test

실행 시점이나 환경에 따라 결과가 달라질 수 있는 테스트다.

### ✅ 22. 예시

```typescript
test('현재 시간이 오전이다', () => {
  expect(new Date().getHours()).toBeLessThan(12);
});
```

### ✅ 23. 문제

오전에는 성공하지만 오후에는 실패할 수 있다.

### ✅ 24. 실제 서비스에도 비결정적인 요소가 있다

```text
Network Latency

Concurrent Requests

Worker Scheduling

Database Lock

External API Response

System Clock
```

### ✅ 25. 모든 비결정성을 제거할 수 있을까?

실제 운영 환경에서는 불가능하다.

### ✅ 26. 대신 테스트 조건을 통제한다

```text
Fixed Test Data

Controlled Clock

Mock Provider

Isolated Database

Explicit Assertions

Known Environment
```

### ✅ 27. 중요한 원칙

**테스트 환경의 불필요한 변동성을 제거하되, 실제 제품의 동시성·오류 복구 능력까지 숨겨서는 안 된다.**

## 4. 테스트 실패의 네 가지 분류

### ✅ 28. 기본 분류

```text
PRODUCT_DEFECT

TEST_DEFECT

INFRASTRUCTURE_FAILURE

UNDETERMINED
```

### ✅ 29. PRODUCT_DEFECT

실제 애플리케이션이 업무 요구사항을 만족하지 못한 경우다.

예:

```text
동일한 신청으로 주문 2건 생성
```

### ✅ 30. TEST_DEFECT

테스트 코드나 Fixture가 잘못된 경우다.

예:

```text
요소가 나타나기 전에 즉시 검사
```

### ✅ 31. INFRASTRUCTURE_FAILURE

테스트 실행 환경이 정상적으로 준비되지 않은 경우다.

예:

```text
CI Runner Disk Full

Test DB Connection Failure

Browser Installation Failure
```

### ✅ 32. UNDETERMINED

현재 증거만으로 원인을 확인할 수 없는 상태다.

### ✅ 33. 중요한 구분

한 번 실패했다가 성공했다는 이유만으로 `TEST_DEFECT`라고 판단하지 않는다.

### ✅ 34. 보조 상태

```text
SUSPECTED

CONFIRMED
```

를 추가해 분류의 확실성을 표현할 수 있다.

### ✅ 35. 예시

```json
{
  "failureType": "TEST_DEFECT",
  "confidence": "CONFIRMED",
  "evidence": "잘못된 즉시 Assertion을 안정적인 Locator Assertion으로 변경한 뒤 반복 검증"
}
```

가상 진단 결과다.

### ✅ 36. AI가 원인 분류를 도와줄 수 있다

하지만 AI의 판단만으로 `CONFIRMED` 처리하지 않는다.

## 5. Flaky Test의 주요 발생 원인

### ✅ 37. 대표 원인

| 원인 | 실제 현상 |
|---|---|
| Async Timing | 데이터 로딩 전 검증 |
| Shared State | 다른 테스트가 데이터를 변경 |
| Concurrency | 테스트 순서에 따라 결과 변경 |
| Network | 외부 API 응답 지연 |
| Test Data | 고정 ID 또는 중복 Fixture |
| Clock | 날짜·시간대 차이 |
| Randomness | 무작위 입력값 |
| Resource | CI CPU·Memory 부족 |
| Browser | 브라우저별 동작 차이 |
| Product Race | 실제 서비스의 동시성 결함 |

### ✅ 38. 대부분의 원인은 테스트 코드만 보고 확정하기 어렵다

실제 실행 로그, Fixture, CI 환경, 애플리케이션 상태를 함께 확인해야 한다.

### ✅ 39. 원인 분석 순서

```text
Failure
    ↓
Failed Assertion
    ↓
Test Steps
    ↓
Application State
    ↓
Test Data
    ↓
Concurrency
    ↓
Environment
    ↓
Root Cause
```

### ✅ 40. 중요한 원칙

**Timeout을 늘리거나 Retry를 추가하기 전에 실패 조건부터 확인한다.**

## 6. 가장 흔한 문제 — 고정 시간 대기

### ✅ 41. 잘못된 Playwright 테스트

```typescript
await page.goto('/products');

await page.waitForTimeout(3000);

expect(
  await page.getByText('상품 목록').isVisible(),
).toBe(true);
```

### ✅ 42. 문제

3초 안에 렌더링이 끝난다는 보장이 없다.

### ✅ 43. CI에서 발생할 수 있는 상황

```text
Local
0.5초 로딩

CI
3.5초 로딩

↓

FAIL
```

### ✅ 44. 반대 상황

항상 0.5초 만에 끝나는 작업이라면 불필요하게 3초를 기다리게 된다.

### ✅ 45. 해결 방법

고정 시간 대신 실제 완료 조건을 기다린다.

### ✅ 46. 개선 코드

```typescript
import {
  test,
  expect,
} from '@playwright/test';

test('상품 목록을 표시한다', async ({ page }) => {
  await page.goto('/products');

  await expect(
    page.getByRole('heading', {
      name: '상품 목록',
    }),
  ).toBeVisible();
});
```

### ✅ 47. Web-first Assertion

Playwright는 `toBeVisible()`과 같은 Assertion에서 기대 조건을 일정 시간 동안 재검사한다.

### ✅ 48. 중요한 차이

```typescript
expect(await locator.isVisible()).toBe(true);
```

는 해당 순간의 결과를 즉시 검사한다.

반면:

```typescript
await expect(locator).toBeVisible();
```

는 조건을 기다리면서 검증한다.

### ✅ 49. Playwright 공식 권장

`page.waitForTimeout()`은 디버깅 용도 외에는 사용을 지양하도록 안내한다.

### ✅ 50. 주의

자동 대기가 있다고 모든 Race Condition이 해결되는 것은 아니다.

어떤 상태가 완료됐는지 정확하게 정의해야 한다.

## 7. 실제 고객 행동을 기준으로 기다린다

### ✅ 51. 화면이 표시된 것과 사용 가능한 것은 다르다

예:

```text
신청 모달 표시

↓

요금제 API Loading

↓

선택 옵션 활성화
```

### ✅ 52. 잘못된 검사

모달이 보인다는 사실만 확인한다.

### ✅ 53. 좋은 검사

실제 요금제 옵션이 선택 가능한지 확인한다.

### ✅ 54. 예시

```typescript
test('요금제 선택이 가능하다', async ({ page }) => {
  await page.goto('/test-product');

  await page.getByRole('button', {
    name: '신청하기',
  }).click();

  const dialog = page.getByRole('dialog');

  await expect(dialog).toBeVisible();

  const selector = dialog.getByRole('combobox', {
    name: '요금제',
  });

  await expect(selector).toBeEnabled();

  await selector.click();

  await page.getByRole('option', {
    name: '테스트 요금제',
  }).click();
});
```

### ✅ 55. 코드 전제

실제 UI의 Accessible Name, Staging Fixture, Routing 구조에 맞춰 작성해야 한다.

### ✅ 56. 중요한 점

데이터가 로딩됐다는 사실과 고객이 기능을 사용할 수 있다는 사실을 구분한다.

## 9. Test Isolation이란?

### ✅ 66. Test Isolation

하나의 테스트가 다른 테스트의 실행 결과나 상태에 의존하지 않도록 분리하는 것이다.

### ✅ 67. 잘못된 구조

```text
Test A
주문 생성

↓

Test B
Test A의 주문 상태 변경

↓

Test C
Test B의 주문 삭제
```

### ✅ 68. 문제

Test B만 단독으로 실행하면 필요한 주문 데이터가 없어서 실패할 수 있다.

### ✅ 69. 올바른 구조

```text
Test A
독립적인 Fixture 생성
검증
정리

Test B
독립적인 Fixture 생성
검증
정리
```

### ✅ 70. Browser Isolation

```text
Cookies

Local Storage

Session Storage

Browser Context
```

등을 분리한다.

### ✅ 71. Playwright

기본적인 Test Fixture 구조를 활용하면 테스트마다 분리된 Browser Context를 사용할 수 있다.

### ✅ 72. 하지만

브라우저를 분리했다고 Backend DB까지 자동으로 분리되는 것은 아니다.

### ✅ 73. 중요한 원칙

**브라우저 격리와 데이터베이스 격리는 서로 다른 문제다.**

## 10. Shared State 문제

### ✅ 74. 흔한 문제

```text
Test A
테스트 주문 상태를 COMPLETED로 변경

Test B
같은 주문이 PENDING일 것으로 기대

↓

FAIL
```

### ✅ 75. 테스트 순서에 따라 결과가 달라진다

### ✅ 76. Shared State 후보

```text
Database Rows

In-memory Cache

Singleton Service

Mock State

Global Variables

Filesystem

Environment Variables
```

### ✅ 77. Jest / Vitest 환경

Mock 호출 기록이나 Singleton 상태가 다음 테스트에 영향을 줄 수 있다.

### ✅ 78. 해결

테스트별로 상태를 초기화한다.

### ✅ 79. 예시

```typescript
beforeEach(() => {
  jest.clearAllMocks();
});
```

### ✅ 80. 주의

`clearAllMocks()`는 Mock 호출 기록 등을 초기화하는 기능이다.

테스트 대상의 모든 전역 상태, DB, 파일, 실제 외부 서비스를 초기화하지는 않는다.

### ✅ 81. `resetAllMocks`, `restoreAllMocks`

이 기능들은 서로 다른 목적을 가지므로 현재 Jest 설정을 확인하고 사용한다.

### ✅ 82. 중요한 원칙

테스트 상태의 원천을 이해하지 못한 채 `beforeEach`에 초기화 코드를 무작정 추가하지 않는다.

## 11. NestJS와 PostgreSQL 테스트 격리

### ✅ 83. 현재 Backend 환경에서 중요한 문제

NestJS Integration Test가 PostgreSQL을 사용하는 경우다.

### ✅ 84. 위험한 방식

테스트가 실제 운영 DB를 향해 실행되는 것이다.

### ✅ 85. 필요한 분리

```text
Production DB

≠

Local Test DB

≠

Staging Test DB
```

### ✅ 86. 환경변수만 믿을 수 있을까?

실행 전에 실제 연결 대상도 검증해야 한다.

### ✅ 87. 예시

```typescript
function assertSafeTestDatabase(): void {
  if (process.env.NODE_ENV !== 'test') {
    throw new Error('TEST_ENV_REQUIRED');
  }

  const databaseUrl = process.env.DATABASE_URL;

  if (!databaseUrl) {
    throw new Error('TEST_DATABASE_URL_REQUIRED');
  }

  const parsed = new URL(databaseUrl);

  const approvedHosts = new Set([
    'localhost',
    '127.0.0.1',
    'test-db',
  ]);

  if (!approvedHosts.has(parsed.hostname)) {
    throw new Error('UNAPPROVED_TEST_DATABASE_HOST');
  }
}
```

### ✅ 88. 위 코드는 최소 예시다

실제 테스트 DB 이름, AWS Account, 사용자 권한 등을 추가로 확인해야 한다.

### ✅ 89. 특히 주의

Host가 `localhost`라는 이유만으로 안전한 DB라고 단정할 수 없다.

SSH Tunnel이나 Port Forwarding으로 Production DB에 연결돼 있을 수 있기 때문이다.

### ✅ 90. 권장 구조

별도 테스트용 DB Credential을 사용하고 해당 Credential 자체가 Production DB를 변경할 수 없도록 제한한다.

### ✅ 91. 중요한 원칙

**환경변수 검증과 실제 권한 격리를 함께 적용한다.**

## 12. 테스트 데이터 충돌

### ✅ 92. 고정된 데이터 사용

```text

TEST-ORDER-001
```


```typescript
  return `TEST-${randomUUID()}`;
```

### ✅ 96. 중요한 점

무작위 식별자를 사용한다고 테스트 자체가 비결정적이어야 하는 것은 아니다.

### ✅ 97. 목적

테스트 데이터 충돌을 방지하기 위해 ID만 고유하게 만드는 것이다.

### ✅ 98. 기대 결과

동일한 업무 규칙으로 검증한다.

### ✅ 99. Test Fixture

```text

Test ID

Resource ID

Owner
```

를 연결해 정리할 수 있다.

### ✅ 100. 정리 정책

테스트 종료 시 생성한 데이터만 제거한다.

### ✅ 101. 위험

테스트 데이터 정리를 위해 DB 전체를 초기화하는 명령을 실행해서는 안 된다.

### ✅ 102. 중요한 원칙

**테스트 데이터 정리는 실제 생성한 리소스의 범위 안에서만 수행한다.**

## 13. Database Transaction으로 테스트 격리하기

### ✅ 103. Transaction Rollback

하나의 테스트에서 수행한 DB 변경을 Rollback하는 방식으로 격리할 수 있다.

### ✅ 104. 개념

```text
BEGIN
   ↓
Test Data Insert
   ↓
Test Assertions
   ↓
ROLLBACK
```

### ✅ 105. 장점

테스트 이후 DB 상태를 정리하기 쉽다.

### ✅ 106. 하지만 NestJS E2E에서는 한계가 있다

HTTP 요청을 처리하는 애플리케이션이 테스트 코드와 별도의 DB Connection을 사용한다면 테스트의 Transaction으로 모든 변경을 Rollback할 수 없다.

### ✅ 107. 외부 Side Effect

DB Rollback으로 실제 메시지 발송이나 S3 Write가 취소되는 것도 아니다.

### ✅ 108. 따라서

```text
Unit / Repository Test:
Transaction Rollback 고려

HTTP E2E:
별도 Test DB와 Fixture Lifecycle

External Provider:
Mock / Sandbox
```

처럼 구분한다.

### ✅ 109. Prisma Interactive Transaction

Prisma는 Transaction API를 제공한다.

### ✅ 110. 주의

모든 테스트를 하나의 장시간 Transaction으로 감싸는 방식은 Lock, Timeout, Connection 점유 문제를 만들 수 있다.

### ✅ 111. 중요한 원칙

**Transaction은 유용한 격리 수단이지만 모든 Integration Test를 자동으로 안전하게 만드는 장치는 아니다.**

### ✅ 120. 권장 조사

```text

vs

workers=2

vs

현재 CI Worker 설정
```

으로 비교한다.

### ✅ 121. 중요한 원칙

**병렬 실행을 끄는 것은 진단 도구일 수 있지만 동시성 결함의 근본적인 해결책은 아니다.**

## 18. Clock과 Timezone

### ✅ 149. 날짜 관련 테스트는 불안정하기 쉽다

예:

```text
월말

자정

UTC

쿠폰 유효기간

예약 만료
```

### ✅ 150. 잘못된 코드

```typescript
test('쿠폰이 유효하다', () => {
  const expiresAt = new Date('2026-11-05T12:00:00Z');

  expect(expiresAt.getTime()).toBeGreaterThan(
    Date.now(),
  );
});
```

### ✅ 151. 문제

시간이 흐르면 테스트가 실패한다.

### ✅ 152. 해결

고정된 Clock을 사용한다.

### ✅ 153. 예시

```typescript
describe('쿠폰 만료 검증', () => {
  beforeEach(() => {
    jest.useFakeTimers();

    jest.setSystemTime(
      new Date('2026-11-05T00:00:00Z'),
    );
  });

  afterEach(() => {
    jest.useRealTimers();
  });

  test('만료 전 쿠폰은 유효하다', () => {
    const expiresAt = new Date(
      '2026-11-06T00:00:00Z',
    );

    expect(Date.now()).toBeLessThan(
      expiresAt.getTime(),
    );
  });
});
```

### ✅ 154. 주의

Fake Timer가 비동기 작업이나 실제 I/O 동작에 영향을 줄 수 있다.

### ✅ 155. 더 좋은 구조

업무 로직에 현재 시간을 명시적인 입력으로 전달할 수 있다.

### ✅ 156. 예시

```typescript
function isExpired(
  expiresAt: Date,
  now: Date,
): boolean {
  return now.getTime() >= expiresAt.getTime();
}
```

### ✅ 157. 테스트

```typescript
test('만료 시각과 같으면 만료다', () => {
  expect(
    isExpired(
      new Date('2026-11-05T00:00:00Z'),
      new Date('2026-11-05T00:00:00Z'),
    ),
  ).toBe(true);
});
```

### ✅ 158. 중요한 원칙

**날짜·시간 테스트는 실제 시스템 시각에 불필요하게 의존하지 않도록 설계한다.**

## 21. Retry는 무엇을 해결하는가?

### ✅ 177. Retry

실패한 테스트를 다시 실행하는 것이다.

### ✅ 178. 장점

간헐적인 실패를 관측하고 추가 증거를 확보할 수 있다.

### ✅ 179. 단점

실제 결함이 첫 실행에서 발생했어도 이후 실행 성공으로 가려질 수 있다.

### ✅ 180. 기본 구조

```text
Test Attempt 0
FAIL

↓

Test Attempt 1
PASS

↓

Flaky Outcome
```

### ✅ 181. 중요한 사실

Playwright는 Retry가 설정되면 실패한 테스트를 새로운 Worker Process에서 다시 실행한다.

### ✅ 182. 의미

처음 실패한 Worker의 일부 상태가 재시도에서는 사라질 수 있다.

### ✅ 183. 따라서

재시도 성공이 실제 제품 문제를 해결했다는 의미는 아니다.

### ✅ 184. 더 위험한 구조

```text
최대 Retry 10회

↓

언젠가 PASS

↓

CI 성공
```

### ✅ 185. 문제

신뢰할 수 없는 검증 결과를 계속 성공으로 포장할 수 있다.

### ✅ 186. 권장

Retry는 제한적으로 사용하고 최초 실패도 반드시 기록한다.

관련 테스트에서 간헐적 실패가 확인됐다면 더 엄격하게 처리해야 한다.

### ✅ 200. 권장 기본 정책

**중요한 업무 검증의 불규칙한 실패는 원인을 확인할 때까지 Merge를 보류한다.**

### ✅ 201. 이유

실제 제품의 Race Condition이나 데이터 정합성 문제가 숨어 있을 수 있기 때문이다.

### ✅ 202. 결론

Retry는 실패를 관측하는 방법이지 위험을 무시하도록 허락하는 장치가 아니다.

## 25. Flaky Test Detection

### ✅ 212. Flaky Test를 어떻게 발견할까?

동일한 테스트를 통제된 환경에서 여러 번 실행한다.

### ✅ 213. Playwright

```bash
pnpm exec playwright test \
  tests/e2e/application-dropdown.spec.ts \
  --repeat-each=20 \
  --retries=0 \
  --workers=1
```

### ✅ 214. 실행 목적

동일 테스트의 반복 실행에서 불규칙한 실패가 발생하는지 확인한다.

### ✅ 215. 왜 `--retries=0`인가?

최초 실패를 다른 실행 성공으로 덮지 않고 관측하기 위해서다.

### ✅ 216. 왜 Worker를 1개로 설정하는가?

먼저 병렬성 영향을 줄인 조건을 확인하기 위해서다.

### ✅ 217. 이후

실제 CI Worker 설정에서도 반복 실행한다.

### ✅ 218. 결과 비교

```text
Sequential:
20회 PASS

Parallel:
15회 PASS
5회 FAIL
```

### ✅ 219. 해석

공유 상태, 동시성, 자원 경쟁 문제를 의심할 수 있다.

### ✅ 220. 하지만 확정은 아니다

실제 CI 환경과 테스트 데이터가 어떻게 달라졌는지 조사해야 한다.

### ✅ 221. 중요한 원칙

반복 테스트는 결함을 발견할 확률을 높일 수 있지만 몇 번 통과했다고 Flaky 가능성이 완전히 사라지는 것은 아니다.

## 26. Flakiness Rate

### ✅ 222. Test Flakiness를 지표로 관리한다

### ✅ 223. 간단한 정의

```text
Flaky Test Rate

=

최초 실패 후 Retry 성공한 Test Case 수
───────────────────────────────
Retry 평가가 가능한 전체 Test Case 수
```

### ✅ 224. 예시

```text
전체 평가 가능한 Test Case
200개

첫 실행 실패 후 Retry 성공
10개
```

### ✅ 225. 결과

```text
Flaky Test Rate

5%
```

### ✅ 226. 주의

이 수치는 테스트 실행 정책과 Retry 횟수에 의존한다.

### ✅ 227. Retry가 0회라면?

최초 실패 이후 성공 여부를 관측하지 못하므로 같은 방식의 Flaky Rate를 계산할 수 없다.

### ✅ 228. 보완 지표

```text
First Attempt Failure Rate

Retry Recovery Rate

Persistent Failure Rate

Test Execution Coverage
```

를 구분한다.

### ✅ 229. First Attempt Failure Rate

최초 실행에서 실패한 비율이다.

### ✅ 230. Retry Recovery Rate

최초 실패한 테스트 중 재시도에서 성공한 비율이다.

### ✅ 231. Persistent Failure Rate

허용된 재시도에서도 성공하지 못한 비율이다.

### ✅ 232. 중요

이 지표들을 모두 동일한 분모로 계산해서는 안 된다.

### ✅ 233. Metric Definition

각 지표의 분자·분모·관측 기간을 문서화한다.

### ✅ 242. 테이블 예시

```sql
CREATE TABLE test_execution_attempts (
  id UUID PRIMARY KEY,

  test_id TEXT NOT NULL,

  run_id TEXT NOT NULL,

  commit_sha TEXT NOT NULL,

  environment TEXT NOT NULL,

  attempt_number INTEGER NOT NULL,

  status TEXT NOT NULL CHECK (

      'SKIPPED',
      'INTERRUPTED'

  duration_ms INTEGER,

  failure_code TEXT,

  started_at TIMESTAMPTZ NOT NULL,

  finished_at TIMESTAMPTZ,

  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

  UNIQUE (
    run_id,
    test_id,
    attempt_number
  )
);
```

## 30. CI Signal Quality

### ✅ 256. CI Signal이란?

자동 테스트 결과가 실제 코드의 품질에 대해 제공하는 신호다.

### ✅ 257. 좋은 Signal

```text
코드 결함 발생
      ↓
테스트 실패
      ↓
원인 확인 가능
```

### ✅ 258. 나쁜 Signal ①

```text
실제 코드 정상

↓

테스트 반복 실패
```

### ✅ 259. 나쁜 Signal ②

```text
실제 코드 결함

↓

테스트 PASS
```

### ✅ 260. 두 문제가 모두 위험하다

### ✅ 261. False Positive

실제 결함이 없는데 테스트가 문제를 보고하는 경우다.

### ✅ 262. False Negative

실제 결함이 있는데 테스트가 발견하지 못하는 경우다.

### ✅ 263. Flaky Test의 주요 문제

개발자가 테스트 실패를 신뢰하지 않게 될 수 있다.

### ✅ 264. 더욱 위험한 결과

```text
어차피 테스트가 자주 실패하니까
이번에도 무시하자.
```

### ✅ 265. 따라서

**CI의 신뢰성은 테스트가 많이 실행된다는 사실보다 실패 결과를 실제 문제로 신뢰할 수 있는지에 달려 있다.**

### ✅ 273. 중요한 원칙

## 32. Test Quarantine이란?

### ✅ 274. Quarantine

불안정하거나 문제가 있는 테스트를 일반 검증 경로와 구분해 별도로 관리하는 절차다.

### ✅ 275. 일반적인 목적

반복적인 테스트 결함 때문에 정상 개발 전체가 중단되는 문제를 줄이는 것이다.

### ✅ 276. 하지만 위험한 구현

```text
Flaky Test 발견

↓

test.skip()

↓

문제 해결 완료
```

### ✅ 277. 왜 위험할까?

테스트를 실행하지 않게 됐을 뿐 실제 문제가 해결된 것은 아니다.

### ✅ 278. 올바른 Quarantine

```text
Flaky Test Detected
        ↓
Root Cause Investigation
        ↓
Risk Classification
        ↓
Quarantine Eligibility
        ↓
Owner / Expiry
        ↓
Separate Execution
        ↓
Evidence Collection
        ↓
Repair / Re-enable
```

### ✅ 279. 중요한 원칙

**Quarantine은 문제를 보이지 않게 만드는 기능이 아니라 격리한 문제를 계속 추적하고 해결하는 운영 절차다.**

---

## 33. Quarantine 대상 선정

### ✅ 280. 모든 테스트를 Quarantine할 수 있을까?

권장하지 않는다.

### ✅ 281. 격리를 검토할 수 있는 경우

```text
낮은 위험의 부가 UI 검사

검증된 Test Harness 결함

현재 환경에서 지원하지 않는 브라우저 검사

일시적인 테스트 인프라 문제
```

### ✅ 282. 단 실제 근거가 필요하다

테스트가 자주 실패한다는 이유만으로 격리하지 않는다.

### ✅ 283. 격리하면 안 되는 대표적인 테스트

```text
Customer Authorization

Order Idempotency

Critical Pricing

Personal Data Access

Notification Approval

Application Submission
```

### ✅ 284. 만약 이런 테스트가 불안정하다면?

Merge를 보류하고 실제 제품 결함인지 우선 조사한다.

### ✅ 285. 불가피하게 테스트 코드 자체가 고장 났다면?

동등한 필수 검증을 다른 테스트로 제공한 뒤 예외 승인 여부를 검토해야 한다.

### ✅ 286. 중요한 원칙

**Critical Business Test를 Quarantine했다는 사실이 필수 업무 검증을 면제해 주지는 않는다.**

## 36. Playwright의 Skip / Fixme / Fail

### ✅ 305. Playwright Annotation

Playwright는 `skip`, `fixme`, `fail` 등의 Annotation을 지원한다.

### ✅ 306. test.skip()

해당 테스트를 실행하지 않는다.

### ✅ 307. test.fixme()

수정이 필요한 테스트를 실행하지 않는 용도로 사용할 수 있다.

### ✅ 308. test.fail()

테스트가 실패할 것으로 기대한다.

테스트는 실제로 실행되며 예상과 달리 성공하면 문제가 보고될 수 있다.

### ✅ 309. 세 기능의 차이

| Annotation | 실제 실행 | 용도 |
|---|---|---|
| `test.skip()` | 실행 안 함 | 해당 조건에서 적용하지 않는 검사 |
| `test.fixme()` | 실행 안 함 | 수정 대기 등 |
| `test.fail()` | 실행 | 알려진 실패를 추적 |

### ✅ 310. 중요한 주의

Quarantine을 무조건 `test.skip()`으로 구현하면 실패 증거를 더 이상 수집할 수 없다.

### ✅ 311. 권장 방향

별도 Quarantine Test Suite 또는 별도 CI Workflow에서 계속 실행하도록 설계한다.

### ✅ 312. Critical Test

실제 검증이 없는 상태에서 Skip으로 통과 처리하지 않는다.

```text
       ↓
Repair Tracking
```

### ✅ 314. 중요한 차이

Quarantine Suite가 실패한다고 무조건 전체 CI를 통과시킬지 말지는 사전에 정한 위험 정책에 따른다.

### ✅ 315. 그러나

필수 테스트가 빠진 상태에서는 일반 CI PASS를 전체 품질 검증 완료로 표현해서는 안 된다.

### ✅ 316. GitHub Actions

`continue-on-error` 옵션을 이용하면 특정 Step 또는 Job 실패가 전체 결과에 미치는 영향을 조정할 수 있다.

### ✅ 317. 위험

`continue-on-error`를 잘못 사용하면 실제 실패가 최종 성공처럼 보일 수 있다.

### ✅ 318. GitHub Actions Context

Step의 `outcome`과 `conclusion`은 다를 수 있다.

### ✅ 319. 예시

```text
Step Outcome:
failure

Step Conclusion:
success
```

가 가능한 상황이 있다.

### ✅ 320. 따라서

필수 검증 단계에는 무분별하게 `continue-on-error`를 사용하지 않는다.

1105에서는 선택된 테스트 자체가 얼마나 신뢰할 수 있는지 다뤘다.

```text
Test Execution
       ↓
Initial Result
       ↓
PASS / FAIL
       ↓
Retry Observation
       ↓
Failure Classification
       ↓
Product Defect?
       ↓
Test Defect?
       ↓
Infrastructure Failure?
       ↓
Root Cause Investigation
       ↓
Test Stabilization
       ↓
Reliable CI Gate
```

이번 편에서 가장 중요한 원칙은 일곱 가지다.

**첫 번째 — 테스트가 실패했다가 성공해도 문제가 사라진 것은 아니다.**

실제 제품 결함이 간헐적으로 발생하는 경우일 수 있다.

**두 번째 — 고정 시간 대기보다 실제 상태를 검증한다.**

```text
3초 기다리기

보다

실제 옵션이 선택 가능한 상태인지 확인
```

하는 것이 적절하다.

**세 번째 — 테스트는 서로 독립적이어야 한다.**

공유 DB, Fixture, Mock, Browser State가 테스트 결과를 변경하지 않아야 한다.

**네 번째 — Retry는 실패를 숨기는 도구가 아니다.**

최초 실패와 Retry 결과를 별도로 보관한다.

**다섯 번째 — Quarantine은 테스트 삭제가 아니다.**

담당자, 원인, 대체 검증, 만료일, 복귀 조건이 필요하다.

**여섯 번째 — 중요한 업무 검증은 보호해야 한다.**

```text
Authorization

Order Idempotency

Pricing

Notification Approval
```

같은 테스트는 간헐적으로 실패한다고 무조건 제외하지 않는다.

**일곱 번째 — CI의 목적은 초록색 성공 표시가 아니다.**

실제 코드의 문제를 신뢰할 수 있게 감지하는 것이다.

현재 투게더몰에서 가장 현실적인 적용 순서는 다음과 같다.

```text
1. 중요한 업무 테스트 분류

2. 테스트 DB / Fixture 격리

3. Playwright 대기 방식 점검

4. 최초 실패와 Retry 결과 기록

5. Flaky Test 반복 실행

6. 실패 원인 분류

7. Critical Test Merge Gate

8. 제한적인 Quarantine 정책

9. CI Signal Report

10. AI 기반 테스트 안정화 지원
```

특히 현재 1인 개발 환경에서는 테스트를 많이 추가하는 것보다 **고객 신청·가격·권한·알림 발송 같은 핵심 기능을 검증하는 몇 가지 테스트를 실제로 신뢰할 수 있게 만드는 것**이 우선이다.

처음부터 전문적인 Test Analytics Platform이나 복잡한 Quarantine 자동화를 구축할 필요는 없다.

기존 Jest 또는 Vitest, Playwright, GitHub Actions의 결과를 올바르게 수집하고 관리하는 것만으로도 시작할 수 있다.

최종적으로 기억해야 할 원칙은 다음과 같다.

**좋은 테스트 시스템은 실패가 한 번도 발생하지 않는 시스템이 아니다. 실패가 발생했을 때 그것이 실제 제품 결함인지, 테스트 코드 문제인지, 실행 환경 문제인지 근거를 바탕으로 구분하고, 중요한 문제를 무시하지 않으면서 안정적인 개발과 배포를 가능하게 만드는 시스템이다.**
