## 1. 복구 매뉴얼을 만들었다고 실제로 복구할 수 있을까?

### ✅ 1. 1110과의 연결

1110에서는 운영 장애를 발견하고, 원인을 조사하고, 승인된 절차에 따라 안전하게 복구하는 방법을 다뤘다.

```text
Incident Detection
       ↓
Evidence Collection
       ↓
Severity Classification
       ↓
Runbook Selection
       ↓
Safety Preconditions
       ↓
Human Approval
       ↓
Controlled Mitigation
       ↓
Recovery Verification
```

1111에서는 한 가지 질문을 추가한다.

**이 절차들이 실제 장애 상황에서도 정상적으로 작동한다는 것을 어떻게 확인할 수 있을까?**

### ✅ 2. 흔한 개발 방식

```text
장애 발생
    ↓
원인 분석
    ↓
수정
    ↓
복구 매뉴얼 작성
    ↓
다음 개발
```

### ✅ 3. 문제

매뉴얼을 작성했지만 실제로 실행한 적이 없을 수 있다.

### ✅ 4. 예시

DB 연결 장애가 발생했을 때 대응하도록 Runbook을 작성했다.

```text
1. RDS 상태 확인

2. DB 연결 상태 확인

3. Backend Readiness 확인

4. 원인 해결

5. 서비스 검증
```

### ✅ 5. 그러나 실제 장애에서

- DB가 끊겨도 Readiness가 정상으로 표시된다.
- 알림이 오지 않는다.
- 재연결 이후 Prisma Client가 정상화되지 않는다.
- 신청 요청의 결과가 불명확해진다.

같은 문제가 발생할 수 있다.

### ✅ 6. Runbook 존재와 복구 가능성은 다르다

```text
Runbook Written

≠

Recovery Verified
```

### ✅ 7. 그래서 필요한 과정

```text
Failure Hypothesis
       ↓
Controlled Failure
       ↓
Detection
       ↓
Runbook Execution
       ↓
Recovery
       ↓
Business Verification
```

### ✅ 8. 이번 편의 목표

다음 기술과 운영 개념을 학습한다.


### ✅ 9. 가장 중요한 원칙

**장애를 일으키는 것이 목적이 아니다. 장애가 발생했을 때 고객에게 어떤 영향이 발생하고, 시스템이 어떻게 대응하며, 얼마나 안전하게 복구할 수 있는지 확인하는 것이 목적이다.**

## 2. Operational Resilience란?

### ✅ 10. 정의

Operational Resilience는 시스템이 장애와 예기치 않은 상황에서도 중요한 업무를 유지하거나, 영향을 제한하고, 정상 상태로 회복할 수 있는 능력이다.

### ✅ 11. 단순 안정성과의 차이

안정성은 정상 동작을 지속하는 것에 집중한다.

복원력은 장애가 발생했을 때의 행동과 회복까지 고려한다.

### ✅ 12. 예시

```text
정상 상태:
고객 신청 정상 접수
```

```text
장애 상태:
외부 알림 서비스 실패
```

이때 고객 신청까지 중단할 필요가 있는지 판단해야 한다.

### ✅ 13. 잘 설계된 구조라면

외부 알림이 실패하더라도 핵심 주문 접수는 지속할 수 있을 수 있다.

```text
Application Submission
        ↓
Order Created
        ↓
Notification Pending
```

### ✅ 14. 반대로

알림 발송 성공이 업무 완료의 필수 조건이라면 주문 상태와 고객 안내 정책이 달라져야 한다.

### ✅ 15. 따라서 복원력은 업무 규칙과 연결된다

모든 서비스가 무조건 장애를 무시하고 계속 실행하는 것이 좋은 것은 아니다.

### ✅ 16. 중요한 질문

```text
어떤 기능이 핵심인가?

어떤 기능을 일시적으로 중단할 수 있는가?

장애가 다른 기능으로 전파되는가?

실패한 작업을 나중에 안전하게 복구할 수 있는가?
```

### ✅ 17. 중요한 원칙

**운영 복원력은 서버가 살아 있는지보다 핵심 비즈니스 기능이 장애 상황에서 어떻게 동작하는지를 기준으로 평가한다.**

## 3. Reliability·Availability·Resilience

### ✅ 18. Reliability

일정 기간 동안 시스템이 요구된 기능을 정상적으로 수행하는 능력이다.

### ✅ 19. Availability

필요한 시점에 서비스를 사용할 수 있는 상태를 의미한다.

### ✅ 20. Resilience

실패 상황에서 영향을 제한하고 대응·복구하는 능력이다.

### ✅ 21. 비교

| 개념 | 핵심 질문 |
|---|---|
| Reliability | 정상적으로 동작하는가? |
| Availability | 지금 사용할 수 있는가? |
| Resilience | 실패했을 때 어떻게 견디고 회복하는가? |
| Recoverability | 정해진 절차로 복구할 수 있는가? |

### ✅ 22. 예시

NestJS 서버는 정상 실행 중이다.

### ✅ 23. 하지만 PostgreSQL이 연결되지 않는다

```text
Backend Process:
RUNNING

Database:
UNAVAILABLE
```

### ✅ 24. 결과

고객 신청 API는 실패할 수 있다.

### ✅ 25. 중요한 구분

```text
Process Running

≠

Service Available

≠

Business Function Working
```

### ✅ 26. 중요한 원칙

**복원력 테스트는 프로세스·API·DB·업무 결과를 각각 검증해야 한다.**

## 4. Failure Mode란?

### ✅ 28. PostgreSQL의 Failure Mode

```text
Connection Refused

Connection Timeout

Connection Pool Exhaustion

Deadlock

Slow Query

Database Unavailable
```

### ✅ 29. 외부 API의 Failure Mode

```text
Timeout

HTTP 429

HTTP 500

Malformed Response

Authentication Failure

Unknown Outcome
```

### ✅ 30. Frontend의 Failure Mode

```text
Chunk Load Failure

API Timeout

JavaScript Runtime Error

State Corruption

Unsupported Response
```

### ✅ 31. Background Worker

```text
Worker Crash

Duplicate Job Delivery

Poison Message

Backlog Growth

Provider Timeout
```

### ✅ 32. 중요한 점

같은 기능이 실패하더라도 원인과 대응 방식은 다를 수 있다.

### ✅ 33. 따라서

```text
Affected Component

+

Failure Mode

+

Business Impact
```

로 분석한다.

## 5. Failure Mode and Effects Analysis — FMEA

### ✅ 34. FMEA란?

시스템에서 발생할 수 있는 실패 형태와 영향을 사전에 분석하는 방법이다.

### ✅ 35. 주요 질문

```text
어디서 실패할 수 있는가?

왜 실패할 수 있는가?

어떤 업무에 영향을 주는가?

얼마나 심각한가?

얼마나 쉽게 발견할 수 있는가?

어떤 예방·복구 수단이 있는가?
```

### ✅ 36. 기본 구성

```text
Component

Failure Mode

Cause

Effect

Severity

Occurrence

Detection

Controls

Action
```

### ✅ 37. Severity

실패 시 영향의 심각도다.

### ✅ 38. Occurrence

실패가 발생할 가능성 또는 관측 빈도에 대한 평가다.

### ✅ 39. Detection

실패를 얼마나 쉽게 발견할 수 있는지 평가한다.

### ✅ 40. 중요한 주의

FMEA의 등급 기준은 조직에서 미리 정의해야 한다.

정확한 사고 확률을 알지 못하는데 숫자를 확률처럼 사용하면 안 된다.

---

## 6. FMEA 실제 예시

### ✅ 41. 온라인 휴대폰 판매몰 기준

| 구성 요소 | Failure Mode | 업무 영향 | 대응 후보 |
|---|---|---|---|
| 신청 API | DB 연결 실패 | 신청 접수 중단 | DB 복구·안전한 실패 처리 |
| 주문 서비스 | 중복 요청 | 주문 중복 생성 | 멱등성·DB 제약 |
| 가격 계산 | 잘못된 할인 적용 | 가격 정합성 오류 | 업무 검증·기능 제한 |
| 알림 Worker | 외부 API Timeout | 고객 안내 지연·중복 위험 | 결과 확인·재시도 정책 |
| 관리자 | 주문 검색 실패 | 운영 업무 지연 | 오류 분석·복구 |
| Frontend | Chunk 404 | 일부 화면 진입 실패 | 이전 Asset 보존·복구 |
| 인증 | 권한 우회 | 개인정보 노출 가능성 | 접근 차단·긴급 조사 |

### ✅ 42. 모든 Failure Mode의 우선순위가 같을까?

아니다.

### ✅ 43. 주문 중복이나 권한 우회

고객에게 직접적인 피해가 발생할 수 있어 우선순위가 높다.

### ✅ 44. 일부 비핵심 UI 오류

실제 업무 영향이 작다면 상대적으로 낮을 수 있다.

### ✅ 45. 중요한 원칙

**실험 난이도가 아니라 실제 업무 피해를 기준으로 테스트 우선순위를 정한다.**

## 7. Risk Priority Number — RPN

### ✅ 46. FMEA에서는 RPN을 사용할 수 있다

일반적으로 다음 요소를 곱한다.

```text
RPN = Severity × Occurrence × Detection
```

### ✅ 47. 예시

각 항목을 1~5점 척도로 정했다고 가정한다.

```text
Severity: 5

Occurrence: 3

Detection: 4
```

### ✅ 48. 계산

```text
RPN = 60
```

### ✅ 49. 하지만 중요한 한계

RPN이 높은 장애만 위험하다고 판단해서는 안 된다.

### ✅ 50. 예시

발생 가능성이 매우 낮더라도 개인정보 노출이나 데이터 삭제는 심각한 피해를 만들 수 있다.

### ✅ 51. 따라서

```text
Critical Severity Override
```

를 별도로 둔다.

### ✅ 52. 추천 우선순위

```text
Critical Business Risk
        ↓
Historical Incidents
        ↓
High RPN
        ↓
Other Failure Modes
```

### ✅ 53. 중요한 원칙

**FMEA 점수는 분석을 보조하는 수단이고 심각한 업무 위험을 무시하도록 만드는 기준이 아니다.**

## 9. Dependency Failure Map

```text
       ↓

       ↓
Order Service
       ↓

```

### ✅ 61. PostgreSQL 실패

신청 저장이 중단될 수 있다.

### ✅ 62. 외부 알림 실패

시스템 설계에 따라 신청 접수는 계속 유지할 수 있다.

### ✅ 63. 인증 실패

정상 고객의 신청 접근이 차단될 수 있다.

### ✅ 64. 따라서 의존성을 분류한다

```text

OPTIONAL
```

### ✅ 65. CRITICAL

기능 수행에 반드시 필요한 의존성이다.

### ✅ 66. DEGRADABLE

장애가 발생해도 제한된 기능으로 운영할 수 있는 의존성이다.

### ✅ 67. OPTIONAL

핵심 업무와 독립적으로 실패를 처리할 수 있는 의존성이다.

### ✅ 68. 중요한 원칙

**어떤 의존성을 제거해도 되는지는 개발 편의가 아니라 실제 업무 계약과 고객 안내 정책에 따라 결정한다.**

## 10. Chaos Engineering이란?

### ✅ 69. 정의

시스템에 통제된 실패 조건을 주입하고, 예상한 행동과 실제 결과를 비교해 복원력에 대한 가설을 검증하는 실험 방식이다.

### ✅ 70. 단순히 서버를 고장 내는 것일까?

아니다.

### ✅ 71. 핵심 구조

```text
Steady State

↓

Hypothesis

↓

Controlled Fault Injection

↓

Observe

↓

Compare

↓

Improve
```

### ✅ 72. 일반 테스트

```text
정상 입력
       ↓
정상 결과
```

를 검증한다.

### ✅ 73. Chaos Experiment

```text
정상 업무
       ↓
특정 의존성 장애
       ↓
예상한 복구 동작
```

을 검증한다.

### ✅ 74. 중요한 차이

무작위로 인프라를 중단시키는 것이 아니다.

### ✅ 75. 좋은 실험

명확한 가설, 제한된 영향 범위, 관측 방법, 중단 조건, 복구 절차를 가진다.

### ✅ 76. 중요한 원칙

**Chaos Engineering은 장애를 만드는 기술이 아니라 실패 상황에서 시스템에 대한 가정을 검증하는 실험 방법이다.**

---

## 11. Chaos Engineering과 Fault Injection

### ✅ 77. Fault Injection

특정 장애 조건을 의도적으로 발생시키는 기술이다.

### ✅ 78. 예시

```text
외부 API Timeout 반환

DB 연결 실패 모의

Worker 처리 예외

HTTP 500 응답

네트워크 지연
```

### ✅ 79. Chaos Engineering

Fault Injection을 포함해 시스템의 정상 상태, 가설, 관측과 개선까지 연결하는 과정이다.

### ✅ 80. 관계

```text
Chaos Experiment
       ↓
Fault Injection
       ↓
System Response
       ↓
Result Analysis
```

### ✅ 81. 중요한 원칙

**오류를 한 번 발생시켰다는 사실만으로 복원력 실험을 완료했다고 판단하지 않는다.**

## 12. GameDay란?

### ✅ 82. GameDay

실제 장애를 가정하고 운영 대응 절차를 연습하는 훈련이다.

### ✅ 83. 목표

시스템뿐 아니라 대응하는 사람과 문서, 알림, 승인, 복구 절차가 정상적으로 작동하는지 확인한다.

### ✅ 84. 실험과의 차이

```text
Fault Injection:
시스템의 특정 실패 동작 검증
```

```text
GameDay:
장애 탐지부터 복구까지 전체 대응 검증
```

### ✅ 85. 예시

```text
DB 장애 주입
       ↓
Alert 탐지
       ↓
Incident 생성
       ↓
로그 조사
       ↓
Runbook 실행
       ↓
복구
       ↓
업무 검증
```

### ✅ 86. GameDay 성공의 의미

장애가 전혀 없었다는 뜻이 아니다.

### ✅ 87. 실제 목표

장애를 정확하게 탐지하고 대응할 수 있는지 확인하는 것이다.

### ✅ 88. 중요한 원칙

**GameDay는 기술 테스트이면서 운영 절차 훈련이다.**

---

## 13. Steady State란?

### ✅ 89. Steady State

## 21. NestJS Provider Fault Injection 예시

### ✅ 145. 인터페이스

```typescript
export interface NotificationProvider {
  send(input: {
    operationKey: string;
    recipientKey: string;
  }): Promise<{
    providerMessageId: string;
  }>;
}
```

### ✅ 146. 테스트용 Fake

```typescript
type FakeMode =
  | 'SUCCESS'
  | 'TIMEOUT'
  | 'REJECTED';

export class FakeNotificationProvider
  implements NotificationProvider {

  public callCount = 0;

  constructor(
    private readonly mode: FakeMode,
  ) {}

  async send(input: {
    operationKey: string;
    recipientKey: string;
  }): Promise<{
    providerMessageId: string;
  }> {
    this.callCount += 1;

    if (this.mode === 'TIMEOUT') {
      throw new Error('SIMULATED_TIMEOUT');
    }

    if (this.mode === 'REJECTED') {
      throw new Error('SIMULATED_REJECTION');
    }

    return {
      providerMessageId: `TEST-${input.operationKey}`,
    };
  }
}
```

### ✅ 147. 이 Fake의 역할

실제 고객에게 알림을 발송하지 않고 실패 결과를 재현한다.

### ✅ 148. 주의

`SIMULATED_TIMEOUT`을 즉시 발생시키는 것은 지연 자체를 재현하는 것이 아니라 Timeout 결과에 대한 서비스 반응을 테스트하는 것이다.

### ✅ 149. 실제 Timeout 동작

별도의 제한 시간·취소 처리·네트워크 지연 테스트로 확인해야 한다.

### ✅ 150. 중요한 원칙

**실패 결과의 처리 테스트와 실제 시간 초과 동작 테스트를 구분한다.**

```text
중복 업무 효과:
없음

결과 불명:
별도 관리
```

### ✅ 196. 주의

모든 외부 Provider가 정확히 한 번 발송을 보장하지는 않는다.

### ✅ 197. 따라서

실제 Provider의 Idempotency 지원 여부에 따라 설계해야 한다.

### ✅ 198. 중요한 원칙

**Queue 메시지의 재전달 가능성을 없애려 하기보다 중복 업무 효과를 제어하는 설계가 필요하다.**

## 32. 다섯 번째 실험 — Frontend Chunk Load Failure

### ✅ 214. 개념 예시

```typescript
import { test, expect } from '@playwright/test';

test('Chunk 로딩 실패 시 복구 안내를 표시한다', async ({
  page,
}) => {
  await page.route(
    '**/assets/*.js',
    async (route) => {
      if (
        route.request().url().includes('lazy-example')
      ) {
        await route.abort();
        return;
      }

      await route.continue();
    },
  );

  await page.goto('/test-page');

  // 실제 lazy-loaded 화면을 여는 동작이 필요하다.

  // Chunk 실패 후 사용자 안내와 복구 동작을 검증한다.
});
```

### ✅ 215. 중요한 전제

이 코드는 Fault Injection의 기본 형태를 보여준다.

실제 Vite Asset 이름과 라우팅에 맞춘 테스트 동작과 Assertion을 추가해야 한다.

### ✅ 216. 추가로 확인할 것

```text

Safe Reload

Unsaved Form Data

Old Asset Retention
```

### ✅ 217. 중요한 원칙

**Frontend 복구 테스트에서도 고객이 입력 중인 신청정보의 유실 위험을 함께 확인한다.**

## 43. RTO와 RPO

### ✅ 282. RTO — Recovery Time Objective

업무 또는 시스템을 복구하기 위해 설정한 목표 시간이다.

### ✅ 283. RPO — Recovery Point Objective

복구 과정에서 허용할 수 있는 데이터 손실 시점의 차이에 대한 목표다.

### ✅ 284. 두 개념은 다르다

```text
RTO:
얼마나 빨리 복구해야 하는가?
```

```text
RPO:
어느 시점까지의 데이터가 보존돼야 하는가?
```

### ✅ 285. 예시

RTO 30분이라는 목표를 설정할 수 있다.

### ✅ 286. RPO 5분이라는 목표를 설정할 수도 있다.

### ✅ 287. 주의

이 수치는 설명을 위한 임의의 예시다.

### ✅ 288. 실제 목표

고객 업무 피해와 회사가 감당할 수 있는 위험, 운영 인프라에 따라 정한다.

### ✅ 289. 중요한 점

장애 주입 테스트에서 DB 연결 복구를 검증했다고 백업 복구의 RPO까지 검증한 것은 아니다.

### ✅ 290. 중요한 원칙

**서비스 재시작 훈련과 실제 데이터 복구 훈련은 서로 다른 시나리오로 관리한다.**

### ✅ 295. 추가 검증

### ✅ 296. 중요한 원칙

**백업이 존재한다는 사실만으로 데이터 복구 가능성과 목표 RPO가 검증된 것은 아니다.**

## 📌 요약

1110에서는 실제 장애 발생 이후 안전한 Runbook을 이용해 대응하는 방법을 다뤘다.

```text
Incident Detection
       ↓
Evidence Collection
       ↓
Mitigation
       ↓
Recovery
       ↓
Business Verification
```

1111에서는 장애 발생 이전에 이 절차가 정상적으로 작동하는지 확인하는 방법을 다뤘다.

```text
Critical Business Journey
       ↓
Failure Mode Analysis
       ↓
Risk Prioritization
       ↓
Steady State
       ↓
Failure Hypothesis
       ↓
Isolated Fault Injection
       ↓
Incident Detection
       ↓
Runbook Execution
       ↓
Recovery Verification
       ↓
Result Analysis
       ↓
Regression Prevention
```

이번 편에서 가장 중요한 원칙은 일곱 가지다.

**첫 번째 — 장애 복구 매뉴얼이 존재한다고 복구 가능성이 검증된 것은 아니다.**

실제 테스트 환경에서 Runbook을 실행해야 한다.

**두 번째 — 무작위로 장애를 발생시키지 않는다.**

명확한 가설과 업무 불변조건을 정의한 후 제한된 실패를 주입한다.

**세 번째 — 실험 대상은 격리된 테스트 환경이어야 한다.**

기존 개발 DB와 운영 RDS, 실제 고객 알림 시스템에 영향을 주지 않아야 한다.

**네 번째 — 서버 정상화와 업무 정상화는 다르다.**

DB가 다시 연결돼도 고객 주문 중복이나 업무 결과 불명이 남아 있을 수 있다.

**다섯 번째 — 실험 중단과 복구 완료를 구분한다.**

Fault Injection을 멈췄더라도 시스템이 원래 상태로 돌아왔는지 확인해야 한다.

**여섯 번째 — 복원력은 시간과 실제 결과로 검증한다.**

탐지 시간·복구 시간뿐 아니라 중복 주문·알림·데이터 정합성을 확인한다.

**일곱 번째 — 실험 결과를 미래의 테스트와 Runbook 개선에 활용한다.**

실패를 발견하는 것만으로 끝내지 않고 Regression Test와 운영 지식으로 축적한다.

현재 투게더몰에서는 다음 순서가 적합하다.

```text
1. 핵심 신청 Journey 분석

2. FMEA 작성

3. Mock Provider Timeout Test

4. Order Idempotency Test

5. 독립 PostgreSQL 장애 테스트

6. Worker Crash Test

7. Frontend Chunk Failure Test

8. GameDay Runbook

9. Recovery Verification Report

10. 필요하면 Testcontainers / FIS 검토
```

특히 현재 1인 개발 환경에서는 **운영 환경에 직접 장애를 발생시키는 실험보다 실제 핵심 업무를 검증할 수 있는 실패 시나리오를 테스트 코드로 추가하는 것**이 가장 효과적이다.

처음에는 Fake Provider와 독립된 PostgreSQL Test DB만으로도 상당수의 중요한 장애 대응 시나리오를 검증할 수 있다.

이후 실제 네트워크 단절이나 인프라 장애를 재현할 필요성이 확인되면 Testcontainers·Toxiproxy·AWS FIS를 단계적으로 검토하면 된다.

최종적으로 기억해야 할 원칙은 다음과 같다.

**좋은 복원력 시스템은 장애가 절대로 발생하지 않는 시스템이 아니다. 실패할 수 있다는 사실을 전제로 중요한 업무의 피해 범위를 제한하고, 어떤 실패가 발생해도 문제를 탐지하고 안전하게 대응하며, 실제 고객 업무가 정상적으로 복구됐다는 것을 검증할 수 있는 시스템이다.**

```text
Business Traffic Forecast
       ↓
Critical API Selection
       ↓
Baseline Performance
       ↓
Controlled Load Test
       ↓
Bottleneck Analysis
       ↓
Capacity Estimation
       ↓
Scaling Strategy
       ↓
Performance Budget
       ↓
Production Monitoring
```

주요 내용:

- Capacity Planning
- Throughput과 Latency
- RPS·Concurrency
- Little's Law
- p95·p99 Latency
- Performance Budget
- Load Test·Stress Test·Spike Test
- NestJS API 부하 테스트
- PostgreSQL Connection Pool
- Prisma Query 성능
- N+1 Query 탐지
- React·CloudFront 정적 자원 성능
- EC2 CPU·Memory 병목
- Vertical Scaling과 Horizontal Scaling
- AWS Auto Scaling 도입 조건
- 광고 유입 급증과 신청 API 처리량
- DB·외부 API Rate Limit
- 안전한 테스트 환경 및 비용 관리
- Codex를 활용한 성능 분석과 개선 계획

목표는 **광고·사전예약·신제품 출시로 고객 유입이 늘어났을 때 현재 서버가 어느 정도의 요청을 안전하게 처리할 수 있고, 어떤 부분을 먼저 최적화하거나 확장해야 하는지 데이터로 판단하는 것**이다.
