# 1110 운영 자동화/AI 워크플로우 심화 (65/N)
## Incident Response Automation·Automated Mitigation·Runbook Execution·Human-in-the-loop Recovery와 운영 장애 대응 자동화

**시리즈 날짜: 2026년 11월 10일**

---

## 1. 장애를 발견한 이후에는 무엇을 해야 할까?

### ✅ 1. 1109와의 연결

1109에서는 새로운 배포 이후 실제 서비스의 상태를 평가하는 방법을 다뤘다.

```text
New Deployment
       ↓
Runtime Verification
       ↓
Technical Metrics
       ↓
Business SLI
       ↓
Critical Invariant
       ↓
Release Decision
```

이번 편에서는 `HOLD` 또는 `ROLLBACK_REVIEW`와 같은 결과가 발생했을 때 실제로 어떤 조치를 해야 하는지 다룬다.

### ✅ 2. 흔한 장애 상황

```text
CloudWatch Alarm
       ↓
Application API 5xx 증가
       ↓
개발자에게 알림
       ↓
로그 직접 확인
       ↓
원인 조사
       ↓
서버 재시작
       ↓
정상 여부 확인
```

### ✅ 3. 문제

장애가 발생할 때마다 개발자가 처음부터 로그를 찾고 대응 방법을 판단해야 한다.

### ✅ 4. 더 위험한 상황

```text
장애 발생
    ↓
AI가 오류 분석
    ↓
AI가 서버 재시작
    ↓
AI가 DB 변경
    ↓
AI가 Worker 재실행
```

AI의 판단이 잘못됐다면 장애를 확대할 수 있다.

### ✅ 5. 개선된 구조

```text
Incident Detection
       ↓
Evidence Collection
       ↓
Severity Classification
       ↓
Impact Assessment
       ↓
Runbook Selection
       ↓
Safety Preconditions
       ↓
Approval
       ↓
Controlled Mitigation
       ↓
Recovery Verification
       ↓
Incident Closure
```

### ✅ 6. 이번 편의 핵심

**장애 대응에 필요한 정보 수집과 판단을 자동화하면서, 실제 운영 환경을 변경하는 행위에는 명시적인 권한과 검증 절차를 적용한다.**

## 2. Incident Response란?

### ✅ 7. 정의

Incident Response는 서비스 장애나 보안·업무 이상이 발생했을 때 이를 탐지하고, 영향을 줄이고, 정상 상태로 복구하는 과정이다.

### ✅ 8. 주요 단계

```text
DETECT

TRIAGE

ASSESS

MITIGATE

RECOVER

VERIFY

REVIEW
```

### ✅ 9. DETECT

이상 상황을 탐지한다.

### ✅ 10. TRIAGE

오류를 분류하고 중복된 알림을 정리한다.

### ✅ 11. ASSESS

영향 범위와 심각도를 판단한다.

### ✅ 12. MITIGATE

추가 피해가 발생하지 않도록 임시 조치를 수행한다.

### ✅ 13. RECOVER

장애 원인을 해결하고 서비스를 정상화한다.

### ✅ 14. VERIFY

실제 고객 업무가 정상적으로 복구됐는지 확인한다.

### ✅ 15. REVIEW

원인과 대응 과정을 정리하고 재발 방지 방법을 수립한다.

### ✅ 16. 중요한 원칙

**장애 대응의 목표는 서버의 에러 메시지를 없애는 것이 아니라 실제 고객 피해를 줄이고 정상적인 업무를 복구하는 것이다.**

---

## 3. Incident와 Alert의 차이

### ✅ 17. Alert

모니터링에서 발견한 특정 이상 신호다.

예:

```text
API 5xx Rate 증가

RDS Connection 증가

Frontend Error 발생
```

### ✅ 18. Incident

실제 서비스에 영향을 주는 문제를 조사하고 대응하기 위한 관리 단위다.

### ✅ 19. 하나의 Incident에 여러 Alert가 연결될 수 있다

```text
Incident:
신청 API 장애

├── API 5xx 증가
├── DB Timeout 증가
├── Application Success 감소
└── Customer Error 증가
```

### ✅ 20. 반대로

모든 Alert가 실제 Incident가 되는 것은 아니다.

### ✅ 21. 예시

테스트 목적으로 의도한 요청이 실패했거나 짧은 순간의 일시적인 Metric 변동일 수 있다.

### ✅ 22. 따라서

```text
Raw Alert
    ↓
Deduplication
    ↓
Correlation
    ↓
Incident Candidate
    ↓
Triage
```

구조를 사용할 수 있다.

### ✅ 23. 중요한 원칙

**Alert의 개수와 실제 발생한 장애의 개수는 다르다.**

---

## 4. Incident Severity

### ✅ 24. Severity

장애가 고객과 업무에 미치는 영향의 심각도를 구분하는 기준이다.

### ✅ 25. 예시 분류

| 등급 | 기준 예시 | 대응 |
|---|---|---|
| SEV1 | 전체 신청 불가, 개인정보 노출 가능성 | 긴급 대응 |
| SEV2 | 핵심 기능 상당 부분 장애 | 우선 대응 |
| SEV3 | 일부 사용자·기능 장애 | 영향 조사 및 조치 |
| SEV4 | 경미한 UI·비핵심 기능 문제 | 일반 업무 처리 |

### ✅ 26. 중요한 구분

Severity는 장애가 미치는 영향이고 Priority는 해결 작업의 우선순위다.

### ✅ 27. 예시

```text
신청 API 전체 장애
SEV1
```

### ✅ 28. 또 다른 예시

```text
특정 FAQ 아이콘 표시 오류
SEV4
```

### ✅ 29. 단순 HTTP 오류율만으로 결정하지 않는다

핵심 업무 API 한 개가 중단됐다면 전체 API 오류율이 낮아도 심각한 장애일 수 있다.

### ✅ 30. 판단 기준

```text
Affected Users

Affected Business Function

Data Integrity

Security Impact

Duration

Recovery Difficulty
```

### ✅ 31. 중요한 원칙

**장애 등급은 시스템 자원 사용량보다 실제 업무 영향과 복구 긴급도를 우선해 판단한다.**

---

## 5. Severity 자동 분류의 한계

### ✅ 32. AI가 Severity를 판단할 수 있을까?

로그와 업무 지표를 바탕으로 초기 등급을 제안할 수 있다.

### ✅ 33. 그러나 실제 피해 범위를 모를 수 있다

```text
Error Rate:
1%

Affected Operation:
APPLICATION_SUBMIT
```

### ✅ 34. 실제 의미

전체 요청의 1%라도 특정 상품의 신청 고객에게 집중됐다면 상당한 피해가 발생했을 수 있다.

### ✅ 35. 따라서

AI의 Severity는 초기 추천값으로 사용한다.

### ✅ 36. 중요한 업무 정책

인증 우회나 고객정보 노출 같은 위험은 별도 Hard Guardrail로 처리한다.

### ✅ 37. 분류 불가

```text
SEVERITY_UNDETERMINED
```

상태를 허용한다.

### ✅ 38. 중요한 원칙

**확인되지 않은 장애를 편의상 낮은 Severity로 분류하지 않는다.**

## 6. Incident 상태 관리

### ✅ 39. 상태 모델

```text
DETECTED

TRIAGING

INVESTIGATING

MITIGATING

RECOVERING

VERIFYING

RESOLVED

CLOSED
```

### ✅ 40. DETECTED

새로운 이상 신호가 발견됐다.

### ✅ 41. TRIAGING

실제 장애인지 확인한다.

### ✅ 42. INVESTIGATING

관련 로그와 업무 영향을 조사한다.

### ✅ 43. MITIGATING

추가 피해를 줄이기 위한 조치를 수행한다.

### ✅ 44. RECOVERING

정상적인 서비스 상태로 복구하고 있다.

### ✅ 45. VERIFYING

복구 이후 기술·업무 지표를 검증한다.

### ✅ 46. RESOLVED

정의된 복구 기준을 충족했다.

### ✅ 47. CLOSED

장애 보고와 후속 조치 정리가 완료됐다.

### ✅ 48. 중요한 구분

`RESOLVED`와 `CLOSED`는 동일한 상태가 아니다.

### ✅ 49. 중요한 원칙

**서버가 재시작됐다는 이유만으로 Incident를 종료하지 않는다.**

## 7. Incident Data Model

### ✅ 50. 최소 정보

```text
Incident ID

Severity

Status

Detected At

Affected Operation

Business Impact

Related Release

Owner

Current Hypothesis

Evidence
```

### ✅ 51. JSON 예시

```json
{
  "incidentId": "INC-20261110-001",
  "severity": "SEV2",
  "status": "INVESTIGATING",
  "affectedOperation": "APPLICATION_SUBMIT",
  "relatedRelease": "release-20261109-001",
  "rootCauseStatus": "HYPOTHESIS",
  "customerImpact": "일부 신청 요청 실패"
}
```

### ✅ 52. 중요한 주의

가상 데이터다.

실제 발생한 장애라는 의미가 아니다.

### ✅ 53. Root Cause 상태

```text
HYPOTHESIS

SUPPORTED

CONFIRMED

UNKNOWN
```

으로 관리한다.

### ✅ 54. 필요한 이유

AI가 원인을 추정했을 뿐인데 확정된 해결책처럼 실행하는 것을 방지하기 위해서다.

## 8. Incident Deduplication

### ✅ 55. 장애가 발생하면 Alert가 반복된다

```text
15:00 API Error

15:01 API Error

15:02 API Error

15:03 API Error
```

### ✅ 56. 잘못된 구조

Alert마다 새로운 Incident를 만든다.

### ✅ 57. 문제

하나의 장애에 대해 여러 복구 작업이 동시에 실행될 수 있다.

### ✅ 58. 권장

관련 Alert를 하나의 Incident로 묶는다.

### ✅ 59. Correlation Key 후보

```text
Service

Operation Key

Error Fingerprint

Environment

Time Window
```

### ✅ 60. 단순 Error Message만으로 충분할까?

아니다.

같은 메시지가 서로 다른 원인에서 발생할 수 있다.

### ✅ 61. 중요한 원칙

**Alert 중복 제거는 알림 소음을 줄이는 기능이면서 복구 작업 중복 실행을 방지하는 안전장치이기도 하다.**

## 9. Incident Detection Pipeline

### ✅ 62. 현재 기술 스택 기준

```text
React Frontend
       ↓
Frontend Error Collector

NestJS Backend
       ↓
Structured Log / Metrics

AWS EC2 / RDS
       ↓
CloudWatch
       ↓
Incident Correlation
       ↓
Incident Record
       ↓
Notification
```

### ✅ 63. Frontend

실제 고객이 경험하는 JavaScript 오류와 API 실패를 탐지한다.

### ✅ 64. Backend

Exception, Timeout, Database Error 등을 수집한다.

### ✅ 65. CloudWatch

인프라 상태 및 운영 Metric을 감시한다.

### ✅ 66. Business Metric

신청 실패, 중복 주문, 알림 상태 불명 등을 별도로 확인한다.

### ✅ 67. 중요한 구분

`CloudWatch Alarm = 고객 장애 확정`이 아니다.

### ✅ 68. 중요한 원칙

**모니터링 신호를 실제 고객 업무와 연결해야 의미 있는 Incident Response가 가능하다.**

## 10. CloudWatch Alarm의 세 가지 상태

### ✅ 69. 대표 상태

```text
OK

ALARM

INSUFFICIENT_DATA
```

### ✅ 70. OK

설정된 평가 기준에서 정상 상태라고 판단한 경우다.

### ✅ 71. ALARM

설정된 임계 조건을 만족한 경우다.

### ✅ 72. INSUFFICIENT_DATA

평가에 필요한 데이터가 충분하지 않은 상태다.

### ✅ 73. 주의

`INSUFFICIENT_DATA`를 자동으로 정상 처리하면 중요한 장애를 놓칠 수 있다.

### ✅ 74. 반대로

모든 Missing Data를 심각한 장애로 판단하면 불필요한 대응이 발생할 수 있다.

### ✅ 75. 따라서

Metric 종류에 따라 Missing Data 처리 정책을 정의해야 한다.

### ✅ 76. 중요한 원칙

**알림 상태와 실제 서비스 상태를 별도로 확인한다.**

## 12. Mitigation과 Recovery의 차이

### ✅ 83. Mitigation

추가 피해를 줄이는 임시 조치다.

### ✅ 84. Recovery

실제 문제를 해결하고 정상 서비스를 복원하는 과정이다.

### ✅ 85. 예시

```text
신규 알림 중복 발송 위험
```

### ✅ 86. Mitigation

```text
해당 알림 Worker의
신규 작업 처리 중단
```

### ✅ 87. Recovery

```text
중복 발송 원인 수정

↓

멱등성 검증

↓

Worker 재개
```

### ✅ 88. 중요한 점

Worker를 중지하는 것만으로 장애가 해결된 것은 아니다.

### ✅ 89. 중요한 원칙

**피해 확산 방지와 정상 업무 복원은 별도의 목표로 관리한다.**

## 13. 대응 작업의 위험도 분류

### ✅ 90. 복구 작업도 위험도가 있다

| 작업 | 일반적 위험도 | 자동화 방향 |
|---|---|---|
| 로그 조회 | LOW | 읽기 전용 자동화 |
| Readiness 조회 | LOW | 자동화 적합 |
| 오류 집계 | LOW | 자동화 적합 |
| Feature Flag 변경 | MEDIUM~HIGH | 범위 제한·승인 |
| Worker 일시 중지 | HIGH | 업무 영향 검토 |
| Backend Rollback | HIGH | 호환성 검토·승인 |
| Queue 대량 재처리 | HIGH | 승인·멱등성 |
| DB 대량 수정 | CRITICAL | 별도 복구 절차 |
| IAM 권한 변경 | CRITICAL | 강화된 승인 |

### ✅ 91. 같은 작업도 환경에 따라 위험도가 달라진다

Staging Worker 중지와 Production 알림 Worker 중지는 고객 영향이 다르다.

### ✅ 92. 중요한 기준

```text
Environment

Affected Resource

Business Impact

Side Effect

Reversibility

Blast Radius
```

### ✅ 93. 중요한 원칙

**복구 작업의 위험도는 명령어 자체보다 실제 운영 자원과 고객 업무에 미치는 영향을 기준으로 정한다.**

## 14. Automated Mitigation

### ✅ 94. 의미

사전에 정의된 안전 조건을 만족하는 범위에서 피해를 줄이기 위한 조치를 자동화하는 것이다.

### ✅ 95. 비교적 안전한 자동화

```text
Read-only Diagnostics

Incident Context Collection

Related Release Lookup

Known Error Signature Search
```

### ✅ 96. 제한이 필요한 자동화

```text
Feature Disable

Worker Pause

Traffic Routing Change

Rollback
```

### ✅ 97. 자동화 조건

```text
Precondition

Permission

Risk

Approval

Execution Limit

Postcondition
```

### ✅ 98. 중요한 원칙

**무엇을 실행할지보다 어떤 조건에서 실행하지 말아야 하는지를 먼저 정의한다.**

## 15. Runbook이란?

### ✅ 99. 정의

특정 장애에 대해 필요한 진단·대응·검증 단계를 표준화한 절차다.

### ✅ 100. 예시

```text
APPLICATION_API_5XX_RUNBOOK
```

### ✅ 101. Runbook이 답해야 하는 질문

```text
어떤 장애인가?

어떤 데이터를 확인해야 하는가?

어떤 작업을 수행할 수 있는가?

누가 승인해야 하는가?

어떤 경우 중단해야 하는가?

어떻게 정상화를 확인하는가?
```

### ✅ 102. Runbook의 목적

장애 상황에서 담당자가 매번 새로운 대응 방법을 생각하지 않도록 돕는다.

### ✅ 103. 하지만 주의

Runbook이 존재한다고 실제 문제를 자동으로 해결하는 것은 아니다.

### ✅ 104. 중요한 원칙

**Runbook은 검증 가능한 대응 절차이고, 실행 권한과 실행 결과는 별도로 통제해야 한다.**

## 29. TypeScript 복구 정책

### ✅ 188. 정책을 코드로 표현한다

```typescript
type ActionKind =
  | 'READ_DIAGNOSTICS'
  | 'DISABLE_FEATURE'
  | 'PAUSE_WORKER'
  | 'ROLLBACK_BACKEND'
  | 'MUTATE_DATABASE';

type Decision =
  | 'ALLOW_READ_ONLY'
  | 'REQUIRE_APPROVAL'
  | 'BLOCK';

interface RecoveryRequest {
  action: ActionKind;
  environment: 'test' | 'staging' | 'production';
  incidentVerified: boolean;
  targetVerified: boolean;
  rollbackCompatible: boolean;
}
```

### ✅ 189. 평가 함수

```typescript
function evaluateRecovery(
  input: RecoveryRequest,
): Decision {
  if (!input.targetVerified) {
    return 'BLOCK';
  }

  if (input.action === 'MUTATE_DATABASE') {
    return 'BLOCK';
  }

  if (
    input.action === 'READ_DIAGNOSTICS'
  ) {
    return 'ALLOW_READ_ONLY';
  }

  if (!input.incidentVerified) {
    return 'BLOCK';
  }

  if (
    input.action === 'ROLLBACK_BACKEND' &&
    !input.rollbackCompatible
  ) {
    return 'BLOCK';
  }

  return 'REQUIRE_APPROVAL';
}
```

### ✅ 190. 중요한 점

이 함수는 실행 허용 여부에 대한 초기 정책만 평가한다.

### ✅ 191. 실제 실행 전 추가 검증

```text
Authenticated Actor

Authorization

Valid Approval

Resource State

Execution Lock

Audit
```

가 필요하다.

### ✅ 192. 중요한 원칙

**순수한 정책 함수와 실제 AWS·DB를 변경하는 Executor를 분리한다.**

## 31. 복구 작업의 멱등성

### ✅ 200. Idempotency

동일한 논리적 작업을 반복 요청해도 의도하지 않은 중복 효과가 발생하지 않도록 설계하는 성질이다.

### ✅ 201. 왜 중요한가?

복구 API 호출이 Timeout될 수 있기 때문이다.

### ✅ 202. 상황

```text
Worker Pause 요청
       ↓
실제 Pause 성공
       ↓
API 응답 Timeout
       ↓
관리자 재시도
```

### ✅ 203. 위험

단순 Pause라면 큰 문제가 없을 수 있지만 일부 작업은 재실행 시 추가 Side Effect를 만들 수 있다.

### ✅ 204. 따라서

```text
Operation Key

Current Status

Previous Result

External Outcome
```

을 관리한다.

### ✅ 205. 중요한 구분

모든 AWS API나 Shell 명령이 본질적으로 멱등성을 보장하는 것은 아니다.

### ✅ 206. 중요한 원칙

**복구 요청의 중복 방지는 작업별 실제 Side Effect를 기준으로 설계한다.**

상태 제약조건, Audit, 실행 소유권, Approval Foreign Key 등을 추가한다.

### ✅ 212. 중요한 원칙

**같은 Incident의 같은 조치가 여러 번 실행되지 않도록 실제 DB 제약과 실행 정책을 적용한다.**

## 33. 실행 소유권과 원자적 Claim

### ✅ 213. 문제

두 Worker가 동일한 복구 작업을 동시에 실행할 수 있다.

### ✅ 214. 해결

조건부 상태 변경으로 실행 소유권을 획득한다.

### ✅ 215. 예시

```sql
UPDATE recovery_operations

SET
  state = 'CLAIMED',
  started_at = NOW()

WHERE id = $1
  AND state = 'PENDING'

RETURNING id;
```

### ✅ 216. 반환된 Row가 없다면?

다른 프로세스가 이미 Claim했거나 실행할 수 없는 상태일 수 있다.

### ✅ 217. 하지만 주의

이것만으로 분산 환경의 모든 장애를 해결하지는 못한다.

### ✅ 218. 추가 설계

```text
Lease Expiry

Execution Epoch

Crash Recovery

External Outcome Reconciliation
```

이 필요할 수 있다.

### ✅ 219. 중요한 원칙

**DB에서 작업을 Claim한 사실과 외부 시스템 변경이 성공한 사실을 구분한다.**

## 34. Worker Pause

### ✅ 220. 실제 업무 예시

### ✅ 223. 중요한 점

### ✅ 225. SQS

### ✅ 227. 중요한 원칙

**Worker Pause의 실제 의미는 사용 중인 Queue 기술과 Consumer 배포 구조에 따라 달라진다.**

### ✅ 247. 중요한 원칙

## 39. Feature Kill Switch

### ✅ 256. 상황


### ✅ 258. 장점

### ✅ 259. 하지만 조건이 있다

### ✅ 260. 중요한 점

### ✅ 261. Kill Switch와 업무 정책

가격 계산·주문 인증 같은 핵심 정책을 단순 Frontend Flag만으로 강제하면 안 된다.

### ✅ 262. 중요한 원칙

**Kill Switch는 새로운 피해를 제한하는 도구이며 기존 Side Effect까지 취소하지는 않는다.**

## 📌 요약

1109에서는 배포 직후 실제 서비스 상태를 평가하는 방법을 다뤘다.

```text
Deployment
       ↓
Release Health
       ↓
Critical Invariant
       ↓
HOLD / ROLLBACK_REVIEW
```

1110에서는 실제 장애가 확인된 이후 안전하게 대응하는 방법을 다뤘다.

```text
Incident Detection
       ↓
Alert Correlation
       ↓
Severity Classification
       ↓
Evidence Collection
       ↓
Business Impact
       ↓
Runbook Selection
       ↓
Safety Preconditions
       ↓
Human Approval
       ↓
Controlled Mitigation
       ↓
Recovery Verification
       ↓
Incident Closure
       ↓
Postmortem
```

이번 편에서 가장 중요한 원칙은 일곱 가지다.

**첫 번째 — 장애 탐지와 복구 실행을 분리한다.**

CloudWatch Alarm이 발생했다고 무조건 서버를 재시작하지 않는다.

**두 번째 — Read-only Diagnostics부터 자동화한다.**

운영 환경을 변경하지 않고도 필요한 정보를 수집할 수 있다.

**세 번째 — Mitigation과 Recovery를 구분한다.**

Worker를 중지해 추가 피해를 줄였더라도 실제 장애 원인은 남아 있을 수 있다.

**네 번째 — Runbook에는 실행 전·후 검증을 포함한다.**

무엇을 실행했는지뿐 아니라 실제로 어떤 상태가 됐는지 확인한다.

**다섯 번째 — 위험한 작업은 범위를 제한하고 승인한다.**

AI가 추천한 조치라도 Production 변경은 별도 권한과 승인 절차를 거친다.

**여섯 번째 — Unknown Outcome을 무조건 재실행하지 않는다.**

외부 메시지나 주문 처리 결과가 불확실하다면 먼저 실제 결과를 확인한다.

**일곱 번째 — 복구 완료는 실제 업무 정상화로 판단한다.**

서버가 실행되고 HTTP 200을 반환한다는 사실만으로 고객 신청과 주문 처리가 정상이라고 확정하지 않는다.

현재 투게더몰에서는 다음 순서가 적합하다.

```text
1. 중요한 장애 기준 정리

2. CloudWatch / NestJS Alert 정리

3. Incident Record 표준화

4. Read-only Diagnostic Collector

5. 주요 장애 Runbook 작성

6. Recovery Verification 자동화

7. AI Evidence Summary

8. 제한된 Approval Workflow

9. Worker / Feature Mitigation

10. 필요하면 SSM Automation
```

처음부터 복잡한 자동 복구 시스템을 만들 필요는 없다.

현재 1인 개발 환경에서 가장 실용적인 것은 **장애가 발생했을 때 관련 배포와 로그, 고객 영향 범위, 실행 가능한 대응 절차를 자동으로 정리해 주는 시스템**이다.

이후 실제로 반복 발생하는 장애가 확인되면 해당 Runbook의 일부를 제한적으로 자동화할 수 있다.

최종적으로 기억해야 할 원칙은 다음과 같다.

**좋은 장애 대응 자동화는 AI가 운영 환경을 마음대로 수정하는 시스템이 아니다. 실제 장애의 영향과 근거를 빠르게 확인하고, 사전에 검증된 절차와 제한된 권한으로 추가 피해를 줄인 다음, 고객 업무가 정상적으로 복구됐음을 증거로 확인하는 시스템이다.**
