## 1. Terraform Plan이 성공했다면 인프라도 정상일까?

### ✅ 1. 1118과의 연결

1118에서는 Infrastructure CI/CD를 통해 Terraform 변경사항을 검증하고 승인된 변경만 AWS에 적용하는 방법을 다뤘다.

```text
Infrastructure Change
       ↓
Pull Request
       ↓
Terraform Validation
       ↓
Trusted Plan
       ↓
Policy Guard
       ↓
Human Approval
       ↓
Controlled Apply
       ↓
Post-apply Verification
```

이제 다음 질문에 답해야 한다.

**Terraform Apply가 성공했다는 사실만으로 실제 AWS 인프라가 정상이라고 판단할 수 있을까?**

### ✅ 2. 실제 운영 상황

새로운 SKT 홈페이지를 구축하기 위해 Terraform Module을 작성했다고 가정한다.

```text
SKT Frontend
       ↓
CloudFront
       ↓
S3

SKT Backend
       ↓
EC2
       ↓
PostgreSQL
```

### ✅ 3. Terraform 실행 결과

```text
terraform fmt:
PASS

terraform validate:
PASS

terraform plan:
PASS

terraform apply:
SUCCESS
```

### ✅ 4. 하지만 실제 접속 결과

```text
Frontend:
정상 표시

Backend:
500 Internal Server Error

Database:
연결 실패
```

### ✅ 5. 가능한 원인

- EC2의 IAM Role에 필요한 권한이 없음
- Security Group에서 DB 연결이 차단됨
- RDS Subnet과 라우팅 구성이 잘못됨
- Backend가 잘못된 SSM Parameter를 참조함
- CloudFront가 존재하지만 Origin에 접근하지 못함
- 애플리케이션 실행 설정이 실제 인프라와 일치하지 않음

### ✅ 6. 중요한 차이

Terraform은 인프라 구성을 생성하고 관리할 수 있다.

그러나 실제 서비스의 모든 업무 요구사항이 충족됐는지를 자동으로 증명하지는 않는다.

### ✅ 7. 필요한 기술

Infrastructure Testing이다.

### ✅ 8. 전체 구조

```text

       ↓

       ↓

       ↓

```

### ✅ 9. 이번 편의 핵심 질문

**실제 고객 서비스에 영향을 주지 않으면서 AWS 인프라의 보안·연결·실행·복구 요구사항을 자동으로 검증할 수 있을까?**


**인프라 테스트는 Terraform 코드가 유효한지, AWS 자원이 정상적으로 생성되는지, 실제 애플리케이션이 해당 자원에서 올바르게 동작하는지를 구분해서 검증해야 한다.**

## 2. Infrastructure Testing이란?

### ✅ 12. 정의

Infrastructure Testing은 서버·네트워크·데이터베이스·스토리지·권한·복구 설정 등이 실제 요구사항을 충족하는지 검증하는 과정이다.

### ✅ 13. 일반적인 애플리케이션 테스트

```text
Unit Test
       ↓
Integration Test
       ↓
E2E Test
```

### ✅ 14. 인프라 테스트

```text
Configuration Test
       ↓
Policy Test
       ↓
Resource Integration Test
       ↓
Infrastructure E2E Test
       ↓
Recovery Test
```

### ✅ 15. 예시

애플리케이션 테스트는 다음과 같은 질문에 답한다.

```text
고객 신청 API가
올바른 주문 데이터를 저장하는가?
```

### ✅ 16. 인프라 테스트는 다음을 확인한다.

```text
Backend가 RDS에 접근할 수 있는가?

승인되지 않은 외부 접근은 차단되는가?

EC2 IAM Role이 필요한 SSM Parameter만 읽는가?

CloudFront에서 Frontend Asset을 제공하는가?

백업에서 새로운 DB를 복구할 수 있는가?
```

### ✅ 17. 중요한 원칙

**Infrastructure Testing은 애플리케이션 로직 테스트를 대체하지 않고 실제 운영 환경에서 해당 로직을 실행하기 위한 기반이 정상인지 확인한다.**

## 3. Infrastructure Test Pyramid

### ✅ 18. 모든 테스트에서 실제 AWS 자원을 만들어야 할까?

아니다.

가볍고 저렴한 테스트부터 실행하는 것이 효율적이다.

### ✅ 19. 추천 구조

```text
             Recovery Test
                  ▲
             AWS E2E Test
                  ▲
          Integration Test
                  ▲
           Plan Policy Test
                  ▲
         Terraform Native Test
                  ▲
            Static Validation
```

### ✅ 20. 아래쪽 테스트

실행이 빠르고 실제 AWS 자원을 생성하지 않아도 되는 경우가 많다.

### ✅ 21. 위쪽 테스트

실제 AWS 서비스를 사용하고 생성·삭제 비용과 실행시간이 증가할 수 있다.

### ✅ 22. 테스트별 비교

| 테스트 | 실제 AWS 생성 | 대표 목적 |
|---|---|---|
| `terraform fmt` | 없음 | 코드 형식 |
| `terraform validate` | 없음 | 구성 유효성 |
| Native Mock Test | 없음 | Module 조건 |
| Plan Policy Test | 없음 | 예상 변경 검증 |
| Terratest | 테스트에 따라 있음 | 실제 Resource 동작 |
| Infrastructure E2E | 있음 | 전체 연결 검증 |
| Recovery Test | 있을 수 있음 | 복구 능력 검증 |

### ✅ 23. 현재 추천

초기에는 아래 세 단계를 우선 도입한다.

```text
Static Validation

+

Native Mock Tests

+

Plan Policy Tests
```

### ✅ 24. 중요한 원칙

**실제 AWS 자원을 생성하지 않고 검증할 수 있는 요구사항은 가능한 한 낮은 비용의 테스트 단계에서 먼저 검증한다.**

## 4. Infrastructure Testing과 Terraform Plan

### ✅ 25. Terraform Plan의 역할

현재 Terraform Configuration이 실제 AWS 자원에 어떤 변경을 가하려고 하는지 확인한다.

### ✅ 26. 예시

```text
aws_security_group_rule.backend_to_rds

+ create
```

### ✅ 27. Plan이 보여 주는 것

Security Group Rule을 생성하려는 계획이다.

### ✅ 28. Plan이 직접 보장하지 않는 것

```text
실제 Backend에서 DB까지 연결되는가?

DB의 인증 정보가 올바른가?

PostgreSQL Query가 정상 실행되는가?
```

### ✅ 29. 추가 테스트

```text
Plan:
예상 변경 확인

Integration Test:
실제 연결 확인
```

### ✅ 30. 중요한 원칙

**Terraform Plan은 변경 예측 도구이고 실제 인프라 동작 검증은 별도의 테스트로 수행해야 한다.**

## 5. Terraform Static Test

### ✅ 31. 가장 기본적인 검증

```bash
terraform fmt -check -recursive
```

```bash
terraform init \
  -backend=false \
  -lockfile=readonly \
  -input=false
```

```bash
terraform validate
```

### ✅ 32. 확인할 내용

```text
HCL Syntax

Resource Argument Validation

Provider Schema Compatibility

Module Structure

Variable References
```

### ✅ 33. 중요한 제한

`terraform validate`는 실제 AWS 계정의 현재 네트워크 연결 상태를 확인하는 테스트가 아니다.

### ✅ 34. 또 다른 제한

Validation이 성공했다고 인프라 비용이 적절하다는 의미도 아니다.

### ✅ 35. 중요한 원칙

**Static Validation은 모든 Infrastructure Pipeline의 기본 단계지만 실제 운영 검증의 최종 단계는 아니다.**

## 6. Terraform Native Test

### ✅ 36. Terraform의 자체 테스트 기능

Terraform은 `.tftest.hcl` 파일을 이용해 Module 동작을 테스트할 수 있다.

### ✅ 37. 지원 버전

Terraform 1.6부터 Native Test Framework를 사용할 수 있다.

### ✅ 38. 주요 기능

```text
run

variables

assert

expect_failures

mock_provider

override_resource

override_data
```

일부 기능은 Terraform 버전에 따라 지원 범위가 다르다.

### ✅ 39. 테스트 파일 예시

```text
modules/
└── service-log-group/
    ├── main.tf
    ├── variables.tf
    ├── outputs.tf
    └── tests/
        └── configuration.tftest.hcl
```

### ✅ 40. 실행

```bash
terraform test
```

### ✅ 41. 가장 중요한 주의

`terraform test`는 기본적으로 `apply` 방식으로 실행되는 Test Run을 사용할 수 있다.

실제 AWS Provider를 사용한다면 Resource가 생성될 수 있다.

### ✅ 42. 안전한 시작 방식

```text
Mock Provider

+

command = plan
```

### ✅ 43. 중요한 원칙

**`terraform test`라는 명령어 자체를 안전한 읽기 전용 명령어로 간주하지 않는다.**

## 7. 테스트용 Terraform Module 만들기

### ✅ 44. 실습 목표

CloudWatch Log Group의 설정이 의도한 값으로 생성되는지 검증한다.

### ✅ 45. Module 파일

```hcl
# modules/service-log-group/main.tf

terraform {
  required_version = ">= 1.7.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
}

resource "aws_cloudwatch_log_group" "this" {
  name              = var.name
  retention_in_days = var.retention_days

  tags = var.tags
}
```

### ✅ 46. Variable

```hcl
# modules/service-log-group/variables.tf

variable "name" {
  type = string
}

variable "retention_days" {
  type = number

  validation {
    condition = contains(
      [7, 14, 30, 60, 90],
      var.retention_days
    )

    error_message = (
      "Unsupported retention policy."
    )
  }
}

variable "tags" {
  type    = map(string)
  default = {}
}
```

### ✅ 47. Output

```hcl
# modules/service-log-group/outputs.tf

output "log_group_name" {
  value = aws_cloudwatch_log_group.this.name
}
```

### ✅ 48. 중요한 전제

이 Module은 인프라 테스트 학습용이다.

실제 감사 로그의 법적 보관 기간이나 회사 정책을 위 예시에 맞춰 변경해서는 안 된다.

### ✅ 49. 중요한 원칙

**Infrastructure Unit Test는 실제 업무에서 보호해야 하는 설정 조건을 명시적인 입력과 검증 규칙으로 표현하는 데 활용한다.**

## 8. Mock Provider 기반 Native Test

### ✅ 50. 테스트 파일

```hcl
# modules/service-log-group/tests/configuration.tftest.hcl

mock_provider "aws" {}

run "log_group_configuration" {
  command = plan

  variables {
    name           = "/telecom-commerce/test/backend"
    retention_days = 30

    tags = {
      Project     = "telecom-commerce"
      Environment = "isolated-test"
      ManagedBy   = "terraform"
    }
  }

  assert {
    condition = (
      aws_cloudwatch_log_group.this.name ==
      "/telecom-commerce/test/backend"
    )

    error_message = "Unexpected log group name."
  }

  assert {
    condition = (
      aws_cloudwatch_log_group.this.retention_in_days ==
      30
    )

    error_message = "Invalid retention period."
  }

  assert {
    condition = (
      aws_cloudwatch_log_group.this.tags["Environment"] ==
      "isolated-test"
    )

    error_message = "Missing test environment tag."
  }
}
```

### ✅ 51. 실행 준비

실제 Module 디렉터리에서 실행한다.

```bash
cd infra/modules/service-log-group
```

```bash
terraform init \
  -backend=false \
  -input=false
```

### ✅ 52. 테스트 실행

```bash
terraform test \
  -filter=tests/configuration.tftest.hcl
```

### ✅ 53. 기대 결과

```text
Test:
PASS
```

단, 실제 Terraform·Provider 버전과 구성에 따라 결과를 확인해야 한다.

### ✅ 54. 중요한 특징

Mock Provider가 실제 AWS API를 호출하는 대신 필요한 값을 모의로 제공한다.

### ✅ 55. 중요한 제한

Mock Provider의 테스트가 통과했다고 실제 CloudWatch에 Log Group이 생성된 것은 아니다.

### ✅ 56. 중요한 원칙

**Mock Test는 Module의 설정과 조건을 검증할 수 있지만 실제 AWS의 권한·서비스 상태·네트워크 연결을 검증하는 것은 아니다.**

## 9. Mock Provider의 동작 원리

### ✅ 57. Mock Provider

Terraform Test에서 실제 Provider 대신 가상의 Resource 및 Data Source 값을 생성한다.

### ✅ 58. 예시

```text
Actual AWS Provider
       ↓
AWS API
```

```text
Mock AWS Provider
       ↓
Generated Test Values
```

### ✅ 59. 장점

AWS 자격 증명 없이 Module의 설정과 내부 계산을 검증할 수 있다.

### ✅ 60. 테스트 대상

```text
Resource Name

Tags

Retention

Output

Variable Validation

Module Configuration
```

### ✅ 61. 중요한 한계

Mock Provider가 생성한 ARN·ID 등의 값은 실제 AWS 서비스가 생성하는 값과 형식이 다를 수 있다.

### ✅ 62. 따라서

모의 ID나 ARN의 실제 AWS 형식까지 검증해야 한다면 적절한 Mock Value를 정의하거나 실제 Integration Test를 수행해야 한다.

### ✅ 63. 중요한 원칙

**Mock을 이용한 테스트에서는 모의 데이터의 성격과 실제 Provider 응답을 구분해야 한다.**

### ✅ 66. Apply Test

```hcl

```

### ✅ 67. 중요한 주의

### ✅ 68. 종료 시 정리

Terraform Test는 생성한 테스트 Resource를 종료 시 정리하려고 시도한다.

### ✅ 69. 하지만

정리가 실패해 Resource가 남을 수 있다.

### ✅ 70. 중요한 원칙

**실제 Provider를 사용하는 Apply Test는 AWS에 비용이 발생하는 통합 테스트로 분류한다.**

## 13. Plan-based Policy Test

### ✅ 80. 1118과 연결

Terraform Plan을 JSON으로 변환하면 변경사항을 프로그램에서 분석할 수 있다.

### ✅ 81. Plan JSON 생성

```bash
terraform plan \
  -out=reviewed.tfplan
```

```bash
terraform show \
  -json reviewed.tfplan \
  > reviewed-plan.json
```

### ✅ 82. 중요한 주의

Saved Plan과 Plan JSON에 Secret이 포함될 수 있다.

따라서 실제 운영 Plan을 일반적인 테스트 Fixture로 Git에 저장하지 않는다.

### ✅ 83. 안전한 테스트 방식

```text
Synthetic Plan Fixture

↓

Policy Script

↓

Expected PASS / BLOCKED
```

### ✅ 84. 주요 정책

```text
Production RDS Delete Block

Production S3 Delete Block

Resource Replacement Review

Unexpected IAM Admin Block

Public Database Block

Unapproved Resource Creation
```

### ✅ 85. 중요한 원칙

## 15. Plan Policy Unit Test 예시

### ✅ 91. Policy 함수

```javascript
// infra/policies/evaluate-plan.mjs

export function evaluatePlan(plan, environment) {
  if (
    typeof plan?.format_version !== 'string' ||
    !plan.format_version.startsWith('1.')
  ) {
    return {
      status: 'BLOCKED',
      reason: 'UNSUPPORTED_FORMAT',
    };
  }

  if (
    plan.errored === true ||
    plan.complete === false
  ) {
    return {
      status: 'BLOCKED',
      reason: 'INCOMPLETE_PLAN',
    };
  }

  const changes = plan.resource_changes;

  if (!Array.isArray(changes)) {
    return {
      status: 'BLOCKED',
      reason: 'RESOURCE_CHANGES_NOT_VERIFIED',
    };
  }

  for (const resource of changes) {
    const actions = resource?.change?.actions;

    if (!Array.isArray(actions)) {
      return {
        status: 'BLOCKED',
        reason: 'INVALID_ACTIONS',
      };
    }

    const signature = actions.join(',');

    if (
      signature === 'no-op' ||
      signature === 'read'
    ) {
      continue;
    }

    if (environment === 'production') {
      return {
        status: 'BLOCKED',
        reason: 'PRODUCTION_MUTATION_REQUIRES_APPROVAL',
      };
    }

    if (
      environment === 'isolated-test' &&
      signature === 'create' &&
      resource.type === 'aws_cloudwatch_log_group' &&
      !resource.change.importing
    ) {
      continue;
    }

    return {
      status: 'BLOCKED',
      reason: 'UNAPPROVED_CHANGE',
    };
  }

  return {
    status: 'PASS',
    reason: 'POLICY_CHECK_PASSED',
  };
}
```

## 20. Ephemeral Environment란?

### ✅ 121. 정의

특정 테스트 또는 검증 작업을 위해 일시적으로 생성하고 작업이 끝나면 정리하는 환경이다.

### ✅ 122. 일반적인 Staging

```text
Staging Infrastructure

↓

Always Running
```

### ✅ 123. Ephemeral Environment

```text
Test Run Start
       ↓
Create Test Infrastructure
       ↓
Run Tests
       ↓
Collect Results
       ↓
Destroy Test Infrastructure
       ↓
Verify Cleanup
```

### ✅ 124. 장점

테스트 사이의 데이터와 인프라 설정 간섭을 줄일 수 있다.

### ✅ 125. 비용 측면

필요할 때만 실행하는 경우 상시 Staging보다 비용을 절감할 수 있다.

### ✅ 126. 단점

인프라 생성 시간이 증가한다.

일부 AWS Resource는 생성과 삭제에 상당한 시간이 걸릴 수 있다.

### ✅ 127. 중요한 원칙

**Ephemeral Environment는 자동 삭제가 보장되는 무료 환경이 아니라 테스트용 자원의 생성과 종료를 관리하는 운영 방식이다.**

## 27. Terratest 코드 예시

### ✅ 163. 테스트 목표

격리된 AWS Test Account에서 CloudWatch Log Group을 생성하고 설정을 확인한 뒤 정리한다.

### ✅ 164. Go 테스트

```go
//go:build aws

package test

import (
    "os"
    "os/exec"
    "strings"
    "testing"
    "time"

    "github.com/gruntwork-io/terratest/modules/terraform/v2"
    "github.com/gruntwork-io/terratest/modules/teststructure/v2"
)

func TestIsolatedLogGroup(t *testing.T) {
    if os.Getenv("RUN_AWS_INFRA_TEST") != "yes" {
        t.Skip("AWS integration test disabled")
    }

    expectedAccount := os.Getenv("AWS_TEST_ACCOUNT_ID")

    if len(expectedAccount) != 12 {
        t.Fatal("Test AWS account ID required")
    }

    command := exec.Command(
        "aws",
        "sts",
        "get-caller-identity",
        "--query",
        "Account",
        "--output",
        "text",
    )

    output, err := command.Output()

    if err != nil {
        t.Fatal("AWS identity verification failed")
    }

    actualAccount := strings.TrimSpace(
        string(output),
    )

    if actualAccount != expectedAccount {
        t.Fatal("Unexpected AWS account")
    }

    runID := time.Now().UTC().
        Format("20060102-150405")

    terraformDir := teststructure.CopyTerraformFolderToTemp(
        t,
        "../",
        "fixtures/test-log-group",
    )

    options := &terraform.Options{
        TerraformDir: terraformDir,

        Vars: map[string]interface{}{
            "test_run_id": runID,
            "expected_test_account_id": expectedAccount,
        },
    }

    // 부분적으로 생성된 자원도 정리를 시도한다.
    t.Cleanup(func() {
        terraform.Destroy(t, options)
    })

    terraform.InitAndApply(t, options)

    actualName := terraform.Output(
        t,
        options,
        "log_group_name",
    )

    expectedName :=
        "/telecom-commerce/infra-test/" + runID

    if actualName != expectedName {
        t.Fatalf(
            "Unexpected log group: %s",
            actualName,
        )
    }
}
```

### ✅ 165. 중요한 전제

실제 실행을 위해서는 테스트 Fixture와 `go.mod`가 필요하다.

사용 중인 Terratest 버전에서 Package 경로와 API가 일치하는지 확인해야 한다.

### ✅ 166. 테스트 Fixture의 필수 조건

```text
No Production Backend

No Existing Resource Import

Dedicated Test Account

Limited Resource Types

Expected Account Allowlist
```

### ✅ 167. 이름 충돌

위 테스트의 시간 기반 Run ID는 설명용이다.

## 30. Test Timeout과 Cleanup

### ✅ 181. 테스트 Timeout

Integration Test에 전체 실행시간 제한을 설정한다.

### ✅ 182. 하지만

Go 테스트 Timeout이 발생하면 정상적인 Cleanup 절차를 실행하지 못할 수 있다.

### ✅ 183. 발생 가능한 상황

```text
Terraform Apply
       ↓
Resource Created
       ↓
Test Timeout
       ↓
Go Process Terminated
       ↓
Cleanup Not Executed
```

### ✅ 184. 개선 방향

```text
Appropriate Timeout

Resource Creation Budget

Unique TestRunId

Cleanup Attempt

Orphan Resource Scanner
```

### ✅ 185. 중요한 주의

Timeout을 무제한으로 늘리면 예상보다 큰 AWS 비용이 발생할 수 있다.

### ✅ 186. 중요한 원칙

**Infrastructure Test는 너무 짧은 Timeout으로 Cleanup이 중단되는 위험과 너무 긴 Timeout으로 비용이 증가하는 위험을 함께 관리해야 한다.**

## 31. Orphan Resource란?

### ✅ 187. 정의

테스트가 끝났지만 정상적으로 제거되지 않고 AWS에 남아 있는 자원이다.

### ✅ 188. 예시

```text

FAILED

STILL EXISTS
```

### ✅ 189. 비용이 큰 사례

```text

Test RDS Instance

Test NAT Gateway

Test Load Balancer

Test EBS Volume
```

### ✅ 190. 중요한 문제

테스트 자체는 오래전에 종료됐지만 Resource는 계속 비용을 발생시킬 수 있다.

### ✅ 191. 필요한 구조

```text
Test Run Metadata
       ↓
Resource Inventory
       ↓
Expired Resource Candidates
       ↓
Owner Verification
       ↓
Approved Cleanup
```

### ✅ 192. 중요한 원칙

**테스트 자원의 Cleanup은 Test Runner 내부 동작뿐 아니라 AWS 계정 전체에서 독립적으로 검증할 수 있어야 한다.**

### ✅ 274. 검증 예시

```text
↓

↓

↓

Synthetic Order Created

↓

Correct Response
```

### ✅ 275. 중요한 주의

Production DB에 가상의 주문을 생성해 테스트하지 않는다.

### ✅ 276. 중요한 원칙

**Infrastructure E2E Test는 실제 업무 경로를 재현하되 완전히 분리된 Synthetic Environment에서 수행해야 한다.**

### ✅ 284. 대표적인 테스트

```text
Configuration Recovery
```

### ✅ 285. 중요한 차이

백업이 존재한다는 사실과 백업으로 실제 시스템을 복구할 수 있다는 사실은 다르다.

## 48. RTO와 RPO

### ✅ 288. RTO — Recovery Time Objective

장애가 발생했을 때 업무를 복구하기 위해 허용하는 목표 시간이다.

### ✅ 289. RPO — Recovery Point Objective

복구 과정에서 허용할 수 있는 데이터 손실 범위를 시간 기준으로 정의한 목표다.

### ✅ 290. 예시

```text
RTO:

2시간 이내 서비스 복구
```

```text
RPO:

최대 15분의 데이터 손실 허용
```

위 값은 학습용 예시이며 실제 회사의 목표가 아니다.

### ✅ 291. 중요한 구분

RTO는 복구에 걸리는 시간을 평가한다.

RPO는 데이터가 어느 시점까지 복원되는지 평가한다.

### ✅ 292. 중요한 원칙

**RTO와 RPO는 서로 다른 복구 요구사항이며 백업이 존재한다는 사실만으로 두 목표를 만족했다고 판단하지 않는다.**

## 50. RDS Snapshot Restore Test

### ✅ 300. RDS Snapshot

특정 시점의 DB 상태를 복원하는 데 활용할 수 있는 백업이다.

### ✅ 301. 중요한 AWS 동작

RDS Snapshot을 복원하면 일반적으로 새로운 DB Instance가 생성된다.

### ✅ 302. 따라서

복원 테스트가 기존 운영 DB를 그대로 덮어쓰는 방식이라고 생각하면 안 된다.

### ✅ 303. 권장 테스트 구조

```text
Synthetic Test RDS
       ↓
Test Data Insert
       ↓
DB Snapshot
       ↓
New Restored DB Instance
       ↓
Connectivity Verification
       ↓
Test Data Verification
       ↓
Cleanup
```

### ✅ 304. 중요한 제한

실제 Production Snapshot에는 고객정보가 포함될 수 있다.

### ✅ 305. 현재 추천

처음에는 Synthetic Test Database를 이용해 Snapshot과 Restore 과정을 학습한다.

### ✅ 306. 중요한 원칙

**RDS Restore Test는 기존 운영 DB를 변경하지 않는 별도 복구 환경에서 수행한다.**

## 51. RDS Restore의 검증 항목

### ✅ 307. 단순 복원 성공만 확인하면 부족하다


```text

```

### ✅ 310. 중요한 주의

RDS Snapshot에서 새로운 DB를 복원하더라도 실제 Application의 연결 주소가 자동으로 변경되는 것은 아니다.

### ✅ 311. 따라서

복구 테스트용 Backend를 별도의 Restored DB Endpoint에 연결해야 한다.

### ✅ 312. 중요한 원칙

**DB 복구 성공은 RDS 인스턴스 생성 완료가 아니라 실제 애플리케이션이 복원된 데이터로 정상 동작한다는 사실까지 확인해야 한다.**

## 52. Point-in-Time Recovery

### ✅ 313. PITR

정해진 백업 보관 기간 안에서 특정 시점으로 DB를 복원하는 기능이다.

### ✅ 314. RDS에서의 동작

지원되는 RDS 구성에서는 특정 시점을 선택해 새로운 DB 인스턴스로 복원할 수 있다.

### ✅ 315. 예시

```text
10:00

정상 주문 데이터 존재
```

```text
10:05

잘못된 DB 변경 발생
```

```text
10:10

장애 발견
```

### ✅ 316. 복원 후보

장애 발생 전의 복구 가능한 시점으로 새로운 DB를 생성한다.

### ✅ 317. 중요한 위험

복원 시점을 장애 이전으로 선택하면 그 이후 정상적으로 생성된 주문 데이터가 새 DB에 포함되지 않을 수 있다.

### ✅ 318. 따라서

PITR은 단순히 이전 DB로 돌아가는 버튼이 아니다.

### ✅ 319. 필요한 검토

```text
Latest Restorable Time

Affected Records

Legitimate New Orders

Data Reconciliation

Business Recovery Plan
```

### ✅ 320. 중요한 원칙

**PITR 복구에서는 잘못된 데이터 변경을 되돌리는 것과 이후 정상적으로 생성된 업무 데이터를 보존하는 문제를 함께 고려해야 한다.**

---

## 53. Recovery Test와 실제 재해 복구

### ✅ 321. Synthetic Recovery Test

가상의 DB와 작은 데이터를 사용해 복구 절차의 기술적 동작을 검증한다.

### ✅ 322. Production Recovery Readiness Test

실제 운영 Backup 정책과 복구 설정, IAM 및 네트워크 조건을 점검한다.

### ✅ 323. 중요한 차이

Synthetic Test가 성공해도 실제 Production DB 규모에서 동일한 시간에 복구할 수 있다고 보장하지 않는다.

### ✅ 324. 이유

```text
Database Size

Storage Performance

Snapshot Restore Duration

Network Configuration

Application Dependency
```

등이 다를 수 있기 때문이다.

### ✅ 325. 중요한 원칙

**작은 테스트 DB의 복구시간을 실제 Production RTO 달성 근거로 그대로 사용하지 않는다.**

## 55. Failure Injection

### ✅ 332. 정의

시스템의 장애 대응 능력을 확인하기 위해 통제된 장애 상황을 만드는 테스트다.

### ✅ 333. 예시

```text

External API Timeout

Worker Crash

Network Latency

Resource Unavailability
```

### ✅ 334. 목적

실제 장애 상황에서 시스템이 안전하게 실패하고 복구되는지 확인한다.

### ✅ 335. 중요한 조건

장애를 발생시키는 대상과 영향 범위를 정확하게 통제해야 한다.

### ✅ 336. 초기 추천

AWS Resource를 직접 중단하기보다 독립 테스트 환경에서 애플리케이션의 의존성을 Mock 처리해 장애를 주입한다.

### ✅ 337. 중요한 원칙

**Failure Injection은 실제 고객 서비스를 일부러 불안정하게 만드는 작업이 아니라 격리된 환경에서 복구 가능성과 실패 처리를 검증하는 작업이다.**

## 56. AWS Fault Injection Service

### ✅ 338. AWS FIS

AWS Fault Injection Service는 AWS Workload에 장애 상황을 주입하는 실험을 구성할 수 있는 서비스다.

### ✅ 339. 주요 요소

```text

Target

Action

Stop Condition

Experiment Role
```

### ✅ 340. 중요한 기능

CloudWatch Alarm 등을 Stop Condition으로 설정할 수 있다.

### ✅ 341. Safety Lever

실행 중인 실험을 중지하고 새로운 실험 실행을 차단하는 안전장치도 제공한다.

### ✅ 342. 하지만

Stop Condition이나 Safety Lever가 있다고 실제 Production 실험이 무조건 안전한 것은 아니다.

### ✅ 343. 현재 추천

AWS FIS를 도입하기 전에 테스트 전용 환경에서 애플리케이션 수준의 장애 주입을 먼저 구현한다.

### ✅ 344. 중요한 원칙

**AWS FIS는 충분한 운영 준비와 안전 경계가 확보된 이후 사용하는 고급 검증 도구로 취급한다.**

```yaml
  contents: read
```

## 📌 요약

1118에서는 Terraform을 GitHub Actions와 연결해 검토한 변경만 AWS에 적용하는 Infrastructure CI/CD를 다뤘다.

```text
Infrastructure Change
       ↓
Trusted Plan
       ↓
Policy Review
       ↓
Approval
       ↓
Controlled Apply
       ↓
Post-apply Verification
```

1119에서는 이를 실제 인프라 동작과 복구 가능성까지 검증하는 테스트 체계로 확장했다.

```text
Infrastructure Configuration
       ↓
Static Validation
       ↓
Native Mock Test
       ↓
Plan Policy Test
       ↓
Dedicated Test Account
       ↓
Infrastructure Integration Test
       ↓
Application E2E Test
       ↓
Recovery Verification
       ↓
Cleanup Verification
       ↓
Infrastructure Test Evidence
```

이번 편에서 가장 중요한 원칙은 다음과 같다.

**첫 번째 — Terraform Plan 성공과 실제 인프라 동작 성공은 다르다.**

Terraform이 Resource를 생성했다고 Backend와 RDS의 실제 연결까지 자동으로 검증된 것은 아니다.

**두 번째 — Terraform Native Test는 실제 AWS Resource를 생성할 수 있다.**

`terraform test`가 기본적으로 Apply Test를 수행할 수 있다는 사실을 이해하고 처음에는 Mock Provider와 Plan Test를 우선 사용한다.

**세 번째 — 실제 AWS Integration Test는 전용 계정에서 수행한다.**

```text
Test Account

+

Restricted IAM Role

+

Test-only State

+

Synthetic Data
```

를 기본 조건으로 한다.

**네 번째 — Terratest는 필요한 곳에만 도입한다.**

Go를 이용한 실제 인프라 검증은 유용하지만 모든 Terraform Module에 적용할 필요는 없다.

**다섯 번째 — Ephemeral Environment도 실제 AWS 비용을 발생시킨다.**

테스트가 종료돼도 일부 Resource가 남을 수 있다.

따라서 Test Cleanup과 실제 Resource Inventory 확인이 필요하다.

**여섯 번째 — 네트워크 연결과 애플리케이션 정상 동작을 분리한다.**

```text
TCP Connection

Database Authentication

Application Query

Business Operation
```

은 서로 다른 검증 단계다.

**일곱 번째 — Backup이 존재한다는 사실과 복구 가능성은 다르다.**

RDS Snapshot이나 PITR을 이용해 실제로 데이터를 복원하고 필요한 업무 기능이 정상인지 확인해야 한다.

**여덟 번째 — RTO와 RPO는 다르다.**

RTO는 복구 소요시간의 목표다.

RPO는 데이터 손실 허용 범위의 목표다.

**아홉 번째 — Failure Injection은 테스트 환경에서 시작한다.**

실제 Production EC2나 RDS를 중단하는 대신 Mock을 이용한 안전한 장애 재현부터 진행한다.

**열 번째 — AI는 테스트 결과를 분석하는 역할이다.**

실제 Test Evidence를 근거로 실패 원인 후보와 검증 방법을 제안하게 한다.

최종적으로 현재 투게더몰에서 가장 현실적인 도입 순서는 다음과 같다.

```text
1. Terraform Static Validation

2. Terraform Native Mock Test

3. Plan Policy Unit Test

4. Infrastructure Test Report

5. AWS Test Account 필요성 검토

6. 최소 AWS Integration Test

7. TestRunId 및 Cleanup Verification

8. S3 / CloudFront 접근 테스트

9. EC2 / RDS 연결 테스트

10. Synthetic Application E2E

11. Ephemeral Staging 검토

12. RDS Restore Verification

13. RTO / RPO Evidence

14. Failure Injection

15. AI-assisted Infrastructure Test Analysis
```

현재는 React·NestJS·PostgreSQL과 AWS를 혼자 관리하는 상황이므로 처음부터 복잡한 AWS Integration Test Platform을 만들 필요는 없다.

가장 먼저 구축해야 할 것은 다음 구조다.

```text
Terraform Module
       ↓
Mock Test
       ↓
Policy Test
       ↓
Static CI
       ↓
Verified Test Result
```

이 구조가 안정적으로 동작한다면 다음 단계에서 실제 AWS Test Account를 이용한 Integration Test를 추가할 수 있다.

장기적으로 신규 SKT·KT 홈페이지가 추가되면 공통 Terraform Module을 사용하면서도 각 브랜드의 실제 인프라가 요구사항대로 동작하는지 독립적으로 검증할 수 있다.

특히 다음과 같은 운영 성과를 남길 수 있다.

```text
Terraform 변경 검증 자동화

인프라 보안 정책 검증

AWS Test Environment 격리

실제 Network / IAM 연결 검증

Database Restore Test

RTO / RPO 측정

Test Resource Cleanup Verification

Infrastructure Change Evidence
```

이러한 작업은 단순히 인프라 설정을 작성하는 경험을 넘어, 실제 운영 환경의 장애 위험을 줄이고 복구 능력을 검증하는 실무 역량으로 연결된다.

최종적으로 기억해야 할 원칙은 다음과 같다.

**좋은 Infrastructure Testing은 Terraform 코드가 오류 없이 실행되는지 확인하는 작업이 아니다. 실제 AWS 인프라가 업무에 필요한 보안·연결·성능·복구 요구사항을 충족하는지 검증하고, 테스트 과정에서 생성한 자원까지 안전하게 관리할 수 있음을 증명하는 과정이다.**
