## 1. 광고 유입이 급증하면 현재 서버는 얼마나 버틸 수 있을까?

### ✅ 1. 1111과의 연결

1111에서는 장애를 미리 재현하고 시스템이 실제로 복구 가능한지 확인하는 방법을 다뤘다.

```text
Critical Business Journey
        ↓
Failure Mode Analysis
        ↓
Controlled Fault Injection
        ↓
Incident Detection
        ↓
Recovery Verification
```

1112에서는 다른 종류의 문제를 다룬다.

**프로그램에 오류가 없더라도 요청이 증가하면 서비스가 느려지거나 중단될 수 있다.**

### ✅ 2. 온라인 휴대폰 판매몰의 특징

일반적인 웹사이트와 달리 특정 시점에 고객 요청이 집중될 수 있다.

예를 들면 다음과 같다.

```text
신제품 출시

사전예약 시작

네이버 광고 집행

특가 프로모션

문자·알림 발송

↓

순간적인 고객 유입 증가
```

### ✅ 3. 흔한 상황

평소에는 고객이 정상적으로 상품을 조회한다.

하지만 사전예약 시작 직후 상품 상세페이지 요청과 신청 API 호출이 집중된다.

```text
Normal Traffic
       ↓
Stable Service

Campaign Traffic
       ↓
High Concurrency
       ↓
Slow API
       ↓
Database Saturation
       ↓
Application Failure
```

### ✅ 4. CPU만 확인하면 충분할까?

아니다.

CPU가 낮아도 DB Lock이나 외부 API Timeout 때문에 요청이 지연될 수 있다.

### ✅ 5. RAM만 늘리면 해결될까?

반드시 그렇지 않다.

실제 병목이 SQL Query나 DB Connection Pool이라면 EC2 RAM 증설 효과가 제한적일 수 있다.

### ✅ 6. 서버를 여러 대 실행하면 해결될까?

일부 애플리케이션 병목은 완화될 수 있다.

하지만 RDS Connection이 부족하다면 서버가 늘어난 만큼 DB 연결 요청도 증가할 수 있다.

### ✅ 7. 이번 편의 핵심 질문

**현재 시스템이 처리할 수 있는 트래픽 수준을 어떻게 측정하고, 어느 부분을 먼저 최적화하거나 확장해야 할까?**

**실제 병목을 측정하기 전에 서버부터 증설하지 않는다.**

## 2. Capacity Planning이란?

### ✅ 10. 정의

Capacity Planning은 예상되는 업무량을 처리하기 위해 필요한 시스템 자원을 분석하고 준비하는 과정이다.

### ✅ 11. 단순 서버 사양 결정이 아니다

```text
CPU

RAM

Database Connections

Network

Storage I/O

External API Limits
```

까지 함께 고려한다.

### ✅ 12. 예시

사전예약 기간에 평소보다 신청 요청이 세 배 증가한다고 가정한다.

현재 시스템이 어느 정도를 처리하는지 모르면 필요한 서버 규모를 결정하기 어렵다.

### ✅ 13. 필요한 데이터

```text
Current Traffic

Peak Traffic

Request Distribution

Response Time

Resource Utilization

Failure Rate
```

### ✅ 14. Capacity Planning의 목표

성능을 높이는 것뿐 아니라 불필요한 인프라 비용을 줄이는 것이다.

### ✅ 15. 중요한 구분

```text
Capacity:
처리할 수 있는 업무량

Demand:
실제로 들어오는 업무량
```

### ✅ 16. 중요한 원칙

**현재 Capacity와 예상 Demand의 차이를 파악해야 적절한 확장 전략을 선택할 수 있다.**

## 3. 방문자 수와 요청 수는 다르다

### ✅ 17. 하루 방문자 10,000명

이 정보만으로 서버 부하를 정확하게 알 수 있을까?

아니다.

### ✅ 18. 이유

한 명의 고객이 여러 API를 호출할 수 있기 때문이다.

### ✅ 19. 예시

```text
고객 1명

상품 목록 조회
    ↓
상품 상세 조회
    ↓
요금제 조회
    ↓
리뷰 조회
    ↓
신청 모달 진입
```

### ✅ 20. 각 동작이 API 요청을 발생시킨다면?

한 번의 방문에서도 여러 Backend Request가 발생한다.

### ✅ 21. 동시에

Frontend의 이미지·JS·CSS 파일은 CloudFront에서 제공될 수 있다.

### ✅ 22. 따라서 요청을 구분한다

```text
Page Views

Static Asset Requests

API Requests

Database Queries

External API Calls
```

### ✅ 23. 중요한 원칙

**방문자 수를 곧바로 Backend 요청 수 또는 DB Query 수로 변환해서는 안 된다.**

## 4. RPS란?

### ✅ 24. RPS — Requests Per Second

1초 동안 처리하는 HTTP 요청 수를 뜻한다.

### ✅ 25. 기본 계산

```text
RPS

=

전체 요청 수
────────────
측정 시간(초)
```

### ✅ 26. 예시

1분 동안 6,000건의 요청을 처리했다고 가정한다.

```text
6,000 ÷ 60

= 100 RPS
```

### ✅ 27. 하지만 이 값은 평균이다

1분 동안 균일하게 100 RPS가 발생했다는 뜻은 아니다.

### ✅ 28. 실제 상황

```text
00~10초:
20 RPS

10~20초:
300 RPS

20~60초:
70 RPS
```

처럼 요청이 집중될 수 있다.

### ✅ 29. 중요한 지표

```text
Average RPS

Peak RPS

Requests by Operation
```

### ✅ 30. 중요한 원칙

**일평균 트래픽보다 실제 고객이 몰리는 짧은 구간의 Peak Traffic이 장애 대응에 더 중요할 수 있다.**

---

## 5. RPS와 Concurrency의 차이

### ✅ 31. Concurrency

같은 시점에 진행 중인 작업의 수를 뜻한다.

### ✅ 32. RPS

일정 시간 동안 얼마나 많은 요청이 들어오거나 완료됐는지를 나타낸다.

### ✅ 33. 둘은 다르다

```text
100 RPS

≠

동시 요청 100개
```

### ✅ 34. 예시

요청 하나가 평균 0.1초 동안 처리된다면 동시 처리 중인 요청 수는 상대적으로 적을 수 있다.

### ✅ 35. 반대로

요청 하나가 5초 동안 처리된다면 같은 RPS에서도 훨씬 많은 요청이 동시에 진행된다.

### ✅ 36. 따라서

다음 관계를 이해할 필요가 있다.

```text
Throughput

Latency

Concurrency
```

### ✅ 37. 중요한 원칙

**동시에 얼마나 많은 고객이 접속했는지보다 현재 서버에 얼마나 많은 작업이 진행 중인지가 자원 병목과 더 직접적으로 연결될 수 있다.**

---

## 6. Little's Law

### ✅ 38. Little's Law

안정적인 시스템에서 평균 도착률, 평균 체류 시간, 평균 시스템 내 작업 수 사이의 관계를 설명한다.

### ✅ 39. 기본 공식

```text
L = λ × W
```

각 항목의 의미는 다음과 같다.

```text
L:
평균 진행 중인 작업 수

λ:
단위 시간당 평균 처리량

W:
작업의 평균 체류 시간
```

### ✅ 40. 예시

서버가 100 RPS를 처리하고 요청 평균 시간이 0.2초라면?

```text
L = 100 × 0.2

L = 20
```

### ✅ 41. 의미

안정적인 조건에서 평균적으로 약 20개의 요청이 시스템 안에 존재하는 상황이다.

### ✅ 42. 응답 시간이 2초로 증가하면?

같은 100 RPS를 유지한다고 가정할 때:

```text
L = 100 × 2

L = 200
```

### ✅ 43. 중요한 의미

처리 지연이 늘면 동시에 진행 중이거나 대기 중인 작업도 증가할 수 있다.

### ✅ 44. 주의

Little's Law는 안정적인 관측 구간에서 평균값 사이의 관계다.

### ✅ 45. 따라서

갑작스러운 Spike나 계속 증가하는 Queue에 단순 적용해 정확한 동시 요청 수를 예측한다고 주장해서는 안 된다.

### ✅ 46. 중요한 원칙

**응답 시간이 증가하면 같은 유입량에서도 시스템에 남아 있는 작업이 늘어나 추가적인 병목을 만들 수 있다.**

---

## 7. Throughput과 Latency

### ✅ 47. Throughput

시스템이 일정 시간 동안 실제로 완료한 업무량이다.

### ✅ 48. Latency

하나의 요청 또는 작업이 완료되기까지 걸린 시간이다.

### ✅ 49. 좋은 성능

```text
높은 Throughput

+

낮은 Latency

+

낮은 Error Rate
```

를 함께 만족하는 상태다.

### ✅ 50. 주의

Throughput만 증가했다고 성능이 좋아진 것은 아니다.

### ✅ 51. 예시

```text
처리량:
증가

응답시간:
급격히 증가

오류율:
증가
```

### ✅ 52. 이 경우

시스템을 실제 처리 한계 이상으로 밀어붙였을 수 있다.

### ✅ 53. 중요한 원칙

**많은 요청을 처리하는 능력과 고객에게 빠르고 정확하게 응답하는 능력을 함께 평가한다.**

---

## 8. p50·p95·p99

### ✅ 54. p50

응답시간의 중앙값이다.

### ✅ 55. p95

관측된 요청 중 약 95%의 응답시간이 그 값 이하인 지점이다.

### ✅ 56. p99

약 99%가 해당 값 이하인 지점이다.

### ✅ 57. 예시

```text
p50:
150ms

p95:
800ms

p99:
2,500ms
```

### ✅ 58. 의미

대부분의 요청은 빠르지만 일부 요청이 상당히 느릴 수 있다.

### ✅ 59. 평균만 보면?

일부 고객이 겪는 심각한 지연이 가려질 수 있다.

### ✅ 60. 중요한 주의

관측 표본이 적을수록 p99 같은 높은 분위수는 불안정하게 측정될 수 있다.

### ✅ 61. 따라서

분위수와 함께 요청 수를 기록한다.

### ✅ 62. 중요한 원칙

**성능 지표에는 p95·p99뿐 아니라 측정한 요청 수와 테스트 조건을 포함한다.**

---

## 9. Saturation이란?

### ✅ 63. Saturation

시스템 자원이 처리 한계에 가까워진 상태다.

### ✅ 64. CPU Saturation

CPU 사용률이 높은 상태로 유지되며 작업 대기가 발생할 수 있다.

### ✅ 65. Database Saturation

연결 수나 Query 처리 능력이 한계에 가까워질 수 있다.

### ✅ 66. External API Saturation

외부 Provider가 Rate Limit을 반환할 수 있다.

### ✅ 67. Queue Saturation

대기 작업이 처리 속도보다 빠르게 증가할 수 있다.

### ✅ 68. 중요한 점

모든 Saturation이 CPU 사용률에 반영되지는 않는다.

### ✅ 69. 예시

```text
EC2 CPU:
25%

DB Connection Pool:
Exhausted

신청 API:
Timeout
```

### ✅ 70. 중요한 원칙

**CPU 사용률이 낮더라도 요청 대기·DB 연결·외부 의존성 때문에 시스템이 포화 상태일 수 있다.**

## 10. Load Test의 종류

### ✅ 71. 부하 테스트를 하나로 생각하면 안 된다

| 테스트 | 목적 |
|---|---|
| Load Test | 예상 업무량에서 정상 작동 확인 |
| Stress Test | 처리 한계와 실패 형태 확인 |
| Spike Test | 순간적인 트래픽 급증 확인 |
| Soak Test | 장시간 실행 시 자원 누수 확인 |
| Scalability Test | 자원 증설 효과 검증 |
| Capacity Test | 목표 성능을 만족하는 최대 처리량 추정 |

### ✅ 72. Load Test

예상되는 트래픽 수준에서 오류율과 응답시간을 측정한다.

### ✅ 73. Stress Test

부하를 점진적으로 증가시켜 처리 한계를 찾는다.

### ✅ 74. Spike Test

짧은 순간에 요청량을 급격히 증가시킨다.

### ✅ 75. Soak Test

일정 부하를 장시간 유지하며 메모리 누수나 자원 누적을 관찰한다.

### ✅ 76. 중요한 조건

처음부터 Stress Test를 Production에 실행하지 않는다.

### ✅ 77. 중요한 원칙

**예상 트래픽 검증과 시스템의 고장 한계 탐색은 목적과 위험도가 다른 테스트다.**

## 11. 휴대폰 판매몰의 Workload Model

### ✅ 78. 모든 고객이 같은 요청을 보내지는 않는다

### ✅ 79. 일반 방문자

```text
상품 목록

↓

상품 상세

↓

리뷰 / FAQ
```

### ✅ 80. 구매 의도가 높은 고객

```text
상품 상세

↓

요금제 선택

↓

신청 모달

↓

신청 제출
```

### ✅ 81. 관리자

```text
주문 검색

↓

주문 상세

↓

상태 변경

↓

변경 로그
```

### ✅ 82. 따라서 업무별 요청 비중을 구분한다

### ✅ 83. 가상 Workload Mix

| Operation | 요청 비중 |
|---|---:|
| 상품 목록 | 40% |
| 상품 상세 | 30% |
| 요금제 조회 | 15% |
| 리뷰·FAQ | 10% |
| 신청 관련 조회 | 5% |

### ✅ 84. 주의

이 비율은 설명용이다.

실제 투게더몰의 트래픽을 의미하지 않는다.

### ✅ 85. 신청 제출

고객 데이터를 변경하는 작업이므로 읽기 전용 부하 테스트와 분리한다.

### ✅ 86. 중요한 원칙

**실제 서비스의 요청 비중과 업무 중요도를 반영한 Workload Model을 만들어야 의미 있는 테스트가 된다.**

## 12. 트래픽 Forecast

### ✅ 87. 부하 테스트 전 예상 수요를 정한다

### ✅ 88. 필요한 정보

```text
현재 Peak RPS

예상 광고 유입

상품 상세 조회 비율

신청 제출 비율

이벤트 지속 시간
```

### ✅ 89. 예시

현재 특정 API의 Peak가 20 RPS라고 가정한다.

### ✅ 90. 광고 확대

트래픽이 세 배 증가할 것으로 가정하면:

```text
20 × 3

= 60 RPS
```

### ✅ 91. 추가 여유

예상치를 초과하는 상황까지 고려해 별도의 Headroom을 둔다.

### ✅ 92. 하지만

실제 측정한 Capacity가 없다면 60 RPS를 안전하게 처리할 수 있다고 단정할 수 없다.

### ✅ 93. 중요한 원칙

**트래픽 Forecast는 테스트 목표를 설정하는 입력이며 실제 처리 능력은 측정으로 확인해야 한다.**

## 13. 광고 유입 증가와 Backend 부하

### ✅ 94. 네이버 광고 유입

고객은 상품 상세페이지로 직접 진입할 수 있다.

### ✅ 95. 여기서 발생할 수 있는 작업


## 19. k6의 Arrival Rate

### ✅ 143. VU 방식의 한계

VU 수를 고정하면 요청 처리 시간이 증가하면서 실제 요청 생성 속도가 낮아질 수 있다.

### ✅ 147. 개념

### ✅ 148. 중요한 주의

### ✅ 150. 중요한 원칙

## 20. Arrival-rate 기반 테스트

### ✅ 151. 코드 예시

```javascript
import http from 'k6/http';
import { check } from 'k6';

const BASE_URL = __ENV.TARGET_BASE_URL;

if (
  !BASE_URL ||
  !/^http:\/\/(127\.0\.0\.1|localhost):\d+$/.test(
    BASE_URL,
  )
) {
  throw new Error(
    'LOCAL_TEST_TARGET_REQUIRED',
  );
}

export const options = {
  scenarios: {
    catalog_read: {
      executor: 'constant-arrival-rate',

      rate: 5,

      timeUnit: '1s',

      duration: '20s',

      preAllocatedVUs: 5,

      maxVUs: 10,
    },
  },

  thresholds: {
    http_req_failed: ['rate<0.01'],

    http_req_duration: ['p(95)<800'],

    dropped_iterations: ['count==0'],

    checks: ['rate>0.99'],
  },
};

export default function () {
  const response = http.get(
    `${BASE_URL}/api/products`,
    {
      redirects: 0,

      timeout: '5s',

      tags: {
        operation: 'catalog_read',
      },
    },
  );

  check(response, {
    'status 200': (r) => r.status === 200,
  });
}
```

### ✅ 152. 이 설정

초당 다섯 번의 Iteration 시작을 목표로 한다.

### ✅ 153. 중요한 차이

하나의 Iteration에 요청을 여러 개 넣으면 API별 RPS와 Iteration Rate는 달라진다.

### ✅ 154. 이 예시

하나의 Iteration에 HTTP 요청 하나가 있으므로 두 수치가 비교적 직접적으로 연결된다.

### ✅ 155. 실제 테스트

Rate를 처음부터 크게 설정하지 않는다.

### ✅ 156. 중요한 원칙

**Arrival-rate 테스트에서는 실제 완료된 요청 수와 dropped_iterations를 함께 확인한다.**

## 26. NestJS Timing Interceptor

### ✅ 187. 처리 시간을 측정하는 예시

```typescript
import {
  Injectable,
  NestInterceptor,
  ExecutionContext,
  CallHandler,
  Logger,
} from '@nestjs/common';

import { Observable } from 'rxjs';
import { finalize } from 'rxjs/operators';
import { performance } from 'node:perf_hooks';

@Injectable()
export class TimingInterceptor
  implements NestInterceptor {

  private readonly logger =
    new Logger(TimingInterceptor.name);

  intercept(
    context: ExecutionContext,
    next: CallHandler,
  ): Observable<unknown> {
    const request = context
      .switchToHttp()
      .getRequest();

    const startedAt = performance.now();

    const operation =
      `${request.method}:${request.route?.path ?? 'unknown'}`;

    return next.handle().pipe(
      finalize(() => {
        const durationMs =
          performance.now() - startedAt;

        this.logger.log(
          JSON.stringify({
            operation,
            durationMs:
              Math.round(durationMs),
          }),
        );
      }),
    );
  }
}
```

### ✅ 188. 실제 적용 전 확인

위 코드는 개념 예시이며 Express 기반 NestJS 요청 객체를 가정한다.

### ✅ 189. 중요한 제한

RxJS `finalize()` 시점은 HTTP 응답이 클라이언트로 완전히 전송된 시점과 같지 않을 수 있다.

### ✅ 190. 따라서

정확한 End-to-end HTTP 응답시간과 최종 상태코드가 필요하다면 Adapter의 Response Finish Event나 기존 APM Instrumentation을 검토한다.

### ✅ 191. 또한

모든 요청에 JSON 로그를 기록하면 로그 수집 비용과 I/O 부하가 증가할 수 있다.

### ✅ 192. 중요한 원칙

**성능 관측 기능 자체가 새로운 병목이 되지 않도록 수집 범위와 비용을 제한한다.**

### ✅ 198. 중요한 주의

## 28. PostgreSQL Connection Pool

### ✅ 201. Connection Pool

DB 연결을 매 요청마다 새로 생성하지 않고 재사용하도록 관리하는 구조다.

### ✅ 202. 장점

DB 연결 생성 비용을 줄인다.

### ✅ 203. 하지만 Pool 크기가 너무 작으면?

요청이 연결을 기다리면서 지연될 수 있다.

### ✅ 204. Pool 크기가 너무 크면?

RDS의 총 Connection 수가 과도해질 수 있다.

### ✅ 205. 중요한 개념

```text
Application Instances

×

Pool Size per Instance

=

Potential Total Pool Connections
```

### ✅ 206. 예시

```text
Backend Instance:
4개

Instance당 Pool:
12개
```

### ✅ 207. 가능한 연결 수

```text
4 × 12 = 48
```

### ✅ 208. 주의

실제로 항상 48개가 연결되는 것은 아니다.

또한 DB 관리자·Migration·Worker 등의 별도 연결도 고려해야 한다.

### ✅ 209. 중요한 원칙

**애플리케이션의 Pool 크기는 RDS의 전체 Connection Budget과 함께 설계한다.**

## 34. pg_stat_statements

### ✅ 243. 기능

SQL 실행 횟수와 실행 시간 등의 통계를 확인하는 PostgreSQL Extension이다.

### ✅ 244. 예시 SQL

```sql
SELECT
  queryid,

  calls,

  ROUND(
    total_exec_time::numeric,
    2
  ) AS total_ms,

  ROUND(
    mean_exec_time::numeric,
    2
  ) AS average_ms

FROM pg_stat_statements

ORDER BY total_exec_time DESC

LIMIT 20;
```

### ✅ 245. 중요한 전제

`pg_stat_statements`가 활성화된 환경이어야 한다.

### ✅ 246. 설정 확인

### ✅ 247. 주의

운영 RDS 설정을 테스트 목적으로 임의 변경하지 않는다.

### ✅ 248. SQL 원문

개인정보나 민감한 조건이 포함될 수 있으므로 로그와 보고서에 무분별하게 복사하지 않는다.

### ✅ 249. 중요한 원칙

**느린 Query 하나만 찾는 것이 아니라 자주 실행돼 전체 DB 시간을 많이 소비하는 Query도 조사한다.**

## 49. Backpressure

### ✅ 351. Backpressure

시스템이 처리 가능한 속도보다 많은 작업이 들어올 때 부하를 조절하는 전략이다.

### ✅ 352. 예시

```text
Incoming Requests
       ↓
Rate Limit
       ↓
Application
```

### ✅ 353. 필요한 이유

모든 요청을 무제한 수용하면 Timeout과 Queue 증가가 발생할 수 있기 때문이다.

### ✅ 354. 대표적인 방법

```text
Rate Limiting

Concurrency Limit

Queue

Load Shedding

Timeout

Retry Budget
```

### ✅ 355. 중요한 주의

핵심 신청 API에서 무조건 요청을 거부하면 고객의 실제 신청 기회를 잃을 수 있다.

### ✅ 356. 따라서

부하 제한 기준과 고객에게 표시할 안내를 함께 설계한다.

### ✅ 357. 중요한 원칙

**Backpressure는 장애 확산을 방지하기 위한 전략이지만 고객 업무의 우선순위를 고려해야 한다.**

## 📌 요약

1111에서는 장애를 통제된 환경에서 재현하고 복구 능력을 검증하는 방법을 다뤘다.

```text
Failure Hypothesis
       ↓
Fault Injection
       ↓
Incident Detection
       ↓
Recovery Verification
```

1112에서는 트래픽 증가에 따라 발생할 수 있는 처리량과 성능 한계를 측정하는 방법을 다뤘다.

```text
Traffic Baseline
       ↓
Workload Model
       ↓
Capacity Forecast
       ↓
Isolated Load Test
       ↓
Throughput / Latency / Errors
       ↓
Bottleneck Analysis
       ↓
Performance Budget
       ↓
Optimization
       ↓
Scaling Decision
       ↓
Production Monitoring
```

이번 편에서 중요한 원칙은 일곱 가지다.

**첫 번째 — RPS와 동시 요청 수는 다르다.**

Little's Law를 통해 처리량과 평균 응답시간이 시스템 내 작업 수에 어떤 영향을 주는지 이해해야 한다.

**두 번째 — 평균 성능만 확인하지 않는다.**

p95·p99와 오류율, 요청 수를 함께 확인한다.

**세 번째 — Production에 무제한 Load Test를 실행하지 않는다.**

격리된 테스트 환경과 Synthetic Data를 사용한다.

**네 번째 — 서버보다 실제 병목을 먼저 찾는다.**

CPU·Memory·Connection Pool·Query·외부 API를 구분해서 분석한다.

**다섯 번째 — Prisma Connection Pool을 무조건 늘리지 않는다.**

실제 Prisma 버전과 RDS Connection Budget을 기준으로 설정한다.

**여섯 번째 — Auto Scaling은 자동으로 모든 병목을 해결하지 않는다.**

애플리케이션이 여러 인스턴스에서 동작할 준비가 돼 있어야 하며 DB의 한계도 고려해야 한다.

**일곱 번째 — 처리 한계보다 안전한 처리 수준이 중요하다.**

Performance Budget을 만족하는 조건에서 실제 업무를 안정적으로 처리할 수 있는 Capacity를 확인해야 한다.

현재 투게더몰에서 가장 현실적인 실행 순서는 다음과 같다.

```text
1. 주요 API별 RPS·p95 수집

2. EC2 CPU·Memory 확인

3. Prisma Pool·DB Connection 점검

4. 관리자·상품 Query 병목 조사

5. 독립된 Test DB 준비

6. k6 Low-load 테스트

7. Peak Traffic 시나리오 검증

8. 성능 개선 후 재측정

9. Capacity Forecast

10. 필요하면 EC2 / RDS 확장
```

현재 1인 개발 환경에서 처음부터 ALB나 Auto Scaling Group을 도입할 필요는 없다.

우선 **현재 시스템의 실제 트래픽과 응답시간을 측정하고, 안전한 테스트 환경에서 어느 지점부터 지연과 오류가 증가하는지 파악하는 것**이 더 중요하다.

특히 사전예약·네이버 광고 집행·신제품 출시처럼 트래픽 증가 시점을 어느 정도 예측할 수 있는 업무라면, 해당 이벤트 이전에 주요 API의 Capacity를 검증하는 방식이 효율적이다.

최종적으로 기억해야 할 원칙은 다음과 같다.

**좋은 Capacity Planning은 트래픽이 증가할 때마다 더 비싼 서버를 구매하는 것이 아니다. 실제 고객 요청과 시스템 병목을 측정하고, 코드·DB·Cache를 먼저 최적화한 다음, 필요한 수준의 인프라를 근거를 가지고 확장하는 과정이다.**
