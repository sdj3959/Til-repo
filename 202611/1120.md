## 1. AWS 서버가 갑자기 사라진다면?

### ✅ 1. 1119와의 연결

1119에서는 Infrastructure Testing을 통해 실제 AWS 자원의 생성·연결·보안·복구 기능을 검증하는 방법을 다뤘다.

```text
Terraform Configuration
       ↓
Static Validation
       ↓
Infrastructure Test
       ↓
AWS Integration Test
       ↓
Recovery Verification
       ↓
Cleanup Verification
```

1120에서는 이를 실제 운영 장애에 대응하기 위한 복구 체계로 발전시킨다.

### ✅ 2. 실제 운영 상황

온라인 휴대폰 판매몰이 다음과 같은 환경에서 실행되고 있다고 가정한다.

```text
고객
  ↓
CloudFront
  ↓
React Frontend
  ↓
NestJS Backend
  ↓
RDS PostgreSQL
```

추가로 S3·SSM Parameter Store·CloudWatch·외부 상담 및 알림 API를 사용한다고 가정한다.

실제 서비스의 연결 구조와 가용성 설정은 AWS Resource Inventory를 통해 확인해야 한다.

### ✅ 3. 장애 발생

어느 날 운영 중인 EC2에 문제가 발생했다.

```text
Frontend:
정상 표시

Backend:
접속 실패

Database:
정상
```

### ✅ 4. 고객에게 발생하는 문제

상품은 볼 수 있지만 실제 휴대폰 신청을 완료할 수 없다.

### ✅ 5. 더 위험한 상황

RDS의 데이터가 잘못 변경됐다고 가정한다.

```text
고객 신청:
정상 접수

관리자 주문관리:
기록 누락

상담 진행:
일부 완료

알림톡:
이미 발송됨
```

### ✅ 6. 단순 서버 재시작으로 해결될까?

아니다.

데이터가 잘못되었거나 이미 외부 시스템에서 처리된 작업이 있다면 서버를 재시작하는 것만으로 복구할 수 없다.

### ✅ 7. 필요한 것은?

**Disaster Recovery와 Business Continuity Planning이다.**

## 2. Disaster Recovery란?

### ✅ 12. 정의

Disaster Recovery, 줄여서 DR은 심각한 장애나 재해가 발생했을 때 IT 시스템과 데이터를 복구하기 위한 기술 및 운영 체계다.

### ✅ 13. 대표적인 장애

```text
EC2 Instance Failure

Database Failure

Network Failure

Storage Corruption

Accidental Deletion

Credential Compromise

Availability Zone Failure

AWS Region Disruption
```

### ✅ 14. DR에서 중요한 것

복구 절차를 문서로 작성하는 것만으로 충분하지 않다.

### ✅ 15. 필요한 세 가지

```text
Recoverable Resources

Executable Recovery Procedure

Verified Recovery Result
```

### ✅ 16. 예시

RDS에 자동 백업이 설정돼 있다.

하지만 실제로 복원해 본 적은 없다.

### ✅ 17. 판단

백업 설정이 존재하는 것은 확인했지만 실제 복구 능력은 충분히 검증되지 않았다.

### ✅ 18. 중요한 원칙

**Disaster Recovery는 장애 발생 시 사용할 수 있는 구체적인 복구 절차와 실제 검증 결과를 포함해야 한다.**

---

## 3. Business Continuity란?

### ✅ 19. 정의

Business Continuity는 IT 장애가 발생하더라도 중요한 업무를 가능한 범위에서 지속하거나 적절한 대체 절차로 운영하는 것이다.

### ✅ 20. Disaster Recovery와 차이

```text
Disaster Recovery:

시스템과 데이터 복구
```

```text
Business Continuity:

장애 중에도 중요한 업무를
어떻게 유지할 것인가?
```

### ✅ 21. 투게더몰 예시

Backend가 정상 동작하지 않는다.

### ✅ 22. 가능한 업무 지속 방식

- 장애 공지 제공
- 상품 정보 조회 유지
- 관리자에게 장애 상태 안내
- 이미 접수된 주문의 처리 현황을 별도 승인된 자료로 확인
- 새로운 신청의 접수 가능 여부를 명확하게 표시

### ✅ 23. 위험한 방식

Backend가 동작하지 않는데도 고객에게 신청이 정상 접수된 것처럼 보여 주는 것이다.

### ✅ 24. 중요한 원칙

**Business Continuity는 서비스의 모든 기능을 억지로 유지하는 것이 아니라 장애 중에도 안전하게 제공할 수 있는 업무를 구분하는 것이다.**

---

## 4. Disaster Recovery와 High Availability

### ✅ 25. High Availability

장애가 발생하더라도 서비스 중단을 최소화하도록 여러 자원이나 장애 대응 구조를 구성하는 것이다.

### ✅ 26. 예시

```text
Backend A
       │
       ├── Load Balancer
       │
Backend B
```

하나의 Backend가 실패했을 때 다른 Backend가 요청을 처리할 수 있다.

### ✅ 27. Disaster Recovery

대규모 장애나 데이터 손실 이후 시스템과 데이터를 복구하는 것이다.

### ✅ 28. 중요한 차이

Multi-AZ RDS가 구성돼 있다고 잘못된 SQL 실행이나 데이터 삭제까지 자동으로 되돌릴 수 있는 것은 아니다.

### ✅ 29. 데이터 오류

잘못된 데이터 변경이 복제될 수도 있다.

### ✅ 30. 따라서

```text
High Availability

+

Backup / Recovery

+

Business Reconciliation
```

을 함께 고려해야 한다.

### ✅ 31. 중요한 원칙

**High Availability는 장애 발생 시 서비스 지속에 중점을 두고 Disaster Recovery는 손상되거나 중단된 시스템과 데이터를 복구하는 데 중점을 둔다.**

---

## 5. 장애 유형 분류

### ✅ 32. 모든 장애에 같은 복구 방법을 사용할까?

아니다.

### ✅ 33. 분류

| 장애 | 첫 대응 방향 |
|---|---|
| Backend Process Crash | 프로세스·로그·헬스 확인 |
| EC2 인스턴스 장애 | EC2 상태·인프라 복구 |
| RDS 연결 실패 | 네트워크·인증·DB 상태 확인 |
| 잘못된 코드 배포 | 배포 버전 검토·롤백 |
| DB 데이터 훼손 | 쓰기 차단·데이터 복구 |
| S3 객체 삭제 | 버전 및 백업 확인 |
| CloudFront 설정 장애 | Origin·Cache·배포 상태 확인 |
| 외부 API 장애 | 격리·재시도 정책·업무 상태 확인 |
| AWS Region 장애 | 별도 복구 전략 판단 |

### ✅ 34. 중요한 의미

Backend 코드 오류라면 DB를 복원할 필요가 없을 수 있다.

### ✅ 35. 반대로

데이터가 손상됐는데 Backend만 재시작하면 원인을 해결하지 못한다.

### ✅ 36. 중요한 원칙

**장애 원인을 분류하기 전에 복구 수단부터 실행하지 않는다.**

---

## 6. 장애의 영향 범위

### ✅ 37. Blast Radius

특정 장애가 다른 서비스나 기능에 영향을 미치는 범위다.

### ✅ 38. 예시

공통 Backend가 LG U+·SKT·KT 홈페이지의 신청을 모두 처리한다고 가정한다.

```text
LGU ─┐
     │
SKT ─┼── Shared Backend
     │
KT ──┘
```

### ✅ 39. 장애 발생

공통 Backend에 장애가 발생하면 세 홈페이지의 신청 기능이 동시에 영향을 받을 수 있다.

### ✅ 40. 반면

각 브랜드의 Frontend만 분리했다면 특정 브랜드의 정적 파일 장애는 다른 브랜드에 영향을 주지 않을 수도 있다.

### ✅ 41. 필요한 분류

```text
Brand

Application

Backend

Database

Network

External Provider
```

### ✅ 42. 중요한 원칙

**서비스 확장 시 공통 인프라의 비용 절감 효과뿐 아니라 장애가 여러 브랜드에 동시에 전파될 위험도 평가해야 한다.**

---

## 7. Single Point of Failure

### ✅ 43. SPOF란?

특정 자원 하나가 실패했을 때 전체 업무가 중단될 수 있는 구조를 의미한다.

### ✅ 44. 예시

```text
Customer
       ↓
Single EC2
       ↓
Single RDS
```

### ✅ 45. 발생 가능한 위험

EC2 하나가 실패하면 Backend 기능 전체가 중단될 수 있다.

### ✅ 46. 중요한 점

현재 실제 EC2가 단일 인스턴스인지, 다중 인스턴스인지 확인해야 한다.

### ✅ 47. 단일 인스턴스라도

자동 복구·Backup·IaC·배포 Artifact가 준비돼 있다면 복구 능력을 높일 수 있다.

### ✅ 48. 그러나

단일 인스턴스 자동 복구가 다중 인스턴스 High Availability와 동일한 것은 아니다.

### ✅ 49. 중요한 원칙

**SPOF를 발견하면 무조건 서버를 여러 대 만드는 것보다 실제 업무 영향과 복구 목표를 기준으로 대응 방식을 결정한다.**

---

## 8. Business Impact Analysis

### ✅ 50. BIA란?

장애가 사업에 어떤 영향을 미치는지 평가하는 과정이다.

### ✅ 51. 온라인 판매몰의 중요 기능

```text
상품 조회

휴대폰 신청

신청 정보 저장

주문 상태 관리

상담 진행

알림 발송

광고 유입 분석
```

### ✅ 52. 기능별 중요도는 같을까?

아니다.

### ✅ 53. 예시

| 기능 | 장애 영향 |
|---|---|
| 고객 신청 | 신규 접수 중단 |
| 주문관리 | 주문 처리 지연 |
| 상품 조회 | 고객 탐색 불가 |
| 상담 API | 고객 응대 지연 |
| 광고 분석 | 성과 데이터 누락 가능 |
| 리뷰 조회 | 부가 기능 이용 불가 |

### ✅ 54. 중요한 점

광고 분석이 잠시 중단되는 것과 실제 고객 신청이 사라지는 것은 업무 영향이 다르다.

### ✅ 55. 중요한 원칙

**Recovery Priority는 서버 종류보다 실제 고객과 사업에 미치는 영향을 기준으로 설정해야 한다.**

## 9. Recovery Priority

### ✅ 56. 가상의 우선순위

```text
P0:
고객 신청 및 기존 주문 데이터

P1:
관리자 주문관리와 상담 상태

P2:
상품 조회와 고객 안내

P3:
통계·리뷰·부가 기능
```

### ✅ 57. 중요한 전제

위 우선순위는 학습용 예시다.

실제 회사 업무 흐름과 계약·법적 의무를 확인해 결정해야 한다.

### ✅ 58. 복구 의존성

업무 중요도가 높더라도 하위 의존 시스템이 준비되지 않았다면 바로 복구할 수 없다.

### ✅ 59. 예시

```text
Database Recovery
       ↓
Backend Recovery
       ↓
Application Submission
       ↓
Admin Processing
```

### ✅ 60. 중요한 원칙

**복구 우선순위와 실제 기술적 복구 순서를 구분해야 한다.**

---

## 10. RTO란?

### ✅ 61. 정의

Recovery Time Objective는 허용 가능한 목표 복구시간이다.

### ✅ 62. 예시

```text
RTO:

2시간
```

장애 발생 후 목표 시간 안에 해당 업무를 복구하도록 계획한다.

### ✅ 63. 중요한 점

RTO는 실제 복구에 걸린 시간이 아니다.

### ✅ 64. 목표와 실제 측정

```text
Target RTO:

120분

Measured Recovery Time:

85분
```

### ✅ 65. 결과

위 가상 사례에서 측정된 복구시간은 목표 이내다.

### ✅ 66. 하지만

테스트 환경에서 측정한 결과가 실제 Production 복구시간과 같다고 단정할 수는 없다.

### ✅ 67. 중요한 원칙

**RTO는 복구 목표이고 실제 달성 여부는 사고 또는 복구 훈련에서 측정한 결과로 확인한다.**

---

## 11. RPO란?

### ✅ 68. 정의

Recovery Point Objective는 허용할 수 있는 데이터 손실 범위를 시간으로 표현한 목표다.

### ✅ 69. 예시

```text
RPO:

15분
```

### ✅ 70. 의미

특정 장애 상황에서 목표로 허용한 데이터 손실 시점의 범위를 의미한다.

### ✅ 71. 실제 사례

```text
10:00

정상 DB
```

```text
10:10

최근 복구 가능한 데이터 시점
```

```text
10:15

장애 발생
```

### ✅ 72. 이 경우

장애 시각과 복구 가능 시점 사이의 간격은 5분이다.

### ✅ 73. 중요한 한계

이 시간만 보고 실제로 어떤 신청·주문 데이터가 손실됐는지 확정할 수 없다.

### ✅ 74. 필요한 확인

실제 복원 DB의 주문·신청 데이터와 별도 근거를 비교해야 한다.

### ✅ 75. 중요한 원칙

**RPO 검증에서는 복구 시각과 함께 실제로 누락된 업무 데이터가 있는지 확인해야 한다.**

---

## 12. RTO와 RPO의 차이

### ✅ 76. 비교

| 항목 | RTO | RPO |
|---|---|---|
| 의미 | 복구시간 목표 | 데이터 손실 목표 |
| 핵심 질문 | 언제 정상화되는가? | 어디까지 데이터가 남는가? |
| 검증 방법 | 시간 측정 | 복구 데이터 검증 |
| 대표 위험 | 장시간 서비스 중단 | 정상 주문 데이터 손실 |

### ✅ 77. 가상의 목표

```text
Customer Application:

RTO 2시간
RPO 15분
```

### ✅ 78. 중요한 점

RTO를 만족했더라도 신청 데이터가 예상보다 많이 손실됐다면 RPO 목표를 충족하지 못했을 수 있다.

### ✅ 79. 반대로

데이터 손실 없이 복구했더라도 서비스 복구에 지나치게 오래 걸릴 수 있다.

### ✅ 80. 중요한 원칙

**RTO와 RPO는 독립적인 목표이므로 각각 다른 검증 근거가 필요하다.**

## 14. AWS Disaster Recovery 전략

### ✅ 86. 대표적인 네 가지 방식

```text
Backup and Restore

Pilot Light

Warm Standby

Multi-site Active/Active
```

### ✅ 87. Backup and Restore

평소 백업을 유지하고 장애가 발생하면 새 인프라와 데이터를 복구한다.

### ✅ 88. Pilot Light

핵심 데이터 및 최소한의 복구 기반을 유지하고 필요할 때 나머지 인프라를 확장한다.

### ✅ 89. Warm Standby

축소된 규모의 서비스 환경을 계속 운영하다 장애 시 확장한다.

### ✅ 90. Multi-site Active/Active

복수의 환경이 실제 트래픽을 처리한다.

### ✅ 91. 비교

| 전략 | 평소 비용 | 운영 복잡도 | 복구 특성 |
|---|---|---|---|
| Backup and Restore | 비교적 낮음 | 낮음~중간 | 복구시간 필요 |
| Pilot Light | 증가 | 중간 | 일부 기반 사전 준비 |
| Warm Standby | 더 높음 | 높음 | 대기 환경 활용 |
| Active/Active | 일반적으로 높음 | 매우 높음 | 지속적인 다중 서비스 |

### ✅ 92. 중요한 전제

실제 복구시간과 데이터 손실은 서비스 구성 및 검증 결과에 따라 달라진다.

### ✅ 93. 현재 추천

복구 요구사항과 예산이 확인되지 않았다면 Multi-region Active/Active부터 설계하지 않는다.

### ✅ 94. 중요한 원칙

**가장 복잡한 DR 아키텍처가 아니라 승인된 RTO·RPO 목표를 충족하는 가장 적절한 비용의 전략을 선택한다.**

---

### ✅ 99. 중요한 원칙

**개별 AWS 자원의 복구 절차와 실제 고객 서비스의 전체 복구 순서를 분리해 설계한다.**

## 19. EC2 Automatic Recovery

### ✅ 117. 중요한 제한

모든 종류의 애플리케이션 장애를 자동으로 해결하는 기능은 아니다.

```text
Status Check

EBS Data

Instance Store

Network Interface

Recovery Events
```

### ✅ 120. 중요한 원칙

**EC2 Automatic Recovery는 인프라 장애 대응 수단이며 애플리케이션 Readiness와 배포 검증을 별도로 유지해야 한다.**

## 21. AMI와 EBS Snapshot

필요한 Runtime Configuration은 SSM 등에서 가져온다.

### ✅ 132. 중요한 원칙

**EC2 복구는 서버 파일 복사에만 의존하지 않고 재현 가능한 배포 환경과 필요한 데이터 보존 정책을 함께 준비한다.**

## 25. RDS Multi-AZ

### ✅ 151. 개념

지원되는 RDS 구성에서 다른 Availability Zone에 Standby DB를 유지해 장애 시 Failover를 지원하는 방식이다.

### ✅ 152. 장점

일부 인프라 장애나 AZ 장애에서 DB 가용성을 높일 수 있다.

### ✅ 153. 중요한 한계

잘못 실행된 SQL이나 논리적 데이터 훼손에 대한 Point-in-Time 복구를 대신하지 않는다.

### ✅ 154. 또한

Multi-AZ Failover 시 기존 DB 연결이 끊어지고 새 연결이 필요할 수 있다.

### ✅ 155. 애플리케이션 준비

```text
Connection Timeout

Bounded Retry

Pool Recovery

Idempotency

Unknown Transaction Outcome
```

### ✅ 156. 중요한 원칙

**RDS Multi-AZ는 고가용성 수단이지 백업과 데이터 복구 전략을 대체하는 기능이 아니다.**

## 26. RDS Automated Backup

### ✅ 157. 역할

RDS의 자동 백업 기능을 이용하면 설정된 보존 기간 안에서 복원 가능한 데이터를 관리할 수 있다.

### ✅ 158. 일반적인 RDS DB Instance

Backup Retention Period는 일반적으로 0일부터 35일까지 설정할 수 있다.

0일은 자동 백업을 비활성화하는 의미로 사용될 수 있다.

### ✅ 159. 중요한 전제

RDS 구성 방식에 따라 Backup Retention 설정의 지원 범위와 제약이 다를 수 있다.

### ✅ 160. 반드시 확인할 것

```text
Backup Enabled

Retention Period

Latest Restorable Time

Backup Window

Backup Status
```

### ✅ 161. 중요한 위험

자동 백업이 존재한다고 현재 시각까지 모든 변경사항을 즉시 복원할 수 있는 것은 아니다.

### ✅ 162. 중요한 원칙

**RDS 자동 백업은 실제 설정과 최근 복구 가능 시간을 확인하고 복원 테스트까지 수행해야 한다.**

## 27. RDS 백업 상태 조회

### ✅ 167. 중요한 원칙

**RDS 복구 가능 시점은 추측하지 않고 AWS가 실제 제공하는 정보를 기준으로 확인한다.**

## 28. Snapshot과 PITR

### ✅ 168. Snapshot Restore

특정 Snapshot에 저장된 시점의 데이터로 새로운 DB를 복원한다.

### ✅ 169. PITR

자동 백업 보관 기간 안의 특정 복구 가능 시점을 선택해 새로운 DB를 생성한다.

### ✅ 170. 차이

| 항목 | Snapshot Restore | PITR |
|---|---|---|
| 기준 | 지정된 Snapshot | 선택한 복구 가능 시점 |
| 주요 목적 | 특정 백업 복원 | 시점 기반 데이터 복구 |

| 후속 작업 | 연결·데이터 검증 | 연결·데이터 검증 |

### ✅ 171. 중요한 사실

두 방식 모두 기존 Backend의 Database URL이 자동으로 새 DB를 바라보게 되지는 않는다.

### ✅ 173. 중요한 원칙

## 33. Maintenance Mode

### ✅ 195. 장애 중 고객에게 무엇을 보여 줄까?

### ✅ 198. HTTP 응답

### ✅ 199. 주의

503 응답을 받았다는 사실만으로 서버에서 해당 요청의 DB Commit이 발생하지 않았다고 확정할 수는 없다.

### ✅ 200. 중요한 원칙

**장애 중 고객 안내는 실제 업무 처리 상태와 일치해야 하며 처리 결과가 불명확한 요청은 중복 제출 방지와 상태 조회 절차를 제공해야 한다.**

## 35. Recovery Gate 평가 함수

### ✅ 208. 복구 직후 자동으로 신청 기능을 열어도 될까?

아니다.

### ✅ 209. 필요한 확인

```text
Backend Ready

Database Connected

Data Integrity Verified

Write Safety Verified

External Side Effects Reviewed

Critical Smoke Test Passed
```

### ✅ 210. TypeScript 상태 모델

```typescript
type CheckStatus =
  | 'PASS'
  | 'FAIL'
  | 'NOT_VERIFIED';

type RecoveryCheck =
  | 'BACKEND_READY'
  | 'DATABASE_CONNECTED'
  | 'DATA_INTEGRITY'
  | 'WRITE_SAFETY'
  | 'EXTERNAL_SIDE_EFFECTS'
  | 'CRITICAL_SMOKE_TEST';

type RecoveryInput = {
  incidentId: string;

  checks: Record<
    RecoveryCheck,
    CheckStatus
  >;
};

type RecoveryDecision =
  | 'HOLD'
  | 'ESCALATE'
  | 'HUMAN_APPROVAL_REQUIRED';

export function evaluateRecovery(
  input: RecoveryInput,
): RecoveryDecision {
  const statuses =
    Object.values(input.checks);

  if (
    statuses.includes('FAIL')
  ) {
    return 'ESCALATE';
  }

  if (
    statuses.includes('NOT_VERIFIED')
  ) {
    return 'HOLD';
  }

  if (
    statuses.length !== 6
  ) {
    return 'HOLD';
  }

  return 'HUMAN_APPROVAL_REQUIRED';
}
```

### ✅ 211. 중요한 의미

모든 Check가 PASS여도 바로 서비스 쓰기를 활성화하지 않는다.

### ✅ 212. 마지막 승인

```text
All Checks PASS
       ↓
Human Approval
       ↓
Controlled Write Resume
```

### ✅ 213. 중요한 원칙

**자동 검증은 복구 승인에 필요한 근거를 제공하지만 고객 신청 기능의 재개는 별도의 운영 결정으로 관리한다.**

## 38. Data Reconciliation이란?

### ✅ 225. 정의

서로 다른 데이터 원천이나 복구 전후의 기록을 비교해 누락·중복·불일치 여부를 확인하고 조정하는 과정이다.

10시부터 10시 5분까지 정상적으로 발생한 주문이 복구본에 포함되지 않을 수 있다.

```text
Original DB Evidence

Application Logs

External Provider Records

Approved Business Export

Admin Processing History
```

### ✅ 229. 중요한 주의

로그나 외부 Provider 데이터에 개인정보가 포함될 수 있으므로 실제 비교 과정에서 접근권한과 보존 정책을 적용해야 한다.

### ✅ 230. 중요한 원칙

**복구 시점 이후 발생한 정상 업무 데이터는 손상된 데이터와 구분해 재조정해야 한다.**

## 39. 데이터 손실과 중복의 구분

### ✅ 232. 중복

### ✅ 236. 중요한 원칙

**데이터 복구 후에는 누락·중복·외부 시스템과의 상태 불일치를 별도로 검증한다.**

## 41. Idempotency와 복구

### ✅ 244. Idempotency

같은 논리적 작업이 여러 번 요청되더라도 중복된 업무 결과가 발생하지 않도록 설계하는 성질이다.

### ✅ 245. 고객 신청 예시

```text
Logical Application A
       ↓
Attempt 1
       ↓
Timeout
       ↓
Attempt 2
       ↓
Same Application Result
```

### ✅ 246. 데이터베이스 제약

실제 업무 정의에 맞는 Unique Constraint를 이용할 수 있다.

### ✅ 247. 중요한 주의

고객 연락처만으로 Unique Constraint를 설정하면 정당한 복수 주문까지 차단할 수 있다.

### ✅ 248. 추천

업무적으로 동일한 신청 시도를 식별할 수 있는 안정적인 Key와 처리 상태를 관리한다.

### ✅ 249. 중요한 원칙

**복구 상황의 중복 신청 방지는 단순 전화번호 중복 검사가 아니라 실제 업무의 논리적 요청 단위를 기준으로 설계한다.**

## 42. Outbox Pattern과 복구

### ✅ 250. 문제 상황

신청 DB Commit 이후 카카오톡 알림 발송 작업을 수행한다.

```text
Application Commit
       ↓
Notification Send
```

### ✅ 251. 장애 발생

알림이 발송됐지만 DB에 발송 결과를 기록하기 전에 프로세스가 종료됐다.

### ✅ 252. 결과

```text
External Provider:
Sent

Internal Database:
Unknown
```

### ✅ 253. 위험

복구 후 Worker가 같은 알림을 다시 전송할 수 있다.

### ✅ 254. Outbox Pattern

업무 트랜잭션과 함께 발송할 이벤트를 기록하고 별도의 Worker가 실제 전송을 수행하는 구조다.

### ✅ 255. 중요한 한계

Outbox를 사용한다고 외부 Provider의 실제 중복 발송이 자동으로 완전히 방지되지는 않는다.

### ✅ 256. 필요한 추가 설계

```text
Provider Idempotency Support

Message Key

Send Attempt Tracking

Unknown Outcome Handling

Provider Reconciliation
```

### ✅ 257. 중요한 원칙

**복구 시 Outbox와 외부 Provider의 실제 처리 결과를 확인하지 않은 상태에서 모든 미완료 작업을 무조건 재실행하지 않는다.**

외부 Provider의 상태가 내부 DB 복구 시점과 일치하지 않을 수 있다.

### ✅ 265. 복구 방식

외부 Provider가 제공하는 상태 조회 또는 승인된 대사 절차를 사용한다.

### ✅ 266. 위험한 접근

상태를 확인할 수 없다는 이유로 실제 고객 알림을 다시 전송하는 것이다.

### ✅ 267. 추천 상태

```text
CONFIRMED_NOT_SENT

CONFIRMED_SENT

UNKNOWN

REQUIRES_MANUAL_REVIEW
```

### ✅ 268. 중요한 원칙

**외부 시스템의 처리 결과가 불명확하면 자동 재실행보다 안전한 상태 조회와 수동 검토를 우선한다.**

## 47. S3 Versioning

### ✅ 277. 기능

S3 Versioning은 객체의 여러 버전을 보존할 수 있도록 지원한다.

### ✅ 278. 예시

```text
image.webp

Version A:
정상 이미지
```

```text
Version B:
잘못된 이미지
```

### ✅ 279. 복구

필요한 경우 정상 Version을 다시 현재 Version으로 복원하는 작업을 수행할 수 있다.

### ✅ 280. 중요한 점

Versioning이 활성화되지 않은 기간에 삭제·덮어쓰기된 데이터를 항상 복구할 수 있는 것은 아니다.

### ✅ 281. 또 다른 위험

Version ID를 지정해 영구 삭제한 객체 버전은 일반적인 Delete Marker 복구와 다르다.

### ✅ 282. 중요한 원칙

**S3 Versioning은 객체 복구 능력을 높이지만 모든 삭제·보안 사고에 대한 완전한 백업을 보장하지 않는다.**

## 49. S3 Object Lock과 백업

### ✅ 288. Object Lock

지원되는 구성에서 객체 버전의 삭제 또는 변경을 제한하는 보존 기능이다.

### ✅ 289. 활용 목적

중요한 백업 객체에 대한 실수 또는 악의적인 삭제 위험을 줄이는 데 활용할 수 있다.

### ✅ 290. 중요한 주의

Object Lock에는 Governance Mode와 Compliance Mode 등의 차이가 있다.

### ✅ 291. 특히 Compliance Mode

보존 기간 동안 객체를 제거하거나 설정을 변경하는 작업이 강하게 제한될 수 있다.

### ✅ 292. 비용 문제

보존 정책이 지나치게 길면 삭제할 수 없는 객체 때문에 비용이 계속 발생할 수 있다.

### ✅ 293. 중요한 원칙

**삭제 방지 정책은 강력한 보호 장치이지만 보존 기간과 실제 업무 요구사항을 확인하지 않고 적용해서는 안 된다.**

## 52. Route 53과 DNS Failover

### ✅ 304. DNS Failover

여러 Endpoint가 준비된 환경에서 Health Check와 Routing Policy 등을 이용해 트래픽 경로를 변경할 수 있다.

### ✅ 305. 중요한 전제

실제로 정상 동작하는 대체 Endpoint가 있어야 한다.

### ✅ 306. 예시

```text
Primary Endpoint:
Unhealthy

Secondary Endpoint:
Healthy
```

### ✅ 307. 위험한 상황

Secondary Backend는 정상이나 필요한 DB가 복원되지 않았다.

### ✅ 308. 결과

DNS를 전환해도 실제 신청 기능은 정상화되지 않을 수 있다.

### ✅ 309. 추가 주의

DNS TTL과 Resolver Cache 때문에 트래픽 전환이 모든 사용자에게 즉시 반영된다고 보장할 수 없다.

### ✅ 310. 중요한 원칙

**DNS Failover는 정상 서비스가 가능한 대체 환경이 준비된 경우에만 복구 수단으로 활용할 수 있다.**

## 53. AWS Region 장애

### ✅ 311. 가장 큰 장애 시나리오 중 하나

운영 Region의 여러 서비스가 동시에 영향을 받을 수 있다.

### ✅ 312. 필요한 전략

```text
Cross-region Backup

Infrastructure Configuration

Alternate Region Capacity

Secret / IAM Recovery

DNS / Traffic Routing

Data Reconciliation
```

### ✅ 313. 중요한 현실

Region 복구를 준비하려면 추가 비용과 운영 복잡도가 발생할 수 있다.

### ✅ 314. 통신 3사 확장과의 관계

세 브랜드가 같은 Region과 공통 Backend를 사용한다면 하나의 Region 장애가 여러 사이트에 영향을 줄 수 있다.

### ✅ 315. 중요한 원칙

**Multi-region DR은 단순히 EC2를 다른 Region에 하나 더 만드는 것이 아니라 데이터·네트워크·인증·배포·트래픽 전환을 포함하는 전체 서비스 복구 전략이다.**

---

## 54. Cross-region Backup

### ✅ 316. 개념

중요한 백업을 다른 AWS Region에도 보관하는 방식이다.

### ✅ 317. 장점

특정 Region에서 문제가 발생한 경우 다른 Region의 백업을 이용해 복구할 수 있는 가능성을 높인다.

### ✅ 318. 주요 검토

```text
Supported Resource

Backup Copy Schedule

Copy Completion

KMS Key

Restore Permission

Target Region

Retention
```

### ✅ 319. 중요한 점

Cross-region Backup이 존재해도 실제 서비스가 다른 Region에서 즉시 실행되는 것은 아니다.

### ✅ 320. 중요한 원칙

**Cross-region Backup은 데이터 복구 기반이며 서비스 복구를 위해서는 별도 인프라와 실행 절차가 필요하다.**

---

## 55. Cross-account Backup

### ✅ 321. 목적

운영 계정과 다른 AWS 계정에 백업을 보관해 계정 수준의 사고 위험을 줄일 수 있다.

### ✅ 322. 필요 조건

AWS Organizations와 AWS Backup 지원 범위, IAM·KMS 설정 등을 확인해야 한다.

### ✅ 323. 중요한 제한

모든 AWS Resource와 암호화 키 구성이 동일한 방식으로 Cross-account 복사를 지원하는 것은 아니다.

### ✅ 324. 추가 비용

백업 저장·복사·복원에 비용이 발생할 수 있다.

### ✅ 325. 중요한 원칙

**Cross-account Backup은 보안 격리를 강화하는 선택지이며 실제 서비스와 암호화 구성의 지원 범위를 확인한 뒤 도입한다.**

---

## 56. AWS Backup Vault Lock

### ✅ 326. 기능

AWS Backup의 Recovery Point 삭제와 백업 보관 정책 변경을 제한할 수 있는 기능이다.

### ✅ 327. Governance Mode

권한을 가진 일부 주체가 정책을 관리할 수 있는 방식이다.

### ✅ 328. Compliance Mode

유예 기간이 끝나면 Vault Lock의 변경 또는 제거가 매우 강하게 제한되는 방식이다.

### ✅ 329. 중요한 위험

잘못 설정한 보존 기간으로 백업 삭제가 제한되면 예상하지 못한 장기 비용이나 운영 제약이 발생할 수 있다.

### ✅ 330. 현재 추천

기본 백업과 Restore Test를 먼저 구축한 후 필요한 경우 별도의 승인 절차로 검토한다.

### ✅ 331. 중요한 원칙

**불변 백업 정책은 복구 보안을 높이는 수단이지만 최초 도입부터 무조건 가장 강한 잠금을 적용하지 않는다.**

### ✅ 335. 중요한 원칙

**Backup Strategy는 데이터의 중요도·변경 빈도·복원 방법·보관 요건을 기준으로 구성한다.**

## 58. Backup Retention

### ✅ 336. Retention

백업을 얼마나 오래 보관할지 정의하는 정책이다.

### ✅ 337. 예시

```text
Automated Database Backup

Long-term Archive
```

### ✅ 338. 중요한 점

보관 기간이 길수록 비용과 복구 범위가 달라질 수 있다.

### ✅ 339. 하지만

짧은 Retention은 오래전에 발생한 데이터 손상을 뒤늦게 발견했을 때 복구 가능한 시점을 제한한다.

```text
Recovery Objectives

Legal Retention Requirement
```

### ✅ 341. 중요한 원칙

**Backup Retention은 비용 최적화 대상인 동시에 데이터 복구 능력에 직접 영향을 주는 보안·운영 정책이다.**

## 59. Backup과 Replication의 차이

### ✅ 342. Replication

원본 데이터의 변경을 다른 위치에 복제하는 방식이다.

### ✅ 343. Backup

특정 시점이나 보관 정책에 따라 복구에 사용할 데이터를 보존하는 방식이다.

### ✅ 344. 중요한 차이

원본에서 잘못 삭제된 데이터가 복제 환경에도 반영될 수 있다.

### ✅ 345. 따라서

Replication만으로 모든 데이터 삭제 사고를 복구할 수 있다고 가정하면 안 된다.

### ✅ 346. 필요한 조합

```text
High Availability / Replication

+

Versioned Backup

+

Recovery Procedure
```

### ✅ 347. 중요한 원칙

**Replication은 서비스 지속에 도움이 될 수 있지만 복구 시점을 보존하는 백업과 동일하지 않다.**

## 61. Recovery Drill

### ✅ 354. 정의

실제 장애가 발생하기 전에 복구 절차를 연습하고 검증하는 활동이다.

### ✅ 355. 초기 훈련

```text
Tabletop Exercise
```

실제 AWS 자원을 변경하지 않고 장애 상황과 대응 절차를 검토한다.

### ✅ 356. 다음 단계

```text
Isolated Restore Test
```

독립 환경에서 Synthetic Data를 복원한다.

### ✅ 357. 이후

```text
Infrastructure Rebuild Test
```

IaC와 Application Artifact를 이용해 테스트용 환경을 다시 구축한다.

### ✅ 358. 중요한 주의

실제 Production에서 장애를 발생시키는 훈련은 더 높은 수준의 안전 준비와 별도 승인이 필요하다.

### ✅ 359. 중요한 원칙

**복구 훈련은 문서 검토부터 시작해 실제 복원 검증으로 단계적으로 발전시킨다.**

## 65. TypeScript 복구시간 계산

### ✅ 376. 목표

복구 시점과 업무 정상화 시점의 간격을 계산한다.

### ✅ 377. 코드

```typescript
interface RecoveryTimingInput {
  incidentAt: string;

  businessVerifiedAt: string;
}

type RecoveryTimingResult =
  | {
      status: 'CALCULATED';

      recoveryMinutes: number;
    }
  | {
      status: 'INVALID';

      reason: string;
    };

export function calculateRecoveryTime(
  input: RecoveryTimingInput,
): RecoveryTimingResult {
  const incidentAt =
    Date.parse(input.incidentAt);

  const verifiedAt =
    Date.parse(input.businessVerifiedAt);

  if (
    !Number.isFinite(incidentAt) ||
    !Number.isFinite(verifiedAt)
  ) {
    return {
      status: 'INVALID',
      reason: 'INVALID_TIMESTAMP',
    };
  }

  if (verifiedAt < incidentAt) {
    return {
      status: 'INVALID',
      reason: 'INVALID_TIME_ORDER',
    };
  }

  return {
    status: 'CALCULATED',

    recoveryMinutes:
      (verifiedAt - incidentAt) / 60_000,
  };
}
```

### ✅ 378. 중요한 점

실제 사고에서는 사고 시작 시각이 나중에 확인될 수도 있다.

### ✅ 379. 따라서

```text

Detection Source

Business Verification Evidence
```

를 함께 기록한다.

### ✅ 380. 중요한 원칙

## 75. Failback이란?

### ✅ 407. 정의

장애로 대체 환경으로 전환한 서비스를 원래 환경 또는 새롭게 정한 주 운영 환경으로 다시 이전하는 과정이다.


## 📌 요약

1119에서는 실제 AWS 인프라를 생성하고 검증하는 Infrastructure Testing을 다뤘다.

```text
Terraform Configuration
       ↓
Infrastructure Integration Test
       ↓
Recovery Verification
       ↓
Cleanup Verification
```

1120에서는 이를 실제 고객 서비스 복구 체계로 확장했다.

```text
Production Infrastructure
       ↓
Failure Scenario Analysis
       ↓
Business Impact Assessment
       ↓
Recovery Objectives
       ↓
Backup Strategy
       ↓
Incident Containment
       ↓
Infrastructure Recovery
       ↓
Database Recovery
       ↓
Data Reconciliation
       ↓
Business Verification
       ↓
Controlled Service Restoration
       ↓
Measured RTO / RPO
       ↓
Recovery Evidence
```

이번 편에서 가장 중요한 원칙은 다음과 같다.

**첫 번째 — 백업이 있다고 복구할 수 있는 것은 아니다.**

실제 복구 테스트를 통해 DB와 애플리케이션이 정상 동작하는지 확인해야 한다.

**두 번째 — High Availability와 Disaster Recovery는 다르다.**

Multi-AZ는 가용성을 높일 수 있지만 논리적 데이터 삭제나 잘못된 SQL 변경을 자동으로 되돌리는 기능이 아니다.

**세 번째 — RTO와 RPO를 구분한다.**

RTO는 서비스 복구시간의 목표다.

RPO는 허용할 수 있는 데이터 손실 범위의 목표다.

**네 번째 — EC2 복구는 NestJS 실행까지 포함한다.**

EC2가 `running` 상태라고 실제 Backend가 정상 동작한다는 의미는 아니다.

**다섯 번째 — RDS PITR은 새 DB를 생성한다.**

새 DB로 복원한 뒤 실제 데이터와 애플리케이션의 연결을 검증해야 한다.

**여섯 번째 — 복구 시점 이후의 정상 주문을 보호해야 한다.**

과거 DB로 복원하면 일부 정상 주문이 누락될 수 있다.

실제 업무 기록과 외부 Provider의 처리 결과를 비교해야 한다.

**일곱 번째 — Timeout은 업무 실패의 확정적인 증거가 아니다.**

DB Commit 이후 응답만 실패한 상황에서는 주문이 이미 저장됐을 수 있다.

**여덟 번째 — 외부 알림은 자동으로 다시 보내지 않는다.**

이미 발송됐지만 내부 DB에 기록되지 않은 상태를 고려해야 한다.

**아홉 번째 — 서비스 재개 전에 Write Safety를 검증한다.**

Backend와 DB가 정상이어도 주문 데이터의 정합성이 확인되지 않았다면 신규 쓰기를 보류할 수 있어야 한다.

**열 번째 — 실제 복구 능력을 훈련과 증거로 검증한다.**

Runbook이 존재하는 것과 실제로 복구할 수 있는 것은 다르다.

현재 투게더몰에 가장 현실적인 도입 순서는 다음과 같다.

```text
1. AWS Resource Inventory 확인

2. EC2 / RDS / S3 실제 구성 정리

3. RDS Backup Retention 확인

4. Latest Restorable Time 조회

5. 기존 배포 Artifact 복구 방법 정리

6. 신청·주문 데이터 정합성 검증 기준 작성

7. Write Freeze / Maintenance Mode 설계

8. Synthetic RDS Restore Test

9. S3 Version Recovery Test

10. EC2 / NestJS 재구축 Test

11. External Provider Reconciliation 절차

12. Recovery Gate와 승인 단계

13. Recovery Drill

14. 실제 RTO / RPO 측정

15. 필요한 경우 Cross-region DR 검토
```

현재는 혼자서 Frontend·Backend·DB·AWS를 관리하고 있으므로 처음부터 고비용 Multi-region Active/Active 인프라를 구축할 필요는 없다.

가장 먼저 다음 세 가지에 답할 수 있어야 한다.

```text
1.

운영 EC2가 사라져도
Backend를 다시 실행할 수 있는가?
```

```text
2.

운영 RDS에 문제가 발생해도
실제 데이터를 복원할 수 있는가?
```

```text
3.

복구 후 실제 고객 신청과 주문이
누락되거나 중복 처리되지 않았는지
확인할 수 있는가?
```

이 세 가지를 실제 검증할 수 있다면 운영 서비스의 복구 능력을 한 단계 높일 수 있다.

특히 휴대폰 판매몰처럼 고객 신청·주문·상담·알림이 여러 시스템에 걸쳐 처리되는 서비스에서는 서버 복구보다 **업무 상태의 정확한 복구**가 더 어려운 문제가 될 수 있다.

최종적으로 기억해야 할 원칙은 다음과 같다.

**좋은 Disaster Recovery는 장애 발생 후 서버를 다시 시작하는 절차가 아니다. 실제 고객 신청과 주문 데이터를 보호하고, 필요한 시스템을 올바른 상태로 복원하며, 복구 결과를 기술·업무 관점에서 검증한 뒤 안전하게 서비스를 재개할 수 있는 운영 체계다.**
