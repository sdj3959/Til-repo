## 1. 고객이 경험한 오류를 개발자가 직접 확인할 수 있을까?

### ✅ 1. 1031과의 연결

1031에서는 서비스 안정성과 실제 신청 완료율을 연결하는 방법을 다뤘다.

```text
Customer Journey
       ↓
Funnel Events
       ↓
Submit Attempt
       ↓
Server-side Result
       ↓
Business SLI
       ↓
Conversion KPI
       ↓
Incident Impact
```

이번 1101에서는 한 가지 문제를 더 깊게 다룬다.

**고객의 신청이 실패했을 때 어떤 브라우저에서, 어느 화면에서, 어떤 동작을 수행하다가 문제가 발생했는지 어떻게 알아낼 수 있을까?**

### ✅ 2. 실제 고객 문의

예를 들어 고객이 다음과 같이 문의했다고 하자.

```text
휴대폰 신청하려고 하는데
계속 안 넘어가요.
```

개발자 입장에서는 정보가 부족하다.

### ✅ 3. 추가로 확인해야 하는 정보

```text
사용한 기기

브라우저

접속한 페이지

실패한 API

서버 처리 결과

애플리케이션 버전
```

### ✅ 4. 기존 방식

고객에게 스크린샷을 요청하고 개발자가 직접 같은 조건을 재현한다.

하지만 문제가 특정 기기나 네트워크 환경에서만 발생하면 재현하기 어려울 수 있다.

```text

       ↓

       ↓

       ↓
```

### ✅ 6. Real User Monitoring이란?

RUM은 실제 사용자의 브라우저나 애플리케이션에서 관측한 성능·오류·사용 경험 정보를 활용하는 모니터링 방식이다.

### ✅ 7. 1030의 Synthetic Monitoring과 차이

Synthetic Monitoring:

```text
자동화된 검사 프로그램이
서비스를 이용해 본다.
```

Real User Monitoring:

```text
실제 고객이 서비스를 이용하면서
발생한 상태를 관측한다.
```

### ✅ 8. RUM의 장점

```text
실제 기기 환경 관측

실제 고객 오류 확인

브라우저별 문제 파악

특정 배포 버전 문제 확인

신청 여정 중단 원인 조사
```

### ✅ 9. RUM의 한계

모든 고객의 모든 행동을 정확히 수집할 수 있는 것은 아니다.

광고 차단기, 네트워크 장애, 동의 상태, 브라우저 정책, 스크립트 초기화 실패 등의 영향을 받는다.

### ✅ 10. 가장 중요한 원칙

**고객의 오류를 분석하기 위해 고객의 개인정보나 신청서 입력값까지 모두 수집할 필요는 없다.**

## 3. Frontend Error의 종류

### ✅ 21. 모든 오류는 같은 문제가 아니다

브라우저 오류를 구분해야 정확한 원인을 찾을 수 있다.

### ✅ 22. Runtime Error

JavaScript 코드 실행 중 발생하는 오류다.

예:

```typescript
const plan = undefined;

console.log(plan.price);
```

### ✅ 23. Unhandled Promise Rejection

처리되지 않은 Promise 실패다.

예:

```typescript
async function loadProduct() {
  throw new Error('PRODUCT_LOAD_FAILED');
}

loadProduct();
```

### ✅ 24. React Rendering Error

컴포넌트를 렌더링하는 과정에서 발생하는 오류다.

### ✅ 25. API Error

서버가 오류 상태를 반환하거나 네트워크 요청에 실패한 경우다.

### ✅ 26. Chunk Load Error

배포 이후 JavaScript 파일을 가져오지 못하는 상황이다.

예:

```text
고객이 구버전 페이지 사용

↓

새 버전 배포

↓

이전 JavaScript Chunk 요청

↓

파일을 찾을 수 없음
```

### ✅ 27. Resource Load Error

JavaScript, CSS, 이미지 등 정적 리소스를 불러오지 못하는 경우다.

### ✅ 28. Interaction Error

사용자가 특정 버튼이나 Dropdown을 사용하는 과정에서 문제가 발생하는 경우다.

### ✅ 29. Business Validation Error

업무 규칙에 따라 요청이 거부된 경우다.

### ✅ 30. 정상적인 Validation과 장애는 다르다

예를 들어 휴대폰 번호 형식이 잘못됐다는 안내는 정상적인 Validation일 수 있다.

하지만 정상 입력을 해도 다음 단계로 진행하지 못한다면 결함을 의심해야 한다.

### ✅ 31. 권장 Error Taxonomy

```text
RUNTIME_EXCEPTION

UNHANDLED_REJECTION

REACT_RENDER_ERROR

API_SERVER_ERROR

API_NETWORK_ERROR

API_CONTRACT_ERROR

CHUNK_LOAD_FAILURE

RESOURCE_LOAD_FAILURE

INTERACTION_FAILURE

BUSINESS_VALIDATION
```

### ✅ 32. 중요

오류 유형은 단순한 문자열이 아니라 사전에 정의된 Enum 또는 Error Code로 관리하는 것이 좋다.

## 4. React Error Boundary

### ✅ 33. Error Boundary란?

React 컴포넌트 렌더링 과정에서 발생하는 일부 오류를 포착하고 해당 UI 영역을 대체 화면으로 표시하는 기능이다.

### ✅ 34. Error Boundary가 없다면?

```text
Application Modal
       ↓
React Rendering Error
       ↓
화면 일부 또는 전체 표시 실패
```

가 발생할 수 있다.

### ✅ 35. Error Boundary를 사용하면?

```text
Application Modal
       ↓
React Rendering Error
       ↓
Error Boundary
       ↓
Fallback UI
       ↓
Error Report
```

처럼 처리할 수 있다.

### ✅ 36. React 공식 동작

Error Boundary는 일반적으로 자식 컴포넌트의 렌더링 오류를 처리한다.

### ✅ 37. 하지만 모든 오류를 잡지는 못한다

대표적으로 다음 오류는 일반적인 Error Boundary만으로 포착되지 않는다.

```text
Event Handler Error

일반적인 비동기 Callback Error

일부 Promise Error

Server-side Rendering Error

Error Boundary 자체 오류
```

### ✅ 38. 따라서 Error Boundary만 설치하면 끝일까?

아니다.

전역 오류 수집과 API 오류 추적을 별도로 구성해야 한다.

## 5. React Error Boundary 코드

### ✅ 39. TypeScript 예시

```tsx
import React from 'react';

interface Props {
  children: React.ReactNode;
  fallback: React.ReactNode;
}

interface State {
  hasError: boolean;
}

export class CriticalJourneyBoundary
  extends React.Component<Props, State> {

  state: State = {
    hasError: false,
  };

  static getDerivedStateFromError(): State {
    return {
      hasError: true,
    };
  }

  componentDidCatch(error: Error): void {
    reportFrontendError({
      category: 'REACT_RENDER_ERROR',
      errorCode: 'REACT_COMPONENT_CRASH',
      routeKey: 'APPLICATION',
      componentKey: 'APPLICATION_MODAL',
    });
  }

  render() {
    if (this.state.hasError) {
      return this.props.fallback;
    }

    return this.props.children;
  }
}
```

`reportFrontendError`는 이후 정의할 제한된 Telemetry 함수다.

### ✅ 40. 사용 예시

```tsx
<CriticalJourneyBoundary
  fallback={
    <div role="alert">
      신청 화면을 표시하지 못했습니다.
      페이지를 새로고침한 뒤 다시 시도해 주세요.
    </div>
  }
>
  <ApplicationModal />
</CriticalJourneyBoundary>
```

### ✅ 41. 중요한 설계

Error Boundary를 전체 App에 하나만 두는 것보다 실제 업무 기능에 맞춰 일부 영역에 배치하는 것이 유리할 수 있다.

### ✅ 42. 예시

```text
Application
    ↓
Global Boundary
    ├── Product Page
    ├── Review Section Boundary
    └── Application Modal Boundary
```

### ✅ 43. 장점

리뷰 영역에 문제가 발생해도 신청 모달까지 사용할 수 없게 되는 상황을 줄일 수 있다.

### ✅ 44. 주의

Fallback 화면이 표시된다고 오류가 해결된 것은 아니다.

### ✅ 45. 운영상 필요

오류를 기록하고 실제 사용자에게 재시도 또는 안전한 대체 경로를 안내한다.

### ✅ 46. 개인정보 보호

실제 `error.message`, `error.stack`, `componentStack`에는 민감한 값이 들어갈 가능성이 있다.

처음부터 원문 전체를 외부 Telemetry로 전송하지 않는다.

## 6. 브라우저 전역 오류 수집

### ✅ 47. Window Error Event

브라우저는 처리되지 않은 일부 오류에 대해 `error` 이벤트를 발생시킨다.

### ✅ 48. 기본 구조

```typescript
window.addEventListener('error', (event) => {
  // 오류 처리
});
```

### ✅ 49. Unhandled Rejection

```typescript
window.addEventListener(
  'unhandledrejection',
  (event) => {
    // Promise 오류 처리
  },
);
```

### ✅ 50. 왜 두 개를 함께 사용해야 할까?

JavaScript 실행 오류와 처리되지 않은 Promise 오류는 발생 경로가 다르기 때문이다.

### ✅ 51. Resource Error

이미지나 Script 로딩 실패는 일반적인 `ErrorEvent`와 다른 이벤트 형태로 전달될 수 있다.

### ✅ 52. Script Error와 Resource Error 구분

```text
RUNTIME_EXCEPTION

RESOURCE_LOAD_FAILURE
```

로 분리한다.

### ✅ 53. Global Handler의 역할

오류를 중앙에서 수집한다.

### ✅ 54. Global Handler가 보장하지 않는 것

모든 오류를 반드시 포착하거나 실제 고객의 화면 상태를 완벽하게 복원하는 기능은 아니다.

### ✅ 55. 특히 Cross-origin Script

브라우저 보안 정책에 따라 일부 오류의 상세 내용이 제한되거나 이벤트가 전달되지 않을 수 있다.

## 7. 개인정보 최소화 Telemetry Event

### ✅ 56. 처음부터 Raw Error를 저장하지 않는다

다음과 같은 이벤트를 권장한다.

```json
{
  "eventId": "synthetic-example-001",
  "category": "API_NETWORK_ERROR",
  "errorCode": "APPLICATION_SUBMIT_NETWORK_FAILED",
  "routeKey": "APPLICATION",
  "componentKey": "APPLICATION_MODAL",
  "applicationVersion": "build-123"
}
```

가상 데이터다.

### ✅ 57. 핵심 필드

```text
eventId

category

errorCode

routeKey

componentKey

applicationVersion

occurredAt
```

### ✅ 58. routeKey

실제 URL 전체가 아니라 사전에 정의된 화면 구분이다.

예:

```text
HOME

PRODUCT_LIST

PRODUCT_DETAIL

APPLICATION

ADMIN_ORDER_LIST
```

### ✅ 59. 위험한 수집

```text
/product?name=홍길동&phone=010...
```

같은 URL 전체를 그대로 저장하면 개인정보가 유출될 수 있다.

### ✅ 60. 안전한 방식

```text
routeKey:
PRODUCT_DETAIL
```

처럼 화면 유형만 기록한다.

### ✅ 61. componentKey

```text
PRODUCT_CARD

PLAN_SELECTOR

APPLICATION_MODAL

SUBMIT_BUTTON
```

처럼 정해진 컴포넌트 이름을 사용한다.

### ✅ 62. Error Code

```text
APPLICATION_SUBMIT_NETWORK_FAILED
```

와 같이 구조화한다.

### ✅ 63. Error Message는?

초기에는 자유 형식의 오류 메시지를 전송하지 않는 것을 권장한다.

### ✅ 64. 이유

개발자가 실수로 Error Message에 실제 신청서 값이나 API 응답을 포함했을 수 있기 때문이다.

## 8. TypeScript Telemetry Schema

### ✅ 65. 이벤트 타입 정의

```typescript
type ErrorCategory =
  | 'RUNTIME_EXCEPTION'
  | 'UNHANDLED_REJECTION'
  | 'REACT_RENDER_ERROR'
  | 'API_NETWORK_ERROR'
  | 'API_SERVER_ERROR'
  | 'API_CONTRACT_ERROR'
  | 'RESOURCE_LOAD_FAILURE'
  | 'INTERACTION_FAILURE';

type RouteKey =
  | 'HOME'
  | 'PRODUCT_LIST'
  | 'PRODUCT_DETAIL'
  | 'APPLICATION'
  | 'UNKNOWN';

type ComponentKey =
  | 'GLOBAL'
  | 'PRODUCT_CARD'
  | 'PLAN_SELECTOR'
  | 'APPLICATION_MODAL'
  | 'SUBMIT_BUTTON';

interface FrontendErrorInput {
  category: ErrorCategory;

  errorCode: string;

  routeKey: RouteKey;

  componentKey: ComponentKey;

  requestId?: string;

  httpStatus?: number;
}
```

### ✅ 66. 전송 이벤트

```typescript
interface FrontendErrorEvent
  extends FrontendErrorInput {

  eventId: string;

  applicationVersion: string;

  occurredAt: string;
}
```

### ✅ 67. Client 식별자는?

처음에는 영구적인 User ID를 전송하지 않아도 오류 분석을 시작할 수 있다.

### ✅ 68. Journey Correlation

필요하다면 짧은 수명의 무작위 Journey ID를 추가한다.

### ✅ 69. 주의

Journey ID도 다른 데이터와 결합하면 개인의 이용 흐름을 추적하는 식별자가 될 수 있다.

수집 목적과 보관기간, 접근권한을 명확히 정한다.

## 9. 안전한 오류 전송 함수

### ✅ 70. 기본 전송

```typescript
const TELEMETRY_ENDPOINT = '/api/telemetry/errors';

const MAX_EVENTS_PER_PAGE = 10;

let sentEvents = 0;

export function reportFrontendError(
  input: FrontendErrorInput,
): void {
  if (sentEvents >= MAX_EVENTS_PER_PAGE) {
    return;
  }

  sentEvents += 1;

  const payload: FrontendErrorEvent = {
    ...input,

    eventId: crypto.randomUUID(),

    applicationVersion:
      import.meta.env.VITE_APP_VERSION ?? 'unknown',

    occurredAt: new Date().toISOString(),
  };

  void fetch(TELEMETRY_ENDPOINT, {
    method: 'POST',

    headers: {
      'Content-Type': 'application/json',
    },

    body: JSON.stringify(payload),

    keepalive: true,
  }).catch(() => {
    // Telemetry 전송 실패가
    // 실제 고객 업무를 막지 않도록 처리한다.
  });
}
```

### ✅ 71. 이 코드의 역할

오류를 제한된 구조로 전송한다.

### ✅ 72. MAX_EVENTS_PER_PAGE

한 페이지에서 너무 많은 오류가 발생할 때 이벤트 폭주를 제한하기 위한 간단한 장치다.

### ✅ 73. 보안상 한계

클라이언트의 제한은 쉽게 우회할 수 있다.

서버에서도 Rate Limit과 Payload 제한을 적용해야 한다.

### ✅ 74. 중요한 설계

Telemetry 요청 자체가 실패하더라도 같은 Telemetry 함수를 재귀적으로 호출하지 않도록 해야 한다.

### ✅ 75. 예시

```text
Telemetry Request Failed

↓

Telemetry Error Report

↓

Telemetry Request Failed

↓

무한 반복
```

이 되면 안 된다.

### ✅ 76. 실제 적용

기존 Axios 또는 Fetch Interceptor가 Telemetry Endpoint의 오류를 다시 수집하지 않도록 제외한다.

### ✅ 77. Sampling

이벤트량이 많아지면 오류 유형별 수집 비율을 정의할 수 있다.

단 고객에게 직접 피해를 주는 심각한 오류는 샘플링 정책을 별도로 검토한다.

### ✅ 78. 주의

위 코드는 개념 설명용으로, 실제 Consent 및 Telemetry 활성화 정책을 확인하는 조건이 추가돼야 한다.

## 10. 전역 Handler 구현

### ✅ 79. 초기 구현

```typescript
export function installGlobalErrorHandlers(): () => void {
  const onError = (event: Event) => {
    const category =
      event instanceof ErrorEvent
        ? 'RUNTIME_EXCEPTION'
        : 'RESOURCE_LOAD_FAILURE';

    reportFrontendError({
      category,
      errorCode:
        category === 'RUNTIME_EXCEPTION'
          ? 'UNCAUGHT_SCRIPT_ERROR'
          : 'RESOURCE_LOAD_FAILED',
      routeKey: 'UNKNOWN',
      componentKey: 'GLOBAL',
    });
  };

  const onUnhandledRejection = () => {
    reportFrontendError({
      category: 'UNHANDLED_REJECTION',
      errorCode: 'UNHANDLED_PROMISE_REJECTION',
      routeKey: 'UNKNOWN',
      componentKey: 'GLOBAL',
    });
  };

  window.addEventListener(
    'error',
    onError,
    true,
  );

  window.addEventListener(
    'unhandledrejection',
    onUnhandledRejection,
  );

  return () => {
    window.removeEventListener(
      'error',
      onError,
      true,
    );

    window.removeEventListener(
      'unhandledrejection',
      onUnhandledRejection,
    );
  };
}
```

### ✅ 80. Capture Phase

일부 정적 리소스의 `error` 이벤트는 일반적인 방식으로 Bubble되지 않으므로 Capture Listener를 활용할 수 있다.

### ✅ 81. 코드의 한계

이 예시는 오류의 종류만 기록한다.

정확한 문제가 발생한 Route나 Component를 찾으려면 별도 Context가 필요하다.

### ✅ 82. 실제 프로젝트에서는

React Router나 현재 Application State에서 허용된 `routeKey`를 제공하도록 연결할 수 있다.

### ✅ 83. 중요한 주의

개발 모드에서는 React 오류가 전역 Handler에도 전달될 수 있어 같은 오류가 중복 수집될 수 있다.

### ✅ 84. Production과 Development 동작 차이

React Error Boundary에 의해 처리된 오류가 전역 Handler로 전달되는 방식은 개발·운영 환경에서 다를 수 있다.

### ✅ 85. 따라서

중복 오류 제거와 환경별 테스트가 필요하다.

## 12. NestJS Request ID Middleware

### ✅ 93. 서버에서 ID 생성

```typescript
import {
  Injectable,
  NestMiddleware,
} from '@nestjs/common';

import {
  Request,
  Response,
  NextFunction,
} from 'express';

import { randomUUID } from 'node:crypto';

@Injectable()
export class RequestIdMiddleware
  implements NestMiddleware {

  use(
    req: Request,
    res: Response,
    next: NextFunction,
  ): void {
    const requestId = randomUUID();

    res.locals.requestId = requestId;

    res.setHeader(
      'X-Request-ID',
      requestId,
    );

    next();
  }
}
```

### ✅ 94. 목적

각 HTTP 요청에 서버가 생성한 식별자를 부여한다.

### ✅ 95. 실제 구현 시

Request Scope 또는 AsyncLocalStorage를 사용하면 Service와 Logger에 Request ID를 전달하기 편리할 수 있다.

### ✅ 96. CORS

Frontend와 Backend가 서로 다른 Origin이라면 브라우저가 `X-Request-ID` 응답 Header를 읽을 수 있도록 `Access-Control-Expose-Headers` 설정이 필요할 수 있다.

### ✅ 97. Header 노출 예시

```typescript
app.enableCors({
  origin: ['https://approved-frontend.example'],

  exposedHeaders: [
    'X-Request-ID',
  ],
});
```

위 도메인은 설명용이며 실제 운영 Origin으로 대체해야 한다.

### ✅ 98. 보안 주의

현재 프로젝트의 Cookie, Credentials, CORS 설정을 확인하지 않고 위 코드를 그대로 덮어쓰지 않는다.

### ✅ 99. 중요한 원칙

Request ID는 진단용 메타데이터다.

인증 토큰이나 권한 증명으로 사용하지 않는다.

## 13. React API Error 수집

### ✅ 100. Fetch Wrapper 예시

```typescript
type RouteKey =
  | 'PRODUCT_DETAIL'
  | 'APPLICATION';

interface ApiRequestContext {
  routeKey: RouteKey;
  componentKey: 'PLAN_SELECTOR' | 'SUBMIT_BUTTON';
}

async function apiRequest(
  url: string,
  options: RequestInit,
  context: ApiRequestContext,
): Promise<Response> {
  if (url === '/api/telemetry/errors') {
    return fetch(url, options);
  }

  try {
    const response = await fetch(url, options);

    if (response.status >= 500) {
      reportFrontendError({
        category: 'API_SERVER_ERROR',
        errorCode: 'API_HTTP_5XX',
        routeKey: context.routeKey,
        componentKey: context.componentKey,
        requestId:
          response.headers.get('X-Request-ID')
          ?? undefined,
        httpStatus: response.status,
      });
    }

    return response;
  } catch (error) {
    reportFrontendError({
      category: 'API_NETWORK_ERROR',
      errorCode: 'API_REQUEST_FAILED',
      routeKey: context.routeKey,
      componentKey: context.componentKey,
    });

    throw error;
  }
}
```

### ✅ 101. 이 코드의 목적

API 실패와 서버 Request ID를 연결한다.

### ✅ 102. 중요한 한계

`fetch`는 HTTP 4xx·5xx 응답만으로 Promise를 Reject하지 않는다.

따라서 HTTP 상태를 직접 검사해야 한다.

### ✅ 103. Business Error

HTTP 200이어도 업무적으로 실패한 응답이 있을 수 있다.

별도의 API Contract와 Business Result Validation이 필요하다.

### ✅ 104. Request Aborted

사용자가 페이지를 이동해 요청이 취소된 상황을 일반적인 네트워크 장애와 구분해야 한다.

### ✅ 105. Timeout

현재 프로젝트의 AbortController 및 Timeout 정책을 확인한다.

### ✅ 106. 실패한 API URL을 그대로 기록할까?

권장하지 않는다.

### ✅ 107. 이유

URL Path나 Query String에 고객 식별자 또는 개인정보가 포함될 수 있다.

### ✅ 108. 대안

```text
API_OPERATION:
APPLICATION_SUBMIT
```

처럼 정해진 API Operation ID를 기록한다.

### ✅ 109. 실제 개선

현재 Axios / Fetch Client가 있다면 중복 Wrapper를 만들지 않고 기존 Interceptor에 연결하는 편이 좋다.

## 25. 오류 Grouping SQL

### ✅ 223. 목표

어떤 오류가 많이 발생하고 있는지 확인한다.

### ✅ 224. PostgreSQL 예시

```sql
SELECT
  error_fingerprint,

  category,

  error_code,

  route_key,

  component_key,

  COUNT(*) AS occurrences,

  COUNT(DISTINCT journey_id)
    AS affected_journeys,

  MIN(received_at) AS first_seen,

  MAX(received_at) AS last_seen

FROM frontend_error_events

WHERE received_at >= $1
  AND received_at < $2

GROUP BY
  error_fingerprint,
  category,
  error_code,
  route_key,
  component_key

ORDER BY occurrences DESC;
```

### ✅ 225. Occurrences

오류 발생 횟수다.

### ✅ 226. Affected Journeys

오류가 관측된 고유 Journey 수다.

### ✅ 227. 주의

Journey ID가 없는 이벤트는 `COUNT(DISTINCT journey_id)`에 포함되지 않는다.

### ✅ 228. 따라서

전체 오류 횟수와 Journey 연결 가능 비율을 따로 관리한다.

### ✅ 229. 샘플링이 있다면?

수집된 오류 건수는 전체 실제 발생 횟수와 다를 수 있다.

Sampling Rate를 기록하고 필요한 경우 추정 지표를 별도로 계산한다.

### ✅ 230. 정확한 실제 고객 수

Journey ID만으로 실제 고유 고객 수를 완전히 파악할 수 있는 것은 아니다.

## 26. Journey 영향 분석 SQL

### ✅ 231. 목표

오류를 경험한 Journey와 그렇지 않은 Journey의 신청 완료 비율을 비교한다.

### ✅ 232. 가정

다음 테이블이 존재한다고 하자.

```text

frontend_error_events
```

### ✅ 233. customer_journeys 예시 필드

```text
journey_id

started_at

completed_at

application_created
```

### ✅ 234. SQL 예시

```sql
WITH error_exposure AS (
  SELECT DISTINCT
    journey_id

  FROM frontend_error_events

  WHERE journey_id IS NOT NULL
    AND received_at >= $1
    AND received_at < $2
)

SELECT
  CASE
    WHEN e.journey_id IS NOT NULL
      THEN 'ERROR_EXPOSED'
    ELSE 'NO_OBSERVED_ERROR'
  END AS group_name,

  COUNT(*) AS total_journeys,

  COUNT(*) FILTER (
    WHERE j.application_created = TRUE
  ) AS completed_journeys,

  ROUND(
    100.0
    * COUNT(*) FILTER (
        WHERE j.application_created = TRUE
      )
    / NULLIF(COUNT(*), 0),
    2
  ) AS completion_rate

FROM customer_journeys j

LEFT JOIN error_exposure e
  ON e.journey_id = j.journey_id

WHERE j.started_at >= $1
  AND j.started_at < $2

GROUP BY group_name;
```

### ✅ 235. 주의

이 SQL은 구조 설명용이다.

실제 Table과 Field가 없다면 그대로 실행할 수 없다.

### ✅ 236. 중요한 해석

```text
NO_OBSERVED_ERROR
```

는 오류가 없었다는 확정적 의미가 아니다.

### ✅ 237. 이유

Telemetry를 수집하지 못했거나 브라우저에서 차단됐을 수 있기 때문이다.

### ✅ 238. Cohort

신청 완료까지 일정 시간이 필요하다면 충분히 시간이 지난 Journey만 분석해야 한다.

### ✅ 239. 인과관계

이 비교만으로 오류가 신청 포기의 직접 원인이라고 단정하지 않는다.

## 28. PerformanceObserver 예시

### ✅ 250. Long Task 관측

```typescript
export function observeLongTasks(): () => void {
  if (
    !PerformanceObserver.supportedEntryTypes.includes(
      'longtask',
    )
  ) {
    return () => {};
  }

  const observer = new PerformanceObserver((list) => {
    for (const entry of list.getEntries()) {
      if (entry.duration < 200) {
        continue;
      }

      reportPerformanceMetric({
        metric: 'LONG_TASK',
        value: entry.duration,
        routeKey: 'APPLICATION',
      });
    }
  });

  observer.observe({
    type: 'longtask',
    buffered: true,
  });

  return () => observer.disconnect();
}
```

`reportPerformanceMetric`은 프로젝트에서 정의할 제한된 Metric 수집 함수다.

1101에서는 실제 고객의 브라우저에서 발생하는 오류를 추적하고 문제의 원인을 조사하는 방법을 다뤘다.

```text
Real User Browser
        ↓
Journey Context
        ↓
Frontend Error
        ↓
Error Classification
        ↓
Request ID
        ↓
NestJS Backend Logs
        ↓
Application Outcome
        ↓
Error Grouping
        ↓
Business Impact
        ↓

```

가장 중요한 원칙은 다음과 같다.

**첫 번째 — Frontend 오류도 운영 장애다.**

서버가 정상이어도 고객의 실제 신청 절차는 실패할 수 있다.

**두 번째 — React Error Boundary만으로 모든 오류를 처리할 수 없다.**

```text
React Error Boundary

+

Global Error Handler

+

Unhandled Rejection

+

API Error Interceptor
```

를 상황에 맞게 구성한다.

**세 번째 — Frontend와 Backend를 Request ID로 연결한다.**

```text
Frontend Error

↓

Request ID

↓

Backend Log

↓

Database / Service Error
```

구조를 마련한다.

**네 번째 — 모든 오류 원문을 수집하지 않는다.**

개인정보와 Secret이 포함될 수 있으므로 구조화된 Error Code와 Route Key를 우선한다.

**다섯 번째 — 오류 수와 실제 고객 피해를 구분한다.**

같은 고객이 오류를 여러 번 경험하거나 한 번의 오류로 구매를 완전히 포기할 수 있기 때문이다.

**여섯 번째 — Session Replay는 필수가 아니다.**

```text
Journey Timeline

+

Error Event

+

Request ID
```

만으로도 많은 장애를 조사할 수 있다.

**일곱 번째 — 오류를 비즈니스 지표와 연결한다.**

오류가 실제 고객의 신청 완료에 어떤 영향을 미쳤는지 분석한다.

현재 투게더몰에서는 다음 다섯 가지가 우선이다.

```text
1. React 신청 모달 Error Boundary

2. NestJS Request ID와 Frontend API 연결

3. 개인정보 없는 Structured Error Event

4. Error Fingerprinting 및 Release Version

5. 신청 Journey와 오류를 연결한 Dashboard
```

이 다섯 가지만 구축해도 다음과 같은 질문에 답하기 쉬워진다.

```text
특정 모바일 브라우저에서만
신청 오류가 발생하는가?

어느 배포 이후 오류가 시작됐는가?

어떤 API 요청이 실패했는가?

오류가 발생한 뒤
실제 주문이 생성됐는가?

고객이 가장 자주 막히는 단계는 어디인가?
```

처음부터 대규모 Monitoring Platform이나 Full Session Replay를 도입할 필요는 없다.

기존 React·NestJS·PostgreSQL·AWS 환경을 활용해 구조화된 오류 수집과 Correlation을 먼저 구현하는 것이 현실적이다.

그리고 최종적으로 기억해야 할 가장 중요한 원칙은 다음과 같다.

**좋은 오류 모니터링은 고객의 모든 정보를 수집하는 시스템이 아니다. 고객이 어떤 기능에서 문제를 경험했는지, 어떤 기술적 원인이 있었는지, 실제 업무에 어떤 영향을 미쳤는지를 필요한 최소한의 데이터로 확인할 수 있는 시스템이다.**
