## 2. 테스트 환경을 구성하는 다섯 가지 요소

### ✅ 9. 첫 번째 — Application Code

검증하려는 실제 코드다.

### ✅ 10. 두 번째 — Runtime

Node.js, pnpm, OS, Browser 등의 실행 환경이다.

### ✅ 11. 세 번째 — Database

테스트에 필요한 Schema와 데이터다.

### ✅ 12. 네 번째 — External Dependencies

외부 인증, 알림, 파일 저장, 광고 API 등이다.

### ✅ 13. 다섯 번째 — Test Harness

Fixture 생성, Test Runner, Setup, Cleanup, Assertion 등을 담당한다.

### ✅ 14. 전체 구조

```text
Test Runner
     ↓
Application Under Test
     ↓
Database
     ↓
External Provider Mock
     ↓
Assertions
     ↓
Cleanup
```

### ✅ 15. 테스트가 신뢰할 수 있으려면

이 구성 요소들의 상태가 예측 가능해야 한다.

### ✅ 16. 중요한 구분

동일한 테스트 결과를 재현한다는 것은 모든 내부 작업이 항상 같은 순서로 실행된다는 뜻은 아니다.

동시성 테스트에서는 실제 실행 순서가 달라지더라도 **최종 업무 불변조건이 항상 유지되는지** 검증해야 한다.

## 3. Deterministic Test Data란?

### ✅ 17. 정의

동일한 테스트 조건에서 기대 결과를 명확하게 계산하고 재현할 수 있도록 설계한 데이터다.

### ✅ 18. 잘못된 테스트 데이터

```typescript
const price = Math.floor(Math.random() * 100000);
```

### ✅ 19. 문제

실행할 때마다 가격이 달라진다.

### ✅ 20. 따라서

테스트 실패를 재현하기 어려울 수 있다.

### ✅ 21. 고정된 Test Fixture

```typescript
const product = {
  code: 'TEST_DEVICE_001',
  basePrice: 1_200_000,
  discount: 200_000,
};
```

### ✅ 22. Expected Result

```typescript
const expectedPrice = 1_000_000;
```

### ✅ 23. 장점

가격 계산 로직이 잘못됐을 때 실제 기대값을 기준으로 오류를 발견할 수 있다.

### ✅ 24. 주의

테스트 대상 함수를 그대로 호출해 기대값을 계산해서는 안 된다.

### ✅ 25. 위험한 코드

```typescript
const expected = calculatePrice(product);

const actual = calculatePrice(product);

expect(actual).toBe(expected);
```

### ✅ 26. 올바른 방식

승인된 업무 규칙이나 독립적으로 검증된 Fixture를 기준으로 기대값을 작성한다.

### ✅ 27. 핵심

**Test Data는 예측 가능해야 하고 Expected Result는 테스트 대상의 잘못된 구현에 의존해서는 안 된다.**

## 4. 고정 데이터와 고유 데이터는 다르다

### ✅ 28. 모든 테스트 데이터를 고정 ID로 만들면?

여러 테스트에서 충돌할 수 있다.

### ✅ 29. 예시

```text
Test A:
ORDER-TEST-001

Test B:
ORDER-TEST-001
```

### ✅ 30. 병렬 실행

```text
Worker A
Order 생성

Worker B
같은 Order 생성

↓

Unique Constraint Error
```

### ✅ 31. 해결

**업무 값은 결정적으로 구성하고, 데이터 식별자는 테스트 실행마다 고유하게 생성한다.**

### ✅ 32. 예시

```typescript
import { randomUUID } from 'node:crypto';

function makeTestProduct() {
  return {
    id: randomUUID(),
    code: `TEST_${randomUUID()}`,
    basePrice: 1_200_000,
    discount: 200_000,
  };
}
```

### ✅ 33. 중요한 부분

가격과 할인 조건은 고정돼 있다.

### ✅ 34. 식별자만 고유하다

따라서 여러 테스트가 데이터를 생성해도 충돌 가능성을 줄일 수 있다.

### ✅ 35. Random UUID의 역할

테스트 격리와 충돌 방지다.

### ✅ 36. 실제 비즈니스 기대값

무작위 생성된 ID가 아니라 별도로 정의된 업무 조건을 검증한다.

## 5. Test Data Factory

### ✅ 37. Factory란?

테스트에 필요한 데이터를 일관된 방식으로 생성하는 함수를 말한다.

### ✅ 38. Factory가 없다면?

각 테스트마다 비슷한 데이터를 직접 작성하게 된다.

```text
Test A
상품 데이터 직접 작성

Test B
상품 데이터 직접 작성

Test C
상품 데이터 직접 작성
```

### ✅ 39. 문제

필수 필드가 추가되거나 Schema가 변경되면 여러 테스트를 수정해야 한다.

### ✅ 40. Factory 도입

```text
Test
  ↓
Data Factory
  ↓
Synthetic Product
```

### ✅ 41. 예시

```typescript
interface ProductFixture {
  id: string;
  code: string;
  name: string;
  basePrice: number;
  discount: number;
}

function makeProductFixture(
  overrides: Partial<ProductFixture> = {},
): ProductFixture {
  return {
    id: crypto.randomUUID(),

    code: `TEST_${crypto.randomUUID()}`,

    name: '테스트 휴대폰',

    basePrice: 1_200_000,

    discount: 200_000,

    ...overrides,
  };
}
```

### ✅ 42. 특정 조건 테스트

```typescript
const product = makeProductFixture({
  basePrice: 1_500_000,
  discount: 300_000,
});
```

### ✅ 43. 장점

기본 데이터는 재사용하면서 필요한 조건만 변경할 수 있다.

### ✅ 44. 주의

Fixture Factory가 실제 주문이나 알림을 생성하는 Production API를 호출해서는 안 된다.

### ✅ 45. 권장

Unit Test용 순수 데이터 Factory와 Integration Test용 DB Factory를 구분한다.

## 6. Fixture와 Seed의 차이

### ✅ 46. Seed Data

애플리케이션이나 환경에 필요한 기본 데이터를 생성하는 용도다.

예:

```text
기본 시스템 설정

테스트용 요금제 목록

테스트 상품 카탈로그

업무 코드 테이블
```

### ✅ 47. Test Fixture

특정 테스트가 실행되기 위해 필요한 상태를 구성한다.

예:

```text
취소 가능한 주문

미승인 알림

만료된 쿠폰

중복 제출 Attempt
```

### ✅ 48. Seed는 환경 단위

```text
Database Created
       ↓
Migration
       ↓
Base Seed
```

### ✅ 49. Fixture는 테스트 단위

```text
Test Started
       ↓
Fixture Created
       ↓
Assertion
       ↓
Fixture Cleanup
```

### ✅ 50. 모든 Fixture를 Seed에 넣을까?

권장하지 않는다.

### ✅ 51. 이유

서로 다른 테스트가 같은 Seed 데이터를 변경하면서 충돌할 수 있기 때문이다.

### ✅ 52. 좋은 구조

```text
Static Reference Data
        ↓
Environment Seed

Dynamic Test Data
        ↓
Per-test Fixture
```

### ✅ 53. 중요한 원칙

**공통 기준 데이터와 테스트마다 변경되는 업무 데이터를 분리한다.**

## 7. Prisma Seed의 역할

### ✅ 54. Prisma는 Seed 기능을 제공한다

대표적인 명령은 다음과 같다.

```bash
pnpm exec prisma db seed
```

### ✅ 55. 단 버전별 설정이 다를 수 있다

현재 프로젝트의 Prisma CLI 버전을 확인해야 한다.

```bash
pnpm exec prisma -v
```

### ✅ 56. Prisma 7 기준

`prisma.config.ts`의 `migrations.seed`에 Seed 명령을 정의할 수 있다.

### ✅ 57. 예시

```typescript
import { defineConfig, env } from 'prisma/config';

export default defineConfig({
  schema: 'prisma/schema.prisma',

  migrations: {
    path: 'prisma/migrations',

    seed: 'tsx prisma/seed.ts',
  },

  datasource: {
    url: env('DATABASE_URL'),
  },
});
```

### ✅ 58. 중요한 주의

이 설정은 Prisma 7 기준의 개념 예시다.

현재 프로젝트에 `prisma.config.ts`가 이미 있다면 기존 설정을 확인해야 한다.

### ✅ 59. Prisma 7의 변경 사항

`migrate dev`나 `migrate reset` 이후 Seed가 자동으로 실행되는 기존 동작이 제거됐다.

### ✅ 60. 따라서

필요한 환경에서 Seed를 명시적으로 실행한다.

### ✅ 61. 프로젝트 버전 확인

Prisma 버전이 다르다면 해당 버전의 공식 문서와 실제 CLI를 기준으로 명령을 결정한다.

### ✅ 62. 중요한 원칙

**Seed 명령은 안전한 Test DB가 확인된 이후에만 실행해야 한다.**

## 8. Migration과 Seed의 실행 순서

### ✅ 63. 기본 순서

```text
Test Database
       ↓
Migration
       ↓
Base Seed
       ↓
Test Fixtures
       ↓
Tests
```

### ✅ 64. Migration

DB 구조를 생성하거나 변경한다.

### ✅ 65. Seed

필요한 기본 데이터를 넣는다.

### ✅ 66. Fixture

특정 테스트가 필요한 상태를 만든다.

### ✅ 67. 실행 순서가 중요한 이유

필요한 테이블이 생성되기 전에 Seed를 실행할 수 없기 때문이다.

### ✅ 68. 예시

```text
Migration
요금제 테이블 생성

↓

Seed
기본 테스트 요금제 생성

↓

Fixture
특정 상품에 요금제 연결
```

### ✅ 69. 주의

`prisma migrate deploy`는 적용할 Migration을 실행하지만 자동으로 테스트 데이터를 생성해 주지는 않는다.

### ✅ 70. 현재 권장

**테스트 환경 생성과 Migration 적용, Seed 실행, 개별 Fixture 생성을 서로 다른 단계로 기록한다.**

## 9. 테스트 환경의 세 가지 선택지

### ✅ 71. 선택지 A — 기존 개발 DB 공유

```text
Local Development DB
        ↓
Application
        ↓
Tests
```

### ✅ 72. 장점

구축이 간단하다.

### ✅ 73. 단점

개발 중인 데이터와 테스트 데이터가 충돌할 수 있다.

### ✅ 74. 선택지 B — 별도 Test DB

```text
OrbStack PostgreSQL
       ├── together_dev
       └── together_test
```

### ✅ 75. 장점

기존 PostgreSQL Container를 재사용하면서 개발 DB와 테스트 DB를 분리할 수 있다.

### ✅ 76. 주의

동일한 DB 서버를 공유하므로 서버 자원과 관리 권한은 여전히 공유될 수 있다.

### ✅ 77. 선택지 C — Ephemeral Container

```text
Test Started
       ↓
PostgreSQL Container Created
       ↓
Migration
       ↓
Fixture
       ↓
Test
       ↓
Container Removed
```

### ✅ 78. 장점

테스트 실행 환경을 독립적으로 구성하고 삭제하기 쉽다.

### ✅ 79. 단점

컨테이너 생성과 Migration에 시간이 추가된다.

### ✅ 80. 현재 추천

초기에는 별도 Test DB로 시작할 수 있다.

동시성 테스트·CI 재현·환경 격리가 중요해지면 Ephemeral Container를 도입한다.

## 10. 방법별 비교

| 항목 | 개발 DB 공유 | 별도 Test DB | Ephemeral Container |
|---|---|---|---|
| 초기 구축 | 쉬움 | 보통 | 보통~높음 |
| 개발 데이터 격리 | 낮음 | 높음 | 높음 |
| 테스트 간 격리 | 별도 구현 | 별도 구현 | 구성에 따라 높음 |
| 반복 실행 속도 | 빠름 | 빠름 | 시작 비용 발생 |
| CI 재현성 | 낮음 | 보통 | 높음 |
| Cleanup | 위험할 수 있음 | 관리 필요 | 비교적 단순 |
| Migration Test | 가능하지만 위험 | 가능 | 적합 |
| 추천 용도 | 일상 개발 | 초기 Integration | CI·격리 검증 |

### ✅ 81. 중요한 구분

Ephemeral Container를 하나 생성한 뒤 여러 테스트가 공유한다면 **테스트 간 데이터 격리는 여전히 필요하다.**

### ✅ 82. Container Isolation

서버 환경을 격리하는 것이다.

### ✅ 83. Test Isolation

각 테스트의 데이터와 상태를 격리하는 것이다.

### ✅ 84. 두 개념을 혼동하지 않는다

```text
Dedicated Container

≠

Automatically Isolated Tests
```

## 12. 기존 개발 DB와 분리하는 방법

### ✅ 95. 권장 구조

```text
OrbStack

postgres-dev
  └── together_dev

postgres-test
  └── together_test
```

### ✅ 96. 장점

개발 DB와 테스트 DB를 물리적인 Container 단위로 분리할 수 있다.

### ✅ 97. 중요한 조건

각 Container에 서로 다른 Port와 Volume을 사용한다.

### ✅ 98. 예시

```text
Development PostgreSQL
localhost:5432

Test PostgreSQL
localhost:15432
```

### ✅ 99. Port는 예시다

## 14. Production RDS를 테스트에서 배제하기

## 15. 테스트 DB Guard

### ✅ 122. DB Identity Check

PostgreSQL에서 연결된 DB 이름과 사용자를 조회할 수 있다.

### ✅ 123. SQL

```sql
SELECT
  current_database() AS database_name,
  current_user AS database_user;
```

### ✅ 124. 실제 결과 검증

```text
database_name:
together_test

database_user:
test_runner
```

같은 기대값과 비교한다.

### ✅ 125. TypeScript 예시

```typescript
import { Client } from 'pg';

interface TestDbIdentity {
  database_name: string;
  database_user: string;
}

export async function assertTestDatabase(
  connectionString: string,
): Promise<void> {
  if (process.env.NODE_ENV !== 'test') {
    throw new Error('TEST_ENV_REQUIRED');
  }

  const client = new Client({
    connectionString,
  });

  try {
    await client.connect();

    const result = await client.query<TestDbIdentity>(
      `
      SELECT
        current_database() AS database_name,
        current_user AS database_user
      `,
    );

    const identity = result.rows[0];

    if (
      identity?.database_name !== 'together_test' ||
      identity?.database_user !== 'test_runner'
    ) {
      throw new Error('UNAPPROVED_DATABASE_IDENTITY');
    }
  } finally {
    await client.end();
  }
}
```

### ✅ 126. 이 코드의 역할

실제로 연결된 Database Identity가 기대값과 일치하는지 확인한다.

### ✅ 127. 하지만 이것만으로 완벽할까?

아니다.

운영 DB 안에 같은 이름의 DB와 Role이 있거나 SSH Tunnel을 사용한다면 문자열 기반 검증의 한계가 있다.

### ✅ 128. 더 강한 방식

테스트 환경 Provisioner가 생성한 임시 DB 연결 정보를 직접 전달하고, 운영 DB용 Credential 자체를 테스트 프로세스에 제공하지 않는다.

### ✅ 129. 추가 안전장치

Test DB 내부에 Provisioner가 생성한 Test-only Marker를 두고 확인하는 방법도 고려할 수 있다.

### ✅ 130. 중요한 주의

Marker 검사 자체가 Production DB 접근을 불가능하게 만드는 보안 경계는 아니다.

### ✅ 131. 최종 원칙

**Guard는 실수 방지용이고, 실제 차단은 DB 접근권한·네트워크·Credential 분리로 강제한다.**

## 21. Testcontainers PostgreSQL 예제

### ✅ 173. 기본 테스트

```typescript
import {
  PostgreSqlContainer,
} from '@testcontainers/postgresql';

import { Client } from 'pg';

describe('PostgreSQL integration', () => {
  it('독립된 PostgreSQL에 연결한다', async () => {
    const container = await new PostgreSqlContainer(
      'postgres:18-alpine',
    )
      .withDatabase('together_test')
      .withUsername('test_runner')
      .withPassword('test_only_password')

      const client = new Client({

          container.getConnectionUri(),

        await client.connect();

          'SELECT 1 AS value',

        await client.end();
      }
    } finally {
      await container.stop();
    }
  });
});
```

를 이용한다.

을 함께 확인한다.

## 25. Test Environment Lifecycle

### ✅ 213. 중요한 부분

테스트 자체의 실패와 환경 생성 실패를 구분한다.

**DB가 실행되지 않아 테스트를 시작하지 못했다면 제품 테스트가 실패했다고 기록하지 않는다.**

## 27. Fixture Lifecycle

### ✅ 224. 개별 Test Lifecycle

```text
Before Test
      ↓
Fixture Setup
      ↓
Action
      ↓
Assertion
      ↓
Cleanup
```

### ✅ 225. Setup

테스트에 필요한 데이터를 생성한다.

### ✅ 226. Action

실제 검증 대상 기능을 실행한다.

### ✅ 227. Assertion

기대 결과와 실제 결과를 비교한다.

### ✅ 228. Cleanup

테스트가 만든 리소스를 정리한다.

### ✅ 229. 중요한 조건

테스트가 실패해도 Cleanup이 실행돼야 한다.

### ✅ 230. TypeScript 예시

```typescript
it('주문 상태를 확인한다', async () => {
  const fixture = await createTestOrder();

  try {
    const result = await getOrderStatus(
      fixture.orderId,
    );

    expect(result).toBe('PENDING');
  } finally {
    await removeTestOrder(fixture.orderId);
  }
});
```

### ✅ 231. 이 코드는 개념 예시다

`createTestOrder`, `getOrderStatus`, `removeTestOrder`는 실제 프로젝트에 맞게 구현해야 한다.

### ✅ 232. 중요한 주의

Cleanup 함수가 실제 고객 주문을 삭제하는 구조여서는 안 된다.

### ✅ 233. Cleanup 기준

테스트 Provisioner가 생성한 리소스만 정리하도록 설계한다.

## 34. Provider Interface 예시

### ✅ 280. 인터페이스

```typescript
interface NotificationProvider {
  send(input: {
    recipientKey: string;
    templateCode: string;
  }): Promise<{
    status: 'ACCEPTED' | 'REJECTED';
  }>;
}
```

### ✅ 281. Mock

```typescript
class FakeNotificationProvider
  implements NotificationProvider {

  public readonly sent: Array<{
    recipientKey: string;
    templateCode: string;
  }> = [];

  async send(input: {
    recipientKey: string;
    templateCode: string;
  }) {
    this.sent.push(input);

    return {
      status: 'ACCEPTED' as const,
    };
  }
}
```

### ✅ 282. 테스트

```typescript
it('승인된 발송을 한 번 실행한다', async () => {
  const provider = new FakeNotificationProvider();

  // 실제 서비스에서 승인 검증을 수행한 뒤
  // Provider를 호출하는 흐름을 테스트한다.

  await provider.send({
    recipientKey: 'SYNTHETIC_RECIPIENT',
    templateCode: 'TEST_TEMPLATE',
  });

  expect(provider.sent).toHaveLength(1);
});
```

### ✅ 283. 중요한 한계

이 예시는 Fake Provider의 기록 기능만 확인한다.

승인·권한·멱등성이 실제 서비스에서 작동하는지 검증하려면 해당 Service를 통해 테스트해야 한다.

### ✅ 284. 실제 외부 발송

Mock이므로 발생하지 않는다.

### ✅ 285. 중요한 원칙

**Mock 자체를 검증하는 것과 Mock을 연결한 실제 업무 서비스를 검증하는 것은 다르다.**

## 37. GitHub Actions PostgreSQL 예시

### ✅ 301. Workflow 예시

```yaml
name: Backend Integration Tests

on:
  pull_request:

permissions:
  contents: read

jobs:
  integration:
    runs-on: ubuntu-latest

    timeout-minutes: 20

    services:
      postgres:
        image: postgres:18-alpine

        env:
          POSTGRES_USER: test_runner
          POSTGRES_PASSWORD: test_only_password
          POSTGRES_DB: together_test

        ports:
          - 5432:5432

        options: >-
          --health-cmd "pg_isready -U test_runner -d together_test"
          --health-interval 5s
          --health-timeout 5s
          --health-retries 10

    env:
      NODE_ENV: test

      DATABASE_URL: postgresql://test_runner:test_only_password@127.0.0.1:5432/together_test

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup pnpm
        uses: pnpm/action-setup@v4

      - name: Setup Node
        uses: actions/setup-node@v4
        with:
          node-version: '24'
          cache: pnpm

      - name: Install dependencies
        run: pnpm install --frozen-lockfile

      - name: Verify test database
        run: pnpm run test:db:guard

      - name: Apply migrations
        run: pnpm exec prisma migrate deploy

      - name: Generate Prisma Client
        run: pnpm exec prisma generate

      - name: Run integration tests
        run: pnpm run test:integration
```

### ✅ 302. 실제 적용 전 확인할 점

다음 스크립트는 프로젝트에 구현돼 있어야 한다.

```text
test:db:guard

test:integration
```

### ✅ 303. Monorepo

`prisma.config.ts`가 있는 실제 Workspace에서 명령이 실행되도록 조정해야 한다.

### ✅ 304. Prisma Version

위 Migration 명령은 설치된 Prisma CLI에서 지원하는지 확인한다.

### ✅ 305. pnpm Version

현재 프로젝트의 `packageManager` 설정과 Action 설정이 일치해야 한다.

### ✅ 306. 중요한 조건

이 Workflow에는 운영 AWS Credential이나 Production DB Secret을 제공하지 않는다.

### ✅ 307. GitHub Actions Secret

테스트에 필요한 값은 Test-only Credential만 사용한다.

### ✅ 308. DB Password

예시 문자열은 테스트용 임시 Service Container에 한정된다.

### ✅ 309. 실제 테스트

Service Container와 연결된 Test DB에서만 Migration과 테스트를 수행한다.

## 38. GitHub Actions Service와 Testcontainers 비교

## 42. Fixture Builder Pattern

### ✅ 343. Builder Pattern

복잡한 테스트 입력을 단계적으로 구성하는 방식이다.

### ✅ 344. 예시

```typescript
type OrderStatus =
  | 'PENDING'
  | 'APPROVED'
  | 'CANCELLED';

interface OrderFixture {
  reference: string;
  status: OrderStatus;
  amount: number;
}

class OrderFixtureBuilder {
  private order: OrderFixture = {
    reference: crypto.randomUUID(),
    status: 'PENDING',
    amount: 1_000_000,
  };

  cancelled(): this {
    this.order.status = 'CANCELLED';
    return this;
  }

  approved(): this {
    this.order.status = 'APPROVED';
    return this;
  }

  withAmount(amount: number): this {
    this.order.amount = amount;
    return this;
  }

  build(): OrderFixture {
    return { ...this.order };
  }
}
```

### ✅ 345. 사용 예시

```typescript
const order = new OrderFixtureBuilder()
  .cancelled()
  .withAmount(1_200_000)
  .build();
```

### ✅ 346. 장점

테스트에서 어떤 상태를 구성하는지 읽기 쉽다.

### ✅ 347. 중요한 주의

위 상태는 설명용이다.

실제 주문 상태 Enum과 업무 규칙을 확인해야 한다.

### ✅ 348. Factory와 Builder 선택

단순 데이터는 Factory, 여러 상태를 조합해야 하는 복잡한 데이터는 Builder가 적합할 수 있다.

## 📌 요약

1105에서는 테스트 자체가 불안정할 때 원인을 구분하고 검증 결과의 신뢰성을 관리하는 방법을 다뤘다.

```text
Test Failure
       ↓
Product Defect?
       ↓
Test Defect?
       ↓
Infrastructure Failure?
       ↓
Root Cause Investigation
```

1106에서는 테스트를 안정적으로 실행하기 위한 데이터와 환경을 다뤘다.

```text
Test Run
       ↓
Safe Environment Selection
       ↓
Isolated Database
       ↓
Prisma Migration
       ↓
Deterministic Seed
       ↓
Per-test Fixture
       ↓
Mock External Providers
       ↓
Business Assertions
       ↓
Cleanup
       ↓
Reproducible Result
```

이번 편에서 중요한 원칙은 일곱 가지다.

**첫 번째 — 테스트 환경과 개발 환경을 분리한다.**

개발 중 사용하는 PostgreSQL 데이터를 테스트가 변경하지 않도록 한다.

**두 번째 — Production RDS를 테스트 실행 경로에서 배제한다.**

```text
Production DB

≠

Test DB
```

라는 구분을 실제 접근권한과 네트워크 구조로 강제한다.

**세 번째 — Seed와 Fixture를 구분한다.**

Seed는 환경의 기본 데이터이고 Fixture는 특정 테스트 상태다.

**네 번째 — 테스트 데이터는 재현 가능해야 한다.**

업무 값은 예측 가능하게 만들고 식별자는 테스트 간 충돌하지 않도록 구성한다.

**다섯 번째 — Container 격리와 Test 격리는 다르다.**

독립 PostgreSQL Container를 생성했더라도 내부 테스트가 같은 데이터를 변경하면 충돌할 수 있다.

**여섯 번째 — 외부 서비스는 Mock으로 안전하게 검증한다.**

실제 고객 알림 발송이나 광고 설정 변경을 테스트에서 실행하지 않는다.

**일곱 번째 — 테스트 종료와 Cleanup을 별도로 검증한다.**

```text
Test PASS

+

Cleanup PASS
```

가 모두 중요하다.

현재 투게더몰에서는 다음 순서가 현실적이다.

```text
1. Test Database Guard

2. 별도 PostgreSQL Test DB

3. Prisma Migration / Seed 정리

4. Synthetic Fixture Factory

5. 주문·인증·가격 테스트 데이터 분리

6. External Provider Mock

7. GitHub Actions PostgreSQL Service

8. 병렬 테스트 데이터 격리

9. 필요한 경우 Testcontainers

10. Cleanup 및 재현성 검증
```

특히 기존 OrbStack 개발 환경과 PostgreSQL 18을 이미 사용하고 있다면, 처음부터 새로운 데이터베이스 인프라를 대규모로 구축할 필요는 없다.

별도의 Test DB를 구성하고 테스트용 Credential을 분리한 뒤 GitHub Actions에서 같은 Migration과 Fixture를 사용하게 만드는 것부터 시작하면 된다.

테스트 규모가 커지거나 동시성 문제가 자주 발생하면 Testcontainers를 추가할 수 있다.

최종적으로 기억해야 할 원칙은 다음과 같다.

**재현 가능한 테스트 환경은 단순히 동일한 테스트 명령을 반복 실행할 수 있는 환경이 아니다. 실제로 어떤 DB와 데이터, Runtime, 외부 의존성을 사용했는지 확인할 수 있고, 다른 개발 작업이나 고객 데이터에 영향을 주지 않으면서 동일한 업무 조건을 다시 검증할 수 있는 환경이다.**
