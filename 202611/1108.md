## 1. 배포는 성공했는데 고객의 신청은 실패했다

### ✅ 1. 1107과의 연결

1107에서 예고한 주제는 Frontend와 Backend 간 API Contract 및 Schema 호환성 관리였다.

```text
Frontend Consumer
       ↓
API Contract
       ↓
Backend Provider
       ↓
Schema Validation
       ↓
Compatibility Testing
```

1108에서는 이를 실제 Production 배포에 적용한다.

### ✅ 2. 가장 흔한 배포 상황

```text
기존 서비스
Frontend V1
Backend V1
Database V1

↓

새로운 버전 배포

↓

Frontend V2
Backend V2
Database V2
```

겉으로 보면 자연스러운 과정이다.

### ✅ 3. 하지만 현실은 다르다

모든 사용자의 브라우저와 서버가 정확히 같은 순간에 새로운 버전으로 변경되지는 않는다.

```text
V2

```

### ✅ 5. 고객 A의 문제

기존 Frontend V1이 Backend V2에서 제거된 API 필드를 사용하고 있을 수 있다.

### ✅ 6. 관리자 문제

관리자 페이지가 오래된 주문 상태 Enum을 사용하고 있을 수 있다.

### ✅ 7. Backend 문제

새 Backend가 아직 적용되지 않은 DB 컬럼을 조회할 수 있다.

## 2. Zero-downtime Deployment란?

### ✅ 12. 정의

사용자가 서비스를 사용하는 동안 가능한 한 서비스 중단 없이 새로운 버전을 적용하는 배포 방식이다.

### ✅ 13. 일반 배포

```text
Old Server
    ↓
Stop
    ↓
Replace
    ↓
Start
    ↓
Ready
```

### ✅ 14. 문제

서버가 중지된 순간부터 다시 요청을 처리할 준비가 될 때까지 접속 오류가 발생할 수 있다.

### ✅ 15. 무중단에 가까운 배포

```text
Old Server
SERVING
    ↓
New Server 준비
    ↓
New Server 검증
    ↓
Traffic 전환
    ↓
Old Server 종료
```

### ✅ 16. 중요한 주의

새 서버를 먼저 실행한다고 무조건 무중단이 되는 것은 아니다.

### ✅ 17. 필요한 조건

```text
동시 실행 가능

트래픽 전환 가능

DB 호환성

요청 종료 처리

외부 작업 중복 방지

Rollback 가능
```

### ✅ 18. 무중단이라는 표현의 한계

모든 네트워크 장애와 애플리케이션 오류를 완전히 제거한다는 의미가 아니다.

### ✅ 19. 운영 목표

배포 때문에 발생하는 서비스 중단과 고객 업무 실패를 최대한 줄이는 것이다.

### ✅ 20. 중요한 원칙

**무중단 배포는 배포 명령 한 개가 아니라 인프라·DB·애플리케이션·클라이언트 간 호환성의 종합적인 결과다.**

## 3. 현재 인프라부터 확인해야 한다

### ✅ 21. 배포 구조에 따라 방법이 달라진다

대표적인 구조는 다음과 같다.

### ✅ 22. 단일 EC2

```text
Internet
    ↓
EC2
    ↓
NestJS
    ↓
RDS
```

### ✅ 23. 단일 EC2 + Reverse Proxy

```text
Internet
    ↓
Nginx
    ↓
NestJS
    ↓
RDS
```

### ✅ 24. 여러 EC2 + Load Balancer

```text
Internet
    ↓
ALB
 ┌──┴───┐
EC2 A  EC2 B
 └──┬───┘
    ↓
   RDS
```

### ✅ 25. 실제 구성 확인

현재 프로젝트에서 다음을 조사해야 한다.

```text
EC2 Instance Count

Nginx 사용 여부

ALB 사용 여부

PM2 / systemd / Container 사용 여부

GitHub Actions 배포 방식

CodeDeploy 사용 여부

Backend Process 실행 방식

Frontend S3 / CloudFront 배포 방식
```

### ✅ 26. 가장 중요한 점

EC2와 RDS를 사용한다는 사실만으로 Blue/Green 배포가 가능하다고 판단할 수 없다.

### ✅ 27. 단일 EC2의 한계

기존 Backend를 종료하고 새로운 Backend를 시작하는 구조라면 잠깐의 중단이 발생할 수 있다.

### ✅ 28. 개선 가능성

Reverse Proxy가 있고 여유 자원이 있다면 같은 EC2에서 기존 프로세스와 새 프로세스를 서로 다른 Port로 실행하고 트래픽을 전환하는 방식을 검토할 수 있다.

### ✅ 29. 하지만 완전한 고가용성은 아니다

EC2 자체에 장애가 발생하면 두 프로세스 모두 영향을 받을 수 있다.

### ✅ 30. 현재 추천

먼저 실제 배포 경로를 확인하고, 단일 EC2에서 가능한 안전한 배포부터 개선한 뒤 필요하면 다중 인스턴스로 확장한다.

## 4. 왜 Frontend와 Backend는 서로 다른 버전이 공존할까?

### ✅ 31. SPA의 특징

React/Vite로 제작한 SPA는 브라우저에서 JavaScript가 실행된다.

### ✅ 32. 고객이 페이지를 열었다

```text
10:00

Frontend V1 다운로드
```

### ✅ 33. 개발자가 배포했다

```text
10:05

Frontend V2 배포
Backend V2 배포
```

### ✅ 34. 고객은 아직 페이지를 새로고침하지 않았다

```text
10:10

고객 브라우저:
Frontend V1

서버:
Backend V2
```

### ✅ 35. 따라서

Backend V2는 일정 기간 Frontend V1의 API 요청도 처리할 수 있어야 한다.

### ✅ 36. 관리자도 마찬가지다

관리자 페이지가 열린 상태에서 Backend가 배포되면 기존 Admin 코드가 계속 실행될 수 있다.

### ✅ 37. 현재 프로젝트에서는 특히 중요하다

고객 Frontend와 관리자 Frontend가 하나의 Backend를 공유한다면 영향을 받는 Consumer가 여러 개다.

### ✅ 38. 추가 Consumer

```text
Customer Frontend

Admin Frontend

Automation Worker

Scheduled Job

External Integration
```

등도 고려한다.

### ✅ 39. 중요한 원칙

**현재 실행 중인 모든 Consumer가 새로운 Backend와 즉시 같은 버전으로 교체된다고 가정하지 않는다.**

## 5. Backward Compatibility

### ✅ 40. 의미

새로운 버전이 기존 Consumer의 기대 동작을 계속 지원하는 것이다.

### ✅ 41. 예시

기존 API 응답:

```json
{
  "orderId": "TEST-001",
  "status": "PENDING"
}
```

### ✅ 42. 새로운 API 응답

```json
{
  "orderId": "TEST-001",
  "status": "PENDING",
  "processingStage": "RECEIVED"
}
```

### ✅ 43. 이 변경은 항상 안전할까?

기존 Consumer가 알지 못하는 필드를 허용하도록 설계돼 있다면 일반적으로 호환성을 유지하기 쉽다.

### ✅ 44. 하지만

Consumer의 Response Schema가 추가 필드를 금지하는 구조라면 실패할 수 있다.

### ✅ 45. 또 다른 예

기존 응답:

```json
{
  "orderId": "TEST-001",
  "status": "PENDING"
}
```

변경 후:

```json
{
  "id": "TEST-001",
  "processingStatus": "RECEIVED"
}
```

### ✅ 46. 문제

기존 Frontend가 `orderId`를 읽고 있다면 오류가 발생할 수 있다.

### ✅ 47. 따라서

필드 이름 변경은 기존 필드를 즉시 삭제하지 않는 방식으로 진행한다.

### ✅ 48. 중요한 원칙

**새로운 필드 추가와 기존 필드 제거는 서로 다른 배포 단계로 분리해야 할 수 있다.**

## 6. API 호환성 변경 유형

### ✅ 49. 상대적으로 안전한 변경

```text
Optional Response Field 추가

기존 Endpoint 유지

기존 요청 형식 지원

새로운 내부 구현
```

### ✅ 50. 위험한 변경

```text
Required Request Field 추가

Response Field 삭제

Response Field Rename

기존 Enum 값 제거

기존 Endpoint 삭제

기존 Field Type 변경
```

### ✅ 51. Enum 확장도 조심한다

예:

```text
PENDING

APPROVED

CANCELLED
```

상태에:

```text
REVIEW_REQUIRED
```

를 추가했다고 하자.

### ✅ 52. 기존 Frontend

세 가지 상태만 처리하도록 작성돼 있을 수 있다.

### ✅ 53. 결과

새로운 상태를 제대로 표시하지 못할 수 있다.

### ✅ 54. TypeScript 타입만 믿을 수 없다

빌드 시점의 타입 검사는 운영 서버에서 새로 전달되는 JSON이 항상 기존 타입을 만족한다고 보장하지 않는다.

### ✅ 55. 권장

Runtime Validation과 Unknown State Fallback을 검토한다.

### ✅ 56. 중요한 원칙

**API 호환성은 필드의 존재 여부뿐 아니라 실제 의미와 업무 동작까지 포함한다.**

## 7. Mixed-version Compatibility Matrix

### ✅ 57. 배포 전 확인해야 하는 조합

| Frontend | Backend | Database | 검증 |
|---|---|---|---|
| V1 | V1 | Expanded | 필요 |
| V1 | V2 | Expanded | 필요 |
| V2 | V2 | Expanded | 필요 |
| V2 | V1 | Expanded | 배포 순서에 따라 필요 |

### ✅ 58. 특히 중요한 조합

```text
Old Frontend

+

New Backend
```

### ✅ 59. 왜 중요한가?

이미 열려 있는 브라우저를 즉시 강제로 업데이트할 수 없기 때문이다.

### ✅ 60. 또 다른 조합

```text
Old Worker

+

New Database
```

### ✅ 61. 배포 중 여러 Worker가 실행된다면?

기존 Worker와 새로운 Worker가 같은 Queue나 DB를 사용할 수 있다.

### ✅ 62. 추가 검증

```text
Old Admin + New API

Old Customer Frontend + New API

Old Worker + New DB

New Worker + Expanded DB
```

### ✅ 63. 중요한 원칙

**최신 버전끼리 정상 동작하는지만 검사하지 않는다.**

## 8. Database Migration이 위험한 이유

### ✅ 64. 가장 흔한 예

기존 컬럼:

```text
Application.planCode
```

변경 후:

```text
Application.selectedPlanCode
```

### ✅ 65. 위험한 배포

```text
기존 컬럼 삭제
       ↓
새 컬럼 생성
       ↓
Backend V2 배포
```

### ✅ 66. 문제

Backend V1이 아직 실행 중이라면 삭제된 컬럼을 계속 조회하려고 한다.

### ✅ 67. 결과

```text
Database Error

↓

Application API 500

↓

Customer Application Failure
```

### ✅ 68. 그래서 필요한 패턴

**Expand-and-Contract Migration**이다.

### ✅ 69. 핵심 아이디어

기존 데이터 구조를 즉시 제거하지 않고 새로운 구조를 추가한 뒤, 모든 Consumer가 전환된 것을 확인하고 제거한다.

### ✅ 70. 중요한 원칙

**Database Schema 변경과 Application Code 변경을 하나의 순간에 동시에 끝내려고 하지 않는다.**

## 9. Expand-and-Contract란?

### ✅ 71. Expand

기존 구조를 유지하면서 새로운 구조를 추가한다.

### ✅ 72. Migrate / Transition

기존 데이터와 프로그램을 새로운 구조로 점진적으로 전환한다.

### ✅ 73. Contract

기존 구조를 더 이상 사용하지 않는 것이 확인되면 제거한다.

### ✅ 74. 전체 구조

```text
Existing Schema
       ↓
EXPAND
새 컬럼 추가
       ↓
COMPATIBILITY
기존·신규 구조 공존
       ↓
BACKFILL
기존 데이터 이전
       ↓
CUTOVER
새 구조 사용
       ↓
VERIFY
이전 구조 사용 여부 확인
       ↓
CONTRACT
기존 컬럼 제거
```

### ✅ 75. 핵심

Expand 단계에서 기존 기능이 계속 동작해야 한다.

### ✅ 76. Transition 단계

기존 데이터와 새로운 데이터가 일치하는지 검증한다.

### ✅ 77. Contract 단계

기존 Consumer가 완전히 제거됐는지 확인해야 한다.

### ✅ 78. 중요한 원칙

**Contract는 새로운 버전 배포 직후 자동으로 실행하는 작업이 아니다.**

## 10. 실제 예시 — 요금제 컬럼 변경

### ✅ 79. 기존 Prisma Model

다음은 개념 예시다.

```prisma
model Application {
  id       String @id @default(uuid())
  planCode String

  @@map("applications")
}
```

### ✅ 80. 변경 목표

`planCode`를 새로운 `selectedPlanCode`로 바꾼다고 가정한다.

### ✅ 81. 위험한 변경

기존 필드를 삭제하고 새로운 필드만 남기는 것이다.

### ✅ 82. Expand 단계

```prisma
model Application {
  id               String  @id @default(uuid())

  planCode         String

  selectedPlanCode String?

  @@map("applications")
}
```

### ✅ 83. 이 단계의 장점

기존 필드를 그대로 유지하므로 구버전 Prisma Client가 계속 사용할 수 있는 구조가 된다.

### ✅ 84. 새 필드가 Nullable인 이유

기존 데이터에는 아직 값이 없기 때문이다.

### ✅ 85. 중요

실제 Model 이름과 DB 컬럼명은 현재 프로젝트의 Prisma Schema를 기준으로 확인해야 한다.

## 11. Expand Migration SQL

### ✅ 86. PostgreSQL 예시

```sql
ALTER TABLE applications
ADD COLUMN selected_plan_code TEXT;
```

### ✅ 87. 결과

```text
plan_code
기존 값 유지

selected_plan_code
NULL
```

### ✅ 88. 기존 Backend

`plan_code`를 계속 사용할 수 있다.

### ✅ 89. 새로운 Backend

새 컬럼이 존재한다는 것을 확인한 후 사용할 수 있다.

### ✅ 90. 중요한 주의

새로운 컬럼을 추가했다고 새로운 프로그램을 바로 배포해도 안전하다는 뜻은 아니다.

### ✅ 91. 추가 확인

```text
Migration Applied

Old Backend Compatible

New Backend Compatible

Data Consistency Policy
```

### ✅ 92. PostgreSQL Lock

`ALTER TABLE`은 변경 종류에 따라 테이블 Lock을 획득한다.

### ✅ 93. 따라서

규모가 큰 운영 테이블에서는 실제 실행 시간과 Lock 대기 영향을 사전 검토해야 한다.

### ✅ 94. 중요한 원칙

**데이터를 삭제하지 않는 Migration도 운영 성능과 가용성에 영향을 줄 수 있다.**

## 12. Dual Write

### ✅ 95. 새로운 컬럼을 추가한 다음

기존과 새로운 컬럼에 동시에 값을 저장하는 전환 단계를 둘 수 있다.

### ✅ 96. 구조

```text
Application Submission
         ↓
NestJS Service
         ↓
DB Transaction
   ┌─────┴─────┐
Old Column   New Column
```

### ✅ 97. 목적

기존 Backend와 새로운 Backend의 데이터 접근 방식을 일정 기간 함께 지원하는 것이다.

### ✅ 98. 예시

```typescript

  data: {
    planCode: selectedPlanCode,

    selectedPlanCode,
  },

```

### ✅ 99. 전제

해당 Prisma Client와 Schema가 두 필드를 지원해야 한다.

### ✅ 100. 중요한 점

### ✅ 101. 하지만 주의

기존 Backend V1이 계속 기존 컬럼만 변경한다면 두 필드가 달라질 수 있다.

### ✅ 102. 해결 정책

구버전 Writer가 남아 있는 동안 어떤 필드를 기준 데이터로 사용할지 정의해야 한다.

### ✅ 103. 필요한 검토

```text
Old Writer

New Writer

Backfill

Read Policy

Consistency Check
```

### ✅ 104. 중요한 원칙

**Dual Write는 코드를 두 군데에 저장하게 만드는 것만으로 끝나지 않는다. 기존 Writer와 새로운 Writer 간 정합성 정책이 필요하다.**

## 13. Backfill이란?

### ✅ 105. 정의

기존 Row에 저장된 데이터를 새로운 컬럼이나 데이터 구조로 이전하는 작업이다.

### ✅ 106. 예시

```text
plan_code
5G_PREMIUM

selected_plan_code
NULL
```

### ✅ 107. Backfill 이후

```text
plan_code
5G_PREMIUM

selected_plan_code
5G_PREMIUM
```

### ✅ 108. 작은 Test DB

단순 UPDATE로 검증할 수 있다.

```sql
UPDATE applications
SET selected_plan_code = plan_code
WHERE selected_plan_code IS NULL;
```

### ✅ 109. Production 주의

대량 UPDATE는 Transaction 시간, Lock, WAL 생성, I/O 사용량을 증가시킬 수 있다.

### ✅ 110. 따라서

실제 데이터량이 크다면 Batch Backfill을 검토한다.

### ✅ 111. Backfill을 실행할 때

기존 Writer가 계속 데이터를 변경하고 있을 수 있다.

### ✅ 112. 따라서

실행 순서와 정합성 검사가 중요하다.

## 14. Batch Backfill

### ✅ 113. 개념

전체 Row를 한 번에 처리하지 않고 일정 단위로 나눠 처리한다.

### ✅ 114. 예시

```text
전체 100,000 Row

↓

1,000 Row

↓

1,000 Row

↓

반복
```

수치는 설명용이다.

### ✅ 115. PostgreSQL 예시

```sql
WITH batch AS (
  SELECT id
  FROM applications
  WHERE selected_plan_code IS NULL
    AND plan_code IS NOT NULL
  ORDER BY id
  LIMIT 500
  FOR UPDATE SKIP LOCKED
)
UPDATE applications AS a
SET selected_plan_code = a.plan_code
FROM batch
WHERE a.id = batch.id
  AND a.selected_plan_code IS NULL
RETURNING a.id;
```

### ✅ 116. 설명

`LIMIT 500`으로 한 번에 처리할 대상을 제한한다.

### ✅ 117. FOR UPDATE

선택한 Row에 대한 변경 충돌을 관리하기 위한 Row Lock을 사용한다.

### ✅ 118. SKIP LOCKED

다른 Transaction에서 잠긴 Row를 기다리지 않고 건너뛸 수 있다.

### ✅ 119. 중요한 전제

테이블·컬럼 이름은 개념 예시다.

실제 Prisma DB Mapping을 확인해야 한다.

### ✅ 120. 반복 실행

업데이트된 Row 수가 0이라고 해서 전체 Backfill이 영구적으로 완료됐다고 판단하면 안 된다.

### ✅ 121. 이유

다른 Transaction이 잠근 Row를 건너뛰었을 수 있기 때문이다.

### ✅ 122. 최종 확인

미완료 Row가 남아 있는지 별도 조회해야 한다.

### ✅ 123. 중요한 원칙

**Backfill은 실행 성공 여부뿐 아니라 실제 데이터 이전 완료와 정합성을 검증해야 한다.**

## 15. Backfill 정합성 검사

### ✅ 124. 미완료 건수

```sql
SELECT COUNT(*) AS missing_count
FROM applications
WHERE plan_code IS NOT NULL
  AND selected_plan_code IS NULL;
```

### ✅ 125. 불일치 건수

```sql
SELECT COUNT(*) AS mismatch_count
FROM applications
WHERE selected_plan_code IS DISTINCT FROM plan_code;
```

### ✅ 126. IS DISTINCT FROM

NULL을 포함한 비교에서도 차이를 구분할 수 있는 PostgreSQL 연산자다.

### ✅ 127. 중요한 점

두 컬럼이 동일한 의미의 값을 보관한다는 전제가 있어야 한다.

### ✅ 128. 실제 값의 변환이 필요하다면?

단순 문자열 비교가 아니라 명시적인 변환 규칙을 기준으로 확인해야 한다.

### ✅ 129. Backfill 완료 조건

```text
Missing Count = 0

Mismatch Count = 0

Writer Consistency Verified
```

같은 기준을 사용할 수 있다.

### ✅ 130. 하지만 주의

새로운 데이터가 지속적으로 생성되는 운영 서비스라면 어느 시점의 데이터까지 검증했는지 고려해야 한다.

### ✅ 131. 최종 원칙

**Backfill 완료와 신규 Writer 전환 완료를 별도 상태로 관리한다.**

## 16. Read Cutover

### ✅ 132. 데이터를 이전했다면?

새로운 컬럼을 읽기 시작할 수 있다.

### ✅ 133. 초기 Read

```typescript
const selectedPlan =
  application.selectedPlanCode
  ?? application.planCode;
```

### ✅ 134. 역할

새 컬럼에 값이 없다면 기존 컬럼으로 Fallback한다.

### ✅ 135. 하지만 언제까지 Fallback할까?

영원히 유지하면 기존 컬럼 사용을 제거하기 어려워질 수 있다.

### ✅ 136. 따라서

Fallback 사용 건수를 측정할 수 있다.

### ✅ 137. 예시

```text
NEW_COLUMN_READ

LEGACY_FALLBACK_READ
```

### ✅ 138. 최종 Cutover

모든 필요한 Row와 Writer가 새 컬럼을 정상적으로 사용한다는 것을 검증한 후 새로운 컬럼을 기준으로 변경한다.

### ✅ 139. 중요한 점

새로운 Reader로 전환한 후에도 일정 기간 기존 Writer와 Rollback 가능성을 검토해야 한다.

### ✅ 140. 중요한 원칙

**새 컬럼을 읽기 시작하는 시점과 기존 컬럼을 삭제하는 시점은 분리한다.**

### ✅ 145. 따라서

## 20. PostgreSQL Lock과 장시간 Migration

### ✅ 166. Schema Migration도 서비스 장애를 일으킬 수 있다

특히 큰 테이블에 Lock을 오래 유지하는 작업이다.

### ✅ 167. 위험한 작업 후보

```text
Large Column Type Change

Large Table Rewrite

Large Data Update

Constraint Validation

Index Creation
```

### ✅ 168. PostgreSQL

DDL 종류에 따라 Lock 수준과 Table Rewrite 여부가 다르다.

### ✅ 169. 작은 테이블

짧게 완료될 수 있다.

### ✅ 170. 큰 테이블

대기 중인 Query가 쌓이거나 요청 지연이 증가할 수 있다.

### ✅ 171. 따라서 실제 운영 전에

```text

Row Count

Index Size

Lock Duration

Query Traffic
```

를 검토한다.

### ✅ 173. 예시

```sql
SET lock_timeout = '3s';
```

### ✅ 174. 주의

실제 Migration Runner의 Transaction 구조에 따라 설정 범위와 적용 방식을 확인해야 한다.

### ✅ 175. 중요한 원칙

**Migration이 성공하는지뿐 아니라 정상 고객 요청을 얼마나 차단하는지도 평가해야 한다.**

## 21. CREATE INDEX CONCURRENTLY

### ✅ 176. PostgreSQL

운영 중 Index를 생성할 때 `CONCURRENTLY` 옵션을 사용할 수 있다.

### ✅ 177. 예시

```sql
CREATE INDEX CONCURRENTLY
idx_applications_selected_plan
ON applications (selected_plan_code);
```

### ✅ 178. 장점

일반적인 Index 생성과 달리 동시 Insert·Update·Delete를 막는 Lock을 피하도록 설계됐다.

### ✅ 179. 하지만 완전히 무영향일까?

아니다.

CPU·I/O를 사용하고 실행 시간이 길어질 수 있다.

### ✅ 180. 중요한 제약

`CREATE INDEX CONCURRENTLY`는 Transaction Block 내부에서 실행할 수 없다.

### ✅ 181. 따라서

현재 Prisma Migration Runner가 어떤 Transaction 경계에서 SQL을 실행하는지 확인해야 한다.

### ✅ 182. 실패 가능성

Concurrent Index 생성이 실패하면 유효하지 않은 Index가 남을 수 있다.

### ✅ 183. 운영 전 확인

```text
Index Existence

Index Validity

Migration History

Rollback Plan
```

### ✅ 184. 중요한 원칙

**무중단에 유리한 SQL 옵션도 별도의 사전 검증과 실패 복구 절차가 필요하다.**

**Frontend 배포에서는 새 파일의 게시뿐 아니라 이전 파일의 보존도 배포 안정성의 일부다.**

## 26. CloudFront Invalidation

### ✅ 219. Invalidation

CloudFront Edge Cache에 있는 특정 객체를 갱신하도록 요청하는 기능이다.

### ✅ 220. 예시 대상

```text
/index.html
```

### ✅ 221. SPA

루트 경로 또는 여러 HTML 경로의 Cache 정책도 고려해야 한다.

### ✅ 222. 하지만 중요한 제한

CloudFront Invalidation은 사용자 브라우저가 이미 로드한 JavaScript 실행 코드를 강제로 바꾸지는 않는다.

### ✅ 223. 또 다른 제한

브라우저 자체 Cache나 다른 중간 Cache의 동작은 별도다.

### ✅ 224. 따라서

```text
Hashed Assets 유지

+

HTML Cache 관리

+

API 호환성
```

이 함께 필요하다.

### ✅ 225. SPA Fallback

CloudFront에서 403/404를 `index.html`로 변환하는 구성도 주의해야 한다.

### ✅ 226. 위험

없는 JavaScript 파일 요청까지 HTML 200 응답으로 변환하면 Chunk Load 오류를 더 알아보기 어렵게 만들 수 있다.

### ✅ 227. 중요한 원칙

**SPA Route Fallback과 정적 Asset의 실제 404 처리를 구분한다.**

## 27. Chunk Load Failure 처리

### ✅ 228. 이미 이전 버전을 사용 중인 고객

Dynamic Import로 새로운 Chunk를 요청할 때 파일이 없으면 오류가 발생할 수 있다.

### ✅ 229. 대응 후보


### ✅ 230. 자동 새로고침만 하면 될까?

신청서에 입력 중인 데이터가 사라질 수 있다.

```text
↓

강제 Reload

입력 내용 유실
```

### ✅ 232. 권장

중요한 입력 과정에서는 업데이트 안내와 안전한 복구 정책을 고려한다.

### ✅ 233. 개인정보 주의

신청서 입력값을 보존하기 위해 전화번호·주소 등 민감한 데이터를 무조건 localStorage에 저장하지 않는다.

### ✅ 234. 실제 구현

업데이트 시점, 저장할 수 있는 최소 상태, 사용자 확인 여부를 명확히 설계한다.

### ✅ 235. 중요한 원칙

**배포를 위해 고객의 진행 중인 신청 작업을 일방적으로 중단하지 않는다.**

## 28. Backend 무중단 배포 방식 비교

### ✅ 236. 대표적인 방식

| 방식 | 특징 | 추가 구성 |
|---|---|---|
| Stop/Start | 기존 프로세스 교체 | 간단 |
| Graceful Restart | 기존 요청 종료를 기다림 | Process Manager 지원 |
| Local Blue/Green | 한 EC2에서 두 프로세스 공존 | Reverse Proxy·여유 자원 |
| Rolling | 여러 Instance를 순차 교체 | 다중 인스턴스 |
| Blue/Green | 새 환경 검증 후 트래픽 전환 | LB·별도 환경 |
| Canary | 일부 트래픽부터 적용 | 트래픽 분할·관측 |

### ✅ 237. Stop/Start

구현은 쉽지만 잠깐의 중단이 발생할 수 있다.

### ✅ 238. Graceful Restart

기존 요청을 종료할 시간을 확보하도록 설계한다.

### ✅ 239. Local Blue/Green

새 프로세스를 별도 Port에서 실행하고 준비가 끝난 뒤 Proxy 라우팅을 전환한다.

### ✅ 240. Rolling

일부 Instance를 교체하면서 나머지가 요청을 처리한다.

### ✅ 241. Blue/Green

새로운 서비스 환경에서 검증한 후 트래픽을 전환한다.

### ✅ 242. Canary

작은 비율의 트래픽으로 새로운 버전을 검증한 후 확대한다.

### ✅ 243. 중요한 원칙

**현재 단일 EC2 운영에 여러 서버를 전제로 한 배포 방식을 무조건 적용하지 않는다.**

## 30. Readiness와 Liveness

### ✅ 254. Health Check를 하나로 처리해도 될까?

서비스가 살아 있는 상태와 실제 요청을 받을 준비가 된 상태는 다르다.

### ✅ 255. Liveness

프로세스가 정상적으로 실행되고 있는지 확인한다.

### ✅ 256. Readiness

새로운 요청을 처리할 준비가 됐는지 확인한다.

### ✅ 257. 예시

```text
Liveness:
Application Process Running

Readiness:
Required Dependencies Available
```

### ✅ 258. NestJS 예시

```typescript
import {
  Controller,
  Get,
  ServiceUnavailableException,
} from '@nestjs/common';

@Controller('health')
export class HealthController {
  @Get('live')
  live() {
    return {
      status: 'ok',
    };
  }

  @Get('ready')
  async ready() {
    const isReady = await checkApplicationReadiness();

    if (!isReady) {
      throw new ServiceUnavailableException(
        'NOT_READY',
      );
    }

    return {
      status: 'ready',
    };
  }
}
```

### ✅ 259. 중요한 전제

`checkApplicationReadiness()`는 실제 프로젝트에 맞게 구현해야 하는 함수다.

### ✅ 260. Readiness 검증

DB 연결과 필수 초기화가 완료됐는지 확인할 수 있다.

### ✅ 261. 주의

모든 외부 Provider가 잠시 실패했다고 무조건 전체 서비스를 Not Ready로 처리하면 오히려 서비스 가용성이 떨어질 수 있다.

### ✅ 262. 따라서

핵심 요청 처리에 필수인 의존성과 부가 기능 의존성을 구분한다.

### ✅ 263. 중요한 원칙

**새로운 Backend가 Port를 열었다는 사실만으로 고객 트래픽을 전환하지 않는다.**

---

## 31. Graceful Shutdown

### ✅ 264. 새 버전으로 전환하면?

기존 Backend를 종료해야 한다.

### ✅ 265. 위험한 종료

```text
Active Request
      ↓
Process SIGKILL
      ↓
Response Lost
```

### ✅ 266. 중요한 신청 API

DB Transaction 완료 직전 프로세스가 종료될 수 있다.

### ✅ 267. 결과 불명

고객은 응답을 받지 못했지만 실제 주문은 생성됐을 수 있다.

### ✅ 268. 따라서

Graceful Shutdown을 고려한다.

### ✅ 269. NestJS

```typescript
app.enableShutdownHooks();
```

를 사용해 종료 Lifecycle Hook을 활성화할 수 있다.

### ✅ 270. 하지만 이것만으로 충분할까?

아니다.

### ✅ 271. 실제로 필요한 것

```text
새 요청 유입 차단

진행 중인 요청 처리

DB Connection 정리

Worker 종료 정책

Timeout 제한

실패한 요청의 결과 확인
```

### ✅ 272. 중요한 제약

종료 신호를 받았을 때 Process Manager와 Load Balancer가 어떤 순서로 요청을 중단하는지 확인해야 한다.

### ✅ 273. 중요한 원칙

**Graceful Shutdown은 기존 요청의 종료를 배려하는 기능이지 모든 외부 Side Effect의 정확히 한 번 실행을 보장하는 장치는 아니다.**

---

## 32. Deployment 중 주문 중복 생성

### ✅ 274. 장애 시나리오

```text
고객 신청 제출
       ↓
Backend Blue
       ↓
Order 생성
       ↓
배포 전환
       ↓
응답 유실
       ↓
고객 Retry
       ↓
Backend Green
```

### ✅ 275. 위험

같은 논리적 신청이 두 번 생성될 수 있다.

### ✅ 276. 따라서

Backend 버전과 무관하게 동일 Attempt Key를 인식해야 한다.

### ✅ 277. 필요한 구조

```text
Logical Attempt Key

Database Unique Constraint

Idempotent Processing

Result Reconciliation
```

### ✅ 278. 중요한 점

Frontend에서 버튼을 비활성화하는 것만으로는 충분하지 않다.

### ✅ 279. 또 다른 문제

Old Worker와 New Worker가 같은 메시지를 처리할 수 있다.

### ✅ 280. 해결

Queue Consumer와 외부 Provider 호출에도 멱등성·소유권·승인 정책을 적용해야 한다.

### ✅ 281. 중요한 원칙

**무중단 배포는 고객 요청이 중복 실행되지 않도록 만드는 업무 안정성 설계와 함께 진행해야 한다.**

---

## 33. Worker 배포와 Queue Compatibility

### ✅ 282. HTTP API만 배포 대상은 아니다

Background Worker도 버전이 바뀐다.

### ✅ 283. 예시

```text
Backend V2
       ↓
Job Payload V2
       ↓
Worker V1
```

### ✅ 284. 문제

Worker V1이 새로운 Job Payload를 처리하지 못할 수 있다.

### ✅ 285. 따라서

Job Payload의 Schema 호환성도 확인한다.

### ✅ 286. 위험한 변경

기존 필드를 삭제하고 새로운 필수 필드만 전달한다.

### ✅ 287. 권장

일정 기간 기존 필드를 유지하거나 명시적인 Job Version을 사용한다.

### ✅ 288. 예시

```typescript
interface NotificationJobV1 {
  version: 1;
  orderId: string;
}

interface NotificationJobV2 {
  version: 2;
  orderId: string;
  templateCode: string;
}
```

### ✅ 289. 중요한 점

새로운 Producer가 V2 Payload를 생성하기 전에 이를 처리할 Worker가 준비돼 있어야 한다.

### ✅ 290. Worker 중복 실행

기존 Worker를 종료하지 않고 새 Worker를 켜면 동일 Job을 처리할 가능성이 있다.

### ✅ 291. 따라서

Queue의 Claim·Lease·Ack·Idempotency 정책을 검토한다.

### ✅ 292. 중요한 원칙

**Worker 배포는 프로그램 교체뿐 아니라 Job Schema와 외부 Side Effect의 연속성을 관리하는 작업이다.**

## 34. Feature Flag란?

### ✅ 293. 정의

코드를 배포한 뒤 특정 기능을 활성화하거나 비활성화할 수 있도록 제어하는 방식이다.

### ✅ 294. 일반 배포

```text
Code Deployed

↓

Feature Enabled
```

### ✅ 295. Feature Flag 사용

```text
Code Deployed

↓

Feature Disabled

↓

Verified

↓

Feature Enabled
```

### ✅ 296. 장점

코드 배포 시점과 실제 기능 활성화 시점을 분리할 수 있다.

### ✅ 297. 예시

새로운 신청 요금제 선택 UI를 배포하되 처음에는 비활성화한다.

### ✅ 298. 검증 이후

일부 내부 테스트 사용자에게 활성화한다.

### ✅ 299. 문제가 없다면

설정된 대상에게 점진적으로 확대한다.

### ✅ 300. 중요한 원칙

**Feature Flag는 기능 활성화 범위를 제어하는 도구이지 DB Migration을 되돌리는 도구가 아니다.**

---

## 35. Feature Flag 상태 설계

### ✅ 301. 기본 상태

```text
DISABLED

INTERNAL_ONLY

CANARY

ENABLED
```

### ✅ 302. DISABLED

기존 기능을 유지한다.

### ✅ 303. INTERNAL_ONLY

승인된 내부 사용자만 새 기능을 사용한다.

### ✅ 304. CANARY

일부 트래픽 또는 사용자 그룹에 새 기능을 제공한다.

### ✅ 305. ENABLED

정해진 전체 대상에게 제공한다.

### ✅ 306. 추가로 필요한 것

```text
Flag Owner

Default Value

Activation Time

Rollback Action

Expiry

Business Risk
```

### ✅ 307. 중요한 제한

고객 Frontend에서 사용하는 Flag를 권한·가격·개인정보 보호 정책의 최종 결정 근거로 사용해서는 안 된다.

### ✅ 308. 이유

브라우저의 Flag 값은 사용자가 조작할 수 있기 때문이다.

### ✅ 309. 따라서

중요한 업무 규칙은 Backend에서 검증해야 한다.

---

## 36. Feature Flag 코드 예시

### ✅ 310. 서버 설정

```typescript
type RolloutStage =
  | 'DISABLED'
  | 'INTERNAL_ONLY'
  | 'CANARY'
  | 'ENABLED';

interface FeatureFlags {
  newPlanSelector: RolloutStage;
}
```

### ✅ 311. 기본값

```typescript
const flags: FeatureFlags = {
  newPlanSelector: 'DISABLED',
};
```

### ✅ 312. 기본 평가

```typescript
function isEnabled(
  stage: RolloutStage,
  isInternalUser: boolean,
): boolean {
  switch (stage) {
    case 'ENABLED':
      return true;

    case 'INTERNAL_ONLY':
      return isInternalUser;

    case 'DISABLED':
      return false;

    case 'CANARY':
      return false;
  }
}
```

### ✅ 313. 중요한 점

위 코드는 CANARY 배분을 구현하지 않은 최소 예시다.

### ✅ 314. 실제 Canary

사용자 그룹이나 안정적인 Rollout Key에 따라 일관되게 배분해야 한다.

### ✅ 315. 요청마다 Math.random 사용

동일한 고객이 새 기능과 기존 기능 사이를 반복해서 이동할 수 있다.

### ✅ 316. 따라서

안정적인 Rollout 정책과 개인정보 보호 기준을 함께 설계한다.

### ✅ 317. 중요한 원칙

**Feature Flag 평가 결과는 재현 가능하고, 중요한 업무에 대한 접근권한과 별도로 검증돼야 한다.**

---

## 37. Feature Flag의 위험

### ✅ 318. Flag가 많아지면?

코드에 서로 다른 실행 경로가 계속 누적된다.

### ✅ 319. 예시

```text
newPlanSelector

newPricingLogic

newApplicationForm

newOrderWorkflow
```

### ✅ 320. 조합이 늘어난다

여러 Flag의 조합마다 다른 오류가 발생할 수 있다.

### ✅ 321. 따라서

장기간 유지해야 하는 운영 설정과 일시적인 배포 Flag를 구분한다.

### ✅ 322. Temporary Release Flag

기능 검증 이후 기존 코드와 함께 제거할 수 있다.

### ✅ 323. Permanent Business Flag

특정 고객이나 상품 유형의 정책을 계속 구분하는 기능이다.

### ✅ 324. 중요한 원칙

**일시적인 배포 Flag는 완료·정리 시점을 정의하고 무기한 남겨두지 않는다.**

---

## 38. Canary Deployment

### ✅ 325. 개념

새로운 버전을 전체 사용자에게 한 번에 제공하지 않고 일부 트래픽부터 적용하는 방식이다.

### ✅ 326. 예시

```text
Old Version
95%

New Version
5%
```

### ✅ 327. 검증

```text
API Error Rate

Application SLI

Latency

Frontend Error

Business Outcome
```

등을 확인한다.

### ✅ 328. 이후 확대

```text
5%

↓

20%

↓

50%

↓

100%
```

이는 설명용 단계다.

### ✅ 329. 중요한 주의

트래픽 비율을 정확히 제어하려면 Load Balancer나 Traffic Router 등 실제 지원되는 인프라가 필요하다.

### ✅ 330. Feature Flag Canary

트래픽 분할 배포와는 다른 방식으로 특정 기능을 일부 사용자에게 제공할 수 있다.

### ✅ 331. 구분

```text
Deployment Canary:
서버 버전 분할

Feature Canary:
```

## 42. Rollback이란?

### ✅ 354. 정의

문제가 발생한 배포에서 이전의 정상적인 코드 버전으로 돌아가는 절차다.

### ✅ 355. 중요한 주의

Rollback이 모든 데이터 변경을 취소한다는 뜻은 아니다.

### ✅ 356. 예시

```text
Backend V2 배포

↓

문제 발생

↓

Backend V1 재배포
```

### ✅ 357. 그런데 DB는?

이미 Expanded Schema가 적용됐을 수 있다.

### ✅ 358. 따라서

Backend V1이 Expanded Schema와 호환되는지 확인해야 한다.

### ✅ 359. 더 위험한 경우

기존 컬럼까지 삭제했다면 Backend V1이 작동하지 않을 수 있다.

### ✅ 360. 결론

**Rollback 가능성은 배포 전 Schema Compatibility에 의해 결정된다.**

---

## 43. Code Rollback과 Data Rollback

### ✅ 361. Code Rollback

이전 애플리케이션 코드를 재배포하는 것이다.

### ✅ 362. Data Rollback

데이터를 이전 상태로 되돌리는 것이다.

### ✅ 363. 두 작업은 다르다

```text
Code Rollback
상대적으로 단순할 수 있음

Data Rollback
업무 데이터 손실 가능성
```

### ✅ 364. 예시

배포 이후 정상적인 고객 신청 100건이 생성됐다.

### ✅ 365. 문제

배포 이전 시점으로 DB 전체를 복구하면 정상적으로 접수된 고객 신청까지 사라질 수 있다.

### ✅ 366. 따라서

운영 DB 전체 복구를 일반적인 코드 배포 Rollback처럼 취급하지 않는다.

### ✅ 367. RDS Backup

백업이나 Point-in-time Recovery는 장애 복구 수단이다.

### ✅ 368. 하지만

복구 과정에서 데이터 정합성과 새로운 업무 데이터의 보존 문제가 발생할 수 있다.

### ✅ 369. 중요한 원칙

**일반 배포 실패에서는 가능한 한 데이터는 유지하고 코드를 되돌릴 수 있도록 설계한다.**

---

## 44. Fix Forward

### ✅ 370. Fix Forward

이전 버전으로 되돌리는 대신 현재 버전을 추가 수정해 문제를 해결하는 방식이다.

### ✅ 371. 적합한 경우

이미 되돌리기 어려운 Schema 변경이 완료된 상황 등이 있다.

### ✅ 372. 하지만

Fix Forward가 항상 더 안전하다는 뜻은 아니다.

### ✅ 373. 선택 기준

```text
Incident Severity

Customer Impact

Rollback Compatibility

Data Mutation

Recovery Time

Fix Complexity
```

### ✅ 374. 예시

Frontend CSS 오류라면 이전 Frontend Build로 되돌릴 수 있을 수 있다.

### ✅ 375. 반대로

DB 구조가 파괴적으로 변경됐다면 이전 Backend로의 Rollback이 실패할 수 있다.

### ✅ 376. 중요한 원칙

**Rollback과 Fix Forward는 실제 데이터와 코드 호환성을 기준으로 선택한다.**

## 45. Rollback Matrix

### ✅ 377. 배포 전에 작성한다

| 현재 코드 | DB 상태 | 이전 코드 복구 |
|---|---|---|
| Backend V2 | Expanded | 가능 여부 검증 |
| Backend V2 | Backfilled | 가능 여부 검증 |
| Backend V2 | New-only | 구버전 호환성 주의 |
| Backend V2 | Contracted | 구버전 실행 불가 가능 |

### ✅ 378. 핵심

새로운 Schema가 기존 코드를 지원하는 동안은 Rollback 선택지가 넓다.

### ✅ 379. Contract 이후

이전 코드가 제거된 컬럼을 참조한다면 Rollback할 수 없다.

### ✅ 380. 따라서

Contract 직전에는 이전 버전으로 되돌아갈 필요가 없는지 다시 확인한다.

### ✅ 381. 중요한 원칙

**Rollback 계획 없이 파괴적 Schema 변경부터 진행하지 않는다.**

## 📌 요약

1106에서는 안정적인 테스트 데이터와 격리된 실행 환경을 구성하는 방법을 다뤘다.

1107에서 예고한 API Contract Testing의 핵심은 Frontend와 Backend 간의 호환성을 검증하는 것이었다.

1108에서는 이를 운영 배포에 적용했다.

```text
New Feature / Schema Change
           ↓
Compatibility Analysis
           ↓
Expand Database
           ↓
Deploy Compatible Backend
           ↓
Backfill / Dual Write
           ↓
Read Cutover
           ↓
Deploy Frontend
           ↓
Feature Activation
           ↓
Business Verification
           ↓
Legacy Consumer Removal
           ↓
Contract Migration
```

이번 편에서 중요한 원칙은 일곱 가지다.

**첫 번째 — 배포 중에는 서로 다른 버전이 공존한다.**

기존 고객의 브라우저는 새로운 Backend 배포 이후에도 이전 JavaScript를 실행할 수 있다.

**두 번째 — 기존 API 계약을 즉시 제거하지 않는다.**

새로운 Backend는 일정 기간 기존 Consumer를 지원해야 할 수 있다.

**세 번째 — DB 변경은 Expand-and-Contract로 나눈다.**

```text
Expand

↓

Transition

↓

Verify

↓

Contract
```

단계로 나눠 진행한다.

**네 번째 — 기존 Frontend Asset을 무조건 삭제하지 않는다.**

이미 열린 브라우저가 오래된 JavaScript Chunk를 필요로 할 수 있다.

**다섯 번째 — Readiness와 실제 업무 성공을 구분한다.**

서버가 정상적으로 시작됐다는 사실만으로 고객 신청까지 정상이라고 보장할 수 없다.

**여섯 번째 — Rollback은 데이터 복구와 다르다.**

코드를 되돌려도 이미 생성된 주문이나 발송된 알림은 되돌아가지 않는다.

**일곱 번째 — 무중단 배포는 인프라와 업무 정합성의 문제다.**

단일 EC2 환경에서는 배포 중단을 줄일 수 있지만 전체 인프라의 고가용성을 보장하지 않는다.

현재 투게더몰에서는 다음 순서가 현실적이다.

```text
1. 실제 배포 구조 확인

2. Frontend / Backend 호환성 검토

3. 이전 Hashed Asset 보존

4. Prisma Migration Risk Review

5. Expand-and-Contract 적용

6. Backend Readiness

7. Graceful Shutdown 검토

8. Rollback Compatibility Matrix

9. Deployment Smoke Test

10. Business SLI 기반 배포 검증
```

처음부터 다중 EC2나 복잡한 Blue/Green 인프라를 도입할 필요는 없다.

먼저 지금의 배포 방식에서 어떤 순간에 서비스가 중단되고 어떤 변경이 기존 브라우저 또는 Worker를 깨뜨리는지 확인하는 것이 우선이다.

특히 **고객 신청·주문 저장·관리자 상태 변경·외부 알림 발송**처럼 실제 업무 결과가 남는 기능은 배포 중에도 정합성을 유지해야 한다.

최종적으로 기억해야 할 원칙은 다음과 같다.

**좋은 배포 시스템은 최신 코드를 빠르게 올리는 시스템이 아니다. 기존 사용자와 새로운 사용자, 이전 데이터와 새로운 데이터, 실행 중인 요청과 새로운 요청이 공존하는 동안에도 핵심 업무를 안전하게 유지하고, 문제가 발생하면 확인된 절차로 복구할 수 있는 시스템이다.**
