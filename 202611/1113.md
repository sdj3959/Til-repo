## 2. Performance Regression이란?

### ✅ 12. 정의

코드·설정·데이터 구조·의존성 등의 변경 이후 이전보다 성능이 악화되는 현상이다.

### ✅ 13. 대표적인 성능 회귀

```text
API 응답시간 증가

DB Query 수 증가

메모리 사용량 증가

CPU 사용량 증가

Frontend Bundle 증가

페이지 로딩시간 증가

Worker 처리량 감소
```

### ✅ 14. 중요한 점

기능적 Regression과 Performance Regression은 다르다.

### ✅ 15. Functional Regression

기존에 정상적으로 동작하던 기능이 더 이상 정상적으로 동작하지 않는 것이다.

### ✅ 16. Performance Regression

기능 자체는 정상적으로 동작하지만 이전보다 더 많은 시간이나 자원을 사용하게 되는 것이다.

### ✅ 17. 예시

| 항목 | 기존 | 변경 후 |
|---|---:|---:|
| 신청 API 상태 | 200 | 200 |
| 실제 주문 생성 | 성공 | 성공 |
| DB Query | 4회 | 40회 |
| p95 응답시간 | 300ms | 850ms |

### ✅ 18. 일반적인 기능 테스트

주문이 생성됐으므로 PASS로 처리할 수 있다.

### ✅ 19. 성능 테스트

Query 수와 응답시간이 증가했기 때문에 추가 검토가 필요하다.

### ✅ 20. 중요한 원칙

**기능 정확성과 성능 안정성은 서로 독립적인 검증 대상으로 관리한다.**

## 3. 성능 회귀는 왜 발생할까?

### ✅ 21. 새로운 기능 추가

기존 API 내부에서 추가적인 업무를 수행하게 된다.

### ✅ 22. DB 조회 변경

필요하지 않은 Relation을 함께 조회하거나 Query가 반복될 수 있다.

### ✅ 23. Dependency 변경

패키지 업데이트로 JavaScript Bundle 크기나 Runtime 동작이 달라질 수 있다.

### ✅ 24. 설정 변경

Connection Pool·Timeout·Cache TTL 설정이 달라질 수 있다.

### ✅ 25. 데이터 증가

코드는 동일하지만 주문 데이터가 계속 증가하면서 Query가 느려질 수 있다.

### ✅ 26. 배포 환경 변경

Node.js 버전이나 EC2 Instance Type, PostgreSQL 버전이 변경될 수 있다.

### ✅ 27. 따라서 원인을 분류한다

```text
Code Regression

Configuration Regression

Dependency Regression

Data Growth Regression

Infrastructure Regression

Measurement Noise
```

### ✅ 28. 중요한 원칙

**성능이 악화됐다고 무조건 최근에 추가한 코드가 원인이라고 단정하지 않는다.**

## 4. Absolute Budget과 Relative Regression

### ✅ 29. Absolute Budget

미리 정의한 절대적인 성능 기준이다.

### ✅ 30. 예시

```text
상품 상세 API p95

800ms 미만
```

### ✅ 31. Relative Regression

기존 버전과 비교해 성능이 얼마나 달라졌는지 판단하는 방식이다.

### ✅ 32. 예시

```text
Baseline:
400ms

Candidate:
600ms
```

### ✅ 33. 상대적 변화

```text
(600 - 400) / 400 × 100

= 50% 증가
```

### ✅ 34. 절대 기준으로 보면?

600ms는 800ms보다 낮다.

```text
Absolute Budget:
PASS
```

### ✅ 35. 상대 비교로 보면?

기존보다 응답시간이 50% 증가했다.

```text
Relative Regression:
DETECTED
```

### ✅ 36. 결론

두 평가 결과가 서로 다를 수 있다.

### ✅ 37. 반대 상황

기존 응답시간이 1,200ms이고 변경 후 1,000ms라면 성능은 개선됐다.

하지만 목표가 800ms라면 여전히 절대 성능 기준을 만족하지 못한다.

### ✅ 38. 중요한 원칙

**절대 목표를 만족하는지와 이전 버전보다 악화됐는지를 각각 평가해야 한다.**

## 5. 성능 변화율 계산

### ✅ 39. Latency 변화율

```text
Latency Change (%)

=

(Current - Baseline)
──────────────────── × 100
      Baseline
```

### ✅ 40. 예시

```text
Baseline:
250ms

Current:
300ms
```

### ✅ 41. 계산

```text
(300 - 250) / 250 × 100

= 20%
```

### ✅ 42. 의미

응답시간이 기존보다 20% 증가했다.

### ✅ 43. Throughput은 방향이 다르다

응답시간은 낮을수록 좋다.

처리량은 동일한 품질 조건에서 높을수록 좋다.

### ✅ 44. 예시

```text
Baseline:
100 RPS

Current:
80 RPS
```

### ✅ 45. 처리량 변화

```text
(80 - 100) / 100 × 100

= -20%
```

### ✅ 46. 중요한 점

Metric의 좋은 방향을 미리 정의해야 한다.

### ✅ 47. 또 다른 주의

Baseline이 0이면 단순 변화율을 계산할 수 없다.

예를 들어 이전 오류율이 0%이고 현재 오류율이 1%라면 상대적 증가율을 무한대로 표시하기보다 절대적인 퍼센트포인트 차이와 실패 건수를 보고한다.

### ✅ 48. 중요한 원칙

**성능 변화율은 Metric의 단위·좋은 방향·기준값의 유효성을 고려해 계산한다.**

## 6. Continuous Benchmarking이란?

### ✅ 49. 정의

성능 측정을 반복적으로 수행하고 변경 이력과 결과를 연결해 시스템의 성능 변화를 지속적으로 관찰하는 방식이다.

### ✅ 50. 일반적인 Benchmark

```text
한 번 테스트

↓

결과 확인

↓

종료
```

### ✅ 51. Continuous Benchmark

```text
Git Commit A
       ↓
Benchmark Result A

Git Commit B
       ↓
Benchmark Result B

Git Commit C
       ↓
Benchmark Result C
```

### ✅ 52. 장점

어떤 변경 이후 성능이 악화됐는지 추적할 수 있다.

### ✅ 53. 중요한 조건

서로 비교할 수 있는 테스트 환경과 Workload가 필요하다.

### ✅ 54. 지속적인 Benchmark의 대상

```text
API Latency

DB Query Count

Query Execution Time

Bundle Size

Memory Usage

Worker Throughput
```

### ✅ 55. 중요한 원칙

**Continuous Benchmarking은 단순히 성능 테스트를 자주 실행하는 것이 아니라 서로 비교 가능한 결과를 축적하는 과정이다.**

## 7. 성능 회귀 탐지 전체 구조

### ✅ 56. 기본 Pipeline

```text
Pull Request
       ↓

       ↓

       ↓
Isolated Test Environment
       ↓
Baseline Benchmark
       ↓
Candidate Benchmark
       ↓

       ↓

       ↓

       ↓

```

### ✅ 57. Changed Files Analysis

어떤 코드가 변경됐는지 확인한다.

변경 내용과 관련된 성능 테스트를 선택한다.

### ✅ 59. Evidence Validation

측정 환경과 요청 수, 오류율, 부하 생성 여부를 검증한다.

### ✅ 60. Regression Evaluation

### ✅ 61. Release Gate

정의된 정책을 충족하지 못하면 배포를 보류하거나 수정하도록 한다.

### ✅ 62. 중요한 원칙

**성능 측정값을 얻는 것보다 그 값을 비교해도 되는지 먼저 검증하는 것이 중요하다.**

## 8. Benchmark Baseline

### ✅ 63. Baseline이란?

새로운 측정 결과를 비교하기 위한 기준이다.

### ✅ 64. Baseline 후보

```text
현재 Production Release

최신 정상 main Commit

승인된 Performance Baseline

최근 여러 정상 Benchmark
```

### ✅ 65. 현재 Production Release

실제 운영 버전과 새 버전의 성능을 비교하는 데 적합하다.

### ✅ 66. 최신 main Commit

Pull Request에서 추가된 변경의 성능 영향을 분석하기 좋다.

### ✅ 67. 승인된 Baseline

장기간 관리해야 하는 성능 기준으로 사용할 수 있다.

### ✅ 68. 중요한 문제

Baseline이 계속 악화되는 버전으로 자동 갱신되면 점진적인 성능 저하를 놓칠 수 있다.

### ✅ 69. 예시

```text
Original:
300ms

PR A:
320ms

PR B:
340ms

PR C:
360ms

PR D:
380ms
```

각 PR의 증가폭은 작지만 전체적으로는 상당히 악화됐다.

### ✅ 70. 따라서

```text
Previous Release Baseline

+

Long-term Reference Baseline

+

Absolute Performance Budget
```

을 함께 관리한다.

### ✅ 71. 중요한 원칙

**직전 버전 비교는 개별 변경의 회귀를 탐지하고 장기 Baseline은 누적된 성능 저하를 탐지한다.**

## 10. 측정 환경 Fingerprint

### ✅ 79. Benchmark 결과에 환경 정보를 남긴다

```json
{
  "environment": "isolated-benchmark",
  "nodeVersion": "24.13.1",
  "pnpmVersion": "10.29.3",
  "postgresMajor": 18,
  "datasetVersion": "catalog-fixture-v1",
  "scenarioVersion": "product-detail-v1",
  "runnerClass": "local-arm64",
  "targetIterationRate": 10
}
```

위 값은 설정 예시이며 실제 테스트 실행 시 측정된 값으로 기록해야 한다.

### ✅ 80. Fingerprint의 목적

측정 결과가 서로 비교 가능한지 판단하기 위해서다.

### ✅ 81. Hash로 관리할 수도 있다

```text
Benchmark Configuration

↓

Canonical JSON

↓

SHA-256 Fingerprint
```

### ✅ 82. 중요한 점

Fingerprint에 Commit SHA까지 포함하면 Baseline과 Candidate가 항상 다르게 나올 수 있다.

### ✅ 83. 따라서

비교 조건 Fingerprint와 실제 코드 버전은 별도 필드로 관리한다.

### ✅ 84. 예시

```text
Environment Fingerprint:
same

Baseline Commit:
A

Candidate Commit:
B
```

### ✅ 85. 중요한 원칙

**코드 버전은 달라야 비교할 수 있고, 코드 이외의 비교 조건은 가능한 한 일관돼야 한다.**

## 11. Measurement Noise

### ✅ 86. Measurement Noise

실제 코드 변경과 직접적인 관계없이 성능 측정값이 달라지는 현상이다.

### ✅ 87. 발생 원인

```text
CPU Scheduling

Background Process

Disk I/O

Network Variance

Garbage Collection

Database Cache

JIT Warm-up
```

### ✅ 88. MacBook에서도 발생할까?

그렇다.

IDE, OrbStack, 브라우저, 로컬 LLM 등이 동시에 실행되면 성능 측정에 영향을 줄 수 있다.

### ✅ 89. GitHub Actions에서도 발생할까?

그렇다.

Runner의 실행 환경과 작업 조건이 항상 완전히 동일하다고 가정할 수 없다.

### ✅ 90. 예시

같은 Commit을 세 번 측정한다.

```text
Run 1:
400ms

Run 2:
425ms

Run 3:
390ms
```

### ✅ 91. 코드가 변경되지 않았지만

측정값이 달라졌다.

### ✅ 92. 따라서

한 번의 측정 결과만으로 작은 성능 차이를 확정하지 않는다.

### ✅ 93. 중요한 원칙

**성능 테스트의 변동성을 이해하지 못하면 정상적인 측정 편차도 코드 Regression으로 잘못 판정할 수 있다.**

## 12. Warm-up과 Steady-state Measurement

### ✅ 94. Warm-up

본격적인 성능 측정 전에 애플리케이션과 DB를 일정 시간 실행하는 과정이다.

### ✅ 95. 필요한 이유

```text
Node.js 초기 실행

JIT Compilation

Database Connection Pool 생성

PostgreSQL Cache

Application Cache
```

등이 초기 요청에서 영향을 줄 수 있기 때문이다.

### ✅ 96. 예시

```text
Warm-up:
30초

Measurement:
60초
```

### ✅ 97. 주의

이 시간은 설명용이다.

실제 시스템이 안정화되는 시간을 관측한 뒤 결정해야 한다.

### ✅ 98. 잘못된 비교

```text
Baseline:
Warm Cache

Candidate:
Cold Cache
```

### ✅ 99. 결과

코드 변경보다 Cache 상태 차이 때문에 Candidate가 느려질 수 있다.

### ✅ 100. Cold Start도 측정해야 할까?

필요하다.

다만 Warm 상태 성능과 별도 시나리오로 측정한다.

### ✅ 101. 중요한 원칙

**Warm-up 이후의 정상 처리 성능과 처음 실행될 때의 Cold Start 성능을 구분한다.**

## 13. 반복 측정과 Median

### ✅ 102. 여러 번 측정한다

예를 들어 동일한 Benchmark를 다섯 번 실행한다.

```text

410ms

Run 3:
405ms

Run 4:
650ms

Run 5:
395ms
```

### ✅ 103. 평균값

비정상적으로 큰 값의 영향을 받을 수 있다.

### ✅ 104. 중앙값

정렬된 값의 가운데 값이다.

```text
395

400

405

410

650
```

### ✅ 105. Median

```text
405ms
```

### ✅ 106. 중요한 한계

Median을 사용한다고 650ms의 측정값을 무시해도 된다는 뜻은 아니다.

### ✅ 107. 650ms가 발생한 이유

실제 Garbage Collection이나 DB Lock 등 중요한 문제일 수 있다.

### ✅ 108. 따라서

```text

Individual Runs

Variation
```

을 함께 저장한다.

### ✅ 109. 중요한 원칙

**반복 측정의 중앙값은 비교 안정성을 높이는 도구이고 큰 변동 자체도 조사할 가치가 있는 정보다.**

## 14. p95의 Median과 전체 요청의 p95

### ✅ 110. 중요한 통계적 구분

각 실행에서 계산한 p95를 모아 중앙값을 구할 수 있다.

```text
Run A p95:
400ms

Run B p95:
420ms

Run C p95:
410ms
```

### ✅ 111. Median of Run p95

```text
410ms
```

### ✅ 112. 하지만 이것은?

세 실행의 모든 요청 데이터를 합쳐 계산한 전체 p95와 같지 않다.

### ✅ 113. 이유

분위수는 단순히 평균하거나 중앙값을 구한다고 전체 분포의 분위수가 되지 않기 때문이다.

### ✅ 114. 따라서 지표 이름을 명확하게 지정한다

```text
median_run_p95_ms
```

또는:

```text
pooled_request_p95_ms
```

### ✅ 115. 각각의 목적

Median Run p95는 반복 실행 비교에 사용할 수 있다.

Pooled Request p95는 합쳐진 요청 분포를 분석하는 데 사용한다.

### ✅ 116. 중요한 원칙

**서로 다른 통계 계산 방식을 동일한 p95라는 이름으로 혼용하지 않는다.**

## 15. Regression Threshold 설계

### ✅ 117. 변화량이 1%만 증가해도 실패시킬까?

일반적으로 지나치게 민감한 기준이 될 수 있다.

### ✅ 118. 상대 변화량 기준

```text
p95가 15% 이상 증가
```

### ✅ 119. 절대 변화량 기준

```text
p95가 50ms 이상 증가
```

### ✅ 120. 두 기준을 함께 사용할 수 있다

```text
Relative Increase >= 15%

AND

Absolute Increase >= 50ms
```

### ✅ 121. 예시 A

```text
Baseline:
20ms

Current:
25ms
```

25% 증가했지만 실제 증가 시간은 5ms다.

### ✅ 122. 예시 B

```text
Baseline:
400ms

Current:
500ms
```

25% 증가했고 실제 증가 시간도 100ms다.

### ✅ 123. 두 번째 사례

상대 기준과 절대 기준을 모두 위반한다.

### ✅ 124. 중요한 주의

위 임계값은 정책 설계 예시다.

실제 허용 범위는 업무 중요도와 기존 측정 변동성을 바탕으로 결정한다.

### ✅ 125. 중요한 원칙

**상대 변화율과 실제 사용자에게 추가되는 지연을 함께 고려하면 불필요한 회귀 판정을 줄일 수 있다.**

## 16. Performance Gate 상태

### ✅ 126. PASS와 FAIL만으로 충분할까?

측정 데이터가 부족하거나 환경이 다르면 판단할 수 없는 경우가 있다.

### ✅ 127. 추천 상태

```text
PASS

WARN

FAIL

INCONCLUSIVE

NOT_VERIFIED
```

### ✅ 128. PASS

필수 검증 조건과 성능 기준을 충족했다.

### ✅ 129. WARN

성능 변화가 있지만 즉시 배포를 차단할 수준인지 추가 확인이 필요하다.

### ✅ 130. FAIL

정의된 성능 Budget 또는 필수 안전 기준을 위반했다.

### ✅ 131. INCONCLUSIVE

실험은 수행했지만 근거 부족이나 환경 차이 때문에 판단하기 어렵다.

### ✅ 132. NOT_VERIFIED

필수 테스트를 수행하지 못했다.

### ✅ 133. 중요한 점

필수 Gate의 INCONCLUSIVE와 NOT_VERIFIED를 자동으로 PASS 처리하지 않는다.

### ✅ 134. 중요한 원칙

**불확실한 결과와 정상 결과를 구분해야 성능 검증 자동화가 신뢰성을 유지할 수 있다.**

## 20. k6 Benchmark 코드

### ✅ 155. 예시 파일

```text
tests/performance/product-detail.js
```

### ✅ 156. 기본 코드

```javascript
import http from 'k6/http';
import { check } from 'k6';

const BASE_URL = __ENV.TARGET_BASE_URL;
const PRODUCT_ID = __ENV.TEST_PRODUCT_ID;

if (
  !BASE_URL ||
  !/^http:\/\/127\.0\.0\.1:\d+$/.test(BASE_URL)
) {
  throw new Error('ISOLATED_LOCAL_TARGET_REQUIRED');
}

if (!PRODUCT_ID) {
  throw new Error('TEST_PRODUCT_ID_REQUIRED');
}

const RATE = Number(__ENV.BENCHMARK_RATE || '5');

if (!Number.isInteger(RATE) || RATE < 1 || RATE > 20) {
  throw new Error('INVALID_BENCHMARK_RATE');
}

export const options = {
  scenarios: {
    product_detail: {
      executor: 'constant-arrival-rate',

      rate: RATE,

      timeUnit: '1s',

      duration: '60s',

      preAllocatedVUs: 20,

      maxVUs: 40,
    },
  },

  summaryTrendStats: [
    'avg',
    'med',
    'p(95)',
    'p(99)',
    'max',
    'count',
  ],

  thresholds: {
    http_req_failed: [
      'rate<0.01',
    ],

    http_req_duration: [
      'p(95)<800',
    ],

    dropped_iterations: [
      'count==0',
    ],

    checks: [
      'rate>0.99',
    ],

    http_reqs: [
      `count>=${RATE * 60}`,
    ],
  },
};

export default function () {
  const response = http.get(
    `${BASE_URL}/api/products/${encodeURIComponent(PRODUCT_ID)}`,
    {
      redirects: 0,

      timeout: '5s',

      tags: {
        operation: 'product_detail',
      },
    },
  );

  check(response, {
    'status is 200': (r) => r.status === 200,

    'expected product returned': (r) => {
      try {
        return r.json('id') === PRODUCT_ID;
      } catch {
        return false;
      }
    },
  });
}
```

### ✅ 157. 중요한 전제

API 경로와 Response Schema는 설명용이다.

실제 상품 API가 ID를 다른 형태로 반환한다면 Assertion을 변경해야 한다.

### ✅ 158. 테스트의 특징

단순 HTTP 200뿐 아니라 예상 상품이 실제로 반환되는지도 확인한다.

### ✅ 159. 부하 제한

예제에서 Rate를 1~20으로 제한했다.

이 범위가 안전한 실제 Capacity라는 의미는 아니다.

초기 로컬 실험의 최대 부하를 제한하기 위한 예시다.

### ✅ 160. 추가 안전 조건

localhost 주소라는 사실만으로 실제 운영 DB와 격리됐다고 판단하지 않는다.

실제 Backend의 연결 대상과 Provider 설정을 실행 전에 별도로 확인한다.

## 21. k6 결과를 JSON으로 저장하기

### ✅ 161. 필요한 이유

터미널 출력만 보면 자동 비교하기 어렵다.

### ✅ 162. handleSummary

k6의 테스트 종료 결과를 가공하거나 파일에 저장하는 기능이다.

### ✅ 163. 앞선 스크립트에 추가할 예시

```javascript
export function handleSummary(data) {
  const metricValues = (name) =>
    data.metrics[name]?.values ?? {};

  const duration =
    metricValues('http_req_duration');

  const failed =
    metricValues('http_req_failed');

  const requests =
    metricValues('http_reqs');

  const drops =
    metricValues('dropped_iterations');

  const summary = {
    scenario: 'product-detail-v1',

    commitSha:
      __ENV.BENCHMARK_COMMIT || 'unknown',

    targetIterationRate: RATE,

    requests:
      requests.count ?? null,

    observedRequestRate:
      requests.rate ?? null,

    averageMs:
      duration.avg ?? null,

    p95Ms:
      duration['p(95)'] ?? null,

    p99Ms:
      duration['p(99)'] ?? null,

    errorRate:
      failed.rate ?? null,

    droppedIterations:
      drops.count ?? 0,
  };

  const output = JSON.stringify(
    summary,
    null,
    2,
  );

  return {
    stdout: output,

    'benchmark-result.json': output,
  };
}
```

### ✅ 164. 중요한 전제

k6의 실제 설치 버전에서 Summary 데이터 구조를 확인해야 한다.

### ✅ 165. dropped_iterations

실행되지 못한 Iteration이 없어 Metric이 결과에 나타나지 않는 경우를 처리할 수 있다.

다만 테스트가 정상 완료되지 않았거나 Summary 자체가 누락됐다면 0건으로 대체해 정상 판정하지 않는다.

### ✅ 166. 결과 파일의 한계

위 JSON은 일부 Metric을 추출한 것이다.

실제 테스트의 종료 코드와 전체 로그를 함께 기록해야 한다.

### ✅ 167. 중요한 원칙

**Benchmark 결과 JSON이 만들어졌다는 사실만으로 테스트가 통과했다고 판단하지 않는다.**

## 24. TypeScript Regression Evaluator

### ✅ 186. 성능 판정 정책

```typescript
type PerformanceStatus =
  | 'PASS'
  | 'WARN'
  | 'FAIL'
  | 'INCONCLUSIVE';

interface PerformancePolicy {
  minRequests: number;

  maxP95Ms: number;

  maxErrorRate: number;

  minAchievedRateRatio: number;

  relativeRegressionLimit: number;

  absoluteRegressionLimitMs: number;
}

interface PerformanceDecision {
  status: PerformanceStatus;

  reasons: string[];

  relativeChange?: number;

  absoluteChangeMs?: number;
}
```

### ✅ 187. Evidence 검증 함수

```typescript
function isValidRun(
  run: BenchmarkRun,
  policy: PerformancePolicy,
): boolean {
  const numericValues = [
    run.targetRate,
    run.observedRate,
    run.requestCount,
    run.p95Ms,
    run.errorRate,
    run.droppedIterations,
  ];

  if (
    !numericValues.every(Number.isFinite)
  ) {
    return false;
  }

  return (
    run.completed &&
    run.targetRate > 0 &&
    run.observedRate >= 0 &&
    run.requestCount >= policy.minRequests &&
    Number.isInteger(run.requestCount) &&
    run.p95Ms > 0 &&
    run.errorRate >= 0 &&
    run.errorRate <= 1 &&
    run.droppedIterations === 0 &&
    run.observedRate / run.targetRate >=
      policy.minAchievedRateRatio
  );
}
```

### ✅ 188. 비교 함수

```typescript
function evaluatePerformance(
  baseline: BenchmarkRun,
  candidate: BenchmarkRun,
  policy: PerformancePolicy,
): PerformanceDecision {
  if (
    !isValidRun(baseline, policy) ||
    !isValidRun(candidate, policy)
  ) {
    return {
      status: 'INCONCLUSIVE',

      reasons: [
        'INSUFFICIENT_OR_INVALID_EVIDENCE',
      ],
    };
  }

  const comparable =
    baseline.scenarioVersion ===
      candidate.scenarioVersion &&

    baseline.datasetVersion ===
      candidate.datasetVersion &&

    baseline.environmentFingerprint ===
      candidate.environmentFingerprint &&

    baseline.targetRate ===
      candidate.targetRate;

  if (!comparable) {
    return {
      status: 'INCONCLUSIVE',

      reasons: [
        'BENCHMARK_CONDITIONS_MISMATCH',
      ],
    };
  }

  const absoluteChangeMs =
    candidate.p95Ms - baseline.p95Ms;

  const relativeChange =
    absoluteChangeMs / baseline.p95Ms;

  const reasons: string[] = [];

  if (
    candidate.errorRate >= policy.maxErrorRate
  ) {
    reasons.push('ERROR_BUDGET_EXCEEDED');
  }

  if (
    candidate.p95Ms >= policy.maxP95Ms
  ) {
    reasons.push('LATENCY_BUDGET_EXCEEDED');
  }

  if (
    reasons.length > 0
  ) {
    return {
      status: 'FAIL',

      reasons,

      relativeChange,

      absoluteChangeMs,
    };
  }

  if (
    baseline.errorRate >= policy.maxErrorRate
  ) {
    return {
      status: 'INCONCLUSIVE',

      reasons: [
        'BASELINE_NOT_HEALTHY',
      ],

      relativeChange,

      absoluteChangeMs,
    };
  }

  if (
    relativeChange >=
      policy.relativeRegressionLimit &&

    absoluteChangeMs >=
      policy.absoluteRegressionLimitMs
  ) {
    return {
      status: 'WARN',

      reasons: [
        'RELATIVE_PERFORMANCE_REGRESSION',
      ],

      relativeChange,

      absoluteChangeMs,
    };
  }

  return {
    status: 'PASS',

    reasons: [],

    relativeChange,

    absoluteChangeMs,
  };
}
```

### ✅ 189. 정책 설정 예시

```typescript

  maxP95Ms: 800,

  maxErrorRate: 0.01,

  minAchievedRateRatio: 0.95,

  relativeRegressionLimit: 0.15,

  absoluteRegressionLimitMs: 50,
};
```

## 33. pg_stat_statements Delta Query

### ✅ 256. Snapshot 저장 구조

독립된 분석용 DB나 테스트 결과 파일에 다음 데이터를 저장할 수 있다.

```sql
CREATE TABLE benchmark_query_snapshots (
  run_id TEXT NOT NULL,

  phase TEXT NOT NULL
    CHECK (phase IN ('BEFORE', 'AFTER')),

  dbid OID NOT NULL,

  userid OID NOT NULL,

  queryid BIGINT NOT NULL,

  toplevel BOOLEAN NOT NULL,

  calls BIGINT NOT NULL,

  total_exec_time DOUBLE PRECISION NOT NULL,

  PRIMARY KEY (
    run_id,
    phase,
    dbid,
    userid,
    queryid,
    toplevel
  )
);
```

### ✅ 257. 차이 계산

```sql
SELECT
  a.queryid,

  a.calls - b.calls
    AS delta_calls,

  a.total_exec_time - b.total_exec_time
    AS delta_total_ms,

  (
    a.total_exec_time - b.total_exec_time
  ) / NULLIF(
    a.calls - b.calls,
    0
  ) AS delta_mean_ms

FROM benchmark_query_snapshots AS a

JOIN benchmark_query_snapshots AS b
  ON a.run_id = b.run_id
 AND a.dbid = b.dbid
 AND a.userid = b.userid
 AND a.queryid = b.queryid
 AND a.toplevel = b.toplevel

WHERE a.run_id = $1

  AND a.phase = 'AFTER'

  AND b.phase = 'BEFORE'

  AND a.calls > b.calls

  AND a.total_exec_time >= b.total_exec_time

ORDER BY delta_total_ms DESC;
```

### ✅ 258. 중요한 한계

이 Query는 Before와 After에 모두 존재하는 Entry만 비교한다.

### ✅ 259. 새로운 Query

Benchmark 이후 처음 등장한 Query는 별도로 수집해야 한다.

### ✅ 260. 사라진 Query

통계 Entry가 사라졌다면 Eviction이나 Reset 여부를 확인해야 한다.

### ✅ 261. 버전 변경

PostgreSQL Major Version이 바뀌거나 Query 구조가 변경되면 동일한 Query ID가 유지된다고 가정하지 않는다.

### ✅ 262. 중요한 원칙

**pg_stat_statements는 강력한 분석 도구지만 통계 Reset·Entry 변경·Query ID의 한계를 고려해야 정확한 회귀 분석이 가능하다.**

## 37. Node.js Bundle Budget Script

### ✅ 289. 초기 JavaScript 크기를 측정한다

예시 파일:

```text
scripts/check-bundle-budget.mjs
```

### ✅ 290. 코드

```javascript
import {
  readFileSync,
  statSync,
} from 'node:fs';

import path from 'node:path';

import {
  gzipSync,
} from 'node:zlib';

const distDir = path.resolve(
  process.argv[2] || 'dist',
);

const entryKey =
  process.argv[3] || 'index.html';

const manifestPath = path.join(
  distDir,
  '.vite',
  'manifest.json',
);

const manifest = JSON.parse(
  readFileSync(manifestPath, 'utf8'),
);

const visited = new Set();

const files = new Set();

function collectStaticImports(key) {
  if (visited.has(key)) {
    return;
  }

  const chunk = manifest[key];

  if (!chunk) {
    throw new Error(
      `MISSING_MANIFEST_ENTRY:${key}`,
    );
  }

  visited.add(key);

  if (
    typeof chunk.file === 'string' &&
    chunk.file.endsWith('.js')
  ) {
    files.add(chunk.file);
  }

  for (const importedKey of chunk.imports ?? []) {
    collectStaticImports(importedKey);
  }
}

collectStaticImports(entryKey);

if (files.size === 0) {
  throw new Error(
    'NO_INITIAL_JAVASCRIPT_FOUND',
  );
}

let rawBytes = 0;

let gzipBytes = 0;

const assets = [];

for (const file of files) {
  const absolutePath = path.join(
    distDir,
    file,
  );

  const content = readFileSync(
    absolutePath,
  );

  const size = statSync(
    absolutePath,
  ).size;

  const compressedSize =
    gzipSync(content).length;

  rawBytes += size;

  gzipBytes += compressedSize;

  assets.push({
    file,

    rawBytes: size,

    gzipBytes: compressedSize,
  });
}

const budgetGzipBytes = 250 * 1024;

const report = {
  entryKey,

  assetCount: assets.length,

  rawBytes,

  gzipBytes,

  budgetGzipBytes,

  status:
    gzipBytes <= budgetGzipBytes
      ? 'PASS'
      : 'FAIL',

  assets,
};

console.log(
  JSON.stringify(report, null, 2),
);

if (report.status === 'FAIL') {
  process.exitCode = 1;
}
```

### ✅ 291. 실행 예시

```bash
node scripts/check-bundle-budget.mjs \
  dist \
  index.html
```

### ✅ 292. 측정 의미

Entry와 정적으로 연결된 JavaScript Chunk의 크기를 중복 없이 합산한다.

### ✅ 293. 중요한 점

동적으로 로딩되는 JavaScript와 CSS, 이미지 등은 이 예시의 Budget에 포함하지 않는다.

### ✅ 294. Gzip 측정 한계

스크립트에서 계산한 Gzip 크기와 CloudFront에서 실제 전송되는 압축 크기는 다를 수 있다.

### ✅ 295. Budget 250KiB

설명용 기준이며 실제 프로젝트에서 검증된 권장 최대치가 아니다.

### ✅ 296. 중요한 원칙

**자동 Bundle Budget은 무엇을 합산했는지와 어떤 리소스가 제외됐는지를 명확하게 정의해야 한다.**


### ✅ 339. 특히 관리자 업무

대용량 주문 Excel Export를 동기적으로 처리하면 다른 API 응답에도 영향을 줄 수 있다.

### ✅ 340. Event Loop Delay 측정

Node.js의 `monitorEventLoopDelay()`를 활용할 수 있다.

### ✅ 341. 개념 코드

```typescript
import {
  monitorEventLoopDelay,
} from 'node:perf_hooks';

const histogram =
  monitorEventLoopDelay({
    resolution: 20,
  });

histogram.enable();

const interval = setInterval(() => {
  const p95Ms =
    histogram.percentile(95) / 1e6;

  const p99Ms =
    histogram.percentile(99) / 1e6;

  console.log({
    metric: 'event_loop_delay',

    p95Ms,

    p99Ms,
  });

  histogram.reset();
}, 10_000);

interval.unref();

export function stopMonitoring() {
  clearInterval(interval);

  histogram.disable();
}
```

### ✅ 342. 중요한 점

Histogram에서 반환하는 시간은 나노초 단위이므로 밀리초로 변환한다.

### ✅ 343. 적용 시 주의

기존 Logger와 모니터링 시스템을 재사용하고 수집 비용을 고려해야 한다.

### ✅ 344. 중요한 원칙

**API 지연 증가를 DB 병목으로 단정하지 말고 Node.js Runtime의 실행 지연도 함께 조사한다.**

## 47. Git Bisect와 Performance Regression

### ✅ 368. 어느 Commit부터 느려졌는지 모를 때

Git Bisect를 활용할 수 있다.

### ✅ 369. 개념

정상 Commit과 문제가 있는 Commit 사이의 변경을 이분 탐색 방식으로 조사한다.

```text
Known Good
    ↓
Commit A
    ↓
Commit B
    ↓
Commit C
    ↓
Known Bad
```

### ✅ 370. 명령 예시

현재 작업 내용이 없는 별도 Worktree 또는 테스트 Checkout에서 실행하는 것이 안전하다.

```bash
git bisect start

git bisect bad <bad-commit>

git bisect good <good-commit>
```

### ✅ 371. 자동 Benchmark

```bash
git bisect run \
  ./scripts/benchmark-bisect.sh
```

### ✅ 372. 중요한 조건

`benchmark-bisect.sh`는 실제 비교 정책을 구현해야 한다.

### ✅ 373. 종료 코드

```text
0:
Good

1~127:
Bad 판정 가능

125:
Skip
```

125는 특별히 해당 Commit을 검증할 수 없는 경우에 사용한다.

### ✅ 374. 주의

빌드 실패나 환경 실패를 성능 Regression으로 잘못 분류하지 않도록 한다.

### ✅ 375. 종료

```bash
git bisect reset
```

### ✅ 376. 중요한 한계

성능 회귀가 여러 변경의 조합으로 발생하거나 Commit마다 성능이 좋아졌다 나빠졌다 한다면 단순 Bisect 결과를 해석하기 어려울 수 있다.

### ✅ 377. 중요한 원칙

**Git Bisect는 성능 문제가 시작된 변경을 좁히는 도구이며 재현 가능한 Benchmark가 먼저 준비돼 있어야 한다.**

## 49. GitHub Actions 예시

### ✅ 386. Workflow

```yaml
name: Performance Verification

on:
  pull_request:

  workflow_dispatch:

permissions:
  contents: read

jobs:
  performance:
    runs-on: ubuntu-latest

    timeout-minutes: 25

    services:
      postgres:
        image: postgres:18-alpine

        env:
          POSTGRES_USER: benchmark_runner
          POSTGRES_PASSWORD: benchmark_only_password
          POSTGRES_DB: benchmark_test

        ports:
          - 5432:5432

        options: >-
          --health-cmd "pg_isready -U benchmark_runner -d benchmark_test"
          --health-interval 5s
          --health-timeout 5s
          --health-retries 10

    env:
      NODE_ENV: test

      DATABASE_URL: postgresql://benchmark_runner:benchmark_only_password@127.0.0.1:5432/benchmark_test

      PERFORMANCE_ENV: isolated-test

    steps:
      - name: Checkout
        uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Setup pnpm
        uses: pnpm/action-setup@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '24'
          cache: pnpm

      - name: Install dependencies
        run: pnpm install --frozen-lockfile

      - name: Verify test environment
        run: pnpm run performance:preflight

      - name: Prepare test database
        run: pnpm run performance:prepare

      - name: Run query budgets
        run: pnpm run test:query-budget

      - name: Build frontend
        run: pnpm run build:frontend

      - name: Check bundle budget
        run: pnpm run performance:bundle

      - name: Run API benchmark
        run: pnpm run performance:benchmark

      - name: Evaluate regression
        run: pnpm run performance:evaluate

      - name: Upload performance evidence
        if: always()
        uses: actions/upload-artifact@v4
```

## 51. Performance History Database

### ✅ 398. 장기적으로 성능 이력을 관리할 수 있다

가벼운 Markdown이나 JSON 기록으로 시작하고 필요해지면 PostgreSQL에 저장한다.

### ✅ 399. 테이블 예시

```sql
CREATE TABLE performance_benchmark_runs (
  id UUID PRIMARY KEY,

  run_id TEXT NOT NULL,

  commit_sha TEXT NOT NULL,

  scenario_key TEXT NOT NULL,

  scenario_version TEXT NOT NULL,

  environment_fingerprint TEXT NOT NULL,

  dataset_version TEXT NOT NULL,

  request_count BIGINT NOT NULL
    CHECK (request_count >= 0),

  target_rate DOUBLE PRECISION,

  observed_rate DOUBLE PRECISION,

  p95_ms DOUBLE PRECISION,

  error_rate DOUBLE PRECISION
    CHECK (
      error_rate IS NULL
      OR error_rate BETWEEN 0 AND 1
    ),

  dropped_iterations BIGINT
    CHECK (
      dropped_iterations IS NULL
      OR dropped_iterations >= 0
    ),

  result_status TEXT NOT NULL
    CHECK (
      result_status IN (
        'PASS',
        'WARN',
        'FAIL',
        'INCONCLUSIVE',
        'NOT_VERIFIED'
      )
    ),

  measured_at TIMESTAMPTZ NOT NULL,

  created_at TIMESTAMPTZ
    NOT NULL DEFAULT NOW(),

  UNIQUE (
    run_id,
    scenario_key
  )
);
```

### ✅ 400. 성능 변화 조회

```sql
SELECT
  measured_at,

  commit_sha,

  p95_ms,

  error_rate,

  request_count,

  LAG(p95_ms) OVER (
    ORDER BY measured_at, id
  ) AS previous_p95_ms

FROM performance_benchmark_runs

WHERE scenario_key = $1

  AND scenario_version = $2

  AND environment_fingerprint = $3

  AND dataset_version = $4

  AND result_status = 'PASS'

ORDER BY measured_at, id;
```

### ✅ 401. 중요한 점

이 SQL은 비교 가능한 정상 Benchmark의 추세를 확인하는 예시다.

실패한 실행은 별도 조회를 통해 관리해야 한다.

### ✅ 402. 중요한 원칙

**성능 이력 조회에서도 비교 조건이 다른 결과를 하나의 추세로 섞지 않는다.**

## 📌 요약

1112에서는 트래픽 증가에 대비해 현재 시스템의 처리 능력과 병목을 측정하는 방법을 다뤘다.

```text
Traffic Forecast
       ↓
Load Test
       ↓
Capacity Estimation
       ↓
Bottleneck Analysis
       ↓
Scaling Decision
```

1113에서는 이를 지속적인 코드 변경 검증으로 확장했다.

```text
Code Change
       ↓
Relevant Benchmark
       ↓
Stable Test Environment
       ↓
Baseline Measurement
       ↓
Candidate Measurement
       ↓
Evidence Validation
       ↓
Absolute Budget
       ↓
Relative Regression
       ↓
Bottleneck Diagnosis
       ↓
Optimization
       ↓
Re-benchmark
       ↓
Release Decision
```

이번 편에서 가장 중요한 원칙은 다음과 같다.

**첫 번째 — 기능 정상과 성능 정상은 다르다.**

기존 기능이 모두 동작하더라도 Query 수와 응답시간이 증가했다면 별도의 성능 검증이 필요하다.

**두 번째 — 절대 기준과 상대 비교를 함께 사용한다.**

```text
Performance Budget

+

Previous Version Comparison

+

Long-term Baseline
```

을 이용해야 개별 Regression과 누적 성능 저하를 모두 탐지할 수 있다.

**세 번째 — 비교 가능한 환경이 먼저다.**

측정 환경·데이터·Workload가 다르면 코드 변경의 실제 성능 영향을 판단하기 어렵다.

**네 번째 — Benchmark의 품질을 먼저 검증한다.**

실제 요청량, 오류율, 표본 수, dropped_iterations를 확인하지 않으면 빠르게 실패하는 시스템이나 충분히 부하를 받지 않은 시스템을 정상으로 판단할 수 있다.

**다섯 번째 — DB Query 수와 실행시간을 함께 본다.**

Query 수가 증가하지 않았더라도 실행 계획과 데이터량 변화로 인해 느려질 수 있다.

**여섯 번째 — Frontend 성능도 배포 전에 확인한다.**

Bundle Size와 Lighthouse, 실제 사용자 성능 지표를 목적에 따라 분리한다.

**일곱 번째 — AI가 원인 후보를 제안하더라도 실제 측정으로 검증한다.**

Git Diff와 성능 지표를 연결하고 수정 이후 동일한 조건으로 재측정해야 한다.

**여덟 번째 — 성능 개선 과정에서 업무 정확성을 유지한다.**

고객 신청·가격 계산·주문 저장·알림 처리의 정확성을 희생하면서 응답시간만 줄여서는 안 된다.

현재 투게더몰에서는 다음 순서가 현실적이다.

```text
1. 상품 상세·관리자 주문 검색 Baseline 기록

2. Prisma Query Count 측정

3. 고객 Frontend / Admin Bundle Size 기록

4. 독립된 Performance Test DB 준비

5. k6 API Benchmark

6. 동일 조건의 이전 버전 비교

7. Performance Report 자동 생성

8. 안정적인 지표부터 GitHub Actions Gate 적용

9. 실제 Production 성능과 Release ID 연결

10. AI 기반 병목 분석 및 재측정
```

특히 현재 1인 개발 환경에서는 모든 코드 변경에 대규모 부하 테스트를 실행하는 방식보다, **Query Count와 Bundle Size처럼 자동 검증하기 쉬운 지표를 먼저 적용하고 중요한 API만 선별해 Benchmark를 수행하는 것**이 효율적이다.

성능 테스트 결과가 충분히 축적된 이후에 p95 Regression Gate와 장기 Performance History를 확대하면 된다.

최종적으로 기억해야 할 원칙은 다음과 같다.

**좋은 Performance Engineering은 서비스를 한 번 빠르게 만드는 것이 아니다. 새로운 기능이 추가되고 데이터가 증가하며 코드와 인프라가 계속 변경되는 동안에도 성능 저하를 조기에 발견하고, 실제 업무 정확성을 유지하면서 지속적으로 개선할 수 있는 검증 구조를 만드는 것이다.**
