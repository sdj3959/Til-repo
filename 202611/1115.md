## 2. Profiling이란?

### ✅ 11. 정의

Profiling은 프로그램이 실행되는 동안 CPU·메모리·함수 호출 등의 자원 사용 특성을 측정하고 분석하는 기술이다.

### ✅ 12. 일반적인 Debugging과의 차이

Debugging은 잘못된 동작의 원인을 찾는 데 집중한다.

Profiling은 정상적으로 실행되더라도 지나치게 많은 시간이나 자원을 사용하는 부분을 찾는 데 집중한다.

### ✅ 13. 예시

```text
Debugging:

왜 가격이 잘못 계산됐는가?
```

```text
Profiling:

왜 가격 계산에 700ms가 걸리는가?
```

### ✅ 14. 대표적인 Profiling 종류

| 종류 | 분석 대상 |
|---|---|
| CPU Profile | 함수와 Call Stack의 실행 특성 |
| Heap Profile | JavaScript 객체의 메모리 사용 |
| Allocation Profile | 메모리 할당이 발생하는 코드 |
| Wall-clock Profile | 실제 경과시간과 대기 |
| React Profile | 컴포넌트 렌더링 비용 |
| System Profile | OS·Native Code·Thread 등의 자원 사용 |

### ✅ 15. 중요한 구분

하나의 Profiling 도구가 모든 종류의 성능 문제를 완벽하게 분석하는 것은 아니다.

### ✅ 16. 중요한 원칙

**성능 문제의 종류를 먼저 구분하고 그 문제에 맞는 Profiling 방법을 선택해야 한다.**

## 4. Tracing과 Profiling의 차이

### ✅ 24. Tracing

업무 작업 단위의 실행 흐름을 추적한다.

```text
application.submit
       ├── validate
       ├── calculatePricing
       └── persistOrder
```

### ✅ 25. Profiling

실행 중인 함수의 Call Stack과 자원 사용 특성을 분석한다.

```text
calculatePricing
       ├── normalizePlans
       ├── findDiscountRule
       ├── calculateFinalPrice
       └── sortRecommendations
```

### ✅ 26. 중요한 차이

Trace의 Span Duration은 일반적으로 작업의 경과시간이다.

CPU Profile은 실행 Stack의 샘플을 이용해 함수의 실행 비중을 분석할 수 있다.

### ✅ 27. 예시

```text
Database Span:
800ms

JavaScript CPU Usage:
낮음
```

이 경우 실제로 SQL 실행이나 네트워크 응답을 기다리는 상황일 수 있다.

### ✅ 28. 반대로

```text
Pricing Span:
800ms

JavaScript CPU Usage:
높음
```

이 경우 가격 계산 로직 내부의 연산 비용이 원인 후보가 된다.

### ✅ 29. 중요한 원칙

**Span이 오래 걸린다고 해당 Span의 JavaScript 함수가 그 시간 동안 계속 CPU를 사용했다고 판단해서는 안 된다.**

## 5. CPU Time과 Wall-clock Time

### ✅ 30. Wall-clock Time

작업이 시작된 시점부터 종료된 시점까지 실제로 흐른 시간이다.

### ✅ 31. CPU Time

CPU가 특정 프로세스나 스레드의 작업을 실제로 실행하는 데 사용한 시간이다.

### ✅ 32. 예시

```text
API 시작:
10:00:00

DB 응답:
10:00:02

API 종료:
10:00:03
```

전체 Wall-clock Time은 3초다.

### ✅ 33. 하지만

실제로 JavaScript가 CPU를 사용한 시간은 3초보다 훨씬 짧을 수 있다.

### ✅ 34. CPU 작업과 I/O 대기

```text
Wall-clock Time
       ├── CPU Execution
       ├── Database Waiting
       ├── Network Waiting
       ├── Scheduling Delay
       └── Other Waiting
```

위 구성은 개념적인 설명이다. 여러 스레드와 병렬 작업에서는 시간 관계가 더 복잡해질 수 있다.

### ✅ 35. Node.js 프로세스 CPU Time

여러 스레드에서 소비한 CPU 시간이 합산될 수 있다.

따라서 여러 CPU 코어를 사용하는 경우 프로세스 CPU Time이 측정된 Wall-clock Time보다 클 수도 있다.

### ✅ 36. 중요한 주의

V8 CPU Profile의 샘플 시간 비중을 운영체제가 측정한 정확한 CPU Time과 동일하게 취급하지 않는다.

### ✅ 37. 중요한 원칙

**실제로 시간이 오래 걸린 작업과 CPU를 많이 소비한 작업을 구분해야 적절한 최적화 방법을 선택할 수 있다.**

## 6. Node.js에서 CPU 사용량을 직접 측정하기

### ✅ 38. 기본 측정 API

Node.js는 다음 기능을 제공한다.

```text
process.cpuUsage()

performance.now()
```

### ✅ 39. 독립 실행 예시

```javascript
// scripts/profile/cpu-vs-wall.mjs

import { performance } from 'node:perf_hooks';

import { setTimeout as sleep } from 'node:timers/promises';

function calculate() {
  let result = 0;

  for (let i = 0; i < 5_000_000; i += 1) {
    result += Math.sqrt(i);
  }

  return result;
}

const startedAt = performance.now();

const cpuBefore = process.cpuUsage();

await sleep(1_000);

const result = calculate();

const cpu = process.cpuUsage(cpuBefore);

console.log({
  result,

  wallTimeMs:
    performance.now() - startedAt,

  userCpuMs:
    cpu.user / 1_000,

  systemCpuMs:
    cpu.system / 1_000,

  totalCpuMs:
    (cpu.user + cpu.system) / 1_000,
});
```

### ✅ 40. 실행

```bash
node scripts/profile/cpu-vs-wall.mjs
```

### ✅ 41. 예상 결과

```text
Wall Time:
1,000ms 이상

CPU Time:
실제 연산과 프로세스 작업에 사용된 시간
```

정확한 실행시간은 장비와 Runtime에 따라 달라진다.

### ✅ 42. 왜 sleep 시간이 CPU Time과 같지 않을까?

`sleep()`으로 기다리는 동안 프로세스가 해당 JavaScript 작업을 계속 계산하는 것은 아니기 때문이다.

### ✅ 43. 중요한 한계

`process.cpuUsage()`는 해당 프로세스 전체의 CPU 사용량을 측정한다.

동시에 여러 요청이 실행된다면 특정 고객 요청 하나만의 CPU 사용량을 정확하게 분리하는 용도로 사용하기 어렵다.

### ✅ 44. 중요한 원칙

**CPU Time을 측정할 때는 측정 대상이 전체 Process인지 특정 Thread인지 특정 함수인지 먼저 확인한다.**

## 7. CPU-bound와 I/O-bound

### ✅ 45. CPU-bound

CPU 연산 능력이 주요 병목이 되는 작업이다.

### ✅ 46. 예시

```text
대규모 가격 계산

복잡한 데이터 변환

대용량 JSON 처리

Excel 파일 생성

이미지 처리

반복적인 정렬
```

### ✅ 47. I/O-bound

데이터베이스·네트워크·파일 등의 응답 대기가 주요 병목인 작업이다.

### ✅ 48. 예시

```text
PostgreSQL Query Waiting

External API Request

S3 Upload / Download

Network Response Waiting
```

### ✅ 49. 대응 방식이 다르다

| 병목 | 개선 방향 |
|---|---|
| CPU-bound | 알고리즘 개선, 반복 연산 감소, Worker Threads 검토 |
| DB I/O-bound | Query·Index·Connection Pool 개선 |
| Network I/O-bound | 요청 감소, Cache, Timeout, 외부 API 분석 |
| Memory-bound | 데이터 크기 제한, 객체 수명 관리, 메모리 구조 개선 |

### ✅ 50. 중요한 원칙

**CPU-bound와 I/O-bound를 구분하지 않으면 DB 대기 문제를 해결하기 위해 JavaScript 계산 코드만 수정하는 잘못된 최적화를 할 수 있다.**

## 8. Sampling Profiler

### ✅ 51. Sampling Profiler

일정한 간격으로 프로그램의 실행 상태와 Call Stack을 관측하는 Profiling 방식이다.

### ✅ 52. 개념

```text
Sample 1:
calculatePricing

Sample 2:
calculatePricing → findRule

Sample 3:
calculatePricing → findRule

Sample 4:
calculatePricing → sortPlans
```

### ✅ 53. 동일한 함수가 반복적으로 관측된다면?

해당 함수 또는 그 하위 작업이 많은 실행시간을 소비하고 있을 가능성이 있다.

### ✅ 54. 장점

모든 함수 호출을 직접 기록하는 방식보다 관측 비용을 낮출 수 있다.

### ✅ 55. 한계

짧게 실행되는 함수는 샘플 사이에서 누락될 수 있다.

### ✅ 56. 또 다른 한계

샘플링 주기와 실행 환경에 따라 측정 결과가 달라질 수 있다.

### ✅ 57. 중요한 원칙

**Sampling Profile의 결과는 전체 실행을 정확히 기록한 완전한 사건 목록이 아니라 관측된 실행 상태를 기반으로 한 분석 자료다.**

## 9. Call Stack

### ✅ 58. Call Stack

현재 실행 중인 함수와 해당 함수를 호출한 상위 함수의 관계를 나타낸다.

### ✅ 59. 예시

```typescript
function calculateFinalPrice() {
  return findDiscountRule();
}

function findDiscountRule() {
  return compareConditions();
}

function compareConditions() {
  return true;
}
```

### ✅ 60. 실행 중 Call Stack

```text
calculateFinalPrice
       ↓
findDiscountRule
       ↓
compareConditions
```

### ✅ 61. CPU Profiler

특정 시점에 어떤 Call Stack이 실행 중인지 샘플링한다.

### ✅ 62. 중요한 주의

`async/await`로 작업이 중단되고 이후 다시 실행되는 경우 동기적인 Call Stack만으로 전체 논리적 업무 연결을 표현하기 어려울 수 있다.

### ✅ 63. 그래서 Trace가 필요하다

Trace는 비동기 업무의 논리적 연결을 분석하는 데 도움을 준다.

### ✅ 64. 중요한 원칙

**Call Stack은 실제 함수 호출 구조를 보여 주고 Trace는 업무의 논리적 실행 경로를 보완한다.**

## 10. Flame Graph란?

### ✅ 65. 정의

Flame Graph는 수집된 Call Stack을 계층적으로 시각화해 어떤 코드 경로가 많은 자원을 소비하는지 분석하는 방법이다.

### ✅ 66. 기본 구조

```text
┌──────────────────────────┐
│     findDiscountRule     │
├──────────────────────────┼─────────────┐
│     calculatePricing     │ serialize   │
├──────────────────────────┴─────────────┤
│           product.getDetail            │
├────────────────────────────────────────┤
│              HTTP Handler              │
└────────────────────────────────────────┘
```

### ✅ 67. 일반적인 해석

아래쪽은 상위 호출 경로를 나타낸다.

위쪽은 하위 함수 호출 경로를 나타낸다.

### ✅ 68. 박스의 넓이

해당 Stack에 속하는 샘플의 비중이나 수집한 자원량을 나타낸다.

### ✅ 69. 넓은 박스

많은 샘플이 해당 코드 경로에서 관측됐음을 의미할 수 있다.

### ✅ 70. 중요한 주의

Flame Graph의 가로축은 일반적으로 실제 시간의 순서를 나타내지 않는다.

### ✅ 71. 색상

도구마다 색상의 의미가 다르다.

빨간색이라고 무조건 오류가 발생한 함수라는 뜻은 아니다.

### ✅ 72. 중요한 원칙

**Flame Graph에서는 박스의 넓이와 호출 관계를 먼저 확인하고 색상이나 가로 위치만으로 성능 문제를 판단하지 않는다.**

## 11. Flame Graph와 Flame Chart

### ✅ 73. Flame Graph

여러 Call Stack 샘플을 집계해 자원 사용 비중을 나타낸다.

### ✅ 74. Flame Chart

시간 순서에 따라 함수와 작업이 언제 실행됐는지 보여 주는 시각화다.

### ✅ 75. 비교

| 항목 | Flame Graph | Flame Chart |
|---|---|---|
| 가로축 | 집계된 자원량 또는 샘플 비중 | 시간 |
| 주요 목적 | Hot Path 탐색 | 실행 순서와 지연 분석 |
| 유용한 질문 | 어느 함수가 가장 많은 자원을 사용하는가? | 특정 사용자 동작 이후 어떤 작업이 실행됐는가? |

### ✅ 76. 예시

### ✅ 77. 반대로

### ✅ 78. 중요한 원칙

**Flame Graph와 Flame Chart는 비슷한 형태로 보이지만 시간과 자원량을 해석하는 방식이 다르다.**

## 12. Inclusive Time과 Self Time

### ✅ 79. Inclusive Time

해당 함수와 하위 함수에 귀속된 실행시간 또는 샘플 비중을 포함한다.

### ✅ 80. Self Time

하위 함수에 귀속된 부분을 제외하고 해당 함수 자체에 귀속된 실행 비용이다.

### ✅ 81. 예시

```text
calculatePricing:
Total 800ms

├── loadRules:
300ms

├── calculateDiscount:
400ms

└── 자체 실행:
100ms
```

### ✅ 82. 이 예시에서

`calculatePricing`의 Inclusive Time은 800ms다.

Self Time은 100ms다.

### ✅ 83. 중요한 해석

상위 함수가 넓게 표시된다고 해당 함수 내부의 모든 코드를 수정해야 하는 것은 아니다.

실제 비용을 많이 소비하는 하위 함수를 조사해야 한다.

### ✅ 84. 주의

위 계산은 단순한 순차 호출 예시다.

Sampling, 재귀 호출, 비동기 작업 등의 경우 Profiler의 집계 방식에 맞게 해석해야 한다.

### ✅ 85. 중요한 원칙

**상위 함수의 Total Time과 실제 함수 자체의 Self Time을 구분해야 효과적인 최적화 지점을 찾을 수 있다.**

## 15. 첫 번째 CPU Profiling 실습

### ✅ 98. 목적

실제 운영 API를 사용하지 않고 CPU Profiler의 동작을 이해한다.

### ✅ 99. 가상의 가격 계산 Workload

```javascript
// scripts/profile/cpu-workload.mjs

import { performance } from 'node:perf_hooks';

const plans = Array.from(
  { length: 200 },
  (_, index) => ({
    id: `TEST-PLAN-${index}`,
    price: 30_000 + index * 100,
  }),
);

const rules = Array.from(
  { length: 200 },
  (_, index) => ({
    planId: `TEST-PLAN-${index}`,
    discount: index * 10,
  }),
);

function findDiscountRule(planId) {
  return rules.find(
    (rule) => rule.planId === planId,
  );
}

function calculatePricing() {
  return plans.map((plan) => {
    const rule = findDiscountRule(plan.id);

    return {
      planId: plan.id,

      finalPrice:
        plan.price - (rule?.discount ?? 0),
    };
  });
}

function runWorkload(rounds) {
  let checksum = 0;

  for (
    let iteration = 0;
    iteration < rounds;
    iteration += 1
  ) {
    const result = calculatePricing();

    checksum += result[0].finalPrice;
  }

  return checksum;
}

// Warm-up
runWorkload(1_000);

const startedAt = performance.now();

const checksum = runWorkload(30_000);

console.log({
  elapsedMs:
    performance.now() - startedAt,

  checksum,
});
```

### ✅ 100. 실행 목적

각 요금제에 대해 할인 조건 배열을 반복적으로 탐색하는 구조를 분석한다.

### ✅ 101. 시간 복잡도

요금제 개수를 P, 할인 규칙 개수를 R이라고 하면 단순 탐색의 최악 시간 복잡도는 대략 다음과 같다.

```text
O(P × R)
```

### ✅ 102. 중요한 전제

위 가격 계산은 실제 통신사 요금제와 지원금 계산 로직이 아니다.

CPU Profiling과 자료구조 최적화를 학습하기 위한 Synthetic Workload다.

### ✅ 103. 중요한 원칙

**첫 Profiling 실험은 실제 고객 데이터와 운영 DB가 필요 없는 독립 실행 코드로 시작한다.**

## 18. 자료구조 개선 실습 — Array.find와 Map

### ✅ 119. 앞선 코드의 병목 후보

```javascript
function findDiscountRule(planId) {
  return rules.find(
    (rule) => rule.planId === planId,
  );
}
```

### ✅ 120. 문제

각 요금제마다 할인 규칙 배열을 처음부터 탐색할 수 있다.

### ✅ 121. 개선 후보

조회용 Map을 먼저 생성한다.

```javascript
const ruleByPlanId = new Map(
  rules.map((rule) => [
    rule.planId,
    rule,
  ]),
);

function findDiscountRule(planId) {
  return ruleByPlanId.get(planId);
}
```

### ✅ 122. 개선 구조

```text
Before:

Plan 1 → Rules 전체 탐색

Plan 2 → Rules 전체 탐색

Plan 3 → Rules 전체 탐색
```

```text
After:

Rules → Map 생성

Plan 1 → Map 조회

Plan 2 → Map 조회

Plan 3 → Map 조회
```

### ✅ 123. 시간 복잡도

Map 구축에 대략 O(R)의 작업이 필요하다.

평균적으로 효율적인 Key 조회를 전제로 하면 요금제 처리 비용은 대략 O(P + R) 수준으로 줄일 수 있다.

### ✅ 124. 중요한 업무 차이

`Array.find()`는 조건을 만족하는 첫 번째 값을 반환한다.

반면 같은 Key로 Map을 반복 생성하면 마지막 값이 남을 수 있다.

### ✅ 125. 따라서

동일한 `planId`에 여러 할인 규칙이 존재하는 실제 서비스라면 우선순위와 적용 조건을 먼저 정의해야 한다.

### ✅ 126. 안전한 첫 번째 값 유지 예시

```typescript
interface DiscountRule {
  planId: string;
  discount: number;
}

function createRuleIndex(
  rules: DiscountRule[],
) {
  const index = new Map<
    string,
    DiscountRule
  >();

  for (const rule of rules) {
    if (!index.has(rule.planId)) {
      index.set(
        rule.planId,
        rule,
      );
    }
  }

  return index;
}
```

### ✅ 127. 중요한 원칙

**알고리즘이 더 빠르더라도 기존 업무 규칙과 결과가 달라지면 올바른 최적화가 아니다.**

```javascript
  mkdir,
  writeFile,
} from 'node:fs/promises';

import { join } from 'node:path';

const outputDirectory =
  'profiling-results/cpu';

await mkdir(outputDirectory, {
  recursive: true,

  mode: 0o700,
});

function runWorkload() {
  let result = 0;

  for (
    let index = 0;
    index < 20_000_000;
    index += 1
  ) {
    result += Math.sqrt(index);
  }

  return result;
}

// Warm-up은 측정 전에 수행한다.
runWorkload();

const session = new Session();

session.connect();

try {
  await session.post(
    'Profiler.enable',
  );

  await session.post(
    'Profiler.start',
  );

  try {
    const result = runWorkload();

    console.log({
      checksum: result,
    });
  } finally {
    const { profile } =
      await session.post(
        'Profiler.stop',
      );

    const filePath = join(
      outputDirectory,

      `cpu-${Date.now()}.cpuprofile`,
    );

    await writeFile(
      filePath,

      JSON.stringify(profile),

      {
        mode: 0o600,

        flag: 'wx',
      },
    );

    console.log({
      profileSaved: filePath,
    });
  }
} finally {
  session.disconnect();
}
```

### ✅ 159. 실행

```bash
node scripts/profile/capture-cpu.mjs
```

### ✅ 160. 장점

Warm-up과 실제 분석 대상 Workload를 분리하기 쉽다.

### ✅ 161. 중요한 전제

이 코드는 Node.js 24에서 사용할 수 있는 Promise 기반 Inspector API를 이용한 독립 테스트 예시다.

### ✅ 162. 운영 적용 주의

이 기능을 그대로 관리자 HTTP API에 노출하지 않는다.

### ✅ 163. 중요한 원칙

## 24. Event Loop Blocking

### ✅ 164. Node.js의 주요 실행 특성

JavaScript 실행은 일반적으로 각 Isolate의 Event Loop를 중심으로 진행된다.

Node.js 프로세스 전체에 스레드가 하나뿐이라는 의미는 아니다.

### ✅ 165. 문제가 되는 상황

하나의 JavaScript 작업이 Event Loop를 오래 점유한다.

```text
Request A:
대규모 가격 계산

Request B:
상품 목록 조회

Request C:
고객 신청
```

### ✅ 166. Request A가 CPU를 계속 사용하면

다른 요청의 JavaScript 처리도 지연될 수 있다.

### ✅ 167. 대표적인 원인

```text
대용량 배열 반복

동기식 파일 처리

복잡한 정렬

대용량 JSON.parse

대용량 JSON.stringify

정규식 과도한 연산
```

### ✅ 168. 잘못된 해결책

CPU-heavy 함수에 단순히 `async` 키워드를 추가하는 것이다.

### ✅ 169. 이유

함수가 `async`라고 해서 내부의 동기 CPU 연산이 자동으로 다른 Thread에서 실행되는 것은 아니다.

### ✅ 170. 중요한 원칙

**Node.js에서 비동기 함수와 병렬 CPU 실행은 서로 다른 개념이다.**

## 25. Event Loop Delay와 Event Loop Utilization

### ✅ 171. Event Loop Delay

Event Loop가 예정된 작업을 얼마나 늦게 실행하는지 관측할 수 있는 지표다.

### ✅ 172. Event Loop Utilization — ELU

Event Loop가 유휴 상태가 아닌 시간의 비율을 나타내는 데 활용할 수 있는 지표다.

### ✅ 173. 중요한 구분

ELU가 높다고 반드시 CPU 사용률도 같은 비율로 높다는 뜻은 아니다.

Event Loop를 차단하는 작업이나 측정 방식의 영향을 받을 수 있다.

### ✅ 174. 측정 코드

```typescript
import {
  monitorEventLoopDelay,
  performance,
} from 'node:perf_hooks';

const delay = monitorEventLoopDelay({
  resolution: 20,
});

delay.enable();

let previousElu =
  performance.eventLoopUtilization();

const timer = setInterval(() => {
  const currentElu =
    performance.eventLoopUtilization();

  const intervalElu =
    performance.eventLoopUtilization(
      currentElu,
      previousElu,
    );

  previousElu = currentElu;

  const hasSamples =
    delay.count > 0;

  console.log({
    eventLoopUtilization:
      intervalElu.utilization,

    eventLoopDelayP95Ms:
      hasSamples
        ? delay.percentile(95) / 1e6
        : null,

    eventLoopDelayMaxMs:
      hasSamples
        ? delay.max / 1e6
        : null,
  });

  delay.reset();
}, 10_000);

timer.unref();

export function stopEventLoopMonitoring() {
  clearInterval(timer);

  delay.disable();
}
```

### ✅ 175. 단위

Event Loop Delay Histogram의 시간은 나노초 단위다.

밀리초로 보고하기 위해 `1e6`으로 나눈다.

### ✅ 176. 중요

`resolution: 20`은 측정 해상도에 영향을 주는 설정이다.

이 값을 사용하는 Histogram에서 관측된 지연값을 별도 해석 없이 순수한 애플리케이션 추가 지연으로 간주해서는 안 된다.

### ✅ 177. 중요한 원칙

**Event Loop Delay·ELU·CPU Usage·API Latency를 함께 비교해 Node.js Runtime의 병목을 분석한다.**

## 27. Garbage Collection — GC

### ✅ 183. Garbage Collection

JavaScript Runtime이 더 이상 접근할 수 없는 객체의 메모리를 회수하는 과정이다.

### ✅ 184. 흔한 오해

변수에 `null`을 할당하면 해당 객체가 즉시 메모리에서 제거된다고 생각하는 것이다.

### ✅ 185. 실제로는

객체에 다른 참조가 남아 있을 수 있으며 메모리 회수 시점도 GC 동작에 따라 달라진다.

### ✅ 186. 예시

```typescript
let order = {
  id: 'TEST-ORDER-001',
};

const retainedOrders = [
  order,
];

order = null;
```

TypeScript의 엄격한 타입 설정에서는 `order`의 타입을 nullable로 선언해야 한다.

### ✅ 187. 중요한 의미

`order` 변수가 더 이상 객체를 가리키지 않더라도 `retainedOrders`가 여전히 해당 객체를 참조할 수 있다.

### ✅ 188. GC의 비용

메모리를 정리하는 과정에서도 CPU와 시간이 필요하다.

### ✅ 189. 주요 문제

```text
Frequent Allocations

Large Object Creation

Growing Retained Heap

GC Pressure

Long Pause
```

### ✅ 190. 중요한 원칙

**메모리 문제는 단순히 객체가 많이 생성되는지뿐 아니라 객체가 언제까지 유지되는지와 GC 비용을 함께 분석해야 한다.**

## 28. GC 관측

### ✅ 191. Node.js PerformanceObserver

GC 관련 Performance Entry를 관측할 수 있다.

### ✅ 192. 예시 코드

```typescript
import {
  PerformanceObserver,
} from 'node:perf_hooks';

let gcCount = 0;

let gcDurationMs = 0;

const observer =
  new PerformanceObserver((list) => {
    for (
      const entry of list.getEntries()
    ) {
      gcCount += 1;

      gcDurationMs += entry.duration;
    }
  });

observer.observe({
  entryTypes: ['gc'],
});

const timer = setInterval(() => {
  console.log({
    gcCount,

    observedGcDurationMs:
      gcDurationMs,
  });

  gcCount = 0;

  gcDurationMs = 0;
}, 10_000);

timer.unref();

export function stopGcMonitoring() {
  clearInterval(timer);

  observer.disconnect();
}
```

### ✅ 193. 확인할 수 있는 것

측정 구간에 관측된 GC Event의 횟수와 Duration 합계다.

### ✅ 194. 중요한 한계

이 값을 그대로 전체 CPU 사용시간이나 모든 요청이 GC 때문에 멈춰 있던 시간으로 해석하면 안 된다.

### ✅ 195. 로그 기반 분석

격리된 환경에서 다음 옵션을 사용할 수도 있다.

```bash
node \
  --trace-gc \
  scripts/profile/cpu-workload.mjs
```

### ✅ 196. 주의

GC 로그가 대량으로 발생할 수 있으므로 장시간 Production에서 무제한으로 활성화하지 않는다.

### ✅ 197. 중요한 원칙

**GC 횟수만 줄이는 것이 목표가 아니라 실제 API 성능과 메모리 안정성을 개선하는 것이 목표다.**

## 29. Node.js Memory Usage

### ✅ 199. 주요 필드

| Metric | 의미 |
|---|---|

| heapTotal | V8이 확보한 Heap 영역 |

### ✅ 201. 측정 코드

```typescript
function bytesToMiB(bytes: number) {
  return Math.round(
    bytes / 1024 / 1024 * 100,
  ) / 100;
}

export function getMemoryMetrics() {
  const memory = process.memoryUsage();

  return {
    rssMiB:
      bytesToMiB(memory.rss),

    heapTotalMiB:
      bytesToMiB(memory.heapTotal),

    heapUsedMiB:
      bytesToMiB(memory.heapUsed),

    externalMiB:
      bytesToMiB(memory.external),

    arrayBuffersMiB:
      bytesToMiB(memory.arrayBuffers),
  };
}
```

### ✅ 202. Worker Threads 사용 시

RSS는 전체 프로세스와 관련된 값이며 Heap 관련 값은 현재 Thread의 Isolate 범위를 고려해야 한다.

### ✅ 203. 중요한 원칙

**JavaScript Heap이 안정적이라고 Node.js 프로세스 전체 메모리도 안정적이라고 판단할 수는 없다.**

## 32. Heap Snapshot 실습

### ✅ 218. 목적

반복적으로 객체가 유지되는 상황을 재현한다.

### ✅ 219. 실습 코드

```javascript
// scripts/profile/memory-scenario.mjs

import {
  writeHeapSnapshot,
} from 'node:v8';

import {
  mkdirSync,
} from 'node:fs';

const directory =
  'profiling-results/heap';

process.umask(0o077);

mkdirSync(directory, {
  recursive: true,

  mode: 0o700,
});

const retainedOrders = [];

function createSyntheticOrders(
  startIndex,
  count,
) {
  return Array.from(
    { length: count },

    (_, offset) => ({
      id:
        `TEST-ORDER-${startIndex + offset}`,

      carrier: 'TEST',

      items: Array.from(
        { length: 20 },

        (_, itemIndex) => ({
          code:
            `TEST-ITEM-${itemIndex}`,

          amount: 1_000,
        }),
      ),
    }),
  );
}

function runScenario(
  startIndex,
) {
  const orders =
    createSyntheticOrders(
      startIndex,

      1_000,
    );

  // 학습 목적으로 객체를 계속 유지한다.
  retainedOrders.push(
    ...orders,
  );
}

function captureSnapshot(label) {
  // --expose-gc로 시작한 테스트에서만 사용.
  global.gc?.();

  const filename =
    `${directory}/${label}-${Date.now()}.heapsnapshot`;

  writeHeapSnapshot(filename);

  console.log({
    label,

    heapUsed:
      process.memoryUsage().heapUsed,

    retainedCount:
      retainedOrders.length,
  });
}

captureSnapshot('baseline');

runScenario(0);

captureSnapshot('after-first');

runScenario(1_000);

captureSnapshot('after-second');
```

### ✅ 220. 실행

```bash
node \
  --expose-gc \
  scripts/profile/memory-scenario.mjs
```

### ✅ 221. 결과

```text
baseline-....heapsnapshot

after-first-....heapsnapshot

after-second-....heapsnapshot
```

### ✅ 222. 실험의 목적

각 작업 이후 `retainedOrders`에 객체가 계속 남는 것을 관측한다.

### ✅ 223. 중요한 주의

`--expose-gc`를 사용한 강제 GC는 실험용이다.

실제 Production에서 요청마다 강제 GC를 실행하는 것은 해결책이 아니다.

### ✅ 224. 중요한 원칙

**Heap Snapshot 실습은 제한된 Synthetic Object를 사용하고 실제 업무 프로세스의 메모리를 무작정 추출하지 않는다.**

## 34. Shallow Size와 Retained Size

```text
       ↓
```

### ✅ 238. 중요한 원칙

## 37. Memory Leak 사례 — 무제한 Cache

### ✅ 253. 위험한 구조

```typescript
@Injectable()
export class ProductCacheService {
  private readonly cache =
    new Map<string, ProductDetail>();

  set(
    key: string,
    value: ProductDetail,
  ) {
    this.cache.set(key, value);
  }

  get(key: string) {
    return this.cache.get(key);
  }
}
```

### ✅ 254. 문제

상품·조건·고객별로 Cache Key가 계속 생성되면 Map 크기가 증가할 수 있다.

### ✅ 255. 필요한 정책

```text
Maximum Entry Count

TTL

Eviction

Invalidation

Memory Budget

Cache Key Design
```

### ✅ 256. 단순 제한 Cache 예시

```typescript
interface CacheEntry<T> {
  value: T;

  expiresAt: number;
}

class BoundedCache<T> {
  private readonly entries =
    new Map<string, CacheEntry<T>>();

  constructor(
    private readonly maxEntries: number,

    private readonly ttlMs: number,
  ) {
    if (
      !Number.isInteger(maxEntries) ||
      maxEntries < 1 ||
      !Number.isFinite(ttlMs) ||
      ttlMs <= 0
    ) {
      throw new Error(
        'INVALID_CACHE_CONFIGURATION',
      );
    }
  }

  get(key: string): T | undefined {
    const entry =
      this.entries.get(key);

    if (!entry) {
      return undefined;
    }

    if (
      Date.now() >= entry.expiresAt
    ) {
      this.entries.delete(key);

      return undefined;
    }

    // 최근 접근한 항목을 뒤로 이동.
    this.entries.delete(key);

    this.entries.set(key, entry);

    return entry.value;
  }

  set(
    key: string,
    value: T,
  ): void {
    this.entries.delete(key);

    this.entries.set(key, {
      value,

      expiresAt:
        Date.now() + this.ttlMs,
    });

    while (
      this.entries.size >
      this.maxEntries
    ) {
      const oldestKey =
        this.entries.keys().next().value;

      if (oldestKey === undefined) {
        break;
      }

      this.entries.delete(
        oldestKey,
      );
    }
  }

  delete(key: string) {
    this.entries.delete(key);
  }
}
```

### ✅ 257. 이 구현의 특징

Cache Entry 개수를 제한한다.

만료된 항목은 조회 시 제거한다.

### ✅ 258. 중요한 한계

Entry 개수 제한만으로 실제 메모리 크기를 정확히 제한하는 것은 아니다.

하나의 Entry가 매우 큰 객체일 수도 있다.

### ✅ 259. 업무 주의

실시간 가격과 지원금 계산 결과는 TTL만 설정한다고 정합성이 보장되는 것은 아니다.

실제 정책 변경 시 Cache Invalidation이 필요할 수 있다.

### ✅ 260. 중요한 원칙

**Cache는 성능을 개선할 수 있지만 크기·수명·데이터 최신성을 제한하지 않으면 새로운 메모리 문제와 업무 오류를 발생시킬 수 있다.**

## 42. Worker Threads

### ✅ 290. Worker Threads

```text
Message Serialization

Data Copying

Separate Heap

Task Scheduling

Error Handling
```

### ✅ 295. 위험한 방식

### ✅ 296. 권장

## 43. Worker Thread 실습

### ✅ 298. CPU 작업 파일

```javascript
// scripts/profile/calculate-worker.mjs

import {
  parentPort,
  workerData,
} from 'node:worker_threads';

let total = 0;

for (
  let index = 0;
  index < workerData.iterations;
  index += 1
) {
  total += Math.sqrt(index);
}

parentPort.postMessage({
  total,
});
```

### ✅ 299. 실행 파일

```javascript
// scripts/profile/run-worker.mjs

import {
  Worker,
} from 'node:worker_threads';

const worker = new Worker(
  new URL(
    './calculate-worker.mjs',

    import.meta.url,
  ),

  {
    workerData: {
      iterations: 20_000_000,
    },
  },
);

const timeout = setTimeout(() => {
  void worker.terminate().catch(
    () => {
      console.error(
        'WORKER_TERMINATION_FAILED',
      );
    },
  );
}, 10_000);

worker.once('message', (result) => {
  console.log({
    result,
  });
});

worker.once('error', () => {
  console.error(
    'WORKER_EXECUTION_FAILED',
  );

  process.exitCode = 1;
});

worker.once('exit', (code) => {
  clearTimeout(timeout);

  if (code !== 0) {
    process.exitCode = 1;
  }
});
```

### ✅ 300. 실행

```bash
node scripts/profile/run-worker.mjs
```

### ✅ 301. 중요한 전제

위 코드는 Worker Thread의 기본 실행 구조를 이해하기 위한 실습이다.

실제 NestJS 요청마다 이 코드를 그대로 사용하라는 의미가 아니다.

### ✅ 302. 실제 구현에 필요한 것

```text
Worker Pool

Task Validation

Queue Limit

Timeout

Cancellation

Resource Limit

Worker Recovery

Graceful Shutdown
```

### ✅ 303. 중요한 원칙

**Worker Thread 도입 여부는 실제 Profiling에서 CPU 병목이 확인되고 알고리즘 개선만으로 충분하지 않을 때 검토한다.**

```tsx
} from 'react';

const handleRender:
  ProfilerOnRenderCallback = (
    id,

    phase,

    actualDuration,

    baseDuration,

    startTime,

    commitTime,
  ) => {
    if (!import.meta.env.DEV) {
      return;
    }

    console.debug({
      component: id,

      phase,

      actualDurationMs:
        actualDuration,

      baseDurationMs:
        baseDuration,

      startTime,

      commitTime,
    });
  };

export function AdminOrdersPage() {
  return (
    <Profiler
      id="AdminOrderTable"

      onRender={handleRender}
    >
      <OrderTable />
    </Profiler>
  );
}
```

### ✅ 317. 중요한 전제

`OrderTable`은 실제 관리자 컴포넌트로 교체해야 한다.

위 예시는 개발 환경에서 간단히 확인하기 위한 것이다.

### ✅ 318. Production Build

React의 일반 Production Build에서는 Profiling이 기본적으로 비활성화된다.

필요하다면 별도의 Profiling-enabled Production Build를 구성해야 한다.

### ✅ 319. 주의

개발 Build와 Production Build는 실행 특성이 다르다.

개발 환경에서 측정한 렌더링시간을 실제 운영 성능으로 확정하지 않는다.

### ✅ 320. 개인정보

Profiler 결과를 전송할 때 고객의 실제 주문 데이터나 Cell 값을 포함하지 않는다.

### ✅ 321. 중요한 원칙

**React Profiling은 개발 단계의 병목 탐색에 먼저 사용하고 실제 운영 환경과 비교하려면 Build 조건을 일치시킨다.**

## 48. TanStack Table과 Virtualization

### ✅ 329. 관리자 주문관리 화면

많은 주문과 Cell을 화면에 표시해야 할 수 있다.

### ✅ 330. Virtualization

전체 데이터 중 현재 화면에 필요한 영역을 중심으로 렌더링하는 방식이다.

### ✅ 331. 개념

```text
전체 주문:
10,000 Rows

현재 화면:
30 Rows

↓

필요한 Row 중심으로 렌더링
```

### ✅ 332. 장점

DOM Node 수와 렌더링 비용을 줄이는 데 도움을 줄 수 있다.

### ✅ 333. 하지만 중요한 한계

전체 주문 배열을 이미 Backend에서 가져왔다면 Browser 메모리 사용량은 여전히 클 수 있다.

### ✅ 334. 따라서

```text
Server-side Pagination

+

필요한 데이터 조회

+

Virtualization
```

을 함께 검토한다.

### ✅ 335. 업무 검증

현재 관리자 시트에서 여러 Cell을 동시에 선택하고 붙여넣는 기능이 필요하다면 Virtualization 이후에도 해당 기능이 올바르게 동작하는지 확인해야 한다.

### ✅ 336. 중요한 원칙

**Virtualization은 렌더링되는 DOM을 줄이는 기술이지 Backend 조회량과 전체 데이터 메모리를 자동으로 줄이는 기술은 아니다.**

## 52. Continuous Profiling

### ✅ 358. 기존 Profiling의 특징

성능 문제가 발생했을 때 개발자가 직접 Profile을 수집한다.

```text
Incident
       ↓
Profiler Start
       ↓
Profile Collection
       ↓
Analysis
```

### ✅ 359. 문제

장애가 이미 종료됐거나 특정 시간대에만 발생한다면 당시 CPU와 메모리 상태를 다시 관측하기 어려울 수 있다.

### ✅ 360. Continuous Profiling

시간에 따라 지속적으로 또는 반복적인 구간으로 Profile을 수집해 과거의 코드 수준 자원 사용 특성을 분석하는 방식이다.

### ✅ 361. 전체 구조

```text
Application Runtime
       ↓
Bounded Profiling
       ↓
Profile Export
       ↓
Profiling Backend
       ↓
Time-range Query
       ↓
Flame Graph Comparison
```

### ✅ 362. 장점

특정 Release 또는 특정 시간대에 어떤 코드가 많은 자원을 소비했는지 조사할 수 있다.

### ✅ 363. 중요한 비용

```text
CPU Overhead

Memory Overhead

Network Export

Profile Storage

Indexing

Retention

Operational Maintenance
```

### ✅ 364. 중요한 원칙

**Continuous Profiling은 지속적인 코드 수준 관측을 가능하게 하지만 관측 비용과 운영 부담까지 함께 고려해야 한다.**

## 53. On-demand와 Continuous Profiling 비교

### ✅ 365. On-demand Profiling

필요한 시점에 제한된 시간 동안 수집한다.

### ✅ 366. Continuous Profiling

일정한 수집 정책에 따라 Profile을 지속적으로 축적한다.

### ✅ 367. 비교

| 항목 | On-demand | Continuous |
|---|---|---|
| 실행 | 필요 시 | 지속적 또는 반복 구간 |
| 과거 장애 분석 | 제한적 | 수집된 구간에서 가능 |
| 초기 구축 부담 | 낮음 | 상대적으로 높음 |
| 저장 비용 | 제한적 | 지속 발생 가능 |
| 운영 복잡도 | 낮음 | 수집·저장·접근 관리 필요 |

### ✅ 368. 현재 1인 개발 환경

처음부터 Continuous Profiling Backend를 구성할 필요는 없다.

### ✅ 369. 추천 단계

```text
1. Local CPU Profiling

2. Local Heap Analysis

3. Controlled Benchmark

4. 필요 시 제한된 Production Profiling

5. 실제 필요성이 확인되면 Continuous Profiling
```

### ✅ 370. 중요한 원칙

**복잡한 상시 Profiling 시스템을 도입하기 전에 기본 Profile을 직접 수집하고 분석할 수 있는 능력을 확보한다.**

```text
Event Loop Delay 증가.

Missing Evidence:

실제 호출 횟수와 배열 크기.
기존 버전과의 동일 조건 비교.

Verification:

Map 기반 조회 구조와 기존 구현 비교.
가격 결과 동일성 검증.
반복 Benchmark.
```

## 📌 요약

1114에서는 Distributed Tracing을 이용해 실제 고객 요청의 전체 처리 경로와 느린 업무 단계를 찾는 방법을 다뤘다.

```text
Customer Request
       ↓
Request ID
       ↓
Trace ID
       ↓
Business Span
       ↓
Database / External API
       ↓
Critical Path
```

1115에서는 이를 애플리케이션 내부의 함수 실행과 메모리 분석으로 확장했다.

```text
Performance Regression
       ↓
Distributed Trace
       ↓
Slow Business Operation
       ↓
CPU / Memory Metrics
       ↓
Runtime Profiling
       ↓
Call Stack / Flame Graph
       ↓
Hot Function / Retained Object
       ↓
Root Cause Hypothesis
       ↓
Controlled Optimization
       ↓
Re-profiling
       ↓
Performance Benchmark
       ↓
Business Verification
```

이번 편에서 가장 중요한 원칙은 다음과 같다.

**첫 번째 — Trace와 Profile은 측정 범위가 다르다.**

Trace는 고객 요청의 업무 실행 경로를 보여 준다.

Profile은 프로그램 내부의 함수 실행과 자원 사용 특성을 분석한다.

**두 번째 — CPU Time과 Wall-clock Time을 구분한다.**

API가 3초 동안 처리됐다고 JavaScript가 3초 내내 CPU를 사용한 것은 아니다.

DB와 외부 API 응답을 기다리는 시간도 존재할 수 있다.

**세 번째 — Flame Graph에서는 실제 실행 비중과 호출 관계를 분석한다.**

가장 넓은 상위 함수만 수정하는 것이 아니라 Self Time과 하위 호출 경로를 조사해야 한다.

**네 번째 — 메모리 증가와 메모리 누수를 구분한다.**

정상적인 Cache Warm-up으로 메모리가 증가할 수도 있다.

불필요한 객체가 계속 유지되는지 반복 Workload와 Heap Analysis를 이용해 확인해야 한다.

**다섯 번째 — Heap Snapshot은 안전한 환경에서 실행한다.**

```text
Execution Pause

Additional Memory

Sensitive Object Contents
```

등의 위험이 있으므로 운영 서버에서 무작정 생성하지 않는다.

**여섯 번째 — Excel Export와 관리자 Table은 여러 관점에서 분석한다.**

```text
Database Query

+

JavaScript Transformation

+

Workbook / Buffer

+

React Rendering

+

Browser Memory
```

를 분리해서 조사해야 한다.

**일곱 번째 — Worker Threads는 CPU 병목이 실제로 확인된 경우에 검토한다.**

모든 느린 API를 Worker Thread로 분리할 필요는 없다.

**여덟 번째 — Continuous Profiling은 필요성이 확인된 뒤 도입한다.**

1인 개발 환경에서는 기본 Node.js CPU Profiling과 제한적인 Heap Analysis만으로도 많은 중요한 문제를 조사할 수 있다.

**아홉 번째 — 최적화 이후 실제 업무 정확성을 반드시 검증한다.**

가격 계산을 빠르게 만들었지만 지원금 적용 조건이 달라졌다면 성공적인 최적화가 아니다.

Excel Export가 빨라졌지만 주문 데이터가 누락됐다면 역시 실패다.

현재 투게더몰에서 가장 현실적인 실행 순서는 다음과 같다.

```text
1. 현재 Runtime Metrics 확인

2. Node.js CPU Profiling 실습

3. 가격 계산 Workload 구성

4. 상품 상세 API CPU 분석

5. 관리자 Excel Export 분석

6. Prisma 대용량 조회 Memory 분석

7. React 주문관리 Table Profiling

8. Cache / Listener Memory Leak 검증

9. 최적화 전후 Benchmark

10. Git Commit 기반 Profiling Report

11. 필요하면 Worker Threads 검토

12. 실제 필요성이 확인되면 Continuous Profiling
```

현재 개발 환경에서는 MacBook Pro와 OrbStack을 활용해 독립된 NestJS·PostgreSQL 테스트 환경을 구축하고, Node.js 기본 Profiler로 상당수의 CPU·메모리 문제를 분석할 수 있다.

처음부터 새로운 AWS 서비스나 대규모 Profiling 플랫폼을 도입할 필요는 없다.

특히 가격 계산, 상품 상세 조회, 관리자 주문관리 시트, Excel 다운로드처럼 실제 운영 업무와 연결되는 기능부터 분석하면 단순한 성능 개선을 넘어 코드 구조와 Runtime 동작에 대한 이해도를 높일 수 있다.

기존 AI 기반 개발 흐름에서도 중요한 변화가 생긴다.

```text
기존:

AI에게 느린 코드를 최적화해 달라고 요청
```

```text
개선:

Trace에서 느린 Service 확인

↓

CPU Profile에서 Hot Function 확인

↓

Heap Analysis에서 객체 유지 원인 확인

↓

측정 근거와 코드 전달

↓

AI에게 최적화 후보 요청

↓

Functional Test

↓

Re-profiling

↓

실제 개선 여부 판단
```

이 방식은 AI가 작성한 코드가 왜 빠른지, 어떤 이유로 문제가 해결됐는지 개발자가 직접 설명하고 검증할 수 있는 기반이 된다.

최종적으로 기억해야 할 원칙은 다음과 같다.

**좋은 성능 최적화는 AI에게 코드를 더 빠르게 만들어 달라고 지시하는 것이 아니다. 실제 요청의 지연 구간을 추적하고 CPU와 메모리의 사용 원인을 측정한 뒤, 가장 효과적인 코드 변경을 선택하고 기존 업무 정확성을 유지하면서 성능이 개선됐음을 다시 증명하는 과정이다.**
