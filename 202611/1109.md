## 1. GitHub Actions가 성공하면 배포도 성공한 것일까?

### ✅ 1. 1108과의 연결

1108에서는 Frontend·Backend·Database를 변경할 때 기존 사용자와 새로운 사용자가 동시에 정상적으로 서비스를 이용하도록 만드는 방법을 다뤘다.

```text
Backward Compatibility
       ↓
Expand-and-Contract
       ↓
Safe Deployment
       ↓
Readiness
       ↓
Traffic Switching
       ↓
Production Verification
```

이번 1109에서는 마지막 단계인 **Production Verification**을 자동화하는 방법을 다룬다.

### ✅ 2. 일반적인 배포 완료 판단

```text
GitHub Actions
SUCCESS

↓

EC2 Deployment
SUCCESS

↓

배포 완료
```

### ✅ 3. 하지만 실제 상황은 다를 수 있다

```text
GitHub Actions
SUCCESS

↓

NestJS Server
RUNNING

↓

Application Submit API
500 ERROR

↓

Customer Application
FAILED
```

### ✅ 4. 또는 이런 상황

```text
Backend
200 OK

↓

Order Created
SUCCESS

↓

Pricing Data
INCORRECT
```

서버는 성공 응답을 반환하지만 실제 업무 데이터는 잘못됐을 수 있다.

### ✅ 5. 따라서 배포 검증은 여러 단계로 나눠야 한다

```text
Deployment Execution
        ↓
Application Readiness
        ↓
Technical Verification
        ↓
Business Verification
        ↓
Release Health Evaluation
        ↓
Release Decision
```

### ✅ 6. 이번 편의 핵심 질문

**배포가 끝난 뒤 어떤 데이터를 확인해야 새로운 버전이 안전하다고 판단할 수 있을까?**

### ✅ 7. 학습할 주요 개념

```text

Error Rate

Latency
```

## 2. Deployment Health와 Service Health

### ✅ 9. Deployment Health

새로운 프로그램이 정상적으로 배포되고 실행됐는지 확인한다.

### ✅ 10. 예시

```text
Build Completed

Artifact Uploaded

EC2 Updated

NestJS Started

Health Check Passed
```

### ✅ 11. Service Health

실제 서비스가 정상적으로 고객 요청을 처리하는지 확인한다.

### ✅ 12. 예시

```text
Product API Success

Application Submit Success

Order Data Correct

Admin Order Lookup Success

No Critical Security Regression
```

### ✅ 13. 둘의 차이

| 항목 | Deployment Health | Service Health |
|---|---|---|
| Backend 실행 | 확인 | 일부 근거 |
| HTTP 200 | 일부 확인 | 업무 결과 추가 검증 |
| DB 연결 | 확인 | 실제 데이터 정합성 별도 |
| 신청 완료 | 직접 보장하지 않음 | 핵심 검증 |
| 주문 중복 방지 | 보장하지 않음 | 핵심 검증 |
| 고객 영향 | 제한적으로 파악 | 실제 업무 지표로 확인 |

### ✅ 14. 배포 성공의 최종 의미

단순히 새 버전이 실행된 것이 아니라 정의된 검증 기준에 따라 정상적인 업무 수행이 확인된 상태여야 한다.

### ✅ 15. 중요한 원칙

**Readiness PASS는 배포 검증의 시작이지 끝이 아니다.**

## 3. Release Health란?

### ✅ 16. Release Health

특정 배포 버전이 운영 환경에서 얼마나 정상적으로 동작하는지 평가한 결과다.

### ✅ 17. Release Health는 하나의 숫자일까?

반드시 그렇지는 않다.

### ✅ 18. 실제로 필요한 정보

```text
Deployment Status

Application Readiness

API Error Rate

API Latency

Frontend Errors

Business SLI

Critical Invariants

Rollback Safety

Evidence Freshness
```

### ✅ 19. 예시

```text
Release:
20261109-001

Deployment:
SUCCESS

Readiness:
PASS

API Error Rate:
NORMAL

Application Submission:
NOT_VERIFIED

Database Consistency:
PASS
```

### ✅ 20. 최종 판단

```text
HOLD
```

가 적절할 수 있다.

### ✅ 21. 이유

중요한 신청 업무가 아직 검증되지 않았기 때문이다.

### ✅ 22. 핵심 개념

**좋은 Release Health 판단은 정상인 항목뿐 아니라 아직 확인하지 못한 항목도 드러내야 한다.**

## 4. Release Decision 상태

### ✅ 23. 추천 상태

```text
PREPARING

DEPLOYED

VERIFYING

HEALTHY

HOLD

ROLLBACK_REVIEW

FAILED

ROLLED_BACK
```

### ✅ 24. PREPARING

배포 준비와 사전 검증을 수행하는 상태다.

### ✅ 25. DEPLOYED

새로운 코드가 배포 대상에 반영된 상태다.

### ✅ 26. VERIFYING

운영 검증을 수행 중이다.

### ✅ 27. HEALTHY

정의된 필수 검증을 통과하고 충분한 근거를 확보했다.

### ✅ 28. HOLD

데이터 부족, 검증 미완료 또는 불명확한 문제 때문에 추가 배포를 중단한 상태다.

### ✅ 29. ROLLBACK_REVIEW

이전 버전 복구 여부를 판단해야 하는 상태다.

### ✅ 30. FAILED

배포 또는 핵심 검증 실패가 확인된 상태다.

### ✅ 31. ROLLED_BACK

승인된 복구 절차로 이전 코드 버전이 다시 배포된 상태다.

### ✅ 32. 중요한 구분

`ROLLBACK_REVIEW`는 Rollback을 실제 실행했다는 뜻이 아니다.

### ✅ 33. 중요한 원칙

**판단 상태와 실제 실행 상태를 분리해 관리한다.**

## 11. PostgreSQL Error Rate SQL

### ✅ 81. 가상 테이블

```text
api_request_events

id
operation_key
status_code
duration_ms
occurred_at
environment
```

### ✅ 82. SQL 예시

```sql
SELECT
  operation_key,

  COUNT(*) AS total_requests,

  COUNT(*) FILTER (
    WHERE status_code >= 500
  ) AS server_errors,

  ROUND(
    100.0
    * COUNT(*) FILTER (
        WHERE status_code >= 500
      )
    / NULLIF(COUNT(*), 0),
    2
  ) AS error_rate_percent

FROM api_request_events

WHERE occurred_at >= $1
  AND occurred_at < $2

  AND environment = 'production'

  AND operation_key NOT IN (
    'HEALTH_LIVE',
    'HEALTH_READY',
    'TELEMETRY_INGEST'
  )

GROUP BY operation_key;
```

### ✅ 83. 중요한 전제

위 테이블은 설명용이다.

### ✅ 84. 실제 프로젝트

현재 로그 또는 Metrics 구조를 먼저 확인한다.

### ✅ 85. 결과 해석

전체 API 평균만 보지 말고 중요한 Operation을 별도로 분석한다.

### ✅ 86. 예시

```text
PRODUCT_LIST

PRODUCT_DETAIL

APPLICATION_SUBMIT

ADMIN_ORDER_SEARCH
```

### ✅ 87. 중요한 원칙

## 12. p95 Latency

### ✅ 88. Latency

요청이 완료되기까지 걸린 시간이다.

### ✅ 89. 평균만 확인하면 부족할 수 있다

대부분의 요청은 빠르지만 일부 고객에게만 매우 긴 지연이 발생할 수 있다.

### ✅ 90. p95

관측된 요청 시간의 약 95%가 이 값 이하인 경계값이다.

### ✅ 91. 예시

```text
p95 = 2,000ms
```

이라면 관측된 요청의 약 95%가 2초 이하에서 완료됐다는 의미다.

### ✅ 92. p99

더 느린 상위 약 1% 요청의 경계 구간을 확인하는 지표다.

### ✅ 93. 중요한 한계

표본이 적으면 높은 분위수의 추정이 불안정할 수 있다.

### ✅ 94. 따라서

```text
p50

p95

p99

Request Count
```

를 함께 보관한다.

### ✅ 95. 중요한 원칙

**Latency 수치만 저장하지 말고 해당 값을 계산한 요청 수와 기간을 함께 기록한다.**

## 13. PostgreSQL p95 계산

### ✅ 96. SQL 예시

```sql
SELECT
  operation_key,

  COUNT(*) AS request_count,

  ROUND(
    AVG(duration_ms)::numeric,
    2
  ) AS average_ms,

  PERCENTILE_CONT(0.95)
    WITHIN GROUP (
      ORDER BY duration_ms
    ) AS p95_ms

FROM api_request_events

WHERE occurred_at >= $1
  AND occurred_at < $2

  AND duration_ms IS NOT NULL

GROUP BY operation_key;
```

### ✅ 97. PERCENTILE_CONT

정렬된 값에서 지정한 분위수를 계산하는 PostgreSQL 함수다.

### ✅ 98. 중요한 점

전체 트래픽과 중요한 API를 구분해서 평가한다.

### ✅ 99. 신청 API

평소 800ms였던 p95가 배포 이후 4초로 증가했다면 조사가 필요하다.

### ✅ 100. 하지만

이 수치만으로 배포가 원인이라고 확정하지 않는다.

### ✅ 101. 비교 조건

```text
Traffic Volume

Request Type

Database Load

External API

Client Environment
```

를 함께 확인한다.

가능하면 비슷한 시간대·트래픽·요청 유형을 기준으로 비교한다.

### ✅ 110. 중요한 원칙

**배포 전후 지표 변화와 배포로 인한 실제 영향은 구분해야 한다.**

---

## 15. Canary Group과 Control Group

### ✅ 111. Canary란?

새 버전을 일부 사용자나 서버에 적용해 검증하는 방식이다.

### ✅ 112. Control

기존 버전을 사용하는 비교 대상이다.

### ✅ 113. 예시

```text
Control
Backend V1

Canary
Backend V2
```

### ✅ 114. 평가

두 집단의 오류율과 지연, 업무 성공을 비교한다.

### ✅ 115. 중요한 전제

새 버전과 기존 버전의 트래픽을 분리할 수 있는 실제 배포 인프라가 필요하다.

### ✅ 116. 단일 EC2

기존 Backend 하나만 교체하는 구조라면 같은 시점의 Control Group이 존재하지 않을 수 있다.

### ✅ 117. 이 경우

배포 전후 비교와 Synthetic Monitoring을 이용한다.

### ✅ 118. Feature Flag

일부 사용자에게 새 기능을 제공하는 방식으로 기능 단위 비교를 할 수 있다.

### ✅ 119. 중요한 차이

```text
Infrastructure Canary

≠

Feature Flag Canary
```

### ✅ 120. 중요한 원칙

**실제로 Control Group이 없는데 Canary 비교 분석을 수행했다고 표현하지 않는다.**

---

## 16. Low Traffic 문제

### ✅ 121. 고객 요청이 적다면?

배포 직후 충분한 데이터가 발생하지 않을 수 있다.

### ✅ 122. 예시 A

```text
Application Submit:
2 Requests

Failures:
0
```

### ✅ 123. 관측 실패율

0%다.

### ✅ 124. 하지만

실제 오류 확률이 0%라는 뜻은 아니다.

### ✅ 125. 예시 B

```text
Application Submit:
2,000 Requests

Failures:
0
```

### ✅ 126. 둘의 차이

후자의 관측 결과가 더 많은 사용 사례에 대한 근거를 제공한다.

### ✅ 127. 따라서

Release Health에 최소 관측량 조건을 도입할 수 있다.

### ✅ 128. 예시

```text
MIN_SAMPLE_NOT_MET
```

### ✅ 129. 중요한 주의

최소 요청 수를 무조건 100건 또는 1,000건으로 정할 수는 없다.

### ✅ 130. 업무 중요도와 허용 가능한 위험, 기대 오류율에 따라 필요한 표본 크기가 달라진다.

### ✅ 131. 현재 추천

트래픽이 적을 때는 실제 고객을 기다리면서 위험을 방치하지 말고 안전한 Synthetic Test와 Staging 업무 테스트를 함께 사용한다.

---

## 17. 관측량과 통계적 불확실성

### ✅ 132. 오류가 0건이어도 불확실성은 존재한다

관측 기간과 표본이 제한돼 있기 때문이다.

### ✅ 133. 가능한 검증

```text
Sample Count

Observed Failure Count

Confidence Interval

Traffic Composition
```

을 함께 고려한다.

### ✅ 134. 비율의 신뢰구간

관측 오류율에 대한 불확실성을 표현할 수 있다.

### ✅ 135. 주의

실제 데이터가 독립적인 무작위 표본인지 여부에 따라 통계적 해석이 달라진다.

### ✅ 136. 반복 요청

동일 고객의 여러 요청을 모두 독립적인 고객 경험으로 취급해서는 안 된다.

### ✅ 137. 일반적인 요청 오류율과 실제 고객 영향도

서로 다른 지표로 관리한다.

### ✅ 138. 중요한 원칙

**트래픽이 적은 상황에서는 강한 정상 판정보다 불확실성을 명확하게 표시하는 것이 안전하다.**

---

## 18. Data Freshness

### ✅ 139. 데이터가 얼마나 최신인가?

Release Verification에서 중요하다.

### ✅ 140. 예시

```text
현재 시각:
15:10

마지막 Metrics 수집:
14:55
```

### ✅ 141. 문제

새 배포가 15:05에 완료됐다면 이전 데이터만 보고 있을 수 있다.

### ✅ 142. 따라서

Metric의 실제 관측 시각을 확인해야 한다.

### ✅ 143. 필드 예시

```text
Observed At

Collected At

Available At

Evaluation At
```

### ✅ 144. 서로 다른 의미

Observed At은 실제 요청이 발생한 시간이다.

Collected At은 Collector가 수집한 시간이다.

Evaluation At은 배포 판단이 수행된 시간이다.

### ✅ 145. 중요한 조건

배포 이후에 발생한 데이터인지 확인해야 한다.

### ✅ 146. 오래된 데이터

```text
STALE_DATA
```

로 표시한다.

### ✅ 147. 중요한 원칙

**새로운 배포를 검증하면서 이전 버전의 Metrics를 사용하지 않는다.**

---

## 19. Missing Data와 Zero Error는 다르다

### ✅ 148. 중요한 상황

```text
Error Count:
0
```

### ✅ 149. 하지만 요청 수는?

```text
Request Count:
0
```

일 수 있다.

### ✅ 150. 이때

실패가 없었다는 사실만으로 정상 판정을 내릴 수 없다.

### ✅ 151. 상태 구분

```text
NO_ERRORS_OBSERVED

NO_TRAFFIC

MISSING_METRICS

STALE_METRICS
```

### ✅ 152. CloudWatch

Alarm 상태는 대표적으로 다음과 같다.

```text
OK

ALARM

INSUFFICIENT_DATA
```

### ✅ 153. INSUFFICIENT_DATA

새 Alarm을 생성했거나 평가에 필요한 데이터가 충분하지 않은 상태일 수 있다.

### ✅ 154. 중요한 주의

이 상태를 정상으로 간주하는 자동 Rollback 정책은 위험하다.

### ✅ 155. 반대로

무조건 장애로 처리하면 정상적인 저트래픽 구간에서 오탐이 발생할 수 있다.

### ✅ 156. 따라서

지표의 특성과 필수 관측 조건에 따라 Missing Data 처리 정책을 정의한다.

### ✅ 157. 중요한 원칙

**데이터가 없는 상태를 오류가 없는 상태와 동일하게 처리하지 않는다.**

---

## 20. CloudWatch Alarm

### ✅ 158. CloudWatch

AWS 리소스와 애플리케이션의 Metrics·Logs 등을 관측할 수 있는 서비스다.

### ✅ 159. Alarm

Metric이 설정한 조건을 만족하는지 평가한다.

### ✅ 160. 주요 설정

```text
Period

Evaluation Periods

Datapoints to Alarm

Threshold

Missing Data Treatment
```

### ✅ 161. Period

한 개 평가 데이터가 집계되는 시간 구간이다.

### ✅ 162. Evaluation Periods

평가에 사용할 최근 데이터 구간의 수다.

### ✅ 163. Datapoints to Alarm

그중 몇 개 구간에서 임계값을 위반해야 ALARM 상태로 전환할지 정의한다.

### ✅ 164. 예시

```text
Evaluation Periods:
3

Datapoints to Alarm:
2
```

### ✅ 165. 의미

최근 세 평가 구간 중 두 구간에서 임계값 위반이 발생하면 ALARM이 될 수 있다.

### ✅ 166. 이 방식의 장점

단발성 변동과 지속적인 문제를 구분하는 데 도움이 된다.

### ✅ 167. 중요한 주의

Missing Data 처리 정책에 따라 실제 평가 결과는 달라질 수 있다.

---

## 21. Release Health에서 CloudWatch 활용

### ✅ 168. CloudWatch Metric 후보

```text
Backend HTTP 5xx

API Latency

EC2 CPU

Memory Usage

RDS Connections

Queue Backlog
```

### ✅ 169. 중요한 구분

EC2 CPU가 높다고 실제 고객의 신청이 실패했다고 단정할 수 없다.

### ✅ 170. 반대로

CPU가 낮아도 애플리케이션 코드 오류로 신청이 실패할 수 있다.

### ✅ 171. 따라서

인프라 지표와 업무 지표를 함께 본다.

### ✅ 172. Custom Metric

NestJS에서 직접 정의한 API Operation별 오류나 업무 결과를 CloudWatch로 전송할 수 있다.

### ✅ 173. 하지만 비용을 고려한다

Custom Metric과 로그 수집량이 늘어나면 비용이 증가할 수 있다.

### ✅ 174. 초기 구성

이미 사용 중인 CloudWatch 로그와 기존 DB 업무 이벤트를 먼저 재사용한다.

### ✅ 175. 중요한 원칙

**Release Health를 위해 처음부터 복잡한 Observability 서비스를 여러 개 도입할 필요는 없다.**

---

## 22. Metric Cardinality

### ✅ 176. Cardinality란?

Metric을 구분하는 Label 또는 Dimension 값의 조합 수다.

### ✅ 177. 위험한 설계

```text
release_id

request_id

customer_id

order_id
```

를 모든 Metric의 Dimension으로 사용하는 것이다.

### ✅ 178. 문제

고유 조합이 지나치게 많아질 수 있다.

### ✅ 179. 따라서

Metric은 낮은 Cardinality로 관리한다.

### ✅ 180. 권장 Dimension 예시

```text
Service

Environment

Operation

Outcome
```

### ✅ 181. Release ID는?

구조화된 Deployment Event나 Log에 기록하고 시간과 배포 버전의 관계를 통해 분석할 수 있다.

### ✅ 182. 필요하다면

일시적인 Canary Group이나 제한된 Version Dimension을 사용할 수 있지만 비용과 Cardinality를 검토한다.

### ✅ 183. 개인정보

고객 이름·전화번호·IP 등의 개인 식별자를 Metric Dimension으로 사용하지 않는다.

### ✅ 184. 중요한 원칙

**운영 지표는 집계에 적합하게 설계하고 개별 요청의 상세 추적은 로그·Trace로 분리한다.**

## 23. Business SLI

### ✅ 185. SLI란?

서비스의 실제 품질을 측정하기 위해 정의한 지표다.

### ✅ 186. 휴대폰 판매몰의 중요한 SLI

```text
Application Submission Success

Order Creation Correctness

Admin Order Availability

Notification Processing Reliability
```

### ✅ 187. 가장 중요한 후보

고객 신청 API의 실제 업무 성공률이다.

### ✅ 188. 단순 HTTP 200으로 충분할까?

아니다.

### ✅ 189. 업무 성공

```text
요청 수신

↓

Validation 통과

↓

DB Transaction 성공

↓

Application / Order 생성

↓

업무 규칙 만족
```

을 확인해야 한다.

### ✅ 190. 중요한 예외

신청이 생성됐지만 HTTP 응답이 유실된 경우가 있다.

### ✅ 191. 따라서

```text
CONFIRMED_SUCCESS

CONFIRMED_FAILURE

OUTCOME_UNKNOWN
```

을 구분한다.

### ✅ 192. 중요한 원칙

**신청 성공률은 HTTP 상태가 아니라 실제 업무 결과를 기준으로 정의해야 한다.**

### ✅ 195. 실패 건수

## 25. 신청 완료율과 배포 검증

```text
↓

Submit Attempt

↓

Application Created
```

### ✅ 203. 배포 직후

Application Created 비율이 급격히 낮아졌다면 문제가 있을 수 있다.

### ✅ 204. 하지만 원인은 여러 가지다

```text
Actual UI Error

Backend Error

Traffic Mix Change

Product Condition Change

Marketing Campaign

Customer Intent
```

### ✅ 205. 따라서

고객 이용 흐름과 기술 오류를 함께 확인한다.

### ✅ 206. 중요한 지표

### ✅ 208. 중요한 원칙

**Conversion 변동을 곧바로 배포 장애라고 확정하지 않되, 실제 기술 오류와 함께 나타나면 우선 조사한다.**

## 26. Database Invariant

### ✅ 209. 배포가 성공했어도 DB 데이터가 잘못될 수 있다

### ✅ 210. 예시

```text
Order Status

Pricing

Application Attempt

Customer Ownership
```

### ✅ 211. 중복 신청

동일한 논리적 Attempt에서 중복 주문이 생성되는지 확인한다.

### ✅ 212. 가격 불일치

고객에게 안내된 최종 가격과 실제 저장된 가격이 업무 정책에 맞는지 확인한다.

### ✅ 213. 상태 전이

허용되지 않은 주문 상태 변경이 발생하는지 확인한다.

### ✅ 214. 권한

고객이 다른 고객의 주문 정보를 조회할 수 있는지 확인한다.

### ✅ 215. 중요한 점

이러한 검증은 실제 고객 데이터에 Write하지 않는 방식으로 구성해야 한다.

### ✅ 216. Production

가능한 범위에서 Read-only Invariant Query를 사용한다.

### ✅ 217. Staging

Synthetic Data를 이용해 실제 쓰기 작업까지 검증한다.

### ✅ 218. 중요한 원칙

**운영 DB 정합성 검증과 테스트 주문 생성은 별도의 안전한 절차로 관리한다.**

## 27. Read-only Invariant SQL

### ✅ 219. 예시 테이블

```text
application_attempts

id
attempt_key
order_id
status
created_at
```

### ✅ 220. 중복 Attempt Key 조사

```sql
SELECT
  attempt_key,

  COUNT(*) AS row_count

FROM application_attempts

WHERE created_at >= $1
  AND created_at < $2

GROUP BY attempt_key

HAVING COUNT(*) > 1;
```

### ✅ 221. 중요한 전제

이 SQL은 예시 Schema 기준이다.

### ✅ 222. 실제 프로젝트

Order·Lead·ApplicationAttempt 모델과 실제 Unique Constraint를 확인해야 한다.

### ✅ 223. SQL 결과가 0건이라면?

조회 조건과 데이터 모델 안에서 중복 Row가 관측되지 않았다는 뜻이다.

### ✅ 224. 하지만

모든 종류의 중복 업무 처리가 없었다고 확정하는 것은 아니다.

### ✅ 225. 중요한 원칙

**정합성 Query는 무엇을 검증했고 무엇을 검증하지 못하는지 명확히 기록한다.**

## 29. Hard Guardrails

### ✅ 233. Hard Guardrail

정의된 조건을 위반하면 다른 지표가 정상이어도 배포 확대를 막는 규칙이다.

### ✅ 234. 예시

```text
Confirmed Duplicate Order

Unauthorized Data Access
```

## 33. TypeScript Release Decision

### ✅ 256. 타입 정의

```typescript
type CheckStatus =
  | 'PASS'
  | 'FAIL'
  | 'NOT_VERIFIED';

type ReleaseDecision =
  | 'HEALTHY'
  | 'HOLD'
  | 'ROLLBACK_REVIEW';

interface ReleaseEvidence {
  criticalInvariant: CheckStatus;

  readiness: CheckStatus;

  requiredSmoke: CheckStatus;

  apiHealth: CheckStatus;

  businessSli: CheckStatus;

  rollbackCompatible: boolean;
}
```

### ✅ 257. 평가 함수

```typescript
function evaluateRelease(
  evidence: ReleaseEvidence,
): ReleaseDecision {
  if (evidence.criticalInvariant === 'FAIL') {
    return 'ROLLBACK_REVIEW';
  }

  const checks = [
    evidence.readiness,
    evidence.requiredSmoke,
    evidence.apiHealth,
    evidence.businessSli,
  ];

  if (checks.includes('FAIL')) {
    return evidence.rollbackCompatible
      ? 'ROLLBACK_REVIEW'
      : 'HOLD';
  }

  if (
    evidence.criticalInvariant !== 'PASS' ||
    checks.includes('NOT_VERIFIED')
  ) {
    return 'HOLD';
  }

  return 'HEALTHY';
}
```

### ✅ 258. 중요한 점

이 코드는 개념 설명을 위한 최소 정책 엔진이다.

### ✅ 259. 자동 Rollback은 실행하지 않는다

함수는 판단 결과만 반환한다.

### ✅ 260. 한계

실제 운영에서는 다음 정보를 추가해야 한다.

```text

Sample Size

Data Freshness

Metric Baseline

Schema Compatibility

Deployment Status
```

### ✅ 261. 중요한 원칙

**Release Decision Engine은 실제 AWS 변경을 실행하는 코드와 분리한다.**

### ✅ 273. 의사결정 예시

| 상황 | 초기 대응 후보 |
|---|---|
| 신규 UI 오류 | Feature Flag OFF 또는 Frontend Rollback 검토 |
| Backend 5xx 급증 | Traffic 차단·Rollback 검토 |
| 주문 중복 생성 | 관련 처리 중단·정합성 조사 |
| 인증 우회 | 즉시 접근 차단·보안 Incident |
| 파괴적 Migration 후 장애 | Fix Forward / 복구 계획 검토 |
| 관측 데이터 부족 | HOLD·추가 검증 |

### ✅ 274. 가장 중요한 점

DB를 되돌리지 않고 이전 Backend를 실행할 수 있는지 확인해야 한다.

### ✅ 275. Rollback 가능

실제 코드와 Schema 호환성이 검증됐다면 이전 버전을 배포하는 방법을 고려한다.

### ✅ 276. Rollback 불가

이전 버전이 현재 DB 구조에서 실행되지 않는다면 추가 수정이나 별도 복구 절차가 필요하다.

### ✅ 277. 중요한 원칙

**Rollback 결정은 단순한 오류율이 아니라 현재 데이터와 업무 상태에서 이전 코드가 안전하게 작동하는지를 기준으로 한다.**

## 37. Automatic Rollback의 실제 조건

### ✅ 278. AWS CodeDeploy

지원되는 배포 구조에서는 배포 실패나 CloudWatch Alarm 등을 기반으로 자동 Rollback을 구성할 수 있다.

### ✅ 279. 그러나

현재 EC2 배포가 직접 SSH, GitHub Actions Script, PM2 등의 방식이라면 CodeDeploy 자동 Rollback이 적용된다고 가정할 수 없다.

### ✅ 280. 실제 확인

```text
CodeDeploy Application

Deployment Group

Alarm Integration

Rollback Configuration
```

이 존재하는지 조사한다.

### ✅ 281. CodeDeploy Rollback

이전 Revision을 새로운 Deployment로 재배포하는 방식이다.

### ✅ 282. 중요한 제한

이전 Deployment에서 발생한 DB 변경이나 외부 알림 발송까지 되돌리지는 않는다.

### ✅ 283. 현재 추천

자동 Rollback은 실제 배포 방식과 Schema 호환성, 고객 업무 안전성이 확인된 제한적인 경우에만 검토한다.

## 40. GitHub Actions Verification 예시

## 📌 요약

1108에서는 운영 서비스의 Frontend·Backend·Database 변경을 안전하게 적용하는 방법을 다뤘다.

```text
Backward Compatibility
       ↓
Expand-and-Contract
       ↓
Safe Deployment
       ↓
Rollback Compatibility
```

1109에서는 배포가 끝난 이후 실제 서비스가 정상인지 평가하는 방법을 다뤘다.

```text
New Release
       ↓
Runtime Version Verification
       ↓
Readiness
       ↓
Synthetic Verification
       ↓
Technical Metrics
       ↓
Business SLI
       ↓
Critical Invariant
       ↓
Evidence Evaluation
       ↓
Release Health
       ↓
Human Decision
       ↓
Final Verification
```

이번 편의 핵심 원칙은 다음과 같다.

**첫 번째 — 배포 성공과 서비스 성공은 다르다.**

GitHub Actions가 성공했더라도 실제 고객 신청이 실패할 수 있다.

**두 번째 — 운영 지표는 실제 배포 버전과 연결해야 한다.**

어느 Commit에서 오류가 시작됐는지 확인할 수 있어야 한다.

**세 번째 — Error Rate와 Latency만으로 충분하지 않다.**

고객 신청 완료와 주문 정합성 같은 Business SLI를 확인한다.

**네 번째 — 데이터가 없으면 정상이라고 판단하지 않는다.**

```text
No Error

≠

No Traffic

≠

Missing Metrics
```

이다.

**다섯 번째 — 중요한 업무 위반은 Health Score보다 우선한다.**

주문 중복 생성이나 개인정보 접근 오류가 있다면 다른 지표가 정상이어도 긴급 대응이 필요하다.

**여섯 번째 — Rollback 가능성을 먼저 확인한다.**

현재 DB 구조에서 이전 Backend가 실행 가능한지 확인해야 한다.

**일곱 번째 — AI는 판단을 지원하고 실제 운영 변경은 통제한다.**

AI가 보고서를 작성할 수 있지만 고객 데이터에 영향을 주는 복구를 무승인으로 실행하게 해서는 안 된다.

현재 투게더몰에서는 다음 순서가 현실적이다.

```text
1. 실제 배포 Commit 확인

2. Backend Readiness

3. Frontend / Admin Smoke Test

4. 핵심 신청 API 검증

5. 기존 CloudWatch 오류 분석

6. Business SLI 연결

7. Rollback Compatibility

8. Release Verification Report

9. Decision Engine

10. 필요 시 Canary / 자동 복구 검토
```

처음부터 복잡한 Canary Analysis Platform이나 자동 Rollback 시스템을 구축할 필요는 없다.

기존 GitHub Actions, CloudWatch, NestJS Logger, PostgreSQL의 업무 결과를 활용해 **배포 후 검증 보고서를 자동 생성하는 것**부터 시작하는 것이 적합하다.

이후 데이터가 충분히 쌓이고 실제 운영 부담이 확인되면 Release Health Scoring과 정책 기반 배포 판정을 확장할 수 있다.

최종적으로 기억해야 할 원칙은 다음과 같다.

**좋은 배포 검증 시스템은 배포가 성공했다고 알려 주는 시스템이 아니다. 실제로 어떤 코드가 실행 중인지, 고객의 중요한 업무가 정상인지, 어떤 오류와 위험이 관측됐는지, 어떤 근거로 유지·중단·복구를 결정했는지를 명확하게 보여 주는 시스템이다.**
