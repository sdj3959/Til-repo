## 1. AWS 인프라를 처음부터 다시 구축해야 한다면?

### ✅ 1. 1116과의 연결

1116에서는 실제 AWS 비용과 고객 신청·주문 처리량을 연결해 인프라의 자원 효율성을 분석하는 방법을 다뤘다.

```text
AWS Billing Data
       ↓
Resource Inventory
       ↓
Resource Efficiency
       ↓
Unit Economics
       ↓
Cost Optimization
       ↓
Validated Savings
```

1117에서는 이러한 인프라 운영의 기반이 되는 **Infrastructure as Code**를 다룬다.

### ✅ 2. 실제 운영 상황

현재 온라인 휴대폰 판매몰이 다음과 같은 환경에서 운영되고 있다고 가정한다.

```text
Customer Frontend
       ↓
CloudFront
       ↓
S3

Admin Frontend
       ↓
CloudFront
       ↓
S3

NestJS Backend
       ↓
EC2
       ↓
RDS PostgreSQL

Application Configuration
       ↓
SSM Parameter Store

Monitoring
       ↓
CloudWatch
```

실제 AWS 자원 구성과 서비스 연결 관계는 운영 계정에서 확인해야 한다.

### ✅ 3. 현재 발생할 수 있는 문제

AWS Console에서 직접 EC2를 생성한다.

RDS를 생성한다.

Security Group을 수정한다.

CloudFront Cache Policy를 변경한다.

SSM Parameter를 추가한다.

시간이 지나면서 현재 AWS 환경에는 여러 변경사항이 쌓인다.

### ✅ 4. 어느 날 신규 서비스 구축이 필요하다

기존 LG U+ 판매몰 외에 SKT와 KT 판매몰을 추가해야 한다.

```text
기존 LGU 운영 환경

        ↓

SKT 신규 서비스

        ↓

KT 신규 서비스
```

### ✅ 5. 문제 발생

기존 환경을 참고해 AWS Console에서 새로운 자원을 만들려고 한다.

하지만 다음 항목이 정확하게 기억나지 않는다.

```text
EC2 Instance 설정

Security Group 연결 관계

RDS Subnet Group

CloudFront Cache Policy

S3 Bucket Policy

IAM Role 권한

CloudWatch Retention

SSM Parameter 경로
```

### ✅ 6. 더 큰 문제

기존 환경과 비슷하게 구축했지만 작은 설정 차이가 발생한다.

```text
LGU:

정상 배포
정상 DB 연결
정상 CloudFront 동작
```

```text
SKT:

배포는 성공
DB 연결 실패
Cache 동작 차이 발생
```

### ✅ 7. 원인 후보

코드는 비슷하지만 인프라 구성이 다르다.

### ✅ 8. 해결 방향

인프라의 목표 상태를 코드로 정의하고 변경 이력을 Git으로 관리한다.


### ✅ 9. 이번 편의 핵심 질문

**기존 AWS 운영 자원을 안전하게 보호하면서 인프라 구성을 코드로 관리하고, 필요할 때 동일한 환경을 재현할 수 있을까?**

**기존에 정상적으로 운영 중인 AWS 환경을 Terraform으로 관리한다는 것은 모든 자원을 삭제하고 다시 생성하는 것이 아니다.**

현재 자원을 안전하게 관리 대상으로 등록하고, 이후 변경사항을 코드와 연결하는 것부터 시작한다.

## 2. Infrastructure as Code란?

### ✅ 12. 정의

Infrastructure as Code, 줄여서 IaC는 서버·네트워크·데이터베이스·스토리지 등의 인프라 구성을 코드로 정의하고 관리하는 방식이다.

### ✅ 13. 기존 방식

```text
AWS Console 접속
       ↓
EC2 생성
       ↓
Security Group 설정
       ↓
RDS 생성
       ↓
DB 연결
       ↓
CloudFront 설정
```

### ✅ 14. IaC 방식

```text
Infrastructure Configuration 작성
       ↓
Git Commit
       ↓
Validation
       ↓
Plan
       ↓
Approval
       ↓
Apply
```

### ✅ 15. 중요한 차이

Console 방식에서는 개발자가 직접 수행한 작업을 별도로 기록해야 한다.

IaC 방식에서는 관리 대상 인프라의 의도된 구성이 코드에 남는다.

### ✅ 16. 예시

```hcl
resource "aws_cloudwatch_log_group" "backend" {
  name              = "/example/staging/backend"
  retention_in_days = 30
}
```

이 코드는 특정 CloudWatch Log Group의 목표 설정을 정의한다.

### ✅ 17. 실제로 얻을 수 있는 장점

- 인프라 변경 이력을 Git으로 추적
- 기존 환경의 구성 파악
- 신규 환경 구축 자동화
- 변경 전 영향 범위 검토
- 반복적인 인프라 구성 표준화
- 인프라 설정 차이 발견

### ✅ 18. 중요한 한계

IaC가 존재한다고 실제 서비스가 자동으로 복구되는 것은 아니다.

DB 데이터, 고객 신청 기록, S3 객체 내용, 애플리케이션 Build Artifact 등의 복구는 별도로 설계해야 한다.

### ✅ 19. 중요한 원칙

**IaC는 인프라 구성의 재현성을 높이는 기술이며 실제 업무 데이터의 Backup과 Restore를 대신하지 않는다.**

## 3. Imperative와 Declarative

### ✅ 20. Imperative 방식

어떤 작업을 어떤 순서로 수행할 것인지 직접 명령하는 방식이다.

```text
1. EC2 생성

2. Security Group 생성

3. EC2에 Security Group 연결

4. RDS 생성

5. Backend와 RDS 연결
```

### ✅ 21. Declarative 방식

최종적으로 어떤 상태가 되어야 하는지 정의한다.

```text
Backend Instance가 존재해야 한다.

Database가 존재해야 한다.

Database는 지정된 Network에 있어야 한다.

Backend에서만 Database에 접근할 수 있어야 한다.
```

### ✅ 22. Terraform의 기본 방향

Terraform은 선언적인 설정을 기반으로 인프라의 현재 상태와 목표 상태를 비교하고 필요한 변경을 계획한다.

### ✅ 23. 예시

기존 Log Group의 보관 기간이 7일이고 코드에서는 30일을 정의했다면 Terraform은 해당 설정을 변경하는 Plan을 만들 수 있다.

### ✅ 24. 중요한 주의

선언적인 방식이라고 변경 결과가 항상 안전한 것은 아니다.

일부 속성 변경은 기존 자원을 수정하는 대신 삭제 후 재생성을 요구할 수 있다.

### ✅ 25. 중요한 원칙

**목표 상태를 선언하는 것과 해당 목표 상태로 안전하게 전환하는 것은 별개의 문제다.**

## 4. Terraform이란?

### ✅ 26. 정의

Terraform은 인프라의 구성을 코드로 정의하고 실제 인프라 자원의 생성·변경·삭제를 관리할 수 있는 IaC 도구다.

### ✅ 27. 주요 구성

```text
Terraform CLI

HCL Configuration

Provider

Resource

Data Source

State

Module

Backend
```

### ✅ 28. HCL

Terraform에서 주로 사용하는 설정 언어다.

HashiCorp Configuration Language의 약자다.

### ✅ 29. Terraform이 할 수 있는 작업

```text
AWS EC2 구성 관리

RDS 구성 관리

VPC / Subnet 구성 관리

Security Group 관리

S3 Bucket 설정 관리

CloudFront Distribution 관리

IAM Role / Policy 관리
```

### ✅ 30. Terraform이 관리하는 범위

AWS Provider가 지원하고 실제 코드 및 State에 등록된 자원을 중심으로 관리한다.

### ✅ 31. 중요한 점

Terraform을 설치했다고 기존 AWS 계정의 모든 자원이 자동으로 관리 대상이 되는 것은 아니다.

### ✅ 32. 중요한 원칙

**Terraform은 AWS 전체를 자동으로 관리하는 도구가 아니라 명시적으로 정의하고 연결한 자원의 수명주기를 관리하는 도구다.**

---

## 5. Terraform과 다른 운영 도구의 차이

### ✅ 33. Terraform

인프라 자원과 그 구성의 수명주기를 관리한다.

### ✅ 34. GitHub Actions

빌드·테스트·배포·Terraform 검증 등의 작업을 자동 실행한다.

### ✅ 35. Docker

애플리케이션과 실행 환경을 Container 형태로 구성한다.

### ✅ 36. SSM Parameter Store

애플리케이션 설정과 필요한 Parameter를 관리한다.

### ✅ 37. Ansible 등 Configuration Management 도구

서버 내부의 패키지·설정 파일·운영체제 구성 등을 관리하는 데 활용할 수 있다.

### ✅ 38. Prisma Migration

PostgreSQL의 애플리케이션 Schema 변경을 관리한다.

### ✅ 39. 비교

| 도구 | 주요 책임 |
|---|---|
| Terraform | AWS 자원 구성 |
| GitHub Actions | 검증 및 배포 실행 |
| Docker | 애플리케이션 실행 패키징 |
| SSM | Runtime Configuration |
| Prisma Migration | DB Schema 변경 |
| Git | 변경 이력 관리 |

### ✅ 40. 중요한 원칙

**Terraform 하나로 애플리케이션 배포·DB Migration·Secret Rotation·운영체제 관리까지 모두 해결하려고 하지 않는다.**

## 6. 현재 투게더몰에 Terraform이 필요한 이유

### ✅ 41. 첫 번째 — 기존 인프라의 문서화

AWS Console의 현재 구성을 코드와 연결해 확인할 수 있다.

### ✅ 42. 두 번째 — 통신 3사 확장

LG U+·SKT·KT 서비스에서 반복되는 인프라 패턴을 재사용할 수 있다.

### ✅ 43. 세 번째 — 장애 복구

인프라 구성 정보가 남아 있으므로 새로운 환경을 구축하는 데 도움을 받을 수 있다.

### ✅ 44. 네 번째 — 보안 설정 관리

Security Group과 IAM Role의 변경 이력을 추적할 수 있다.

### ✅ 45. 다섯 번째 — 비용 관리

1116에서 다뤘던 Cost Allocation Tags와 자원 사양 변경을 코드로 관리할 수 있다.

### ✅ 46. 여섯 번째 — 개발자 의존도 감소

특정 개발자의 기억에만 의존하던 AWS 설정을 팀이나 회사가 확인할 수 있는 형태로 관리할 수 있다.

### ✅ 47. 그러나 중요한 현실

현재 서비스가 정상적으로 운영되고 있다면 Terraform 도입 자체를 이유로 인프라 전체를 변경할 필요는 없다.

### ✅ 48. 현재 추천

```text
Existing Infrastructure Inventory
       ↓
Read-only Analysis
       ↓
Small Import Experiment
       ↓
Zero-change Plan
       ↓
Gradual Adoption
```

### ✅ 49. 중요한 원칙

**1인 개발 환경에서는 Terraform을 한 번에 전체 도입하기보다 관리하기 쉬운 자원부터 점진적으로 코드화하는 것이 적절하다.**

## 7. Terraform 전체 동작 구조

### ✅ 50. 기본 구조

```text
Terraform Configuration
       │
       ├── Provider
       ├── Resource
       ├── Variables
       └── Modules
                 ↓
           Terraform CLI
                 ↓
          State + AWS API
                 ↓
          Execution Plan
                 ↓
            Human Review
                 ↓
               Apply
                 ↓
          Updated AWS Resources
                 ↓
          Updated State
```

### ✅ 51. Configuration

원하는 인프라 구성을 정의한다.

### ✅ 52. State

Terraform의 Resource Address와 실제 AWS 자원 사이의 관계를 관리한다.

### ✅ 53. Provider

Terraform과 AWS API 사이의 연동을 담당한다.

### ✅ 54. Plan

현재 상태와 목표 상태의 차이를 바탕으로 실행할 변경사항을 계산한다.

### ✅ 55. Apply

검토한 변경사항을 실제로 실행한다.

### ✅ 56. 중요한 원칙

**Terraform의 핵심은 단순 자원 생성이 아니라 Configuration·State·실제 인프라 사이의 관계를 관리하는 것이다.**

## 8. Provider

### ✅ 57. Provider란?

Terraform이 특정 플랫폼의 API를 사용해 자원을 관리할 수 있도록 연결해 주는 Plugin이다.

### ✅ 58. AWS Provider

AWS의 EC2·RDS·S3·CloudFront 등의 자원과 연동한다.

### ✅ 59. 기본 설정 예시

```hcl
terraform {
  required_version = ">= 1.10.0, < 2.0.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
}

provider "aws" {
  region = var.aws_region
}
```

### ✅ 60. 중요한 전제

위 버전 범위는 학습용 구성 예시다.

실제 도입 시에는 Terraform 버전과 AWS Provider의 지원 범위를 확인하고 검증된 버전을 고정해야 한다.

### ✅ 61. Provider가 필요한 이유

Terraform 자체가 모든 AWS Resource의 API 세부사항을 직접 알고 있는 것이 아니기 때문이다.

### ✅ 62. Provider Version의 중요성

Provider 버전에 따라 다음 요소가 바뀔 수 있다.

```text
Resource Schema

Required Arguments

Default Values

Computed Attributes

Import Support

Replacement Behavior
```

### ✅ 63. 중요한 원칙

**Terraform Core와 AWS Provider 버전을 별도로 관리하고 버전 업그레이드가 실제 인프라에 미치는 영향을 검증한다.**

---

## 9. Resource

### ✅ 64. Resource

Terraform이 생성하고 변경하며 수명주기를 관리하는 대상이다.

### ✅ 65. 예시

```hcl
resource "aws_cloudwatch_log_group" "backend" {
  name              = "/example/staging/backend"
  retention_in_days = 30

  tags = {
    Project     = "telecom-commerce"
    Environment = "staging"
    Component   = "backend"
  }
}
```

### ✅ 66. Resource Type

```text
aws_cloudwatch_log_group
```

AWS에서 관리하려는 자원의 종류다.

### ✅ 67. Resource Name

```text
backend
```

Terraform 코드 내부에서 사용하는 이름이다.

### ✅ 68. Resource Address

```text
aws_cloudwatch_log_group.backend
```

Terraform이 해당 자원을 식별하는 주소다.

### ✅ 69. 중요한 구분

Resource Address와 실제 AWS 자원 이름은 서로 다르다.

### ✅ 70. 예시

```text
Terraform Address:

aws_cloudwatch_log_group.backend
```

```text
Actual AWS Name:

/example/staging/backend
```

### ✅ 71. 중요한 원칙

**Terraform Resource Name을 변경하는 작업도 State 연결 관계에 영향을 줄 수 있으므로 단순한 변수명 변경처럼 취급하지 않는다.**

---

## 10. Data Source

### ✅ 72. Data Source

이미 존재하는 외부 자원이나 설정 정보를 조회하는 데 사용하는 구성이다.

### ✅ 73. 예시

```hcl
data "aws_caller_identity" "current" {}
```

### ✅ 74. 활용

현재 Provider가 접근하고 있는 AWS 계정 정보를 확인할 수 있다.

### ✅ 75. 기존 VPC 조회 예시

```hcl
data "aws_vpc" "existing" {
  id = var.existing_vpc_id
}
```

### ✅ 76. Resource와 Data Source의 차이

```text
Resource:

Terraform이 해당 자원의
수명주기를 관리한다.
```

```text
Data Source:

외부 자원의 정보를 조회하고
다른 구성에서 활용한다.
```

### ✅ 77. 실제 업무 적용

기존 VPC 전체를 바로 Terraform으로 Import하지 않고 필요한 VPC 정보를 Data Source로 참조할 수 있다.

### ✅ 78. 중요한 제한

Data Source라고 항상 민감정보가 저장되지 않는 것은 아니다.

조회한 속성이 State 또는 Plan에 포함될 수 있다.

### ✅ 79. 중요한 원칙

**아직 관리할 필요가 없는 기존 자원은 Data Source로 참조하고 Terraform의 관리 범위를 불필요하게 확대하지 않는다.**

## 11. Variables·Locals·Outputs

### ✅ 80. Variable

외부에서 설정값을 전달할 수 있게 한다.

```hcl
variable "aws_region" {
  type    = string
  default = "ap-northeast-2"
}
```

서울 Region을 기본값으로 사용하는 설명용 예시다.

### ✅ 81. 환경 변수 정의

```hcl
variable "environment" {
  type = string

  validation {
    condition = contains(
      ["development", "staging", "production"],
      var.environment
    )

    error_message = "Unsupported environment."
  }
}
```

### ✅ 82. Local

여러 Resource에서 공통으로 사용할 값을 계산하거나 정의할 수 있다.

```hcl
locals {
  common_tags = {
    Project     = "telecom-commerce"
    Environment = var.environment
    ManagedBy   = "terraform"
  }
}
```

### ✅ 83. Output

구축된 인프라의 필요한 정보를 외부에서 참조할 수 있도록 정의한다.

```hcl
output "backend_log_group_name" {
  value = aws_cloudwatch_log_group.backend.name
}
```

### ✅ 84. 주의

Output을 통해 DB Password나 외부 API Key를 일반적인 결과로 출력하지 않는다.

### ✅ 85. 중요한 원칙

**환경마다 달라지는 값은 Variable로 분리하고 공통 정책은 Local 또는 Module로 관리하며 Output에는 필요한 최소한의 정보만 노출한다.**

## 14. Terraform State란?

### ✅ 103. 정의

Terraform State는 코드에 정의한 Resource와 실제 인프라 자원 사이의 연결 관계 및 Terraform이 알고 있는 자원 상태를 관리하는 데이터다.

### ✅ 104. 예시

```text
Terraform Resource:

aws_instance.backend
```

실제 AWS 자원:

```text
EC2 Instance ID:

i-example123456789
```

### ✅ 105. State의 역할

두 자원을 연결해 Terraform이 다음 실행에서 어떤 실제 EC2를 관리해야 하는지 알 수 있도록 한다.

### ✅ 106. 개념적인 State 데이터

```json
{
  "resourceAddress": "aws_instance.backend",
  "provider": "aws",
  "remoteResourceId": "i-example123456789"
}
```

위 JSON은 설명용이며 실제 Terraform State Schema가 아니다.

### ✅ 107. State가 없다면?

Terraform은 코드에 정의한 Resource가 이미 AWS에 존재한다는 사실을 알지 못할 수 있다.

### ✅ 108. 결과

기존 Resource가 존재하는데도 신규 생성 계획이 나타날 수 있다.

### ✅ 109. 중요한 구분

```text
Terraform Configuration:
원하는 목표 상태
```

```text
Terraform State:
Terraform이 관리하는 자원의 연결 관계 및 기록
```

```text
Actual Infrastructure:
실제 AWS에 존재하는 현재 구성
```

### ✅ 110. 중요한 원칙

**Terraform State는 단순 Cache 파일이 아니라 실제 운영 자원과 코드 사이의 관계를 관리하는 핵심 운영 데이터다.**


### ✅ 113. 별도로 관리해야 하는 데이터

## 16. Local State의 문제

### ✅ 117. 기본적인 Local State

Terraform은 로컬 Backend를 사용하는 경우 일반적으로 다음 파일에 State를 저장한다.

```text
terraform.tfstate
```

### ✅ 118. 문제 사례

```text
MacBook에서 Terraform 작업
       ↓

       ↓
장비 초기화
       ↓
State 파일 유실
```

### ✅ 119. 실제 AWS 자원은?

State 파일이 없어졌다고 AWS 자원이 자동 삭제되는 것은 아니다.

### ✅ 120. 하지만

Terraform이 기존 AWS 자원과 코드의 연결 관계를 잃어버릴 수 있다.

### ✅ 121. 또 다른 문제

```text

다른 작업 환경 State
```

가 서로 다르면 동일한 AWS 자원을 여러 State에서 관리하는 위험이 발생할 수 있다.

### ✅ 122. 현재 추천

실제 운영 AWS 자원을 관리할 때는 접근권한과 백업, 잠금이 구성된 Remote State를 사용한다.

### ✅ 123. 중요한 원칙

**운영 Terraform State를 개발자 개인 장비에만 보관하는 구조는 장비 변경과 장애 복구 측면에서 위험하다.**

## 18. State Locking

### ✅ 132. 왜 잠금이 필요할까?

동일한 State를 여러 작업이 동시에 수정하면 State 충돌 위험이 발생한다.

### ✅ 133. 예시

```text
Developer A:
terraform apply

Developer B:
terraform apply
```

두 작업이 같은 State를 수정하려고 할 수 있다.

### ✅ 134. State Locking

지원되는 Backend에서 특정 State에 대한 동시 작업을 제한할 수 있는 기능이다.

### ✅ 135. S3 Locking

Terraform의 S3 Backend에서는 다음 설정을 사용할 수 있다.

```hcl
use_lockfile = true
```

### ✅ 136. DynamoDB 기반 잠금

기존 Terraform 구성에서는 DynamoDB Table을 이용해 State Locking을 구현한 사례가 많다.

현재 HashiCorp 공식 문서에서는 이 방식이 deprecated 상태라고 안내한다.

### ✅ 137. 중요한 주의

기존 DynamoDB Locking 환경을 무작정 제거하지 않는다.

Terraform 실행 버전과 기존 실행 주체의 호환성을 확인해 전환해야 한다.

### ✅ 138. Lock 권한

S3 Lockfile을 이용할 때는 State Object 접근 권한과 함께 Lock Object를 생성·조회·삭제할 수 있는 필요한 권한이 있어야 한다.

### ✅ 139. 중요한 원칙

**State Locking은 동일 State에 대한 동시 작업을 보호하지만 AWS Console의 수동 변경이나 서로 다른 State 사이의 중복 관리를 모두 차단하는 기능은 아니다.**

---

## 19. State Lock 오류가 발생하면?

### ✅ 140. 실제 상황

Terraform 실행 중 다음 작업이 State Lock을 기다리게 된다.

### ✅ 141. 첫 번째 확인

다른 Terraform 작업이 실제로 진행 중인지 확인한다.

### ✅ 142. 확인 대상

```text
Local Terminal

GitHub Actions

Other Infrastructure Automation

Previous Failed Operation
```

### ✅ 143. 잘못된 대응

Lock 오류가 발생할 때마다 무조건 잠금을 강제로 해제한다.

### ✅ 144. force-unlock

Terraform에는 Lock을 수동으로 해제할 수 있는 명령이 있다.

하지만 실제 작업이 종료됐고 남아 있는 Lock이 비정상적으로 유지된 경우에 한해 신중하게 검토해야 한다.

### ✅ 145. 중요한 위험

아직 Apply가 진행 중인데 Lock을 해제하면 다른 작업이 같은 State를 변경할 수 있다.

### ✅ 146. 추천 대응

```text
Lock Error
       ↓
Actual Running Job 확인
       ↓
Lock Owner 확인
       ↓
Previous Operation Result 확인
       ↓
State Integrity 확인
       ↓
필요한 경우 승인된 Lock Recovery
```

### ✅ 147. 중요한 원칙

**State Lock 오류는 제거해야 할 불편한 제한이 아니라 동시 인프라 변경을 방지하기 위한 안전장치다.**

## 20. State Backend Bootstrap

### ✅ 148. 처음부터 발생하는 질문

State를 S3에 저장하려면 S3 Bucket이 먼저 존재해야 한다.

그렇다면 State Bucket 자체는 어떻게 Terraform으로 관리할까?

### ✅ 149. Bootstrap

Terraform의 기본 실행 기반을 먼저 준비하는 과정이다.

### ✅ 150. 추천 구조

```text
infra/
├── bootstrap/
│   └── state-backend/
│
└── environments/
    ├── staging/
    └── production/
```

### ✅ 151. Bootstrap의 책임

```text
Terraform State Bucket

Encryption Configuration

Versioning

Block Public Access

필요한 Backend IAM 권한
```

### ✅ 152. 운영 환경의 책임

```text
Application Infrastructure

EC2

RDS

CloudFront

Application S3

Monitoring
```

### ✅ 153. 중요한 점

Bootstrap 과정에서 사용하는 최초 Local State도 중요하다.

이후 별도 Remote Backend로 이전하거나 안전한 보관 정책을 적용해야 한다.

### ✅ 154. 중요한 주의

운영 인프라를 삭제하는 작업과 State 저장소를 삭제하는 작업이 함께 실행되지 않도록 관리 범위를 분리한다.

### ✅ 155. 중요한 원칙

**Terraform을 운영하기 위한 기반 인프라와 실제 고객 서비스를 구성하는 인프라는 별도의 수명주기로 관리하는 것이 적절하다.**

## 21. State Backend Bucket 예시

### ✅ 156. 설명용 Bootstrap 구성

신규 전용 State Bucket을 준비하는 경우의 예시다.

실제 운영 자원 Import와 분리된 Bootstrap Root Module에서 검토한다.

```hcl
resource "aws_s3_bucket" "terraform_state" {
  bucket        = var.state_bucket_name
  force_destroy = false

  lifecycle {
    prevent_destroy = true
  }

  tags = {
    Project   = "telecom-commerce"
    Component = "terraform-state"
    ManagedBy = "terraform"
  }
}

resource "aws_s3_bucket_versioning" "terraform_state" {
  bucket = aws_s3_bucket.terraform_state.id

  versioning_configuration {
    status = "Enabled"
  }
}

resource "aws_s3_bucket_public_access_block" "terraform_state" {
  bucket = aws_s3_bucket.terraform_state.id

  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

resource "aws_s3_bucket_server_side_encryption_configuration" "terraform_state" {
  bucket = aws_s3_bucket.terraform_state.id

  rule {
    apply_server_side_encryption_by_default {
      sse_algorithm = "AES256"
    }
  }
}
```

### ✅ 157. 주요 설정

`force_destroy = false`는 객체가 남아 있는 Bucket의 강제 삭제를 허용하지 않는 방향으로 설정한다.

### ✅ 158. Versioning

State의 이전 Object Version을 보존하는 데 도움이 된다.

### ✅ 159. Encryption

위 예시는 SSE-S3를 사용한다.

회사 보안 정책과 접근권한 관리 요구에 따라 고객 관리형 KMS Key를 사용하는 SSE-KMS를 검토할 수 있다.

### ✅ 160. 실제 운영에서 필요한 추가 검토

```text
Bucket Policy

TLS Enforcement

Least Privilege IAM

KMS Key Policy

Noncurrent Version Retention

State Recovery Procedure
```

### ✅ 161. 중요한 한계

Versioning은 모든 사고에서 자동 복구를 제공하는 기능이 아니다.

이전 State를 복구할 때 실제 AWS 인프라의 현재 상태와 일치하는지 확인해야 한다.

### ✅ 162. 중요한 원칙

**State 저장소는 생성보다 접근권한·삭제 방지·이전 버전 보존·복구 절차가 중요하다.**

## 22. Terraform State의 보안 위험

### ✅ 163. State에는 무엇이 들어갈까?

실제 Provider가 읽거나 관리하는 다양한 Resource Attribute가 포함될 수 있다.

### ✅ 164. 민감정보 후보

```text
Database Password

API Key

Access Token

Private Configuration

Connection Information

IAM Policy Details
```

### ✅ 165. 위험한 방식

```text
terraform.tfstate
       ↓
GitHub Repository Commit
```

### ✅ 166. 또 다른 위험

```text
terraform show -json
       ↓
전체 결과를 Notion 또는 AI API에 전송
```

### ✅ 167. 중요한 사실

Terraform에서 `sensitive = true`를 지정하면 일반 CLI 출력 등에서 값을 가릴 수 있다.

하지만 해당 값이 State나 Plan 파일에서 제거된다는 의미는 아니다.

### ✅ 168. Sensitive Variable 예시

```hcl
variable "db_password" {
  type      = string
  sensitive = true
}
```

위 설정만으로 State에 DB Password가 저장되지 않는다고 보장할 수 없다.

### ✅ 169. 추가 주의

`terraform output -json`, `terraform show -json` 등의 기계 판독용 출력에는 민감한 실제 값이 나타날 수 있다.

### ✅ 170. 중요한 원칙

**Terraform의 sensitive 설정은 출력 보호 기능이지 모든 Secret을 State에서 제거하는 기능이 아니다.**

## 23. Ephemeral Values와 Write-only Arguments

### ✅ 171. Ephemeral Value

Terraform 작업 중 일시적으로 사용되지만 State나 Plan에 저장하지 않는 값과 관련된 기능이다.

### ✅ 172. 지원 버전

Terraform 1.10 이상에서는 Ephemeral Variable 등의 기능을 사용할 수 있다.

Terraform 1.11 이상에서는 지원되는 Resource의 Write-only Argument를 활용할 수 있다.

### ✅ 173. 예시

```hcl
variable "temporary_api_token" {
  type      = string
  sensitive = true
  ephemeral = true
}
```

### ✅ 174. 중요한 제한

Ephemeral Value는 일반적인 모든 Resource Argument에 자유롭게 사용할 수 있는 값이 아니다.

Terraform이 허용하는 Ephemeral Context에서 사용해야 한다.

### ✅ 175. Write-only Argument

지원되는 Provider Resource에서 Secret을 전달하되 일반적인 State 저장을 피할 수 있는 기능이다.

### ✅ 176. 중요한 전제

실제 AWS Provider 버전과 해당 Resource의 Schema에서 지원하는지 확인해야 한다.

### ✅ 177. RDS에 적용할 때

기존 운영 RDS의 Password 관련 설정을 변경하면 애플리케이션 연결 장애나 Secret Rotation 문제가 발생할 수 있다.

따라서 State 보호를 이유로 기존 인증 방식을 무작정 변경하지 않는다.

### ✅ 178. 중요한 원칙

**Terraform의 새로운 Secret 관리 기능은 실제 Provider 지원 여부와 기존 애플리케이션 인증 구조를 확인한 뒤 적용한다.**

## 24. 현재 SSM Parameter Store 구조와 Terraform

### ✅ 179. 현재 운영 방향

기존 애플리케이션 설정을 SSM Parameter Store에서 가져오는 구조를 유지한다고 가정한다.

### ✅ 180. 추천 책임 분리

```text
Terraform:

IAM Role
SSM 접근 권한
Application Infrastructure
Non-secret Configuration
```

```text
SSM / Secrets Manager:

실제 Secret 관리
Secret Version
필요한 Rotation
```

```text
NestJS Runtime:

승인된 IAM Role로 필요한 값 조회
```

### ✅ 181. 위험한 구성

```hcl
data "aws_ssm_parameter" "database_url" {
  name            = "/example/production/DATABASE_URL"
  with_decryption = true
}
```

이렇게 조회한 값을 Terraform 내부에서 사용하면 설정 방식에 따라 Secret이 State에 포함될 수 있다.

### ✅ 182. 더 적절한 구조

Terraform은 Parameter 경로와 애플리케이션 IAM Role의 접근권한을 관리한다.

실제 값은 애플리케이션이 Runtime에 가져온다.

### ✅ 183. 예시

```hcl
variable "database_url_parameter_name" {
  type = string
}

data "aws_iam_policy_document" "runtime_config" {
  statement {
    actions = [
      "ssm:GetParameter"
    ]

    resources = [
      var.database_url_parameter_arn
    ]
  }
}
```

실제 Parameter ARN을 입력받고 필요한 경우 제한된 `kms:Decrypt` 권한을 별도로 정의한다.

### ✅ 184. 중요한 점

Parameter 이름이나 ARN 자체에 Secret 값을 포함하지 않는다.

### ✅ 185. Parameter Store와 Secrets Manager

기존 Parameter Store 구조를 유지할 수 있다.

자동 Rotation 등의 별도 보안 요구가 있는 DB Credential이나 API Secret은 Secrets Manager 도입의 적절성을 검토할 수 있다.

### ✅ 186. 중요한 원칙

**Terraform은 Secret을 직접 다루는 범위를 최소화하고 애플리케이션의 Runtime Secret 조회 구조와 분리하는 것이 적절하다.**

## 26. 잘못된 AWS 계정 변경 방지

## 27. Terraform Plan

### ✅ 202. 정의

Configuration과 State, 실제 인프라 상태를 비교해 필요한 변경사항을 계산한다.

### ✅ 203. Plan의 대표적인 표시

```text
+    Create

~    Update in-place

-    Destroy

-/+  Destroy and recreate

+/-  Create replacement, then destroy
```

```text

```

기존 자원이 제거되고 새로운 자원으로 교체될 수 있다는 의미다.

### ✅ 205. 예시

```text
aws_db_instance.production

-/+ destroy and then create replacement
```

### ✅ 206. 의미

기존 운영 RDS에 대해 예상하지 못한 교체가 계획될 수 있다.

실제 운영 데이터와 서비스 연결에 중대한 영향을 줄 수 있다.

### ✅ 207. 중요한 점

Plan Summary의 숫자만 확인하면 부족하다.

### ✅ 208. 상세 확인 대상

```text
Resource Address

Changed Attribute

Replacement Reason

Resource Dependency

Before Value

After Value

Unknown Values
```

### ✅ 209. 중요한 원칙

**Terraform Plan에서 예상하지 못한 Destroy 또는 Replacement가 발견되면 Apply를 중단하고 원인을 조사한다.**

## 28. Terraform Plan Exit Code

### ✅ 210. 자동화에서 중요한 옵션

```bash
terraform plan -detailed-exitcode
```

### ✅ 211. 종료 코드

| Exit Code | 의미 |
|---|---|
| 0 | Plan 성공, 변경사항 없음 |
| 1 | 오류 발생 |
| 2 | Plan 성공, 변경사항 존재 |

### ✅ 212. 중요한 차이

일반적인 Shell Script에서는 0이 아닌 종료 코드를 실패로 처리하는 경우가 많다.

### ✅ 213. Terraform의 경우

`-detailed-exitcode`를 사용하면 2는 정상적으로 Plan을 계산했고 변경사항이 있다는 뜻이다.

### ✅ 214. 안전한 처리 예시

```bash
#!/usr/bin/env bash

set -euo pipefail

exit_code=0

terraform plan \
  -input=false \
  -lock-timeout=60s \
  -detailed-exitcode \
  || exit_code=$?

case "$exit_code" in
  0)
    echo "PLAN_NO_CHANGES"
    ;;

  2)
    echo "PLAN_HAS_CHANGES"
    ;;

  1)
    echo "PLAN_FAILED"
    exit 1
    ;;

  *)
    echo "PLAN_UNKNOWN_EXIT_CODE"
    exit 1
    ;;
esac
```

### ✅ 215. 중요한 점

`PLAN_HAS_CHANGES`는 변경 승인 완료를 의미하지 않는다.

### ✅ 216. 중요한 원칙

**Terraform Plan의 실행 성공 여부와 실제 인프라 변경의 승인 여부를 분리한다.**

## 29. Plan 파일과 Apply

### ✅ 217. 저장된 Plan

Terraform은 계산한 실행계획을 파일에 저장할 수 있다.

```bash
terraform plan \
  -input=false \
  -out=reviewed.tfplan
```

### ✅ 218. Plan 확인

```bash
terraform show reviewed.tfplan
```

### ✅ 219. 승인된 Plan 적용

```bash
terraform apply reviewed.tfplan
```

위 명령은 검토 및 승인된 파일을 적용하는 방법을 설명하는 것이다.

현재 운영 환경에 실행하라는 의미가 아니다.

### ✅ 220. 장점

검토한 Plan과 실제 적용 대상 Plan을 연결할 수 있다.

### ✅ 221. 중요한 보안 위험

저장된 Plan 파일에는 민감한 Resource Attribute와 Variable 값 등이 포함될 수 있다.

### ✅ 222. 따라서

```text
Private Artifact Storage

Restricted Access

Short Retention

No Git Commit

No Public PR Attachment
```

정책을 적용해야 한다.

### ✅ 223. 중요한 주의

저장된 Plan을 적용할 때는 일반적인 새 Plan 승인 과정과 달리 별도의 대화형 승인 없이 적용될 수 있다.

외부 승인 절차가 반드시 필요하다.

### ✅ 224. Stale Plan

State가 다른 작업으로 변경됐거나 실제 인프라가 달라졌다면 기존 Plan을 그대로 적용할 수 없거나 안전하지 않을 수 있다.

### ✅ 225. 중요한 원칙

**Apply는 승인된 코드와 Plan에 연결하고 적용 전 환경·State·시간 경과·외부 변경 여부를 다시 확인한다.**

기존 AWS 운영 환경이 존재하므로 Brownfield 방식으로 접근하는 것이 적절하다.

## 32. Import의 개념

### ✅ 241. Terraform Import

기존 실제 인프라 자원을 Terraform Resource Address에 연결하는 과정이다.

### ✅ 242. 기본 구조

```text
Existing AWS Resource
       ↓
Import ID
       ↓
Terraform Resource Address
       ↓
Terraform State
```

### ✅ 243. 중요한 점

Import는 기존 자원을 새로운 자원으로 복제하는 작업이 아니다.

### ✅ 244. 그러나 Import만 하면 끝일까?

아니다.

Terraform Configuration이 실제 자원의 설정과 일치해야 한다.

### ✅ 245. 잘못된 예시

```text
실제 RDS:

중요 운영 DB
기존 Instance Class 사용
기존 Backup 정책 사용
```

```text
Terraform Code:

다른 Instance Class
다른 Backup 정책
다른 Engine 설정
```

### ✅ 246. 결과

Import 이후 Plan에서 RDS의 변경 또는 교체가 나타날 수 있다.

### ✅ 247. 중요한 원칙

**Import는 관리 관계를 연결하는 작업이며 기존 인프라를 안전하게 관리할 수 있다는 사실은 이후 Plan을 통해 검증해야 한다.**

## 33. CLI Import와 Import Block

### ✅ 248. CLI Import

```bash
terraform import \
  aws_cloudwatch_log_group.backend \
  /example/staging/backend
```

기존 Log Group을 해당 Resource Address와 연결하는 예시다.

### ✅ 249. CLI Import의 특징

현재 State를 변경한다.

일반적으로 Resource Configuration을 별도로 작성해야 한다.

### ✅ 250. Import Block

Terraform 설정 파일에 Import 대상과 연결할 Resource Address를 정의할 수 있다.

```hcl
import {
  to = aws_cloudwatch_log_group.backend

  id = "/example/staging/backend"
}
```

### ✅ 251. Import Block의 장점

Import 작업을 코드로 기록하고 일반적인 Plan 검토 흐름에 포함할 수 있다.

### ✅ 252. 중요한 차이

CLI Import는 명령 실행으로 State 연결을 수행한다.

Import Block은 Plan에서 Import 계획을 확인한 후 Apply 과정에서 실제 연결이 기록된다.

### ✅ 253. 중요한 점

같은 실제 AWS 자원을 여러 Terraform Resource Address에 중복 Import하지 않는다.

### ✅ 254. 현재 추천

새로운 도입에서는 검토와 이력 관리가 가능한 Import Block을 우선 고려한다.

### ✅ 255. 중요한 원칙

**Import 대상은 실제 AWS 자원 하나와 Terraform Resource Address 하나의 명확한 관리 관계로 유지한다.**

## 34. 첫 번째 Import 실습 — CloudWatch Log Group

### ✅ 256. 왜 Log Group부터 시작할까?

기존 운영 RDS나 EC2보다 관리 범위와 의존 관계를 이해하기 쉬운 자원에서 Import 흐름을 학습할 수 있기 때문이다.

### ✅ 257. 중요한 조건

실제 보안 감사 Log Group이나 보관 요건이 중요한 운영 Log Group을 무조건 첫 실습 대상으로 선택하지 않는다.

가능하면 별도의 테스트 환경 자원을 사용한다.

## 35. Terraform Configuration 자동 생성

### ✅ 266. Terraform의 기능

### ✅ 267. 명령 예시

Import Block과 필요한 Provider 설정이 있어야 한다.

생성하려는 출력 파일은 기존 파일과 충돌하지 않아야 한다.

### ✅ 269. 결과

Terraform이 Provider에서 읽은 정보를 바탕으로 Resource Configuration 초안을 생성할 수 있다.

### ✅ 270. 중요한 한계

자동으로 생성된 코드가 최종적으로 적절한 운영 코드라는 보장은 없다.

### ✅ 271. 확인할 문제

```text
Unnecessary Arguments

Provider Default Values

Computed Attributes

Conflicting Arguments

Hard-coded Resource IDs

Sensitive Configuration

Missing Dependencies
```

### ✅ 272. AI와 연결

Codex에게 자동 생성된 Configuration을 제공해 구조를 정리하게 할 수 있다.

다만 Secret이 포함되지 않았는지 먼저 확인해야 한다.

### ✅ 273. 중요한 원칙

**자동 생성된 Terraform Configuration은 기존 인프라의 구조를 이해하기 위한 초안이며 반드시 검토와 Plan 비교를 거쳐야 한다.**

## 38. RDS 삭제 방지 정책

### ✅ 290. Terraform Lifecycle

```hcl
lifecycle {
  prevent_destroy = true
}
```

### ✅ 291. AWS RDS 보호

```hcl
deletion_protection = true
```

### ✅ 292. 중요한 차이

Terraform `prevent_destroy`는 Terraform 계획 단계의 삭제 방지 정책이다.

RDS `deletion_protection`은 AWS Resource 자체의 보호 설정이다.

### ✅ 293. 함께 사용하는 이유

서로 다른 보호 계층으로 활용할 수 있다.

### ✅ 294. 추가 보호

```text
IAM Deny for Unauthorized Deletion

Production Apply Approval

Verified Backup

Restore Test

Plan Policy Gate
```

### ✅ 295. 중요한 한계

`prevent_destroy`를 설정한 Resource Block 자체를 Configuration에서 제거하면 해당 Lifecycle 규칙도 사라진다.

따라서 이 설정 하나만으로 모든 삭제를 영구적으로 막을 수 있는 것은 아니다.

### ✅ 296. 중요한 원칙

**중요 운영 DB는 Terraform·AWS·IAM·변경 승인·복구 정책을 조합해 다층적인 삭제 방지 구조를 구성한다.**

## 42. Import 이후 Zero-change Plan

### ✅ 321. Zero-change Plan

Import가 완료된 뒤 동일한 Configuration을 기준으로 추가 변경사항이 없는 상태를 확인하는 것이다.

### ✅ 322. 목표 흐름

```text
Before Import:
Existing Resource Unmanaged
```

```text
Import Plan:
Import Only
```

```text
Approved Apply:
State Mapping Created
```

```text
After Import Plan:
No Changes
```

### ✅ 323. 중요한 점

Import 이전에는 Import 작업 자체가 변경사항으로 표시될 수 있다.

### ✅ 324. 최종 확인

Import 완료 후 일반 Plan을 다시 실행한다.

```bash
terraform plan \
  -input=false \
  -detailed-exitcode
```

### ✅ 325. 목표

정상적으로 조회했고 코드와 관리 대상 인프라가 일치한다면 종료 코드 0을 기대할 수 있다.

### ✅ 326. 중요한 한계

Zero-change Plan은 Terraform이 관리하는 Resource와 해당 Provider가 비교하는 Attribute 범위에서 변경이 없다는 뜻이다.

AWS 계정 전체에 문제가 없다는 의미는 아니다.

### ✅ 327. 추가 검증

```text
Customer Homepage

Admin Homepage

Backend Health

Database Connectivity

CloudFront Asset Access

Existing Monitoring
```

### ✅ 328. 중요한 원칙

**Import 완료 기준은 State 등록만이 아니라 Zero-change Plan과 기존 운영 서비스의 정상 동작 검증까지 포함해야 한다.**

## 43. Configuration Drift

### ✅ 329. 정의

코드나 기록된 목표 상태와 실제 인프라 구성이 달라지는 현상이다.

### ✅ 330. 발생 사례

Terraform에서는 다음 설정을 정의했다.

```hcl
retention_in_days = 30
```

하지만 AWS Console에서 누군가 실제 Log Group의 보관 기간을 7일로 변경했다.

### ✅ 331. 결과

```text
Terraform Configuration:
30일

Actual AWS Configuration:
7일
```

### ✅ 332. 일반적인 Drift 원인

```text
Manual Console Changes

Emergency Incident Mitigation

External Automation

Provider Defaults

AWS Service-managed Changes

Out-of-band Configuration Updates
```

### ✅ 333. 중요한 구분

모든 Drift가 잘못된 변경은 아니다.

### ✅ 334. 예시

장애 대응 중 승인된 긴급 변경을 AWS Console에서 수행했다.

운영 변경이 필요했지만 Terraform Configuration에는 아직 반영하지 못했다.

### ✅ 335. 중요한 원칙

**Drift는 구성 차이가 발생했다는 사실을 알려 주며 해당 변경이 승인된 것인지 잘못된 것인지는 추가 확인이 필요하다.**

## 44. Terraform의 세 가지 상태 비교

### ✅ 336. Desired State

Terraform 코드에서 정의한 목표 상태다.

### ✅ 337. Recorded State

Terraform State가 기록하고 있는 기존 자원 정보다.

### ✅ 338. Actual State

실제 AWS에서 현재 적용된 상태다.

### ✅ 339. 가상의 비교

```text
Desired State:
Retention 30일

Recorded State:
Retention 30일

Actual State:
Retention 7일
```

### ✅ 340. 여기서 발생한 문제

실제 인프라가 Terraform의 기존 기록 및 목표 구성과 달라졌다.

### ✅ 341. 일반 Plan

실제 AWS 상태를 조회하고 목표 구성에 맞추기 위한 변경을 계획할 수 있다.

### ✅ 342. Refresh-only Plan

실제 AWS 자원의 변경을 State와 관련 Output에 어떻게 반영할지 확인할 수 있다.

### ✅ 343. 중요한 원칙

**Configuration 변경과 State 기록 변경, 실제 AWS 변경을 서로 구분해야 안전한 Drift 관리가 가능하다.**

## 45. Refresh-only Mode

### ✅ 344. 기본 명령

```bash
terraform plan -refresh-only
```

### ✅ 345. 의미

기존 Terraform State와 실제 인프라 사이의 차이를 조사하고 State 기록을 현재 인프라에 맞추기 위한 Plan을 계산한다.

### ✅ 346. 일반 Plan과 차이

```text
Normal Plan:

실제 인프라를 Configuration에
맞추기 위한 변경을 검토
```

```text
Refresh-only Plan:

State와 Output 기록을
실제 인프라에 맞추는 변경을 검토
```

### ✅ 347. 중요한 주의

Refresh-only는 Terraform Configuration 파일을 자동으로 수정하는 기능이 아니다.

### ✅ 348. 예시

```text
Code:
Retention 30일

Actual:
Retention 7일
```

Refresh-only Apply로 State가 실제 상태를 반영하더라도 Code가 30일로 남아 있다면 이후 일반 Plan에서 30일로 되돌리는 변경이 다시 나타날 수 있다.

### ✅ 349. 따라서

외부 변경을 공식적인 목표 상태로 채택하려면 Terraform Configuration도 적절하게 수정해야 한다.

### ✅ 350. 중요한 원칙

**Refresh-only Mode는 State 기록을 실제 상태에 맞추는 기능이며 변경된 실제 구성을 자동으로 승인하거나 코드화하는 기능이 아니다.**

---

## 46. Drift Classification

### ✅ 351. 모든 Drift를 자동 복구하지 않는다

먼저 변경의 종류를 구분한다.

### ✅ 352. 권장 상태

```text
AUTHORIZED_CHANGE

UNAUTHORIZED_CHANGE

EXPECTED_EXTERNAL_CHANGE

PROVIDER_NORMALIZATION

UNKNOWN_CHANGE
```

### ✅ 353. AUTHORIZED_CHANGE

승인된 운영 변경이 Terraform 코드에 아직 반영되지 않았다.

### ✅ 354. UNAUTHORIZED_CHANGE

승인되지 않은 설정 변경이 발견됐다.

### ✅ 355. EXPECTED_EXTERNAL_CHANGE

Auto Scaling이나 별도의 운영 시스템에서 정상적으로 관리하는 값의 변경이다.

### ✅ 356. PROVIDER_NORMALIZATION

Provider의 Default Value 또는 표현 방식 차이 때문에 발생하는 구성 차이다.

### ✅ 357. UNKNOWN_CHANGE

변경 주체와 의도가 확인되지 않았다.

### ✅ 358. 중요한 원칙

**Drift를 발견하면 변경의 기술적 차이와 변경의 승인 여부를 별도로 확인한다.**

### ✅ 359. 기본 흐름

```text

       ↓

       ↓

       ↓

       ↓
```

### ✅ 361. 권장 기준

실제 운영 인프라에 적용됐거나 승인된 Configuration Commit을 사용한다.

### ✅ 362. 왜 그럴까?

main Branch에 새로운 변경이 Merge됐지만 아직 AWS에는 Apply되지 않았을 수 있기 때문이다.

### ✅ 363. 이 경우

**Drift Detection은 단순히 Plan에 변경사항이 존재하는지 확인하는 것을 넘어 적용되지 않은 코드 변경과 실제 외부 변경을 구분해야 한다.**

### ✅ 385. Node.js Guard 코드

```javascript
// scripts/terraform/check-import-plan.mjs

import { readFileSync } from 'node:fs';

function fail(code) {
  console.error(code);

  process.exit(1);
}

const planPath = process.argv[2];

const approvalsPath = process.argv[3];

if (!planPath || !approvalsPath) {
  fail('PLAN_AND_APPROVALS_REQUIRED');
}

let plan;
let approved;

try {
  plan = JSON.parse(
    readFileSync(planPath, 'utf8'),
  );

  approved = JSON.parse(
    readFileSync(approvalsPath, 'utf8'),
  ).imports;
} catch {
  fail('INVALID_INPUT_JSON');
}

if (
  typeof plan?.format_version !== 'string' ||
  !plan.format_version.startsWith('1.')
) {
  fail('UNSUPPORTED_PLAN_FORMAT');
}

if (
  plan.errored === true ||
  plan.complete === false
) {
  fail('INCOMPLETE_OR_ERRORED_PLAN');
}

if (
  !approved ||
  typeof approved !== 'object' ||
  Array.isArray(approved)
) {
  fail('INVALID_IMPORT_APPROVALS');
}

if (
  !Array.isArray(
    plan.resource_changes,
  )
) {
  fail('RESOURCE_CHANGES_NOT_VERIFIED');
}

const violations = [];

const observedImports = new Set();

for (
  const resource of plan.resource_changes
) {
  const address = resource.address;

  const actions = resource.change?.actions;

  const importing =
    resource.change?.importing;

  if (
    typeof address !== 'string' ||
    !Array.isArray(actions) ||
    actions.length === 0
  ) {
    violations.push({
      reason: 'INVALID_RESOURCE_CHANGE',
    });

    continue;
  }

  if (resource.mode === 'data') {
    const validDataAction =
      actions.length === 1 &&
      (
        actions[0] === 'read' ||
        actions[0] === 'no-op'
      );

    if (!validDataAction || importing) {
      violations.push({
        address,

        reason:
          'UNEXPECTED_DATA_SOURCE_ACTION',
      });
    }

    continue;
  }

  if (resource.mode !== 'managed') {
    violations.push({
      address,

      reason:
        'UNSUPPORTED_RESOURCE_MODE',
    });

    continue;
  }

  // 최초 Import 작업에서는
  // 실제 AWS Resource 변경을 허용하지 않는다.
  const isNoOp =
    actions.length === 1 &&
    actions[0] === 'no-op';

  if (!isNoOp) {
    violations.push({
      address,

      reason:
        'RESOURCE_MUTATION_NOT_ALLOWED',
    });
  }

  if (importing) {
    observedImports.add(address);

    const approvedId =
      Object.hasOwn(
        approved,
        address,
      )
        ? approved[address]
        : undefined;

    if (
      typeof approvedId !== 'string' ||
      importing.id !== approvedId
    ) {
      violations.push({
        address,

        reason:
          'UNAPPROVED_IMPORT_MAPPING',
      });
    }
  }
}

for (
  const address of Object.keys(approved)
) {
  if (!observedImports.has(address)) {
    violations.push({
      address,

      reason:
        'EXPECTED_IMPORT_NOT_FOUND',
    });
  }
}

if (violations.length > 0) {
  console.error(
    JSON.stringify({
      status: 'BLOCKED',

      violations,
    }),
  );

  process.exit(1);
}

console.log(
  JSON.stringify({
    status: 'PASS',

    policy: 'IMPORT_ONLY',

    importCount:
      observedImports.size,
  }),
);
```

### ✅ 386. 실행 예시

```bash

  reviewed-plan.json \
  approved-imports.json
```

### ✅ 387. 주요 특징

최초 Import 과정에서는 관리 대상 AWS Resource의 생성·수정·삭제를 허용하지 않는다.

실제 Import Address와 ID가 승인된 목록과 일치하는지 확인한다.

### ✅ 388. 중요한 제한

위 코드는 최초 Import를 위한 보수적인 학습용 정책이다.

일반적인 인프라 변경을 승인하는 범용 정책 엔진이 아니다.

### ✅ 389. 추가 확인

### ✅ 390. 중요한 원칙

**최초 Import 정책은 가능한 변경을 넓게 허용하기보다 검증된 Import 작업만 허용하는 방향으로 시작한다.**

## 52. Check Block과 Preconditions의 차이

### ✅ 397. Terraform 내부 검증

Terraform은 Variable Validation, Preconditions, Postconditions, Check Block 등 여러 검증 방법을 제공한다.

### ✅ 398. Variable Validation

입력값의 허용 범위를 확인한다.

### ✅ 399. Precondition

특정 Resource나 Output의 전제 조건을 검증하는 데 사용할 수 있다.

### ✅ 400. 예시

```hcl
resource "aws_db_instance" "example" {
  # 실제 DB 구성 Argument는 별도로 정의한다.

  publicly_accessible = var.publicly_accessible

  lifecycle {
    precondition {
      condition = (
        var.environment != "production" ||
        var.publicly_accessible == false
      )

      error_message = (
        "Production database must not be public."
      )
    }
  }
}
```

위 코드는 정책 개념을 설명하는 부분 예시다.

### ✅ 401. Check Block

인프라와 관련된 조건을 확인하고 결과를 관측하는 데 활용할 수 있다.

### ✅ 402. 중요한 차이

Check Block의 Assertion 실패는 일반적으로 경고로 처리될 수 있다.

따라서 이를 반드시 Apply를 차단하는 보안 Gate와 동일하게 취급하지 않는다.

### ✅ 403. 권장

중요한 보안 정책은 적절한 Preconditions·외부 Policy Engine·CI Gate·IAM 제한을 조합해 강제한다.

### ✅ 404. 중요한 원칙

**Terraform의 검증 기능마다 실패 시 동작이 다르므로 실제로 변경을 차단하는 정책인지 경고만 발생시키는 정책인지 확인해야 한다.**

## 53. prevent_destroy와 ignore_changes

### ✅ 405. prevent_destroy

Terraform이 특정 Resource를 삭제하거나 삭제를 수반하는 교체 계획을 적용하지 못하도록 보호하는 Lifecycle 설정이다.

### ✅ 406. ignore_changes

특정 Attribute의 변경을 Terraform의 Update 계획에서 무시하도록 설정할 수 있다.

### ✅ 407. 예시

```hcl
lifecycle {
  ignore_changes = [
    tags["ExternalOwner"]
  ]
}
```

### ✅ 408. 사용 목적

별도의 운영 시스템이 특정 Attribute를 관리하는 경우 관리 충돌을 줄일 수 있다.

### ✅ 409. 위험한 사용

```hcl
lifecycle {
  ignore_changes = all
}
```

이를 단순히 모든 Drift를 없애기 위해 사용하면 중요한 설정 변화가 관리 계획에서 누락될 수 있다.

### ✅ 410. 중요한 점

`ignore_changes`는 실제 인프라 변경을 막는 기능이 아니다.

### ✅ 411. 권장 정책

```text
Ignored Attribute

External Owner

Reason

Security Impact

Review Date
```

를 기록한다.

### ✅ 412. 중요한 원칙

**Lifecycle 설정은 문제를 숨기기 위한 기능이 아니라 명확한 Resource 관리 책임과 안전 경계를 정의하는 기능으로 사용한다.**

```hcl
    "/telecom-commerce/staging/${each.key}/frontend"

  retention_days = 30

  tags = {
    Project     = "telecom-commerce"
    Brand       = each.key
    Environment = "staging"
    ManagedBy   = "terraform"
  }
}
```

### ✅ 429. 중요한 전제

위 설정을 Apply하면 실제 새로운 Log Group이 생성될 수 있다.

기존 자원 Import 실습과 별도의 신규 테스트 환경 구성 예시다.

### ✅ 430. 중요한 원칙

**Module 재사용 예제와 기존 운영 자원 Import 예제를 혼용하지 않는다.**

## 57. for_each와 안정적인 Resource Address

### ✅ 431. count

숫자를 기반으로 여러 Resource Instance를 관리하는 데 사용할 수 있다.

### ✅ 432. 예시

```hcl
count = 3
```

Resource Address는 다음과 같은 형태가 될 수 있다.

```text
aws_instance.example[0]

aws_instance.example[1]

aws_instance.example[2]
```

### ✅ 433. 문제 후보

리스트의 중간 항목이 제거되거나 순서가 바뀌면 관리 대상과 Index의 대응 관계가 변경될 수 있다.

### ✅ 434. for_each

안정적인 Key를 기반으로 Resource를 구분할 수 있다.

```text
module.frontend["lgu"]

module.frontend["skt"]

module.frontend["kt"]
```

### ✅ 435. 장점

브랜드별 인프라의 논리적 식별 관계를 명확하게 관리하기 쉽다.

### ✅ 436. 중요한 주의

`for_each`의 Key를 변경해도 Resource Address가 변경될 수 있다.

### ✅ 437. 현재 추천

신규 브랜드의 실제 마케팅 이름이 달라지더라도 Terraform의 관리 Key는 안정적인 내부 식별자로 유지한다.

### ✅ 438. 중요한 원칙

**Terraform Resource의 반복 구성에서는 변경되기 쉬운 순서나 이름보다 안정적인 업무 식별자를 사용한다.**

## 58. moved Block

### ✅ 439. 기존 Resource 이름을 변경하는 상황

```hcl
resource "aws_cloudwatch_log_group" "backend" {
  # 기존 설정
}
```

이를 다음과 같이 변경하려고 한다.

```hcl
resource "aws_cloudwatch_log_group" "backend_api" {
  # 동일한 기존 설정
}
```

### ✅ 440. 위험

Terraform은 서로 다른 Resource Address로 해석할 수 있다.

### ✅ 441. 필요한 기능

```hcl
moved {
  from = aws_cloudwatch_log_group.backend

  to = aws_cloudwatch_log_group.backend_api
}
```

### ✅ 442. 의미

기존 Resource Address에 연결된 관리 관계를 새로운 주소로 이동한다.

### ✅ 443. Module 이동

기존 Root Module Resource를 새로운 Child Module로 옮길 때도 적절한 `moved` Block을 검토할 수 있다.

### ✅ 444. 중요한 점

Resource Address 이동과 실제 Resource Attribute 변경이 동시에 발생하면 Plan에 추가 변경이 나타날 수 있다.

### ✅ 445. 중요한 원칙

**Terraform 코드 리팩토링은 애플리케이션 코드 리팩토링과 달리 Resource Address 및 State 이동을 함께 고려해야 한다.**

## 62. GitHub Actions Terraform Validation

### ✅ 467. 초기 추천

처음부터 GitHub Actions가 운영 AWS에 직접 Apply하도록 구성하지 않는다.

### ✅ 468. 첫 번째 단계

AWS 인증이 필요하지 않은 정적 검증부터 도입한다.

```text
Terraform Format

Terraform Init without Backend

Terraform Validate

Policy Unit Tests
```

### ✅ 469. Workflow 예시

```yaml
name: Terraform Static Validation

on:
  pull_request:

permissions:
  contents: read

jobs:
  validate:
    runs-on: ubuntu-latest

    timeout-minutes: 10

    defaults:
      run:
        working-directory: infra/environments/staging

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup Terraform
        uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: ${{ vars.TERRAFORM_VERSION }}
          terraform_wrapper: false

      - name: Check formatting
        run: terraform fmt -check -recursive

      - name: Initialize without remote backend
        run: |
          terraform init \
            -backend=false \
            -input=false \
            -lockfile=readonly

      - name: Validate
        run: terraform validate
```

### ✅ 470. 중요한 전제

`TERRAFORM_VERSION`에는 로컬과 CI에서 검증한 정확한 버전이 설정돼 있어야 한다.

### ✅ 471. Lock File

`-lockfile=readonly`를 사용하려면 사전에 검증된 `.terraform.lock.hcl`이 준비돼 있어야 한다.

### ✅ 472. 실제 Workflow 수정

Staging과 Production 등 모든 Root Module을 검증해야 한다면 Matrix 또는 별도 Job으로 확대할 수 있다.

### ✅ 473. 보안 주의

위 Action 버전은 구성 예시다.

실제 운영에서는 검증된 Release와 Full Commit SHA 고정을 검토한다.

### ✅ 474. 중요한 원칙

**외부 AWS 권한 없이 수행할 수 있는 Terraform 검증부터 CI에 적용해 안전한 자동화 기반을 만든다.**

## 63. Terraform Plan CI와 AWS OIDC

### ✅ 475. 실제 AWS 자원의 Plan을 계산하려면

필요한 AWS API 및 State Backend 접근권한이 있어야 한다.

### ✅ 476. GitHub Actions 인증 후보

장기 AWS Access Key를 저장하는 대신 GitHub Actions의 OIDC와 AWS IAM Role을 연결할 수 있다.

### ✅ 477. 구조

```text
GitHub Actions
       ↓
OIDC Token
       ↓
AWS STS
       ↓
Temporary Credentials
       ↓
Authorized Terraform Role
```

### ✅ 478. 장점

장기 Access Key를 GitHub Secret에 직접 저장하는 구조를 줄일 수 있다.

### ✅ 479. 역할 분리

```text
Terraform Plan Role

Terraform Apply Role

Application Deployment Role
```

### ✅ 480. 중요한 점

Plan Role은 관리 대상 자원의 조회를 중심으로 구성한다.

하지만 실제 Remote State Locking에는 제한된 Lock Object 생성·삭제 권한 등이 필요할 수 있다.

### ✅ 481. OIDC Trust Policy

다음 조건을 제한해야 한다.

```text
Expected GitHub Repository

Expected Branch or Environment

Expected Audience

Allowed Workflow Execution Context
```

### ✅ 482. 최신 구성 확인

GitHub OIDC Subject에는 기존 Repository 이름 기반 형식뿐 아니라 새로운 Immutable Subject 형식이 적용되는 Repository도 존재할 수 있다.

실제 Repository가 사용하는 Subject Claim 형식에 맞춰 AWS Trust Policy를 작성해야 한다.

### ✅ 483. 중요한 원칙

**OIDC를 사용한다고 모든 GitHub Actions 실행에 AWS 권한을 부여하지 말고 신뢰하는 Repository와 실행 조건을 명확하게 제한한다.**

## 67. Infrastructure Rollback

### ✅ 503. 이전 Git Commit으로 돌아가면 충분할까?

항상 그렇지는 않다.

### ✅ 504. 예시

RDS의 기존 할당 Storage를 단순 설정 변경으로 축소할 수 없는 상황이 있을 수 있다.

### ✅ 506. 또 다른 예시

RDS Engine Version을 올렸다.

이전 버전으로 코드를 되돌렸다고 DB Engine을 안전하게 Downgrade할 수 있다는 의미는 아니다.

### ✅ 507. Infrastructure Rollback 후보

```text

Controlled Forward Fix

Restore from Backup

Replace with Verified Resource

Traffic Cutover
```

### ✅ 508. 중요한 점

Rollback 과정 자체가 새로운 인프라 변경이므로 다시 Plan과 업무 영향 검증을 수행해야 한다.

### ✅ 509. 중요한 원칙

**Terraform Rollback은 Git Revert만으로 보장되지 않으며 실제 AWS 자원의 변경 가능성과 데이터 복구 전략을 함께 고려해야 한다.**

1116에서는 AWS 비용과 실제 업무량을 연결하고 인프라 자원 효율성을 분석하는 Cloud FinOps를 다뤘다.

```text
AWS Cost Baseline
       ↓
Resource Attribution
       ↓
Business Volume
       ↓
Unit Economics
       ↓
Cost Optimization
       ↓
Validated Savings
```

1117에서는 이러한 인프라를 코드 기반으로 관리하고 변경 위험을 통제하는 방법을 다뤘다.

```text
Existing AWS Infrastructure
       ↓
Resource Inventory
       ↓
Infrastructure Configuration
       ↓
Terraform State
       ↓
Import
       ↓
Zero-change Plan
       ↓
Version Control
       ↓
Infrastructure Plan
       ↓
Policy Guardrails
       ↓
Cost / Security Review
       ↓
Human Approval
       ↓
Controlled Apply
       ↓
Production Verification
       ↓
Drift Detection
```

이번 편에서 가장 중요한 원칙은 다음과 같다.

**첫 번째 — Terraform 도입과 기존 AWS 자원 재생성은 다른 일이다.**

기존 투게더몰의 EC2·RDS·S3·CloudFront는 이미 운영 중인 인프라다.

따라서 기존 자원을 보호하면서 Terraform State와 연결하는 Brownfield 도입 방식이 필요하다.

**두 번째 — Terraform State를 이해해야 한다.**

```text
Configuration:
원하는 인프라 상태
```

```text
State:
Terraform의 관리 관계와 기록
```

```text
Actual AWS:
실제 운영 중인 자원 상태
```

이 세 가지의 관계를 이해해야 안전하게 인프라를 변경할 수 있다.

**세 번째 — Import 이후 Zero-change Plan을 확인한다.**

Import만 성공했다고 기존 AWS 자원 관리가 안전하게 완료됐다고 판단하지 않는다.

기존 설정을 정확하게 반영하고 예상하지 못한 생성·수정·삭제·교체가 발생하지 않는지 확인해야 한다.

**네 번째 — State와 Plan은 민감한 운영 데이터다.**

```text
Sensitive Resource Attributes

Database Configuration

Secret Values

Infrastructure Details
```

가 포함될 수 있으므로 Git·Notion·외부 AI 서비스 등에 원문을 저장하지 않는다.

**다섯 번째 — 운영 환경에서는 S3 Remote State와 Locking을 활용한다.**

개인 MacBook에만 State를 보관하는 구조보다 적절하게 보호된 Remote Backend를 사용하는 것이 좋다.

다만 S3 Versioning만으로 모든 State 문제를 자동 복구할 수 있는 것은 아니다.

**여섯 번째 — Terraform과 기존 SSM·GitHub Actions 구조를 분리한다.**

```text
Terraform:
AWS 인프라 구성
```

```text
SSM / Secrets Manager:
Runtime Configuration 및 Secret
```

```text
GitHub Actions:
검증과 배포 실행
```

```text
Prisma:
애플리케이션 DB Schema
```

각 도구의 책임을 명확하게 유지해야 한다.

**일곱 번째 — Drift는 발견 즉시 복구하는 것이 아니다.**

승인된 긴급 변경일 수도 있고, 별도 운영 시스템이 의도적으로 관리하는 값일 수도 있다.

실제 변경의 이유와 영향 범위를 확인한 뒤 코드 반영 또는 복구 여부를 결정한다.

**여덟 번째 — Terraform Apply는 자동 Rollback을 보장하지 않는다.**

실행 중 일부 인프라만 변경되고 다른 Resource에서 실패할 수 있다.

따라서 실제 AWS 상태를 다시 확인하고 새로운 Plan과 복구 절차를 검토해야 한다.

**아홉 번째 — Policy Guardrails를 통해 위험한 변경을 미리 발견한다.**

```text
Unexpected Destroy

Unexpected Replacement

Public Database

Unsafe IAM

Backup Policy Reduction

Unapproved Import
```

등을 실행 전에 확인한다.

**열 번째 — AI는 인프라 변경의 분석과 검증을 지원한다.**

AI에게 Terraform 코드를 작성하게 할 수 있지만 실제 Plan과 AWS 자원의 의미를 개발자가 이해해야 한다.

AI가 생성한 코드라는 이유만으로 운영 Apply를 승인해서는 안 된다.

현재 투게더몰에 가장 현실적인 도입 순서는 다음과 같다.

```text
1. 실제 AWS Resource Inventory 작성

2. 기존 AWS 인프라 연결 관계 문서화

3. 독립된 테스트 환경에서 Terraform 학습

4. AWS SSO 인증과 Account 검증

5. S3 Remote State 및 Locking 설계

6. 비교적 위험도가 낮은 Resource Import

7. Import 이후 Zero-change Plan 확인

8. 기존 운영 Resource 점진적 코드화

9. Production RDS / IAM 보호 정책

10. 통신 3사 공통 Module 설계

11. Terraform Static CI Validation

12. 승인된 Plan 및 Apply 구조

13. Configuration Drift Detection

14. Cost / Security Policy Guardrails

15. AI Infrastructure Change Report
```

특히 현재처럼 한 명의 개발자가 Frontend·Backend·Database·AWS·CI/CD를 함께 관리하는 환경에서는 인프라 코드를 많이 작성하는 것 자체보다 다음 질문에 답할 수 있는 상태를 만드는 것이 중요하다.

```text
현재 AWS에 어떤 자원이 존재하는가?

각 자원은 어떤 서비스에 사용되는가?

누가 해당 자원을 관리하는가?

무엇을 변경하면 어떤 서비스가 영향을 받는가?

어떤 설정이 이전과 달라졌는가?

기존 환경을 어떻게 복구할 수 있는가?

비용은 얼마나 증가하거나 감소하는가?

이 변경은 실제로 승인된 것인가?
```

이 질문에 답할 수 있는 구조가 만들어지면 SKT·KT 서비스가 추가되더라도 기존 LG U+ 인프라를 무작정 복제하지 않고 공통 패턴을 재사용하며 관리할 수 있다.

또한 새로운 개발자가 투입되거나 운영 환경을 이전해야 할 때도 AWS Console의 현재 설정과 기존 개발자의 기억에만 의존하지 않아도 된다.

장기적으로는 기존 업무 성과를 다음과 같은 형태로 발전시킬 수 있다.

```text
React / NestJS 애플리케이션 개발

+

AWS Infrastructure Management

+

Infrastructure as Code

+

Infrastructure Change Safety

+

Configuration Drift Detection

+

Cloud FinOps

+

AI-assisted Operations
```

이는 단순히 홈페이지 기능을 구현하는 개발 경험을 넘어 실제 운영 환경의 구성·보안·비용·복구·변경 안전성을 관리하는 역량으로 연결된다.

최종적으로 기억해야 할 원칙은 다음과 같다.

**좋은 Infrastructure as Code 운영은 모든 AWS 자원을 자동으로 생성하는 것이 아니다. 현재 운영 중인 자원을 안전하게 보호하면서 인프라 구성을 재현 가능하게 만들고, 모든 중요한 변경을 검증·승인·추적할 수 있도록 관리하는 것이다.**
