## 1. Terraform을 도입한 다음에는 무엇을 해야 할까?

### ✅ 1. 1117과의 연결

1117에서는 Terraform을 이용해 기존 AWS 인프라를 안전하게 코드로 관리하는 방법을 다뤘다.

```text
Existing AWS Infrastructure
       ↓
Resource Inventory
       ↓
Terraform Configuration
       ↓
Terraform Import
       ↓
Terraform State
       ↓
Zero-change Plan
       ↓
Configuration Drift Detection
```

이제 기존 EC2·RDS·S3·CloudFront의 구성을 코드와 연결했다고 가정한다.

### ✅ 2. 남아 있는 문제

개발자가 로컬 MacBook에서 직접 다음 명령을 실행한다.

```bash
terraform plan

terraform apply
```

### ✅ 3. 발생할 수 있는 위험

- 잘못된 AWS 계정에서 실행
- Staging 대신 Production을 변경
- 확인하지 않은 Resource Replacement 실행
- 이전 Terraform Configuration 사용
- 다른 작업과 동시에 State 수정
- 승인 이후 변경된 코드를 적용
- 적용 결과와 실제 운영 상태의 불일치

### ✅ 4. 특히 현재 환경에서는

하나의 개발자가 다음 업무를 함께 담당할 수 있다.

```text
React Frontend

NestJS Backend

PostgreSQL

AWS Infrastructure

GitHub Actions

CI/CD

Monitoring

Cost Management
```

### ✅ 5. 문제가 되는 상황

고객 홈페이지의 작은 기능을 배포하려고 GitHub Actions를 실행했다.

그런데 동일한 Workflow에서 Terraform Apply까지 자동으로 실행된다.

새로운 Terraform 설정에 문제가 있다면 애플리케이션 배포와 무관한 AWS 인프라까지 변경될 수 있다.

### ✅ 6. 개선 방향

애플리케이션 배포와 인프라 변경을 분리한다.

```text

       ↓

```

```text
Infrastructure CI/CD
       ↓
Terraform Validation
       ↓
Infrastructure Plan
       ↓
Policy Review
       ↓
Approval

Controlled Apply
```

### ✅ 7. 이번 편의 핵심 질문

**Terraform 변경사항이 Git에 등록된 순간부터 실제 AWS에 반영될 때까지, 어떤 변경이 어떤 근거로 승인되고 적용됐는지 일관되게 검증할 수 있을까?**

## 2. Infrastructure CI/CD란?

### ✅ 10. 정의

Infrastructure CI/CD는 인프라 코드 변경사항을 자동으로 검증하고 승인된 변경을 실제 인프라에 반영하는 작업 흐름이다.

### ✅ 11. 일반적인 애플리케이션 CI/CD

```text
Git Push
       ↓
Lint
       ↓
Build
       ↓
Unit Test
       ↓
Integration Test
       ↓
Deploy
```

### ✅ 12. Infrastructure CI/CD

```text
Terraform Change
       ↓
Format Validation
       ↓
Configuration Validation
       ↓
Infrastructure Plan
       ↓
Security Policy Check
       ↓
Cost Review
       ↓
Human Approval
       ↓
Apply
       ↓
Infrastructure Verification
```

### ✅ 13. 중요한 차이

애플리케이션 배포는 새로운 Build Artifact를 서버에 전달하는 작업인 경우가 많다.

반면 Terraform Apply는 AWS 자원의 생성·수정·삭제를 직접 수행할 수 있다.

### ✅ 14. 따라서

Infrastructure Pipeline은 일반적인 Application Pipeline보다 변경 영향 범위를 엄격하게 관리해야 할 수 있다.

### ✅ 15. 중요한 원칙

**Infrastructure CI/CD에서는 코드의 문법 검증뿐 아니라 실제 AWS에서 무엇이 변경될 것인지 확인해야 한다.**

## 3. GitOps란?

### ✅ 16. 정의

GitOps는 선언적으로 정의한 시스템의 목표 상태를 버전 관리하고, 실제 시스템을 해당 상태와 지속적으로 일치시키는 운영 원칙이다.

### ✅ 17. 핵심 구조

```text
Git Repository
       ↓
Desired State
       ↓
GitOps Agent
       ↓
Actual Infrastructure
       ↓
State Comparison
       ↓
Reconciliation
```

### ✅ 18. GitOps의 주요 원칙

OpenGitOps는 다음 네 가지 원칙을 제시한다.

```text
Declarative

Versioned and Immutable

Pulled Automatically

Continuously Reconciled
```

### ✅ 19. Declarative

인프라가 어떤 상태여야 하는지 선언적으로 정의한다.

### ✅ 20. Versioned and Immutable

목표 상태는 변경 이력을 확인할 수 있는 버전 관리 체계에 저장한다.

### ✅ 21. Pulled Automatically

Agent가 목표 상태를 자동으로 가져온다.

### ✅ 22. Continuously Reconciled

Agent가 실제 상태와 목표 상태를 비교하고 차이를 조정한다.

### ✅ 23. 중요한 구분

GitHub Actions에서 Terraform을 실행한다는 사실만으로 위 네 가지 원칙을 모두 충족하는 것은 아니다.

### ✅ 24. 중요한 원칙

**Git을 활용한 Infrastructure CI/CD와 엄밀한 의미의 GitOps를 구분해야 한다.**

## 4. Git-based CI/CD와 GitOps

### ✅ 25. Git-based Infrastructure CI/CD

```text
Pull Request
       ↓
Terraform Plan
       ↓
Approval
       ↓
Terraform Apply
```

개발자가 승인한 Workflow가 AWS 인프라를 변경한다.

### ✅ 26. GitOps

```text
Desired State in Git
       ↓
Reconciliation Controller
       ↓
Actual State Observation
       ↓
Difference Detection
       ↓
Controlled Reconciliation
```

### ✅ 27. 차이

| 항목 | Git-based IaC CI/CD | 엄밀한 GitOps |
|---|---|---|
| 구성 저장 | Git | 버전 관리된 선언적 목표 상태 |
| 변경 실행 | Workflow가 수행 | Agent가 목표 상태를 가져와 조정 |
| 실행 방식 | 주로 Push-based | Pull-based |
| 지속적인 상태 조정 | 선택적 | 핵심 원칙 |
| Terraform 활용 | 가능 | 별도 Controller 등과 함께 활용 가능 |

### ✅ 28. 현재 추천

처음부터 상시 Reconciliation Controller를 도입할 필요는 없다.

### ✅ 29. 현실적인 시작점

```text
Git-controlled Terraform

+

Trusted Plan

+

Manual Approval

+

Controlled Apply

+

Scheduled Drift Detection
```

### ✅ 30. 중요한 원칙

**현재 1인 개발 환경에서는 복잡한 GitOps 플랫폼보다 안전한 Git 기반 Terraform 변경 관리 체계를 먼저 구축하는 것이 적절하다.**

## 5. Push-based와 Pull-based

### ✅ 31. Push-based

중앙 Pipeline이 대상 시스템에 접근해 변경을 실행한다.

```text
GitHub Actions
       ↓
AWS AssumeRole
       ↓
Terraform Apply
       ↓
AWS Resources
```

### ✅ 32. Pull-based

대상 환경의 Agent가 승인된 목표 상태를 가져와 적용한다.

```text
Desired State Repository
       ↑
Reconciliation Agent
       ↓
Target Infrastructure
```

### ✅ 33. Push-based의 장점

기존 GitHub Actions와 Terraform을 활용하기 쉽다.

### ✅ 34. Push-based의 주의점

CI Pipeline이 AWS 변경 권한을 가지므로 GitHub Workflow와 OIDC 권한 설정이 중요하다.

### ✅ 35. Pull-based의 장점

대상 환경에서 변경 적용 주체를 제한하는 방식으로 구성할 수 있다.

### ✅ 36. Pull-based의 비용

별도 Controller·운영 권한·Agent 장애 복구·버전 관리가 필요하다.

### ✅ 37. 중요한 원칙

**Push-based가 무조건 위험하고 Pull-based가 무조건 안전한 것은 아니다. 실제 인증·승인·권한·복구 구조를 기준으로 판단한다.**

---

## 6. Git을 Source of Truth로 관리하기

### ✅ 38. Source of Truth

인프라의 의도된 목표 상태를 판단할 때 기준으로 사용하는 정보다.

### ✅ 39. 목표 구성

```text
Git Repository
       ↓
Reviewed Terraform Configuration
       ↓
Approved Infrastructure Definition
```

### ✅ 40. 하지만 Git의 최신 main이 곧 운영 상태일까?

반드시 그렇지는 않다.

### ✅ 41. 실제 상황

Terraform 코드가 main에 Merge됐다.

그러나 아직 Production Apply는 진행되지 않았다.

### ✅ 42. 상태 비교

```text
Main Branch:

새로운 인프라 설정
```

```text
Production AWS:

기존 인프라 설정
```

### ✅ 43. 필요한 개념

**Desired Configuration Commit과 Last Applied Commit을 구분해야 한다.**

### ✅ 44. 중요한 원칙

**Git의 최신 코드와 실제 운영에 반영된 코드가 항상 동일하다고 가정하지 않는다.**

## 7. Desired Commit과 Applied Commit

### ✅ 45. Desired Commit

앞으로 적용하려는 Terraform Configuration의 Git Commit이다.

### ✅ 46. Applied Commit

실제 운영 인프라에 마지막으로 성공적으로 적용된 것으로 기록된 Commit이다.

### ✅ 47. 예시

```text
Desired Commit:

commit-B
```

```text
Last Applied Commit:

commit-A
```

### ✅ 48. 의미

새로운 인프라 변경이 준비됐지만 운영 환경에는 아직 반영되지 않았을 수 있다.

### ✅ 49. 필요한 정보

```text
Configuration Commit

Plan ID

State Target

Approval Status

Apply Result

Verification Result
```

### ✅ 50. 중요한 점

Apply 성공 이후에도 실제 서비스 검증에 실패할 수 있다.

### ✅ 51. 따라서

```text
APPLIED

≠

PRODUCTION_VERIFIED
```

### ✅ 52. 중요한 원칙

**인프라 목표 버전과 실제 적용 버전, 서비스 검증 완료 버전을 분리해서 기록한다.**

## 8. 전체 Infrastructure Delivery Pipeline

### ✅ 53. 권장 구조

```text
Terraform Git Change
       ↓
Pull Request
       ↓
Static Validation
       ↓
Trusted Plan
       ↓
Plan Summary
       ↓
Policy Guard
       ↓
Cost / Security Review
       ↓
Approval
       ↓
Controlled Apply
       ↓
Post-apply Plan
       ↓
Application Smoke Test
       ↓
Deployment Evidence
```

### ✅ 54. 주요 단계

| 단계 | 목적 |
|---|---|
| Static Validation | 코드와 구성의 기본 검증 |
| Trusted Plan | AWS에 적용될 변경 예측 |
| Policy Gate | 위험한 변경 차단 |
| Approval | 실제 변경 승인 |
| Apply | 인프라 변경 실행 |
| Verification | 실제 시스템 동작 확인 |
| Reconciliation | 목표 상태와 실제 상태 차이 조사 |

### ✅ 55. 가장 중요한 구분

Pipeline 단계가 많아졌다는 사실보다 각 단계가 실제로 검증하는 조건이 무엇인지 중요하다.

### ✅ 56. 중요한 원칙

**각 Gate가 무엇을 보장하고 무엇을 보장하지 않는지 명확하게 정의한다.**

## 9. Terraform Static Validation

### ✅ 57. 가장 먼저 도입할 단계

AWS Write 권한 없이 Terraform 코드를 검증한다.

### ✅ 58. 기본 명령어

```bash
terraform fmt -check -recursive
```

```bash
terraform init \
  -backend=false \
  -lockfile=readonly \
  -input=false
```

```bash
terraform validate
```

### ✅ 59. terraform fmt

Terraform 파일의 형식이 올바르게 정리돼 있는지 확인한다.

### ✅ 60. terraform init -backend=false

Remote Backend를 초기화하지 않고 Provider와 Module 등 검증에 필요한 구성 요소를 준비할 수 있다.

### ✅ 61. terraform validate

Terraform Configuration의 구문과 일부 구조적인 일관성을 검증한다.

### ✅ 62. 중요한 한계

다음 문제까지 자동으로 확인하지는 못한다.

```text
실제 AWS 자원 존재 여부

Production Resource Replacement

RDS Downtime

IAM 권한 과다

AWS 비용 증가
```

### ✅ 63. 중요한 원칙

**Static Validation이 성공했다고 실제 Infrastructure Plan이 안전하다는 의미는 아니다.**

## 10. Pull Request 보안 경계

### ✅ 64. Terraform PR의 특징

PR에는 단순 설정값뿐 아니라 다음 내용이 포함될 수 있다.

```text
Terraform Configuration

Module Source

Provider Version

External Data Source

Workflow Script

Policy Script
```

### ✅ 65. 위험한 상황

검증되지 않은 PR 코드에 Production AWS Credential을 제공한다.

### ✅ 66. 왜 위험할까?

Terraform Provider와 외부 실행 스크립트는 실행 가능한 코드일 수 있다.

따라서 단순히 AWS 조회만 허용하더라도 민감한 인프라 정보와 State에 접근할 위험이 있다.

### ✅ 67. 권장 구조

```text
Untrusted Pull Request

↓

Credential-free Static Validation
```

### ✅ 68. 신뢰할 수 있는 코드

```text
Protected Branch

↓

Restricted AWS Plan
```

### ✅ 69. 금지할 패턴

신뢰되지 않은 PR을 `pull_request_target`과 높은 AWS 권한으로 실행하는 구조다.

### ✅ 70. 중요한 원칙

**PR 단계에서는 실행할 코드의 신뢰 수준과 AWS 권한을 분리해야 한다.**

## 11. PR Plan과 실제 Apply Plan

### ✅ 71. PR에서 실행하는 Plan

개발자가 변경 영향을 검토할 수 있도록 미리 계산한 Plan이다.

### ✅ 72. 그러나

PR이 Merge되면 Git Commit SHA가 달라질 수 있다.

### ✅ 73. 추가 변화

Merge가 완료될 때까지 다른 Terraform 변경이 적용됐을 수 있다.

### ✅ 74. 따라서

PR 단계의 Plan을 운영 Apply의 최종 근거로 그대로 사용할 수 있다고 가정하면 안 된다.

### ✅ 75. 권장

```text
Pull Request:

Preliminary Validation
```

```text
Protected Main:

Authoritative Plan
```

### ✅ 76. 중요한 원칙

**최종 Apply는 실제 승인된 Configuration Commit과 대상 State를 기준으로 생성한 Plan에 연결해야 한다.**

## 12. Speculative Plan과 Saved Plan

### ✅ 77. Speculative Plan

```bash
terraform plan
```

변경 영향을 검토하기 위한 일반적인 Plan이다.

### ✅ 78. Saved Plan

```bash
terraform plan \
  -out=reviewed.tfplan
```

실제 적용 가능한 Plan 파일을 저장한다.

### ✅ 79. Saved Plan 적용

```bash
terraform apply reviewed.tfplan
```

### ✅ 80. 중요한 차이

저장된 Plan을 Apply하면 일반적인 대화형 승인 과정을 별도로 거치지 않고 변경이 실행된다.

### ✅ 81. 따라서

Plan 파일을 누가 생성하고 누가 보관하며 누가 실행할 수 있는지 제한해야 한다.

### ✅ 82. 중요한 원칙

**Saved Plan은 단순한 검토 보고서가 아니라 실제 인프라 변경 실행에 사용되는 민감한 Artifact다.**

## 13. Saved Plan의 보안 위험

### ✅ 83. 중요한 사실

Terraform Saved Plan에는 민감한 Variable과 Resource 속성이 포함될 수 있다.

### ✅ 84. 위험한 사용

```text
terraform.tfplan
       ↓
Public GitHub Artifact
```

### ✅ 85. 또 다른 위험

```text
terraform show -json
       ↓
Pull Request Comment
```

### ✅ 86. 권장

```text
Sensitive Plan
       ↓
Restricted Storage
       ↓
Short Retention
       ↓
Approved Execution Context
```

### ✅ 87. 일반 GitHub Artifact의 주의점

일반적인 GitHub Actions Artifact는 Repository 읽기 권한을 가진 사용자가 다운로드할 수 있다.

Private Repository라고 해서 모든 Artifact가 승인된 Apply 담당자에게만 보이는 것은 아니다.

### ✅ 88. 따라서

**실제 AWS State와 Secret이 포함될 수 있는 Raw Plan 파일을 일반 Artifact에 그대로 업로드하지 않는다.**

### ✅ 89. 중요한 원칙

**보안 수준이 확인되지 않은 저장소에 Plan을 전달해야 한다면 원본 대신 안전하게 가공한 변경 요약만 보관한다.**

---

## 14. Plan Promotion이란?

### ✅ 90. 개념

검토·검증한 Terraform Plan을 실제 Apply 단계까지 일관되게 전달하는 운영 방식이다.

### ✅ 91. 기본 구조

```text
Terraform Plan
       ↓
Policy Validation
       ↓
Human Approval
       ↓
Same Plan Artifact
       ↓
Terraform Apply
```

### ✅ 92. 왜 필요할까?

검토한 변경사항과 실제 실행된 변경사항이 달라지는 상황을 줄이기 위해서다.

### ✅ 93. 위험한 구조

```text
Plan A 검토
       ↓
코드 변경
       ↓
Plan B 자동 생성
       ↓
Plan B 무검토 적용
```

### ✅ 94. 중요한 조건

동일한 Plan Artifact를 사용하려면 다음 요소를 확인해야 한다.

```text
Same Configuration Commit

Same Terraform State Target

Same Terraform Version

Compatible Provider Plugins

Plan Artifact Integrity

Approved Execution Context
```

### ✅ 95. 중요한 원칙

**Plan Promotion의 핵심은 실제 실행된 Plan이 검토한 변경사항과 일치한다는 근거를 유지하는 것이다.**

---

## 15. Plan Promotion의 두 가지 운영 방식

### ✅ 96. 방식 A — Saved Plan Promotion

```text
Trusted Plan
       ↓
Secure Plan Storage
       ↓
Approval
       ↓
Verified Plan Retrieval
       ↓
Apply Saved Plan
```

### ✅ 97. 장점

실제 승인한 Saved Plan을 재사용할 수 있다.

### ✅ 98. 단점

Plan 파일의 민감정보 보호와 실행 환경, Artifact 무결성 관리가 필요하다.

### ✅ 99. 방식 B — Re-plan and Re-approve

```text
Initial Plan
       ↓
Review
       ↓
Final Trusted Plan
       ↓
Final Review
       ↓
Apply
```

### ✅ 100. 장점

Saved Plan을 장기간 보관하거나 전달하지 않는 방식으로 구성할 수 있다.

### ✅ 101. 주의점

새롭게 생성한 Plan의 결과를 다시 검토해야 한다.

### ✅ 102. 중요한 원칙

**민감한 Saved Plan을 안전하게 보관할 체계가 없다면 무리하게 Plan Promotion을 구현하지 않고 최종 Plan을 다시 생성해 검토하는 방식을 사용한다.**

---

## 16. Staging Plan을 Production에 사용할 수 있을까?

### ✅ 103. 결론

일반적으로 사용할 수 없다.

### ✅ 104. 이유

Staging과 Production은 다음 정보가 다를 수 있다.

```text
AWS Account

AWS Region

State Backend Key

Resource IDs

Subnet IDs

Security Groups

Instance Types

Domain Names
```

### ✅ 105. 잘못된 구조

```text
Staging Saved Plan
       ↓
Production Apply
```

### ✅ 106. 올바른 구조

```text
Same Reviewed Configuration
       ├── Staging State
       │       ↓
       │   Staging Plan
       │       ↓
       │   Staging Apply
       │
       └── Production State
               ↓
           Production Plan
               ↓
           Production Approval
               ↓
           Production Apply
```

### ✅ 107. 중요한 구분

환경 간에 Promotion할 수 있는 것은 검증된 코드·Module 버전·변경 의도다.

각 환경의 Saved Plan 자체를 공통 Artifact로 사용하는 것은 아니다.

### ✅ 108. 중요한 원칙

**Environment Promotion은 동일한 Terraform Plan 파일을 여러 환경에 실행하는 작업이 아니라 검증된 Infrastructure Configuration을 환경별로 안전하게 적용하는 과정이다.**

## 17. Plan Hash와 Commit SHA

### ✅ 109. Plan Hash

저장된 Plan 파일의 내용으로 계산한 무결성 확인값이다.

### ✅ 110. 생성 예시

```bash
shasum -a 256 reviewed.tfplan
```

### ✅ 111. Git Commit SHA

검토한 Terraform Configuration의 Git 버전을 식별한다.

```bash

```

### ✅ 112. 추가 정보

```text
Terraform Version

Provider Lock File

Environment

State Backend Identity

Plan Creation Time
```

### ✅ 113. 중요한 차이

Git Commit SHA와 Plan Hash는 서로 다른 대상의 식별값이다.

### ✅ 114. 예시

```text

commit-A
```

```text
Plan Hash:

sha256:...
```

### ✅ 115. 중요한 한계

Plan Hash가 일치한다고 해당 Plan이 안전하거나 승인됐다는 사실까지 자동으로 보장되지는 않는다.

### ✅ 116. 필요한 연결

```text
Trusted Producer

Approved Commit

Verified Plan Digest

Approved State Target

Authorized Apply Identity
```

### ✅ 117. 중요한 원칙

**Hash는 파일의 동일성을 확인하는 근거이며 실제 승인과 실행 권한을 대신하지 않는다.**

## 20. 안전한 Plan Summary 생성기

### ✅ 130. 목표

Plan 전체를 GitHub Log나 AI에 노출하지 않고 변경 건수와 위험 유형만 출력한다.

### ✅ 131. 입력

Terraform Plan JSON을 표준 입력으로 전달받는다.

### ✅ 132. 출력

```json
{
  "status": "REVIEW_REQUIRED",
  "create": 1,
  "update": 2,
  "delete": 0,
  "replace": 0
}
```

### ✅ 133. Node.js 예시

```javascript
// infra/scripts/summarize-plan.mjs

import { readFileSync } from 'node:fs';

function fail(reason) {
  console.error(JSON.stringify({
    status: 'INVALID_PLAN',
    reason,
  }));

  process.exit(1);
}

let plan;

try {
  plan = JSON.parse(
    readFileSync(0, 'utf8'),
  );
} catch {
  fail('PLAN_JSON_PARSE_FAILED');
}

if (
  typeof plan?.format_version !== 'string' ||
  !plan.format_version.startsWith('1.')
) {
  fail('UNSUPPORTED_PLAN_FORMAT');
}

if (
  plan.errored === true ||
  plan.complete === false
) {
  fail('INCOMPLETE_PLAN');
}

if (
  plan.resource_changes !== undefined &&
  !Array.isArray(plan.resource_changes)
) {
  fail('INVALID_RESOURCE_CHANGES');
}

const summary = {
  create: 0,
  update: 0,
  delete: 0,
  replace: 0,
  read: 0,
  noop: 0,
  import: 0,
};

const resources =
  plan.resource_changes ?? [];

for (const resource of resources) {
  const actions =
    resource?.change?.actions;

  if (
    !Array.isArray(actions) ||
    actions.length === 0
  ) {
    fail('INVALID_CHANGE_ACTIONS');
  }

  const signature = actions.join(',');

  switch (signature) {
    case 'no-op':
      summary.noop += 1;
      break;

    case 'read':
      summary.read += 1;
      break;

    case 'create':
      summary.create += 1;
      break;

    case 'update':
      summary.update += 1;
      break;

    case 'delete':
      summary.delete += 1;
      break;

    case 'delete,create':
    case 'create,delete':
      summary.replace += 1;
      break;

    default:
      fail('UNSUPPORTED_CHANGE_ACTION');
  }

  if (resource.change.importing) {
    summary.import += 1;
  }
}

const mutatingCount =
  summary.create +
  summary.update +
  summary.delete +
  summary.replace +
  summary.import;

console.log(JSON.stringify({
  status:
    mutatingCount > 0
      ? 'REVIEW_REQUIRED'
      : 'NO_RESOURCE_MUTATIONS',
  ...summary,
}));
```

### ✅ 134. 실행

```bash
terraform show \
  -json reviewed.tfplan \
  | node infra/scripts/summarize-plan.mjs
```

실제 실행 위치에 맞춰 스크립트 경로를 조정해야 한다.

### ✅ 135. 보안상 특징

Resource Value와 실제 Secret을 출력하지 않는다.

### ✅ 136. 중요한 한계

이 코드는 Resource Change 요약 예시다.

`output_changes`나 `resource_drift` 등의 별도 분석까지 완성한 범용 Policy Engine은 아니다.

### ✅ 137. 추가 검증

지원하는 Terraform JSON Format과 정상적인 No-op Plan, Import Plan, Refresh-only Plan을 각각 테스트해야 한다.

### ✅ 138. 중요한 원칙

**AI나 일반 보고서에는 Raw Plan이 아니라 검증된 최소 변경 요약을 제공한다.**

## 21. Policy Gate

### ✅ 139. 단순한 변경 건수만으로 충분할까?

아니다.

### ✅ 140. 예시

```text
CloudWatch Retention 수정:
Update 1건
```

```text
Production RDS Public Access 변경:
Update 1건
```

두 변경 모두 Update 1건이지만 위험도는 다르다.

### ✅ 141. 필요한 정책

```text
Resource Type

Environment

Changed Attribute

Action

Business Criticality

Deletion Protection

Approval Requirement
```

### ✅ 142. 정책 예시

| 변경 | 기본 정책 |
|---|---|
| Staging Log Group 신규 생성 | 일반 검토 |
| Production EC2 Type 변경 | 수동 승인 |
| Production RDS 교체 | 원칙적 차단 |
| Production RDS Public Access 활성화 | 차단 |
| Production S3 Bucket 삭제 | 차단 |
| IAM AdministratorAccess 추가 | 높은 수준의 보안 검토 |

### ✅ 143. 중요한 점

Policy Gate의 PASS는 정의한 정책의 검증이 통과됐다는 의미다.

실제 서비스가 정상 동작한다는 보장은 아니다.

### ✅ 144. 중요한 원칙

**Infrastructure Policy Gate는 변경의 유형과 업무 중요도를 기준으로 위험도를 분류해야 한다.**

## 24. Terraform Static CI 예시

### ✅ 160. 목표

Pull Request에서 위험한 AWS 변경 없이 Terraform 코드를 검증한다.

### ✅ 161. Workflow

```yaml
name: Terraform Static Validation

on:
  pull_request:

permissions:
  contents: read

jobs:
  validate:
    runs-on: ubuntu-latest

    timeout-minutes: 15

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup Terraform
        uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: ${{ vars.TERRAFORM_VERSION }}
          terraform_wrapper: false

      - name: Check Formatting
        run: terraform fmt -check -recursive infra

      - name: Initialize Staging
        working-directory: infra/environments/staging
        run: |
          terraform init \
            -backend=false \
            -lockfile=readonly \
            -input=false

      - name: Validate Staging
        working-directory: infra/environments/staging
        run: terraform validate

      - name: Initialize Production
        working-directory: infra/environments/production
        run: |
          terraform init \
            -backend=false \
            -lockfile=readonly \
            -input=false

      - name: Validate Production
        working-directory: infra/environments/production
        run: terraform validate
```

### ✅ 162. 중요한 전제

실제 저장소에 해당 Root Module들이 있어야 한다.

`TERRAFORM_VERSION`에는 검증된 정확한 Terraform 버전이 설정돼 있어야 한다.

### ✅ 163. Provider Lock File

각 Root Module의 `.terraform.lock.hcl`이 존재하고 해당 Runner에서 검증 가능한 체크섬을 가지고 있어야 한다.

### ✅ 164. Action Version

위 Major Tag는 설명용이다.

실제 운영에서는 신뢰할 수 있는 Release의 전체 Commit SHA 고정을 검토한다.

### ✅ 165. 보안 조건

이 Workflow에는 AWS Credential이나 Production Secret을 제공하지 않는다.

### ✅ 166. 중요한 원칙

**Terraform Static CI는 처음부터 운영 인프라 변경과 완전히 분리된 상태로 도입한다.**

---

## 25. PR Path Filter의 함정

### ✅ 167. 비용 절감 목적으로

Terraform 파일이 변경됐을 때만 Workflow를 실행하고 싶을 수 있다.

### ✅ 168. 예시

```yaml
on:
  pull_request:
    paths:
      - "infra/**"
```

### ✅ 169. 문제

Required Check로 등록한 Workflow가 Path Filter 때문에 실행되지 않으면 PR Merge 조건에 영향을 줄 수 있다.

### ✅ 170. 또 다른 위험

실제 Terraform 검사에 영향을 주는 공통 Script나 Workflow 파일이 필터 대상에서 빠질 수 있다.

### ✅ 171. 현재 추천

필수 승인 Gate 자체는 항상 실행되도록 구성한다.

필요하다면 내부 Job에서 변경 범위를 계산해 불필요한 작업만 제한한다.

### ✅ 172. 중요한 원칙

**Path Filter를 잘못 설정해 중요한 인프라 검증이 실행되지 않은 상태로 Merge되는 상황을 방지한다.**

## 26. Trusted Plan Workflow

### ✅ 173. 다음 단계

실제 AWS Resource를 조회해 Terraform Plan을 생성한다.

### ✅ 174. 안전한 시작 방식

자동 Apply 없이 **Plan-only Workflow**를 만든다.

### ✅ 175. 실행 조건

```text
Trusted Branch

Manual Dispatch

Restricted OIDC Role

Read-oriented AWS Access

No Production Apply
```

### ✅ 176. 예시

```yaml
name: Terraform Production Plan

on:
  workflow_dispatch:

permissions:
  contents: read
  id-token: write

concurrency:
  group: terraform-production-core
  cancel-in-progress: false
  queue: max

jobs:
  plan:
    if: github.ref == 'refs/heads/main'

    runs-on: ubuntu-latest

    timeout-minutes: 20

    steps:
      - name: Checkout Approved Branch
        uses: actions/checkout@v4
        with:
          persist-credentials: false

      - name: Setup Terraform
        uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: ${{ vars.TERRAFORM_VERSION }}
          terraform_wrapper: false

      - name: Configure AWS
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ vars.TERRAFORM_PLAN_ROLE_ARN }}
          aws-region: ap-northeast-2
          role-session-name: terraform-plan

      - name: Confirm AWS Account
        run: |
          account_id="$(aws sts get-caller-identity \
            --query Account \
            --output text)"

          test "$account_id" = \
            "${{ vars.EXPECTED_AWS_ACCOUNT_ID }}"

      - name: Initialize Terraform
        working-directory: infra/environments/production
        run: |
          terraform init \
            -input=false \
            -lockfile=readonly \
            -lock-timeout=60s

      - name: Create Plan
        working-directory: infra/environments/production
        run: |
          terraform plan \
            -input=false \
            -lock-timeout=60s \
            -out="$RUNNER_TEMP/production.tfplan"

      - name: Safe Plan Summary
        run: |
          terraform \
            -chdir=infra/environments/production \
            show -json \
            "$RUNNER_TEMP/production.tfplan" \
          | node infra/scripts/summarize-plan.mjs

      - name: Record Commit
        run: |
          echo "Configuration commit:"
          git rev-parse HEAD
```

### ✅ 177. 중요한 전제

위 예시는 다음 조건을 이미 충족했다고 가정한다.

- 승인된 AWS OIDC Provider
- 제한된 Plan IAM Role
- 기존 Terraform Remote Backend
- State Locking
- 검증된 Terraform Version
- 실제 저장소 경로
- 안전한 Plan Summary Script

### ✅ 178. `queue: max`

현재 GitHub Actions의 Concurrency 기능에서 지원되는 대기열 옵션이다.

실제 운영 Repository에서 지원 여부와 Workflow 정책을 확인해야 한다.

### ✅ 179. 중요한 특징

위 Workflow는 Saved Plan을 생성하지만 다른 Job으로 업로드하거나 Apply하지 않는다.

Runner가 종료되면 임시 Plan 파일은 후속 실행에 사용되지 않는다.

### ✅ 180. 중요한 주의

GitHub Actions Log 자체에도 Resource 이름과 설정 정보가 노출될 수 있으므로 Log 접근권한을 제한한다.

### ✅ 181. 중요한 원칙

**첫 Trusted Plan Workflow는 실제 AWS 변경 없이 변경 영향만 조사하는 구조로 구축한다.**

## 28. OIDC Trust Policy

### ✅ 189. Trust Policy

어떤 GitHub Actions 실행이 해당 AWS Role을 Assume할 수 있는지 제한한다.

### ✅ 190. 중요한 조건

```text
Expected Repository

Expected Branch

Expected GitHub Environment

Expected Audience

Expected Subject Claim
```

### ✅ 191. GitHub OIDC Subject

Repository 생성 시기와 설정에 따라 기존 Subject 형식 또는 Immutable Subject 형식이 사용될 수 있다.

### ✅ 192. 예시 — 기존 형식

```text
repo:organization/repository:ref:refs/heads/main
```

### ✅ 193. 예시 — Immutable 형식

```text

```

### ✅ 194. 중요한 사실

2026년 7월 15일 이후 생성된 Repository 등에는 Immutable Subject 형식이 적용될 수 있다.

### ✅ 195. 중요한 주의

GitHub Environment를 사용하는 Job에서는 Subject Claim에 Environment 정보가 포함되는 형식이 적용될 수 있다.

### ✅ 196. 따라서

인터넷에서 찾은 예시 문자열을 그대로 AWS Trust Policy에 붙여 넣지 않는다.

### ✅ 197. 중요한 원칙

**OIDC Trust Policy는 실제 GitHub Repository의 Token Claim 형식과 정확하게 일치하도록 작성해야 한다.**

### ✅ 205. 중요한 원칙

**GitHub Environment Approval이 존재한다고 가정하지 말고 실제 Repository에서 사용할 수 있는 보호 기능을 확인한 뒤 설계한다.**

## 31. State Locking과 Workflow Concurrency

### ✅ 214. 동일한 문제일까?

아니다.

### ✅ 215. State Locking

Terraform이 사용하는 State에 대한 동시 수정 충돌을 줄이기 위한 기능이다.

### ✅ 216. Workflow Concurrency

GitHub Actions Workflow 또는 Job이 동시에 실행되는 것을 제한하는 기능이다.

### ✅ 217. 권장 구조

```text
Workflow Concurrency
       ↓
Terraform State Locking
       ↓
Infrastructure Change
```

### ✅ 218. 중요한 차이

GitHub Workflow Concurrency는 동일한 GitHub Repository 내부의 실행을 제한한다.

### ✅ 219. 하지만

개발자의 MacBook에서 실행하는 Terraform이나 다른 Repository의 Pipeline까지 자동으로 제한하지는 않는다.

### ✅ 220. 따라서

State Locking은 별도로 필요하다.

### ✅ 221. 중요한 원칙

**Workflow Concurrency와 Terraform State Locking을 중복된 기능이 아니라 서로 다른 보호 계층으로 사용한다.**

## 32. Concurrency Group 설계

### ✅ 222. 예시

```yaml
concurrency:
  group: terraform-production-core
  cancel-in-progress: false
  queue: max
```

### ✅ 223. 목적

동일한 Production Core 인프라에 대한 변경을 동시에 실행하지 않도록 한다.

### ✅ 224. 주의

모든 Terraform 환경이 같은 Group을 사용하면 서로 독립적인 환경까지 불필요하게 대기할 수 있다.

### ✅ 225. 반대로

동일한 State를 변경하는 Workflow마다 다른 Group을 사용하면 Workflow 수준의 직렬화가 이루어지지 않을 수 있다.

### ✅ 226. 추천 식별 방식

```text
terraform-staging-core

terraform-production-core

terraform-production-frontend
```

실제 State 경계와 변경 의존성을 기준으로 설계한다.

### ✅ 227. 중요한 점

Apply 중인 Terraform Job을 새로운 실행 때문에 임의로 Cancel하지 않는다.

### ✅ 228. 중요한 원칙

**Infrastructure Concurrency Group은 Workflow 이름이 아니라 실제 State와 변경 범위를 중심으로 설계한다.**

---

## 33. Pending Workflow의 취소 문제

### ✅ 229. GitHub Actions의 기본 동작

동일한 Concurrency Group에 새 작업이 들어오면 기존 Pending 작업이 교체될 수 있다.

### ✅ 230. 따라서

`cancel-in-progress: false`만 설정했다고 모든 대기 작업이 순서대로 보존되는 것은 아니다.

### ✅ 231. `queue: max`

현재 지원되는 기능을 통해 복수의 대기 작업을 큐에 보관하도록 설정할 수 있다.

### ✅ 232. 하지만 중요한 주의

대기열에서 오래 기다린 Plan은 실제 실행 시점에 오래된 계획이 될 수 있다.

### ✅ 233. 따라서

```text
Pending Work
       ↓
Current Commit Validation
       ↓
Current State Validation
       ↓
Plan Freshness Verification
       ↓
Final Approval
```

이 필요하다.

### ✅ 234. 중요한 원칙

**Infrastructure Queue는 실행 순서를 관리하지만 오래된 변경 계획의 안전성을 자동으로 보장하지는 않는다.**

## 34. Stale Plan

### ✅ 235. 정의

Plan이 생성된 이후 State 또는 관련 실행 환경이 변경돼 기존 Plan을 그대로 적용하기 어려워진 상태다.

### ✅ 236. 예시

```text
10:00

Plan A 생성
```

```text
10:05

다른 Infrastructure Apply
```

```text
10:10

Plan A Apply 시도
```

### ✅ 237. 발생 가능한 문제

Terraform이 Plan을 Stale 상태로 판단해 실행을 거부할 수 있다.

### ✅ 238. 중요한 차이

Terraform이 정상적으로 Apply를 거부하는 것은 안전한 동작일 수 있다.

### ✅ 239. 잘못된 대응

State Lock을 강제로 해제하거나 검토 없이 새 Plan을 생성해 Apply하는 것이다.

### ✅ 240. 올바른 대응

```text
Stale Plan
       ↓
Actual State 확인
       ↓
New Plan
       ↓
Policy Revalidation
       ↓
New Approval
```

### ✅ 241. 중요한 원칙

**Stale Plan을 실행하려고 우회하지 말고 현재 AWS 상태를 기준으로 새로운 변경 계획을 다시 검토한다.**

## 35. Plan Time과 Apply Time의 차이

### ✅ 242. Plan을 생성한 시점

AWS 인프라가 특정 상태였다.

### ✅ 243. Apply 시점

시간이 지나 외부 서비스나 다른 운영 작업에 의해 상태가 달라졌을 수 있다.

### ✅ 244. 중요한 한계

State가 변경되지 않았다고 실제 AWS 환경의 모든 외부 변화가 없었다는 의미는 아니다.

### ✅ 245. 예시

다른 운영자가 Console에서 Security Group을 변경했다.

하지만 Terraform State에는 아직 반영되지 않았을 수 있다.

### ✅ 246. 따라서

중요한 Production 변경에서는 다음 항목을 확인한다.

```text
Recent Console Changes

CloudTrail Events

Other Terraform Runs

Pending Infrastructure Changes

Current Service Health
```

### ✅ 247. 중요한 원칙

**Saved Plan의 동일성뿐 아니라 실제 Apply 시점의 운영 환경과 외부 변경 가능성도 고려해야 한다.**

연결을 확인하기 위해 RDS를 Public으로 전환하거나 모든 IP를 허용하는 규칙을 추가하지 않는다.

### ✅ 278. 중요한 원칙

**네트워크 변경의 성공 기준은 Security Group Rule이 생성됐다는 사실이 아니라 필요한 연결은 유지되고 불필요한 접근은 제한되는 것이다.**

---

## 41. 실제 사례 — RDS 변경

### ✅ 279. 상황

RDS Instance Class를 변경하려고 한다.

### ✅ 280. 중요한 점

RDS 변경은 DB 연결 중단이나 성능 변화가 발생할 수 있는 중요한 작업이다.

### ✅ 281. 필요한 검토

```text
Current DB Metrics

Instance Compatibility

Expected Downtime

Maintenance Window

Existing Connections

Backup

Rollback Feasibility
```

### ✅ 282. 위험한 구조

Terraform Plan에서 RDS 변경이 감지되면 자동 승인하는 방식이다.

### ✅ 283. 권장

RDS의 중요 변경은 별도 승인과 유지보수 절차로 관리한다.

### ✅ 284. 중요한 구분

Terraform Apply 실패 이후 기존 RDS가 항상 원래 상태로 돌아오는 것은 아니다.

### ✅ 285. 중요한 원칙

**RDS Infrastructure 변경은 일반적인 CloudWatch 설정 변경보다 높은 승인과 복구 검증 기준을 적용한다.**

---

## 42. Infrastructure Reconciliation

### ✅ 286. Reconciliation

시스템의 목표 상태와 실제 상태를 비교하고 차이를 해소하는 과정이다.

### ✅ 287. 기본 구조

```text
Desired Configuration
       ↓
Actual AWS State
       ↓
Difference Detection
       ↓
Decision
       ↓
Controlled Change
       ↓
Verification
```

### ✅ 288. 예시

Git에는 CloudWatch Log Retention이 30일로 기록돼 있다.

실제 AWS에서는 7일로 변경됐다.

### ✅ 289. 가능한 대응 A

Git에서 정의한 30일을 유지하도록 실제 AWS 구성을 복구한다.

### ✅ 290. 가능한 대응 B

7일 변경이 공식 승인된 정책이라면 Git의 목표 상태를 7일로 수정한다.

### ✅ 291. 중요한 점

Reconciliation이 반드시 기존 코드로 실제 AWS를 되돌리는 작업만 의미하는 것은 아니다.

### ✅ 292. 중요한 원칙

**차이가 발생한 이유와 승인된 목표 상태를 확인한 뒤 실제 인프라 또는 Configuration을 조정한다.**

---

## 43. Reconciliation Mode

### ✅ 293. 권장 운영 단계

```text
Detect Only

↓

Report and Review

↓

Approved Reconciliation

↓

Automated Reconciliation
```

### ✅ 294. Detect Only

실제 인프라 변경 없이 차이를 탐지한다.

### ✅ 295. Report and Review

Drift 원인과 필요한 대응을 검토한다.

### ✅ 296. Approved Reconciliation

승인된 변경만 적용한다.

### ✅ 297. Automated Reconciliation

사전에 정의한 안전 범위 안에서 자동으로 실제 상태를 목표 상태에 맞춘다.

### ✅ 298. 현재 추천

초기에는 Detect Only와 Report and Review 단계까지만 구현한다.

### ✅ 299. 중요한 원칙

**운영 환경에서 자동 Reconciliation을 도입하기 전에 변경 대상과 위험도가 충분히 제한돼 있어야 한다.**

---

## 44. Drift Detection과 Reconciliation의 차이

### ✅ 300. Drift Detection

차이를 발견한다.

### ✅ 301. Reconciliation

차이를 해소한다.

### ✅ 302. 비교

```text
Drift Detection:

Current ≠ Desired
```

```text
Reconciliation:

Current → Approved Desired
```

### ✅ 303. 중요한 차이

Drift Detection이 성공했다고 운영 인프라가 자동으로 정상 상태로 복구된 것은 아니다.

### ✅ 304. 반대로

자동으로 차이를 복구했다고 해당 변경이 업무적으로 올바른 것이라는 보장도 없다.

### ✅ 305. 중요한 원칙

**Drift 발견·변경 승인·실제 복구·서비스 검증을 서로 다른 단계로 기록한다.**

---

## 45. 긴급 AWS Console 변경

### ✅ 306. 실제 상황

운영 장애가 발생해 Terraform Pipeline을 기다릴 여유가 없다.

### ✅ 307. 가능한 대응

승인된 비상 절차에 따라 AWS Console에서 직접 설정을 변경할 수 있다.

### ✅ 308. 중요한 점

Terraform을 사용한다고 모든 Console 변경이 절대적으로 금지되는 것은 아니다.

### ✅ 309. 필요한 기록

```text
Incident ID

Changed Resource

Changed Attribute

Previous Value

New Value

Reason

Operator

Approval

Timestamp
```

### ✅ 310. 이후 절차

```text
Emergency Console Change
       ↓
Service Recovery
       ↓
Change Evidence
       ↓
Terraform Drift Review
       ↓
Configuration Update or Restore
       ↓
Normal Plan
       ↓
Reconciliation
```

### ✅ 311. 중요한 원칙

**긴급 수동 변경은 허용할 수 있지만 정상 상태로 복귀한 뒤 Terraform Configuration과 실제 AWS 상태의 불일치를 해소해야 한다.**

---

## 46. Break-glass Access

### ✅ 312. 개념

정상적인 운영 절차를 사용할 수 없는 긴급 상황에서 제한적으로 사용하는 비상 접근 권한이다.

### ✅ 313. 활용 상황

```text
Production Incident

Critical Access Recovery

Infrastructure Pipeline Failure

Emergency Network Correction
```

### ✅ 314. 중요한 조건

```text
Explicit Authorization

Short-lived Access

MFA

Audit Logging

Post-incident Review
```

### ✅ 315. 위험한 방식

비상 권한을 평소 개발과 배포 작업에 계속 사용하는 것이다.

### ✅ 316. 현재 추천

일반 작업에서는 제한된 IAM Identity Center Permission Set 또는 OIDC Role을 사용한다.

### ✅ 317. 중요한 원칙

**Break-glass 권한은 일상적인 운영 편의를 위한 권한이 아니라 긴급 복구를 위한 제한적인 접근 수단이다.**

---

## 47. Terraform Apply 부분 실패

### ✅ 318. Terraform Apply가 실패하면

모든 Resource 변경이 자동 Rollback되는 것은 아니다.

### ✅ 319. 예시

```text
IAM Policy Update:
SUCCESS

EC2 Security Group Update:
SUCCESS

CloudFront Update:
FAILED
```

### ✅ 320. 결과

일부 AWS 자원은 이미 변경됐을 수 있다.

### ✅ 321. 올바른 대응

```text
Apply Failure
       ↓
Stop Further Changes
       ↓
Actual Resource Inventory
       ↓
State Verification
       ↓
Customer Impact Check
       ↓
New Plan
       ↓
Recovery Decision
```

### ✅ 322. 금지할 대응

```text
실패 원인 확인 없이
terraform apply 반복
```

### ✅ 323. 중요한 원칙

**Infrastructure Pipeline 실패는 코드 테스트 실패와 달리 실제 운영 자원의 일부가 이미 변경됐을 가능성을 포함한다.**

## 48. Infrastructure Rollback

### ✅ 324. Git Revert

이전 Terraform Configuration으로 코드를 되돌리는 작업이다.

### ✅ 325. 하지만

Git Revert가 실제 AWS 리소스를 원래 상태로 자동 복구한다는 뜻은 아니다.

### ✅ 326. 예시

RDS Storage를 증가시켰다.

이전 코드로 되돌려도 Storage를 단순히 줄일 수 없는 경우가 있다.

### ✅ 327. 또 다른 예시

AWS Resource를 삭제했다.

이전 Terraform 코드가 있다고 삭제된 Resource의 데이터까지 원래대로 복원할 수 있는 것은 아니다.

### ✅ 328. Rollback 후보

```text
Configuration Revert

Forward Fix

Resource Restore

Backup Restore

Traffic Cutover

Replacement Infrastructure
```

### ✅ 329. 중요한 원칙

**인프라 Rollback은 코드 변경뿐 아니라 실제 자원의 가역성과 데이터 복구 가능성을 확인해야 한다.**

## 49. Post-apply Verification

### ✅ 330. Apply 성공 후

실제 고객 서비스가 정상인지 확인한다.

### ✅ 331. 검증 대상

```text
Customer Frontend

Admin Frontend

Backend Health

RDS Connectivity

SSM Parameter Access

CloudFront Distribution

CloudWatch Metrics
```

### ✅ 332. 중요한 구분

Terraform Apply가 성공해도 실제 고객 신청 기능이 실패할 수 있다.

### ✅ 333. 예시

Security Group 변경은 성공했다.

하지만 Backend에서 PostgreSQL 연결이 되지 않는다.

### ✅ 334. 따라서

```text
Terraform Apply:
SUCCESS
```

```text
Business Verification:
FAILED
```

로 별도 기록한다.

### ✅ 335. 중요한 원칙

**Infrastructure Change의 최종 완료 기준에는 Terraform State뿐 아니라 실제 업무 기능의 정상 동작 검증이 포함돼야 한다.**

## 50. 안전한 Production Smoke Test

### ✅ 336. 고객 홈페이지

공개 페이지가 정상적으로 로드되는지 확인한다.

### ✅ 337. 관리자 홈페이지

관리자 로그인 화면 또는 승인된 테스트 계정에서 기본 동작을 확인한다.

### ✅ 338. Backend

실제 운영 환경에서 허용된 Health Check를 확인한다.

### ✅ 339. Database

애플리케이션의 실제 DB 연결 상태를 안전한 방법으로 확인한다.

### ✅ 340. 중요한 주의

실제 고객의 신청서 제출을 자동으로 반복하는 방식으로 운영 Smoke Test를 구성하지 않는다.

### ✅ 341. 외부 Provider

실제 카카오톡 알림이나 주문 생성 등을 무단 실행하지 않는다.

### ✅ 342. 권장

```text
Production:

Read-only / Non-destructive Smoke
```

```text
Staging:

Synthetic Application Flow
```

### ✅ 343. 중요한 원칙

**Post-apply Verification은 실제 고객 서비스에 영향을 주지 않는 검증부터 실행한다.**

## 52. Infrastructure Change Audit

### ✅ 349. 왜 필요한가?

몇 달 후 인프라 장애가 발생했을 때 어떤 변경이 언제 수행됐는지 확인할 수 있어야 한다.

### ✅ 350. 추적 정보

```text
Git Commit

Terraform Plan

Policy Result

Approval

AWS Actor

Apply Result

CloudTrail Event

Post-apply Verification
```

### ✅ 351. Git 기록

어떤 Configuration이 변경됐는지 확인한다.

### ✅ 352. GitHub Actions

어떤 Workflow가 실행됐는지 확인한다.

### ✅ 353. AWS CloudTrail

어떤 AWS API 변경 작업이 수행됐는지 조사할 수 있다.

### ✅ 354. 중요한 차이

CloudTrail만으로 Terraform Configuration의 전체 변경 이유나 승인 근거를 자동으로 알 수 있는 것은 아니다.

### ✅ 355. 중요한 원칙

**Git·CI/CD·Terraform·CloudTrail 기록을 연결해야 인프라 변경의 의도와 실제 실행을 추적할 수 있다.**

## 54. Change Failure Rate

### ✅ 361. Infrastructure Change에도 품질 지표가 필요하다

### ✅ 362. 후보


### ✅ 364. 예시

### ✅ 367. 중요한 조건

변경 건수의 분모와 Incident 연결 기준을 명확하게 정의해야 한다.

### ✅ 368. 중요한 원칙

**Infrastructure Pipeline의 검증 실패와 실제 운영 변경 실패를 구분해야 자동화 품질을 올바르게 평가할 수 있다.**

## 📌 요약

1117에서는 Terraform으로 기존 AWS 인프라를 안전하게 관리하고 Configuration Drift를 탐지하는 방법을 다뤘다.

```text
Existing AWS Infrastructure
       ↓
Terraform Import
       ↓
State Management
       ↓
Zero-change Plan
       ↓
Infrastructure as Code
```

1118에서는 이를 GitHub Actions와 연결해 승인 기반 Infrastructure Delivery 체계로 확장했다.

```text
Infrastructure Change
       ↓
Git Pull Request
       ↓
Static Validation
       ↓
Trusted Terraform Plan
       ↓
Plan Summary
       ↓
Policy Guard
       ↓
Cost / Security Review
       ↓
Human Approval
       ↓
Controlled Apply
       ↓
Production Verification
       ↓
Drift Detection
       ↓
Reconciliation
       ↓
Change Audit
```

이번 편에서 가장 중요한 원칙은 다음과 같다.

**첫 번째 — Terraform 자동화와 GitOps는 같은 개념이 아니다.**

GitHub Actions에서 Terraform Plan과 Apply를 실행하는 것은 Git 기반 Infrastructure CI/CD다.

엄밀한 GitOps는 선언적 목표 상태와 자동 Pull, 지속적인 Reconciliation을 포함한다.

**두 번째 — 검토한 Plan과 실제 적용한 Plan을 연결한다.**

```text
Approved Commit

+

Verified Plan

+

Correct State

+

Authorized Apply
```

구조가 필요하다.

**세 번째 — Saved Plan은 민감한 실행 Artifact다.**

Plan에 실제 Secret과 Resource 정보가 포함될 수 있다.

일반 GitHub Artifact나 Notion에 무분별하게 저장하지 않는다.

**네 번째 — Staging과 Production의 Plan은 분리한다.**

Staging에서 검증한 코드와 변경 의도는 Production에 적용할 수 있다.

그러나 Staging Saved Plan 파일을 Production에 그대로 적용할 수 있는 것은 아니다.

**다섯 번째 — GitHub Actions와 Terraform State Locking을 함께 활용한다.**

Workflow Concurrency는 GitHub 실행을 제한한다.

Terraform State Locking은 State에 대한 동시 작업을 제한한다.

서로 다른 보호 계층이다.

**여섯 번째 — OIDC와 IAM 권한을 분리한다.**

```text
Plan Role

Apply Role

Application Deploy Role
```

은 책임이 다르다.

**일곱 번째 — Apply 성공과 운영 검증 성공을 구분한다.**

Terraform Apply가 성공해도 Backend·RDS·CloudFront에 문제가 발생할 수 있다.

실제 고객 서비스 검증이 필요하다.

**여덟 번째 — Drift 발견 이후 자동으로 원래 설정을 복구하지 않는다.**

승인된 긴급 변경이나 다른 운영 시스템에서 의도적으로 수정한 설정일 수 있다.

실제 변경 이유와 목표 상태를 확인해야 한다.

**아홉 번째 — Infrastructure Rollback은 Git Revert와 다르다.**

실제 AWS 자원의 변경 중에는 이전 상태로 쉽게 되돌릴 수 없는 작업도 존재한다.

**열 번째 — AI는 Infrastructure Review에 활용한다.**

실제 변경사항을 분석하고 위험 후보를 정리하는 데 AI를 사용할 수 있다.

하지만 AWS 변경의 승인과 실제 Apply 권한은 분리해야 한다.

현재 투게더몰에서 가장 현실적인 실행 순서는 다음과 같다.

```text
1. Terraform Static Validation 구축

2. 실제 Terraform State 보호 확인

3. GitHub Actions 권한 검토

4. Terraform Plan Summary Script 작성

5. Infrastructure Policy Unit Test

6. Trusted Plan-only Workflow 구축

7. AWS OIDC / Plan Role 검증

8. Infrastructure Change Manifest

9. Manual Approved Apply 절차

10. Post-apply Smoke Test

11. Scheduled Drift Detection

12. Production Change Audit

13. Staging / Production Promotion 개선

14. Secure Plan Promotion 검토

15. 필요하면 Advanced GitOps 도입
```

현재와 같은 1인 개발 환경에서는 인프라를 완전 자동으로 변경하는 시스템보다 **위험한 변경을 미리 발견하고 승인된 변경만 정확하게 적용하며 결과를 검증하는 구조**가 더 중요하다.

특히 LG U+ 사이트 외에 SKT·KT 홈페이지가 추가되면 변경 대상이 많아지므로 Git 기반 인프라 관리의 가치가 커진다.

```text
LGU Infrastructure

SKT Infrastructure

KT Infrastructure

Shared Infrastructure
       ↓
Reviewed Terraform Changes
       ↓
Environment-specific Plans
       ↓
Approved Infrastructure Delivery
```

이 구조를 통해 인프라 변경 이력과 실제 운영 영향 범위를 체계적으로 관리할 수 있다.

최종적으로 기억해야 할 원칙은 다음과 같다.

**좋은 Infrastructure CI/CD는 AWS 자원을 자동으로 빠르게 변경하는 시스템이 아니다. 누가 어떤 인프라를 왜 변경하려는지 검증하고, 승인된 변경만 정확한 환경에 적용하며, 이후 실제 고객 서비스가 정상이라는 사실까지 확인할 수 있는 운영 체계다.**
