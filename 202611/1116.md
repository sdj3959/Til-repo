## 1. 성능을 개선하면 실제 AWS 비용도 줄어들까?

### ✅ 1. 1115와의 연결

1115에서는 CPU Profiling과 Heap Analysis를 이용해 실제 애플리케이션 내부에서 자원을 많이 사용하는 함수와 객체를 분석하는 방법을 다뤘다.

```text
Performance Regression
       ↓
Distributed Trace
       ↓
Runtime Profiling
       ↓
CPU / Memory Bottleneck
       ↓
Code Optimization
       ↓
Re-profiling
```

1116에서는 여기서 한 단계 더 나아간다.

**코드의 성능 개선을 실제 인프라 자원 사용량과 AWS 운영 비용으로 연결하는 방법을 다룬다.**

### ✅ 2. 실제 운영 상황

상품 상세 API의 가격 계산 로직을 최적화했다고 가정한다.

```text
Before:

상품 상세 API p95:
900ms

EC2 CPU:
평균 60%
```

```text
After:

상품 상세 API p95:
400ms

EC2 CPU:
평균 30%
```

위 수치는 설명용 가상 데이터다.

### ✅ 3. 이제 성능은 개선됐다

고객은 더 빠르게 상품 정보를 조회할 수 있다.

서버는 같은 업무를 처리하면서 이전보다 적은 CPU를 사용할 가능성이 있다.

### ✅ 4. 하지만 AWS 비용은?

기존과 동일한 EC2 Instance를 계속 실행하고 있다면 CPU 사용률이 감소했다고 EC2 요금이 자동으로 감소하지는 않는다.

### ✅ 5. 중요한 차이

```text
CPU Usage Reduction

≠

Immediate AWS Cost Reduction
```

### ✅ 6. 그렇다면 최적화의 의미가 없는 것일까?

아니다.

다음과 같은 효과가 발생할 수 있다.

```text

사전예약 트래픽 대응 여유 증가

향후 서버 증설 시점 지연

더 작은 Instance 사용 가능성

장애 발생 위험 감소
```

### ✅ 7. 중요한 관점

비용 절감은 실제 청구액 감소만을 의미하지 않는다.

기존 자원으로 더 많은 업무를 처리하면서 추가적인 인프라 지출을 피하는 것도 중요한 효율성 개선이다.

### ✅ 8. 이번 편의 핵심 질문

**서비스의 성능과 안정성을 유지하면서 실제 고객 신청 및 주문을 처리하는 데 필요한 인프라 비용을 어떻게 측정하고 최적화할 수 있을까?**

## 2. Resource Efficiency란?

### ✅ 11. 정의

Resource Efficiency는 시스템이 사용하는 CPU·메모리·스토리지·네트워크 등의 자원 대비 얼마나 많은 유효한 업무를 처리할 수 있는지 나타내는 개념이다.

### ✅ 12. 예시

두 개의 Backend 구현이 있다고 가정한다.

| 항목 | 구현 A | 구현 B |
|---|---:|---:|
| 처리량 | 100 RPS | 100 RPS |
| CPU 사용률 | 70% | 35% |
| API p95 | 500ms | 300ms |
| 오류율 | 0.1% | 0.1% |

같은 테스트 환경이라는 전제에서 구현 B는 더 적은 CPU를 사용하면서 더 빠른 응답을 제공한다.

### ✅ 13. 의미

구현 B의 Resource Efficiency가 더 높다고 평가할 수 있는 근거가 생긴다.

### ✅ 14. 중요한 조건

비교 대상의 업무 정확성이 같아야 한다.

### ✅ 15. 잘못된 최적화

상품 가격 계산에서 일부 할인 조건을 제거해 CPU 사용량을 줄였다.

하지만 고객에게 표시되는 최종 가격이 달라졌다.

이는 정상적인 Resource Efficiency 개선이라고 할 수 없다.

### ✅ 16. Resource Efficiency 측정 후보

```text
CPU Seconds per Request

Memory Footprint

Database Queries per Operation

Data Transfer per Page View

Storage Growth per Order

Completed Jobs per Instance Hour
```

### ✅ 17. 중요한 원칙

**Resource Efficiency는 처리한 업무의 양뿐 아니라 업무 정확성·응답시간·오류율을 함께 고려해야 한다.**

## 3. Cost-aware Engineering

### ✅ 18. 정의

Cost-aware Engineering은 개발 단계부터 코드 변경과 아키텍처 결정이 운영 비용에 어떤 영향을 주는지 고려하는 개발 방식이다.

### ✅ 19. 일반적인 개발 방식

```text
기능 요구사항
       ↓
기능 구현
       ↓
테스트
       ↓
배포
```

### ✅ 20. Cost-aware Engineering

```text
기능 요구사항
       ↓
업무 정확성 검토
       ↓
성능 영향 검토
       ↓
자원 사용량 검토
       ↓
운영 비용 검토
       ↓
기능 구현
       ↓
검증
       ↓
배포
```

### ✅ 21. 예시 — 고객 유입 추적

상품 상세페이지에서 고객 행동 이벤트를 수집한다.

기존에는 고객 한 명당 평균 5개의 이벤트를 기록했다.

새로운 기능 추가 이후 평균 30개의 이벤트가 생성된다고 가정한다.

### ✅ 22. 발생 가능한 비용

```text
Backend API Requests

PostgreSQL Insert

Database Storage

CloudWatch Logs

Data Transfer

Analytics Aggregation
```

### ✅ 23. 중요한 질문

추가된 25개의 이벤트가 실제 광고 분석이나 고객 경험 개선에 필요한가?

### ✅ 24. 개선 후보

```text
불필요한 이벤트 제거

중복 이벤트 방지

이벤트 배치 전송

필요한 정보만 저장

보관 기간 정의
```

### ✅ 25. 중요한 원칙

**기능을 추가할 때 개발 비용뿐 아니라 해당 기능을 계속 운영하는 데 필요한 자원과 비용을 함께 고려한다.**

## 4. Cloud FinOps란?

### ✅ 26. 정의

FinOps는 클라우드 비용과 사용량에 대한 가시성을 확보하고, 기술·재무·사업 관점에서 클라우드의 가치를 높이기 위한 운영 방식이다.

### ✅ 27. 단순한 비용 절감 활동일까?

아니다.

클라우드 비용이 어디에서 발생하고 어떤 업무에 사용되며, 그 지출이 적절한 사업 가치를 제공하는지 판단하는 과정이다.

### ✅ 28. 대표적인 운영 흐름

```text
Inform

↓

Optimize

↓

Operate
```

### ✅ 29. Inform

현재 어떤 서비스를 얼마나 사용하고 얼마를 지출하는지 파악한다.

### ✅ 30. Optimize

불필요한 비용과 비효율적인 자원 사용을 조사한다.

### ✅ 31. Operate

개선 작업을 검증하고 비용을 지속적으로 관리한다.

### ✅ 32. 투게더몰에 적용하면

```text
AWS 비용 확인
       ↓
EC2 / RDS / S3 / CloudFront 비용 분류
       ↓
고객 신청 및 주문 처리량 확인
       ↓
비효율적인 사용 조사
       ↓
개선 계획
       ↓
성능 및 비용 재검증
```

### ✅ 33. 중요한 점

개발자가 AWS 비용을 줄이기 위해 임의로 필요한 운영 자원을 삭제하는 것은 FinOps가 아니다.

### ✅ 34. 중요한 원칙

**FinOps는 비용·서비스 품질·사업 요구사항 사이에서 합리적인 결정을 반복적으로 수행하는 운영 방식이다.**

## 5. 1인 개발 환경에서의 FinOps

### ✅ 35. 대기업 수준의 FinOps 조직이 필요할까?

아니다.

현재와 같은 1인 개발 환경에서는 작은 관리 체계부터 시작하는 것이 적절하다.

### ✅ 36. 필요한 최소 구성

```text
월별 AWS 비용 보고서

서비스별 비용 구분

예산 초과 알림

자원 사용량 확인

비용 최적화 후보

개선 전후 비용 비교
```

### ✅ 37. 개발자의 역할

AWS 비용이 왜 증가했는지 기술적인 근거를 확인한다.

### ✅ 38. 회사의 역할

```text
운영 예산 결정

신규 서비스 투자 판단

가용성 요구사항 결정

비용 절감 변경 승인
```

### ✅ 39. 중요한 구분

개발자가 비용을 분석하고 최적화 후보를 제안하는 것과 회사의 운영 예산을 독자적으로 결정하는 것은 다른 일이다.

### ✅ 40. 현재 추천

복잡한 FinOps 플랫폼을 직접 개발하기보다 AWS에서 제공하는 비용 관리 도구와 기존 업무 보고서 자동화를 활용한다.

### ✅ 41. 중요한 원칙

**1인 개발 환경의 FinOps는 최소한의 운영 부담으로 비용을 설명하고 필요한 개선을 실행할 수 있어야 한다.**

## 6. AWS 비용의 구성

### ✅ 42. AWS 비용은 EC2 요금만 발생하는 것이 아니다

현재 기술 환경에서 확인할 수 있는 주요 비용 항목은 다음과 같다.

| 서비스 | 주요 비용 발생 항목 |
|---|---|
| EC2 | 인스턴스 실행시간, 구매 옵션 |
| EBS | 볼륨 용량, IOPS, 처리량, Snapshot |
| RDS | DB 인스턴스, Storage, Backup, I/O 관련 항목 |
| S3 | 저장 용량, 요청, 데이터 검색 및 전송 |
| CloudFront | 요청, 데이터 전송, 선택한 요금제 및 기능 |
| CloudWatch | 로그 수집·보관·조회, Metric, Alarm |
| VPC | NAT Gateway, Public IPv4 등 |
| Route 53 | Hosted Zone, DNS Query |
| ELB | Load Balancer 사용시간 및 처리량 |

실제 사용 여부와 요금 구조는 현재 AWS 계정을 확인해야 한다.

### ✅ 43. 중요한 점

EC2 비용을 줄였더라도 CloudWatch 로그나 데이터 전송 비용이 증가할 수 있다.

### ✅ 44. 예시

```text
EC2 비용:
감소

CloudWatch Logs:
증가

CloudFront Data Transfer:
증가

전체 AWS 비용:
증가
```

### ✅ 45. 따라서

개별 서비스 비용과 전체 인프라 비용을 함께 확인한다.

### ✅ 46. 중요한 원칙

**비용 최적화는 특정 AWS 서비스 하나의 비용을 줄이는 것에서 끝나지 않고 전체 시스템의 비용 변화를 평가해야 한다.**

## 7. Fixed Cost와 Variable Cost

### ✅ 47. Fixed Cost

업무 요청량이 달라지더라도 일정한 기간 동안 비교적 고정적으로 발생하는 비용이다.

### ✅ 48. 예시

```text
항상 실행 중인 EC2

Provisioned RDS Instance

기본 EBS Storage
```

실제 비용은 사용 시간과 구매 방식, 추가 설정에 따라 달라질 수 있다.

### ✅ 49. Variable Cost

실제 사용량에 따라 변화하는 비용이다.

### ✅ 50. 예시

```text
CloudFront Requests

Data Transfer

S3 Requests

CloudWatch Log Ingestion

일부 Database I/O
```

### ✅ 51. 중요한 특징

온라인 판매몰의 월 방문자 수가 두 배 증가하더라도 모든 AWS 비용이 두 배로 증가하지는 않는다.

### ✅ 52. 가상의 예시

```text
고정 성격 비용:
$200

변동 성격 비용:
$50

전체 비용:
$250
```

트래픽 증가로 변동 성격 비용만 두 배가 된다면:

```text
고정 성격 비용:
$200

변동 성격 비용:
$100

전체 비용:
$300
```

### ✅ 53. 중요한 한계

트래픽 증가로 EC2나 RDS 증설이 필요해지면 고정 성격 비용도 단계적으로 증가할 수 있다.

### ✅ 54. 중요한 원칙

**트래픽 증가에 따른 비용을 예측할 때는 사용량에 직접 비례하는 비용과 인프라 증설 시 증가하는 비용을 구분한다.**

## 9. AWS 비용 Metric의 차이

### ✅ 61. Unblended Cost

개별 사용량의 비혼합 요율을 기반으로 비용을 분석할 때 활용할 수 있다.

### ✅ 62. Net Unblended Cost

적용된 할인 등을 반영한 비혼합 비용을 확인하는 데 활용할 수 있다.

### ✅ 63. Amortized Cost

Reserved Instance 또는 Savings Plans 등의 약정 비용을 관련 기간에 배분해 분석하는 데 활용할 수 있다.

### ✅ 64. Net Amortized Cost

상각된 약정 비용과 관련 할인 등을 함께 반영한 비용 관점이다.

### ✅ 65. 중요한 차이

같은 AWS 계정과 같은 날짜 범위를 조회해도 선택한 비용 Metric에 따라 금액이 달라질 수 있다.

### ✅ 66. 예시

Reserved Instance 선결제 비용이 특정 달에 발생했다.

실제 현금 지출 관점과 해당 약정을 사용하는 기간별 자원 비용 관점은 다를 수 있다.

### ✅ 67. 현재 추천

```text
회사 청구액 확인:
실제 Invoice 및 청구 항목 기준

서비스별 경제적 비용:
일관된 Amortized 또는 Net Amortized 기준

월별 추세:
동일 Metric을 유지해 비교
```

### ✅ 68. 추가 확인

세금·환불·크레딧·Support 비용 등을 포함하는지 보고서에 명시한다.

### ✅ 69. 중요한 원칙

## 11. AWS CLI로 비용 조회하기

### ✅ 77. Cost Explorer API

### ✅ 78. 인증 환경

현재 사용 중인 AWS IAM Identity Center 기반 Profile을 재사용할 수 있다.

단, 기존 개발 Profile에 Billing 조회 권한이 있다고 가정하면 안 된다.


### ✅ 80. 중요한 주의

### ✅ 81. 지난달 서비스별 비용 조회 예시

```bash
aws ce get-cost-and-usage \
  --profile togethermall-dev \
  --region us-east-1 \
  --time-period Start=2026-10-01,End=2026-11-01 \
  --granularity MONTHLY \
  --metrics UnblendedCost \
  --group-by Type=DIMENSION,Key=SERVICE \
  --output json
```

Cost Explorer API의 Start 날짜는 포함되지만 End 날짜는 포함되지 않는다.

### ✅ 83. 권한 문제

Cost Explorer에 접근하려면 실제 계정과 Billing 정책에 따라 `ce:GetCostAndUsage` 등의 권한이 필요하다.

### ✅ 84. API 비용

Cost Explorer API 요청에는 별도 요금이 발생할 수 있으므로 매초 또는 매분 반복 조회하는 구조는 피한다.

### ✅ 85. 중요한 원칙

**AWS 비용 조회 자동화는 읽기 전용 권한을 사용하고 API 호출 빈도와 조회 비용도 함께 관리한다.**

## 12. 비용 데이터 자동 수집

### ✅ 86. 목표

매일 또는 매주 서비스별 비용을 수집해 비용 추세를 분석한다.

### ✅ 87. 필요한 패키지 후보

Node.js 기반 AWS SDK v3를 활용할 수 있다.

```bash
pnpm add @aws-sdk/client-cost-explorer
```

실제 Workspace와 기존 AWS SDK 사용 여부를 확인한 뒤 설치한다.

### ✅ 88. 비용 조회 코드 예시

```typescript
import {
  CostExplorerClient,
  GetCostAndUsageCommand,
} from '@aws-sdk/client-cost-explorer';

const client = new CostExplorerClient({
  region: 'us-east-1',

  maxAttempts: 3,
});

interface CostRow {
  periodStart: string;

  periodEnd: string;

  service: string;

  amount: string;

  currency: string;

  estimated: boolean | null;
}

export async function fetchDailyCosts(
  start: string,

  end: string,
): Promise<CostRow[]> {
  const rows: CostRow[] = [];

  let nextPageToken:
    string | undefined;

  do {
    const result = await client.send(
      new GetCostAndUsageCommand({
        TimePeriod: {
          Start: start,

          End: end,
        },

        Granularity: 'DAILY',

        Metrics: [
          'UnblendedCost',
        ],

        GroupBy: [
          {
            Type: 'DIMENSION',

            Key: 'SERVICE',
          },
        ],

        NextPageToken:
          nextPageToken,
      }),
    );

    for (
      const period of
        result.ResultsByTime ?? []
    ) {
      for (
        const group of
          period.Groups ?? []
      ) {
        const metric =
          group.Metrics?.UnblendedCost;

        const service =
          group.Keys?.[0];

        if (
          !metric?.Amount ||
          !metric.Unit ||
          !service ||
          !period.TimePeriod?.Start ||
          !period.TimePeriod?.End
        ) {
          throw new Error(
            'INVALID_COST_EXPLORER_RESULT',
          );
        }

        rows.push({
          periodStart:
            period.TimePeriod.Start,

          periodEnd:
            period.TimePeriod.End,

          service,

          amount:
            metric.Amount,

          currency:
            metric.Unit,

          estimated:
            period.Estimated ?? null,
        });
      }
    }

    nextPageToken =
      result.NextPageToken;
  } while (nextPageToken);

  return rows;
}
```

### ✅ 89. 주요 특징

API 응답의 비용 금액을 문자열로 유지한다.

Pagination Token이 존재하면 다음 페이지까지 조회한다.

### ✅ 90. 중요한 이유

비용 데이터는 소수점 아래 여러 자리까지 제공될 수 있다.

JavaScript의 부동소수점 `number`만 사용해 정밀한 정산을 수행하면 오차가 발생할 수 있다.

### ✅ 91. 권장

```text
Raw Amount:
Decimal String

Financial Calculation:
Decimal Library 또는 PostgreSQL NUMERIC

Display:
보고서 표시 기준에 맞춰 반올림
```

### ✅ 92. 실제 구현 시 추가할 것

```text
Date Range Validation

Maximum Query Window

API Failure Handling

Account Scope

Cost Metric

Currency Validation

Idempotent Storage
```

### ✅ 93. 중요한 원칙

**비용 수집 자동화는 금액의 정밀도와 Pagination, 계정 범위, 추정 데이터 상태를 정확하게 관리해야 한다.**

## 13. AWS 비용 데이터를 저장하는 구조

### ✅ 94. 처음부터 별도의 DB가 필요할까?

아니다.

초기에는 월별 CSV 또는 JSON 결과를 보관하는 방식으로도 충분하다.

### ✅ 95. 자동 분석이 필요해진다면

PostgreSQL에 일별 비용 Snapshot을 저장할 수 있다.

### ✅ 96. 테이블 예시

```sql
CREATE TABLE cloud_cost_daily_snapshots (
  id BIGINT GENERATED ALWAYS
    AS IDENTITY PRIMARY KEY,

  account_scope TEXT NOT NULL,

  usage_date DATE NOT NULL,

  service_name TEXT NOT NULL,

  cost_metric TEXT NOT NULL,

  currency CHAR(3) NOT NULL,

  amount NUMERIC(24, 12) NOT NULL,

  is_estimated BOOLEAN,

  collected_at TIMESTAMPTZ
    NOT NULL DEFAULT NOW(),

  UNIQUE (
    account_scope,
    usage_date,
    service_name,
    cost_metric,
    currency
  )
);
```

### ✅ 97. 중요한 점

환불과 크레딧 등으로 비용이 음수가 될 수 있다.

따라서 모든 비용 금액에 `amount >= 0` 제약을 무조건 추가하지 않는다.

### ✅ 98. Upsert 예시

```sql
INSERT INTO cloud_cost_daily_snapshots (
  account_scope,

  usage_date,

  service_name,

  cost_metric,

  currency,

  amount,

  is_estimated
)
VALUES (
  $1,
  $2,
  $3,
  $4,
  $5,
  $6,
  $7
)

ON CONFLICT (
  account_scope,
  usage_date,
  service_name,
  cost_metric,
  currency
)
DO UPDATE SET

  amount = EXCLUDED.amount,

  is_estimated =
    EXCLUDED.is_estimated,

  collected_at = NOW();
```

### ✅ 99. 왜 Upsert가 필요할까?

AWS 비용 데이터가 이후에 변경되거나 지연 반영될 수 있기 때문이다.

### ✅ 100. 중요한 한계

위 테이블은 날짜별 최신 비용 값을 유지한다.

이전 수집 결과까지 모두 감사 이력으로 보존하려면 별도의 수집 이력 테이블이 필요하다.

### ✅ 101. 중요한 원칙

**비용 데이터는 한 번 수집한 값을 영구적으로 확정하는 방식이 아니라 필요에 따라 다시 조회하고 정합성을 맞출 수 있어야 한다.**

## 14. AWS Budgets

### ✅ 102. AWS Budgets

예상 비용과 실제 비용이 설정한 예산에 접근하거나 초과할 때 알림을 받을 수 있는 도구다.

### ✅ 103. 가상의 예산 정책

```text
Monthly Budget:
$300
```

알림 기준:

```text
Actual Cost 70%

Actual Cost 90%

Actual Cost 100%

Forecasted Cost 100%
```

### ✅ 104. 의미

비용이 실제 예산을 초과하기 전에 대응할 수 있도록 준비한다.

### ✅ 105. 중요한 차이

일반적인 Cost Budget 알림은 결제 차단 기능이 아니다.

### ✅ 106. 예시

```text
예산:
$300

실제 비용:
$320

알림:
발송
```

알림이 발송됐더라도 EC2나 RDS가 계속 실행되면 비용은 계속 발생할 수 있다.

### ✅ 107. Budget Actions

별도의 권한과 설정을 사용해 특정 조치를 수행하도록 구성할 수 있는 기능도 있다.

### ✅ 108. 그러나 현재 추천

Production EC2 또는 RDS를 예산 초과만으로 자동 중단하는 정책은 사용하지 않는다.

### ✅ 109. 중요한 원칙

**AWS Budgets는 비용 위험을 발견하는 수단이며 운영 서비스 중단 여부는 별도의 업무 영향 평가와 승인 절차를 통해 결정한다.**

## 16. Cost Allocation Tags

### ✅ 117. Cost Allocation Tag

AWS 자원이 어떤 프로젝트·서비스·환경에 사용되는지 비용 분석에 활용하기 위한 태그다.

### ✅ 118. 현재 투게더몰에 적용할 수 있는 Tag

```text
Project = togethermall

Environment = production

Component = backend

CostCenter = online-sales

ManagedBy = engineering
```

### ✅ 119. 통신 3사 확장을 고려한 태그

```text
Project = telecom-commerce

Brand = lgu-store

Environment = production

Component = frontend

CostScope = dedicated
```

### ✅ 120. 공통 Backend

```text
Project = telecom-commerce

Brand = shared

Environment = production

Component = backend

CostScope = shared
```

### ✅ 121. 중요한 조건

AWS 자원에 태그를 추가했다고 비용 분석에 즉시 나타나는 것은 아니다.

Billing의 Cost Allocation Tags에서 필요한 Tag Key를 활성화해야 한다.

### ✅ 122. 과거 데이터

AWS는 조건에 따라 과거 Cost Allocation Tag 상태를 Backfill할 수 있는 기능을 제공한다.

하지만 당시 자원에 존재하지 않았던 태그의 과거 값을 자동으로 만들어 주는 것은 아니다.

### ✅ 123. 중요한 원칙

**비용 태그는 신규 AWS 자원을 생성할 때부터 일관된 규칙으로 관리해야 한다.**

## 17. Tagging Convention

```text

Production

PROD
```

### ✅ 127. 권장

허용 값과 대소문자 규칙을 통일한다.

### ✅ 130. 따라서

분류되지 않은 비용을 별도의 `UNALLOCATED` 항목으로 관리한다.

### ✅ 131. 중요한 원칙

**태그는 비용을 설명하기 위한 표준 식별 체계이며 분류되지 않은 비용을 임의의 브랜드에 배정하지 않는다.**

## 18. 통신 3사 홈페이지의 비용 구조

### ✅ 132. 현재 확장 방향

기존 LG U+ 판매몰 외에 SKT와 KT 홈페이지가 추가되는 상황을 고려한다.

### ✅ 133. 아키텍처 후보 A — 완전 분리

```text
LGU Frontend
       ↓
LGU Backend
       ↓
LGU Database
```

```text
SKT Frontend
       ↓
SKT Backend
       ↓
SKT Database
```

```text
KT Frontend
       ↓
KT Backend
       ↓
KT Database
```

### ✅ 134. 장점

서비스별 비용과 장애 영향 범위를 구분하기 쉬울 수 있다.

### ✅ 135. 단점

EC2·RDS·배포·모니터링 등의 운영 부담이 증가할 수 있다.

### ✅ 136. 아키텍처 후보 B — 공유 인프라

```text
LGU Frontend ─┐

SKT Frontend ─┼── Shared Backend
              │         ↓
KT Frontend ──┘   Shared Database
```

### ✅ 137. 장점

중복 인프라를 줄일 수 있다.

### ✅ 138. 단점

한 서비스의 과부하가 다른 서비스에 영향을 줄 수 있다.

또한 테넌트 및 브랜드별 데이터 접근 경계를 엄격하게 검증해야 한다.

### ✅ 139. 비교

| 항목 | 완전 분리 | 공유 인프라 |
|---|---|---|
| 기본 인프라 비용 | 상대적으로 높을 수 있음 | 절감 가능 |
| 운영 복잡도 | 높아질 수 있음 | 공통 관리 가능 |
| 장애 격리 | 비교적 유리 | 별도 제한 정책 필요 |
| 비용 구분 | 비교적 단순 | 배분 정책 필요 |
| 보안 경계 | 물리적·논리적 분리 가능 | 논리적 격리 중요 |

### ✅ 140. 중요한 원칙

**공유 인프라가 저렴하다는 이유만으로 고객정보·관리자 권한·통신사별 가격 정책의 분리를 희생하지 않는다.**

## 19. Dedicated Cost와 Shared Cost

### ✅ 141. Dedicated Cost

특정 서비스에 직접 귀속할 수 있는 비용이다.

### ✅ 142. 예시

```text
LGU CloudFront Distribution

SKT S3 Bucket

KT Dedicated Database

특정 브랜드 Domain
```

### ✅ 143. Shared Cost

여러 서비스가 공동으로 사용하는 인프라 비용이다.

### ✅ 144. 예시

```text
공통 Backend EC2

공통 RDS

공통 관리자 시스템

공통 CloudWatch

공통 CI/CD 인프라
```

### ✅ 145. 중요한 문제

공유 EC2를 사용한다면 각 브랜드가 실제로 얼마의 비용을 사용하고 있는지 직접적인 AWS 청구 항목만으로 구분하기 어려울 수 있다.

### ✅ 146. 따라서

비용 배분 정책을 정의한다.

### ✅ 147. 중요한 원칙

**직접 귀속 가능한 비용과 내부 정책을 통해 배분한 비용을 서로 다른 항목으로 관리한다.**

## 20. Shared Infrastructure Cost Allocation

### ✅ 148. 비용 배분 방법

대표적인 후보는 다음과 같다.

```text
Even Split

Request-based Allocation

Order-based Allocation

Resource-based Allocation

Hybrid Allocation
```

### ✅ 149. Even Split

공통 비용을 각 브랜드에 균등하게 나눈다.

### ✅ 150. Request-based Allocation

각 브랜드의 Backend 요청 비중을 기준으로 배분한다.

### ✅ 151. Order-based Allocation

실제 신청 또는 주문 처리량을 기준으로 배분한다.

### ✅ 152. Resource-based Allocation

CPU·DB Query·Storage·Data Transfer 등 실제 자원 사용량과 관련된 근거를 이용한다.

### ✅ 153. 가상의 공통 비용

```text
Shared Backend + Database:
$300 / Month
```

브랜드별 사용 비중:

```text
LGU:
50%

SKT:
30%

KT:
20%
```

### ✅ 154. 배분 결과

| Brand | Shared Cost |
|---|---:|
| LGU | $150 |
| SKT | $90 |
| KT | $60 |
| 합계 | $300 |

### ✅ 155. 중요한 한계

요청 비중이 50%라고 실제 CPU와 DB 자원도 정확히 50% 사용했다고 볼 수는 없다.

### ✅ 156. AWS Cost Categories

Cost Categories의 Split Charge 기능으로 공통 비용 배분을 검토할 수 있다.

다만 해당 배분 결과가 모든 AWS 비용 데이터 내보내기와 Cost Explorer에 동일하게 적용된다고 가정하면 안 된다.

내부 보고서에서 필요한 배분 결과는 별도로 관리해야 할 수 있다.

### ✅ 157. 중요한 원칙

**Shared Cost 배분은 실제 개별 서비스 청구액이 아니라 명시적인 기준에 따른 내부 비용 계산임을 기록한다.**

## 21. Unit Economics란?

### ✅ 158. 정의

하나의 업무 단위가 발생할 때 필요한 비용과 해당 업무가 만들어 내는 가치를 분석하는 개념이다.

### ✅ 159. Cloud Unit Economics

클라우드 비용을 실제 처리한 업무량과 연결해 자원 효율성을 평가할 수 있다.

### ✅ 160. 온라인 휴대폰 판매몰의 업무 단위

```text
Page View

API Request

Product Detail View

Valid Application Attempt

Confirmed Application

Confirmed Order

Activated Order
```

### ✅ 161. 가장 중요한 점

업무 단위마다 의미가 다르다.

### ✅ 162. 예를 들어

신청서 제출과 실제 휴대폰 개통 완료는 같은 사건이 아니다.

```text
신청

↓

상담

↓

조건 확인

↓

주문 진행

↓

개통
```

### ✅ 163. 따라서

어느 단계의 처리 비용을 계산할 것인지 명확하게 정의한다.

### ✅ 164. 중요한 원칙

**클라우드 비용을 사업 지표와 연결할 때는 실제 업무 완료의 정의가 먼저 확립돼야 한다.**

## 22. Cost per Request

### ✅ 165. 기본 공식

```text
Cost per Request

=

해당 기간의 인프라 비용
────────────────────
해당 기간의 유효 요청 수
```

### ✅ 166. 가상의 예시

```text
Monthly Infrastructure Cost:
$300

Valid API Requests:
1,000,000
```

### ✅ 167. 계산

```text
$300 ÷ 1,000,000

= $0.0003 / Request
```

### ✅ 168. 요청 1,000건당 비용

```text
$0.0003 × 1,000

= $0.30
```

### ✅ 169. 중요한 한계

모든 API 요청의 처리 비용은 동일하지 않다.

### ✅ 170. 예시

```text
Health Check:
매우 가벼운 요청

상품 상세:
여러 DB Query

Excel Export:
대규모 CPU / Memory 사용
```

### ✅ 171. 따라서

전체 요청당 비용은 거시적인 효율성 지표로 사용한다.

필요하다면 Operation별 자원 사용량을 추가로 분석한다.

### ✅ 172. 중요한 원칙

**Cost per Request는 개별 요청의 정확한 원가라기보다 일정 기간의 전체 인프라 효율성을 비교하는 평균 지표다.**

## 23. Cost per Application

### ✅ 173. 실제 업무 중심 지표

온라인 판매몰에서는 고객 신청이 주요 업무 결과 중 하나다.

### ✅ 174. 공식

```text
Cost per Application

=

신청 업무에 배정된 인프라 비용
────────────────────────
실제 유효 신청 완료 건수
```

### ✅ 175. 가상의 예시

```text
Monthly Infrastructure Cost:
$300

Confirmed Applications:
1,500
```

모든 해당 비용을 신청 성과와 연결해 평가한다고 가정한다.

### ✅ 176. 계산

```text
$300 ÷ 1,500

= $0.20 / Application
```

### ✅ 177. 다음 달

```text
Infrastructure Cost:
$360

Confirmed Applications:
2,400
```

### ✅ 178. 계산

```text
$360 ÷ 2,400

= $0.15 / Application
```

### ✅ 179. 결과

| 항목 | 기존 | 변경 후 |
|---|---:|---:|
| AWS 비용 | $300 | $360 |
| 신청 완료 | 1,500건 | 2,400건 |
| 신청당 비용 | $0.20 | $0.15 |

### ✅ 180. 중요한 해석

AWS 비용은 20% 증가했지만 신청 건당 인프라 비용은 25% 감소했다.

### ✅ 181. 따라서

전체 청구액이 증가했다고 비용 효율성이 악화됐다고 단정할 수 없다.

### ✅ 182. 중요한 원칙

**비용의 증가 여부뿐 아니라 실제 업무 처리량 대비 비용이 어떻게 변화했는지 확인해야 한다.**

## 24. Cost per Order와 Cost per Activation

### ✅ 183. 신청 완료 이후의 업무

고객 신청이 실제 판매와 개통으로 이어지는 과정도 구분할 수 있다.

### ✅ 184. 가상의 예시

```text
Infrastructure Cost:
$300

Applications:
1,500

Confirmed Orders:
600

Activations:
500
```

### ✅ 185. 업무 단위별 비용

| Metric | 결과 |
|---|---:|
| 신청당 인프라 비용 | $0.20 |
| 주문당 인프라 비용 | $0.50 |
| 개통당 인프라 비용 | $0.60 |

### ✅ 186. 중요한 주의

위 비용은 동일한 전체 비용을 서로 다른 업무량으로 나눈 지표다.

세 지표를 모두 더해 새로운 총비용을 계산하면 안 된다.

### ✅ 187. Cohort 문제

10월에 신청한 고객이 11월에 개통할 수 있다.

### ✅ 188. 따라서

두 가지 분석 방식이 가능하다.

```text
Period-based:

해당 월의 비용 /
해당 월에 발생한 개통 완료 건수
```

```text
Cohort-based:

특정 신청 집단에 연결된 비용 /
해당 집단의 최종 개통 완료 건수
```

### ✅ 189. 중요한 차이

Period-based 분석은 월별 운영 효율성을 관리하기 좋다.

Cohort-based 분석은 특정 광고 캠페인이나 신청 집단의 최종 성과를 조사하는 데 적합할 수 있다.

### ✅ 190. 중요한 원칙

**신청·주문·개통이 서로 다른 기간에 발생할 수 있으므로 비용과 업무량을 연결할 때 기간과 Cohort 정의를 명확하게 유지한다.**

## 26. Unit Economics 계산 자동화

### ✅ 198. 필요한 입력값

```text
Cost Amount

Currency

Cost Period

Cost Scope

Business Unit Count

Business Unit Definition
```

### ✅ 199. 정밀한 계산

금액 계산에는 Decimal 연산을 활용할 수 있다.

```bash
pnpm add decimal.js
```

실제 프로젝트에 이미 Decimal 연산 도구가 있다면 재사용하는 것이 적절하다.

### ✅ 200. TypeScript 예시

```typescript
import Decimal from 'decimal.js';

interface UnitCostInput {
  costAmount: string;

  currency: string;

  completedUnits: number;
}

type UnitCostResult =
  | {
      status: 'CALCULATED';

      costPerUnit: string;

      currency: string;

      completedUnits: number;
    }
  | {
      status: 'NOT_AVAILABLE';

      reason: string;
    };

export function calculateUnitCost(
  input: UnitCostInput,
): UnitCostResult {
  if (
    !Number.isSafeInteger(
      input.completedUnits,
    ) ||
    input.completedUnits < 0
  ) {
    throw new Error(
      'INVALID_COMPLETED_UNITS',
    );
  }

  if (input.completedUnits === 0) {
    return {
      status: 'NOT_AVAILABLE',

      reason: 'NO_COMPLETED_UNITS',
    };
  }

  const cost = new Decimal(
    input.costAmount,
  );

  if (!cost.isFinite()) {
    throw new Error(
      'INVALID_COST_AMOUNT',
    );
  }

  return {
    status: 'CALCULATED',

    costPerUnit:
      cost
        .div(input.completedUnits)
        .toFixed(8),

    currency:
      input.currency,

    completedUnits:
      input.completedUnits,
  };
}
```

### ✅ 201. 실행 예시

```typescript
const result = calculateUnitCost({
  costAmount: '300.00',

  currency: 'USD',

  completedUnits: 1500,
});

console.log(result);
```

예상 결과:

```json
{
  "status": "CALCULATED",
  "costPerUnit": "0.20000000",
  "currency": "USD",
  "completedUnits": 1500
}
```

### ✅ 202. 중요한 점

신청 건수가 0인 경우 신청당 비용을 0으로 반환하면 안 된다.

비용은 발생했지만 계산할 업무 단위가 없는 상태일 수 있기 때문이다.

### ✅ 203. 실제 구현 시 추가할 것

```text
Cost Period Validation

Currency Consistency

Cost Metric Consistency

Business Count Evidence

Allocation Policy Version

Provisional Billing Status
```

### ✅ 204. 중요한 원칙

**업무량이 없거나 비용 데이터가 유효하지 않은 상황을 정상적인 비용 계산 결과로 위장하지 않는다.**

## 27. PostgreSQL 기반 비용 효율성 분석

### ✅ 205. 업무량 테이블 예시

실제 주문 및 신청 데이터에서 계산한 일별 집계 결과를 저장한다고 가정한다.

```sql
CREATE TABLE business_volume_daily (
  business_date DATE NOT NULL,

  brand_key TEXT NOT NULL,

  confirmed_applications BIGINT NOT NULL
    CHECK (confirmed_applications >= 0),

  confirmed_orders BIGINT NOT NULL
    CHECK (confirmed_orders >= 0),

  PRIMARY KEY (
    business_date,
    brand_key
  )
);
```

### ✅ 206. 배분된 비용 테이블

```sql
CREATE TABLE allocated_cloud_cost_daily (
  usage_date DATE NOT NULL,

  brand_key TEXT NOT NULL,

  currency CHAR(3) NOT NULL,

  cost_metric TEXT NOT NULL,

  allocated_amount NUMERIC(24, 12)
    NOT NULL,

  allocation_policy_version TEXT
    NOT NULL,

  PRIMARY KEY (
    usage_date,
    brand_key,
    currency,
    cost_metric,
    allocation_policy_version
  )
);
```

### ✅ 207. 월별 신청당 비용 조회

```sql
WITH monthly_cost AS (
  SELECT
    brand_key,

    SUM(allocated_amount)
      AS total_cost

  FROM allocated_cloud_cost_daily

  WHERE usage_date >= DATE '2026-10-01'

    AND usage_date < DATE '2026-11-01'

    AND currency = 'USD'

    AND cost_metric = 'UnblendedCost'

    AND allocation_policy_version = 'v1'

  GROUP BY brand_key
),

monthly_volume AS (
  SELECT
    brand_key,

    SUM(confirmed_applications)
      AS applications,

    SUM(confirmed_orders)
      AS orders

  FROM business_volume_daily

  WHERE business_date >= DATE '2026-10-01'

    AND business_date < DATE '2026-11-01'

  GROUP BY brand_key
)

SELECT
  c.brand_key,

  c.total_cost,

  v.applications,

  v.orders,

  ROUND(
    c.total_cost /
    NULLIF(v.applications, 0),

    6
  ) AS cost_per_application,

  ROUND(
    c.total_cost /
    NULLIF(v.orders, 0),

    6
  ) AS cost_per_order

FROM monthly_cost AS c

JOIN monthly_volume AS v
  ON c.brand_key = v.brand_key

ORDER BY c.brand_key;
```

### ✅ 208. 중요한 특징

비용과 업무량을 각각 먼저 집계한 뒤 연결한다.

### ✅ 209. 왜 그럴까?

원본 비용 Row와 원본 주문 Row를 직접 Join하면 여러 행이 중복 연결돼 비용 또는 주문 건수가 과대 집계될 수 있기 때문이다.

### ✅ 210. 중요한 한계

위 Query는 두 집계에 모두 존재하는 브랜드만 반환한다.

비용만 있고 신청 데이터가 없는 브랜드도 보고해야 한다면 `FULL OUTER JOIN` 등의 구조로 누락을 별도 표시해야 한다.

### ✅ 211. 날짜 기준

AWS Billing의 일별 집계 경계와 한국 시간 기준 업무 집계 경계가 다를 수 있다.

### ✅ 212. 따라서

일별 비교에서는 UTC와 KST 차이를 명확하게 처리하고 월별 보고서에서도 기간 정의를 일관되게 유지한다.

### ✅ 213. 중요한 원칙

**비용과 사업 데이터를 연결할 때 Join 중복·누락·시간대 차이·비용 배분 정책을 검증해야 한다.**

## 28. EC2 Right-sizing

### ✅ 214. 정의

실제 Workload에 필요한 CPU·메모리·네트워크·스토리지 성능을 고려해 적절한 EC2 Instance Type을 선택하는 과정이다.

### ✅ 215. 현재 EC2가 과도하게 큰 경우

자원 대부분을 사용하지 않으면서 불필요한 비용을 지출할 수 있다.

### ✅ 216. 반대로 너무 작은 경우

```text
CPU Saturation

Memory Pressure

OOM

Slow API

Deployment Failure
```

등의 문제가 발생할 수 있다.

### ✅ 217. 필요한 관측 데이터

```text
CPU Average

CPU Peak

CPU Percentile

Memory Usage

Network Throughput

EBS I/O

Event Loop Delay

API p95 / Error Rate
```

### ✅ 218. 중요한 점

EC2 기본 CloudWatch Metric만으로 운영체제의 메모리 사용량을 항상 확인할 수 있는 것은 아니다.

CloudWatch Agent 또는 기존 모니터링을 활용해야 할 수 있다.

### ✅ 219. Burst 가능 인스턴스

T 계열처럼 CPU Credit을 사용하는 Instance를 운영한다면 평균 CPU뿐 아니라 Credit 잔량과 사용 특성도 확인한다.

### ✅ 220. 중요한 원칙

**EC2 Right-sizing은 CPU 평균 하나를 근거로 서버 사양을 낮추는 작업이 아니라 실제 Peak와 업무 성능 목표를 만족하는 최소 자원 수준을 찾는 과정이다.**

## 29. AWS Compute Optimizer

### ✅ 221. Compute Optimizer

기존 자원 구성과 사용량 Metric을 분석해 적절한 자원 사양이나 비용 최적화 후보를 추천하는 AWS 서비스다.

### ✅ 222. 활용 대상

실제 지원 범위와 설정에 따라 다음 자원 등을 분석할 수 있다.

```text
EC2
```

## 35. CloudWatch Log Volume 계산

### ✅ 264. 가상의 요청량

```text

100,000

5

Average Event Size:
1KiB
```

### ✅ 265. 하루 로그량

```text
100,000 × 5 × 1KiB

≈ 488MiB
```

### ✅ 266. 개선 후

평균 요청당 로그를 두 개로 줄였다고 가정한다.

```text
100,000 × 2 × 1KiB

≈ 195MiB
```

### ✅ 267. 의미

동일 요청량에서 이론적인 로그 데이터 크기가 감소한다.

### ✅ 268. 중요한 한계

이 계산은 설명용 데이터량 추정이다.

실제 청구량은 로그 구조·수집 방식·서비스 요금 체계와 기타 이벤트의 영향을 받는다.

### ✅ 269. 실제 확인할 것

CloudWatch Logs의 `IncomingBytes` 등의 Metric과 실제 Billing Usage Type을 비교한다.

### ✅ 270. 중요한 원칙

**로그 최적화의 효과는 예상 데이터량뿐 아니라 실제 수집량 및 청구 항목의 변화로 검증한다.**

## 39. CloudFront와 비용 효율성

### ✅ 292. CloudFront

정적 파일과 적절한 공개 콘텐츠를 Edge에서 제공해 Origin의 요청을 줄일 수 있다.

### ✅ 293. 현재 홈페이지에서의 주요 대상

```text

배너 이미지

공개 안내 콘텐츠
```

### ✅ 294. Cache Hit

CloudFront가 Origin을 호출하지 않고 Cache에서 콘텐츠를 제공할 수 있는 상황이다.

### ✅ 295. Cache Miss

Origin으로 요청이 전달될 수 있는 상황이다.

### ✅ 296. Cache Hit Ratio 개선 효과

```text
Origin 요청 감소

S3 GET 요청 감소 가능

Backend Origin 부하 감소 가능

응답시간 개선 가능
```

### ✅ 297. 중요한 주의

CloudFront에서 Cache Hit가 증가했다고 고객에게 전달하는 전체 데이터 전송량도 같은 비율로 줄어드는 것은 아니다.

### ✅ 298. 이유

Cache에서 제공된 이미지라도 실제 고객에게 전송되는 데이터는 존재하기 때문이다.

### ✅ 299. 중요한 원칙

**CloudFront 최적화에서는 Origin 부하 감소와 고객 방향 데이터 전송 비용을 서로 다른 항목으로 분석한다.**

### ✅ 319. 이유

### ✅ 320. 필요한 정책

```text
Active Release Assets

Previous Release Assets

Rollback Retention

Old Unreferenced Assets

Temporary Files
```

### ✅ 321. 중요한 원칙

**S3 비용을 줄이기 위해 기존 배포 Asset을 삭제할 때는 고객의 Chunk Load Failure와 Rollback 가능성을 함께 고려한다.**

## 43. S3 Lifecycle

### ✅ 322. S3 Lifecycle

객체의 보관 기간과 Storage Class 전환, 만료 등을 자동화할 수 있는 기능이다.

### ✅ 323. 적용 후보

```text
임시 Export 파일

오래된 테스트 Artifact

사용되지 않는 로그 파일

정책상 정리 가능한 이전 Version

오래된 분석 보고서
```

### ✅ 324. 위험한 방식

전체 Bucket에 일괄 만료 규칙을 설정하는 것이다.

### ✅ 325. 예시

```text
Rule:

모든 Object

30일 이후 삭제
```

이 규칙이 실제 상품 이미지나 운영 Frontend Asset까지 적용된다면 서비스 장애가 발생할 수 있다.

### ✅ 326. 권장

```text
Dedicated Prefix

Object Tag

Explicit Ownership

Retention Policy

Approved Lifecycle Scope
```

를 기준으로 적용 범위를 제한한다.

### ✅ 327. 중요한 원칙

**S3 Lifecycle은 삭제 권한을 가진 강력한 운영 정책이므로 실제 데이터 종류와 복구 요구사항을 확인한 뒤 적용한다.**

## 44. S3 Storage Class 선택

### ✅ 328. 무조건 저렴한 Storage Class로 이동하면 될까?

아니다.

### ✅ 329. 고려할 항목

```text
Access Frequency

Object Size

Retrieval Cost

Retrieval Time

Minimum Storage Duration

Transition Request Cost
```

### ✅ 330. 예시

자주 조회되는 휴대폰 상품 이미지를 보관 비용만 보고 장기 보관용 Storage Class로 이동하면 고객 이미지 로딩과 데이터 검색 비용에 영향을 줄 수 있다.

### ✅ 331. 작은 객체 문제

매우 작은 객체를 대량으로 다른 Storage Class로 전환하면 요청 비용이 저장 비용 절감 효과보다 클 수 있다.

### ✅ 332. 최소 보관 기간

일부 Storage Class에는 최소 보관 기간이 존재한다.

예를 들어 S3 Standard-IA는 30일, Glacier Deep Archive는 180일 등의 최소 보관 기간 요건을 고려해야 한다.

### ✅ 333. 중요한 원칙

**S3 Storage Class는 단순 GB당 가격이 아니라 전체 객체 수명주기의 예상 비용과 접근 요구사항을 기준으로 선택한다.**

### ✅ 350. 목적

### ✅ 351. Savings Plans

### ✅ 353. 중요한 위험

향후 서비스 구조나 자원 사양이 바뀌면 기존 약정을 충분히 사용하지 못할 수 있다.

### ✅ 354. 통신 3사 확장 상황

```text

↓

↓

↓

```

### ✅ 355. 따라서

신규 아키텍처가 확정되지 않은 상태에서 현재 인프라만 기준으로 장기 약정을 구매하는 것은 신중해야 한다.

### ✅ 356. 확인할 정보

```text
Usage Stability

Commitment Coverage

Commitment Utilization

Architecture Roadmap

Instance Migration Plan

Contract Term
```

### ✅ 357. 중요한 원칙

**장기 약정은 할인율만 보고 구매하지 않고 실제 장기 사용 가능성과 아키텍처 변경 계획을 함께 검토한다.**

## 50. Cost Optimization과 Reliability Trade-off

### ✅ 372. 비용과 안정성은 항상 같은 방향으로 움직일까?

아니다.

### ✅ 373. 예시

```text
EC2 Instance 축소
       ↓

       ↓
CPU Headroom 감소
       ↓

```

### ✅ 374. 또 다른 예시

```text
Backup Retention 축소
       ↓
Storage 비용 감소
       ↓
복구 가능한 기간 감소
```

### ✅ 375. 또 다른 예시

```text
Trace Sampling 축소
       ↓

       ↓

```

### ✅ 376. 따라서

비용 절감 후보를 평가할 때 다음 조건을 함께 확인한다.

```text

Security Impact

Recovery Impact

Business Impact

Operational Complexity
```

### ✅ 377. 중요한 원칙

**비용 절감으로 증가하는 장애 위험과 고객 피해 가능성을 평가하지 않으면 실제 사업 가치가 감소할 수 있다.**

## 51. Cost Optimization Decision Matrix

### ✅ 378. 가상의 개선 후보

| 개선안 | 예상 효과 | 주요 위험 |
|---|---|---|
| 반복 DB Query 감소 | CPU·DB 효율 개선 | 업무 결과 변경 |
| 불필요한 Debug Log 감소 | 로그 수집 비용 절감 | 진단 정보 부족 |
| 상품 이미지 압축 | 전송량 감소 | 이미지 품질 저하 |
| EC2 사양 축소 | 직접 비용 절감 | Peak 성능 저하 |
| RDS Storage 이전 | 장기 비용 개선 가능 | 마이그레이션 위험 |
| 백업 삭제 | 저장 비용 감소 | 복구 능력 저하 |

### ✅ 379. 현재 추천 순서

먼저 실제로 사용하지 않는 비용과 불필요한 자원 소비를 조사한다.

### ✅ 380. 그다음

업무 성능을 유지하면서 비용을 줄일 수 있는 코드·Query·이미지·로그 최적화를 수행한다.

### ✅ 381. 마지막

실제 Headroom이 확보된 경우 인프라 사양 변경을 검토한다.

### ✅ 382. 중요한 원칙

**큰 비용 절감 효과가 예상된다는 이유만으로 위험도가 높은 변경부터 실행하지 않는다.**

## 53. Estimated Savings와 Realized Savings

### ✅ 388. Estimated Savings

개선안을 적용하기 전에 계산한 예상 절감액이다.

### ✅ 389. Realized Savings

개선 이후 실제 비용 데이터를 근거로 확인한 절감 효과다.

### ✅ 390. 예시


```text
$70
```

### ✅ 392. 중요한 점

예상 절감액을 실제 절감액으로 보고하면 안 된다.

### ✅ 393. 비용 회피 — Cost Avoidance

서버를 증설해야 할 것으로 예상했지만 코드 최적화 덕분에 기존 자원으로 증가한 트래픽을 처리할 수 있었다.

이 경우 추가 비용을 피했을 가능성이 있다.

### ✅ 394. 중요한 제한

실제로 지출하지 않은 가상의 비용을 현재 청구액에서 감소한 비용과 동일하게 보고하지 않는다.

### ✅ 395. 추천 상태

```text

VALIDATION_PENDING

REALIZED

COST_AVOIDANCE_ESTIMATE

NOT_VERIFIED
```

### ✅ 396. 중요한 원칙

**예상 절감·실제 절감·비용 회피는 서로 다른 성과로 기록한다.**

### ✅ 434. 중요한 전제

### ✅ 435. 초기 추천

AWS Console에서 수행한 주요 인프라 변경을 기록하고 비용 검토가 필요한 변경에 승인 체크리스트를 적용한다.

### ✅ 436. 중요한 원칙

**Cost Gate는 실제 인프라 변경에 대한 예측과 검토를 수행하지만 추정 비용만으로 운영 안전성을 판단하지 않는다.**

## 📌 요약

1115에서는 애플리케이션 내부에서 CPU와 메모리를 소비하는 함수와 객체를 찾아 코드 수준의 최적화를 수행하는 방법을 다뤘다.

```text
Runtime Profiling
       ↓
CPU / Heap Analysis
       ↓
Function-level Bottleneck
       ↓
Code Optimization
       ↓
Re-profiling
```

1116에서는 이를 실제 AWS 운영 비용과 사업 성과로 연결했다.

```text
Application Performance
       ↓
Runtime Resource Usage
       ↓
AWS Cost Baseline
       ↓
Resource Cost Attribution
       ↓
Business Volume
       ↓
Unit Economics
       ↓
Optimization Candidates
       ↓
Cost / Reliability Trade-off
       ↓
Controlled Optimization
       ↓
Validated Savings
       ↓
Continuous FinOps Monitoring
```

이번 편에서 가장 중요한 원칙은 다음과 같다.

**첫 번째 — CPU 사용량 감소와 실제 AWS 비용 감소는 다르다.**

고정적으로 실행 중인 EC2나 RDS는 자원 사용량이 줄더라도 동일한 사양을 유지하면 비용이 그대로일 수 있다.

하지만 확보된 성능 여유를 통해 서버 증설을 피하거나 적절한 사양으로 전환할 수 있다.

**두 번째 — AWS 비용은 실제 업무량과 연결해야 한다.**

```text
Total Cost

+

Business Volume

=

Unit Economics Analysis
```

AWS 비용이 증가했더라도 신청 건당 비용이 감소했다면 효율성은 개선됐을 수 있다.

**세 번째 — Cost Explorer와 Budgets는 서로 다른 역할을 한다.**

Cost Explorer는 비용 분석에 활용한다.

Budgets는 예산 관련 위험을 확인하는 데 활용한다.

Cost Anomaly Detection은 비정상적인 지출 변화를 조사하는 데 활용한다.

일반적인 Budget Alert만으로 모든 추가 비용이 자동 차단되는 것은 아니다.

**네 번째 — Right-sizing은 실제 성능 근거를 기준으로 수행한다.**

```text
CPU

Memory

Database Connections

Network

Peak Traffic

Performance Budget
```

을 함께 고려해야 한다.

**다섯 번째 — 통신 3사 홈페이지의 비용 귀속을 명확하게 한다.**

```text
Dedicated Cost

+

Allocated Shared Cost

+

Unallocated Cost
```

구조를 통해 신규 브랜드와 공통 인프라의 비용을 구분할 수 있어야 한다.

**여섯 번째 — Observability도 운영 비용의 일부다.**

CloudWatch Logs·Custom Metrics·OpenTelemetry Trace는 서비스 안정성을 높이는 중요한 기능이다.

하지만 수집 범위와 데이터량이 지나치게 증가하지 않도록 관리해야 한다.

**일곱 번째 — 비용 최적화 때문에 복구 능력을 희생하지 않는다.**

Backup 삭제·RDS 축소·EC2 중지·S3 Lifecycle 변경은 실제 업무와 장애 복구 요구사항을 기준으로 검토한다.

**여덟 번째 — 예상 절감과 실제 절감을 구분한다.**

```text
Estimated Savings

Realized Savings

Cost Avoidance
```

는 서로 다른 성과다.

실제 비용 절감이라고 주장하려면 변경 이후 청구 데이터와 업무 지표를 확인해야 한다.

**아홉 번째 — AI는 비용 최적화의 의사결정을 지원한다.**

실제 비용 계산과 AWS 변경 권한은 검증 가능한 시스템과 승인 절차로 관리한다.

AI는 비용 증가 원인 후보와 개선 방향, 추가 검증 계획을 작성하는 데 활용한다.

현재 투게더몰에서 가장 현실적인 실행 순서는 다음과 같다.

```text
1. 최근 3개월 AWS 비용 확인

2. EC2 / RDS / S3 / CloudFront 비용 분리

3. AWS Budgets 및 비용 이상 알림 확인

4. 실제 AWS Resource Inventory 정리

5. CloudWatch Log Volume 조사

6. Prisma Query 및 CPU 병목 최적화

7. 상품 이미지 및 CloudFront 전송량 최적화

8. Cost Allocation Tag 정책 정의

9. 통신 3사 공통 비용 배분 설계

10. 신청 및 주문 건당 인프라 비용 계산

11. 실제 Capacity 근거 기반 Right-sizing

12. 비용 최적화 전후 Benchmark

13. 월별 FinOps Report 자동 생성

14. 필요한 경우 장기 구매 옵션 검토
```

특히 현재와 같은 1인 개발 환경에서는 처음부터 대규모 FinOps 플랫폼을 개발할 필요는 없다.

가장 먼저 필요한 것은 다음 연결 구조다.

```text
AWS Billing Data
       ↓
서비스별 비용
       ↓
실제 고객 신청 및 주문량
       ↓
업무당 인프라 비용
       ↓
성능 / 안정성 검증
       ↓
개선 효과 보고서
```

이 구조를 구축하면 단순히 회사에 AWS 비용을 줄였다고 보고하는 것을 넘어 다음과 같은 성과를 근거를 가지고 설명할 수 있다.

```text
불필요한 DB Query 감소

고객 신청 API 성능 유지

동일 서버에서 처리 가능한 업무량 증가

불필요한 로그 수집량 감소

상품 이미지 데이터 전송량 감소

신청 건당 인프라 비용 개선

추가 서버 증설 비용 회피

통신 3사 서비스의 비용 가시성 확보
```

또한 이러한 데이터는 기존 업무 성과 보고서와 경력기술서에도 활용할 수 있다.

단순히 React와 NestJS를 사용해 홈페이지를 개발했다는 설명보다, 실제 운영 서비스의 성능·안정성·인프라 비용을 분석하고 개선 효과를 검증했다는 경험이 더 구체적인 운영 역량을 보여 줄 수 있다.

최종적으로 기억해야 할 원칙은 다음과 같다.

**좋은 Cloud FinOps는 무조건 저렴한 서버를 사용하는 것이 아니다. 고객에게 필요한 성능과 신뢰성을 유지하면서 실제 업무 처리에 필요한 자원 사용량을 줄이고, 클라우드 비용을 사업 성과와 연결해 가장 합리적인 인프라 운영 결정을 내리는 과정이다.**
